# Copies, Inventory Lists & Detail Pages

Internal numbers, copy counts, grouping, duplicate detection, chips, and what a detail page is for.

- **Quick offer mode** (#537) is the Copies list's bulk-listing pass: the platform and the starting status are set once in a bar above the rows (`inventory/quick-offer-bar.tsx`) and every **Add to new offer** from then on — the row's `⋮` entry, its promoted icon and the selection bar's `New offer` buttons (#277/#497) — calls `createOfferAction` outright instead of opening `OfferFormDialog`. It goes **further than #234**, which pre-fills the dialog: pre-filling still leaves the dialog, and the dialog is the mouse trip. The offers carry **no price and no URL** deliberately — that is what makes it a bulk pass, and both land on the offer's own screen once the listing exists — so the catalog-value pre-fill (#230) is the ordinary flow's, not this one's. The bar **is** the mode's whole affordance and is why a silent create is safe: which platform, which status and how many offers the pass has made are impossible not to see, and a failure has nowhere else to be reported. It is therefore **not persisted**, unlike every other way of working this list remembers (`groupMode`, the split axes, the worklist platform): a mode that skips a confirmation must never be in force on a screen the collector has just opened. The `⋮` entry **renames itself** (`New offer on Colnect`, via `CopyRowActions.quickOffer`) rather than reading the same in both modes. A platform with **no `platformCurrency`** does not arm it — the currency is fixed at the platform on its first offer (#196) and that choice belongs in the create form, so the ordinary dialog stays in effect rather than the pass failing per click or quietly fixing a currency for good.

- A **copy's notes print in full under its row**, never behind a hover (#116). The chip they replaced (`notes`, with the text as its tooltip) was the one field on the row with no fixed vocabulary — a postmark type, why this copy was kept — and hiding what only the note can say behind a hover made it the one thing on the row that had to be hunted for, while every chip beside it says its piece outright. The line is drawn **only when there is a note**, so a list of copies without them keeps its height exactly — which is also why it is a line rather than a reserved area. It sits **inside the row's text column**, so it starts where the row's words do rather than under the photo, and it is `pre-wrap` and untruncated: a note typed as two lines reads as two, and a note clipped at a width is a tooltip again. Mirrors the auction lot row, which already printed `lot.notes` this way. Because `InventoryItemRow` is rendered from eight screens the line reaches all of them, which is right — a note is a fact about the copy, not about the list it is being read in.

- A copy's **internal number** (#268) is a per-collection sequence on `Item.itemNo`, unique with `collectionId`, assigned at creation and never editable. It is handed out by bumping `Collection.nextItemNo` in one `UPDATE ... RETURNING` (`allocateItemNumbers` in `src/lib/items.ts`, which takes a range for a bulk intake) — **never** `max(itemNo) + 1`: the number gets written on the physical piece, so a deleted copy must retire its number rather than pass it to the next one. Every `item.create*` site must supply it. Display and search parsing are pure in `src/lib/item-number.ts` (`formatItemNo` → `#00123`, zero-padded so a column lines up; `parseItemNoSearch` accepts `123` / `00123` / `#00123`). A numeric search matches the number **in addition to** the text search, never instead of it — `200` is also a plausible catalog number. It rides in the row's meta line and the Edit dialog's title, not in a form field: a permanently disabled input earns no space. How wide it renders is the collector's choice — `Collection.itemNoPad` (Settings → General), display-only, so changing it renumbers nothing and cannot break a search (leading zeros are insignificant to `parseItemNoSearch`). Client surfaces read it through `useCollectionItemNoPad`, a query rather than a prop, because `InventoryItemRow` is rendered from eight screens. In listing texts it is `{itemNo}` / `{itemNo:N}` (#268) — padded to the collection width, or to `N`; an unusable `N` falls back to the collection width rather than emptying the token, and **no `#` is added**, since a template is literal text. `TitleTemplateCopy` therefore carries `itemNo` *and* `itemNoPad`: collection-level data on a per-copy shape, because the pure engine has no other channel.

- The **short number** pattern is now every major entity's (#432), and the box that consumes them is #431. `Issue.issueNo`, `Purchase.purchaseNo`, `Sale.saleNo` and `AuctionLot.auctionLotNo` join `Item.itemNo` (#268) and `Offer.offerNo` (#416), each off its own `Collection.next<Entity>No` counter through one shared `allocateEntityNumber` (`src/lib/items.ts`) — the same atomic `UPDATE ... RETURNING`, never `max + 1`, because a number that has been quoted must not come to mean something else. One counter per entity rather than one shared sequence: a collector counts purchases and issues separately, and sharing would make every number jump for reasons nothing on screen explains. Every `create*` therefore runs **in a transaction** — `createPurchase`/`createSale`/`createAuctionLot` gained one for exactly this, so a failed create cannot burn a number. `AuctionLot` is the one without a unique index: a lot carries no `collectionId` (it reaches its collection through its sale), and denormalizing that would be a second answer to "which collection is this lot in" for the sake of a safety net the counter already provides; `auctionLotNo` is also deliberately **not** `lotNo`, which is the *house's* number — typed in, optional, repeating across sales, and the field an Allegro capture writes the offer id into (#355). `AuctionSale` gets no number: the lot is what one refers to, and it carries its sale's address. The numbers render through one `EntityNoChip` (unpadded — `Collection.itemNoPad` exists because a copy number goes on the physical piece and a column of stock cards has to line up; none of these do). The **box** is `parseQuickJump` in the pure `src/lib/quick-jump.ts` (prefix table: `i` `o` `p` `s` `iss` `lot`, longest-prefix-first so `iss12` is never `i` + `ss12`) plus `resolveQuickJump` in `quick-jump-server.ts` behind `GET /api/collections/[collectionId]/quick-jump`. It is a **jump, not a search**, and does nothing until Enter: a bare `200` is refused rather than guessed at, because it is as likely a catalog number, a year or a price. The slug in the returned href is read **server-side** off the authorized collection, never taken from the query — the answer is an address the browser is about to follow. Where each lands is a product decision stated in that module: copy and issue to their list filtered to the number (neither has a screen of its own), offer to the `/o/<slug>/<no>` redirect (#416) so a jump and a followed marketplace link are one journey, purchase/sale to their detail screens, and a lot to its **sale** with the lot highlighted (#374) — a lot is read in the company of its parcel.

- **Copies held per stamp** (#348) come from `src/lib/copy-counts.ts` — one `groupBy` over the disposition flags for a whole page of stamps, never a count per row — and render through the shared `CopyCountBadge` on every surface that lists a stamp (issue tree, flat list, pickers). Counted **per stamp exactly**, never rolled up from variant children (the tree shows the child's own badge one line down, so a rollup would show one copy twice), and **excluding sold copies**, because the badge sits beside *View copies* and must agree with what that popup lists (#207). The in-flight delivery states are deliberately *not* filtered — a copy in transit is bought — while the two exception outcomes (`UNAVAILABLE_DELIVERY_STATES`) and disposed-of copies are, since #396: the badge answers *how many of this do I have*. A stamp with none shows **nothing**, the same unmarked-default rule as the subtype chip and the single format. The disposition figures are markers that overlap (in collection *and* for sale), so they are listed in the tooltip, never summed. What the **variants** hold is the *second* number **inside the same chip** (#528, `countVariantDescendantCopies`, drawn as a muted parenthesised `3 (+2) copies` by the same `CopyCountBadge` — a second chip on a line that already carries catalog numbers, a Colnect link, a subtype and a price read as noise): copies of every descendant whose effective `actsAsVariant` is true, at any depth — ADR-0010 §3's rule as #101/#130's valuation and #238's price rollup apply it, so a distinct entry (error, plate flaw, overprint) is out while a variant filed *under* one is in. Two numbers, never one sum: they answer different questions, and the tree already draws each child's own badge one line down. Its totals come from `countCopiesByStamp` rather than a second `groupBy`, so "a copy you hold" cannot come to mean two things; `loadStampCopyCounts` is the one entry point loading the pair, because every surface showing one shows the other. It is the one thing that makes the badge show a **zero** — `0 (+2) copies`, when the stamp has no copies of its own, which is the ordinary shape of an unknown-variant umbrella whose copies are all filed under specific variants; the no-badge-for-none rule is untouched, since that row does hold something. The **intake step** states the same holding as a *line* rather than a chip (#562): picking a stamp into a purchase lot is where the keep-or-sell call is taken, and answering it meant leaving the dialog for Inventory several hundred times a parcel. It carries two axes the badge does not — the **conditions** those copies are in, and **where each copy is** (`countHeldCopyRowsByStamp`, one `groupBy` over condition, delivery state **and** the disposition flags at once, because a disposition figure taken over one set beside a condition figure taken over another is a sentence whose halves describe different copies; rolled up by the pure `summarizeHeldCopies` in `held-copies.ts`, which is a separate module precisely because `copy-counts.ts` is `server-only` and the line is drawn client-side). The **counting set is the badge's exactly** — one shared `heldCopiesWhere`, so what "held" means cannot drift between the axes — and what differs is the *sentence*: the headline counts **delivered copies only**, because a copy bought and not yet arrived is rightly counted by every figure in the app (ADR-0032 §7) and "you hold 1" is still the wrong thing to say about it. Two cases hit that on the first real parcel: an auction settlement creates the lot's identified copies `ordered` with every disposition flag false (`auctions.ts`), so the line read *1 with no disposition (MNH)* at a collector holding the only physical copy in tweezers; and the second copy from the stockbook being sorted right now, entered ten minutes ago, read as existing stock. So every other bucket is its own clause with its own count and conditions and **no disposition markers** (an in-flight copy's is unset or provisional — a blank dressed up as a decision), `to_sort` standing apart from both sides since the copy is here but not filed, and the *purchase* deliberately unnamed: the useful fact is the state, and a link would not fit on one line. The buckets are **`COPY_BUCKETS` in `delivery-state.ts`** — `copyBucket` lifted out of `wants.ts`, which now reads it from there — one declaration of order, of which delivery state each stands for, and of both wordings the axis is read in: a bare tally (`1 held · 1 in transit`, the want list) and a sentence clause (`1 on its way`, this line). Two surfaces answering "have I got this" must not be able to disagree, and the clause hues come off `COPY_BUCKET_COLOR` for the same reason. The per-condition figures inside a clause appear only when the clause spans **more than one condition**, never merely more than one copy: with one condition the clause's count has already said it (`2 being sorted (2 MNH)`). Conditions are **listed, never ranked** — ADR-0032's rule, so *you hold a worse copy, keep this one* is not expressible and must not be invented. What the earlier draft of #562 also proposed and the issue then **cut** is **presetting the disposition chips** from the counts: the remembered last-used disposition (#121/#234) carries a run-wide intent ("this whole stockbook is stock") the counts cannot see, the interesting half of the call is the unrankable one, and a line read at a glance already answers it — a preset is a separate issue to be argued from experience, not guessed at spec time. The three `groupBy`s in `copy-counts.ts` now share one `heldCopiesWhere`, so what "held" means cannot drift between the axes. The **want marker** rides on the same line, judged by `WantChip`'s own `copy` against the condition and certificate *currently in the form* (format null — intake has no format field), which is the point: on the copy rows and in the after-intake review it speaks about a decision already taken. `listAllIssues` therefore loads `loadStampWantSummaries` beside the copy counts it always loaded, since the picker's rows are `StampDetailLine`s and the badge was already drawing there while the want chip was dark.

- **Which offers something is in** (#276, #349) is a read-only popup off the Copies, Stamps and Issues row menus, fed by `listOffersForTarget` (`offers/for-target`, a static segment ahead of `[offerId]`) — unpaginated, because a target sits on a handful of listings at most. It is scoped by an `OfferLookupTarget` (`item | stamp | issue`) mirroring the copies popup's targeting (#110), and a **stamp matches exactly**, never rolled up from its variant children — the same rule as the copies-held badge (#348), since the tree shows a child's own entry one line down and a rollup would report one listing twice. The stamp/issue surfaces go through `useOffersPopupAction`, the `{ action, dialog }` row-action hook; the Copies list keeps its panel-level dialog union. It lists **every** state, terminal included (unlike the offers list, which hides closed ones by default, #245): a sold or withdrawn listing is exactly what one asks a piece's history for. Ordered live-first (`active → paused → ready → preparing → sold → withdrawn`), newest first within a rank, so "where is this on sale right now?" is answered by the top of the list. The row reuses the Offers list's presentation (platform/state chips, needs-action + bidding badges, asking price with base-currency equivalent), opens the offer's detail screen on click, and links the platform listing separately. The action is **unconditional** — a sold copy's past listings are as much the question as a live one's, and the row carries no offer count to hide it by.

- A **platform exclusion** (#506) is the collector saying the *not offered on platform X* worklist (#259) has already been answered for one copy: `ItemPlatformExclusion`, a `(itemId, platformId)` row whose *presence* is the whole state — no reason column, because the worklist only needs the question settled and the copy's own `notes` are where a why belongs, and because a flag with nothing to fill in is what lets the bulk write be one press. Both FKs **cascade**, unlike every reference that records something that happened: an exclusion is a preference, so deleting the platform contact must not be blocked by it and the copy takes its own with it. It reads as one more `and.push` inside the same `notOfferedPlatformId` branch — every other clause there says a copy *cannot* be listed yet, this one says the collector has decided — beside `excludedPlatformId`, the review half, which carries **no `forSale` implication** on purpose: a copy set aside and then taken off sale would otherwise fall out of both readings at once and be unreachable. One `setItemPlatformExclusion` serves the row and the bulk bar, because a decision about one copy and about a thousand is the same decision; it is idempotent in both directions (`createMany … skipDuplicates` / `deleteMany`), which is what makes it safe to point at a selection already in a mix of states, and it **refuses** an unknown platform while merely *dropping* copy ids from elsewhere — the platform is what the call is about, the copies are a set. The copy form owns the whole set (`excludedPlatformIds`, absent meaning *leave alone*, a list meaning *replace*), while the row's ⋮ entry and the bulk button turn exactly one platform on or off and are therefore offered **only while the filter names one** — a decision always names a platform, and inventing a picker for it would be a second way to answer what the form already asks. Both halves live in one toolbar `<select>` (`EXCLUDED_OPTION_PREFIX`, two `optgroup`s) since the second exists only to correct the first; only the worklist choice is remembered per collection (#275), because the review is somewhere one goes to look, not the list one works from.

- A **stamp × condition collision** (#513) is the *other* duplicate question, beside #167's "this very copy is on two active offers of one platform": a **different** copy of the same stamp in the same condition is the mistake worth catching before the copies go on — Colnect refuses the second offer outright, and on a marketplace that allows it the collector is still competing with themselves. Every surface below therefore states the **fact** and never a rule (#524): *these copies are already offered on platform X, same stamp and condition*. The dialog lists on whatever platform was picked, so asserting Colnect's rule while creating a Delcampe offer was simply wrong. The pure half is `src/lib/offer-collision-rules.ts` (`collidingItemIdsByOffer`, unit-tested), keyed through `copyGroupKey` under `DEFAULT_GROUP_AXES` — literally #372's duplicate key, so the warning and the grouping cannot drift, and format/certificate never split it. A candidate the offer **already lists** is deliberately not reported: that is `containsItemIds`' fact, and one thing said twice in two vocabularies is worse than said once — but such a copy still contributes its key, since a *second* candidate beside it would still be the offer's second copy of that stamp. The read is `collidingItemIds` in `offers.ts` (one `offerSetItem` query narrowed by the candidates' stamps, condition matched in memory), feeding both `findStampConditionCollisions` (route `offers/stamp-condition-collisions`, hook `useStampConditionCollisions`) and `ComposeTargetOffer.collidingItemIds`. It counts **every live offer** — preparing/ready/active/paused, unlike #167's active-only — because a duplicate is worth catching while both listings are still drafts. Three surfaces, all warnings and never gates: the `AddToOfferDialog` picker marks a colliding offer with an amber chip (pickable, and nothing left out of the add — only *literally* already-listed copies are dropped) and grows a **Conflicts** facet beside the state ones, which cuts across them and is therefore a group of its own, unpersisted (it is a question about *this* selection, not a way the collector likes the picker to open), hidden at count zero and **released** rather than shown empty while the targets are still loading; the stacked create form takes `notice` + `onPlatformChange` on `OfferFormDialog` and re-asks when the platform changes, since the platform is what a collision is relative to; and the Copies list's bulk bar asks only while `scopedPlatform` names one (#506's shared reading of the filter), offering **Add to #12 instead** — `AddToOfferDialog`'s `initialTargetOfferId`, which also opens the picker **on the conflict facet** and forces the state facet to *All offers* until touched — arriving from the conflict is a request to look at exactly those offers, and the remembered facet would otherwise hide the very offer the picker was opened to confirm.

- **Duplicate grouping on the Copies list** (#372) collapses the list to one row per *bag of interchangeable copies*, and **multi-select** (#373) is the escape hatch for the compositions it cannot express. The key's fixed part is `stamp × condition` — Colnect refuses a second offer for the same stamp in the same condition, so a group mixing conditions would produce an offer that cannot be posted — with **format** and **certificate** as two independently joinable axes (`CopyGroupAxes`, remembered per collection). Both on, the key is exactly the one `valuateItemRows` is computed on, so every group has one unambiguous per-copy figure; where members disagree on an axis left at *any* the row is marked **mixed**, which with the axis on cannot occur by construction. The pure half — key encode/decode, `mixedAxes`, `outlierCopyIds` — is `src/lib/copy-groups.ts` (unit-tested); the read is `listItemDuplicateGroups` in `items.ts`, beside `listItemsPaginated` so both narrow through the same private `buildItemWhere`. Grouping is **server-side** because the list is offset-paginated: a client-side grouping would split a group at a page boundary and report two half-counts. Groups order **count descending** then `stampId` (total, so pagination cannot repeat or skip one), which is why the sort control is *hidden* rather than left offering an order it cannot honour. Grouping is **not filtering** — the sidebar filters decide which copies you look at, the toggles what counts as the same item, and both compose — but it does force the composition picker's eligibility (**for sale, delivered, unsold**), so the delivery-state and *Include sold* controls grey out and the holdings bar narrows with it. **Expanding a group needs no endpoint of its own**: a key *is* a filter combination, so members come back through the ordinary items query with the panel's filters plus the key (`groupMemberFilters`) — which is what the `"none"` certificate sentinel exists for, null being a value exactly as `"single"` is for format. The group row's own action is a **selection** shortcut, not a second listing flow (#398): its members carry the list's ordinary checkboxes and the row's own checkbox — a `⋮` entry until #422 moved it into the select gutter — ticks them, so what happens to a bag of copies is decided once, in #373's bulk bar. There was a dedicated *List all as one offer* dialog first, and two ways to compose an offer out of the same rows is one more than the screen can explain — the packaging question it answered is already `AddToOfferDialog`'s *Add as* (`createOffer`'s `seedPerCopy`: one single-copy set each rather than one set holding everything). **Outliers** (differing from the group's *most common* value on an *any* axis, never a fixed "format ≠ single" test) keep their marking on the member rows and are **left out of** the quick select-all, but tick individually like any other copy. The shortcut is **not** conditioned on the group being open: it expands the row and walks the member pages to the end before ticking (a partly loaded group would tick a subset and call it "all"), holding the request as a nonce whose *served* value is a **ref** — bookkeeping about a request is not something the row renders, and a second state would be a `setState` inside the effect that discharges it. Because a grouped panel runs no flat query, `CopySelection` carries the **items**, not ids (`onToggle(item)`, `onSetMany(items, selected)`) and the panel's selection is a `Map<id, ItemListItem>`: there is no page here to resolve a member's id against. Which copies are still free **on a platform** is deliberately not re-asked in that dialog — the list's own *Not offered on…* filter (#259) is the entry point the feature exists for, and it also pre-fills the platform into the form. `AddToOfferDialog` takes `items: ItemListItem[]` throughout; `ComposeTarget*.containsItemIds` replaced the old boolean, so an offer holding *some* of a selection keeps those copies out of the add and says so, and only one holding *every* copy is disabled. Its packaging choice is **one control, not two submit buttons** (unlike `ComposeSetDialog`), because it governs the stacked create form too, whose submit lives inside the offer form. A checkbox beside an `InventoryItemRow` sits in the shared `SELECT_STRIP` (`inventory-copy-list.tsx`) — a full-height `<label>` gutter with the box centred in it — on every surface that has one: a copy row is four lines tall, so a top-aligned box reads as belonging to the first line, and a 13-pixel target is poor for a list one works through by ticking. The sale-line picker keeps its own shape, where the whole row toggles.

- The Copies list's **grouping is a mode, not a flag** (#421, #424): `none | duplicates | location | ref | issue`, one persisted per-collection preference, because they are readings of one list and exactly one can be in effect. **Filing groups** collapse the list by *where a copy is*, and differ from #372's duplicate groups on every axis that matters. They force **no eligibility** — "where is it?" is a fair question about a sold copy still on the shelf, so `Include sold` / `Include no longer held` stay live and the holdings bar is not re-narrowed. A location groups **exactly**, never rolled up: a nested location is its own row stating its full path, since a roll-up would report one copy under every ancestor and the location filter's own subtree scope (#385) is already how one asks for a branch. A ref only means anything inside its location, hence `(locationId, locationRef)` and not `locationRef` alone. The reading order is location path then #330's `compareLocationRef`, neither of which SQL can express, so `listItemLocationGroups` reads the groups **whole and pages them in memory** — bounded by the collection's locations × refs in use, not by its copies, and a *total* order, which is what makes paging over it neither repeat nor skip a group. Null and `""` refs are folded into one "no ref" group after the `groupBy`, which the database cannot do for us. Two sentinels carry the buckets an absent filter cannot express — `NO_LOCATION` / `NO_LOCATION_REF` (`location-groups.ts`, pure, so a client row can name them without importing a server module), the `"single"`/`"none"` pattern again — and a group addresses its own members through the **ordinary items query** with `locationExact: true`, so no per-group endpoint exists. A filing row is deliberately **thin** next to a duplicate row: a group is a *place*, so it states the place and the count, and what the copies are is what the member rows answer. **Issue groups** (#424) are the same shape a third time — thin row, no eligibility forced, read whole and paged in memory, members addressed through the ordinary items query — and differ in the two places the subject differs. The reading order is the **Issues list's own** (year, then `primaryCatalogSortKey`, then name; #181), because a collector scanning copies by series is reading the list they browse the catalogue in and two orders for one subject is two things to learn; the issue-less bucket sorts last, being the absence of the subject rather than a thin edge of it. And the issue lives on the *stamp*, which `groupBy` cannot reach, so the filtered set is scanned and counted in memory over a two-field select — `listItemYearFacets`'s own shape, the year being on the stamp for the same reason. Membership is many-to-many but a copy is counted under **one** issue, its stamp's first, so the groups partition the list and their counts add up to it; `FIRST_ISSUE_MEMBERSHIP` (`orderBy: { issueId: 'asc' }, take: 1`) is what makes that *one* answer — an unordered `take: 1` let the row, the grouping and the title reads each name a different issue for one copy, which is a latent bug this fixed rather than a new rule. Counting on the first membership while reading members back through the ordinary `issueId` filter (which matches **any**) is #172's existing pair, deliberately not a third rule: they differ only for a stamp filed in two issues, and an issue filter meaning "and no earlier one" would make the sidebar's own filter answer a question nobody asks of it.

- Every **grouped row shares one shell** (`inventory/copy-group-shell.tsx`, #422): the expand arrow, the select-all box, the member list and the page-walking `useGroupMembers`. The arrow is **vertically centred** (a group row is four lines tall, and one pinned to the top reads as belonging to the first line), and quick select-all (#398) is a **checkbox in the same `SELECT_STRIP` gutter the member copies use** — one click, in the column the eye is already in — rather than a `⋮` entry, which was two clicks and a menu to read for the thing the row is most used for. The duplicate row's `⋮` therefore disappeared entirely: it held nothing else. `allSelected` stays **derived from the copies actually ticked**, never from the pending request, so a box can never claim "all" before the page walk that makes it true has finished.

- A **sold** copy carries its own chip on the copies list (#393), tinted `success` rather than the disposal chip's error tint — it left the collection the way it was meant to, so the chip states an outcome instead of raising an alarm. It can only ever appear under *Include sold* (#207), which is exactly the mixed view it exists for. `ItemListItem.sold` comes from `_count.saleLineItems` on `ITEM_LIST_SELECT` — the very relation `excludeSold` filters on, so the chip and the filter cannot disagree. Soldness stays outside `isHeld` (#394), as it always has.

- A **detail page reads; it does not become a second editor** (#517/#518/#519). A copy, a stamp and an issue each have a screen of their own — `inventory/[itemId]`, `stamps/[stampId]`, `issues/[issueId]` — reached from the list row's `⋮` menu — first entry — **and promoted to the row's quick actions** (`useDetailPageAction`, `shared/use-detail-page-action.ts`), first icon there too, since going to a record's screen is the one thing every one of these rows can do. The icon is on **rows inside the detail screens as well** (an issue's stamp tree, a stamp's variants and issues, the copies on either) through the same `RowQuickActions`: a row in a card is still a row, and reaching a record should not be a different gesture depending on which screen you met it on. That is also why a `readOnly` copy row renders **exactly this one** icon rather than none — `readOnly` means the copy is not edited from a screen that is not the Copies list, and it would be an odd kind of read-only that refused to let you read more (so the #110 popup gains it too). Whole-row click was weighed against the icon and **rejected** for these rows, the `offer-row.tsx` / `OfferTargetRow` precedent notwithstanding: a copy row is selectable (#373's checkbox is right beside it) and an issue-tree row expands, so a click there is already spoken for, and the rows are dense with controls that each mean something else (a chip copies, a thumbnail opens a lightbox, a price edits inline). They **consolidate**, they do not replace: the popups they gather (#110 copies, #114 prices, #276/#349 offers) stay exactly where they are, because a popup answers one question without leaving the list and a page is for when the whole picture is wanted — and every field on these screens is still written through the dialog that already owned it, a second editing surface for one record being a second place to keep honest. The chrome is one kit (`shared/detail-page.tsx`: `DetailLayout`, `DetailCard`, `DetailFullRow`, `FieldGrid`, `Field`, `EmptyNote`), and the layout is a **dashboard, not a column**: one column of cards down the middle of a wide monitor is a screenful of scrolling beside a grey plain. It is **two explicit columns** — `DetailColumns` + one `DetailColumn` per side — and **which card sits where is each screen's own decision**, stated in its JSX. The split is the same question on all three: the left column is what the record *is*, the right is what the collection *does* with it (copies, offers, purchase, sale) — which is also the reading order when a narrow window collapses the two into one. Two earlier attempts are worth not repeating: a `grid` places a card in a *row*, so the row is as tall as its tallest card and every shorter one beside it leaves a hole, and `dense` packing cannot rescue it (it only pulls a card forward into a gap something actually fits into, and a four-field card against a stamp tree fits nowhere); CSS **multi-column** does fix the holes — it balances columns rather than filling rows — but it *decides the order*, and the pairings that make these screens readable (an issue's stamp tree beside its completeness grid, a copy's physical facts beside its trade history) are not something a height-balancing algorithm knows about. So the columns ending at different heights is **accepted**, the alternative being a hole or an order nobody chose; keeping the taller column's tail short is what the ordering is for. `auto-fit` over a minimum width is the single-column fallback and is not a breakpoint — this app has none, being desktop-only. **A card with nothing on it is not rendered at all** (#536) — `empty` on `DetailCard`, which returns `null`, so emptiness is the card's own business rather than each page remembering its own `&&`. The Notes card was the first to work this way and the Wants card (#532) the second; #536 made it the rule, because a heading over "never sold" is furniture that answers a question nobody asked and pushes the answers that do exist further down a column these screens are trying to keep short. Pass a query's loading flag into `empty` too: a card that appears once, filled, beats one that flashes an empty shell or fills and then vanishes. `EmptyNote` survives for the other case — a card that *does* hold something and has nothing to draw right now (a checklist filter that matched none of the tree). The **exception** is a section whose empty state carries the only way to create the first entry ("No lots yet. Add a priced lot…" on a purchase order, "No lots in this sale yet" on an auction sale): that is the way in, not clutter, and it stays — which is why the older detail screens (#165 offer, #166 sale, #120 purchase) were audited under #536 and left as they are. Vertical spacing is a **margin per card**, not `gap`: `row-gap` does nothing in multi-column; the container cancels the last one. `DetailCard` carries `break-inside: avoid`, which costs nothing outside a masonry. `DetailFullRow` is also the identity band across the top. Each card that shows *related records* is shared with the popup it mirrors rather than re-rendered — `RelatedOffersCard` (which owns `OfferTargetRow`, the popup importing it back) and `RelatedCopiesCard` (the popup's `InventoryCopyList` in `readOnly`), so a listing or a copy cannot read one way inline and another in a dialog. The header identity is `shared/stamp-identity.tsx`, shared by the copy and stamp screens for the same reason. Each page reads through the **list's own** enrichment — `getStampListItem` / `getIssueListItem` beside the existing `getItemListItem` — so the page and the row it was opened from cannot describe one record differently; the copy page reads through `listItemsPaginated({ ids })` rather than `getItemListItem`, because that one is owner-scoped and the URL carries a collection slug. `CatalogPricesCard` shows the **cross-catalog averages** inline and puts the per-edition breakdown behind #114's own dialog: the average is the figure a value is read off, and copying the whole matrix onto three screens would be #114 rewritten three times. The issue screen's **completeness grid** (`issue-completeness.ts` + the pure `issue-completeness-rules.ts`) is the disposition × condition half of #133, computed on demand for one issue exactly as #133 reasoned — the list keeps #54's lightweight indicator. Two figures, and they answer different questions: **owned** is progress, **complete sets** is the *minimum* across every required member, so one missing stamp is zero however deep the pile of the others. Dispositions **overlap** (a copy is in the collection *and* for sale), so the rows never sum to *Any*; the exclusions are `copy-counts.ts`'s exactly, or the card and the badge beside it would disagree about what having one means. Format is deliberately **not** an axis here — that is the rest of #133.

- In-location refs (`A234`) are ordered by `compareLocationRef` (`src/lib/location-ref.ts`): prefix first, then the trailing number, separators ignored, blanks last. Use it anywhere refs are sorted — a plain numeric collator disagrees as soon as the separator varies.
