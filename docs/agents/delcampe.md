# Delcampe Integration

Which platform is Delcampe, the listing profiles an upload row is built from, how its categories are learned, and what is deliberately not here.

- **Delcampe is configured, not connected** (#608; [ADR-0034](../decisions/0034-delcampe-listing-profiles.md)). There is a REST API, and it is not used: it sits behind the paid **API Pass**, and listings are created by uploading a CSV through **Easy Uploader**, so the file's columns are the contract and every one of them has to be answerable before an exporter exists (#610). Most of them already are — the title and description are the platform contact's templates (#210, #266), the price, quantity and `selling_type` are the offer's own (#449), the currency is `platformCurrency` (#196), the images are the photo plan — which is the whole reason this issue adds so little: what was missing is four groups of columns that describe *a way of selling* rather than a stamp. They are held as one named `DelcampeListingProfile` on the Delcampe platform `Contact` (`src/lib/delcampe-listing-profile.ts`, pure rules in `delcampe-listing-profile-rules.ts`), one of which is the platform's default (`Contact.defaultDelcampeListingProfileId`) and any of which an offer may name instead (`Offer.delcampeListingProfileId`) — #486's shape, resolved by the single `resolveDelcampeListingProfileForOffer` so the settings screen, the offer card and the export cannot come to disagree about which settings a row carries. All four groups travel in **one** profile rather than in a dictionary each, because the case that makes a second answer necessary is a single case: a heavier lot wants the other shipping model, and it is chosen at the moment the row is built. Both references are `SetNull` and nothing is promoted when the default is deleted — the collector decides what the next upload carries, and a silently inherited default is how something unmeant gets listed.

- **The shipping model is a name, and it cannot be checked** — the one place this is *inverted* from Allegro. #486's profile stores Allegro's own rate-set id with the name as a screen label, so renaming it on the marketplace breaks nothing; here the CSV carries the **name itself**, there is no id in reserve, and the list it would be validated against (`GET /shippingModels`) is behind the API Pass. So `cleanDelcampeListingProfileValues` checks that it is present and nothing more, and the editor says out loud that it must read exactly as it does on Delcampe. That sentence is the feature: a model renamed there means a rejected upload, and the refusal must not read as a fault in the export, because nothing about the file was wrong and nothing here could have known.

- **`minimum_bid_step` is a stored rule, not a value** — `0,01` was observed on cheap listings and `0,10` on dearer ones, so three columns (`minBidStepThreshold` / `minBidStepBelow` / `minBidStepAtOrAbove`) and one pure function, `delcampeMinimumBidStep`, whose boundary is **inclusive at the top**: a listing priced exactly at the threshold takes the larger step. Stated once, because "more expensive" is otherwise decided again by every caller and the export and the settings preview then disagree on exactly one price. The threshold is a field precisely *because* it was never confirmed against Delcampe: a guess compiled into the exporter is one nobody can see or correct, while a guess seeded into a settings field is corrected the first time a listing disagrees with it. The editor reads the rule back as the sentence it will be applied by, from that same function.

- **The renewal counters are shop stock, and the promotions are money.** 28 days × 99 renewals is a fixed-price listing that stays up until it sells; an auction wants a real end date and a second set of defaults, which is #620's and deliberately not a reinterpretation of these. The five `option_*` flags are stored, all off, rather than written `N` by the exporter — a column that costs money and is filled in by code is a decision nobody could find later. `has_renewable_options` sits with them because it only means anything while one of them is on. The keys, the CSV column names and the labels are one list (`DELCAMPE_PROMOTION_OPTIONS`), so the editor and the exporter cannot name them differently.

- **The category is learned, and the register it is learned into is not Delcampe's** (#609; [ADR-0035](../decisions/0035-delcampe-learned-categories.md)). An Easy Uploader row wants `category_id`, and the collector was keeping the mapping in a spreadsheet — which is the wrong shape twice over: Delcampe's tree is cut by *period* (`Stamps > Europe > Poland > 1944-…. Republic > 1944-60 > Used stamps`) where this collection is cut by area, and the answer also turns on facts nothing here records dependably (a souvenir sheet goes to `7911` where the same country and condition as a single goes to `7938`). A lookup table can only answer when its key holds everything that decides the answer, so what was reused instead is #488's *register*: `AllegroCategoryLesson` became **`PlatformCategoryLesson`**, which is what it always was — keyed per (collection, `platformId`) since the day it was written, with the Allegro name the only Allegro thing about it. The pure half is `platform-category-rules.ts` (the key, the ladder, the ranking, the "Learned from …" sentence) and the reads and writes are `platform-category.ts`; `allegro-category*.ts` keeps only what Allegro genuinely adds. This was cheap **because ADR-0026 §1 kept two registers rather than one** — `AllegroCategoryParameterMemory` never moved and never will, Delcampe's categories carrying no parameters at all. The key gained **no axis**, in particular none for the souvenir-sheet case: an axis for a fact this app does not record would be a claim it cannot make, and it would change Allegro's behaviour, which the generalisation must not. What answers that case is the per-offer override, which is therefore the design rather than a nicety.

- **Two suggestion sources, and the third is a person.** Allegro falls through to `GET /sale/matching-categories`, which guesses from a listing title; Delcampe has no such endpoint and no usable API here at all, so `Offer.delcampeCategorySource` is `learned | manual` against Allegro's three, and an unmatched key falls through to the **picker**. That is not a failure state — it is the first offer of a kind, and the register is what makes it the only one. Learning happens on **`preparing → ready`** (#494's moment) for a reason that is stronger here than it was there: a Delcampe listing goes up as a CSV uploaded days later (#610), so a register that learned at publication would answer the question long after it stopped mattering. `backfillDelcampeCategory` sits beside `backfillAllegroCategory` in the same three mutations and is a **backfill, never a refresh** — a category is a decision about what the goods are, and re-deriving it under a collector who corrected it would undo that silently; ↻ *Match again* is the explicit way back, and it **clears** on a miss rather than keeping the old value, since asking the register what it says now must not be answered with something the register did not say.

- **Delcampe's own category list is snapshotted, and it is a dictionary rather than a mapping.** `7945` with no name is the spreadsheet again, so `DelcampeCategory` holds the tree Delcampe publishes at `delcampe.net/en_GB/collectables/category-id/` — the page its own help centre sends sellers to, there being no API. Nothing in it says what a *stamp* should be listed as; losing it costs names on a screen and nothing else, which is what makes refreshing it in the background safe to have at all. It is the one table in this schema with **no `collectionId`**: Delcampe's taxonomy is identical for every collection on the instance, and a per-collection copy would be N copies of one public fact refreshed N times (`StorageCacheEntry` is the precedent). The refresh is a walk of somebody else's site and is written as one — nothing unless a collection has named a Delcampe platform, nothing while the snapshot is under twenty hours old (so a restarting dev server never crawls), sequential at ~1.2 s, a **429 ends the pass**, and **only a complete pass may delete**. The one thing that makes it a few hundred requests rather than a few thousand is in the parser: a page that expanded a heading's children *in place* has already answered for that heading's own page, so `parseDelcampeCategoryPage` reports only the links it did not expand. The parse is pure and tested against saved markup, because "the list stopped being readable" must fail a test rather than only empty a picker quietly. `pnpm delcampe:categories` and a button in Settings do the same pass by hand.

- **The marker carries no listing module.** `Contact.platformModule` gains `"delcampe"` (`platform-modules.ts`), set on its own Settings tab exactly as Colnect's and Allegro's are and exclusive through the shared `setModulePlatform` — it is the one fact the profiles, #609's learned categories and #610's export cannot work out for themselves. It is pointedly **absent** from `LISTING_MODULE_RULES`, so `hasListingModule` answers false: nothing offers ⚡ *List via Assistant* on a Delcampe offer and none of Colnect's preconditions (an item-ID per stamp, a mapped grade) is asked of one. That is #471's distinction — naming a module is not a promise about listing — applied to a marketplace whose listing path is a file this app writes.

- **Nothing in this layer formats a file.** The contract's two asymmetries — the upload writes decimals with a **comma** (`"0,10"`), the export file returns them with a **dot** (`17.44`) — belong to the writer and the reader (#610, #611). The rules module answers *what* a row says and holds no formatting at all, which is also why `personal_reference` (seller-visible only, which is what makes #154's decision to put the offer's own short URL in it safe) is not modelled here: it is the offer's, not the profile's.

- **Where it is seen.** Settings → Delcampe is three panels, in setup order: which platform is Delcampe, its profiles, then its categories — a profile being what the collector *configures* and the register being what the app has *learned*, the Allegro tab's own ordering. The categories panel carries one thing Allegro's does not, the state of Delcampe's published list, because that is the only thing on the screen that can be *stale* and a picker searching a list nobody has read looks broken rather than empty. The offer's own screen carries **On Delcampe** (`offer-delcampe-card.tsx`) beside where the Allegro card sits, for that card's reason (#494) — the value is settled while the listing is being prepared, not inside whichever dialog eventually exports it — and it states what the chosen profile *holds*, since "Standard letter" says nothing about which shipping model, how often it renews or what bid step the row will carry. **Two** sections rather than Allegro's three: a category and a profile, there being no parameters at all. The category picker (`shared/delcampe-category-picker.tsx`) is **Delcampe's own tree, searched in place** — both halves, which the local snapshot is what makes cheap: the tree is how somebody who knows where their stamps live gets there and the only rendering in which a *heading* reads as a heading, the search is how anyone else does, and narrowing keeps the tree rather than flattening it so a hit is still shown where it sits. Built from the paths client-side (`buildDelcampeCategoryTree`), because the path *is* the parent link and a node's path is the only thing unique about it; a **heading cannot be chosen** (`LocationTreeSelect`'s grouping-location rule, same words), and a node may be both listable and a parent — `Occupations` is. Matching is over the whole path on **word starts**, since `Used stamps` names hundreds of rows and a substring match would answer `used` with every *unused* category there is. The list is loaded **once per picker** rather than queried per keystroke — ~7 000 short rows, tens of kilobytes compressed, public data — which is what lets expanding and searching agree instantly. A typed number is **always** accepted, matched or not: Delcampe's list is the authority and this is a snapshot of it.
