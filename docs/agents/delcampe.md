# Delcampe Integration

Which platform is Delcampe, the listing profiles an upload row is built from, how its categories are learned, how a batch leaves and comes back, and what is deliberately not here.

- **Delcampe is configured, not connected** (#608; [ADR-0034](../decisions/0034-delcampe-listing-profiles.md)). There is a REST API, and it is not used: it sits behind the paid **API Pass**, and listings are created by uploading a CSV through **Easy Uploader**, so the file's columns are the contract and every one of them has to be answerable before an exporter exists (#610). Most of them already are — the title and description are the platform contact's templates (#210, #266), the price, quantity and `selling_type` are the offer's own (#449), the currency is `platformCurrency` (#196), the images are the photo plan — which is the whole reason this issue adds so little: what was missing is four groups of columns that describe *a way of selling* rather than a stamp. They are held as one named `DelcampeListingProfile` on the Delcampe platform `Contact` (`src/lib/delcampe-listing-profile.ts`, pure rules in `delcampe-listing-profile-rules.ts`), one of which is the platform's default (`Contact.defaultDelcampeListingProfileId`) and any of which an offer may name instead (`Offer.delcampeListingProfileId`) — #486's shape, resolved by the single `resolveDelcampeListingProfileForOffer` so the settings screen, the offer card and the export cannot come to disagree about which settings a row carries. All four groups travel in **one** profile rather than in a dictionary each, because the case that makes a second answer necessary is a single case: a heavier lot wants the other shipping model, and it is chosen at the moment the row is built. Both references are `SetNull` and nothing is promoted when the default is deleted — the collector decides what the next upload carries, and a silently inherited default is how something unmeant gets listed.

- **The shipping model is a name, and it cannot be checked** — the one place this is *inverted* from Allegro. #486's profile stores Allegro's own rate-set id with the name as a screen label, so renaming it on the marketplace breaks nothing; here the CSV carries the **name itself**, there is no id in reserve, and the list it would be validated against (`GET /shippingModels`) is behind the API Pass. So `cleanDelcampeListingProfileValues` checks that it is present and nothing more, and the editor says out loud that it must read exactly as it does on Delcampe. That sentence is the feature: a model renamed there means a rejected upload, and the refusal must not read as a fault in the export, because nothing about the file was wrong and nothing here could have known.

- **`minimum_bid_step` is a stored rule, not a value** — `0,01` was observed on cheap listings and `0,10` on dearer ones, so three columns (`minBidStepThreshold` / `minBidStepBelow` / `minBidStepAtOrAbove`) and one pure function, `delcampeMinimumBidStep`, whose boundary is **inclusive at the top**: a listing priced exactly at the threshold takes the larger step. Stated once, because "more expensive" is otherwise decided again by every caller and the export and the settings preview then disagree on exactly one price. The threshold is a field precisely *because* it was never confirmed against Delcampe: a guess compiled into the exporter is one nobody can see or correct, while a guess seeded into a settings field is corrected the first time a listing disagrees with it. The editor reads the rule back as the sentence it will be applied by, from that same function.

- **The renewal counters are shop stock, and the promotions are money.** 28 days × 99 renewals is a fixed-price listing that stays up until it sells; an auction takes the profile's own second duration group instead (#620, below) and never falls back to these. The five `option_*` flags are stored, all off, rather than written `N` by the exporter — a column that costs money and is filled in by code is a decision nobody could find later. `has_renewable_options` sits with them because it only means anything while one of them is on. The keys, the CSV column names and the labels are one list (`DELCAMPE_PROMOTION_OPTIONS`), so the editor and the exporter cannot name them differently.

- **An auction is a second field group on the same profile, and it is seeded with nothing** (#620; [ADR-0034](../decisions/0034-delcampe-listing-profiles.md) §7). `auctionDuration` / `auctionRenewTotalCount` supply an auction row's `renew_duration` and `renew_total_count`, and `auctionEndDay` / `auctionEndTime` supply the two cells that are empty on every quick buy; `delcampeSellingType` picks the group from `Offer.listingType` (#449), so no listing carries a Delcampe-only flag saying how it is sold. The **blankness is the design**: §3 seeded the bid-step threshold because 0,01 and 0,10 were *observed*, and there are no auctions to observe — so a default here would not be a correctable guess but an invisible one, a plausible 7 × 1 uploading without anyone reading it where a blank is refused at export, named on the offer's card and read back in Settings. `delcampeAuctionGaps` is that one sentence, shared so the editor's preview and a refused batch cannot disagree about whether a profile can list an auction. The two end cells are **text written verbatim**, which is the shipping model's rule applied a second time: the spelling Easy Uploader wants was never confirmed, a picker would be a claim about it that only a release could correct, and blank is a row that states no end rather than a fault. And `price` carries the **starting** price — #477's rule, sharper here because `Offer.price` is one column holding an asking price on a quick buy and the standing bid on an auction (#449), so an auction with no `startingPrice` is refused rather than opened at whatever sits beside it; `minimum_bid_step` is computed against that same figure, so the step is the step for the listing it opens.

- **The category is learned, and the register it is learned into is not Delcampe's** (#609; [ADR-0035](../decisions/0035-delcampe-learned-categories.md)). An Easy Uploader row wants `category_id`, and the collector was keeping the mapping in a spreadsheet — which is the wrong shape twice over: Delcampe's tree is cut by *period* (`Stamps > Europe > Poland > 1944-…. Republic > 1944-60 > Used stamps`) where this collection is cut by area, and the answer also turns on facts nothing here records dependably (a souvenir sheet goes to `7911` where the same country and condition as a single goes to `7938`). A lookup table can only answer when its key holds everything that decides the answer, so what was reused instead is #488's *register*: `AllegroCategoryLesson` became **`PlatformCategoryLesson`**, which is what it always was — keyed per (collection, `platformId`) since the day it was written, with the Allegro name the only Allegro thing about it. The pure half is `platform-category-rules.ts` (the key, the ladder, the ranking, the "Learned from …" sentence) and the reads and writes are `platform-category.ts`; `allegro-category*.ts` keeps only what Allegro genuinely adds. This was cheap **because ADR-0026 §1 kept two registers rather than one** — `AllegroCategoryParameterMemory` never moved and never will, Delcampe's categories carrying no parameters at all. The key gained **no axis**, in particular none for the souvenir-sheet case: an axis for a fact this app does not record would be a claim it cannot make, and it would change Allegro's behaviour, which the generalisation must not. What answers that case is the per-offer override, which is therefore the design rather than a nicety.

- **Two suggestion sources, and the third is a person.** Allegro falls through to `GET /sale/matching-categories`, which guesses from a listing title; Delcampe has no such endpoint and no usable API here at all, so `Offer.delcampeCategorySource` is `learned | manual` against Allegro's three, and an unmatched key falls through to the **picker**. That is not a failure state — it is the first offer of a kind, and the register is what makes it the only one. Learning happens on **`preparing → ready`** (#494's moment) for a reason that is stronger here than it was there: a Delcampe listing goes up as a CSV uploaded days later (#610), so a register that learned at publication would answer the question long after it stopped mattering. `backfillDelcampeCategory` sits beside `backfillAllegroCategory` in the same three mutations and is a **backfill, never a refresh** — a category is a decision about what the goods are, and re-deriving it under a collector who corrected it would undo that silently; ↻ *Match again* is the explicit way back, and it **clears** on a miss rather than keeping the old value, since asking the register what it says now must not be answered with something the register did not say.

- **Delcampe's own category list is snapshotted, and it is a dictionary rather than a mapping.** `7945` with no name is the spreadsheet again, so `DelcampeCategory` holds the tree Delcampe publishes at `delcampe.net/en_GB/collectables/category-id/` — the page its own help centre sends sellers to, there being no API. Nothing in it says what a *stamp* should be listed as; losing it costs names on a screen and nothing else, which is what makes refreshing it in the background safe to have at all. It is the one table in this schema with **no `collectionId`**: Delcampe's taxonomy is identical for every collection on the instance, and a per-collection copy would be N copies of one public fact refreshed N times (`StorageCacheEntry` is the precedent). The refresh is a walk of somebody else's site and is written as one — nothing unless a collection has named a Delcampe platform, nothing while the snapshot is under twenty hours old (so a restarting dev server never crawls), sequential at ~1.2 s, a **429 ends the pass**, and **only a complete pass may delete**. The one thing that makes it a few hundred requests rather than a few thousand is in the parser: a page that expanded a heading's children *in place* has already answered for that heading's own page, so `parseDelcampeCategoryPage` reports only the links it did not expand. The parse is pure and tested against saved markup, because "the list stopped being readable" must fail a test rather than only empty a picker quietly. **Every tick logs**, unlike the quiet hourly sweeps beside it: a skip states its reason and a run states `added / removed / changed / unchanged` as counts, because a daily job against somebody else's site is one where "not running at all" and "ran and found nothing" are opposite problems that silence makes identical — and removals read **zero after an incomplete pass**, matching what the write does. `describeDelcampeCatalogChanges` is that sentence, shared so the log, the settings panel and `pnpm delcampe:categories` cannot describe one pass three ways.

- **The marker carries no listing module.** `Contact.platformModule` gains `"delcampe"` (`platform-modules.ts`), set on its own Settings tab exactly as Colnect's and Allegro's are and exclusive through the shared `setModulePlatform` — it is the one fact the profiles, #609's learned categories and #610's export cannot work out for themselves. It is pointedly **absent** from `LISTING_MODULE_RULES`, so `hasListingModule` answers false: nothing offers ⚡ *List via Assistant* on a Delcampe offer and none of Colnect's preconditions (an item-ID per stamp, a mapped grade) is asked of one. That is #471's distinction — naming a module is not a promise about listing — applied to a marketplace whose listing path is a file this app writes.

- **The batch leaves as one flat ZIP, and a refusal is the whole batch** (#610; [ADR-0036](../decisions/0036-delcampe-easy-uploader-export.md)). What #610 added is a *manifest that agrees with an archive*, not a second way of collecting anything: the bulk listing workspace (#322) is already one platform's `ready` offers, which is the shape of one Easy Uploader batch, and `readOfferUploadSet` is the same read the per-offer ZIP and the batch archive are built from — so a picture in the bundle is byte-identical to and named exactly as the same picture downloaded on its own. The pure half is `delcampe-export-rules.ts` (the column list, the decimal comma, the CSV quoting, one row, the refusals a row can carry) and the batch is `delcampe-export.ts`, behind `POST …/offers/delcampe-export`. **Flat**, unlike #323's folder per offer, because `images` names its pictures by file name and nothing else — a folder would name files Easy Uploader cannot find — and the one case that costs (two offers whose titles slug the same) is suffixed **per offer**, so one listing's pictures stay a run of one stem. **All-or-nothing**, and deliberately the opposite of the photo archive's skip-and-report: a missing folder in a download is visible and free, while a missing *row* is a listing that never happened and looks exactly like an offer waiting for the next batch. Every `ready` offer is one the collector said was ready, so one that cannot be written is a fault to fix — named, with every reason at once, before a file exists. Nothing is trimmed to fit (#405's rule, #477's rule): a title silently shortened is a listing nobody proofread, and an auction with nothing to open the bidding at is refused rather than opened at the offer's other price column (#620).

- **Two numbers in the file are observations, and both are typed rather than compiled.** `minBidStepThreshold` was the first (ADR-0034 §3); the title cap is the second, and it landed as **`Contact.maxTitleLength`** beside #403's two rather than as a Delcampe constant — the same kind of fact as the description cap, read live by every surface that shows a title, blank on a platform that states none. Delcampe publishes the figure nowhere this app can read, and an unconfirmed number a collector can correct in Settings is worth more than one that needs a release. The **ongoing-sales ceiling went the other way and is not held at all**: #610 proposed refusing an over-full batch, and this app cannot see the live count — listings are uploaded by hand, ended by buyers and relisted by Delcampe — so anything counted here would be *its own offers* rather than the seller's sales, blocking a legitimate batch as confidently as it passed an over-full one while reading like a guarantee. Keeping the batch inside the package is the collector's, and the user guide says so out loud.

- **The batch comes back as a file too, and that is where a listing becomes live** (#611; [ADR-0037](../decisions/0037-delcampe-active-items-reconciliation.md)). Delcampe publishes a CSV of the seller's own *active items* carrying `personal_reference` back, which is the whole reason #610 put the offer's own short URL in it — so the loop closes without an API at all. `ready → active` is written **here**, on Delcampe's own word with Delcampe's own `id_auction`, and pointedly not by the export: a downloaded file is not a listing, Easy Uploader can refuse it, and an offer moved on the strength of a download would read as live while nothing was posted. The id lands on `Offer.delcampeItemId` (unique per collection, the address #612 will match an order's items on) and `Offer.url` is **composed** from it rather than stored twice. **Absence is the signal**, and it is cleaner here than in #467: an Allegro sweep is paged, so only a finished one may derive anything (`listingsSweptAt`), while a file has no pages — every listing that is up is in it. A `DelcampeListing` row the newest import did not carry is marked `ENDED` keeping the date it was last seen **up**, and the offer is left exactly as it was, because what the absence *meant* — sold, ended, pulled — the file does not say and #612 is where it is asked. The rows are never pruned, unlike Allegro's aged-out `ENDED` ones: an ended listing's id is precisely what a sold order will name months later. The pure half is `delcampe-import-rules.ts` (the RFC 4180 reader, the reference rule, the reconciliation), `delcampe-import.ts` performs it, `delcampe-worklist.ts` reads it back.

- **Two listings claiming one offer is refused, and the origin is not.** Delcampe does not enforce uniqueness on `personal_reference` — the collector's own live listings already carry one reference twice — so a duplicate refuses **both** rows, applies neither and reports the offer number they name; the same rule covers an offer already up as a *different* listing that is also in the file, while one whose id is **absent** from it has come down and the new listing takes over, that being a relist rather than a guess. What is deliberately *not* enforced is the origin: ADR-0036 §2 puts the absolute URL in the column because a dev instance restored from a production dump shares every value inside the database, and reading it back narrows that to **the path decides which offer, and the slug must be this collection's**. A file is not a page, so #417's origin rule does not transfer — the collector picked this file, from their own account, on their own instance — and comparing origins would silently orphan every listing already up the day the instance moves from a LAN address to a domain name, with no way to correct them but one at a time on somebody else's site.

- **What the file says about money reaches an offer only where the offer is an auction.** #481's rule, narrowed twice by what this file does not state: there is no selling format in it, so the local `listingType` is the whole test (Allegro's `bidWriteFor` demands both sides agree; here only one side speaks), and there is no currency, so the platform contact's own (#196) stands in and a figure is written only where the two match. A **fixed-price** listing's `present_price` is never written back — it is the collector's own asking price coming home, and a file that disagrees with it is drift (#542), a thing to show rather than to resolve in the marketplace's favour. `bids_number` counts *bids* where `Offer.bidderCount` counts *people*; the file does not carry the number the column is named for, so what is stored is what was said and the difference is stated rather than papered over.

- **Where it is read.** *On Delcampe* (`offers/delcampe`), a fourth entry under Offers beside *Sold on Allegro*, and the other end of *Bulk Listing*: the batch leaves as a file from the workspace and comes back as one here. What is up and matched is a **count in the header**, never a list — those listings need nothing from anybody and the offers list already shows them with their addresses — so the screen carries only the two things an import leaves behind that somebody has to act on: what has **come down** while the offer here is still open, and what matched **no offer**, each with the sentence describing what to go and fix. The header states when the last export was read and which file it was, for the Allegro worklist's reason: a reconciliation is only as true as the file it was done from. The offer's own **On Delcampe** card states the same listing from the same row, leading the card because whether this is up is asked before what the next upload will carry — an observation among two settings, and the only thing on that card nobody may edit.

- **Nothing in this layer formats a file.** The contract's two asymmetries — the upload writes decimals with a **comma** (`"0,10"`), the export file returns them with a **dot** (`17.44`) — belong to the writer and the reader (`delcampe-export-rules.ts` and `delcampe-import-rules.ts`), which is also why neither knows about the other: a shared "Delcampe number" helper would have to be told which direction it was in on every call. The rules module answers *what* a row says and holds no formatting at all, which is also why `personal_reference` (seller-visible only, which is what makes #154's decision to put the offer's own short URL in it safe) is not modelled here: it is the offer's, not the profile's.

- **Where it is seen.** Settings → Delcampe is three panels, in setup order: which platform is Delcampe, its profiles, then its categories — a profile being what the collector *configures* and the register being what the app has *learned*, the Allegro tab's own ordering. The categories panel carries one thing Allegro's does not, the state of Delcampe's published list, because that is the only thing on the screen that can be *stale* and a picker searching a list nobody has read looks broken rather than empty. The offer's own screen carries **On Delcampe** (`offer-delcampe-card.tsx`) beside where the Allegro card sits, for that card's reason (#494) — the value is settled while the listing is being prepared, not inside whichever dialog eventually exports it — and it states what the chosen profile *holds*, since "Standard letter" says nothing about which shipping model, how often it renews or what bid step the row will carry. **Two** sections rather than Allegro's three: a category and a profile, there being no parameters at all. The category picker (`shared/delcampe-category-picker.tsx`) is **Delcampe's own tree, searched in place** — both halves, which the local snapshot is what makes cheap: the tree is how somebody who knows where their stamps live gets there and the only rendering in which a *heading* reads as a heading, the search is how anyone else does, and narrowing keeps the tree rather than flattening it so a hit is still shown where it sits. Built from the paths client-side (`buildDelcampeCategoryTree`), because the path *is* the parent link and a node's path is the only thing unique about it; a **heading cannot be chosen** (`LocationTreeSelect`'s grouping-location rule, same words), and a node may be both listable and a parent — `Occupations` is. Matching is over the whole path on **word starts**, since `Used stamps` names hundreds of rows and a substring match would answer `used` with every *unused* category there is. The list is loaded **once per picker** rather than queried per keystroke — ~7 000 short rows, tens of kilobytes compressed, public data — which is what lets expanding and searching agree instantly. A typed number is **always** accepted, matched or not: Delcampe's list is the authority and this is a snapshot of it.

- **A sale comes back from a screen, not from a file** (#612; [ADR-0038](../decisions/0038-delcampe-order-import.md)). #611 stops at "this listing came down" because a file cannot say whether that was a sale, and the sold-items CSV that *could* have said so was refused twice over: it carries **no order id** (rows sit one per item, so one parcel would be inferred from a buyer plus close timestamps — a guess with a confident label) and it carries **every buyer's full address and e-mail in bulk**, which is exactly what #467 leaves unread and #463 fetches only on request. So the answer is asked of the seller's own **My Sold Items** screens, where the collector is already standing when they pack the parcel: the Assistant marks each order row with what it is here — a link to the sale, or an **Import** affordance — and one click records it. `Sale.externalRef` carries Delcampe's order id, the same column #479 puts an Allegro order number in, so "already recorded" is one query and a re-import is a link rather than a second sale. The pure half is `delcampe-order-rules.ts` (the amount and date readers, and `planDelcampeOrderSale`), `delcampe-order.ts` performs it, behind `GET …/sales/by-delcampe-order` and `POST …/sales/delcampe-order`.

- **The order is recorded whole or not at all, and what the page says about money is read three ways.** All-or-nothing is #610's rule from the other direction and it is *sharper* here: Allegro's flow (#463) reviews a dialog before it writes, while this click happens on Delcampe's page with nothing in between, so a sale missing a line would understate the proceeds and look complete. Every reason is named at once, each naming its item, because the collector is about to go and fix them and finding the second one after fixing the first is two trips. A row finds its offer on **`Offer.delcampeItemId` first** (#611's exact id — the reason #612 waited for it) and then on the printed `personal_reference` through `offerNoFromPersonalReference`, ADR-0037 §4's rule unchanged; which set went is `mapLineToSets`, which refuses an offer with several sets left rather than picking one. The money: the sale's currency is the **platform's** (#196) and a row whose symbol names another refuses the order — a **bare `$` is not dollars**, since Delcampe writes `US$` and "probably dollars" is how a sale is recorded in the wrong money; `buyerPaidTotal` (#205) is taken only from a total stated **exactly**, in that currency and not below the rows, never from the `±` figure beside it, which is Delcampe's own conversion; and a row priced **zero** is a cancelled item, which zeroes the order with it. The sale is dated by the **latest** row, a bill being complete on the last purchase in it. **Delcampe's phases are not mirrored onto `Sale.status`**: an imported order starts at `ordered`, because the status is what the collector has done about the parcel (#191/#492) and two systems claiming one field is how they drift — which is also why the tracking number printed on the same row is not read, that being answered when the sale is marked sent (#491).
