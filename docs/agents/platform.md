# Platform & Architecture

Stack, collection scoping, routing, database and migrations, RSC boundaries, deployment.

- Collection-scoped access control: `collectionId` on data, owner has full access, checks live server-side.

- Collection URLs: `/c/[collectionSlug]/...`; slug resolution authorizes by internal `collectionId`.

- Better Auth for authentication.

- Prisma with PostgreSQL (minimum **version 15** — migrations use `NULLS NOT DISTINCT`; see ADR-0006). Treat schema changes as product decisions.

- **The Prisma client is generated, not committed, and the commands that need it are what generate it** (#791, #862). `src/generated/prisma/` is gitignored, so nothing in git ever creates it, and without it `pnpm typecheck` fails in over a thousand places — `Cannot find module '../../src/generated/prisma/client'` once, and then every inferred type downstream of it collapsing to `implicitly has an 'any' type`. Three sessions in one day each read that as their own change breaking the tree and went looking in their diff, which is the honest reaction to the symptom and the wrong one. `pnpm typecheck`, `pnpm test:unit` and `pnpm test:integration` each run `scripts/ensure-prisma-client.sh` as a pre-script, and `pnpm check:static` runs it from its serial prelude; it generates the client when it is missing or older than `prisma/schema.prisma` or `pnpm-lock.yaml`, and costs 0.01 s when it is current. So the commands the *Testing Direction* section of AGENTS.md tells you to run cannot see a missing or stale client. It is deliberately **not** a `prebuild` or `prelint` pre-script: `scripts/static-checks.sh` runs lint, typecheck and build concurrently, and a `prisma generate` rewriting the client while `tsc` reads it is the same race that file documents for Next's route types.

- **`pnpm install` is not what guarantees the client, and in a spawned worktree it is usually not what generates it either** (#862). #791 added a root `postinstall`, which fixes the fresh-*clone* case and does not cover the fresh-*worktree* case that nearly every session here is in. A spawned worktree arrives with `node_modules` **already populated** — the harness copies it from the main checkout rather than installing — while the generated client sits *outside* `node_modules`, because Prisma 7's generator writes to `output = "../src/generated/prisma"`, so the copy does not bring it along. Whether the session's own `pnpm install` repairs that is then decided by something with nothing to do with the client: pnpm skips every lifecycle script when it considers an install up to date, so a copied `node_modules` that already matches `pnpm-lock.yaml` gives `Already up to date` in a fifth of a second, no `postinstall`, and no client. Twelve worktrees created together on 2026-09-07 were checked: all twelve had `node_modules`, none had a client. That branch was masked only while the main checkout was *behind* the lockfile, which is what forced every copy to be stale and every session's install to be a real one. **That masking ended on 2026-09-07**, and it did not take a `pnpm install` to end it: pnpm 11 reconciles `node_modules` to the lockfile before running *any* package script, so a `pnpm slot release` in the main checkout — expected to be a no-op — performed a 62-package install and levelled the checkout with the lockfile. There was therefore never a command to avoid, and the condition is live rather than latent: a worktree spawned from that checkout now copies a `node_modules` that already matches, its install is a 200 ms no-op, and it gets no client. That is why the guarantee does not live in the install. The `postinstall` stays, because it still earns its keep on a real clone, and its `prisma/schema.prisma` guard is load-bearing rather than defensive: the Dockerfile's `deps` stage installs from `package.json` and the lockfile alone — `prisma/` arrives a stage later — so an unguarded `prisma generate` would fail the image build in a layer that has no schema to generate from. Copying the schema into that layer is the tempting fix and the wrong one: it would invalidate the install cache on every migration.

- **Rebasing onto a `main` that carries a migration leaves the client *stale* rather than missing, and that is the dangerous shape** (#862). A missing client is loud — one `Cannot find module` and a landslide of `implicitly has an 'any' type`. A stale one compiles, and its tests pass against a schema the branch no longer declares. The rebase rewrites `prisma/schema.prisma` and leaves it newer than the generated client, so `scripts/ensure-prisma-client.sh` catches it and the next `pnpm typecheck`, `pnpm test:unit` or `pnpm test:integration` regenerates before it runs. Anything that does not go through those — `pnpm exec tsc` by hand, the dev server, a script — still needs `pnpm prisma:generate` from you. `pnpm install` will not do it: it skips lifecycle scripts whenever it thinks it is up to date, which after a rebase it usually does.

- Bumping the bundled `postgres:` image to a new major breaks the dev stack: the `db_data` volume keeps the old cluster and 18+ images relocated the data directory. It needs a dump/restore, never just a tag change — follow `docs/development/postgres-upgrade.md`. Production uses an external database and is unaffected.

- **A migration that has been written is never edited — a correction is a new migration.** Not only once it has shipped: an applied migration's checksum lives in `_prisma_migrations`, so touching the file breaks `migrate deploy` on every database that already ran it, starting with the local e2e one, and the only way out is a reset. That the file is still uncommitted, or was written five minutes ago in the same session, changes nothing — the rule has no exception, because the exception is exactly the case where somebody's database has already applied it. Fixing a column in the migration that introduced it is a second migration that drops and re-adds it, with a comment saying why; where the table is new in the same batch there is no data to carry, and saying so in the comment is what stops a later reader looking for the backfill.

- **One session at a time writes a migration.** A migration is a timestamped file, and nothing about working on a branch keeps two of them apart: two sessions each add one, each runs the suite against its own database, each branch is green, and the two only ever meet once both are in one tree — where `migrate deploy` applies them in filename order, an order neither author ran. If that order is wrong, or the two touch the same column, the fix cannot be an edit, because the rule above has no exception: it is a *third* migration correcting the pair, written by whoever notices, which is strictly more work than not having written them in parallel. Per-worktree slots do not help here and are not meant to — they give each worktree its own database, which isolates the *state*, not the *ordering*, and two isolated databases is exactly how both branches came to be green. So a task that adds a migration runs alone; a task without one parallelises freely, which is nearly all of them.

- A data migration that **renumbers a column covered by a unique index must drop that index first**. PostgreSQL checks unique *indexes* immediately — only a unique *constraint* declared `DEFERRABLE` can be deferred, and Prisma writes indexes — while the order rows are updated in is unspecified, so a renumbering that shifts values along an existing sequence transiently duplicates one and fails on whichever row it happens to reach first. It is the classic `UPDATE … SET n = n + 1` collision, and it fails *sometimes*: green on one database and red on another. Nothing in the suite can catch it either, because integration tests run `migrate deploy` against a fresh database, where the table the migration rewrites is empty. `20260814210000_scan_batch_on_purchase` has the hazard and shipped with it deliberately — the whole scan-ingest track (#566–#587) releases together, so no database ever holds the intermediate state, and every fresh deploy renumbers an empty table. Do not copy the shape from it.

- **`prisma format` is not used here, and running it once costs you the diff you were reading** (#840). On a clean tree at `7637244` it rewrote `prisma/schema.prisma` with **1238 insertions and 975 deletions**, none of them semantic: the file is hand-aligned and carries long prose comments above most models, and the formatter re-columnises every field block it meets. Nothing warns, because nothing is wrong — the command did what it is for. What it costs is the thing you were about to check: the twelve lines of the model you just added are now somewhere inside a two-thousand-line reformat, and the only honest way back is `git checkout -- prisma/schema.prisma` and aligning the new block by hand. Align by hand from the start instead. **The figures are dated on purpose** — the schema grows, so re-measure rather than quoting them; the issue that produced this bullet recorded 1302/974 five weeks earlier, and the shape of the finding, not the number, is what carries.

- **`prisma migrate diff` is the only check this project has that a hand-written migration matches the schema — and it is read by grepping for your own table, never for emptiness** (#840). Every migration here is written by hand and no script, test or CI job verifies any of them against `prisma/schema.prisma`, so this command is not one option among several. But on a clean tree it already reports **thirteen tables**, so *"the diff is not empty"* carries no information at all and *"my table is not in the diff"* carries all of it. Read it that way and it works; read it for silence and it can only ever tell you that this project has a schema.

  **The invocation is not the one the Prisma documentation leads with, and the obvious one fails.** `--from-migrations` needs `datasource.shadowDatabaseUrl` in `prisma.config.ts`, which is not set and is not being set — so on Prisma 7 it exits with that message rather than a diff. What works is to deploy the migrations to a throwaway database and diff *that* against the schema, which is the same comparison by a different route:

  ```
  PATH="$HOME/.orbstack/bin:$PATH" pnpm e2e:db:up      # docker, per the bullet below
  eval "$(scripts/dev-slot.sh env)"
  PGPASSWORD=stamporama createdb -h localhost -p "$STAMPORAMA_E2E_DB_PORT" -U stamporama stamporama_shadow
  DATABASE_URL="postgresql://stamporama:stamporama@localhost:$STAMPORAMA_E2E_DB_PORT/stamporama_shadow" \
    pnpm exec prisma migrate deploy
  DATABASE_URL="postgresql://stamporama:stamporama@localhost:$STAMPORAMA_E2E_DB_PORT/stamporama_shadow" \
    pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma
  ```

  **Deliberately not a `package.json` script** (#840 asked). It would have to own a database and a URL, which `scripts/e2e-db.sh` already owns and which is the only reason that file exists; a second entry point into the same Compose project is how the two drift apart. The value the script was for — running it the same way twice — is what writing the invocation down here buys instead.

- **What the thirteen tables are, and why the count is the wrong thing to remember** (#840). Two kinds, and neither is a reason to ignore a hit:

  - **Seven are structural and permanent**: `acceptance_profile_certificate_status`, `acceptance_profile_format`, `platform_category_lesson`, `stamp_catalog_price`, `stamp_format_factor`, `want_certificate_status` and `want_format`, each reported as a *removed unique index*. They are the `NULLS NOT DISTINCT` indexes of ADR-0006 — which is also why this project requires PostgreSQL 15+ — and Prisma's schema language cannot express one, so the migration creates it and the schema cannot declare it. `SELECT c.relname FROM pg_index x JOIN pg_class c ON c.oid = x.indrelid WHERE x.indnullsnotdistinct` re-derives the list against any database, which is the answer to keep; any future index of the same kind makes it eight.
  - **Six are ordinary pre-existing drift** that nobody has closed: an index Prisma would name differently (`allegro_category_parameter_memory`), a `DEFAULT 'EUR'` the schema does not declare (`collection.baseCurrency`), an index in the database and not in the model (`contact.defaultDelcampeListingProfileId`), a foreign key the migration wrote without `ON UPDATE CASCADE` (`issue.collectionAreaId`), and `DEFAULT ARRAY[]::text[]` on four scalar-list columns (`lot_builder_preset`, `offer_photo_entry`). Every one is expressible in the schema, so every one is closeable — by a *new* migration, never an edit.

  **The list above is evidence, not a lookup table.** It was taken at `7637244` and the second kind grows whenever a hand-written migration says something the model does not; a reader who treats it as exhaustive and finds a fourteenth table will conclude they have real drift, and a reader who treats it as a permitted-noise list will wave through their own. Neither is what it is for. **Nothing about a difference being old makes it noise** — the only question the command answers is whether *your* table is in the output, and the seven above are the only entries where the answer "yes, and it is fine" is structural rather than a judgement.

- Explicit module boundaries under `src/`.

- A **server component must not import a value from a `"use client"` module**. Under RSC those exports arrive as *client references*, not as values, and nothing warns: `Math.min(MAX_CARDS, n)` where `MAX_CARDS` came from a client file is `NaN`, which is how the ref-card sheet (#565) printed one card for every count typed — silently, and only once a `count` was in the URL, because the no-count path returned its default before ever touching the constant. A constant both halves read belongs in a **pure `src/lib/` module** neither owns (`MAX_REF_CARDS` / `parseRefCardCount` in `location-ref.ts`, moved there by #569), and the parse belongs there too so a unit test can hold it. The reverse direction — a client component importing a pure module — is fine and is the idiom.

- **A runtime import cycle between `src/lib/` modules fails at module-init time, and neither the type check nor the test suites see it.** #658 closed one — `trade-candidates.ts` → `trade-lines.ts` → `trade-line-actions.ts` → `trade-proposals.ts` → back — and the whole thing typechecked and passed 3598 tests, because `tsx` happened to enter the ring at a module whose constants were already evaluated. Under webpack's RSC graph it entered elsewhere, and a `const` read at module scope from the half-initialized module threw `Cannot access 'X' before initialization` on a route that had nothing to do with the change. Two things follow. Each layered pair here states which side is **above** in its own header (`trade-access.ts`'s no-imports-upward rule, `trade-reservations.ts`'s, `item-valuation.ts`'s) — read those before adding an import, since a module that is imported *by* a lower one is below it whatever its header claims about the domain. And where a rule needs only the *fact* that a record exists, take the ids rather than the read that produces them: `TradeActionSources.unvaluedLineIds` and `proposedLineIds` are that shape, and it is what keeps a low module from reaching up for a high one's read. A cycle is cheap to check for — walk the non-`import type` edges under `src/` and look for a back edge — and worth checking whenever a new domain module is wired into an existing chain.

- **A control character in source is written as an escape, never as a raw byte.** A composite map key is a natural place to want one — `` `${vendorId}\u0000${number}` `` cannot alias another concatenation the way a `-` or a `:` can — and five files had been typing the NUL *literally* into the template. It runs correctly and it typechecks, and the cost lands somewhere else entirely: `grep` and `ripgrep` classify a file holding a 0x00 byte as **binary** and skip it in silence. `grep -n "export" src/lib/issues.ts` answered with nothing at all, on a 2,500-line module exporting fifty-two things, and `rg` said only "binary file matches" — so the module was invisible to every ordinary code search until somebody happened to open it. What makes it dangerous is that the failure looks like an *answer*: a search that returns no hits reads as "this codebase does not have that", which is how `listIssueYearFacets` came to look like it did not exist. `\u0000` is the house spelling (it was already what `offer-title-template.ts` used for `EMPTY_MARK` two lines above the raw ones), it is unambiguous inside a regex literal as well as a string, and unlike `\0` no following digit can turn it into something else. The same goes for `\u0003` and any other invisible sentinel: the point of the character is that data never contains it, and none of that requires the *source file* to contain it either.

- **The pnpm version has exactly one pin — `packageManager` in `package.json` — and everything else derives from it** (#1050). `pnpm/action-setup` in `.github/workflows/ci.yml` carries no `version:` input and reads that field; the Dockerfile's `corepack enable` reads it too; nothing else states a version. A sweep for the literal `11.25.0` before the pnpm 12 bump returned **one line**, and a sweep for the mechanisms that could carry a second (`corepack`, `action-setup`, `packageManager`, `npm i -g pnpm`, `PNPM_VERSION`, `pnpm@`) returned eight lines across four files, none of them a version. So a pnpm bump is one edit, and a session that goes looking for the other pins is looking for something that is not there — which is worth saying, because `node` genuinely does have three (Dockerfile, five `setup-node` steps, and the `renovate.json` rule that groups them).

- **Corepack is what honours that pin, and it is versioned separately from pnpm and from Node** (#1050). pnpm 12 renamed its npm entry point from `bin/pnpm.cjs` to `bin/pnpm.mjs`; corepack maps that path per version range and only learned the new one in **0.35**. The whole **Node 22 line ships corepack 0.34.x** and cannot launch pnpm 12; `node:24.20.0-alpine`, which the Dockerfile builds on, ships 0.35, and the image build was checked against it rather than assumed. **The failure names no version and reads as a corrupt download** — `Cannot find module '<cache>/corepack/v1/pnpm/12.3.4/bin/pnpm.cjs'`, a bare Node stack trace with no pnpm output at all — so the instinct is to clear the corepack cache, which fixes nothing because the fetched tarball is correct and the path looked for is not. CI does not go through corepack (`pnpm/action-setup` installs pnpm itself), so this is a **local-machine** failure and neither CI nor the image can see it.

- **`onlyBuiltDependencies` in `pnpm-workspace.yaml` had been dead since pnpm 11 while reading as load-bearing, and `allowBuilds` is the live setting** (#1050). The file named the same five packages twice — `allowBuilds` as a map, `onlyBuiltDependencies` as a list — and the Dockerfile comment beside the install credited both for keeping `ERR_PNPM_IGNORED_BUILDS` away. pnpm's own changelog settles it: *"`onlyBuiltDependencies`, `onlyBuiltDependenciesFile`, `neverBuiltDependencies` and `ignoredBuiltDependencies` were replaced by `allowBuilds` in pnpm 11 and silently ignored since, so a workspace migrated from pnpm 10 kept them around looking active."* The dead block is gone; a clean install and a `--target deps` image build both still run the prisma, esbuild, sharp and unrs-resolver build scripts. **The general shape is the one worth carrying: pnpm 12 fails on a setting it does not recognise, and says nothing at all about one it recognises and ignores** — so *the install is green* is not evidence that a setting in that file does anything. Check a build-scripts setting against the changelog, not against the exit code.

- **pnpm 12 prepends a second YAML document to `pnpm-lock.yaml` recording pnpm itself** (#1050). `lockfileVersion` stays `'9.0'` and the existing document is untouched, but the file gains ~100 lines in front of it: a `packageManagerDependencies` importer pinning the `packageManager` version, and `packages`/`snapshots` entries for all eight `@pnpm/exe.*` platform binaries — every platform, not the one that ran the install, so it is reproducible across macOS, Linux, glibc, musl and Windows. **It is written once, by the first install that materialises `node_modules`, and `--frozen-lockfile` does not stop it** — a dry run against a populated `node_modules` reports the lockfile up to date and then a real install after `rm -rf node_modules` writes the block, which is a confusing pair to meet in that order. Two installs after that leave the file byte-identical. The consequence that costs something is that the addition is at the **top** of the file, so every open branch carrying a lockfile change conflicts there and must be rebased.

- **TypeScript 7 moved the compiler API out of the package root, and that is a change of package shape rather than a stricter compiler** (#1051). Measured on **7.0.2** on 2026-09-10, and stated with the version because the whole claim is about one: `node_modules/typescript/package.json` declares `exports["."]` as `./lib/version.cjs`, and that file is three lines exporting `version` and `versionMajorMinor`. Nothing else. `createSourceFile`, `forEachChild`, `ScriptTarget`, `ScriptKind`, `Extension` and every `is*` predicate are gone from `import ts from "typescript"` — the parser lives in the Go binary now, and the JS surface is under `typescript/unstable/*`. **The distinction is the whole of what a later session needs.** The bump produced 30 type errors and two failing unit tests, and **not one of them was in `src/`**: the only two importers in the tree are `tests/unit/unit-suite-purity.test.ts` and `tests/unit/stamp-form-dialog-invalidation.test.ts`, which walk a parse tree rather than use it for types. That nothing simply stopped being checked was established rather than assumed — a planted `export const n: number = "not a number"` still reported `TS2322` under 7.0.2. And `Integration tests` and `Extension checks` were green on Renovate's #865 for a reason, not by luck: nothing under `tests/integration/` imports the package at all, and `extension/`'s own `tsc --noEmit` passes on 7.0.2, which for that workspace is a two-major jump from the 5.9.3 it declares.

- **What blocks the bump is `typescript-eslint`, and on 2026-09-10 no published version of it accepted TypeScript 7** (#1051). `@typescript-eslint/typescript-estree` reads `ts.Extension.Cjs` at the top of `dist/create-program/shared.js`, so it dies **at module load**, before any `eslint.config.mjs` is consulted — which is why no config change avoids it. The version installed here is 8.63.0 and it arrives transitively, `eslint-config-next` → `typescript-eslint`, so it is not ours to pin. **Bumping it is not the answer either, and that was checked rather than hoped for**: `latest` was 8.70.0, there is no v9, and its tarball still reads `ts.Extension.Cjs` on the same line and still declares `peerDependencies.typescript` as `">=4.8.4 <6.1.0"`. **The route that looks available and is not is worth more here than the ones that are**: scoped `pnpm` overrides pinning `typescript` back to the 6.x this project declares, under all seven typescript-eslint parents, install a second copy and change nothing, because `typescript` is a **peer** and the peer is satisfied by the root's. So `pnpm lint`, and with it `Static checks`, cannot pass on TypeScript 7 by any arrangement of this tree.

  **`pnpm install` says so before any CI run, and `main` says nothing** — that contrast is the cheap early signal, and it is one line: `✕ unmet peer typescript / Installed: 7.0.2 / Wanted ">=4.8.4 <6.1.0"`, naming all eight `@typescript-eslint/*` packages. The 6.x on `main` sits inside that range, so the warning is genuinely new rather than background noise.

  **And the error string collides with an unrelated incident already recorded in `renovate.json`.** That file's framework-group description says `eslint` cannot move without `eslint-config-next` because, split across two groups, it *"sat red for eight weeks with TypeError: Cannot read properties of undefined (reading 'Cjs')"* (#47). **Same string, different cause** — that one was a config/plugin split, this one is a version gap between typescript-eslint and the compiler. Do not merge the two incidents on the strength of the message.

- **There is a replacement route for a session that needs an AST, and it is recorded as available rather than as recommended** (#1051). `typescript/unstable/ast` exports every predicate and enum the two tests use — `isImportDeclaration`, `isNamedImports`, `isCallExpression`, `isIdentifier`, `isStringLiteral`, `ScriptTarget`, `ScriptKind` — and `forEachChild` is a method on `Node` rather than a free function. What has no replacement is producing a `SourceFile` from text: there is no `createSourceFile(text)` anywhere in the JS API. The route that works is `new API({ cwd }).updateSnapshot({ openProjects: [<tsconfig>] })` from `typescript/unstable/sync`, then `project.program.getSourceFile(path)`, which spawns the native binary and took **177 ms** to load this project whole and hand back a tree whose imports read correctly. **Two costs, both named because neither is obvious from the timing**: the package calls that surface `unstable` in its own export map, so a minor release may move it; and it puts a subprocess inside `pnpm test:unit`, including inside `unit-suite-purity.test.ts`, which is the test that enforces the suite's purity rule.

- **Every host port this project pins comes from a per-worktree *slot*** (#781). Two sessions in two worktrees could not both run the suite before this: `docker-compose.e2e.yml` had no `name:`, so Compose named the project after the directory — two directories, two projects, both binding host 5433, and the second `docker compose up -d --wait` dying on `port is already allocated`. A slot is a small integer, and slot N shifts every pinned port by 10 × N: the app container's 3000, a bare `next dev`'s 3002, the e2e database's 5433. It also names the e2e Compose project `stamporama-N`, so the project follows the slot instead of the directory. **The main worktree is slot 0 and writes nothing down** — that is today's numbers and today's project name exactly, which matters because it is the path the project is actually used on. Linked worktrees take 1, 2, 3… on first use. `scripts/dev-slot.sh` resolves it, `pnpm slot` prints the table, and `pnpm test:integration` / `pnpm e2e:db:reset` go through `scripts/e2e-db.sh` — which is why `localhost:5433` no longer appears three times in `package.json`.

- **A slot is reclaimed by the worktree going away.** There is deliberately no shared registry: a slot lives in that worktree's own untracked `.env.slot`, and allocation reads those files through `git worktree list`. A directory that is gone therefore holds nothing, and no table exists that could outlive the thing it describes — which is the failure this design is avoiding, because a port held by a worktree nobody removed surfaces weeks later, in an unrelated session, as `port is already allocated` with no visible cause. `pnpm slot release` frees a number without removing the worktree, and writing `STAMPORAMA_SLOT=` into `.env.slot` (or the environment) pins a particular one. **`package.json` declares that script as the path alone, with no verb of its own, and `dev-slot.sh` defaults to `show`** (#913): pnpm *appends* a script's arguments rather than inserting them, so the `show` that used to be written there occupied `$1` and pushed the caller's verb into `$2`, where nothing read it — `pnpm slot release` printed the table and released nothing, for as long as the command has existed, and two sessions reported a slot freed that was still held. The default has to be `show` rather than the older `env` for bare `pnpm slot` to keep printing the table as the bullet above says it does; nothing depended on the old default, because `scripts/e2e-db.sh` is the only caller that wants the `export` lines and it names `env` explicitly. The *container* is reclaimed with the slot for the same reason the project name is derived from the slot: a container left behind by a removed worktree is the one Compose reuses when the next worktree takes that number, rather than a stranger holding the port. What that does not tidy is a slot nobody claims again — `pnpm slot` shows who holds what and `pnpm e2e:db:down` stops one, as does `docker compose -p stamporama-N -f docker-compose.e2e.yml down`.

- Two things sit outside the slot on purpose. `.claude/` is untracked and per-worktree, so `.claude/launch.json` cannot interpolate anything and cannot follow the slot: a worktree that starts a dev server through it sets that file's port by hand to the number `pnpm slot` prints. And `max_connections=300` on the e2e database stays where it is — it was sized for **one** suite (workers × Prisma pool), and slots give each worktree its own database precisely so that budget is never split between two.

- **`docker` must be on the PATH `pnpm test:integration` is run with, and *absent from this PATH* is a different claim from *not installed*** (#933). The two are indistinguishable from inside a session and were confused four times in two days: two sessions checked Docker Desktop, colima, podman, `~/.docker/bin` and `~/.rd/bin`, found none of them, and reported that the machine had no Docker. Every check was correct and the conclusion was false. **The cost is never the failed command; it is the suite that stops being run** — this file's own rule sends a session to `pnpm test:integration` before a schema or domain-logic change, and a session that believes the runtime is missing does not verify some other way, it stops verifying, honestly, and CI sees those cases first.

- **The reusable half is *why* the two claims come apart: a session does not compute its PATH, it inherits it**, from whatever process launched it — so it can be running an environment older than the machine's own configuration. That is exactly what happened here, and it is measurable rather than inferred. The user moved from Docker Desktop to OrbStack on the evening of 2026-09-07 and `~/.zshrc` gained `export PATH="$HOME/.orbstack/bin:$PATH"` as its **line 17**, at an mtime of `2026-09-07 20:03`. A session's PATH here begins `antigravity-ide`, then `postgresql@18`, then `nvm` — `.zshrc` lines 15, 12 and 10, in the order three unconditional *prepends* produce — and does not contain line 17 at all. **If the rc file were simply unread, the first two would be missing too**; a clean non-interactive `zsh -c` carries none of the three, which is what unread actually looks like. - **The connection pool must never be what keeps a process alive** — `src/lib/db.ts` sets `allowExitOnIdle: true`, and that one option is the difference between a ten-minute required run and a four-minute one (#880). `pg` defaults `idleTimeoutMillis` to 10 s and keeps the idle socket *refed*, so a process whose last query has already returned sits doing nothing for ten seconds and then exits. `node --test` runs one process per file, and the integration suite is 143 files: 135 of them paid that ten seconds each — **a fixed ~1,350 seconds of worker time per run, whatever the machine.** Removing it took the `Integration tests` job from **10 min 03 s to 3 min 31 s** (its test step, 559 s to 168 s), and `Static checks` at ~4 min is now the wall clock. It is the same rule every background timer in `instrumentation-node.ts` already states for itself — "the timer never keeps the process alive on its own" — and it holds for the same reason: what keeps the server up is its HTTP listener. A client *checked out* for a query is still refed, so nothing in flight can be cut short by it.

- **Measure per-file before optimising the suite, and measure at the concurrency you are asking about.** `pnpm test:integration:time [concurrency]` (`scripts/time-integration-tests.mjs`) spawns each file the way the runner does and prints the wall clock of each, so the parts add up to the whole. Pass **4** for a question about CI — a GitHub `ubuntu-latest` runner has four cores where a dev machine has sixteen, and a suite measured locally looks four times healthier than it is. Baseline at concurrency 4, 2026-09-07, both halves measured on the same tree: **370.2 s before, 32.6 s after**, the same 1,656 tests in 143 files, median file 0.8 s, slowest `demo-seeder.test.ts` at 6.6 s, pool utilisation 98%. The number that mattered was not any file's — it was that 135 files sat within a second of each other at a **flat 10.4 s floor**, and the eight fast ones were exactly the eight that either never opened the database or happened to call `prisma.$disconnect()` in an `after` hook. A flat distribution is the finding: it says the cost is per-process and structural, and that the obvious fixes — sharding across databases, attacking the slowest files, moving tests off the per-PR path — would each have divided the idle wait rather than removing any of it.

- **Quote a local speed-up as a ratio and you will be wrong about CI; quote it as seconds removed and you will be right.** #880 measured 370.2 s → 32.6 s locally, an 11.4×, and projected the `Integration tests` job at ~1.5 min. It came in at **3 min 31 s** — a 3.3×. Nothing about the diagnosis was wrong: the waste removed was the same fixed ~1,350 seconds of worker time both times, and the arithmetic reconciles (2,236 slot-seconds before, 672 after, 1,564 gone against 1,350 predicted). What does not transfer is the *fraction*, because a runner's real work is roughly five times slower than this machine's — so the same fixed tail was 91% of the local run and 60% of CI's. **A fixed cost is a shrinking fraction of a slower machine.** Say how many seconds a change removes, and let the ratio fall out of whichever machine is being asked about.

- **`next build` and `tsc` cannot share Next's generated route types, and the collision is silent** (#881). Every build rewrites `<distDir>/types/routes.d.ts` — 26 KB, through a plain `fs.promises.writeFile`, with no atomic rename — partway through, so a `tsc` reading it at the wrong instant is handed a truncated file and fails somewhere that has nothing to do with the change. `scripts/static-checks.sh` therefore hands the typecheck `.next-typecheck/types/`, a copy taken while nothing is running, reached through `tsconfig.typecheck.json`. **Do not "simplify" that into giving the build its own `NEXT_DIST_DIR` instead.** `next typegen` bakes the dist directory into `next-env.d.ts`, so the two processes would then fight over *that* file at the repository root — and running typegen against a non-default dist directory also **appends it to the tracked `tsconfig.json` and reformats the whole file**. Both were tried; the copy is what is left. What keeps the copy honest is `tsc --listFiles` against each config in turn: 2,893 files, identical sets.
