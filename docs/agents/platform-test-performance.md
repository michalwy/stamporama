# Platform: how the suites run, and what they cost

The connection pool, the integration suite's isolation rules, measuring it, and the shape of `Static checks`. Read before changing a suite's runtime or CI timing. Split out of [`platform.md`](platform.md) (#2700).

- **The connection pool must never be what keeps a process alive** — `src/lib/db.ts` sets `allowExitOnIdle: true`, and that one option is the difference between a ten-minute required run and a four-minute one (#880). `pg` defaults `idleTimeoutMillis` to 10 s and keeps the idle socket *refed*, so a process whose last query has already returned sits doing nothing for ten seconds and then exits. `node --test` runs one process per file, and the integration suite is 143 files: 135 of them paid that ten seconds each — **a fixed ~1,350 seconds of worker time per run, whatever the machine.** Removing it took the `Integration tests` job from **10 min 03 s to 3 min 31 s** (its test step, 559 s to 168 s), and `Static checks` at ~4 min is now the wall clock. It is the same rule every background timer in `instrumentation-node.ts` already states for itself — "the timer never keeps the process alive on its own" — and it holds for the same reason: what keeps the server up is its HTTP listener. A client *checked out* for a query is still refed, so nothing in flight can be cut short by it.

- **The integration suite never needs the ECB to answer** (#1648). It is a required check, and on 2026-10-04 a `504` from the ECB failed it on three runs in four, on a pull request that had not touched rates. A test that asserts what the ECB says reads it from `tests/fixtures/ecb/` through `installEcbStub()` — the ECB's own responses, recorded once, with the data API's key and window still applied, so the request the code builds and the parsing of a real answer are both still exercised. Fourteen other files reach the daily table in passing (a write converting a price) and treat a failed fetch as *no rate*, as the app does; the suite was run with every ECB request refused and passed whole, and that is the property to keep: **a test may let a lookup fail, never depend on one succeeding.** Check it again after adding one with a `--import` guard that throws on `ecb.europa.eu`, through `NODE_OPTIONS`.
- **An integration test counts only its own rows; the database is shared with every file running at that moment** (#2199). The runner starts one process per file, all against the one e2e database, so a count over a whole table — `prisma.photo.count()` with no `where` — also counts what other files create and delete meanwhile. The one-off collage test asserted *nothing was stored* that way and failed on `main` and on a Renovate batch at random; run beside the 34 other files that write photos it failed 10 rounds in 10, and once scoped to its own collection it passed 20 in 20. A *nothing changed* assertion scopes the count to the test's collection (or another owner only that file creates). A table with no collection to scope by is counted whole only when that file is its sole writer: `storage-cache.test.ts` counts `storageCacheEntry` whole, and stays correct only while no other file writes one.
- **Measure per-file before optimising the suite, and measure at the concurrency you are asking about.** `pnpm test:integration:time [concurrency]` (`scripts/time-integration-tests.mjs`) spawns each file the way the runner does and prints the wall clock of each, so the parts add up to the whole. Pass **4** for a question about CI — a GitHub `ubuntu-latest` runner has four cores where a dev machine has sixteen, and a suite measured locally looks four times healthier than it is. Baseline at concurrency 4, 2026-09-07, both halves measured on the same tree: **370.2 s before, 32.6 s after**, the same 1,656 tests in 143 files, median file 0.8 s, slowest `demo-seeder.test.ts` at 6.6 s, pool utilisation 98%. The number that mattered was not any file's — it was that 135 files sat within a second of each other at a **flat 10.4 s floor**, and the eight fast ones were exactly the eight that either never opened the database or happened to call `prisma.$disconnect()` in an `after` hook. A flat distribution is the finding: it says the cost is per-process and structural, and that the obvious fixes — sharding across databases, attacking the slowest files, moving tests off the per-PR path — would each have divided the idle wait rather than removing any of it.

- **Quote a local speed-up as a ratio and you will be wrong about CI; quote it as seconds removed and you will be right.** #880 measured 370.2 s → 32.6 s locally, an 11.4×, and projected the `Integration tests` job at ~1.5 min. It came in at **3 min 31 s** — a 3.3×. Nothing about the diagnosis was wrong: the waste removed was the same fixed ~1,350 seconds of worker time both times, and the arithmetic reconciles (2,236 slot-seconds before, 672 after, 1,564 gone against 1,350 predicted). What does not transfer is the *fraction*, because a runner's real work is roughly five times slower than this machine's — so the same fixed tail was 91% of the local run and 60% of CI's. **A fixed cost is a shrinking fraction of a slower machine.** Say how many seconds a change removes, and let the ratio fall out of whichever machine is being asked about.

- **`Static checks` runs its three checks at once, and what that bought was 40 seconds, not 94** (#881). `scripts/static-checks.sh` starts `pnpm lint`, `tsc` and `pnpm build` together inside the one job, which keeps its name — splitting them into three jobs would make each its own required context and needs the ruleset on a protected `main` changed first, which is the user's decision and not a session's. Serially the three were 101 s + 60 s + 34 s = **195 s**; concurrently on a four-core runner they were **155 s**, and the job went from **4 min 09 s to 3 min 05 s**. The parts say why the overlap is partial: each check ran roughly twice as slowly as it does alone — build 101 → 154 s, lint 60 → 112 s, typecheck 34 → 70 s — because four cores do not hold three CPU-bound processes, and because `next build` runs its own `tsc` over the same program, so the typecheck is paid for twice inside that window. **The job is no longer the wall clock**: `Integration tests` on the same run was 3 min 34 s, so anything further taken off `Static checks` is worth nothing at all until that one moves.

- **`next build` and `tsc` cannot share Next's generated route types, and the collision is silent** (#881). Every build rewrites `<distDir>/types/routes.d.ts` — 26 KB, through a plain `fs.promises.writeFile`, with no atomic rename — partway through, so a `tsc` reading it at the wrong instant is handed a truncated file and fails somewhere that has nothing to do with the change. `scripts/static-checks.sh` therefore hands the typecheck `.next-typecheck/types/`, a copy taken while nothing is running, reached through `tsconfig.typecheck.json`. **Do not "simplify" that into giving the build its own `NEXT_DIST_DIR` instead.** `next typegen` bakes the dist directory into `next-env.d.ts`, so the two processes would then fight over *that* file at the repository root — and running typegen against a non-default dist directory also **appends it to the tracked `tsconfig.json` and reformats the whole file**. Both were tried; the copy is what is left. What keeps the copy honest is `tsc --listFiles` against each config in turn: 2,893 files, identical sets.

- **`next build` type-checks the same program `pnpm typecheck` does, and that duplication is kept on purpose** (#889, decided by the user on 2026-09-30). `typescript.ignoreBuildErrors` would remove it and make `pnpm build` succeed on a tree that does not type-check. The user answered that question no, so `pnpm build` stays self-sufficient: it is what a person runs locally to see whether a change compiles, and the Dockerfile's builder stage runs nothing else. A release image could not have been built from a failing tree either way, because `Build image (…)` carries `needs: [static-checks, …]`. What the duplication costs is **42–61 s** of `Running TypeScript` inside the build's log on CI. What removing it would buy is **nothing on a required run**: across the ten green `main` runs up to 2026-09-30, `Static checks` took 155–233 s and `Integration tests` 267–359 s, so the job finished 50–190 s under the ceiling every time. On a release image it would save ~41 s of a ~350 s per-architecture build. `next.config.mjs` states the decision beside the option. **Do not re-file this as a discovery**; reopen it only when `Static checks` is the wall clock again.

- **Next's build cache is absent from CI on purpose, and `No build cache found` on every run is expected** (#890, decided by the user on 2026-09-30). Nothing restores or saves `.next/cache`, so every `Static checks` run compiles from nothing: `Compiled successfully in` 63–88 s. The first reason is the ceiling measured in the item above, which holds here too: taking the whole compile out of `Static checks` changes a required run by 0 s. The second is how the cache would restore. GitHub scopes an Actions cache per branch and falls back only to the default branch, so a branch's first run restores `main`'s cache, and every branch changes source, which is what the cache is keyed on. A key made from dependencies alone would hit, but it can restore stale output, and that is worse than none. The third is the image. The Dockerfile's `pnpm build` runs inside buildx and cannot see an Actions cache. Buildx on a hosted runner does not keep a `RUN --mount=type=cache` between runs without a further action that moves it in and out. That dependency would buy at most the ~46 s compile of a ~140 s build step, on release tags only. **Revisit only together with a change that moves `Integration tests`**, or if release image time starts to matter.
