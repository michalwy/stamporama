# Shared UI Patterns & Primitives

Toolbars, filters, expansion, reordering, tooltips, icons, thumbnails, tokens, toast, inline editing.

- A list filter over **several values at once** is `MultiSelectFilter` (`shared/multi-select-filter.tsx`, #425) — a toolbar-sized button that opens a checkbox list, never a `<select multiple>`, which turns into a scrolling box the height of the toolbar. It reads the one value's name when one is ticked and **counts** them when more are (`3 conditions`), so the control cannot grow and shove the toolbar around. Selection applies as it is made — the list behind it is what says what a tick did, so an Apply button would only ask the collector to confirm what they can already see — and *clearing* is the list's own first row rather than a control beside the trigger, since clearing and unticking everything are one act. It is a **popover, not a layer**: it keeps its own Escape and outside-click instead of joining the escape stack (#361), the same call the notification centre makes, and portals to `<body>` with fixed positioning so a toolbar's `overflow` cannot clip it. The value rides in the URL comma-separated, exactly as `areaIds` does, and an empty list is the **absence** of the filter rather than an unmatchable empty set. Server-side, one axis keeps **one** filter on it: `conditionIds` / `formatIds` / `deliveryStates` (#425, #427) replaced their singular forms on `ItemListFiltersPaginated` **outright**, and every caller pinning one value — a duplicate group addressing its own members, the sale-lot composition picker's `delivered` (#164), `GROUP_ELIGIBILITY` — passes a single-entry list through the same field, so there is never a second knob to keep in step. Renaming rather than adding is also the only way the compiler finds the callers; where one is reached by a **spread** it cannot (`GROUP_ELIGIBILITY`, the duplicate-grouping valuation filters), so those carry a `satisfies` / an explicit annotation — an unrenamed key in a spread is silently dropped, and dropping `deliveryState: "delivered"` would quietly widen a group's eligibility. Two axes are **not a plain `in`**, and share one helper (`nullableIdWhere`): format, where `"single"` is the *null* format (ADR-0020), and certificate, where `"none"` is (ADR-0006 §2, #428). A null is never a member of an `in`, so ticking the sentinel beside a real value is two branches ORed — and that `OR` goes into `buildItemWhere`'s **AND list**, never the top level, where the search's own `OR` would collide with it (and where two such axes at once would swallow one another). Certificate had **no filter at all** before #428 — the field existed only so a duplicate group could address its own members — which is why adding the control came with the rename rather than after it. An unrecognised delivery state is **dropped** from the list rather than passed through, so a stale link narrows to the states it does name and, once nothing is left, shows the whole list rather than an empty screen.

- Row-level actions go in a single `⋮` menu, not a cluster of per-row buttons. Use the shared `RowActionsMenu` (`src/app/c/[collectionSlug]/shared/row-actions-menu.tsx`); destructive actions get `danger` + `separatorBefore`. Dialog-opening actions expose `{ action, dialog }` hooks rendered at the row level (see `use-price-details-action.tsx`, `use-inventory-copy-actions.tsx`) so the dialog survives the menu closing. Section-level adds (e.g. + Add area) stay as standalone buttons. An action a *precondition* blocks is **disabled with a `hint`**, not hidden (#273): the hint is a muted second line under the label saying why, because a disabled control never gets a hover event and a silently missing entry is unguessable. Hide it only when the row itself already answers the question — a copy not marked *For sale* shows no offer action, since the disposition chip is right there. A handful of the most-repeated actions are additionally **promoted onto the row** as icon buttons (`RowQuickActions` + `pickRowActions`, `shared/row-quick-actions.tsx`), which is the shape #261 was missing: a promotion is a **shortcut, never a move** (the entry stays in the menu, so nothing is reachable only by the icon), the button is an **icon with a tooltip and no label**, and it is **always drawn — dimmed at rest, full strength on row hover**, never revealed *by* the hover: appearing on hover makes aiming a two-step move (hover to find out where the buttons are, then aim), which is worse than the dimmed icon it was meant to save. It carries `tabIndex={-1}` (#445/#446) so a row keeps one tab stop. A **grouped** list keeps the menu (#516): the copies inside an expanded duplicate / filing / issue group are ordinary `InventoryItemRow`s, and grouping decides what a row is listed *under*, never what may be done to it. The three grouped branches used to pass `readOnly` instead — which is what hid it — so the handlers now travel as one `CopyRowActions` bundle (`inventory-copy-list.tsx`), built once in `InventoryListPanel` and spread onto the flat list and threaded through each group list and row. One prop rather than thirteen at each of two layers is the point: a new action reaches the grouped views without anyone remembering to plumb it, which is the failure mode #516 *was*. The **group row itself** still carries no menu — #422 deliberately replaced its one entry with the select-gutter checkbox. Callers pass the *same* `RowAction` objects they gave the menu, so a shortcut and its entry cannot drift — which is why an icon must name its action on its own (`Add copy` is `⧉`, not a second `＋` beside `Add stamp`). Promoted so far: the Issues list (issue row: edit / add stamp / add copy; stamp row: edit / add child stamp / add copy), the **Copies** list (edit / edit stamp / add to offer / add to new offer), the flat **Stamps** list (edit / add copy), the **Wants** list (detail page / edit), the **Offers** list (edit / sell), the **Purchases** list (edit alone) and the **Auction lots** list (bid unchanged / contents) — with the **Sales** list deliberately left alone (#527). Each list promotes what *it* repeats rather than a fixed trio — the flat stamp list has no *add child stamp*, because a variant is added from the issue tree where its parent is on screen, and the copies list promotes **both** offer verbs because they are one decision made per copy ("does this join a listing or open one"), and promoting only *add to offer* would have made it the accidental default for want of a second click. The copy row is rendered from eight screens and takes an `actionsOverride`, so the promotion is picked from the *resolved* list: a screen that hands the row fewer actions simply shows fewer icons, and `pickRowActions` skipping an absent key is what makes that silent rather than a crash. What a list does **not** promote is decided by three subtractions, which is what settled #527's four remaining lists: an action the **row's own click** already performs (*Open* everywhere, *Open sale* on a lot) is not promoted, since an icon aimed at what the whole row does is a smaller target for the same result; an action the row already draws as a **labelled control** — the offer row's and the lot row's `Listing` chip, the sale row's `Transaction` chip — is not promoted either, a shortcut past the menu being the point rather than a second copy of a control that is already on screen; and **destructive** entries are never promoted at all. Applied honestly this leaves *one* icon on Purchases and **none** on Sales, and both are the right answer rather than a shortfall — "no promotion" is a valid outcome, and two dimmed icons duplicating visible controls is exactly the sprawl #125 collapsed. The **auction lot** row is the density case: the busiest menu of the set on the row that already carries inline bid fields, and it takes two — `checked` + `contents`, the watchlist pass itself — while every *bid-fill* entry stays in the menu because the row's own cells are where a new figure is typed. Both are present on every lot (a blocked one disabled with its hint, #273), so the promoted pair is a **constant width** and cannot shunt the closing time and the `⋮` about from row to row, which is what that column's fixed widths exist to prevent. The menu **portals to `<body>`** at z-index 200, so rows living *inside a dialog* must raise it past that dialog's own `zIndexBase + 1` (`zIndex` prop) — otherwise it opens behind the panel, invisible, and the click meant for an entry lands on the backdrop and closes the dialog (#468 hit exactly this). It is also not an escape layer, so a dialog holding such rows takes `dismissable={!menuOpen}` off the menu's `onOpenChange`, or one Escape closes menu and dialog together (#361). An entry that **goes somewhere** carries `href` rather than an `onSelect` calling `router.push` (#557), and the menu and `RowQuickActions` both draw it as a real `<a>` — a `router.push` navigates on a plain left click and on nothing else, so cmd/ctrl+click opened the row in the same tab, the middle button did nothing and the browser's context menu had no *Open link in new tab* to offer, because there was no link. `onSelect` stays what every *other* kind of entry uses (a dialog, a mutation, a `window.open` to a marketplace), none of those being a place with an address; the two together would navigate twice, and a `disabled` entry falls back to the button, an anchor having no disabled state and a dead-looking link that is still followed being worse than no link. The same rule reaches the **rows** through `RowLink` (`shared/row-link.tsx`): a row that reads as a link has to be one, but a row is full of controls and interactive content nested inside an `<a>` is neither valid nor reliably clickable, so the anchor is an **overlay** at `ROW_LINK_Z` over a `position: relative` row and anything needing its own pointer behaviour is lifted with `ROW_LINK_ABOVE`. What gets lifted is not just the controls but **every tooltip** — an overlay over a `Tooltip` swallows the hover it exists for — which in practice means the whole chip line under a row's name, so the row's *name* is the link's surface and the chip line is not; a plain click there still opens the row, because the row keeps its own `onClick` and the lifted region is above the anchor, and the anchor stops its own click so the two cannot both fire. The `role="link"` / `tabIndex` / Enter handling those rows carried by hand comes **off**: the anchor is the tab stop now, and two on one row is one too many. Four rows take it (offer, purchase, sale, auction sale, plus the related-offers card); the **auction lot** row deliberately does not — it is an amounts grid of inline-editable figures, quick-fill controls and popovers, so the overlay would have to be lifted off nearly every part of it and would end up covering only the gaps, and its own `handleRowClick` already answers a modified click with a new tab while *Open sale* in its menu is the real link.

- **Lot / set cards are collapsed by default** (#382) — purchase-order lots, offer sets and an auction sale's lots alike, through the shared `useCardExpansion` (`shared/use-card-expansion.ts`), which owns the state at the *panel* level so one screen has one rule and a Collapse all / Expand all control to operate it. These screens are **scanned** first ("which lots are in this order", "which sets are in this listing") and a card's contents are a second question asked of one of them; expanded-by-default meant a four-lot order opened as several screens of copy rows. Exactly two things open a card unasked: the card the collector **navigated to** (#374's `?lot=`, passed as `initiallyExpandedId` and *seeded* into the state, so it can still be closed by hand and clearing the highlight does not shut it), and a card that **appears while the screen is open** — it was created here, so it is what is being looked at. The latter is derived from the ids themselves rather than from a just-added signal: it covers a create that yields several cards, needs no plumbing through the dialogs, and the first render is the baseline (all three views mount after their data has loaded), so an ordinary page load opens nothing. A lone card is **not** an exception — one rule, nothing to infer. The **sale's packing view** (#166) keeps its cards expanded, deliberately, because a packing list is read rather than scanned, and that exemption is the reason to leave `sold-units-view.tsx` alone. The hook takes an optional third argument, a `CardExpansionStore`, and holds the open set there instead of in component state — the purchase order passes its remembered per-order state, the offer and auction screens pass nothing and are unchanged. Both rules above still hold against a **restored** set, which is the point: the baseline is what was restored, so a lot created while the screen is open still opens itself, and a deep-linked card is seeded on top of what was stored rather than replacing it (that seeding is the one write that happens during render, guarded to the single pass where `known` is still null, and idempotent so a double-invoked render costs nothing).

- A **grouped list** is collapsed by default too, but through `useGroupExpansion` (`shared/use-group-expansion.ts`, #538) and **not** `useCardExpansion` — the Copies list's three groupings (#372/#421/#424) hold the state at the panel so Expand all / Collapse all can speak for the whole list, and the three group rows lost their own `useState`. The two hooks differ on the case that matters: a *card* appearing while the screen is open was created here and opens itself, whereas a grouped list is cursor-scrolled and its rows appear because the collector scrolled — and every open group **fetches its own members**, so a page of forty arriving pre-expanded is four hundred copies nobody asked for. The state is therefore a **mode plus its exceptions** (`expandAll` + `overrides`) rather than a set of open ids: a group loaded *after* Expand all comes in open, which is what the control means on a list whose end has not been reached, while `allExpanded` is read over the ids currently loaded so the label always describes what is on screen. `resetKey` is the grouping mode, since carrying `expandAll` across would open every row of a list nobody has looked at. `toggleAll` clears the exceptions — a statement about the whole list is exactly what overrules the rows toggled by hand. The control sits on its **own line above the rows**, right-aligned, as #382's does: in the filter toolbar it read as one more way of narrowing the list.

- A control that is **auxiliary to a field beside it** carries `tabIndex={-1}` (#445/#446). Tab is how a form is filled in, so it should walk the *fields* — a stop per helper turns a card of three texts or a dialog of six vendors into a slalom, and the collector's hands leave the keyboard for something they never asked to visit. The line is **not "icon vs. label" and not "small vs. large"**, it is *could this control be skipped and the field still be completed*: a copy `⧉` (#327), a 🌐 translations opener (#293–#296), a template's click-to-insert token chips (the syntax can be typed), a search box's own clearing `✕`, a price grid's ⤴ carry-forward and the issue dialog's per-vendor prefix overrides (#377 — rare, and one per vendor stands in front of the numbers) are all skipped, because each is a shortcut to something the field itself already offers. What **stays** in the order is anything that is the only way to reach a piece of state from the keyboard: a `✎` that opens the field at all, a Save / Cancel pair on an inline edit, a `+ Add` that commits the select next to it, a `✕` that removes a row, a sort-direction toggle, a filter chip. Those are controls in their own right that happen to sit near an input, not helpers on it. Bake the rule into the shared component (`copy-button.tsx`, `translations-field.tsx`, `template-builder.tsx`'s chips, `list-toolbar.tsx`'s `CLEAR_BTN`) rather than at each call site, so a new caller inherits it. Mouse reachability is unchanged, and everything inside a dialog such a control opens tabs normally — the exclusion is about the *route in*, never about the surface it leads to. A dialog whose fields are **remembered** puts the cursor in the one field that is not: the Add copy dialog (#534) focuses the in-location **Ref** on open, because condition, location and disposition all come back from the last copy (#234) and only the ref changes per item in an intake pass. Mount-only, and it stays a no-op when the field it names is disabled (Ref needs a location) — a focus effect that fires later pulls the cursor out from under a collector who has already started typing, which is why #222's focus-after-picking-a-location is a *separate*, flag-driven effect and not this one widened. The intake condition step reads the same rule onto its **catalog value** field (#593), and is the one place where the claim cannot be `data-autofocus`, since the field is not on screen at mount — see `purchases-and-intake.md` for what it is guarded with instead.

- Drag-to-reorder lists use the shared kit in `src/app/c/[collectionSlug]/shared/reorder-list.tsx` (`useReorderList`, `InsertionLine`, `DragGrip`, `showLineAt`, `dragStyle`) — the container is the drop target, not the row. `handleOnly` starts a drag only from a row's ⠿ grip, so a stray press on the row body doesn't (offer photo plan, #313).

- Click-to-edit inline fields use the shared `src/app/c/[collectionSlug]/shared/inline-text.tsx` (`InlineText`) — offer price / listing URL, sale transaction link. Where the display is itself interactive (a link that opens), pass `editControl` so a separate ✎ enters edit mode instead of the display's own click being hijacked (#214). A **link** field is editable in every lifecycle state (#213, #292): a listing or order page is most often what one goes back to *after* the thing completed, so a terminal state is a reason to keep the field open, not to lock it. Where the display is **smaller than the default input box** — small print like #498's base-currency line — pass `inputStyle` with the metrics of the text it replaces: a row that grows when a field opens and shrinks when it closes makes a dense grid unreadable to tab through. `InlineText` is a **text** field, so a value with a shape of its own does not go through it: an Allegro parameter (#494, `offer-allegro-card.tsx`'s `Parameter`/`ParameterInput`) is answered by whatever Allegro says it is — a dictionary's options, a from/to pair, a typed number — built from the same spec the category picker's form uses, with the draft↔value pair shared as `parameterDraft`/`parameterValueFromDraft` in `allegro-category-rules.ts` so one stored answer opens the same way on both surfaces. It commits on **Save/Enter** rather than on blur, since several controls in one row make a blur between them meaningless, and it writes *one* answer (`setAllegroOfferParameter`) rather than the category and all of them: correcting a recalled value is not a re-pick, and must not restate where the category came from.

- A **hover hint is the shared `Tooltip`** (`shared/tooltip.tsx`), never the browser's `title` attribute (#291). The bubble portals to `<body>` with `fixed` coordinates, so no ancestor's `overflow` clips it, and it is **clamped to the window** by `TooltipBubble` — measured in a layout effect, then *flipped* to the trigger's other side when it overruns vertically (sliding would cover the control it describes) and *slid* when it overruns horizontally (a trigger has no other side to flip to). That clamp lives in the primitive on purpose: a hint is most needed on the controls sitting at the edges of the screen, which are exactly the ones whose bubble runs off it, and leaving it to callers meant every such site had to notice the problem first. `placement`/`align` are therefore a **preference, not a guard** — set `align` where the anchoring itself reads better, not to avoid an edge — a native tooltip ignores the theme, appears after a delay nothing else in the app has, and cannot carry formatting. Native `title` survives in exactly two places: revealing text that is *already on screen* but ellipsized (the hint repeats the visible string, which is the browser's overflow affordance, not a tooltip), and the printable packing sheet, a server-rendered artifact that should not become a client component for hover text that never prints. Three things follow from the wrapper the component inserts. **Empty content renders no bubble**, so a conditional hint stays one code path instead of branching between a wrapped and an unwrapped child — which would move the child in the layout. Layout the child carried (`flex`, `marginLeft: auto`, `position: absolute`, `width: 100%`) moves to the wrapper's **`style`**, or the row shifts around it. And a tooltip **inside** another tooltip suppresses the outer one while it is open, matching what nesting `title` did — triggers nest constantly here (a chip with its own hint inside a clickable row that has one), and `mouseenter` does not re-fire on the ancestor, so both bubbles would otherwise sit on screen at once. `title` doubling as an icon-only control's accessible name is not a reason to keep it: give the control an `aria-label` and the hint a `Tooltip`.

- Every icon comes from **one module named for meanings** (#459; ADR-0030): `src/app/icons.tsx`, the only file that may import `lucide-react`. Draw one with `<Icon name="edit" />` — the vocabulary is the app's own words for an act (`edit`, `delete`, `withdraw`, `bidCeiling`, `translations`), never the picture, so changing a drawing is a one-line edit in the map and `IconName`'s closed union makes an unknown name a **type error** rather than a second glyph for an act that already has one. Two meanings sharing a drawing still get two names (`close` and `clear` are both an ✕ and are not the same act) — that is what lets one of them change later. Size (five steps, `md` = 16px default), stroke (`1.75`), inherited `currentColor` and the alignment nudge that lets one element sit in a sentence, a chip and a flex row alike are all decided **in the module**, never at the call site: a per-site size is exactly the inconsistency #459 removed. A component that draws an icon for its callers takes an `IconName` and sizes it itself (`RowAction.icon`, `CountFilterChip.icon`), so every row menu in the app looks alike; widen a `label` to `ReactNode` only where the icon *is* the label (a ✓/✕ segmented control). Icons are decorative (`aria-hidden`) and the control carries the `aria-label`. What stays **text** is typography, not iconography: `…`, `–`, `×` between dimensions, `≈ ≥ ≤ ≠ • ⌘ ⏎`, the `›` in a location or category path, arrows inside prose, and the `═ ─` rulers in generated listing text. A native `<select>` renders text only, so a grouping icon sits *beside* the control, not inside its `<option>`s. `extension/` is out of scope (no React) and must not grow a parallel icon system.

- A **thumbnail fits, never crops** (#525): every `objectFit` on a thumbnail comes from `THUMB_OBJECT_FIT` (`src/app/photo-viewer.tsx`, re-exported from `inventory/photo-thumb.tsx`, `"contain"`) — the copy/stamp rows, the photo strip and editor, the offer photos card and its add-attachment dialog, the listing workspace card, the packing sheet. A stamp is the subject of its thumbnail, and `cover` hides exactly what the thumbnail is opened for — a margin, a perforation, an overprint at the edge. The box keeps its size and the image letterboxes inside it against the tile background. Import the constant rather than writing the value, so a new thumbnail cannot quietly go back to cropping; the **lightbox** is not a thumbnail and has always been `contain` on its own.

- **Hovering a thumbnail enlarges it** (#632): `ThumbPreview` (`src/app/photo-viewer.tsx`, re-exported from `inventory/photo-thumb.tsx`) wraps a thumbnail so that resting on it opens a 20rem preview of the same photo, captioned with the label the plain hint used to carry. It is the shared `Tooltip` **with a picture in it**, not a second hover mechanism — placement, viewport clamping and the rule that an inner hint silences the outer one are the hard part and are already right there — which is why `Tooltip` grew a `delay` prop rather than the preview growing its own: a hint costs nothing to have been shown and opens at once, while a 20rem picture flashing up for every thumbnail a pointer crosses on the way down a list is exactly the flicker the pause (400 ms, cancelled on leave) exists to prevent. Every thumbnail that already carried a `Tooltip` for its label **swaps that wrapper** for this one, so no site ends up with two hover surfaces and no label is lost: the copy/stamp rows and the read-only strip, the offer photos card and its add-attachment picker and collage tiles, the listing workspace card, the purchase scan tiles and the zoom view's piece grid. The preview draws the **full** variant over the thumbnail already on screen as a backdrop, so it opens with the picture — upscaled and soft — rather than an empty box, and it **fits** in its box for the same reason a thumbnail does. It complements the click, which still opens the lightbox. Two sites are deliberately outside it: the **photo editor**'s cards, which are already large and are dragged, and the **packing sheet**, which is a printout. It reaches the partner's page too (#666), and that is why it and the lightbox moved to `src/app/photo-viewer.tsx`: they now take **resolved sources** (`ViewablePhoto`: a key, a `src`, a label) rather than a collection id, so a picture addressed through a share token and a picture addressed through the collection route are looked at by one component. `photo-thumb.tsx` keeps the collection-scoped `PhotoLightbox` and `collectionPhotoViews` as the adapter — a screen inside `/c/` calls exactly what it always did.
- Prefer in-place editing for fields where inline edits are practical.

- A list's **filter toolbar is sticky** (`STICKY_TOOLBAR_STYLE` in `shared/list-toolbar.tsx`, #358): the page itself scrolls — there is no inner scroll container — so `top: 0` is the app's own top edge, and the z-index (5) must stay under the portalled row-action menus (200) and dialogs (100). `ListToolbar` carries it for the card-embedded lists (Issues, Stamps, Copies, Sales); the Offers and Purchases panels build their own toolbar row and spread it together with the **page** background, since a transparent bar would let rows scroll through it.

- Shared base components for list screens (loading, empty, filters, table, endless scroll).

- Use semantic color tokens from `src/app/globals.css` for UI intent. New tokens must have values in both `:root` (light) and `.dark` blocks. The exception is a control or overlay where **the colour is the subject rather than the intent**: the watermark tool's channel chips (#625, `ScanToolButton`'s `tint`) are the red, the green and the blue of the scan itself, and the reading label drawn on a scan (#598) has to stay legible over white paper and printed ink in either theme. Borrowing `--color-error` for *the red channel* would make it share a colour with *something is wrong* on the one surface whose job is judging a picture. Those literals are named and reasoned about at their definition; everything that means a **state** still goes through a token.

- **A remembered preference is scoped to what it is a fact about, and anything scoped to one *record* needs a cap.** The lot views' `groupBy` / `sort` toggles are ways of *reading* an order, so they are stored per collection under one key each (`lot-view-prefs.ts`) and cost nothing as the collection grows. The purchase-order screen's own state — which lots are open, which issue groups are collapsed, the filter chips, the scans card (#566) — is a fact about **one order**, and there the naïve key-per-thing grows without bound: the collapsed groups were keyed `…:<collectionId>:<lotId>`, so after a year of intake the store held an entry for every lot ever opened and **not one of them could be evicted**, because a key naming only a lot cannot be traced back to the order it belongs to. The pattern that fixes it (`shared/purchase-ui-state.ts` + the pure half in `lib/purchase-ui-state.ts`) is **one entry per record plus a most-recently-used index** holding each entry's size, so eviction never parses the entries to weigh them. Cap on **two axes at once** — a count (50) and a byte budget (1.5 MB of the ~5 MB origin quota, shared with every other stored preference): a `cuid()` is 25 chars and `localStorage` charges UTF-16, which puts a typical order near 10 KB against a heavy one's ~51 KB, and that fifty-fold spread means a count cap cannot bound the bytes while a byte cap alone would keep hundreds of ancient entries. There is deliberately **no TTL**: a stale expansion state costs nothing, since ids that no longer exist simply are not on screen, whereas a wrongly-expired one costs exactly the clicks the feature exists to remove. An entry equal to the screen's defaults is deleted rather than stored, so an order merely opened in passing never takes a slot; a `QuotaExceededError` is recovered from by dropping the least-recently-used entry and retrying, because the quota is shared and can be full while this store is well inside its own budget; and a malformed entry reads as *no stored state* rather than throwing, which is also why there is no schema version. The store rides `lot-view-prefs`' notification event rather than owning a second one — the order screen reads both, and two channels would let half a screen update while the other half stayed stale.

- URL state for navigation/filters/sorting/pagination; toast for ephemeral feedback. The toast is `ToastProvider` / `useToast()` (`src/app/toast-provider.tsx`, #541), hand-written for the reason the tooltip and the multi-select popover are — a few dozen lines against a dependency, and every overlay question it raises the app has already answered. Mounted in the **root** layout, not the collection one: settings, the collections list and the sign-in shell all take actions worth confirming, and a provider mounted per section is one every new section has to remember. What earns one is a **completed action whose result the collector cannot see from where they are standing**, and the *link* is the point — the entity that was just created or moved, so getting back to it is a click rather than a search. Where the result is on screen it gets none: a row appearing in the list being looked at already flashes (#158), and a title redrawing as it saves is its own confirmation, so a toast on top of either is the same news twice. Creation that **navigates** to what it made (a purchase, #139; a sale; an offer) gets none either — arriving on the thing is better than a note saying it exists. It is not an escape-stack layer (#361), being neither trapped nor waiting on an answer; it portals to `<body>` and gates on `useSyncExternalStore` with a null server snapshot rather than a `useState` flipped in an effect (the `usePersistedFlag` rule — portalled content is not in the server's HTML). The live region exists before any toast does, or the first one is the *arrival* of a region rather than an update to one and goes unannounced; `role="status"`, never `alert`, since expected news must not talk over what the collector is doing. The timer pauses on hover and on focus within, so a link is never pulled out from under the pointer reaching for it, and the stack is capped at four with the **oldest** dropped — the one whose link has already had its chance. Blocking failures stay **inline**, next to the form that caused them: a toast is dismissed and gone, which is exactly wrong for something that has to be acted on; the `error` tone is for a failure with no form left on screen. A remembered **client preference** (localStorage) that a *server-rendered* screen reads must go through `useSyncExternalStore` with a **null `getServerSnapshot`** — `usePersistedFlag` and `usePersistedSort` are the pattern. Reading `localStorage` straight in render makes the pre-hydration render disagree with the server's, and React then discards the whole tree and re-renders it on the client. `usePersistedSearch` is the exception, and only because the pickers using it are portalled after a click and never server-render.- Printable views (#330, the sale packing list) are their own route rendering a plain server-side sheet — no filters, no lazy loading — because the artifact is the printout, not an interactive screen. Print support lives in `globals.css`: mark app chrome and on-screen controls `.no-print`, wrap the sheet in `.print-sheet` (drops screen padding), and rely on the `@media print` block that forces the colour tokens to an ink-friendly light palette (so the dark theme never prints as a black page). Use real `<table>` markup so headers repeat across pages, and `.print-footer` to pin a provenance footer to the foot of the page (fixed in paged media; the sheet reserves the strip with its bottom padding). Which columns a sheet prints is a per-user choice stored **globally** (one `usePersistentString` key holding a CSV of column keys — a stored empty string must read as "all off", which a set of booleans can't express), not scoped to the collection or the record.

- A list's **summary bar** sums the *filtered* set, read whole through its own endpoint rather than summed from the loaded pages — a total that grows as you scroll is worse than none — and renders a mode-matched skeleton so nothing below it shifts (#151). The offers one (#317) leads with **asking value** alone, because the per-state counts it would otherwise repeat already live in the filter chips (#332); **More** reveals the copies' catalog value + purchase cost (the holdings pair, #134) and a per-platform split, behind an expander because they cost a valuation pass and answer an occasional question. Its copy count is **per membership** (a copy on two platforms is two sellable offers) while the holdings figures **deduplicate** (it is one piece of stock) — the divergence is deliberate and documented at `OffersAskingSummary.itemCount`. The per-platform breakdown repeats **all three** figures — a slice answers the same questions as the total — as a grid whose amount columns sit at the **left**, beside the platform name (a right-aligned far edge makes a wide screen unreadable), the asking column landing under the total's. Platform rows are each complete in themselves and deliberately **do not sum to the total**: a copy on two marketplaces is valued in both. Overlapping slices are why the valuation is a single pass — `getHoldingsValuationByGroup` fetches and values the union once and aggregates per group, so adding a platform costs an aggregation, not a pricing run. The arithmetic is pure in `src/lib/offer-summary.ts` (unit-tested, no Prisma), mirroring `aggregateHoldings`; `offersSummary` and `listOffersPaginated` share one `offerListWhere` so the bar and the rows can never disagree.

- A **hierarchical filter's scope** is the collector's (#385), not a fixed rule: `useSubtreeScope(axis)` (`shared/subtree-scope.tsx`) is one persisted flag per axis — `area`, `location` — defaulting to *include descendants*, because picking "Poland" and being shown only what sits directly on that node is not what browsing a tree means. It is **global**, not per-collection like the area/year *selection* (`use-collection-filter-store`): it is a way of reading a tree, and it sits beside the equally-global collapsed-set key. The two axes resolve in different places and that is inherent: an area selection is expanded **client-side** through the shared `resolveAreaFilterIds` (never an inline `getDescendantIds` + self, which is how six screens came to each own a copy of the rule), while a location's subtree is resolved **server-side** in `resolveLocationScope` — every location-filtering read goes through it, so the list, its holdings bar and its year facets cannot disagree about what "in Klaser A" means. `SubtreeScopeToggle` renders **only when the selected node has children**: on a leaf both states select the same rows, and a control that cannot change anything is noise on a screen already dense with filters. The area sidebar's in-scope shading follows the toggle, so the tree marks the set the list is actually showing.

- Password managers overlay their fill icon on short **identifier** inputs — a catalog prefix, an order number, a lot number, a location ref — and `autoComplete="off"` alone does not stop them (#262, #389). Spread the shared `NO_AUTOFILL` (`shared/no-autofill.ts`) onto such a field; it carries the per-vendor opt-outs (`data-lpignore`, `data-1p-ignore`, `data-bwignore`) beside `autoComplete`, because each extension only honours its own. Do not re-inline the four attributes: they were copy-pasted at eight sites before this and a new field was fixed only once someone reported it.

- A list toolbar's toggle chip is the shared `FilterChip` (`shared/filter-chip.tsx`) — the offers status filter (#332) and the sales one (#392) are one control, and `FILTER_CONTROL_STYLE` is the box every toolbar select shares with it so a mixed row lines up. A **remembered** filter follows #325's rule exactly: the URL wins where it names a value (a shared link keeps meaning what it meant), the stored per-collection value fills in otherwise, and every change writes both — so clearing the filter clears the memory of it. The sales status filter carries **no counts**: there is no sales facet endpoint, and a chip promising a number it cannot compute is worse than a bare one.

- An **amount field is `NumericInput`** (`shared/numeric-input.tsx`), never a native `type="number"`. Native number inputs silently drop a comma in a period-locale browser, so a collector typing `12,50` submitted `12` (#233); this is a `type="text"` / `inputMode="decimal"` input that live-sanitises through `sanitizeDecimalInput` (`src/lib/decimal-input.ts`) and rewrites the caret to where the sanitised prefix ends, so a rejected keystroke does not throw the cursor to the end. It also takes a **simple arithmetic expression** — `1+2`, `12,50*3`, `(4,20+1,80)/2` (#580) — evaluated on **blur**, because a field being edited must show what is being typed and there is no moment before blur at which a half-written sum is meaningfully wrong. Evaluation is a hand-written recursive-descent parser over `+ - * / ( )`, never `eval`: the input is a string off a form, and a real parser is both smaller than the sandbox an `eval` would need and the only way to *fail* on `1+` rather than throw. Malformed input is **returned as typed** rather than blanked or zeroed — the collector's text is the only record of what they meant, and every caller already rejects a non-finite amount with its own message, so there is one failure path instead of two. The blur handler calls the consumer's `onChange` with the blur event so a controlled parent picks the result up off the same `e.target.value` it reads from a change; without it the component's state would keep the expression while the DOM showed the number. The same evaluation runs **server-side** in `normalizeDecimalInput`, which every amount parser (`offer-rules`, `sale-rules`, `auction-rules`, `intake-catalog-value`, the price grid, the purchase and contact actions) already calls first — that is what covers a form submitted before its field was ever blurred, and it is why the rule is one shared util rather than a handler per dialog. `normalizeDecimalInput` only parses when the value **contains an operator**, so a plain `1,234.56` still normalises to a `Number()`-rejecting string rather than being reinterpreted. A negative result is *not* clamped here: it is passed on and refused by the caller's `n < 0` branch, which already has the right message. **Integer** fields — year, day, month, template dimensions, bid percents, item limits — deliberately stay native `type="number"`: they have no separator to disambiguate and no sum to work out, and their spinners are worth keeping.
