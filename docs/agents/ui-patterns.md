# Shared UI Patterns & Primitives

Toolbars, filters, expansion, reordering, tooltips, icons, thumbnails, tokens, toast, inline editing.

- A list filter over **several values at once** is `MultiSelectFilter` (`shared/multi-select-filter.tsx`, #425) — a toolbar-sized button that opens a checkbox list, never a `<select multiple>`, which turns into a scrolling box the height of the toolbar. It reads the one value's name when one is ticked and **counts** them when more are (`3 conditions`), so the control cannot grow and shove the toolbar around. Selection applies as it is made — the list behind it is what says what a tick did, so an Apply button would only ask the collector to confirm what they can already see — and *clearing* is the list's own first row rather than a control beside the trigger, since clearing and unticking everything are one act. It is a **popover, not a layer**: it keeps its own Escape and outside-click instead of joining the escape stack (#361), the same call the notification centre makes, and portals to `<body>` with fixed positioning so a toolbar's `overflow` cannot clip it. The value rides in the URL comma-separated, exactly as `areaIds` does, and an empty list is the **absence** of the filter rather than an unmatchable empty set. Server-side, one axis keeps **one** filter on it: `conditionIds` / `formatIds` / `deliveryStates` (#425, #427) replaced their singular forms on `ItemListFiltersPaginated` **outright**, and every caller pinning one value — a duplicate group addressing its own members, the sale-lot composition picker's `delivered` (#164), `GROUP_ELIGIBILITY` — passes a single-entry list through the same field, so there is never a second knob to keep in step. Renaming rather than adding is also the only way the compiler finds the callers; where one is reached by a **spread** it cannot (`GROUP_ELIGIBILITY`, the duplicate-grouping valuation filters), so those carry a `satisfies` / an explicit annotation — an unrenamed key in a spread is silently dropped, and dropping `deliveryState: "delivered"` would quietly widen a group's eligibility. Two axes are **not a plain `in`**, and share one helper (`nullableIdWhere`): format, where `"single"` is the *null* format (ADR-0020), and certificate, where `"none"` is (ADR-0006 §2, #428). A null is never a member of an `in`, so ticking the sentinel beside a real value is two branches ORed — and that `OR` goes into `buildItemWhere`'s **AND list**, never the top level, where the search's own `OR` would collide with it (and where two such axes at once would swallow one another). Certificate had **no filter at all** before #428 — the field existed only so a duplicate group could address its own members — which is why adding the control came with the rename rather than after it. An unrecognised delivery state is **dropped** from the list rather than passed through, so a stale link narrows to the states it does name and, once nothing is left, shows the whole list rather than an empty screen. Options may carry a **`group`** (#846), which draws a heading over each adjacent run of them and is the answer to a control holding switches that do not all pull the same way — the Copies list's four spare filters, where *No photos* and *Missing catalog value* narrow and the two *Include* switches widen. Concatenating four labels does not make that legible; two headings do, and the option labels still have to read correctly **on their own**, because the trigger shows a single ticked option's label with no heading beside it (which is why the widening pair keeps the word *Include*). `clearLabel` goes with it: a control whose trigger names the control rather than an axis (*More filters*) has no "all" to offer, so its clear row says what clearing does instead of repeating the trigger. Where a multi-select's ticks are **`AND`ed** rather than ORed — the Copies list's disposition trio, three independent booleans on a copy rather than three values of one axis — the control has to say so in a hover, because a checkbox list reads as *any of these* by default.

- A list filter over **one of several** values, where that choice has settings of its own, is `SingleSelectFilter` (`shared/single-select-filter.tsx`, #868) — the Copies list's grouping. A native `<select>` is the right control for a one-of choice and stays so everywhere else on these bars; what it cannot do is carry the two *Split by …* switches that qualify *Group duplicates*, which is why those had been drawn beside it and only once duplicates was picked. The panel takes a **`footer`** spelled exactly like `TreeSelectPanel`'s (#846) and **always drawn**, so the switches are visible from the moment the dropdown opens rather than after the interaction that would have dismissed it. They are **disabled under the other groupings, under a heading naming the one they apply to** (*When grouping duplicates*) — not defaulted, because the splits join the *duplicate key* and there is no honest reading of them over issue groups, and inventing one would be inventing product behaviour; and not merely present, because "present but meaningless" is the failure mode a panel of always-drawn sub-controls invites. Disabled-and-labelled is what buys the discoverability the whole change is for: a collector who has never grouped duplicates learns from the panel that duplicates has two further settings. A disabled switch keeps showing its stored state, so one left on last week reads as waiting rather than as silently applied. The trigger **summarises the footer** — `describeCopyGrouping` (`lib/copy-grouping.ts`, pure and unit-tested) names the one split and counts the two, `MultiSelectFilter`'s own rule — which is worth more than a wider panel on a row this dense, and costs nothing because the trigger is a fixed box. That box has a **character budget** (`COPY_GROUPING_LABEL_BUDGET`) pinned by a test rather than by anything at runtime: an over-long label is silently ellipsised, and the half that gets cut is the half saying which splits are on. The control reads the **effective** grouping, not the stored one — a filing grouping remembered from before the last location was deleted falls back to the flat list, and the dropdown must not sit there claiming a grouping the list is not under. Dismissal is `useFilterPopover`'s (`shared/filter-popover.tsx`), extracted from `MultiSelectFilter` in the same change so the two dropdowns on one bar are one convention rather than two: a popover and not an escape layer (#361), portaled to `<body>`, closing on Escape, an outside click, a page scroll or a resize — and **never on a pick**, which is `closeOnSelect: false`'s reasoning (#846) reaching the third control on the bar. **Its second caller is the auction lots toolbar** (#1070), and it is what makes the `footer` a shared shape rather than one screen's arrangement: *Show closed* relaxes the outcome group's single-select (#504) and had sat out on the bar beside the group it modified with nothing saying so — the same defect one control along. That is the line to apply, and it cuts both ways with #772's: a control that **qualifies** a choice goes inside the control it qualifies, a control whose options **are** the choice goes on the surface, and a control that is simply **on or off** is a chip and folds into nothing. The switch itself is now the shared `FilterFooterToggle` (`shared/filter-popover.tsx`) rather than a copy per screen, and it takes a `disabledHint` because the sentence naming *when* a disabled switch would apply is the caller's own — a disabled control gets no hover of its own, so the hint rides on the wrapper. **A single-select-with-counts needs no new component**: the count goes in the option's own label, spelled exactly as `All sellers (3)` is in the native `<select>` beside it (#1029), and the *any* row is a facet row like any other — but check whether it can honestly be **summed** from the options under it before assuming it can, because #1029's `sumCounts` reasoning holds only where they partition (the auction closing windows overlap, and its outcome options each override a default the *any* row obeys, so both are counted server-side instead).

- Row-level actions go in a single `⋮` menu, not a cluster of per-row buttons. Use the shared `RowActionsMenu` (`src/app/c/[collectionSlug]/shared/row-actions-menu.tsx`); destructive actions get `danger` + `separatorBefore`. Dialog-opening actions expose `{ action, dialog }` hooks rendered at the row level (see `use-price-details-action.tsx`, `use-inventory-copy-actions.tsx`) so the dialog survives the menu closing. Section-level adds (e.g. + Add area) stay as standalone buttons. An action a *precondition* blocks is **disabled with a `hint`**, not hidden (#273): the hint is a muted second line under the label saying why, because a disabled control never gets a hover event and a silently missing entry is unguessable. Hide it only when the row itself already answers the question — a copy not marked *For sale* shows no offer action, since the disposition chip is right there. A handful of the most-repeated actions are additionally **promoted onto the row** as icon buttons (`RowQuickActions` + `pickRowActions`, `shared/row-quick-actions.tsx`), which is the shape #261 was missing: a promotion is a **shortcut, never a move** (the entry stays in the menu, so nothing is reachable only by the icon), the button is an **icon with a tooltip and no label**, and it is **always drawn — dimmed at rest, full strength on row hover**, never revealed *by* the hover: appearing on hover makes aiming a two-step move (hover to find out where the buttons are, then aim), which is worse than the dimmed icon it was meant to save. It carries `tabIndex={-1}` (#445/#446) so a row keeps one tab stop. A **grouped** list keeps the menu (#516): the copies inside an expanded duplicate / filing / issue group are ordinary `InventoryItemRow`s, and grouping decides what a row is listed *under*, never what may be done to it. The three grouped branches used to pass `readOnly` instead — which is what hid it — so the handlers now travel as one `CopyRowActions` bundle (`inventory-copy-list.tsx`), built once in `InventoryListPanel` and spread onto the flat list and threaded through each group list and row. One prop rather than thirteen at each of two layers is the point: a new action reaches the grouped views without anyone remembering to plumb it, which is the failure mode #516 *was*. The **group row itself** still carries no menu — #422 deliberately replaced its one entry with the select-gutter checkbox. Callers pass the *same* `RowAction` objects they gave the menu, so a shortcut and its entry cannot drift — which is why an icon must name its action on its own (`Add copy` is `⧉`, not a second `＋` beside `Add stamp`). Promoted so far: the Issues list (issue row: edit / add stamp / add copy; stamp row: edit / add variant range / add copy — the **range** rather than `add-child`, #1150, because a catalogue that splits a stamp into a lettered run splits it into several at once, so the one-at-a-time sibling is the exception and keeps to the menu), the **Copies** list (edit / edit stamp / add to offer / add to new offer), the flat **Stamps** list (edit / add copy), the **Wants** list (detail page / edit), the **Offers** list (edit / sell), the **Purchases** list (edit alone), the **Auction lots** list (bid unchanged / contents) and the **lot builder**'s proposal (open the copy / pin / reject, #760 — its two acts, made ninety times in a sitting, which is why `pin` and `reject` were added to the copy row's promoted vocabulary rather than the screen growing icons of its own) — with the **Sales** list deliberately left alone (#527). Each list promotes what *it* repeats rather than a fixed trio — the flat stamp list has no *add child stamp*, because a variant is added from the issue tree where its parent is on screen, and the copies list promotes **both** offer verbs because they are one decision made per copy ("does this join a listing or open one"), and promoting only *add to offer* would have made it the accidental default for want of a second click. The copy row is rendered from eight screens and takes an `actionsOverride`, so the promotion is picked from the *resolved* list: a screen that hands the row fewer actions simply shows fewer icons, and `pickRowActions` skipping an absent key is what makes that silent rather than a crash. What a list does **not** promote is decided by three subtractions, which is what settled #527's four remaining lists: an action the **row's own click** already performs (*Open* everywhere, *Open sale* on a lot) is not promoted, since an icon aimed at what the whole row does is a smaller target for the same result; an action the row already draws as a **labelled control** — the offer row's and the lot row's `Listing` chip, the sale row's `Transaction` chip — is not promoted either, a shortcut past the menu being the point rather than a second copy of a control that is already on screen; and **destructive** entries are never promoted at all. Applied honestly this leaves *one* icon on Purchases and **none** on Sales, and both are the right answer rather than a shortfall — "no promotion" is a valid outcome, and two dimmed icons duplicating visible controls is exactly the sprawl #125 collapsed. The **auction lot** row is the density case: the busiest menu of the set on the row that already carries inline bid fields, and it takes two — `checked` + `contents`, the watchlist pass itself — while every *bid-fill* entry stays in the menu because the row's own cells are where a new figure is typed. Both are present on every lot (a blocked one disabled with its hint, #273), so the promoted pair is a **constant width** and cannot shunt the closing time and the `⋮` about from row to row, which is what that column's fixed widths exist to prevent. The menu **portals to `<body>`** at z-index 200, so rows living *inside a dialog* must raise it past that dialog's own `zIndexBase + 1` (`zIndex` prop) — otherwise it opens behind the panel, invisible, and the click meant for an entry lands on the backdrop and closes the dialog (#468 hit exactly this). It is also not an escape layer, so a dialog holding such rows takes `dismissable={!menuOpen}` off the menu's `onOpenChange`, or one Escape closes menu and dialog together (#361). An entry that **goes somewhere** carries `href` rather than an `onSelect` calling `router.push` (#557), and the menu and `RowQuickActions` both draw it as a real `<a>` — a `router.push` navigates on a plain left click and on nothing else, so cmd/ctrl+click opened the row in the same tab, the middle button did nothing and the browser's context menu had no *Open link in new tab* to offer, because there was no link. `onSelect` stays what every *other* kind of entry uses (a dialog, a mutation, a `window.open` to a marketplace), none of those being a place with an address; the two together would navigate twice, and a `disabled` entry falls back to the button, an anchor having no disabled state and a dead-looking link that is still followed being worse than no link. The same rule reaches the **rows** through `RowLink` (`shared/row-link.tsx`): a row that reads as a link has to be one, but a row is full of controls and interactive content nested inside an `<a>` is neither valid nor reliably clickable, so the anchor is an **overlay** at `ROW_LINK_Z` over a `position: relative` row and anything needing its own pointer behaviour is lifted with `ROW_LINK_ABOVE`. What gets lifted is not just the controls but **every tooltip** — an overlay over a `Tooltip` swallows the hover it exists for — which in practice means the whole chip line under a row's name, so the row's *name* is the link's surface and the chip line is not; a plain click there still opens the row, because the row keeps its own `onClick` and the lifted region is above the anchor, and the anchor stops its own click so the two cannot both fire. The `role="link"` / `tabIndex` / Enter handling those rows carried by hand comes **off**: the anchor is the tab stop now, and two on one row is one too many. Four rows take it (offer, purchase, sale, auction sale, plus the related-offers card); the **auction lot** row deliberately does not — it is an amounts grid of inline-editable figures, quick-fill controls and popovers, so the overlay would have to be lifted off nearly every part of it and would end up covering only the gaps, and its own `handleRowClick` already answers a modified click with a new tab while *Open sale* in its menu is the real link.

- **Lot / set cards are collapsed by default** (#382) — purchase-order lots, offer sets and an auction sale's lots alike, through the shared `useCardExpansion` (`shared/use-card-expansion.ts`), which owns the state at the *panel* level so one screen has one rule and a Collapse all / Expand all control to operate it. These screens are **scanned** first ("which lots are in this order", "which sets are in this listing") and a card's contents are a second question asked of one of them; expanded-by-default meant a four-lot order opened as several screens of copy rows. Exactly two things open a card unasked: the card the collector **navigated to** (#374's `?lot=`, passed as `initiallyExpandedId` and *seeded* into the state, so it can still be closed by hand and the arrival mark going does not shut it — on the auction sale and the purchase order alike that mark is a one-shot flash released two seconds in, #850 and #876), and a card that **appears while the screen is open** — it was created here, so it is what is being looked at. The latter is derived from the ids themselves rather than from a just-added signal: it covers a create that yields several cards, needs no plumbing through the dialogs, and the first render is the baseline (all three views mount after their data has loaded), so an ordinary page load opens nothing. A lone card is **not** an exception — one rule, nothing to infer. The **sale's packing view** (#166) keeps its cards expanded, deliberately, because a packing list is read rather than scanned, and that exemption is the reason to leave `sold-units-view.tsx` alone. The hook takes an optional third argument, a `CardExpansionStore`, and holds the open set there instead of in component state — the purchase order passes its remembered per-order state, the offer and auction screens pass nothing and are unchanged. Both rules above still hold against a **restored** set, which is the point: the baseline is what was restored, so a lot created while the screen is open still opens itself, and a deep-linked card is seeded on top of what was stored rather than replacing it (that seeding is the one write that happens during render, guarded to the single pass where `known` is still null, and idempotent so a double-invoked render costs nothing).

- A **grouped list** is collapsed by default too, but through `useGroupExpansion` (`shared/use-group-expansion.ts`, #538) and **not** `useCardExpansion` — the Copies list's three groupings (#372/#421/#424) hold the state at the panel so Expand all / Collapse all can speak for the whole list, and the three group rows lost their own `useState`. The two hooks differ on the case that matters: a *card* appearing while the screen is open was created here and opens itself, whereas a grouped list is cursor-scrolled and its rows appear because the collector scrolled — and every open group **fetches its own members**, so a page of forty arriving pre-expanded is four hundred copies nobody asked for. The state is therefore a **mode plus its exceptions** (`expandAll` + `overrides`) rather than a set of open ids: a group loaded *after* Expand all comes in open, which is what the control means on a list whose end has not been reached, while `allExpanded` is read over the ids currently loaded so the label always describes what is on screen. `resetKey` is the grouping mode, since carrying `expandAll` across would open every row of a list nobody has looked at. `toggleAll` clears the exceptions — a statement about the whole list is exactly what overrules the rows toggled by hand. The control sits on its **own line above the rows**, right-aligned, as #382's does: in the filter toolbar it read as one more way of narrowing the list.

- A control that is **auxiliary to a field beside it** carries `tabIndex={-1}` (#445/#446). Tab is how a form is filled in, so it should walk the *fields* — a stop per helper turns a card of three texts or a dialog of six vendors into a slalom, and the collector's hands leave the keyboard for something they never asked to visit. The line is **not "icon vs. label" and not "small vs. large"**, it is *could this control be skipped and the field still be completed*: a copy `⧉` (#327), a 🌐 translations opener (#293–#296), a template's click-to-insert token chips (the syntax can be typed), a search box's own clearing `✕`, a price grid's ⤴ carry-forward and the issue dialog's per-vendor prefix overrides (#377 — rare, and one per vendor stands in front of the numbers) are all skipped, because each is a shortcut to something the field itself already offers. What **stays** in the order is anything that is the only way to reach a piece of state from the keyboard: a `✎` that opens the field at all, a Save / Cancel pair on an inline edit, a `+ Add` that commits the select next to it, a `✕` that removes a row, a sort-direction toggle, a filter chip. Those are controls in their own right that happen to sit near an input, not helpers on it. Bake the rule into the shared component (`copy-button.tsx`, `translations-field.tsx`, `template-builder.tsx`'s chips, `list-toolbar.tsx`'s `CLEAR_BTN`) rather than at each call site, so a new caller inherits it. Mouse reachability is unchanged, and everything inside a dialog such a control opens tabs normally — the exclusion is about the *route in*, never about the surface it leads to. A dialog whose fields are **remembered** puts the cursor in the one field that is not: the Add copy dialog (#534) focuses the in-location **Ref** on open, because condition, location and disposition all come back from the last copy (#234) and only the ref changes per item in an intake pass. Mount-only, and it stays a no-op when the field it names is disabled (Ref needs a location) — a focus effect that fires later pulls the cursor out from under a collector who has already started typing, which is why #222's focus-after-picking-a-location is a *separate*, flag-driven effect and not this one widened. The intake condition step reads the same rule onto its **catalog value** field (#593), and is the one place where the claim cannot be `data-autofocus`, since the field is not on screen at mount — see `purchases-and-intake.md` for what it is guarded with instead.

- Drag-to-reorder lists use the shared kit in `src/app/c/[collectionSlug]/shared/reorder-list.tsx` (`useReorderList`, `InsertionLine`, `DragGrip`, `showLineAt`, `dragStyle`) — the container is the drop target, not the row. `handleOnly` starts a drag only from a row's ⠿ grip, so a stray press on the row body doesn't (offer photo plan, #313). The album page canvas (#769) is deliberately **not** this kit — it reorders shapes inside one SVG rather than rows in a list — but it draws the same language and for the same reason: the source goes pale and dashed, the landing place is a bar in the gap in front of the target, and both are **insert-before, never a swap** (#816). What its mark means is pure in `src/lib/album-drag.ts` and is the same function the drop is written with, so the two cannot describe different rules.

- Click-to-edit inline fields use the shared `src/app/c/[collectionSlug]/shared/inline-text.tsx` (`InlineText`) — offer price / listing URL, sale transaction link. Where the display is itself interactive (a link that opens), pass `editControl` so a separate ✎ enters edit mode instead of the display's own click being hijacked (#214). A **link** field is editable in every lifecycle state (#213, #292): a listing or order page is most often what one goes back to *after* the thing completed, so a terminal state is a reason to keep the field open, not to lock it. Where the display is **smaller than the default input box** — small print like #498's base-currency line — pass `inputStyle` with the metrics of the text it replaces: a row that grows when a field opens and shrinks when it closes makes a dense grid unreadable to tab through. `InlineText` is a **text** field, so a value with a shape of its own does not go through it: an Allegro parameter (#494, `offer-allegro-card.tsx`'s `Parameter`/`ParameterInput`) is answered by whatever Allegro says it is — a dictionary's options, a from/to pair, a typed number — built from the same spec the category picker's form uses, with the draft↔value pair shared as `parameterDraft`/`parameterValueFromDraft` in `allegro-category-rules.ts` so one stored answer opens the same way on both surfaces. It commits on **Save/Enter** rather than on blur, since several controls in one row make a blur between them meaningless, and it writes *one* answer (`setAllegroOfferParameter`) rather than the category and all of them: correcting a recalled value is not a re-pick, and must not restate where the category came from.

- A **hover hint is the shared `Tooltip`** (`shared/tooltip.tsx`), never the browser's `title` attribute (#291). The bubble portals to `<body>` with `fixed` coordinates, so no ancestor's `overflow` clips it, and it is **clamped to the window** by `TooltipBubble` — measured in a layout effect, then *flipped* to the trigger's other side when it overruns vertically (sliding would cover the control it describes) and *slid* when it overruns horizontally (a trigger has no other side to flip to). That clamp lives in the primitive on purpose: a hint is most needed on the controls sitting at the edges of the screen, which are exactly the ones whose bubble runs off it, and leaving it to callers meant every such site had to notice the problem first. `placement`/`align` are therefore a **preference, not a guard** — set `align` where the anchoring itself reads better, not to avoid an edge — a native tooltip ignores the theme, appears after a delay nothing else in the app has, and cannot carry formatting. Native `title` survives in exactly two places: revealing text that is *already on screen* but ellipsized (the hint repeats the visible string, which is the browser's overflow affordance, not a tooltip), and the printable packing sheet, a server-rendered artifact that should not become a client component for hover text that never prints. Three things follow from the wrapper the component inserts. **Empty content renders no bubble**, so a conditional hint stays one code path instead of branching between a wrapped and an unwrapped child — which would move the child in the layout. Layout the child carried (`flex`, `marginLeft: auto`, `position: absolute`, `width: 100%`) moves to the wrapper's **`style`**, or the row shifts around it. And a tooltip **inside** another tooltip suppresses the outer one while it is open, matching what nesting `title` did — triggers nest constantly here (a chip with its own hint inside a clickable row that has one), and `mouseenter` does not re-fire on the ancestor, so both bubbles would otherwise sit on screen at once. `title` doubling as an icon-only control's accessible name is not a reason to keep it: give the control an `aria-label` and the hint a `Tooltip`.

- Every icon comes from **one module named for meanings** (#459; ADR-0030): `src/app/icons.tsx`, the only file that may import `lucide-react`. Draw one with `<Icon name="edit" />` — the vocabulary is the app's own words for an act (`edit`, `delete`, `withdraw`, `bidCeiling`, `translations`), never the picture, so changing a drawing is a one-line edit in the map and `IconName`'s closed union makes an unknown name a **type error** rather than a second glyph for an act that already has one. Two meanings sharing a drawing still get two names (`close` and `clear` are both an ✕ and are not the same act) — that is what lets one of them change later. Size (five steps, `md` = 16px default), stroke (`1.75`), inherited `currentColor` and the alignment nudge that lets one element sit in a sentence, a chip and a flex row alike are all decided **in the module**, never at the call site: a per-site size is exactly the inconsistency #459 removed. A component that draws an icon for its callers takes an `IconName` and sizes it itself (`RowAction.icon`, `CountFilterChip.icon`), so every row menu in the app looks alike; widen a `label` to `ReactNode` only where the icon *is* the label (a ✓/✕ segmented control). Icons are decorative (`aria-hidden`) and the control carries the `aria-label`. What stays **text** is typography, not iconography: `…`, `–`, `×` between dimensions, `≈ ≥ ≤ ≠ • ⌘ ⏎`, the `›` in a location or category path, arrows inside prose, and the `═ ─` rulers in generated listing text. A native `<select>` renders text only, so a grouping icon sits *beside* the control, not inside its `<option>`s. `extension/` is out of scope (no React) and must not grow a parallel icon system.

- A **thumbnail fits, never crops** (#525): every `objectFit` on a thumbnail comes from `THUMB_OBJECT_FIT` (`src/app/photo-viewer.tsx`, re-exported from `inventory/photo-thumb.tsx`, `"contain"`) — the copy/stamp rows, the photo strip and editor, the offer photos card and its add-attachment dialog, the listing workspace card, the packing sheet. A stamp is the subject of its thumbnail, and `cover` hides exactly what the thumbnail is opened for — a margin, a perforation, an overprint at the edge. The box keeps its size and the image letterboxes inside it against the tile background. Import the constant rather than writing the value, so a new thumbnail cannot quietly go back to cropping; the **lightbox** is not a thumbnail and has always been `contain` on its own.

- **Hovering a thumbnail enlarges it** (#632): `ThumbPreview` (`src/app/photo-viewer.tsx`, re-exported from `inventory/photo-thumb.tsx`) wraps a thumbnail so that resting on it opens a 20rem preview of the same photo, captioned with the label the plain hint used to carry. It is the shared `Tooltip` **with a picture in it**, not a second hover mechanism — placement, viewport clamping and the rule that an inner hint silences the outer one are the hard part and are already right there — which is why `Tooltip` grew a `delay` prop rather than the preview growing its own: a hint costs nothing to have been shown and opens at once, while a 20rem picture flashing up for every thumbnail a pointer crosses on the way down a list is exactly the flicker the pause (400 ms, cancelled on leave) exists to prevent. Every thumbnail that already carried a `Tooltip` for its label **swaps that wrapper** for this one, so no site ends up with two hover surfaces and no label is lost: the copy/stamp rows and the read-only strip, the offer photos card and its add-attachment picker and collage tiles, the listing workspace card, the purchase scan tiles and the zoom view's piece grid. The preview draws the **full** variant over the thumbnail already on screen as a backdrop, so it opens with the picture — upscaled and soft — rather than an empty box, and it **fits** in its box for the same reason a thumbnail does. It complements the click, which still opens the lightbox. Two sites are deliberately outside it: the **photo editor**'s cards, which are already large and are dragged, and the **packing sheet**, which is a printout. It reaches the partner's page too (#666), and that is why it and the lightbox moved to `src/app/photo-viewer.tsx`: they now take **resolved sources** (`ViewablePhoto`: a key, a `src`, a label) rather than a collection id, so a picture addressed through a share token and a picture addressed through the collection route are looked at by one component. `photo-thumb.tsx` keeps the collection-scoped `PhotoLightbox` and `collectionPhotoViews` as the adapter — a screen inside `/c/` calls exactly what it always did.
- Prefer in-place editing for fields where inline edits are practical.

- **Choosing a filter must never change the layout of the filter bar** (#868) — the general rule the Copies bar is now built to, stated by the user on seeing the grouping sub-controls arrive on a pick. Three costs, and he hit all three in one sitting: a control that appears only after a selection **cannot be discovered** (you do not know it exists until you have done the thing that summons it, and if that thing also dismisses the surface you may never see it — #846's first pass); it **moves everything beside it**, so the bar reflows under the pointer at the moment the collector is working it, which is #848's complaint one row up; and it makes the bar's **width unpredictable** on a row already carrying eleven filter controls and three actions (#846, #847). The rule bites in two different ways and both are on this bar. **A control that comes and goes** is answered by keeping it and changing its state: grouping's two *Split by …* switches moved **inside** the dropdown (below), and the sort control is now **greyed with the reason on it** (`sortDisabledReason` on `ListToolbar`) rather than removed under a grouping — every grouping brings its own total order (duplicate groups by count #372, filing groups by location path, issue groups by the Issues list's order #181), so the choice cannot be honoured, but a control that vanishes takes ten characters of bar width *and* its own explanation with it. *Reset filters* (#733) is the one that went the other way: it holds its slot and turns **`visibility: hidden`** while there is nothing to reset, out of the tab order and the accessibility tree, because there is nothing to discover about a reset with nothing to reset and #733's objection to a permanently dead control on a dense row still stands. **A control that changes width** is answered by giving it a fixed one: every dropdown on that bar sits in a `FilterSlot` (`inventory-list-panel.tsx`, `FILTER_WIDTH`) and `MultiSelectFilter` takes `fullWidth` to fill it, ellipsising a long label instead of stretching. Counting several values rather than listing them (#425) bounds a trigger's growth; it does not hold it still — `All conditions`, `Mint` and `3 conditions` are three widths. A **native `<select>`** is stable across picks on its own, since it sizes to its widest *option* — but only while the font does not change, so an active one is marked by colour and border and **never by weight** (the platform worklist select; #847 had already made that call on the quick offer button, where a label that thickens on click re-lays the row out under the cursor). The `Tooltip` wrapping a bar control needs `flexShrink: 0` of its own: it renders an `inline-flex` span, and *that* span is the row's flex child rather than the fixed slot inside it. **The named exception** is a control conditional on the collection's own data — no formats defined, no format filter; no locations, no location filter and no filing grouping. That is stable for the session, it is not a response to a pick, and an axis a collection does not have has no filter. The cost of all this is a bar a few rem wider at rest, which is the trade the rule asks for: predictable beats compact when the thing being predicted is where the control will be when the pointer gets there.

- **A filter is a way of looking, so it never unticks anything — and a bulk action never reaches a row the collector cannot see** (#1020/#1021, decided by the user on 2026-09-10, answering #872). The bar over a ticked selection **counts, labels and acts on the ticked rows that are *in view*; the ticked rows the filter is hiding stay ticked and come back when the filter is released.** This reconciles two rules that were written pointing in opposite directions and both of which are right. #853 wrote that **a chip must not throw a selection away** — *the selection is left alone; release the chip and it is still ticked* — because pressing a chip is not a way of deselecting, and a collector who built a run of fifteen must not lose it by looking at the card another way. #863 wrote that **a control over "everything here" means everything the filter is showing, not everything the data holds** — a box that reports *partial* over a strip whose every square is ticked, or that ticks pieces the chip is hiding, is describing rows nobody is looking at. They met on the card-scans strip, where the bar could say *3 tiles selected* with one on screen and *Identify 3 tiles as one stamp* would have acted on all three. Counting the visible ones satisfies both: nothing is unticked, and no write reaches a row the collector never saw. Two alternatives were rejected — **leaving it** (the state needs deliberate work to reach and the outcomes are reversible, but a bulk identify then touches a tile nobody looked at) and **preventing it instead of resolving it** (refusing a chip while a selection is up, or clearing the selection with a confirmation, both heavier than the thing they prevent).

  **Its cost is stated rather than glossed, because the user weighed it and took it, and getting the wording right is most of the work:** the number on the bar **moves when a chip is pressed with nothing deselected**. *3 tiles selected* becomes *1 of 3 ticked tiles in view* and then *3* again, and a collector who does not already hold the distinction between *ticked* and *in view* reads that drop as the app having lost his selection. So the headline names **both** figures rather than the one it is acting on; a second line says what became of the others in the only terms that matter — *still ticked, and back when the chip is released* — and appears **only while any are hidden**, so a resting bar reads exactly as it always did; and the **action button names the number it will act on**, which a headline carrying two numbers can no longer do on its own. Where a bar already narrows for a *second*, unrelated reason the two must not blur into one figure: the Copies list's listing actions apply to the part of the selection an offer can be made of, so *in view* and *qualifies* are said separately and on the control each belongs to (`inventory-lists.md`).

  **Three sets, and keeping them apart is the whole of the rule.** What is **ticked** outlives every filter; what is **in view** is what the bar counts and what an action is handed; what still **exists** is the only one computed over the unfiltered data. **Pruning a selection must never be narrowed to the filtered set** — pruning is about rows that no longer *exist* (a tile identified away, a copy deleted), and narrowing it would delete a selection merely because a chip was pressed, which is #853's failure arriving by another route. It is the one place this change goes quietly wrong, and it is asserted by a test on both surfaces rather than left as a comment. **Clearing is the collector's own act and clears everything**, hidden rows included, with the hint saying so while any are hidden: unticking only what is on screen empties the bar and leaves ticks standing that no control on screen can then reach, and *clear* writes nothing to a row in any case. **And the bar is up while *anything* is ticked, not while anything is in view** — with every ticked row hidden it reads `0 of 5` and keeps only *Clear*, since that is the one place those five are visible and the one control that can still reach them; a bar that vanished would leave a selection nothing on screen could reach, reappearing later with nothing to explain it. Every action on it is then **absent rather than disabled** (`#682`'s own reading of the same choice): there is nothing that could honestly be offered over rows the collector cannot see, and a dead button beside a live *Clear* reads as a fault.

  **A fold is not a filter, and this is the half a reader will get wrong.** It is written out because the looser wording of the rule invites the mistake: *a bulk action never reaches a row the collector cannot see* reads as though anything off screen were meant, and a folded group's rows are off screen. **#863's own sentence is narrower** — *a control over "everything here" means everything **the filter** is showing* — and that is the one to build to. A **filter** decides which rows the screen has at all, and can hide rows the collector has never laid eyes on; a **fold** is a way of reading rows the screen already has, chosen in the moment, normally for rows he has just ticked himself. Only the first narrows a bar.

  **The argument, because a preference and a conclusion look alike once written down.** A folded group or batch still draws its **own tri-state box reporting those very ticks** (#422; `copy-group-shell.tsx` sets `indeterminate` on it) — so a bar refusing to count what that box reports would be two controls on one screen answering one question and disagreeing, which this file already calls worse than the thing it fixes (the scans strip's `SetAsideToggle` is suppressed under a chip for exactly that reason). It also preserves **tick-a-group / fold / tick-the-next / act**, which is what a select-all is *for*, and the code already agrees: `useGroupMembers` opens a folded group on a select-all so the copies are visible **at the moment they are ticked** — which is where visibility is worth paying for, and it is a different moment from the act.

  **So, stated once: *in view* is the ticked rows the list has loaded for the current filter set — the flat pages, plus the members each group row has fetched, folded or not.** Fold is irrelevant to it. On the card-scans strip this collapses to a predicate, every tile being loaded (`scan-tile-selection.ts`, `selectedInView` beside `selectedInOrder`); on a cursor-paginated list it cannot, the filters being resolved server-side, so the lists report what they hold (`rows-in-view.ts` and `use-rows-in-view.ts`, with the Copies list's own reading in `inventory-lists.md`).

  **And the residual, in the same place rather than left to be met.** *Loaded for the filter set* is not *held by the filter set*: a row matching the filter but sitting in a page nobody has scrolled to is **ticked, uncounted and unreachable until it loads**. Nothing is lost and no action can touch it, and it returns on scrolling exactly as a hidden tick returns on releasing the filter — but the number is a fact about what has loaded, and a reader expecting it to be a fact about the filter will be surprised once. A stated gap is worth more than a clean sentence.

  **A picker dialog is the first of the two exceptions, and it is the same rule reframed rather than a hole in it** (#1046, decided by the user on 2026-09-10, answering the same question one surface over). The four copy pickers — `compose-set-dialog.tsx`, `attach-copies-dialog.tsx`, `trade-copy-picker-dialog.tsx`, `add-sale-line-dialog.tsx` — **keep the whole selection and submit it whole**, and the submit button **says how many ticked rows the current filters are hiding**: *Add 7 copies (3 hidden by these filters)*. **The label says nothing at all when nothing is hidden** — *Add 7 (0 hidden)* is noise on every ordinary use, and ordinary use is most uses — which is why `hiddenTicksSuffix` answers the empty string for zero rather than a parenthetical saying so, and why a caller appends it unconditionally instead of branching. The arithmetic is `countHiddenTicks` (`src/lib/picker-hidden-ticks.ts`, pure and unit-tested), and it takes the **rows on screen** rather than the filters, because in three of the four the area rail is resolved *server-side* while the year facet and the search are client-side: a tick made under *Poland* is simply absent from the fetched list once the rail moves, and subtracting what is shown from what is ticked answers all three axes without the dialog having to know which one did it. That is also why the parenthetical says *these filters* and not *this search*, which the issue and the decision both spell — the search box is one of three or four controls that can hide a tick, and naming only it would be wrong on the commonest of them.

  **The reframing is the useful half, and it is what makes this an exception rather than an inconsistency.** What the list rule protects is not *an action must not reach a hidden row* but **the collector must not be surprised by what it reached**. On a list, where a bar acts on the collection and a mistake writes to rows nobody looked at, narrowing is how that is achieved. In a picker, which ends in **one explicit submit whose count is read before it is pressed**, honesty achieves it more cheaply and gives nothing up.

  **The two answers not taken, because this is the second time the question has been asked about a different surface and it will be asked a third.** **Narrowing the submit to what is shown** destroys what a picker is for: search *Poland*, tick four, search *1950*, tick three, add all seven is the workflow it exists to support, and the Copies list gave that up **deliberately** rather than by accident — the equivalent there is *the number moves when a chip is pressed, and the hidden ones come back*. **Exempting a picker silently** leaves the surprise standing: *Add 7* above three visible rows is exactly the astonishment #1020/#1021 exists to prevent, and that the count is read before pressing is only a defence **if the count explains itself** — a bare seven does not.

  **A fold is not a filter here either**, and the sale-line picker is where it bites: a collapsed quantity offer's sets are **in view**, because its group row is on screen carrying its own `N selected` and a label disagreeing with that would be two controls on one screen answering one question. Callers pass the rows their **filters** produced, never the rows their folds happen to be showing.

  **The same picker can also refuse to act because of something off screen, and that is answered by a control rather than by a rule about the selection** (#1080, the lead's choice on the user's explicit instruction to decide it — *"zdecyduj sam"* — rather than a reading of anything he had settled). The sale-line dialog is the only one of the four with a **per-row input**: a price on each ticked set, rendered **only on the visible row**, with the submit gated on every ticked set carrying a valid one. So a set that is picked, has its price cleared, and is then hidden by the search or a collapsed group left the submit disabled **with nothing on screen saying why**. It is the paragraph above arriving through the other half of the selection — there *the button acts on more than you can see*, here *the button refuses to act because of something you cannot see* — and it is arguably the worse of the two, since a wrong action is visible afterwards and a dead button explains nothing at all. **The footer names the count and the count is a control**: *2 picked sets have no price*, and pressing it clears whatever is hiding them and narrows the picker to **exactly** those sets, opening the offers they sit in. A **Without a price** facet under *Selected* is the same act with a lit state, so the narrowing is a filter the collector can see is on and can release; both are drawn only while there is something to narrow to, and both go in the render that the last missing price is filled in — the narrowing is **derived** from the count rather than a flag written back, or filling the last price would leave an empty list under a *No sets match these filters* hint with the control that turned it on already gone. The predicate is `setsMissingPrice` / `priceValid` (`src/lib/picker-missing-price.ts`, pure and unit-tested), read by the submit and by the control alike, because a picker disabling its submit over a set its own control does not list is the smallest surface this project's *the number and the write cannot disagree* has. Two smaller consequences follow and neither is decorative: the **type facet counts move onto the narrowed set**, since a facet promising `Single 12` over two visible rows is a count that disagrees with the rows beneath it (#843); and **a collapsed group needs no wording of its own**, because a narrowing that picks out individual sets already forces its groups open — which is what the search has done in this dialog since it was written, so one control answers a fold and a filter alike. **Clearing the search here discards nothing that outlives the dialog**, which is worth saying beside the remembered-filter rule below rather than left for a reader to wonder about: this is the one picker whose box is a plain `useState` and **not** `usePersistedSearch` — the five that persist one are compose-set, attach-copies, trade-copy-picker, add-to-offer and the stamp picker — so #325's *clearing the filter clears the memory of it* has nothing to bite on and the control costs the collector no stored phrase.

  **The rejected options are the valuable half, this being the second question about the same relationship on the same surface.** **Surfacing the invalid picked rows regardless of the search** was refused on who performs the navigation: a list that quietly disobeys its own filter is a list that lies, while a control the collector presses, which visibly changes the filter and says so, is not. **The end state is the same rows on screen — what differs is whether the collector asked for them**, and that is the whole of the objection. **Validating on pick** was refused as aimed at a state that does not occur: the price **pre-fills from the offer's asking price** (`toggleSet` in `add-sale-line-dialog.tsx`, from `listSellableOffers`' `Number(r.price).toFixed(2)`, which is finite and non-negative), so no set can enter the selection without one and the invalid state is only ever reached by **clearing** a field — which the collector is very likely mid-edit on. It is not a stricter version of the fix; blocking an empty field would stop somebody retyping a price. **And a bare count was refused as half a fix**: naming the number without a route to the rows leaves the collector hunting, which is why the control is a control.

  **The currency-mismatch case is not in it, and the tree rather than a judgement is what settles that.** A set listed in another currency is flagged *Listed in X, but this sale is in Y — re-list it* and is **not selectable at all** — the checkbox is disabled and the row's click is inert — so such a set is never in the selection and *missing a price* can never describe one. The question was left open by the decision on purpose and is answered here by measurement: there is nothing to fold in.

  **And the other three pickers are unaffected, which was confirmed rather than assumed.** `compose-set-dialog.tsx`, `attach-copies-dialog.tsx` and `trade-copy-picker-dialog.tsx` gate their submits on `isPending`, an empty selection, and — in *Attach copies* alone — a re-link confirmation drawn as a **banner over the whole dialog** rather than on a row, which no filter can hide. **A submit can only be gated on something a filter hides where the picker has a per-row input**, and that is a property of the surface rather than an omission on the other three: a shared control growing this requirement is what the check was for, and it has not.

  **Purchase intake is the second exception, and it is a different model rather than the same rule reframed** (#1045, decided by the user on 2026-09-10 on the lead's recommendation, answering the question #1031 left open). On the three lists this rule was built on — the card-scans strip, the Copies list and the Offers list — a tick is a **row**, which is what lets a bar narrow honestly to what is on screen. On the intake sort screen a tick can be a **container** — an issue group, a lot, the whole order — resolved server-side and standing for copies that were never loaded, so *all 40 to sort* is a promise about a query rather than a count of anything the screen holds. Narrowing that to what is in view would turn *file this whole card* into *file the eleven rows I have scrolled to*, which is a different act. So this screen gives up both halves: the bar counts and acts on the **whole** selection, hidden ticks included, and the figure it prints comes from `countLotBulkScope` through the same `readLotBulkScope` the write reads, so the number and the write cannot disagree about what will be touched. What stands in the rule's place is #565's own mechanism, which lives in [`purchases-and-intake.md`](purchases-and-intake.md) and is not restated here: a container records the chip **and** the disposition axis it was taken under (`CopyContainer.filter` / `.disposition`), and pressing either **retires** it (`dropFilteredContainers`, `dropDispositionContainers`), so *all 40 to sort* cannot silently become *all 900*.

  **Why a named exception rather than a clause in the rule above, since the alternative was real and was weighed.** The two are answers to different questions — this rule is about **what a bulk action may reach**, and the container model about **what a selection means** — so a clause folding the second into the first would be exercised by one surface in four while having to describe a mechanism the other three do not have, and it would make the general rule harder to state without making intake any safer. **The picker exception is not a precedent for this one, and the two are worth telling apart**: a picker keeps what the rule is protecting and meets it more cheaply, because it ends in one explicit submit whose count is read before it is pressed; intake cannot state the rule's aim in the rule's own terms at all, which is why it is named rather than reframed. **Nothing about #565's behaviour changed when this was decided** — what was wrong was that the invariant in `AGENTS.md` read as though it covered intake, so a reader comparing the two found a contradiction and could not tell a gap from a decision. And the exception is the **intake sort screen** and nothing wider: intake's own picker, *Attach copies* (`attach-copies-dialog.tsx`), is one of the four above and behaves as a picker.

- A control that **qualifies a choice rather than making one** goes inside the control it qualifies, not beside it (#846). `TreeSelectPanel` takes a `footer` and `LocationTreeSelect` a `panelFooter` for exactly this: the Copies list's subtree switch (#385, *+ sub-locations / this location only*) used to appear as a sibling of the location dropdown the moment a branch node was picked — a second control to find, a second thing to read past on every visit, and one that says nothing at all except about the node just chosen. In the panel it is outside the `role="listbox"`, so it is not one more option to arrow through. The **area** panel's copy of the same switch stays where it is: that one sits over an always-open tree with no dropdown to go inside.

  Moving it there brought **two conditions with it**, and the first pass shipped without either, which made the control worse than where it started. It must be **drawn whenever the panel is open** — not once a branch node is picked. Conditional rendering carried over from the sibling arrangement, where it was about room on a crowded bar; inside a panel it competes with nothing, and gating it on the pick put it on screen only *after* the interaction that dismissed the panel, so it could not be found by anyone who did not already know it was there. And the panel must **stay open on a pick**: `useTreeSelect` takes `closeOnSelect`, true for a **form field**, where the pick is the whole act and a form is waiting underneath, false for a **filter**, where the list behind the panel is what says what the pick did and there is nothing to go back to. Closing was the exception rather than the rule on that bar in any case — `MultiSelectFilter` applies each tick and stays open. A panel that survives the pick must also **re-measure its position** afterwards: it is `position: fixed` off the trigger, recomputed on scroll and resize only, and a filter pick re-renders the screen behind it (the Copies bar grows a *Reset filters* control the moment anything is narrowed), so the trigger can move out from under it.
- A list's **filter toolbar is sticky** (`STICKY_TOOLBAR_STYLE` in `shared/list-toolbar.tsx`, #358): the page itself scrolls — there is no inner scroll container — so `top: 0` is the app's own top edge, and the z-index (5) must stay under the portalled row-action menus (200) and dialogs (100). `ListToolbar` carries it for the card-embedded lists (Issues, Stamps, Copies, Sales); the Offers and Purchases panels build their own toolbar row and spread it together with the **page** background, since a transparent bar would let rows scroll through it. A **banner above a list** — quick offer mode's parameters, the bar over the ticked selection — belongs *inside* that block rather than between it and the rows, or it scrolls away while the thing it describes stays (#848), and both take `LIST_BANNER_STYLE` so two banners in one slot cannot drift into different widths and paddings the way #537's and #373's had. Both take the block's `footer` slot, as ordinary rows of it, so **putting either up pushes the rows down** — and that is deliberate on every list alike, long or short (#885). For the quick-offer bar it was always right: it goes up on a click aimed at it, when nothing is under way, so the shift reads as feedback. For the selection bar it is an accepted flaw, and the reasoning is worth having because the next person to see it will reach for one of the two mechanisms that have already been tried and rejected. **Neither failed on its own terms.** The first hung the bar out of the flow, drawn over the rows: it moved nothing, but it *covered* the row beneath it, and "a scroll notch brings the row back" is false at the top of the list, where `scrollTop` is already `0` — the first row stayed half-hidden for as long as anything was selected, and the top is where a person starts ticking. The second kept the bar in flow and paid for its height by **moving the viewport**: the block grows by `H`, `window.scrollBy` moves the scroll position by `H` in the same layout effect, and the rows hold still. That works on a page long enough to scroll and cannot work on a shorter one — `scrollBy` clamps at zero — so the rows shifted on a short list and not on a long one (#884), and **the screen's behaviour came to depend on how many rows happened to be on it**. That is why it went: a **uniform flaw is easier to work with than an unpredictable one**, consistency being a property of the whole screen that a fix winning one case had traded away. The user decided it after living with both, and a candidate for making the short list work was left deliberately unbuilt rather than refuted. **The answer is expected to be a redesign of the bar (#849), not a cleverer compensation** — so a third mechanism in this slot is the move to argue for on that issue rather than to write here. **The decision covers the screen and not just this slot**: the Copies list's platform-exclusion alert (#506) sits below the block rather than in it, in the flow, and displaces the rows the same way — which is what #864 was filed over and why the user settled it as correct as it stands. Compensating for one strip and not its neighbours would rebuild exactly the inconsistency #885 removed, with the control swapped rather than the problem solved, and an alert is likelier than a selection bar to come up on a list too short to pay for it. The lot builder pins a **figures band** rather than a filter row (#760): the same style spread onto the band carrying what the pick came to and *Re-roll*, over a proposal read a hundred rows at a time where every row is a decision — which is what forced those figures down to three lines, since a bar worth pinning has to be one you can afford to keep on screen.

- Shared base components for list screens (loading, empty, filters, table, endless scroll).

- **A screen that picks an area is one card, and the rail lives inside it** — the shape the copies, stamps and Issues lists and the bulk listing workspace all already have. The shape is literal and shared: a flex row with `gap: 0`, `border: 1px solid var(--color-border)`, `borderRadius: 0.75rem`, `overflow: clip`, `background: var(--color-bg-elevated)`, holding `AreaFilterSidebar` / `ListFilterSidebar` first and the work beside it in a column that draws the single `borderLeft` divider. The rail is not a floating box with a gap next to it — a rail that ends where its own list of areas ends, beside content that starts somewhere else, is the one thing that makes a screen read as a different application, which is exactly what the lot builder did for two releases. **Inside that card, two shades do all the work and each says something.** A *band* — `padding: 0.875rem 1.25rem` with a rule under it — is the container's own white and is part of the card, the way a list stacks its toolbar, its selection bar and its rows; a *frame* — `--color-bg-page`, `borderRadius: 0.5rem`, the shape `HoldingsSummaryBar` and `OffersSummaryBar` already carry — is recessed **into** that white and is for figures over the current scope, a callout, a small form. A frame reads as inset only because there is white around it, so a page-coloured box drawn straight onto the page shows as a hairline and nothing else: that is the failure mode, and it is why a new screen copies the container before it copies anything inside it. Rows keep the elevated surface with a `--color-bg-subtle` heading strip above them, hover on `--color-bg-row-hover` and a chosen row on `--color-accent-soft`, and a group of rows draws its rule with `borderTop` on every row **but the first**, so the last row does not lay a second hairline on the card's own border.

- Use semantic color tokens from `src/app/globals.css` for UI intent. New tokens must have values in both `:root` (light) and `.dark` blocks. The exception is a control or overlay where **the colour is the subject rather than the intent**: the watermark tool's channel chips (#625, `ScanToolButton`'s `tint`) are the red, the green and the blue of the scan itself, and the reading label drawn on a scan (#598) has to stay legible over white paper and printed ink in either theme. Borrowing `--color-error` for *the red channel* would make it share a colour with *something is wrong* on the one surface whose job is judging a picture. Those literals are named and reasoned about at their definition; everything that means a **state** still goes through a token.
- A **dictionary entry may carry a colour** (#728) — today a `StampCondition` and a `CertificateStatus`, the two axes drawn as chips on nearly every list — and the colour is a **palette key, never a hex**: one of `TAG_COLORS` (`src/lib/tag-colors.ts`), painted from `--color-tag-<hue>` / `-soft` / `-border`, which `globals.css` defines once per theme exactly as a disposition is. This is the third category beside *intent* and *the colour is the subject*: the hue means nothing at all, it only means **this entry and not that one**, which is why it is picked from a list rather than reasoned about — and why storing what the collector picked as a hex would be wrong. One stored hex is a single value asked to work on a white page and a near-black one; mid-greys vanish on both and anything bright enough for the dark theme glares on the light one, so naming the hue and letting the theme say what it is worth is what keeps a collector's choice legible in both. `tagColorTokens()` is the only reader: it answers with the **neutral chip** for null and for anything outside the vocabulary, so no colour is a real answer (a collector who wants one condition to jump out wants the rest quiet) and a value written before the vocabulary can never reach a `var()` that does not exist. The chip itself is `ConditionChip` / `CertificateStatusChip` (`shared/dictionary-chip.tsx`), and it **looks the colour up from the cached dictionary rather than taking it on the row**: every list already hands its rows a `conditionId`, the dictionary is a handful of entries behind one `staleTime: 60_000` query, and threading a `conditionColor` through a dozen read models, their group and lot variants and the four screens that reshape them would mean a recolour hunting down every read that had copied the old value into a payload. While that query is in flight the chip draws neutral — a chip that says its abbreviation in grey is right, only quieter, whereas a chip that waits is a row that moves under the reader — and the settings panels **invalidate the dictionary query** as well as calling `router.refresh()`, or the one screen not showing the new colour is the one the collector just chose it on. Adding a hue means values in **both** theme blocks and a new entry in `TAG_COLORS`; the shape around the tint is the shared `ROW_CHIP` (`chip-styles.ts`), which the copy row, the duplicate group, the trade line and the lot line had each written out identically — survivable while every chip was grey, not once one of them can be coloured, because a tinted chip and a plain one on the same line must differ **only** in tint. Defaults are seeded (`DEFAULT_CONDITIONS`) and backfilled by migration, and the add dialog pre-selects the first unused hue (`nextTagColor`), so a colour is never something a collector has to go and configure before the feature does anything.

- **Motion reads `prefers-reduced-motion` in one module, and the arrival is deliberately unsignalled under it** (#1022, decided by the user on 2026-09-10). `globals.css` had suppressed all three animations it owns — `.just-added-flash` (#158), `.arrival-flash` (#850/#876) and the toast slide (#541) — under `@media (prefers-reduced-motion: reduce)` since each was written, and the comment beside `.arrival-flash` said that under that preference *the scroll and the card opening are the arrival*. **The scroll was `scrollIntoView({ block: "center", behavior: "smooth" })` with no preference check at all**, on three screens: the auction sale's `?lot=` card, the purchase order's, and the trade summary's *Go to the first*. So the collector who asked for less motion got the flash removed and the **whole page gliding** — the CSS kept the preference and the JavaScript did not, which is the shape to look for whenever an animation is guarded in one language and triggered from another. The fix is **where it is decided, not per call site**: `shared/motion.ts` is the only place in the app that reads the media query, and `scrollIntoView(el, opts)` there takes `Omit<ScrollIntoViewOptions, "behavior">`, so a call site *cannot* restate the preference even by accident — three call sites each reaching for `matchMedia` is three chances to miss the fourth, and the fourth would never be caught, because **nothing in the five required checks looks at a screen** and an unguarded `smooth` is green for ever. `tests/unit/motion.test.ts` is the one thing in the suite that can see any of this, and it can only see the decision, which is the argument for having moved the decision somewhere a test can reach. **A scroll that must be instant whatever the preference stays on the DOM method with no `behavior`** — `shared/autocomplete.tsx` and `shared/delcampe-category-picker.tsx`, where gliding on an arrow key would be wrong under either preference — and that is instant because `behavior: "auto"` resolves to the element's computed CSS `scroll-behavior`, which this app sets **nowhere**. That last fact was swept for rather than assumed, and it is the half a grep for the JavaScript spelling cannot see (`collaboration.md`, *Sweeping for a claim*: ask what else asserts this, and in what form). The sweep found no other page-scale motion: three `@keyframes`, all three already guarded; zero CSS `scroll-behavior`; no Web Animations API and no `animate-*` class anywhere; and 38 inline `transition:` declarations plus 73 Tailwind `transition` classes which are all hover tint, opacity or a chevron rotating in place, none of them moving the page.

  **Nothing replaces the flash, and that is the decision rather than the leftover.** A static ring cleared on the same timer and a dismissible marker were both weighed and refused. This is a **self-hosted app with one collector**, so the audience for the preference is that collector, and he does not use it — a behaviour written for nobody is a second behaviour to keep working. A dismissible marker is precisely what #850 and #876 removed, so re-introducing it under one preference would make the screen behave two ways for the same act. And since #911 the purchase order's arrival **switches the view to Group by lot**, which is a visible, motionless change, so on that screen something does happen without the flash; the auction sale has no equivalent, and that asymmetry is accepted rather than fixed. **If a second person ever uses this app, this is the decision to revisit first.**


- **A remembered preference is scoped to what it is a fact about, and anything scoped to one *record* needs a cap.** The lot views' `groupBy` / `sort` toggles are ways of *reading* an order, so they are stored per collection under one key each (`lot-view-prefs.ts`) and cost nothing as the collection grows. The purchase-order screen's own state — which lots are open, which issue groups are collapsed, the filter chips, the scans card (#566) — is a fact about **one order**, and there the naïve key-per-thing grows without bound: the collapsed groups were keyed `…:<collectionId>:<lotId>`, so after a year of intake the store held an entry for every lot ever opened and **not one of them could be evicted**, because a key naming only a lot cannot be traced back to the order it belongs to. The pattern that fixes it (`shared/purchase-ui-state.ts` + the pure half in `lib/purchase-ui-state.ts`) is **one entry per record plus a most-recently-used index** holding each entry's size, so eviction never parses the entries to weigh them. Cap on **two axes at once** — a count (50) and a byte budget (1.5 MB of the ~5 MB origin quota, shared with every other stored preference): a `cuid()` is 25 chars and `localStorage` charges UTF-16, which puts a typical order near 10 KB against a heavy one's ~51 KB, and that fifty-fold spread means a count cap cannot bound the bytes while a byte cap alone would keep hundreds of ancient entries. There is deliberately **no TTL**: a stale expansion state costs nothing, since ids that no longer exist simply are not on screen, whereas a wrongly-expired one costs exactly the clicks the feature exists to remove. An entry equal to the screen's defaults is deleted rather than stored, so an order merely opened in passing never takes a slot; a `QuotaExceededError` is recovered from by dropping the least-recently-used entry and retrying, because the quota is shared and can be full while this store is well inside its own budget; and a malformed entry reads as *no stored state* rather than throwing, which is also why there is no schema version. The store rides `lot-view-prefs`' notification event rather than owning a second one — the order screen reads both, and two channels would let half a screen update while the other half stayed stale.

- URL state for navigation/filters/sorting/pagination; toast for ephemeral feedback. The toast is `ToastProvider` / `useToast()` (`src/app/toast-provider.tsx`, #541), hand-written for the reason the tooltip and the multi-select popover are — a few dozen lines against a dependency, and every overlay question it raises the app has already answered. Mounted in the **root** layout, not the collection one: settings, the collections list and the sign-in shell all take actions worth confirming, and a provider mounted per section is one every new section has to remember. What earns one is a **completed action whose result the collector cannot see from where they are standing**, and the *link* is the point — the entity that was just created or moved, so getting back to it is a click rather than a search. Where the result is on screen it gets none: a row appearing in the list being looked at already flashes (#158), and a title redrawing as it saves is its own confirmation, so a toast on top of either is the same news twice. Creation that **navigates** to what it made (a purchase, #139; a sale; an offer) gets none either — arriving on the thing is better than a note saying it exists. It sits **top right** (#702), where the eye already is — a confirmation of something just done belongs beside the screen that caused it, not at the far corner of the window — and the stack grows *downwards* from there, newest nearest the corner, so a toast never moves once it is on screen and an older one expiring below it cannot pull a link out from under the pointer. It is not an escape-stack layer (#361), being neither trapped nor waiting on an answer; it portals to `<body>` and gates on `useSyncExternalStore` with a null server snapshot rather than a `useState` flipped in an effect (the `usePersistedFlag` rule — portalled content is not in the server's HTML). The live region exists before any toast does, or the first one is the *arrival* of a region rather than an update to one and goes unannounced; `role="status"`, never `alert`, since expected news must not talk over what the collector is doing. The timer pauses on hover and on focus within, so a link is never pulled out from under the pointer reaching for it, and the stack is capped at four with the **oldest** dropped — the one whose link has already had its chance. Blocking failures stay **inline**, next to the form that caused them: a toast is dismissed and gone, which is exactly wrong for something that has to be acted on; the `error` tone is for a failure with no form left on screen. A remembered **client preference** (localStorage) that a *server-rendered* screen reads must go through `useSyncExternalStore` with a **null `getServerSnapshot`** — `usePersistedFlag` and `usePersistedSort` are the pattern. Reading `localStorage` straight in render makes the pre-hydration render disagree with the server's, and React then discards the whole tree and re-renders it on the client. `usePersistedSearch` is the exception, and only because the pickers using it are portalled after a click and never server-render.- Printable views (#330, the sale packing list) are their own route rendering a plain server-side sheet — no filters, no lazy loading — because the artifact is the printout, not an interactive screen.   **A chip is a single token: it never wraps and never shrinks** — `whiteSpace: nowrap` and `flexShrink: 0`, both on `FilterChip` itself (#558, #1075). It may leave the row; it must not break in half. A chip that holds its width makes the **row** wrap instead of the label, which is the thing a collector can read — a control two lines tall with half a phrase on each is not. **This is the same rule `ui-shell.md` states for the Areas row** (#675/#775, in those exact two properties), which is what makes it a rule about chips rather than about whichever screen last hit it. #558 is the bug that produced it — the *Closed* chip on the Auction Sales bar dropping onto a line of its own — and until #1075 it was fixed **only** on that screen, because the fix went into a local copy: `Sold, not recorded`, `Changed since listed` (offers) and `No catalog value` (trade side column) could all still break in half. Both properties are inert while a row fits — CSS applies `flex-shrink` only against negative free space, and every container rendering a chip here is `flexWrap: wrap`, so an item that will not fit starts a new line rather than being squeezed. **They change nothing at any width where a single chip fits**, which is why widening the shared component was not a visual change to the eight screens already on it. The auctions file's `CONTROL_STYLE` went the same way — byte-identical to `FILTER_CONTROL_STYLE`, so deleting the chip and leaving it would have kept half of one duplication. **The general form, because the next copy will be justified the same way: *nothing else does yet* is a prediction, and a shared control is cheaper to widen than a fork is to reconcile.** **Five more screens carried a byte-identical private `CONTROL_STYLE` of their own and now import the shared one** (#1102) — contacts, copies, the listing workspace, purchases and wants — so the constant has one declaration again. **What is worth carrying is how they were found**: two identical bodies under different names share **no string to grep for**, and a name sweep is exactly wrong here in both directions, since `settings/album-template-preview.tsx` still declares a `CONTROL_STYLE` that is a *different* box (its own width and no `minHeight`) and is not a copy of anything. So the panel that had remembered its search longest (#465) is the one where the forbidden outcome actually shipped, and it was found by reasoning about the hook rather than by looking at the screen. **A shared control repaired is not the same as every caller repaired**, which is the general form and is the same argument `FilterChip` makes two paragraphs up: a fork is invisible to the fix. The guard is `pushedRef` rather than a comparison with the local value, because the value in force lags the input by the whole debounce while somebody is typing and a plain comparison would pull half-typed text back out from under them. That is exactly what a restored *chip* cannot manage among sixteen of them, which is why #1018 had to buy the same honesty for the auction lots list with a band under the toolbar. **The phrase nobody remembers typing is the outcome the rule forbids, and never the mechanism** — a remembered search that did not show itself would break it, and a tracked one that does, does not. **The remembering rule has a second half, and until #844 only the first half existed: whichever home answered is written *back* into the other.** A value read out of storage and applied to the screen but never written to the URL leaves a reload with nothing to read — and it is not only the reload, it is the back button and copying the address to another window, which is why URL state is an invariant here rather than a preference. The shared area/year selection (`src/lib/list-area-year-filter.ts`, `shared/use-list-area-year-filter.ts`) is the worked example, and #853's `?tiles=` chip is the same spelling one screen over: the parameter is read **before** the remembered choice so a pasted link wins, the mirror back is a **`replace`** because a restore is not a navigation the back button should have to walk through, both halves of a pair are stated once either is (or the next load half-falls-back to memory again), and the precedence is written beside the code rather than left to load order. Two guards make it an effect that can run on every render: it writes only where the address does not already describe the screen, and **only once anything has been said at all** — a list nobody has narrowed keeps a clean address. That second guard is load-bearing for the *memory* too, and is where #844's actual reset came from: a per-collection preference is read through `useSyncExternalStore` with an empty server snapshot, so the first render after a reload sees no stored filter whether or not one exists, and the mirror-into-storage that four list panels ran unconditionally on mount overwrote the collector's filter with nothing on every single page load. **A mount effect that mirrors a hydrated preference anywhere has to wait for `useHydrated()`** (`shared/lot-view-prefs.ts`); the null-server-snapshot rule above keeps the render honest and says nothing about the effects that follow it. A **retirement** goes through the same write as a restore — an area id the collection no longer has is dropped and the parameter naming it corrected to `all`, exactly as a scan chip that stops counting retires — which is why the guard asks what has been *stated*, not merely what is in force. The **year is deliberately not retired** the same way: its facets arrive asynchronously and are themselves narrowed by the area in force, so an empty facet list is *nothing here right now* rather than *no such year*.
- **Chips or a counted dropdown is decided by what the options *are*, not by how many there are** (#772). `MultiSelectFilter`'s economy is counting values rather than listing them (#425), which is what keeps a trigger from growing — and it is the wrong trade where the option **names** are the thing being picked between and there are a handful of them. The issue tree's checklist filter is the worked case: its resting label read `3 checklists`, which is the text `ChecklistsBadge` was already showing on the same row, so opening the dropdown was a click spent learning something the row had not said — while *basic* beside *specialized*, *perforated* beside *imperforate* (#531, `catalog-and-stamps.md`) is exactly what a collector chooses by. It is now a wrapping row of `FilterChip`s, one per checklist, each toggled on its own. **This is the far side of #846's line**, which is worth stating because the two look alike: a control that *qualifies* a choice goes inside the control it qualifies, and a control whose options *are* the choice goes on the surface. Three things travel with the swap. **No count on the chip**, though `FilterChip` offers one — a checklist's stamp count is over the whole issue while the tree beneath may also be narrowed by the list's own filter (#631), and a count that disagrees with the rows under it is worse than none (#843). **No *All* chip**: nothing ticked is the absence of a filter rather than an empty set (`filterStampTreeByChecklists`), and with every chip on screen unticking the last is both visible and the whole act, which is `MultiSelectFilter`'s own reading of clearing kept rather than dropped — #843's *already-selected is a no-op* is the opposite case, a single-choice facet list carrying an explicit **All** row. And the row **wraps**: it sits in a header of its own with nothing beside it, so a second line costs no other control, which is what makes an unbounded option list safe here and would not make it safe on a filter bar. **#868 does not reach this control** — it is not on one. Every site is a header strip over an expanded tree (the Issues list row, the issue screen's **Stamps** card, the stamp picker), so no slot width is in play; a chip taking `fontWeight: 600` when active does shift the chips after it, which is `FilterChip`'s behaviour on the five toolbars already using it and is left alone rather than forked here. `FilterChip` gained exactly one thing for this: a **`toggle`** flag that puts `aria-pressed` on the button. It is off by default and is deliberately not derived from `active` — the status filters it was written for (#332, #392) are a **one-of** choice, and a row of pressed/unpressed toggles would describe those wrongly — but a multi-select chip row needs it, because the control it replaced was a checkbox list that announced its ticks and an accent tint announces nothing. Swapping a counted dropdown for chips **costs a reader that state unless it is put back**, and that is the one regression this shape invites.

- An **amount field is `NumericInput`** (`shared/numeric-input.tsx`), never a native `type="number"`. Native number inputs silently drop a comma in a period-locale browser, so a collector typing `12,50` submitted `12` (#233); this is a `type="text"` / `inputMode="decimal"` input that live-sanitises through `sanitizeDecimalInput` (`src/lib/decimal-input.ts`) and rewrites the caret to where the sanitised prefix ends, so a rejected keystroke does not throw the cursor to the end. It also takes a **simple arithmetic expression** — `1+2`, `12,50*3`, `(4,20+1,80)/2` (#580) — evaluated on **blur**, because a field being edited must show what is being typed and there is no moment before blur at which a half-written sum is meaningfully wrong. Evaluation is a hand-written recursive-descent parser over `+ - * / ( )`, never `eval`: the input is a string off a form, and a real parser is both smaller than the sandbox an `eval` would need and the only way to *fail* on `1+` rather than throw. Malformed input is **returned as typed** rather than blanked or zeroed — the collector's text is the only record of what they meant, and every caller already rejects a non-finite amount with its own message, so there is one failure path instead of two. The blur handler calls the consumer's `onChange` with the blur event so a controlled parent picks the result up off the same `e.target.value` it reads from a change; without it the component's state would keep the expression while the DOM showed the number. The same evaluation runs **server-side** in `normalizeDecimalInput`, which every amount parser (`offer-rules`, `sale-rules`, `auction-rules`, `intake-catalog-value`, the price grid, the purchase and contact actions) already calls first — that is what covers a form submitted before its field was ever blurred, and it is why the rule is one shared util rather than a handler per dialog. `normalizeDecimalInput` only parses when the value **contains an operator**, so a plain `1,234.56` still normalises to a `Number()`-rejecting string rather than being reinterpreted. A negative result is *not* clamped here: it is passed on and refused by the caller's `n < 0` branch, which already has the right message. **Integer** fields — year, day, month, template dimensions, bid percents, item limits — deliberately stay native `type="number"`: they have no separator to disambiguate and no sum to work out, and their spinners are worth keeping.
- **A dialog shared across many screens cannot own its own cache invalidation, so the rule that the call sites do it is written as a test rather than as a convention** (#918). `StampFormDialog` is opened from nine screens and its `onSubmit` returns `void`, called before any server action runs — it knows the Save button was pressed, never that a write succeeded, so invalidating from inside it would refetch after a failed save. The policy therefore sits at the call site, beside the `result.status` branch, which is also where `router.refresh()` already lives. **That is the arrangement which produced the bug** — six of the nine invalidated nothing — so the answer is not a note asking the next screen to remember: it is one shared hook, so there is a single thing to call, and `tests/unit/stamp-form-dialog-invalidation.test.ts`, which fails when a file that imports any of the five catalogue-write dialogs never calls it — the rule is keyed on *opening a dialog whose submit handler the opener supplies*, because that is what makes the opener the file that owns the write. Reach for that pair whenever a dialog crosses this many screens; the reasoning, the mirror direction it settles, and what the check deliberately cannot see are in [`catalog-and-stamps.md`](catalog-and-stamps.md), stated once so the number of screens and the limits of the check are not maintained in two places.
