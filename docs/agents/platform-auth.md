# Platform: sessions, the proxy and signing in

How a session stays alive, what `src/proxy.ts` does and does not do, and where signing in lands. Split out of [`platform.md`](platform.md) (#2700).

- **A session lasts until the collector signs out, and the half that makes that true is a cookie renewed on every request** (#1175, ADR-0052). Better Auth writes its session cookie exactly once, at sign-in, with `Max-Age = session.expiresIn`. It *does* re-issue it from `getSession` and *does* slide the stored row — but only onto a response it controls, and `auth.api.getSession({ headers })` **discards the `Set-Cookie` it produced**. Every session read in this app is that call, from a server component or a server action; there is no `authClient.useSession()` anywhere and no `nextCookies()` plugin. So the row slid and the browser's cookie never did, and seven days after signing in, mid-task, the browser stopped sending it. **Read that as the general shape rather than as one bug**: a Better Auth behaviour that only lands on a response is a behaviour this app does not get, and `getSession` returning the right answer is no evidence that the response half happened. `src/proxy.ts` re-issues the cookie verbatim with a fresh `Max-Age` on every request; `src/lib/session-lifetime.ts` holds the spans (400 days, refreshed daily — #1468) and the sign-in screen's pure rules.

- **The long lifetime is not what keeps a session alive — the renewal is, and dropping it would re-introduce the same defect at 400 days** (#1175). Browsers cap a cookie's lifetime at **400 days** whatever the server asks for. Anything that removes `src/proxy.ts`, narrows its matcher away from the screens, or reaches for a longer `expiresIn` *instead of* the renewal is making the original mistake with a slower clock.

- **A server action is the one request the proxy does not renew on, and so an action refreshes nothing by itself** (#2426). Next merges a cookie the proxy sets into the action's own cookies (`mergeMiddlewareCookies`), and an action whose cookies changed is answered with `x-action-revalidated` = static-and-dynamic: the browser evicts its prefetched screens and fetches the whole current page again — every server component of the layout and the page — after **every** server action on every screen. From #1175 until #2426 that was the case for all of them, and on an offer it meant the page's valuation worked out again per price typed. The renewal still runs on every other request — the screen an action runs on was loaded through the proxy, and the reads that follow an edit come through it too — so #1175's lease moves with every visit; `tests/unit/session-lifetime.test.ts` pins both halves. **What a screen draws from its server component is re-read only because the screen asks**: `router.refresh()`, or `revalidatePath` in the action; a screen drawn from TanStack Query invalidates its queries. The audit made with #2426 found five places the implicit refresh had been covering, now explicit: the issue headers of an offer's and an auction sale's screens (a set, a copy, a stamp or a lot line can bring an issue the page has not read), the Allegro connection card after a refused token test, the album picture picker after a delete, and the tab titles after renaming a contact, a trade's partner or an offer. **A new screen that keeps server-read props beside an action must refresh for them** — nothing else will.

- **`session.expiresIn` can never exceed 400 days, because Better Auth writes it as the cookie's `Max-Age` at sign-in and its serializer throws above that** (#1468, ADR-0052's amendment). ADR-0052 first spelled "never" as ten years and every sign-in failed on the server; nobody noticed for weeks because the proxy renews an existing cookie through Next, which does not check, and a signed-in collector never signs in again. `COOKIE_MAX_AGE_CEILING_SECONDS` holds the limit once. **A number that only reaches the wire on a path nobody takes in ordinary use is pinned by driving that path** — `tests/unit/session-lifetime.test.ts` signs in through `betterAuth` itself with the app's `SESSION_OPTIONS` over the memory adapter, rather than asserting the constant.

- **`src/proxy.ts` is Next 16's spelling of middleware, and it authorizes nothing** (#1175). `middleware.ts` still works and emits a deprecation warning on every build; `proxy.ts` exporting `proxy` is the current convention and the build then reports `ƒ Proxy (Middleware)`. This one re-leases an opaque cookie — no secret, no database, no Prisma, so it stays on the Edge runtime. **Route protection is not here and should not move here**: it is each layout's, page's and server action's own `getSession`, which has the database and the collection to hand. `docs/architecture/overview.md` described a protecting middleware for a long time and no such file ever existed; that paragraph is now corrected, so a session finding it in an old copy should not go looking for the file.

- **The proxy also tells each request which screen it is for, and that is information rather than authorization** (#1176). It sets `x-stamporama-screen` — `src/lib/sign-in-return.ts` holds the name — to the path plus the collector's own query, with Next's `_rsc` dropped because that parameter is on the URL a client-side navigation asks for and not on the one in the address bar. **It exists because nothing else in the request can answer the question**: a server component is given its `params`, never the address the browser asked for, and a server action is given neither, so without it a redirect to the sign-in screen cannot say where the collector was. It still authorizes nothing and the bullet above stands: the header permits no read and no write, and it is **set** rather than added, so a browser sending one of its own has it overwritten. **Do not read it for anything but a return address** — it is the client's URL, and the moment a decision keys off it the proxy has started authorizing.

- **Every rule about where signing in lands is pure and in one file; the parts that cannot be pure are a line each** (#1176). `src/lib/sign-in-return.ts` decides which destinations are allowed, and nothing at the ninety-odd `redirect(await signInPath())` call sites decides anything. `src/lib/sign-in-redirect.ts` reads the proxy's header and `SignInPage` reads the query parameter — that is the whole of the impure half. **`signInPath()` returns the path rather than performing the redirect, deliberately**: `redirect()` is declared to return `never`, and that is what narrows `session` to non-null in every one of those callers. A helper that redirected would have to reproduce that narrowing, and an `await` on a `Promise<never>` does not.

- **An open redirect is how this feature goes wrong, and the two values that look like paths and are not are `//host` and `/\host`** (#1176). A browser reads both as another site despite the leading slash, and `\` is checked alongside `/` because browsers normalise it. A value arriving on the query string has already been percent-decoded by the time `isReturnableScreen` sees it, so `%2F%2Fhost` and `%5Chost` are the same two cases rather than extra ones. `tests/unit/sign-in-return.test.ts` pins them, and asserts on the **round trip** — onto the URL, off the query string — because an encoding both halves get wrong in the same way passes a one-sided assertion.
- **Registration is closed by default** (the owner, 2026-11-27, #2713). `STAMPORAMA_ALLOW_REGISTRATION` (`true`/`1`/`yes`/`on`) opens it; an instance with **no account at all** is always open, so a fresh installation can create its first. The rule is server-side: `signUpGuard` in `src/lib/registration.ts`, a Better Auth `before` hook on `/sign-up/email` answering 403, wired in `src/lib/auth.ts` with `isRegistrationOpen()` from `registration-server.ts`. `/sign-up` and the sign-in screen's *Sign up* link read the same function per request (`connection()`), so an `.env` change needs a restart, not a rebuild. Tested through Better Auth itself in `tests/unit/registration.test.ts`.
- **Since #2719 that environment switch is only the default.** An administrator's switch at `/admin` (`instance_settings.registrationOpen`) decides once it has been used — `resolveRegistrationSwitch` in `registration.ts`, read per request by `getRegistrationSwitch` in `registration-server.ts`, so it needs no restart. Null means never used, and then the environment decides exactly as above; the empty-instance rule is unchanged. → [`admin.md`](admin.md)
