# Browser Extension (Stamporama Assistant)

The `extension/` package, its modules, the Colnect matcher and the marks it draws on marketplace pages.

- Browser extension (Stamporama Assistant, #253; ADR-0015) lives in `extension/` — a separate pnpm-workspace package (MV3, esbuild + hand-written `manifest.json`, own `tsconfig`). It is **excluded from the app's** `pnpm lint`/`typecheck`; build and check it on its own with `cd extension && pnpm build|typecheck`. It calls the Colnect matcher endpoints with an `AssistantToken` bearer (session-or-token auth via `src/lib/route-auth.ts`), because the extension reaches us cross-site from colnect.com. Its match window groups results and hides the decisions the collector has effectively already taken (#305): a `needs-confirm` row every candidate of which already carries some Colnect ID — the matcher never silently overwrites (#250), so those rows return on every re-scan. One free candidate keeps the row, since that free stamp is most likely the answer (`isAlreadyLinkedElsewhere` in `core/decisions.ts`). The same rule governs the *numbers*: the backfill (#280) fills a catalog the stamp has none for and only **reports** one the two sides disagree on, so #433 is the collector settling one of those disagreements by hand — `proposeBackfill` resolves each conflict's `overwriteNumber` by the very rules a fill uses (a prefix it cannot recover or one from another area offers nothing, exactly as it writes nothing), and `overwriteColnectCatalogNumber` (`POST …/colnect/overwrite-number`) replaces that one vendor's row, refusing a catalog the stamp holds no number in — that is the backfill's job, and two paths claiming one field is how they drift. It is deliberately **not** part of confirming a match: linking an item and rewriting a number already held are two different claims, and only the second destroys something, hence its own confirm naming both values and its own route rather than a flag on `confirm`. The duplicate policy (#85) is the fill's, run over a proposal shaped like one so an overwrite and a fill can never disagree about what collides; the write **rings no doorbell** (#423's `data-stamporama-assistant-matched`), which announces a *match*, not a number. The **date of issue** rides the same rails one field wider (#655): our stamps are commonly dated by year alone — a root stamp from its issue's (#70), a variant from its parent's (#360) — while a Colnect page states the day, so `proposeIssuedDate` (`src/lib/colnect-date.ts`, pure) compares the two **per component**, and that split is the whole design. A stamp reading `1945` against a printed `1945-01-22` disagrees about nothing, so the month and day are an ordinary fill written with the match; a *differing* year, month or day is a disagreement reported and left alone, settled by `overwriteColnectIssuedDate` (`POST …/colnect/overwrite-date`) on #433's terms — its own route, offered only on a row naming a single stamp — but **not one row at a time** (#668): a page is dozens of matches, the answer is *yes* on nearly all of them, and a click plus a confirm each made settling them the slowest thing in the window. Every date row now carries a **tick instead of a button**, ticked as it is drawn, and one press of **Write** commits the lot behind a single confirm naming how many dates are about to be replaced. The ticks cover the fill as well as the disagreement, so a stamp can be left out of the automatic dating too, and unticking a fill is expressed by **withholding `issuedOn`** for that item rather than by a second flag — the instance dates from the printed value and from nothing else, so sending none *is* "leave this stamp's date alone" (a `conflict` row is deliberately not stripped that way: the disagreement would leave the screen with it). The changes are written **before** the batch match, so the match that follows sees the settled dates rather than re-reporting them, and the first failure stops the run — the rest are the same call to the same instance. The state is a `Set` of `colnectId|stampId` keys, per window and never persisted: it says "not this stamp, this time", while the standing answer stays the **Fill missing issue dates** toggle. It is keyed rather than indexed because the list is rebuilt on every render, and toggling a tick deliberately re-renders **nothing** but the button's promise — a redraw would fold the collector's open `<details>` sections shut under the cursor. Colnect knowing **less** than we do proposes nothing at all, exactly as a ref matching our number does. An overwrite replaces the date **whole**, clearing a component Colnect does not state: the collector has just called our year wrong, and a day kept under an abandoned year is a date neither side ever stated. It writes to the **stamp only** — `Issue.year` covers many stamps and one Colnect item is about one of them — and it is its **own toggle** (`issueDateSync`, default on) rather than the backfill's, wanting Colnect's numbers and wanting its dates being two separate appetites; both are opt-in on the wire, so an older Assistant writes neither by accident. The printed value **travels verbatim** (`issuedOn`) and is parsed on the instance, matcher and overwrite alike, so the window and the instance cannot hold two readings of one page — and it rides on `SlimItem` too, since the load-time match (#283) is what the window reuses as its preview and a preview omitting the dates would promise less than the write it leads to. That match is also what the **toolbar badge** counts, which makes the window's results and the badge one fact told twice: the badge is drawn once as the page loads and nothing on the page changes when a match is written, so the window **pushes its results back** (`results-updated`) on every redraw and the worker refreshes cache and badge together — a badge still counting rows the collector has just settled is the failure, and re-deriving the count in the worker from `badgeTodo` (`core/decisions.ts`, shared with the load-time path) is what stops the two ways of counting one page from drifting. The push names the address it describes and is dropped unless the tab is still on it, the fragment aside: a navigation has already cleared the badge for itself, and an answer arriving after it would resurrect a count for a page nobody is looking at. Offered only on rows that name a single stamp — a linked one or a one-candidate `needs-confirm` — since correcting a number on an unchosen sibling is a change nobody would think to look for. What the matcher compares is strict and pure, but what it *recalls* out of the database is a `contains` net, and that net is built from **each digit run** of the printed number and never from all its digits at once (`catalogDigitRuns`, ANDed on one `some`, in both readers — the matcher's and the picker's): `PL BL30 B4` concatenates to `304`, which no stored `BL30 B4` contains, so the item read as `no-candidates` with the stamp sitting right there (#435). A run survives every spacing and punctuation difference between the two sides, which is exactly what the key already folds away; a digit-free number (Michel's Roman local issues) still recalls on its bare value, case-insensitively. The reveal control lives in the toolbar row, not the section heading: with every such row hidden the section is gone and would take the only way back with it. Tokens are obtained by **self-registration** (#252): Settings → Assistant exposes a one-time code + the instance's own origin on the page, and a toolbar-icon click exchanges it at `POST /api/assistant/register` (`src/lib/assistant-registration.ts`). A `PlatformModule` has **two halves** (#408): extraction (`matches`/`extract`, required) and **listing** (`listing: { formUrl, isFormUrl, fill, listedUrl, attachPhotos? }`, optional) — reading a marketplace page and posting to one are the symmetric halves of one job, so listing lives in the neutral interface rather than inside the Colnect module, which is what lets Delcampe (#154) and Allegro (#355) reuse it. A read-only module is a *complete* module and its platform simply offers no **List via Assistant** (#407); `moduleReports()` says which modules carry which half, so no surface hard-codes ids. The task is the **listing kit** (#405) unchanged, mirrored by hand in `extension/src/platform/listing.ts` as `core/decisions.ts` mirrors the matcher response — it states what the listing *holds*, never how a form is laid out, so Colnect's URL shape and field names appear nowhere outside `src/platform/colnect/` (#410). Driving one is `listing-run.ts`, **two pure steps** because a navigation separates them (`resolveListingTarget` → `fillListing`), leaving the tab-opening and the report back to the instance to the wiring (#407/#409). Filling **stops before submit** — the collector clicks the platform's own button — the page is checked with `isFormUrl` **and** with `isFormDocument` first — two questions because a marketplace answers the form's own address with something that is not the form yet (#419: Colnect's anti-bot interstitial, which reloads itself into it), and filling that page wrote nothing while reporting every field as missing, so the text half of a listing vanished and only the pictures — attached later, on the reloaded form — landed. The document check is therefore a **`retry`, not a refusal**: `fillListing` says "not yet", and the wiring (`fillThroughReloads`) waits for the tab's next `complete` and starts the whole attempt over, injection included, since a fresh document holds no content script. The watcher is armed **before** the fill, or a reload landing while the message is in flight is the one event it misses; it is bounded by both a short wait and an attempt count, because a page that never becomes the form (a sign-in, a challenge) has to end in the error it already has rather than in a spinner. A URL that is not the form's at all stays an outright refusal — that is the collector having navigated away, not a page on its way. The outcome is a **report, not a verdict**: `filled` *and* `skipped` both come back, each named for the collector rather than for the DOM, because a field the task cannot answer (an unmapped condition above all) is no reason to abandon the rest of the form. The three ways a task finds no module — the platform names none, the id is unknown here, the module only reads — are three different answers. That **wiring** (#409) is the registration contract a second time, on a second element (`#stamporama-assistant-listing`, `extension/src/core/listing-handoff.ts`): the workspace writes `{ v, requestId, task }` into it as text and the extension answers with `data-listing-state` / `-message` / `-request` / `-report` on the same node — the page owns the node and re-renders it, so text in and attributes out is the only direction that survives. The gesture is what differs from #252: a listing starts from a click on an offer *card*, so there is no toolbar click to grant `activeTab`, and the extension instead **registers a content script for the profile's origin** (`background/instance-scripts.ts`, `chrome.scripting.registerContentScripts`, port included so `:3002` is not `:3000`) — reconciled against the stored profiles off `chrome.storage.local` changing, so registering, correcting a URL and deleting a profile are one code path, and injected into that origin's already-open tabs, a freshly registered script only reaching documents loaded after it. `host_permissions` is already `http://*/*` + `https://*/*`, so none of it prompts. `requestId` is minted by the page and echoed back — an answer names the handoff it answers, and a request already answered is ignored, so a re-render is not read as the collector asking again — and `<html>` carries `data-stamporama-assistant` (the version) on every instance page, without which **List via Assistant** is a button that silently does nothing on a browser with no extension. The worker (`background/listing.ts`) then does the part `listing-run.ts` deliberately has no `chrome.*` for: open the form **beside** the workspace tab, wait (capped, a closed tab reported as such — a promise that never settles leaves the card spinning), have the *content* script fill it because the DOM is there, report back. It needs **no profile and makes no instance call**: a task is self-contained and the origin that wrote it is one the collector registered. Storing the URL and moving Ready → Active stays the page's own job (#407) — the extension reports, the instance decides. The offer's own screen offers the handoff one state **earlier** (#554): from `preparing`, under exactly the conditions its quick-advance is offered under and judged by the very same `readyBlockers` (#418) — the preconditions asked at Ready plus the photos, `listingBlockers` reporting only the `not-ready` this click undoes — and the transition goes **first**, the kit being served for a Ready offer alone, so a refused advance ends it with its own words rather than letting the Assistant refuse it again in different ones. It is one act to the collector and the state chip sits beside the button, hence no toast of its own; the bulk workspace is untouched, being a batch of Ready offers by definition. **Closing that loop** is #412: the entry's URL exists only after the collector presses Save, so `PlatformListing` gains one more neutral member — `listedUrl(url)`, the same knowledge `isFormUrl` carries on the other side of Save, returning the URL rather than a boolean because it is *stored* and the module is what decides which part of the address bar is the record (Colnect lands straight on `/…/market/sale/<code>`, confirmed by posting one, and drops query + fragment). The wait between filling and Save is written to `chrome.storage.local` per listing tab (`background/pending-listings.ts`, pruned at 12h), never held in the worker: a collector takes minutes over a form and an MV3 service worker is unloaded in seconds, so a navigation wakes it with nothing but a tab id and the record is what turns that into meaning. The content script also arms a one-shot `submit` watcher, which buys the one distinction the capture cannot make on its own — a **posted** listing whose entry page was never recognised is reported when the tab closes, while an **abandoned** form is silence, because an untouched Ready offer is not news (a form re-served with validation errors is why the report waits for the tab to close rather than firing on the first unrecognised page). The write-back has **two deliverers, in order**: the answer goes onto the handoff node and the *page* publishes it through the same `publishOfferAction` its own Publish calls — #407's rule, with the collector watching — and the instance content script replies whether it is `taken`, which it decides by re-reading the node's **text** for that `requestId` (the page's own half of the contract, so "is anyone still following this" is answerable without inventing a channel). Not taken — dismissed, replaced by the next offer's handoff, tab closed — and the worker POSTs to `…/offers/[offerId]/listed` with the profile matching the page's **origin + the task's collection**, the only pair that names one connection. `recordOfferListed` is therefore **idempotent**: `ready` publishes, an already-`active` offer has a *blank* URL filled in and a recorded one left alone, anything else is refused, so the two paths racing is a no-op and never a conflict — and a marketplace submission can never quietly take a paused or sold offer live. Colnect's own half (#410, `colnect/listing.ts`, against the form mapped in #402) declares the **komplet in the URL** (`…/sell/new/category/stamps/item/<id>%2C<id>…` over the copies' item-IDs in listing order, **deduplicated** — the form keys one fieldset per item, so a second copy of one stamp cannot be declared twice and is named in the report instead of dropped). It fills each copy's condition (`new_sale[cond_20_<id>]`, through #404's mapping), the price, the number of sets and the two texts, and leaves `expiry_date` / `auto_renewal_*` exactly as served — required, pre-filled, matching nothing here, so writing our own would clobber the collector's defaults; `options[] = separate_listings` is never touched either, but a *ticked* one is reported, since it moves pricing to the per-item fields and turns pictures off. An **over-long text is neither written nor truncated**: truncating mangles chosen wording, and a scripted assignment past `maxlength` is not refused the way a paste is, so the form would carry a value Colnect then rejects — the report gives both numbers and points at #403's counter. Colnect's **currency is a seller-level setting** and not a form field, which is what a platform locking its currency (#196) is for. A `<select>` is set by **selecting the option**, never by assigning `value`: a grade the form does not offer is then a refusal rather than a silent no-op. **Pictures** (#411) are one more optional neutral member — `attachPhotos(doc, photos)` — and are the run's **last** step, never part of `fill`: Colnect's Dropzone posts each picture over AJAX the moment it is handed over, minting a draft `sale_id` *before* the sale is saved (#402), so this is the first thing in a whole listing that writes to the marketplace at all and it happens with a filled form already in front of the collector. Whether that leaves orphans behind on an abandoned form is still #402's open question; putting photos last is what makes the answer not matter much either way. The images are what the kit already carries (#405) — the upload set, in upload order, under the ZIP's own names (#314/#326) — so nothing on the app side changed. Three pure decisions sit in `listing-run.ts` before a byte moves: a module with no uploader is **silence, not a gap**; a plan that is not `ready` is a skip naming what Stamporama is doing about it; and a set past `LISTING_PHOTO_BUDGET_BYTES` fills **from the front**, the plan's order being the priority order (#313), exactly as the platform's own photo limit fills it. An **out-of-date** render is none of those and is deliberately not reported here — the offer's Photos card already carries that signal, and repeating it in a fill report would turn a signal into a warning. The bytes are fetched in the **worker** (`background/photo-client.ts`, the photo route's own Assistant token, the profile named by page origin + task collection exactly as #412's write-back names it) and cross to the content script **base64** over `attach-photos`, because extension messaging is JSON and a `File` does not survive it — which is also where the budget comes from, and why the ceiling is stated rather than hidden. The `File`s are built in the page, the realm the form is in. Colnect's own half finds the Dropzone's real `<input type="file">` **structurally**, by what it accepts: it is the one control in the form #402 mapped that Colnect does not address by a `new_sale[...]` name, so there is no name to match on. Every failure is a **skip, never a refusal** — an unaccepted file type, a `disabled` uploader (which is what ticking *separate listings* does), a non-`multiple` input, a fetch that failed — because the fallback the scope asks for is dragging the offer's ZIP in, not redoing the listing. The report says the pictures were **handed over**, not that they arrived: the upload is Colnect's own AJAX and the thumbnails appearing in the Dropzone are what confirms it, right where the collector is already looking. The **match handoff** is that same contract a third time (`#stamporama-assistant-match`, `extension/src/core/match-handoff.ts` ↔ `src/app/c/[collectionSlug]/offers/assistant-match-handoff.ts`), for the step *before* a listing: posting needs every stamp matched, so an offer's Items card hands over the catalogue search it already builds (#423) and the worker does the two things a page cannot — open the tab and put the match window in front of it (`open-match`, answered `running` → `opened`, since what happens in that window is the collector's own work). A **third** node rather than a task type on the listing one, because an offer being prepared is matched *and* listed and the two answers must not overwrite each other; the URL is re-parsed on the extension side and refused unless http(s), it being handed straight to `chrome.tabs.create`. The write comes back not down that path but as a **doorbell**: every confirmed match sets a changing `data-stamporama-assistant-matched` on `<html>` of every instance tab, carrying no request id on purpose — any match may be the one a screen is waiting for, re-reading an offer is cheap, and matching started from the toolbar icon has no handoff to answer at all. **Link all** is therefore page-driven, a queue taken when the walk starts and advanced on each ring: the extension cannot know what is still missing, and a walk re-derived from fresh data would reopen the row the collector deliberately skipped. **Going back to a live listing** (#462) is that same run at a second address: `PlatformListing` gained one more optional member, `editUrl(task)`, because on Colnect the edit page *is* the sale form — `…/sell/edit/sale_id/<code>` over the code the stored entry URL already carries (#412), same `new_sale[…]` names, same five grades, same Dropzone — so `fill` has no variant, `isFormUrl` answers for both addresses, and the task's `mode` decides the URL and nothing else. Optional for `attachPhotos`' reason: posting to a marketplace is no promise a posted listing can be reached again, and Allegro's Assistant form (#493) is entered through a sequence that exists only on the way to a *new* listing — hence `supportsUpdate` on `listingModuleRules`, a third question beside the two #471 already separated. The preconditions are **one evaluation asked about two acts**: everything about the goods is identical on an edit form, and only the leading state check moves — `create` wants Ready, `update` wants Active *and* a listing URL, each standing alone as `not-ready` does. Nothing records what was last posted, deliberately: an update reloads **every** field whether or not it changed, since a field left out because it looked unchanged is how a listing quietly keeps an older value, and a stored snapshot would be a second copy of the offer to keep honest — so the button is simply always there. What that reasoning ruled out was a *per-field* diff, and #542 later separated the coarser question out of it: `Offer.listingContentChangedAt` (`offer-listing-drift.ts`) is stamped when an offer that is **up** — `active` or `paused`, both being listings a buyer can see — has its composition, its stated price or one of its texts changed, and answers "which of my live listings did I change?" without claiming to know *what* in them changed. It is a timestamp of the **first** such change and not a snapshot, so it reads as "diverging since…" (the figure a collector triages by), it cannot fall out of step with the offer the way a stored copy would, and it is two plain columns (`LISTING_DRIFT_WHERE`) rather than another comparison that has to be resolved to ids (#499's). It carries **no filter chip of its own**: it is the same category as `needsAction` — a live marketplace entry that is wrong and only the collector can put right — so *Needs action* selects **both**, unioned as ids in `resolveOfferOverlays` (never folded into `needsActionRows`, which counts *dead copies*, which drift is not) and deduplicated for the facet, since removing a set that sold elsewhere is itself a change and one offer must not be counted twice by a badge that opens one list. The URL narrowing survives as `listingOutOfDate=1` with a chip rendered **only while it is on**, the #481 rule — a filter reached by a link with no way back off it is a list quietly lying about what it holds — because the notification centre's own group (`offer-listing-changed`, `warning`, graded below the `critical` pair on the one line drawn everywhere here: no double sale is possible) has to land on exactly the rows it counted. That group is read **oldest-divergence-first**: it is a backlog, not news, and nothing in the world will ever mention a stale listing if it does not. The trigger is #513: a set joining an offer that was already posted is the case the whole signal exists for. Two changes sit outside it on purpose — an auction's **current** price is an observation of the bidding (#449/#481), not something the seller changed, while its **starting** price is the seller's own statement and counts; and the generated photos keep their own out-of-date signal (#311), which says the same kind of thing about the images and says it on the card the images are on. It clears on exactly three acts, each of which genuinely puts the current contents in front of buyers: publication (`ready → active`), an Assistant **update** that saved — reported `updated` and written by the *page* through `markOfferListingSyncedAction`, the same "the extension reports, the instance decides" rule (#407) the publish path follows, and the one write #462 said an update makes — and **Mark listing up to date** by hand, which every platform with no update flow needs and which is also the answer when the change was not worth going back for. Pausing and **resuming** clear nothing: a resume puts the same entry back up. And a closed listing simply stops reporting, the flag being *derived* as `listingContentChangedAt && isListedState(state)` in both readers rather than cleaned up on every terminal transition. Pictures are a **replacement**: the listing's existing set is deleted first (`a.del-button`, Colnect's own AJAX, one at a time and each waited out — a burst is how an account earns a 429 mid-edit, #487's reasoning arriving at the same answer), because appending would leave the live listing carrying two of everything on the second run; a deletion Colnect does not confirm **stops the upload** rather than duplicating the set, the form staying filled and the offer's ZIP being the fallback #411 already wrote down. That is also why `attachPhotos` may answer asynchronously here — #493 opened that door for Allegro's watermark dialog and this walks through it for a plainer reason. A saved edit is reported `updated` and writes **nothing**: the offer was Active before the run and carries the very URL the run was sent to, so the publish path is not merely skipped but unreachable — which is what `PendingListing.mode` is for, Colnect answering a saved edit with the identical entry page a saved new sale lands on. The bulk workspace (#322) is untouched, being scoped to Ready offers because posting is what a batch is for.

- Assistant **lot capture** (#355; ADR-0015 §third-half, ADR-0021 §8) is the extension's third module half — `capture` (`isListingUrl` / `capture`, `extension/src/platform/capture.ts`), beside `extraction` (now optional too) and `listing`. Allegro carries **capture alone**, and that is a complete module: a marketplace this collection only ever bids on is neither a catalogue to match against nor a shop to list into, so `PlatformModule` has no required half left and `moduleReports()` names all three. The toolbar click therefore has a **third meaning**, decided in the worker off the URL alone (`findCaptureModuleForUrl`) because the click is what grants `activeTab` and no content script has run yet: registration, capture, match. Capture opens `capture.html` — a window of its own, sharing only the profile badge and the window slot with the match window, since one lot's five fields and a page of candidate stamps are different questions. Reading is the **page's own JSON**, never its markup: Allegro renders through `opbox` boxes that ship their data beside them as `<script type="application/json">` while every class name is hashed per build, so a selector would break silently and a capture that breaks silently records a lot with no bid. Three blobs found **by shape** (the box ids are opaque and per-page): `biddingSection` → closing instant + current figure + currency + `popularityLabel`, `sellerName` → the seller, JSON-LD `Product` → the title (`document.title` carries Allegro's own suffixes). The auction test is `biddingSection.visible` — a *Kup teraz* offer carries the identical section with `visible: false` and a null `endingDate` — and a fixed-price page is a **refusal naming what the page is**, not an error: there is no bid to observe and no close to age against, and a lot invented from one would sit in the watchlist forever. The one judgement the module makes is **bid or opening price**, from the bidder count (`/licytuj/`, so the fixed-price *"9 osób kupiło"* in the same field reads as none): with nobody bidding, Allegro still prints "Aktualna cena", and recording that as a bid would cost the parcel money nobody has offered (#351). Allegro's *Numer oferty* is the same digits as the offer id and is carried **twice on purpose**: `platformOfferId` is the listing's identity, matched on and never shown, while `lotNo` is a number *on a lot* — the slot a house sale's lot number occupies, displayed and editable — so the watchlist reads the same however a lot got there. The URL stored is the canonical `/oferta/<offerId>`, never the slug or the `/produkt/…?offerId=` shape — the id is the part of every address that is the listing, and it is what makes a **re-capture a refresh**. `findCapturedLot` looks for it in **both places it is recorded**, because a lot added by hand carries whichever the collector happened to type: `lotNo` **equal** to the offer id, scoped to sales on that platform (an offer number is unique on the marketplace, so equality is the whole test — and the scope is what stops a house sale's `Lot 42` being read as offer 42, one field over two vocabularies), or the `url` at the **address's own boundaries** (`/<id>`, `-<id>`, `offerId=<id>`) and never as a bare substring, `8795065609` otherwise matching the middle of `18795065609` and refreshing a different auction's bid. A match then writes and then writes `currentBid` + `checkedAt` through `setAuctionLotBid` and **nothing else**, because the title, the closing time and the composition are what the collector has since typed. Everything about *where* it lands is server-side: the platform from `Contact.platformModule = "allegro"` (Settings → Allegro, one select, the exclusive setter now shared with Colnect's identical question in `module-platform.ts`), the seller resolved by name through `resolvePurchaseContact` as a typed-in name is, the parcel through #352's open-sale matching. `dryRun` is the same function answering what *would* happen, so the window's preview can never describe something the save would not do — and it resolves nothing into existence, hence the seller **lookup** rather than a resolve on that path. There is deliberately **no declarative content script for allegro.pl**: the feature starts with a click, which is also what grants access, so the script is injected then rather than run on every page of a shop the collector browses. An unset platform is a refusal pointing at the tab that fixes it (`no-platform-module`), never a guess. **Find in Stamporama** (#529) is the extension's fourth gesture and the only one that is not a toolbar click: a *selection*, right-clicked, on any page at all (`contextMenus`, `contexts: ["selection"]`). The icon's three meanings are decided by what the page **is**, and this one by what the collector **pointed at** — a different question, so a different affordance rather than a fourth branch in `chrome.action.onClicked`. It needs no content script and no `activeTab`, the text arriving inside the click (`info.selectionText`), which is exactly what makes it work on the marketplaces no module here covers. The window (`search.html`, `extension/src/search/`) shares the Assistant window slot with the match and capture windows and carries the selection as `?q=`, put in an **editable** box rather than searched for silently: a selection catches whatever the mouse caught, so refining it is a keystroke instead of a second drag on the page. The read is `GET …/api/collections/<id>/search?q=` (`src/lib/collection-search.ts`, session-or-token as every other Assistant route), and it **decides nothing about what matches** — the stamp half is the inventory picker's own search (#104/#73), the issue half the issue picker's, the copy half the Copies list's (#106), because the three lists a collector reads already disagree about what a query means and a fourth notion invented here would answer a question no screen would then repeat. The *stamps* group carries the answer the menu was clicked for, and the window renders it as **two sections**: the stamps carrying open **wants** (#532) are split out into a section of their own, **first**, and *Stamps* is what is left. A section rather than a chip on a row, because a want found by scrolling past twenty stamps is a want found too late; **split** rather than highlighted, because a row appearing in both would make the leading section a decoration rather than an answer (the link is the same either way, so moving it costs nothing). Wanted leads because it is the answer that decides a bid — holding a copy does not close a want, so a stamp already in the collection may be exactly what is being looked for in another condition, and a count that only said how many are held would answer the easier half. A want row is **one row per want**, ordered most urgent first across the whole result and edged in the priority colour, led by the axes in the want list's own wording with the *stamp underneath* — the inverse of every other row here, since at an auction the decision is made on the condition, and a chip reading `1 want` sends the collector back to the app. Two wants on one stamp are two decisions and never a count. The `here` / `coming` figures are that **want's own**, not the stamp's — a mint-only want reads zero beside a used copy in the drawer — and `coming` is what stops a second purchase of something already ordered; `toSort` folds into `here`, sorted-versus-on-the-desk deciding nothing at an auction. The acceptance **ids** the app's summary carries are dropped at the boundary: nothing in that window holds a copy to test them against. The held count rides on want rows too (that pair *is* the upgrade case), travels as both figures (#348 and #528's variant descendants), is **never summed** — a copy of a specific variant is not a copy of the umbrella — and reads **Not held** at zero, an empty badge being indistinguishable from a badge that failed. The **negative** want answer is a sentence rather than an absent section, which is indistinguishable from a window that never asked. A **copy** row wears the inventory row's own disposition chips (#550) — *In collection* / *For sale* / *For trade*, `copyDispositions` in `extension/src/core/search.ts`, the app's order, wording and hues (#99) — because which piece this is answers only half the question at an auction and whether it is a keeper, a duplicate already for sale or trade material is the half that decides the bid; three independent flags and never one state, so any number of them show at once, and **none** showing is the app's own answer for a copy whose disposition was never decided rather than an invented *No disposition* chip. Rows carry **relative paths** and the origin is composed extension-side against the one the profile authenticated against, #466's rule; the menu is `removeAll` + `create` on both `onInstalled` and `onStartup`, Chrome persisting context menus and refusing a duplicate id, so a bare `create` would make an update the one event that breaks the entry.

- The match window **confirms a decision, not a write** (#515). `askConfirm` in `extension/src/popup/index.ts` is raised by `confirmOne` (which names the one candidate stamp it links, out of several) and by `overwriteOne` (which destroys a catalog number we hold) — and by nothing else. `writeAuto` writes without one: the button already reads `Write 8 auto-matches + 3 catalog numbers` and the badge above it names the target, so the overlay only restated the label just clicked, and an auto-match is by definition the case the matcher (#250) had no doubt about. It then **closes the window** the moment the instance answers — no pause to let the result line be read, which would only be the dismiss step this removed worn differently. A batch write is the last act in this window, and closing loses nothing, since the write is already on the instance and the next icon click re-scans; the merge and status line before the close stay as what the window falls back to should the close not take. The auto-close is the *batch* button's alone: resolving ambiguous matches is done several in a row, so those keep the window up. The **capture window closes on a successful save** for the same reason (#522): one lot is one window, the composition is entered in the app rather than here, so the save is the last act — and a failed save keeps the window up, holding the corrections typed into the form beside the reason they did not land.

- Assistant **distribution** (#288; ADR-0017, superseding ADR-0016) — published to an **unlisted Chrome Web Store listing**; the store assigns the ID and signs, so there is no CRX, no signing key and nothing served by the instance. `extension/pack.mjs` (`pnpm assistant:zip` from the root) writes a store ZIP with the app version stamped in; CI's `publish-extension` job uploads and publishes it per release tag (`CWS_CLIENT_ID`/`CWS_CLIENT_SECRET`/`CWS_REFRESH_TOKEN` secrets, `CWS_PUBLISHER_ID`/`CWS_EXTENSION_ID` variables), but only when `extension/` changed since the release the **store** already holds — asked for with `:fetchStatus`, taking the newer of the published and in-review revision, so a submission that failed or was paused is picked up by the next release rather than lost. The store's `uploadState` is `SUCCEEDED` on this API (v1.1's `SUCCESS` is accepted too); the job is also dispatchable on a tag, so a refused submission is retried without moving it. Self-hosted force-install was tried and fails: Chrome honours a non-store `update_url` only on an enterprise-managed machine. The unpacked dev build and the store build stay **two extensions** with two IDs (`extension/identity.mjs`; `manifest.json` carries no `key`), so both can live in one browser and a dev profile can never reach a production collection.

- The **Colnect condition mapping** (#404) is the condition-side counterpart of #248's catalog-abbreviation mapping, and lives in the same place: one row per `StampCondition`, per collection, in **Settings → Colnect**. Per collection and not per platform `Contact`, because Colnect's vocabulary is **fixed and global** (#402 — the identical five options render under every item of a multi-item sale form), so only Colnect's option value is stored and the label it renders as lives in code (`src/lib/colnect-conditions.ts`, pure). The two rules it does **not** inherit from #248 are the interesting ones: there is no exact-abbreviation fallback and nothing is silently ignored — an unmapped condition is a listing **precondition failure** (#406), because a wrong grade on a published listing is worse than a blank the collector fills in. `guessColnectGrade` exists but matches the **abbreviation alone** and only ever proposes. Every condition is listed whether or not it is mapped, so a blank select *is* the unmapped state and a legitimate answer (no cover grade exists on Colnect); clearing a mapping **deletes the row**, so "unmapped" has one representation everywhere. The panel has no draft and no Save — the select is the control, one write per change — and `setColnectConditionMapping` validates against the built-in list, so a stored value can always be rendered and posted. `loadColnectConditionMap(collectionId)` is the read primitive #405/#406 build on, loaded **once per offer**: a komplet is dozens of copies over a handful of conditions.

- Colnect prints a private note as **plain text**, so a link in one is not clickable — which is what `extension/src/core/instance-links.ts` (#417) fixes, on the sale page's own `._sl-private-note` element and nowhere else. Two rules, and they are separate on purpose: **origin decides whether** (only an instance in `chrome.storage.local` is rewritten — an extension that linkifies arbitrary text on a third-party page is a phishing vector, and "an address I hold a token for" is the one definition page content cannot spoof), and **path decides what it says** (`/o/<slug>/<no>` → `Offer #42`; the older `/c/<slug>/offers/<cuid>` → a plain `Stamporama offer`, a cuid being worth nobody's eyes). Matching on origin alone is also why both shapes are one case: notes published before #416 keep working. The mark comes from `extension/src/core/mark.ts`, which inlines it through esbuild's `dataurl` loader — deliberately rather than `chrome.runtime.getURL`, which would need a `web_accessible_resources` entry handing every page the extension's id, and 355 bytes is cheaper than that trade. It picks the icon **matching this build's toolbar** off a `__DEV_BUILD__` define (amber unpacked, blue released, ADR-0017): a collector running both copies reads the colour to know which extension just spoke to them, so a mark that is always blue lies on half of those pages. Pure DOM, so it is unit-tested under `linkedom` like the platform modules; idempotent, and it skips text already inside an `<a>`.

- The **link from a listing back to the offer it is here** (#466) is the selling-side counterpart of that: `extension/src/core/offer-marker.ts` draws it in **two shapes**, both opening in a new tab: a corner card on an Allegro offer page (that page *is* one offer), and a **plain** `Offer #42` link after the row's own `nr: <id>` line in **Mój asortyment** (there the question is asked once per row, and the row already prints its identifier there). The number is found by *being that id* — the leaf whose whole text is it — a fact about content rather than about markup, with the anchor as the fallback. Plain and not a chip: a bordered box with its own background pushes a cell laid out by the marketplace around, which is exactly what the first cut did. The list is watched with a `MutationObserver` and every anchor records **which** listing it was answered for — paging that table reuses its row elements, so a bare "already linked" flag would leave a row pointing at the previous page's offer — and a listing that matched nothing is recorded too, or a table of somebody else's offers is re-tested for ever. It is drawn *into the page* rather than offered by the toolbar click, because that click already means **capture this as an auction lot** (#355) and quietly changing what a gesture does is worse than a second, separate affordance; and because "this one is mine" is worth knowing before any click. A page it is on states only *which listing* it is — the id off the address, through the capture half's own `listingId(url)`, so the shell never names Allegro — and the **instance** decides whether that listing is ours: a listing being bid on and one being sold are the same URL and the same markup. `findOffersForListings` (`src/lib/offers.ts`, `GET …/offers/by-listing`, session-or-token like the matcher) answers it from Allegro's synced ids first (`AllegroListing` / `AllegroOrderLine`, #467 — exact) and falls back to the boundary rule over `Offer.url` — resolved **in memory** (`urlNamesPlatformOffer`) over the collection's stored addresses, because a batch of 200 ids as `OR` arms would be a thousand `LIKE`s while the addresses are two small columns read once. It takes **many ids per call**: a list asks about every row it draws, and per-row lookups would be a request per row. It answers a **relative** path: the extension joins it to the base URL it authenticated against, so the address never depends on `BETTER_AUTH_URL`. Neither shape is anchored to a class name — every Allegro class is hashed per build, which is why the capture module reads the page's JSON and never its markup — so the card floats where no selector is needed and the inline link hangs off an anchor found by its **address**. This is also the one place the extension scripts a marketplace declaratively without a click, narrowed to `/oferta/*`, `/produkt/*` and `…/obsluga-ofert/moj-asortyment*` (ADR-0015).

- The **link back from a listing to the auction lot it is being bid on as** (#575) is #466's buying-side twin, and the two are deliberately the same act on the same page: `extension/src/core/lot-marker.ts` draws a corner card naming `Lot #12 · Open` over the parcel the lot sits in, opening the lot's own address (`…/auctions/sales/<saleId>?lot=<lotId>`, a lot having no page of its own) in a new tab. Drawn into the page rather than offered by the toolbar click for #466's reason twice over — that click already means *capture this as a lot* (#355), and this is the answer deciding whether to make it: a tracked listing is captured again only to refresh its bid, an untracked one is a new lot. **One shape only**, unlike the offer side's two: the buying-side counterpart of *Mój asortyment* is a search result full of strangers' auctions, where marking the two a collector happens to track would answer a question nobody asked on markup the site rebuilds as you type. The page states which listing it is (the capture half's own `listingId(url)`, so the shell still never names Allegro) and the **instance** states whether that is a lot of ours, the two lookups asked **independently** and in parallel from `markOwnListings`: a listing is ours to sell, ours to bid on, or — nearly always — neither, and no answer stands in for another. Hence a second endpoint (`GET …/auctions/lots/by-listing` → `findLotsForListings`, session-or-token, batched and capped like the offer one though the page that asks is a batch of one) rather than another field on #466's, the two being asked of different halves of the collection. The matching rule is `findCapturedLot`'s **unchanged** — `lotNo` equal to the offer id and scoped to sales on the Allegro platform, plus the `url` at the address's own boundaries — because "already tracked" must mean here exactly what it means to a save, or a listing would show no card and then refresh a lot on the next click; it is read **in memory** through `urlNamesPlatformOffer` over the collection's addressed lots, the offer lookup's own trade (#466), and an unset platform module costs only the `lotNo` half rather than the whole answer. The outcome travels raw (`pending`) and is worded by a map mirrored by hand in the extension (`OUTCOME_LABEL`, the app's *Open*), as `copyDispositions` mirrors the inventory's chips (#550) — an unknown word is printed rather than dropped. The card carries the **sale**, not the lot's title: the title is what the page in front of the collector already says, while which parcel this lands in is the fact only Stamporama holds. Both markers now hang in a shared fixed corner **stack** (`core/marker-shell.ts`, `data-stamporama-markers`, pruned when the last chip leaves so a page of misses is left as it was found) rather than each positioning itself: a listing is one or the other in practice, but nothing in either answer says so, and two chips claiming one corner would leave the lower unreadable. The stack counts as the Assistant's own markup in `isAssistantNode`, or creating and pruning it would schedule the re-scans that watcher exists to avoid.

- **The mark on a sold order** (#612; [ADR-0038](../decisions/0038-delcampe-order-import.md)) is #466's split applied to a *sale*, and the first mark in this extension that offers an **act** rather than an answer. `extension/src/platform/delcampe/orders.ts` reads Delcampe's own **My Sold Items** screens through a fourth module half — `orders` (`matches` / `read`, `platform/orders.ts`, found by `findOrdersModuleForUrl`) — and the Delcampe module carries **only** that half, which is a complete module: there is no Delcampe form to fill (#608/#610 list by uploading a file), no catalogue of Delcampe's to match against, and these are the collector's own sales rather than somebody else's auctions. The page states *which order* a row is (`payment-request/<id>`) and the **instance** states what that order is here — a link to the sale, or **Import** — batched through `GET …/sales/by-delcampe-order`, session-or-token, answering a relative path, all three exactly as the offer and lot lookups do. It is #466's **inline** shape rather than a corner chip because a phase screen is a list: the question is asked once per row and the answer belongs beside the link that already names the order. The click needs no confirm overlay (#515's rule — the button says *Import* and the row beside it says which order), it says *Importing…* while the instance decides because it is the one mark that starts something, and a refusal keeps the sentence in a `title` with the button under it, since the way through is to fix what it names and press it again. `core/marker-shell.ts` grew from "the corner stack" into "what the Assistant drew": `isAssistantNode` moved there with the three mark attributes, because the page watcher's own question has to cover a mark added later and an answer assembled from constants scattered across modules is one that silently stops covering one.

- **The reading is anchored on addresses and decides nothing** (#409's contract, kept strictly). The module reports what a row printed — `US$3.00`, `Sun 22 Mar 2026 at 22:25`, and *both* figures the header prints for one total (`± €13.95` converted, `US$16.15` in the listings' own currency) — and the instance settles which currency that is, what day it was, which offer each item is and whether the order may be recorded at all (`delcampe-order-rules.ts`, unit-tested in the app rather than inside somebody else's page). Delcampe's classes are not hashed per build like Allegro's, and the addresses are still what a page is *about*: the order off `payment-request|bills/<id>`, the items off `item/<id>.html`, the buyer off `user/profile/<id>-<login>`, and the grouping by **containment** — the nearest ancestor of an item link naming exactly one order *is* that item's order, which is one rule covering all six phase screens (`list`, `to-invoice`, `invoiced`, `to-send`, `sent`, `archived`; they differ only in which `bills/<id>/status/<transition>` links they carry, a fact about the order rather than the page). A single-item order is why a row climbs on "one item link **and no order link**": the block holds exactly one item there, and a row that swallowed the header would read the order's total as the stamp's price. Two things have no address and are read from content — an amount is a leaf whose **whole** text is a currency figure (`USA $5 Liberty` is a title containing something price-shaped, and a title is never a leaf that is only a price), a date is a leaf that reads as one — and the paid price is the **first** amount in a row, which is also true of a discounted one, where Delcampe prints the price paid, its conversion, then the original struck through. The buyer is **a login and a name** and the block also carries their address and a message relay: what is never read cannot be stored.

- **The orders half serves a second marketplace** (#698; [ADR-0041](../decisions/0041-colnect-transaction-import.md)), and what a second one needed is the interesting part. `extension/src/platform/colnect/orders.ts` reads Colnect's own transaction screens — the detail (`/<locale>/transaction/show/id/<id>`) and the list (`/<locale>/transaction/list`) — and the Colnect module now carries **three** halves. Anchored on addresses like Delcampe's: the order off the detail's own path (accepted **with and without** a locale segment, the list's *Details* href carrying none while every other address on the page does), each item off `market/sale/<code>` — `Offer.colnectSaleId` (#696), the only join a row offers, Colnect printing no seller reference — and the buyer off `collectors/collector/<login>`. What has no address is read from its **printed label** (`Item count:`, `Started:`, `Shipping method:`) and Colnect's own classes (`_sl-entry`, `_sl-price`, `_t-transaction-price`) are tried first as a shortcut and never relied on. Three fields joined the contract, all as printed: `PlatformOrderLine.quantityText` (Colnect counts a row, Delcampe prints one row per copy), `PlatformOrder.soldAtText` (Colnect dates the **order**, Delcampe its rows — one of the two is always null) and `PlatformOrder.shippingMethodText`. The header's figures keep **the words beside them** (`Total with shipping € 12.00`): four amounts that differ only in meaning cannot be told apart by size, and dropping the label destroys the decision rather than deferring it. The row a listing sits in is `_sl-entry` where it exists and otherwise a climb that stops at a **second** sale code and at the transaction's own furniture (the buyer link, the totals block) — that second stop is what keeps a single-listing transaction from reading its total as the stamp's price, the same trap Delcampe's single-item order set.

- **A screen may be readable and not importable** (`PlatformOrder.canImport`, #698). Colnect prints a transaction in two places and truncates its items in one of them (`+ 12 more listings`), so the list can say *whether* an order is recorded and must not offer to record it — ADR-0038 §3 from the other side. It is a fact about the screen, so the module that read it reports it, and the mark grew a third state (`not-recorded`: plain text, no link, no button) rather than the shell learning which marketplace truncates what. The two order messages now carry the **module id**, and `order-client.ts` builds `…/sales/by-<module>-order` and `…/sales/<module>-order` from it: an order id means nothing without the site that issued it, the two marketplaces are matched against different columns, and a third module needs nothing in the client.

- **The act reports in a window, and the mark goes back to answering** (#698's follow-up; [ADR-0041](../decisions/0041-colnect-transaction-import.md) §11). `core/order-dialog.ts` — a backdrop and a panel drawn into the page, opened **on the click** in a `working` state, then either the sale (its number as a link, plus buyer / date / lines / lines total / buyer paid / shipping / status, and the count of lines whose set nobody has chosen, #697) or **every** refusal as its own list item. The mark could carry neither: `Not imported` with three reasons run together in a `title` is the all-or-nothing rule stated in the one place it cannot be read, and `Sale #34` is a number with nothing to check the page against. A sale that was **already** recorded is described identically — a re-import is a link, and a link worth following is worth describing. Not a confirmation (#515 unchanged: nothing is asked before the write) and not a replacement for the mark, which still answers beside the row after the window is closed. It closes on its button, on the backdrop (only a click that *started* there — a drag out of a selection is not a dismissal), and on **Escape**, whose handler is taken off with it or a content script would keep swallowing the page's own key. `ORDER_DIALOG_ATTR` joins `isAssistantNode`, or the page watcher would chase the window we just drew. It serves **Delcampe too**, deliberately: one act with two behaviours is worse than the behaviour it replaces. The instance therefore answers both imports with an `ImportedSaleSummary` (`src/lib/order-import-summary.ts`, read the same way for a sale just written and one already there) and the refusals travel as a **list** as well as the joined sentence the mark keeps.

- **A value printed beside its label is not an element** (#698, found on the live page). Colnect writes `<b>Started:</b> August 23, 2026 2:21 PM`, so the first reader — which walked elements — saw the label, found no value, and refused every transaction over a date printed right there. Three rules replaced it: a labelled line is the **smallest element whose own text begins with the label and says more than it** (every ancestor's text begins with it too, and the innermost is the line the page drew); where no element holds both — Colnect's header is one flat run of `<b>` labels and bare text — the value is read **forward from the label**, siblings and text nodes alike; and every value **ends where the page's next label begins**, from a list of the page's own labels rather than at any word with a colon, since `Shipping method: Stamps→domestic: Registered mail` carries one inside the value. The same three now find the buyer's name, which was being read off whatever element happened to hold the link.

- **The listing's own id travels on the task** (#696). `ListingTask.listingId` — the platform's own identifier for the live listing, `Offer.colnectSaleId` on Colnect — mirrored **optionally**, so a kit served by an instance predating the column is still a valid task rather than a malformed one, exactly as `mode` (#462) is. `colnectSaleEditUrl` prefers it and keeps `colnectSaleCode(task.listingUrl)` as the fallback: the two strings are the same code, but the one in the URL sits behind a **locale segment that is whatever Colnect served**, and a code the instance states directly is one the extension does not have to recover. It stays a neutral field rather than a Colnect-shaped one for `allegro`'s reason in reverse — an id is a thing every marketplace has, and turning one into an address is the module's job. `colnectSaleCode` is now mirrored on **both** sides (`src/lib/colnect-link.ts`), the instance needing the same reading to write the column the task carries; the two are hand-mirrored like every other contract here, and a reading that drifts apart is a listing edited at the wrong address.
