# Catalog, Stamps, Checklists & Wants

Format, subtype, catalog prefixes and numbers, the issue stamp tree, checklists and wants.

- Physical **format** (pair, block, strip) is an axis of its own (ADR-0020), not a stamp — superseding #135's "record a multiple as its own `Stamp` with a self-descriptive number" for *homogeneous* multiples, which collapsed on deep variant trees (Infla `309 → 309A → 309AP → 309APa`: `formats × nodes` stamps, and "a pair, variant not yet identified" inexpressible because a pair of `309BP` is not a child of a pair of `309B`). `StampFormat` is a per-collection dictionary shaped like `StampCondition`, referenced from `Item.formatId` *and* `StampCatalogPrice.formatId`. **Null means single** — no such row is seeded, exactly as a null `certificateStatusId` means "no certificate" (ADR-0006 §2) — so nothing needed backfilling. A multiple is **never decomposed**: no unit count exists, nothing multiplies or divides by one, and completeness treats format as a breakdown dimension beside condition ("the series in pairs?" like "the series in MNH?"). Zusammendrucke with their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) stay their own `Stamp` — the test is whether the catalog numbered it, not whether it holds more than one stamp. A format's price is **explicit or derived**: an explicit `StampCatalogPrice` row wins, else the single's price × a `StampFormatFactor`, because catalogs publish one factor per issue and an explicit price only where a multiple deviates. Factors live in one table with nullable anchors — the all-null row *is* the collection default (no second `defaultFactor` mechanism to explain) — resolved by **fixed precedence**, `(issue set?, area depth, condition set?)` lexicographically, never a specificity score: *where* deliberately outranks *for which condition*. The rule is pure in `src/lib/format-factor.ts`; `format-pricing.ts` wraps it per stamp because it needs the area ancestry and issue. A format is **translatable** like every other dictionary that reaches a listing (#344; `StampFormatTranslation`, two independently-falling-back columns, `format` in the shared `TranslatableEntity` union), and renders through `{format}` / `{formatAbbr}` + `{#formatLegend}` (#345) — where a **single resolves empty**, the common case, handled by the existing tidy pass rather than by a rule of its own. Lists gain an **`as`** switcher beside the condition one (#343), defaulting to Single, hidden without formats, stored as `""` because Single is not a row. A list column **derives** where nothing explicit was recorded and marks it with the same `~` + italics an unknown-variant rollup uses (#238) — one vocabulary for *inferred, not recorded*, distinguished only by tooltip. The Copies list takes format as a **filter**, never a switcher (a copy's format is a fact), and `valuateCopy` resolves at `Item.formatId`: with no explicit price and no factor a multiple is **unpriced**, never valued at the single's figure. Per-row factor resolution would be a query per row, so `makeFormatFactorLookup` loads the factor rows + area tree once and resolves in memory. A multiplier is **edited where its scope lives** — an issue's from its row on the Issues list, an area's from its row under Areas — so the anchor is never a field the surrounding screen already answers; Settings edits only the collection default and areas and **does not list issue-anchored rows at all**, excluding them *at the query* (`getCollectionFormatFactors`) rather than filtering after: there can be one per issue per format, which is thousands of rows. A scoped list shows what is set on that row alone, never what would apply through inheritance — it is an editor, and showing a parent's rule under a child invites editing it from the wrong place. The scoped editor is one component exposed both as a `{ action, dialog }` row-action hook and as a plain dialog, because the areas panel maps its rows and cannot call a hook per row. The price grid gains format **tabs**, not columns, and a derived value renders as the cell's placeholder so it stores nothing until typed over. Price cell keys grew a **trailing** `~<formatId>` segment, optional so pre-format payloads still parse. **Intake records a format too** (#573): `intakeStamps` no longer hard-codes `formatId: null`, and the field sits beside condition and certificate in the intake step — the piece is a block at the moment it is identified, and correcting it afterwards is one copy edit per piece, from memory, after the sorting pass. Single-stamp intake only, the rule photos follow (#148) and for a stronger reason — a whole-checklist intake fans out across many stamps and one format could not be true of all of them — so the server drops it for a checklist rather than refusing, and hidden entirely until the collection defines formats, as the list's own format controls are. It is deliberately **not** remembered per collection, and that asymmetry against the three fields around it is the decision, not an oversight: condition repeats down a stockbook page (all mint, all used) so remembering it saves hundreds of clicks, while single is the default state of the world and a multiple is the exception, so a sticky format would mark every later single as a block until noticed — this feature's own failure inverted, and worse, since a format nobody chose is invisible where a missing one reads as *single*. The reasoning is parked at the `useState` in `IntakeConditionDialog`, which is where someone counting three remembered fields and one not would go to "fix" it — and the reset is **enforced there too**, off the identity of the `selection` prop, rather than inherited from the dialog being conditionally rendered: a remount is a fact about the component tree, so keeping the dialog mounted across a transition later would quietly make the field sticky again, and no test can see it. `selection` is rebuilt at every pick, which a key derived from the stamp id is not — a block of four followed by singles of the same stamp is one intake run. `IntakeHoldingsLine`'s live want marker takes the format as its third axis for the same reason its docstring gave for passing null before. **Completeness takes it as a third axis too** (#133, closing what #519 left open): `CompletenessCount` carries `formatId` and `ChecklistCompletenessGrid` gains `formats` — the same disposition × condition grid per format, counted over copies of that format alone, so a block never fills a gap in a set of singles. `rows` stays the roll-up across every format and is unchanged, which is what keeps it the honest answer to *have I got the series at all*: mixing formats there is the mixing the `conditionId: null` column already does down the condition axis, not a claim that a pair is two singles. Which formats appear is **what the checklist is actually held in**, judged over its own stamps (a block held for the neighbouring specialized set opens no column here) — the dictionary supplies only the order, single first — because format is sparse where condition is not, and a grid per dictionary row would be a wall of zeros. The card draws them as **tabs**, the price grid's choice for the same reason (a third dimension inline is unreadable), and draws none at all where only one format is held, so the overwhelmingly common singles-only collection sees the card it always saw. It rides on the existing `groupBy` as one more `by` column — a format breakdown is a regrouping of the copies already read, never a second query.

- A **checklist** (#531; ADR-0031) is the collecting goal, as against `Issue`, which is the publication event — a named list of stamps that counts as one complete unit, and an issue may carry several (basic beside specialized, perforated beside imperforate, tabbed beside plain). It replaces `IssueMember.requiredForCompleteness`, one boolean that gave an issue exactly one set; the migration turned every issue with a required member into one checklist named after it and dropped the column, so **there is no required flag to consult** — membership of a `ChecklistStamp` row *is* required-ness, and an optional extra is an `IssueMember` on no checklist. `Checklist.issueId` is nullable on `StampFormatFactor`'s idiom (null spans issues), but only the issue-scoped editor exists (`useChecklistsAction`, on the issue's row, ADR-0020 §7). `sortOrder` is load-bearing: the **first** checklist is what a single-checklist row shows and what a new stamp joins by default. Every derived fact names its subject explicitly — **per checklist** for the completeness grid and the catalog-price total (a union would count a shared stamp once, for a figure answering neither question), the **union** for `requiredCount`, the declared range (#333) and the issue gallery (#137), **one named checklist** for the intake fan-out, auction lot composition and the picker's *whole set* buttons. The issue row collapses several to a `3 checklists` badge with the detail in its tooltip (#425's counting rule); the issue's detail page is where each gets its own completeness and value card. That badge stays an **indicator** — narrowing is a `MultiSelectFilter` above the row's *expanded* tree and in the detail page's Stamps card header, never in the collapsed chip line (a toolbar-sized control per row outweighs it), held in local state because a per-issue filter has no single URL parameter on a list of many issues. `filterStampTreeByChecklists` (`src/lib/stamp-tree-filter.ts`, pure) drops non-members but **keeps a node with a surviving descendant**, returning it in `contextIds` to be dimmed: a variant is read through its ancestors, and `309AP` without its `309` is a number nobody can place. That ancestor rule is now `filterStampTree`, one predicate-shaped walk the checklist filter and #631's match narrowing both go through, since both are the same question about a tree. The filter is on all three tree surfaces — issue row, issue detail, stamp picker — and `contextIds` is now the **only** thing any of them fades: #631 turned the picker's non-matches from faded to hidden, so the one dimmed state left means *kept for a descendant* and nothing else. **`Checklist.name` has no unique constraint and nothing resolves a checklist by it** — names repeat freely across issues and never meet, since every read is scoped by `issueId`; a repeat *within* one issue gets #178's advisory ⚠, checked client-side against the already-loaded list. **Completeness reads the variant tree, not the membership literally** (#661): a copy filed under a child whose effective `actsAsVariant` is true satisfies the listed stamp, at any depth (#239) and stopping at the first distinct entry — ADR-0010 §3's rule as the unknown-variant valuation (#101/#130) and the headline-price rollup (#238) already read it, and what #130 said completeness would do before the readers were left counting `stampId` literally. `checklist-variant-rollup.ts` is the I/O half — two queries per screen (`buildDescendantMap`, then the variant flags and parent edges along it), widening the counting set to those children and attributing each row back — and `satisfiedMember` in `checklist-completeness-rules.ts` is the rule. Attribution is **per checklist, nearest member first**, and both halves of that are load-bearing: one map over the union could not let a `226yw` copy answer the basic list as `226` and the specialized one as itself, and a checklist naming both would otherwise let one piece of paper fill two of its slots. All three readers go through it — the issue's grid, the Copies list group header (#594) and the lot's for-sale header (#563) — and so does `wantGapForStamps` (#548), because *add what is missing* sits on the completeness card and a gap that read `stampId` literally would want a stamp the fraction above it had just called held. That is also why `createWantsForIssue` now takes its gap **per checklist and unions the results** rather than over the merged membership: attribution is a question about one membership, and the union would answer it for the specialized list and leave the basic list's umbrella looking missing. Unioning the gaps keeps the shared stamp wanted once.

- A **want** (#532; ADR-0032) is what the collection is *looking for*, and it is deliberately **not** a fourth disposition: `inCollection`/`forSale`/`forTrade` live on a copy, an `Item` is one physical copy (ADR-0007), and a wanted stamp has no copy — a `wanted` flag would force phantom rows and poison every count that reads inventory. A want carries an **acceptance set per axis, where zero rows means "any"**: `WantCondition` (plain composite key — `Item.conditionId` is required, so there is no "none" value), `WantCertificateStatus` and `WantFormat` (**nullable** FK, because a null there *is* a value — "no certificate" per ADR-0006 §2, and "single" per `StampFormat` — with `UNIQUE … NULLS NOT DISTINCT` as `stamp_catalog_price_unique` has it). **"At least X" is inexpressible on purpose**: `StampCondition.sortOrder` is display order, `U` and `MNG` are cancellation and gum rather than two points on one scale, and `CTO`/`FDC` are on no scale at all, so any minimum-quality rule would invent an ordering the dictionary does not guarantee. Upgrades then need no concept of their own — a used copy held against a mint-only acceptance set simply does not satisfy the want. `closedAt` is `Item.disposedAt`'s idiom (null = open, one column, so every filter stays a plain `where`). There is deliberately **no price on a want** — built, then dropped by `20260811140000_want_drop_max_price` before it meant anything: a want has no date, so a figure on it is a price opinion frozen the day it was typed and never corrected (ADR-0029 §2's objection to a *configured* ratio, once per row), and the whole-series add makes it unworkable outright — one field over twelve stamps worth wildly different amounts, where copying stamps one ceiling onto all of them, splitting by catalogue invents limits nobody stated *and* freezes them at today's catalogue, and splitting evenly prices a key value like a common one. What a stamp is worth **at the moment of buying** is the recommendation engine's answer from recorded results (ADR-0022/ADR-0029), against the copy in hand; two mechanisms for one question is how they drift. `priority` is what survives of "how much do I care", and it needs no maintenance to stay true. What a copy satisfies is the pure `wantMatchesCopy` (`src/lib/want-rules.ts`), shared so the intake review, the list and any later consumer (#253/#250, trade) cannot disagree; storage and reads are `src/lib/wants.ts`. The **review belongs to the moment a copy reaches the collector's hands** — the transition into `delivered` — not to the moment its row was written (#532). One rule covers every route in: a hand-added copy starts delivered and is reviewed at once; intake creates `ordered` (or `to_sort` on an already-arrived order) and raises nothing, so `intakeStampsAction` deliberately returns no `copies`; `bulkUpdateLotItems`/`Scoped` return the copies their change *moved into* delivered (candidates read **before** the write, since afterwards a copy that just arrived is indistinguishable from one that was already here), and `updateItem` returns `becameDelivered`. That is also what closes the auction-settlement gap without a second review being bolted onto it: a parcel won, settled into a purchase and sorted converges on the very transition every other route does. Both intake paths raise the **review** — `intakeStamps` now returns the copies it created rather than a count, and `createItemAction` returns the one it made — and the review offers **close / narrow / leave open** per want. **Nothing closes automatically**: that would discard a record of intent, and narrowing (the common case) is a judgement the app cannot make. What it may do is *seed* — `narrowConditionSeed` ticks every condition except the one that arrived, from the dictionary's membership and never its order, and only when the set was empty, since a set already narrowed is an answer the collector gave once. Completeness targets are a **generator, not a source** (`createWantsForMissing`): explicit rows once, wide open (a gap carries no acceptance criteria), skipping stamps with a held copy or an **open** want — a *closed* one is not a reason to skip, the gap being real again — which is what makes pressing the button twice a no-op. The add form takes **one stamp or a whole checklist** (`WantCreateInput`): `StampSelect` gained an opt-in `checklist` prop that turns on the browser's per-checklist *whole set* buttons (the copy form does not pass it — one copy is one copy), and the fan-out writes one want **per stamp** sharing the form's acceptance, priority and note, since a set-shaped want could never be half met. It skips a stamp with an **open** want and reports the count, but deliberately **not** one merely held — that is the gap generator's rule, and wanting a better copy of something held is the ordinary case. `priority` is stored as its **rank** (`Int`, 0 = high, 1 = normal, 2 = low), not as the word: the list is ordered by it and paged on the server, and the only order Postgres can put a `text` column in is its spelling — `high < low < normal`, which nobody means. `want-rules.ts` owns the vocabulary and the word is what crosses the wire, the form and the filter; one column, not a word plus a rank that must agree with it. The list row leads with the stamp's catalog photos (#137) and the screen carries the shared `ListFilterSidebar`, but the list itself is **cursor-scrolled, not fetched whole**: `listWantsPaginated` + `listWantYearFacets` share one `buildWantListWhere`, so a facet cannot count a row the page would not show, and the year is dropped only for the facets (each count says what *that* year would leave). This is deliberately not Contacts' whole-list-and-filter-locally shape — an address book is a few hundred rows, a want list is a collecting plan's shopping list and runs to thousands. The condition filter ORs in `conditions: { none: {} }`, since an empty acceptance set means "any" and such a want really would take the condition asked about. Order is `closedAt` nulls-first → `priority` → `createdAt desc` → `id`, the last being what makes an offset page stable over ties. Area and year ride in `useCollectionFilterStore`, not the URL (#143), on the stamp picker's reasoning. The row shows a **catalogue range**, not a price: a want accepts a *set* of (condition, certificate, format) combinations and each has its own value, so one number would be one combination picked out of the set answering a narrower question than the row asks (`wantCatalogRange`, pure, in `want-valuation.ts`). Each combination goes through **`valuateCopy`** — the function that prices a physical copy — so a want's figure and the copy that eventually satisfies it cannot drift; min/max in the **base currency only**, since two currencies are not a range; an unpriced or unconvertible combination is **counted, never zeroed** (a catalogue gap would drag every range to nothing) and the row reports `priced / accepted`; `estimated` is inferred from **no recorded row for the format**, not from a factor existing, because a format can be priced explicitly *and* carry one. One pricing pass **per page** — the page's stamps' prices plus the per-collection preamble the stamps list already loads — and only in `listWantsPaginated`, the intake review and the form drawing none. The row promotes **Open stamp page** (the shared `useDetailPageAction`, first in the menu as everywhere) and **Edit** to hover quick actions through `pickRowActions`, so a shortcut and its menu entry cannot drift; the stamp screen returns the favour with a read-only **Wants** card (`related-wants-card.tsx`, off a `stampId` filter) leading its right column, showing closed wants faded — noise on a list, but on one stamp the record that it was looked for and found — and **rendering nothing at all when the stamp is on no want**, loading included so it never flashes an empty state: Copies and Offers are about every stamp and print "none yet" as a real answer, while wanting one is the exception, and a card saying "you are not looking for this" on every catalogue page is furniture. Priority is a chip beside the acceptance chips, in three deliberately **different** tokens (warning / info / muted): a scale whose middle and bottom look alike is one you read the word off, and then the colour is decoration. **Flat is the shape and issue grouping is a view of it** (`listWantIssueGroups`, a remembered *By issue* toggle): a want's subject is a stamp and its acceptance sets are per stamp — within one series the key value is wanted MNH with a certificate and the rest "anything" — so an issue heading over those rows overstates, the dominant reading is matching a stamp in hand against one searchable row, and an issue-shaped spine would be a second answer to the completeness grid ADR-0031 already gives from copies *held*, re-coupling exactly what §6 separated. Grouped server-side on #424's reasoning (offset paging would split a group across a page boundary and report two half-counts), counted on the stamp's **first** issue membership and read back through an `issueId` filter matching **any** — #172's pair, not a third rule — with `NO_ISSUE` for stamps in none. The row reads `open / total`, both counted with every filter **except** status, since a denominator that moved with the Open/Closed toggle would be a fraction of nothing; which groups *appear* still obeys status, and because status narrows on `closedAt` alone that falls out of the two counts with no second query. The catalogue lists carry the want back the other way (#532): `loadStampWantSummaries` denormalizes each stamp's **open** wants onto `StampListItem.wants` and `StampNodeData.wants` — scoped to the page's ids, `loadStampCopyCounts`' call — and `WantChip` draws them, absent when there are none (a marker on a few rows is a signal; one on every row reading `0` is a column) and coloured by the *loudest* of the wants behind it. The detail is a **click popover, not a tooltip**: a dozen wants × three axes flattened into prose was unreadable, and a popover draws them as the want list draws them. Because the summary is *copied onto two other read models*, `useAddWantAction` invalidates the stamps and issues caches as well as the wants one — refreshing only its own list left the chip missing until a reload. The chip is built on the shared `STAMP_SECONDARY_CHIP` base so it sits on the line its neighbours do, and **always draws its count, one included** — an icon alone gives the chip no text to set its line box from and it came out shorter than every chip beside it. It is on **auction lot lines** too, where it answers the sharper question: a line names a concrete `(condition, certificate, format)`, so it passes a `copy` and the chip runs **`wantMatchesCopy`** — the intake review's own predicate, so a lot marked as matching and the review that greets that copy on arrival cannot disagree. A match is drawn as a **ring**, not another colour: colour is already spoken for by priority, and two meanings on it leave neither readable. That is what `StampWantSummaryEntry.acceptance` is for — the words are for reading, the ids for deciding, both off one row. The marker rides on **copies** the same way: loaded in `enrichItemRows`, the one funnel every copies view goes through (Copies list, a purchase order's intake, the lot and group readers), so no surface loads it separately — and on `CopyGroupRow`, where a group being one stamp at one condition means the answer covers every copy in it. On a held copy the ring reads as the **upgrade** signal, holding one never having closed a want. What the collection already has of a wanted stamp is a **split, not a count** (`WantCopyCounts`: held / ordered / inTransit, `to_sort` folded into held since the copy is on the desk either way) and it rides on both `WantListItem.copies` and `StampWantSummary.copies`, so the chip's popover carries it too. One figure hid the case that matters: a want stays open until the collector closes it — correct, the stamp is not here — but an *ordered* copy then looked exactly like no copy, so the same stamp at the next auction read as an untouched gap and the want urged a second bid. Held and on-its-way are different answers to "should I be bidding on this". Deliberately **derived, never stored**, and it closes nothing: no third state on the want, and ADR-0032 §7 stands. The buckets are held / **toSort** / ordered / inTransit — `to_sort` stands apart from held, an arrived-but-unsorted copy being a different answer to "have I got this" than a filed one — and the figures **leave out the copy they are drawn on** (`loadItemWantSummaries`, keyed per copy rather than per stamp so two copies of one stamp on a page each omit a different one): a purchase-order row otherwise reported *one in transit* about itself, and a count meant to say "something else is coming" must not be satisfied by the row you are reading. It is counted **twice, and the two must never be drawn as one**: per *stamp* (`WantListItem.copies`, `StampWantSummary.copies`) is the upgrade context — everything held whichever want it answers — while per *want* (`WantListItem.matchingCopies`, `StampWantSummaryEntry.copies`, filtered by `wantMatchesCopy`) is the **only** figure allowed to claim something is on its way. A used copy in the post satisfies a want for "anything" and a mint-only want not at all, so one line above a list of wants tells the collector to stop bidding on the mint copy they were right to chase. Both tallies come off **one** `loadCountedCopies` read, so they cannot be taken over different sets. Named acceptance profiles are #533 and deliberately not folded in.

- A **named acceptance profile** (#533; ADR-0032 §9) **seeds**, it is never referenced. `AcceptanceProfile` + three member tables carry exactly the axes a want carries (nullable members and `NULLS NOT DISTINCT` included), and applying one *copies* the sets onto the want — hence there is deliberately **no `profileId` on `Want`**, and that absence *is* the decision, which a schema cannot state and ADR-0032 §9 therefore does. `CollageTemplate`'s shape (#308), and the precedent is the reason: a reference would make editing a profile a silent rewrite of what every existing want accepts, closed ones included, whose acceptance is a record of a decision already taken rather than a setting. So a delete needs no in-use check and an edit needs no warning; the cost — changing a profile *and* the wants carrying its terms is two acts — is answered by a bulk edit over a **chosen** set of wants if it ever proves tedious, deliberately unbuilt. `validateAcceptance` and the `AcceptanceInput` shape live in `src/lib/acceptance.ts`, shared by `wants.ts` and `acceptance-profiles.ts` so the two cannot disagree about what "no certificate" means. The picker is inside the shared acceptance editor (`want-acceptance-fields.tsx`), so the want form and the intake review's narrow step get it from one place and the Settings editor that *defines* profiles turns it off (`profiles={false}`); which profile it shows is **derived** by comparing the sets (`acceptanceSetsEqual`, pure, in `want-rules.ts`) rather than stored — a seed leaves nothing to read, and editing one box drops it to *Custom*, the terms no longer being that profile's. The profile a want was **saved** on leads the next add (`LS_LAST_ACCEPTANCE_PROFILE`, per collection, `readRememberedProfile`/`rememberProfileFor`), the last subtype's (#342) and last condition's (#121) idiom — wants are entered in runs and a run is one set of terms. Saved rather than *picked* (a profile cancelled is not what was gone with), **derived on submit** rather than tracked as a selection (the form has no other notion of "the current profile", and a second one would be a thing to keep in step), **cleared** when the terms match no profile (an off-profile want says the run moved on, and the stale id would seed the next want with terms just chosen against), and read on **add** alone — an edit shows the want's own terms and the intake review's narrow step has ADR-0032 §7's own seed to keep. Applied during **render**, the settings panels' "adjust state when something arrives" pattern rather than an effect, and once, flagged rather than conditioned on the sets being empty so a background refetch cannot re-seed boxes deliberately cleared. **One memory, both doors** (#695): the Issue list's bulk *add missing* dialog reads and writes the very same key on the very same rules, having previously kept none at all — a run of wants is one evening on one set of terms whichever dialog it is entered through, and two stores over one question would each answer it with the other's last run missing. That dialog also gained **Priority**, in the shared editor's `extra` cell beside the three axes exactly as the want form has it, applied to every want the run writes and carried to `createWantsForIssue` (`normal` by default, which is the column's default and what the completeness card's own button — a plain button that asks nobody anything — keeps writing). The chips are `want-priority-choice.tsx`, lifted out of the want form rather than copied: what made the bulk dialog lack the field at all was that asking one question at two scales had two implementations.

- A stamp's **catalog prefix** is resolved from *three* levels since #675, not two (#66/#377/#675), and the resolution is one walk. The **issue's** override comes first (`IssueCatalogPrefix`, one row per issue × vendor, `areaPrefix` NOT NULL — an issue has one level above it, so "inherit" is the absence of a row, which is what the dialog's blank field stores). Failing that, walk up the area tree and stop at the **first area that states a prefix** — a `CollectionAreaVendor` row for this vendor, or the area's own `CollectionArea.catalogPrefix`, which answers for *every* vendor — with the vendor row winning inside that one area. It is `StampFormatFactor`'s rule (ADR-0040, beside ADR-0020): **where outranks for which**. Worked example: Poland sets `catalogPrefix = PL` and a Fischer row with no prefix; child GG sets `catalogPrefix = GG` and says nothing about Fischer; Fischer under GG is **`GG`** — the nearer area decided, and repeating the Fischer exception on GG is how you keep it. `CollectionAreaVendor.areaPrefix` therefore carries **three** states and the difference between two of them is what makes the area level usable at all: `''` is the stated *no prefix here* and stops the walk, NULL is the ordinary tick — the vendor is recorded here and the prefix inherits — and anything else is that prefix. Merging those two is what would make ticking Mi, Sg, Yt and Fi on a `PL` area write four rows that each kill `PL`, which is the typing #675 exists to remove; `20260822130000_area_vendor_prefix_inherit_vs_none` rewrote every pre-#675 NULL to `''`, since a row was the only prefix level then and the resolver stopped at any row it found. The prefix is the **catalog identity**, deliberately not a display layer: it decides the rendered chip, the stamp picker's match keys, generated listing texts, derived offer-set and auction-lot names, duplicate detection (#85) and the Colnect strict full-key match (#155) alike — a stamp reading `Mi·SP 1` while the duplicate checker still thinks `Mi·PL 1` is the bug this rules out. One resolution serves everything: `effectivePrefixFor` (`area-prefix.ts`) server-side, its client mirror `resolveAreaVendorPrefix` (`area-vendor.ts`) — the two are held to identical answers by one shared case table (`tests/fixtures/area-prefix-cases.ts`), because they are the same rule written twice — and the pure `buildAreaVendorMaps(areas, prefixByIssue)` → **`vendorMapFor(areaId, issueId)`** everywhere a row renders a number, never `vendorMapByArea.get(areaId)`, which answers only half the question. The override map is loaded **whole, once per read** (`issue-prefix.ts`; client `issues/catalog-prefixes`, keyed under `["issues", collectionId]` so existing issue invalidations cover it): the table is sparse by construction and a screen needs it before drawing its first chip. `duplicate-catalog.ts`'s `CatalogPrefixContext` additionally takes prefixes *typed into a form but not saved* — the issue create dialog checks numbers against an issue that does not exist yet, so the form is the only place its prefixes can come from. The prefix input sits **in front of** the First/Last range in the issue dialog, where it renders, with the area's prefix as its placeholder.

- **Numbering vendors and price books are two declarations on an area, not one list** (#675; ADR-0040). `CollectionAreaVendor` says whose numbers this area's stamps carry and `CollectionAreaCatalog` says which volumes price it; the schema always had them apart, but one dialog keyed by *book* wrote both, deriving the vendor rows at save time with "non-null prefix wins, else last wins" — so two Michel volumes rendered two prefix boxes backed by one stored value and silently discarded one of them, and a vendor could not exist without a book at all. Both lists are now written explicitly (`syncAreaVendors` / `syncAreaCatalogBooks`), a vendor may be recorded with **no** book, and the area dialog is two sections: *Numbering* (the area prefix, one row per vendor with an optional override and a "none" mark, one marked leading) and *Price sources* (the books, one marked as the valuing volume). The **primary splits with them**: `CollectionArea.primaryCatalogVendorId` leads numbering — the catalog sort key (#181), the leading label, the primary chip — and `primaryCatalogNameId` keeps only its valuation job (`item-valuation.ts`). That split is also why `updateCollectionArea` gates the subtree sort-key recompute on the **vendor** changing: swapping which Michel volume prices an area moves nothing about how its stamps sort. Price books **inherit** down the tree through one resolution, `buildEffectiveAreaCatalogMap` — nearest ancestor that attaches any, the whole list at a time — which the trade's agreed catalog (#638), the variant price grid and the stamp catalog-prices tab all read; before #675 only the first of those walked the tree, which is why the same books had to be re-attached at every leaf area.

- A catalog number sorts in **families**, not as one sequence (ADR-0014). The denormalized `primaryCatalogSortKey` on `issue`/`stamp` is a **text** key — `<prefix><10-digit zero-padded number><suffix>`, lowercase, so `"200"` is `0000000200`, `"200a"` is `0000000200a` and `"P15"` is `p0000000015` — stored `COLLATE "C"` so the database's byte order and JS `<` are the same order, the key being compared in both. It was an integer of the *leading* digits, which is why every family Michel writes with a letter prefix (`P` Porto, `Bl` blocks, `D` Dienst, `W`/`S`/`Zd`) parsed to `NULL` and fell into the number-less bucket at the end of every list, ordered by name — `P15` above `P1—14` on the Issues list, the report that prompted the reshape. ASCII putting digits before letters is what makes the basic numbering sort first and each prefix follow as its own block; the suffix rides along, so `200` now precedes `200a` instead of tying and falling through to the name. A number carrying **no digits at all** (a bare Roman `IIIA`, #383's scheme) still has no key and still sorts last — Roman numerals do not order alphabetically, and inventing an order for them here would be a guess. A second column (family beside number) was rejected: the key is threaded through a dozen `ORDER BY`s, selects and in-memory comparators, and two columns is two chances to order by half the key. Every in-memory ordering goes through `compareCatalogSortKeys`; nothing subtracts keys any more.

- A stamp's **subtype** (ADR-0010 §6; #338–#340, #342) is shown wherever stamps are listed or picked — issue tree, flat stamp list, Copies list, pickers — through the shared `SubtypeChip`, and is available in listing texts as `{subtype}`. The collection's **default** subtype renders **nothing**, on both surfaces: it is the row assigned automatically to every new child, so it carries no information the tree did not already give, and badging every variant "Variant" scales noise with the collection. Which subtype is default is already the collector's choice, so that *is* the setting. Read models report the subtype as stored (`subtypeLabel` → `{ name, isDefault }`) and the surface drops the default — except `toTitleCopy`, which drops it *before* resolving the translation so the default never surfaces as a translation gap to fill (#299). The name is user-visible listing text, hence translatable like any other (`StampSubtypeTranslation`, one `name` column — a subtype has no abbreviation). The last subtype saved is remembered per collection (`LS_LAST_SUBTYPE`) and pre-fills the next add, alongside #234's copy defaults.
- A stamp's **attributes** (#71, resolved; #72) are **six typed columns on `Stamp`**, never an entity-attribute-value framework: every surface an attribute must reach — list columns, server-side filters, listing tokens, entity translations, the agent API registry, the Colnect matcher, the CSV import — is typed, and a generic EAV would buy six adapters for flexibility nobody asked for. `denomination` and `perforation` are **strings as printed** (`10 gr`, `1 zł`; `11½`, `11½:12`, `imperf`): facts about *one* stamp, printed rather than named, never translated, so a dictionary of either would hold a row per stamp — and a face value is not tradeable money, so it is not an amount plus a currency (the exchange-rate machinery has nothing to say about `10 groszy, 1920`; parse a numeric part out later if something needs to sort by it, the way `primaryCatalogSortKey` parses a catalog number). `colorId` / `watermarkId` / `paperId` / `printingId` reference four dictionaries — `StampColor`, `StampWatermark`, `StampPaper`, `StampPrinting` — shaped on `StampSubtype` with **no `isDefault`** (there is no "usual colour"; a stamp that states none has none, so nothing is seeded and nothing was backfilled) and `onDelete: Restrict` like every dictionary. One module, `src/lib/stamp-attributes.ts`, serves all four by dispatching over `StampAttributeKind` (`stamp-attribute-kinds.ts`, pure, also the labels the one **Attributes** Settings tab and its actions read); a fifth dictionary is a new kind and a new store entry, not a new module. Attributes belong to the **stamp node, never the copy** — the measuring tools (#598, #614, #625) deliberately store nothing because a reading is evidence for picking the variant, not a field on the copy — and **nothing is inherited** down the variant tree: a child states its own value or none (ADR-0010; no third state to model). What earns a column is that something in the app *reads* it — listing texts read denomination and colour (#738), the measuring tools compare perforation and watermark (#740); size, designer, printer, print run and gum type wait until something does. Tags (#152) are a different thing: a label the collector invents, not a fact the catalogue states. The demo dataset (`src/lib/demo/seed-attributes.ts`) derives denomination and colour from the stamp names it already had and the rest from area and period rules, so #736–#740 have values to show. The four dictionaries gained one Colnect-facing column since: `colnectValue` (#739), what Colnect prints for that row, unique per collection — see `extension.md` for why the mapping is a column rather than a `ColnectConditionMapping`-shaped table.
- **Entering and showing the attributes** (#736, #737) puts them on one path through the app, and the shape of that path is what the two issues decided. The stamp form fetches a stamp's stored values **by stampId** (`getStampAttributeValuesAction`), the way the subtype assignment, the translations and the photos already do — nine callers build `StampFormData` from nine different row types, and making each carry six more fields to edit one stamp is exactly what that pattern exists to avoid; the section is gated on the fetch so a save made before it lands cannot submit blank fields over stored values. A **dictionary select renders only once its dictionary has rows**, the subtype block's own rule, because nothing is seeded and a select offering only `—` is furniture. On the write side an attribute key absent from the input leaves the stored value untouched and a blank clears it (`pickStampAttributeWrites`, the rule `colnectId` already follows), which is what lets a form that renders three of the six save without blanking the other three. Order and field labels live once, in the pure `stamp-attribute-kinds.ts` (`STAMP_ATTRIBUTE_FIELDS`), so the form, the detail card and the list line cannot disagree. The detail page gets **its own Attributes card**, omitted when the stamp states none (#536) and listing all six once it is there — six em dashes on every stamp would push what the page does say down the column. On a list the six are **one muted line under the chip line** (`StampAttributesLine`, shared by the flat row and the tree node), never four columns — #737 rules columns out for the tree and both rows' chip lines are already full — and a stamp that states none draws nothing. Filtering is the **four dictionaries only**, as `colorIds`/`watermarkIds`/`paperIds`/`printingIds`: URL-backed multi-selects, empty meaning *every value* and never *states none*, combining with AND across dictionaries, hidden while a dictionary is empty, and counted into the **year facets** because they are filters rather than display axes like the condition and format switchers. Denomination and perforation join the list's existing search `OR` instead (#71 §6): free text with no vocabulary to tick.

- **The six in listing texts** (#738) are six ordinary per-copy tokens — `{denomination}`, `{perforation}`, `{color}`, `{watermark}`, `{paper}`, `{printing}` — and the decision behind them is that they are *nothing special*: each resolves through `distinct` and joins with ` / ` across a mixed offer, each renders empty on the stamps that state nothing (which is most of them), and the tidy pass #345 already needed for a single's absent `{format}` is what carries the orphaned separator away. What did change is the translation surface: the four dictionaries join `TranslatableEntity`, so `{color}` resolves in the platform's listing language exactly as `{subtype}` does and an untranslated row is **reported as a gap** in the title preview and fillable from the offer dialog (#298/#299) rather than silently printed in the default language. `entity-translations.ts` reaches those four rows through `stampAttributeTranslationStore(kind)` — the delegates `stamp-attributes.ts` already owns, narrowed to three calls — rather than four more copies of its per-entity block, so a fifth dictionary stays one entry in one table; `current` comes back empty for them because a one-column entity has no siblings for the write to preserve. `{denomination}` and `{perforation}` are deliberately **not** translatable and never flag: they are printed as printed, and no language rewrites `11½`. There is no default row to suppress the way `{subtype}` suppresses the collection's default — a stamp that states no colour has a null relation, which is the unmarked case (ADR-0020's rule, arrived at again from the other side).

- Quick-adding a catalog value is one shared dialog (`shared/quick-price-dialog.tsx`) over a `QuickPriceSubject` — a **stamp × condition × certificate**, not a copy. The Copies list, PO intake and sale-lot views pass an `ItemListItem` (it satisfies the shape structurally, a copy carrying its own condition); the Issue list builds one from a stamp-tree node plus the list's **display condition** with certificate = none, matching what the price column renders (#341). `useQuickPriceDialog` returns `{ open, dialog }` and owns the save. The trigger is a **+ catalog value** link in the row's price slot — never a `⋮` entry: pricing belongs where the price is, so every list opens it the same way (#228, #341).
  - **It prices the single, wherever it is opened from, and there is no parameter for anything else.** A figure typed into it is read off a paper catalogue and a catalogue quotes singles; a multiple's value is that figure times the resolved `StampFormatFactor`, which is precisely how `pickFormatCatalogPrice` values a copy in a format with no explicit row. So `quickSetCatalogPrices` takes no `formatId` and always writes `formatId: null`, and `getQuickCatalogPriceContext` reads and prefills from that same row. Writing the *shown* format's row instead — which the Issue list, the auction lines and `useQuickPriceDialog` used to do, while the Copies list and the PO screen did not — did two wrong things at once: filed a single's quotation as the multiple's own price, and suppressed the factor for that stamp for good, from a dialog whose collector asked for neither. An explicit format price is a deliberate act and belongs on the stamp's **Prices** tab, the one screen showing the grid it deviates from.
  - The format the caller is showing survives as **`displayFormatId`, context and never a target**: `QuickCatalogPriceContext.displayFormat` carries its abbreviation and the factor resolved for this stamp × condition, and each `QuickCatalogTarget` carries `formatAmount`, any explicit price already on file for it. From those the dialog draws one read-only line per catalogue — `4-blk: × 2.2 = 27.50 EUR`, recomputed as the collector types — so the number they are checking against the copy in their hand is on screen without the dialog pretending to write it. Two other answers matter as much: an explicit row already on file is **named** (nothing typed here moves it), and *no factor at all* is **said** (that copy stays unpriced however carefully the single is filled in, which is worth knowing before the dialog closes on a job that looks done). The condition badge names condition × certificate only — a badge reading `MNH · 4-blk` over an input that files the single's price is the exact misreading #343's badge was added to prevent.

- The **picker browser is the issues list, paged** (#604). It used to load every in-scope issue whole — `listAllIssues`, the full `ISSUE_SELECT` with each issue's members, their numbers, photos and checklists, plus copy counts and wants over the lot — and then filter the year and the search text *in the browser*. That is a whole collection in one payload at "All areas", growing with the collection while nothing narrows it, so it now rides on the list's own machinery: `useIssuesInfinite` over `/api/collections/[collectionId]/issues` (50 a page, cursor), `useIssueYears` for the year panel, `InfiniteScrollSentinel` at the foot, and area / year / search resolved **server-side** — `parseCatalogSearch` included, so a prefixed number reaches the same rows here as on the list (#146/#289). A row's tree is `useIssueMembers` on expand, the list's rule; the header draws from `IssueListItem`, which already carries the gallery (#137), the checklist badge's counts and its price totals, so the picker gained the totals and the members' headline prices simply by reading the row the list reads. The search box **lifts to the popup** rather than living on the list, because it narrows the year facets too and both are server reads now. What could not survive the move unchanged is #186: the server says *which issues* matched, not *which stamps inside them*, so the row derives it — `needsInnerStampMatch` asks whether the row's own name, year, `issueNo` or declared range accounts for the hit, and only where it does not does the row read its members while still collapsed and match them with `matchedStampsInIssue` (both since extracted to `src/lib/issue-stamp-match.ts` and shared with the list, #631). That kept the auto-expand and the dimming exactly as they were — the dimming has since become hiding (#631) — and confines the extra read to the case that needs it: an issue matched by its own number never fetches, and a broad search that opens many rows at once is the accepted cost of keeping the behaviour (the alternative, deciding it on the server, would put a stamp-level answer on a list-level read model that nothing else wants). A row measures itself against the **debounced** text the page was fetched with, never the box's live value, or it would narrow itself on a query the server has not answered yet.

- A picked stamp is carried as `PickedStamp` (`inventory/stamp-picker-shared.ts`) with `catalogLabels` — **prefix-formatted** numbers (`Mi·PL 1B`), one chip each in the summary — never a joined string of raw numbers (#357): three catalogs' numbers side by side read as "1B, 39, 1" and name none of them. Build them with `orderedCatalogLabels` (primary vendor first) at every site, including the edit-mode prefill, which must resolve the vendor map from the **copy's own area**.

- A **child stamp inherits the parent node's year**, not the issue's (#360) — a variant or reprint is dated from the node it hangs under. `StampFormDialog` skips the issue-members query when a parent is prefilled, so the caller passes `prefilledParentIssuedYear`; the Year input is uncontrolled and keyed on the derived default so re-seeding actually reaches the DOM. Root-level stamps still start from the issue year (#70). Either way that is a *starting* value and the collector's to correct — which is what makes Colnect worth asking: matching a stamp fills the month and day from the catalogue page's own "Issued on" where our date has none, and reports rather than corrects a component the two sides state differently (#655; the rule and its reasoning live in `extension.md`, the pure decision in `src/lib/colnect-date.ts`). A child hangs under a node at **any** depth, in the picker as on the Issues list (#401): `SelectableStampNode` gated `+ variant` — and, surviving #239, the *unknown variant* marker — on `depth === 0`, which no rule anywhere backs (the tree is `Issue → X → Xa → Xay → XayI` by design, #54; the server has always accepted any `parentStampId`). Depth is for indentation and nothing else.

- The issue-list stamp tree **opens a parent that just gained a child** (#359). Expansion is derived, never a `setState` in an effect: the panel raises an `ExpandStampSignal` (`{ stampId, nonce }`) and each node compares it against the toggle the collector last made — so a manual collapse sticks, while a *repeat* add under the same parent carries a fresh nonce and opens it again.

- A catalog's numbers on the two dialogs that *generate* stamps are one **spec** field (#452), not a First/Last pair: `parseCatalogNumberSpec` (`src/lib/catalog-number.ts`) splits a comma-separated list and hands each piece to `resolveCatalogRange`, so every scheme #149/#150/#383 added keeps working *inside* a segment. The point is the case one range cannot state — `2895A-2897A, 2895B-2897B`, one series printed in two variants. The **declared series range is derived, not typed**: suffixes dropped, prefix kept, min to max of the bases, so that spec declares `2895–2897` while creating all six stamps. A spec may mix numbering families — `3025-3027, BL48` is a run plus the issue's block — so the declared range is measured over the **basic (prefix-less) numbering** whenever the spec has any, `computeIssueRangeExtension`'s own ranking, and over the first segment's family otherwise; a foreign-family segment still creates its stamp, it just does not widen the range. No number may repeat. **Edit issue keeps First/Last** — there the pair *is* the declared range and nothing is generated — so `parseCatalogNumbers` lives on beside `parseCatalogNumberSpecs` in `src/app/actions/issues.ts`.

- A **catalog CSV is a second door onto that same spec** (#716–#718: rules → writes → dialog, one design). One row is one issue — a year, a name, and a numbers cell in exactly `parseCatalogNumberSpec`'s syntax, so `2895A-2897A, 2895B-2897B` means here what it means in the create dialog and the stamps an import creates are the stamps that dialog would have created; a second dialect is how the two would drift. `src/lib/catalog-import-rules.ts` is the pure half — `readCatalogImportFile` for the columns, `planCatalogImport` for the per-row verdicts — and it is a module of its own rather than a query inside either consumer because the **preview and the commit must be the same answer computed once**, a screen that promised what the writer then did differently being the failure the whole track is shaped to avoid. Three things the file deliberately does **not** carry: the **area** (one is chosen per import, a file per country, which keeps the format trivial and invents no area-matching scheme), the **vendor** (the area's `primaryCatalogVendorId`, so there is one numbering column and no vendor question) and the **prefix** (the ordinary three-level walk, #675, which is I/O and therefore the caller's). There is **no header contract** — the collector maps the columns in the dialog — which is the one thing that separates this reader from the Colnect (#645) and Delcampe (#611) ones: those read somebody else's export, whose column names are a published fact, while this reads a file the collector typed. The **first record is the header**, flatly, rather than sniffed: a rule deciding whether a row *looks* like data has no honest answer for a catalogue whose first issue is called `1918`. The delimiter *is* sniffed (`,`, `;`, tab — a Polish Excel writes `;`) on the first **record** and not the first line, since `parseCsvRecords` drops blank ones and a file opening with an empty line would otherwise have its delimiter judged off the wrong line. Only the numbers column is required; a file with no name or year column is an ordinary catalogue listing, and an unmapped column is `null` rather than an out-of-range index so *the collector did not answer* and *the collector pointed at column 4* stay different states. A row is **new-issue**, **fill-existing** (its numbers overlap exactly one issue: append the missing numbers, fill an *empty* name or year and never overwrite a filled one, `noChange` where it would do neither) or **error**, and errors are skipped at commit rather than blocking the file. Existing detection is **catalog identity** (#85) — vendor + effective prefix + number — so `Mi·SP 1` never answers for `Mi·PL 1`; a number held by a stamp on **no** issue is an error rather than a gap, there being nothing to fill and a creation there duplicating an identity. Classification runs **in order and against the earlier rows of the same file**, so two rows generating one number do not both plan to create it and the *second* is the one refused — which is what makes the plan executable exactly as written, the commit walking it top to bottom with nothing left to re-decide. The dialog's ≤50 auto-create cap (`AUTO_CREATE_MAX_STAMPS`) deliberately does **not** apply — it exists because a long positional run is a poor idea in a dialog where every stamp is about to be typed over, and a file is precisely the bulk path — but `CATALOG_IMPORT_MAX_STAMPS_PER_ROW` (200) stays, a row asking for hundreds being a mis-mapped column rather than a series.

- **Running the import** is `src/lib/catalog-import.ts` (#717), the server half of the same track. It does the two things the plan cannot: resolves the collection side the classification is judged against — the area's leading vendor (`buildPrimaryVendorByAreaMap`, #675), that vendor's effective prefix for the area, and every existing catalog identity one of the file's numbers could collide with — and then carries the verdicts out. **The commit re-plans; it is never handed a plan.** A classification is only as good as the collection it was measured against, and the client's copy is both stale and unauthenticated, so `buildCatalogImportPlan` is what the preview and the commit both call and a row that became a duplicate while the preview sat open is refused rather than written. A **new-issue** row is exactly what `createIssueAction` would have built from the same spec — the numbers generate the stamps (#70) and the declared range is derived from the spec, not typed (#452). A **fill** row does three things **in that order and deliberately not as one transaction**: the empty fields first (a stamp takes its issued year from the issue it is appended to, so filling the year afterwards would leave the very stamps the row created without it), then the missing numbers only, appended at the end of the sibling group (#549), then the declared range widened over what was just appended (#333's `computeIssueRangeExtension`, through `getIssueRangeSuggestions`). The range step takes **only this import's vendor and only an `extend`**: the same computation also offers `adopt-basic`, which *replaces* a declared range with the members' basic numbering, and rewriting a range the collector chose is not something an unattended bulk file should do. An issue declaring no range for the vendor gets none — one row of a file covers its own numbers, not the issue's. Filling is `fillIssueDetails`, whose emptiness test lives in the `where` clause rather than in a read before the write, so *never overwrite* holds by construction rather than by how close the two ran; `updateIssue` cannot serve here at all, being the edit dialog's write, which replaces the whole record and would blank an issue's numbering because the row said nothing about it. **Writes are per row and a failed row does not stop the file** — an all-or-nothing transaction would throw away hundreds of good rows for one late failure — and the report counts issues created, issues filled, stamps created, rows *unchanged* and rows *skipped* apart, because "you have imported this file already" and "this row was wrong" are different answers and #716 kept `noChange` precisely to tell them apart. The **duplicate guard (#85) is not re-run** and is not missing: a colliding row *is* the `fill-existing` verdict, so a `new-issue` row's candidates are by construction numbers nothing holds. Two things had to give way for this: `assertAutoCreateInput`'s ceiling became a parameter (`AUTO_CREATE_MAX_STAMPS` is a property of the *dialog*, where every generated stamp is about to be typed over, and says nothing about a file), and `getIssueRangeSuggestions` still selected `IssueMember.requiredForCompleteness`, a column #531 removed — Prisma rejected the query and `getIssueRangeSuggestionsAction`'s `catch` returned `[]`, so every coverage suggestion since has silently been an exception. It now measures against the issue's checklists' stamps, which is what that flag became. Same leftover `moveStampNode` carried until #549's tests reached it; the lesson is that a `catch` returning an empty list hides a broken query indefinitely.

- **The import dialog** is `src/app/c/[collectionSlug]/issues/catalog-import-dialog.tsx` (#718), reached from an **Import CSV** button in the Issues toolbar beside *+ Add issue* — the two doors onto the same spec, one issue at a time and a country at a time. Four steps, because each answer is what makes the next question askable: the file, the area, the mapping, the preview. **The file picker and the paste box are one door, not two** — both end as the same raw CSV string and nothing downstream can tell which was used, which is what makes the paste box cheap enough to have at all (a collector who keeps the catalogue in a spreadsheet copies a block of it). Reading the file into columns happens **in the browser** (`readCatalogImportFile` is pure and carries no `server-only`), because the mapping step needs the column names before any question can be put to the collection; classifying the rows does not, so `previewCatalogImportAction` computes it and `commitCatalogImportAction` computes it again from the same text and mapping — the screen therefore promises exactly what the writer does. The mapping is **guessed from the header words and shown for checking**, never contracted: each detected column is listed with the first values under it, and a wrong guess is one select away from right. Only the numbers column blocks the *Preview* button. The **area names its catalog on screen the moment it is chosen** (`useAreaVendorMaps`, the same primary-vendor walk the server resolves) — the wrong area files a whole country under the wrong numbering and there is nothing in the file to catch it. The preview draws at most `PREVIEW_ROW_CAP` (1000) rows because a country's catalogue is thousands and the table would crawl, but the summary counts all of them and **every refused row is listed however far down the file it sits** — the cap may only ever hide rows that are going to work. The result step counts *rows skipped* and *rows already imported* apart, which is what #716's `noChange` exists for.

- **Auto-creating an issue's stamps** (#70) has no master switch (#451): the per-catalog *Assign to stamps* boxes on the **Add issue** dialog *are* the decision, and `createIssueAction` gates on the presence of any `autoCreateVendor_*` field. They tick themselves off the (uncontrolled) range inputs, re-read on every `formVersion` bump — the primary when its own range can generate stamps at all (parses, ≤ 50), the rest when the primary is on and their span matches it. A box the collector clicked is **pinned** and never auto-set again, so a deliberate choice outlives further typing; #185's on-blur *Last* fill writes the DOM directly, so it bumps `formVersion` itself or the ticks would not follow.

- A **catalog-number chip copies its number on click** (#420, `shared/catalog-number-chip.tsx`), everywhere one is drawn — stamp/issue/copy rows, the pickers, the quick-price dialog. What it copies is narrower than what it reads: the **area prefix stays and the vendor abbreviation goes** (`Mi·PL 200` → `PL 200`), because the prefix is part of the number's identity (#66/#377) while the catalogue is context the collector already has in the field they are pasting into. The rule is pure (`catalogChipCopyValue` from the parts, `catalogChipCopyValueFromLabel` where a surface only carries a formatted label — the pickers' `catalogLabels`, an issue's declared range; a label whose head is not a short letter run is left whole, since eating a multi-word number like `Ark. 103` is the worse mistake). Confirmation **recolours the chip** instead of adding a ✓: these sit in wrapping rows of four or five and a glyph appearing would reflow the line under them. It renders a `<button>`, which is also what keeps it safe inside a click-through row (#374).

- The **variant price grid** (#618) is a grid over a **tree**, and that shape is the whole decision: rows are the stamp tree (indented, the Issues list's own tree), columns are the collection's conditions, cells are inline-editable prices. The rollup (#238, #616) is worth exactly as much as the completeness of the variant prices behind it — it picks the *lowest* price among a stamp's variant children, so a tree with three of eight variants priced answers a question about three variants while looking like an answer about the stamp, and a **listing** may not rest on it at all (#617) — while entering those prices was the slowest thing in the workflow: `quick-price-dialog` (#341) covers one stamp × condition × certificate and the stamp editor's grid covers one stamp, so a Michel tree of the `309 → 309A → 309AP → 309APa` shape was eight dialogs opened one after another, against a printed catalogue that prints those very figures side by side on one line. The surface therefore has the shape of the **source**. Three axes are chosen **once above the grid** rather than becoming columns: the catalog **edition** (which carries the vendor and the currency with it, so there is no separate currency control and no way for two cells of one column to disagree about what they are denominated in), the **certificate** (defaulting to none, which is what a catalogue quotes and what the headline rollup and a listing are read on), and the **format** as tabs — ADR-0020's own choice, a third dimension inline being unreadable — with a derived value rendering as the cell's **placeholder** so it stores nothing until typed over. There is **no draft and no Save**: one write per cell, the Colnect condition-mapping panel's idiom (#404), which is the only one that survives a grid this size, a lost draft here being a page of typing; a value equal to what is already stored writes nothing, so walking a filled row with Tab does not rewrite it. **Tab walks down a condition column** (#626) — the per-stamp grid's convention (#232), not the browser's left-to-right default. **Tab off the last cell lands on the footer's *Done*** (#753) — auto-saving per cell had left the dialog with no button in its own tab order at all, the shell drawing its close *above* the body, so a fast `price → Tab → price → Tab` pass walked focus out of the dialog and into the browser's address bar within a column; backwards off the first cell the browser still takes over, into the edition and format controls above the grid, which are the dialog's own. *Done* submits nothing — there is nothing to submit — and closes, the same act Enter on a cell already performs. **Enter saves the cell and closes the dialog** (#634), superseding #626's second half where it followed that same order: Tab is still the single movement rule for working a column through, and Enter is the way back *out* of a grid that was opened to fill one gap, which is how most of them are opened. A refused write keeps the dialog open with the message on its cell — closing on a failure throws the typed figure away at the one moment nothing else holds it. The **first cell of that walk takes focus** once the payload is in (#634): `DialogShell`'s own autofocus runs on mount, while the grid is still loading, so it landed on the close button and the first act after opening a dialog opened to type into was reaching for the mouse; it is the first cell *of the walk*, so a locked umbrella row is skipped here exactly as it is by Tab. It was built the other way round (*Tab across, Enter down*) on the argument that a column there is one catalogue's conditions while a row here is one stamp and a printed catalogue prints that line across; the reversal is a use finding, not a change of mind about the shape: what is actually filled is the column, because a tree is worked one condition at a time down a catalogue page — and two price grids that disagree about Tab is muscle memory wrong half the time. The walk is over the cells that can be **typed in**, so a locked umbrella row is simply absent from it and unlocking one needs no second rule. The grid **writes `StampCatalogPrice` rows and invents nothing**: an empty cell stays empty and clearing one **deletes** the row rather than storing a zero. Editable on **whatever edition is chosen**, unlike the per-stamp grid's newest-only rule (#91) — that rule exists because that grid shows every edition at once and has to say which one is *the* one, while here the collector has named it. Scope is an **issue** or a **stamp**, never an area or a checklist: a checklist is a collecting goal (#531) and a variant tree crosses it, while the printed catalogue's page is an issue. A **stamp scope resolves up to its tree's root** and renders the whole tree from there, which is what lets #617's blocker — whose subjects are the *unpriced variants*, not the umbrella — and the Items card's umbrella row open the same grid. A scope opened **for one copy** asks for the opposite with `subtree` (#679): it starts the drawn tree at the stamp named and shows that stamp's own descendants, because the item being listed is one umbrella and `Mi·NL 175`'s whole tree in answer to a question about `175E` buries the two rows that would unblock the listing under five that have nothing to do with it. The rollup is unharmed — an umbrella's value is the lowest of its **own** descendants, and every one of them is still drawn. Which openings pass it is one rule: **the ones that also narrow to a copy's axes** (#633), the Items card's *Price variants* and #617's blocker links, since both are one question about one copy. The blocker's links still name the *variant* and now carry the umbrella beside it (`StampSubject.treeStampId`), the grid being the umbrella's: a grid holding that one variant's row could not close the fault, the cheapest variant being unknowable until its siblings are priced too. A subtree resolves its editions and multipliers against the nearest area link **at or above** the stamp it starts from, not against that stamp alone — a variant node need not carry a `StampAreaLink`, and a grid with no editions cannot be filled in at all; a whole-tree scope keeps taking its root's. Sibling order is one rule with a stated fallback: `IssueMember.sortOrder` (#549) where the stamp is a member of an issue, then the denormalized catalog sort key (ADR-0014), then the id; an issue scope is therefore exactly the Issues list's order, and a stamp scope reaching a descendant in no issue still has the catalogue's own. `useVariantPriceGrid` takes the scope **at the click** rather than per hook, because a hook cannot be called in a `.map` (`useChecklistPriceActions`' constraint, #531) and two of the three entry points open it over whichever row was pressed; a caller with one fixed scope — the issue's row on the Issues list, where the multiplier editor already lives (ADR-0020 §7) — passes `defaultScope` and gets a ready-made `{ action }`. `onSaved` fires **once, on close, and only when something was written**, since refetching an issues list after every committed cell is refetching on every keystroke. **A grid opened from an offer is narrowed to the copy being listed** (#633): one condition column, the certificate and the format fixed to that copy's, and those two controls **gone rather than disabled** — a listing blocked on an unpriced tree (#617) is blocked at one `condition × certificate × format`, and every other column and control on screen is a way to walk off the axis the question was asked on. The catalog edition stays switchable, a copy fixing none, and a line above the grid names the scope, because a single unlabelled column says nothing about which certificate or format its figures are for. It is applied **client-side**, off a `VariantPriceRestriction` passed beside the scope: the payload is the whole tree either way (the axes are switched constantly in every other entry point, so one read per opening is the cheaper trade), and this is a statement about what is drawn. It is dropped whole when any axis is unknown to the collection's dictionaries — a grid merely wider than asked for is the harmless failure, a grid with no columns is not. The two offer surfaces carry the axes to it: `OfferPlatformItem` reports the first copy's, as it already does for the row's derived variant, and the `no-variant-price` blocker attaches to each named variant the axes of the copy that reported it (`StampSubject.axes`, deduplicated first-seen like the label). Every other entry point still draws the whole grid: those are opened to work a tree through, not to close one blocker. The **worklist** (`/stamps/variant-prices`, its own sidebar entry under Catalog) is what turns filling the gaps into a session rather than a hunt: umbrellas whose variants are not fully priced, widest gap first. It counts an umbrella as incomplete on **the conditions the collection actually holds or lists at** — the distinct conditions of its undisposed copies, which covers held and listed alike since `forSale` is a disposition of a copy in hand — and not on every row of the dictionary, or every tree is incomplete for ever. The rule is pure (`unpricedVariantCells`, `src/lib/variant-price-coverage.ts`), and three of its non-axes are decisions: **certificate none** and **format single** (a multiple derives from the single by a factor, ADR-0020 §5, so a priced single leaves nothing missing), and **whichever edition is newest with a price** — `pickCatalogPriceFor`'s own fallback, so a figure recorded in 2019 and never repeated still counts, asking for it again on every new edition being how every tree stays incomplete for ever. An **intermediate node is never counted** (it is an umbrella of its own, ADR-0010 §3, whose value *is* the lowest of its children), and in the grid its row is **read-only until unlocked** (#627): saying *umbrella* beside an open input was not enough — a row of empty boxes reads as a page of gaps to fill whatever is written next to it, while what typing into one actually does is override a computed figure. So the cell prints that figure instead, `≈`-prefixed, muted and italic — #238's own vocabulary for *inferred, not recorded* — as a `<span>` rather than a disabled input, which is also what keeps it out of the Tab walk without a second rule saying so. Read-only, never removed, and the row's padlock is the whole reason: an umbrella's own price does outrank the rollup (#616), so recording one stays a legitimate act, made a deliberate one — the lock decides which act is the *default*, not which is allowed, and an umbrella that already carries a price prints it plainly, with no `≈`, because that is the operative figure. The rolled-up figure is computed **client-side** off the grid's own columns (lowest of the row's variant-kind descendants at any depth, derived format values included, since `valuateCopy` rolls those up too) — which is why `VariantPriceRow` carries `isVariant` beside `identified`: the tree's shape does not say which children roll up, and the flat `isVariant` filter is exactly `valuateItemRows`' own, a distinct entry's variant grandchild included. It is taken on **the edition chosen above the grid** rather than #238's newest-with-a-price fallback, the one place it may differ from the headline the lists print: every other cell on screen is that edition's, and a rollup quietly taken from another would not line up with the column it sits above. A tree whose area resolves **no primary catalog** reports nothing rather than everything: that is a catalog-setup gap, and reporting it here would fill the worklist with trees no amount of typing could complete. Only stamps that **have children** are considered, a small fraction of any catalogue, and their descendants' prices are read in one query — `loadVariantPricesForUmbrellas`' own shape.

- A **missing name prints nothing, not a placeholder** (#535). `StampTitle` (`shared/issue-view.tsx`) draws the stamp name on the issue tree and the picker; a stamp without one now renders an empty string rather than "(unnamed)", and its date loses the comma that was separating it from the absent name. A stamp is read by its catalog number, which the detail line under it already carries, so a column of "(unnamed)" was the same non-fact repeated down every row. The flat stamp list already worked this way (`stamps/stamp-row.tsx` omits the whole name line). This is about **display**; a `?? "(unnamed…)"` in a *label* — a delete confirmation, a dialog title, a picker's summary line — stays, because a sentence naming the thing it is about cannot have a hole in it. The rule reached the Copies list's **duplicate group headers** in #678 (`inventory/duplicate-group-row.tsx`), the one display surface #535 missed: the count chip leads that line and is what the row is for, the group's catalog numbers sit two lines under it, and a header reading "(unnamed stamp)" on every group of an unnamed tree said nothing any of them did not.

- The issue's **stamp tree is ordered by hand** (#549, `IssueMember.sortOrder`). Until it existed the tree had no `ORDER BY` at all, so this is the first time the order is *stated*; existing members were seeded in **insertion order** (`stamp.createdAt`), which is what the default has to be — a collector who has arranged nothing should see the stamps in the order they were added. The value is only ever read **within one sibling group** — the issue's roots against each other, one parent's variants against each other, and the two never compared — so a reorder densely renumbers the single group it was handed and leaves every other group's values alone, and a value shared across groups is not a collision. That is also why an append is `max(sortOrder) over the whole issue + 1`: one number is past every group at once, and it is the right answer before the newcomer's parent is even known. `MEMBER_SELECT` had two readers that had to agree — `listIssueMembers` ordering in SQL and `toIssueData` in memory through `orderIssueMembers`, both `sortOrder` then `stampId` — and since #604 took the picker off the whole-issue read model there is only the SQL one, the in-memory pair having gone with it; a second reader arriving must order the same way, and cannot do it in the select, which is `as const` and whose readonly `orderBy` is not assignable to Prisma's input type (the same reason `checklists` is ordered in the mapper). Arriving stamps land **at the end, keeping their own relative order**: `moveStampNode` and `mergeIssues` both re-stamp what they move, a position being a statement about *one* issue's tree and nothing a stamp carries between them. The pure half is `src/lib/issue-member-order.ts`, and its one real rule is that a reorder names a **complete** sibling group: the tree can be narrowed by #531's checklist filter, and a drag inside a narrowed tree would move a stamp past a sibling that was never on screen — which is why the UI puts that filter away while reordering *and* the server refuses a partial group, one being a courtesy and the other the guarantee. `effectiveParentId` mirrors `buildStampTree`'s roots rule (a variant whose base belongs to another issue is drawn as a root, so it is grouped as one), or the order would be validated against a grouping nobody can see. The UI is `shared/stamp-tree-reorder.tsx` over #306/#313's `useReorderList`: reordering is **a mode, not an always-on affordance** — thirty rows each carrying a permanent grip read as a list you are expected to be rearranging, which is not what looking a number up is — and the toggle sits at the **foot** of the tree beside **+ Add stamp**, both being things done to the tree as a whole rather than to a row in it. `StampTreeGroup` is a component rather than a hook call per level because a group needs its own `useReorderList` instance and the groups are found by recursion; it takes a `renderNode`, so the list row's editable node and the detail page's linked one stay two different rows on one wiring. The drag is optimistic and rolls back on refusal, a drag that snapped back a third of a second later reading as a drag that did not take. There is deliberately **no "custom order" sort on the flat Stamps list**: it spans issues, so there is no single sequence to sort by, and the tree — which has never had a sort switcher — simply *is* the order.
- A stamp is **reassigned to a different parent** in place (#656, `reparentStampNode`) — the finer-grained neighbour of #54's move-to-another-issue, and the correction for a stamp filed at the top level that turns out to be a sub-variant of another, or filed under the wrong base. Only the tree edge is written. The catalog numbers, the name and the subtype are facts about the stamp rather than about where it hangs, and every copy, want, offer line and checklist entry names `stampId` — so nothing else moves, and the stamp's own branch comes with it because reparenting is a statement about *one* edge. The parent must be a **member of the same issue**, which is the rule a parent already obeyed (`addStampToIssue` refuses one from anywhere else) and the one `buildStampTree` reads: a member whose parent is absent from the issue is drawn as a root, so a cross-issue parent would leave the child rendering exactly as it did before the move, at a position the data no longer agrees with. Filing a stamp under another issue's stamp is therefore two intelligible steps — move the node (#54), then say where it hangs — and the picker offers **no parent (top level)** as a first-class answer, since without it a misfiling could only be undone by deleting the stamp. Two refusals, both worth stating rather than flattening: a parent that is not a member, and a **cycle** — the guard climbs the proposed parent's ancestry (through stamps outside the issue too, a chain that leaves and comes back still being a chain) and stops if it meets the stamp being moved. The dialog does not offer that branch at all, so the refusal is normally something the collector never has to read. A stamp arriving at a parent with **no subtype** takes the collection default, the rule `addStampToIssue` writes by (ADR-0010 §2a); one that already carries a subtype keeps it, because that subtype is the collector's own classification and re-deriving it would quietly discard it. It lands **at the end of its new sibling group** for #549's reason. Nothing is recomputed afterwards and there is nothing to recompute: unknown-variant detection (#239), the headline-price rollup (#238) and checklist completeness (#133/#661) are all read off this very `parentId` at query time, which is why both the old parent and the new one answer differently on the next read — the reason those derivations were never cached in the first place. The action lives in the tree row's `⋮` beside **Move to another issue…**, and only there: the issue *detail* screen's tree carries no row actions at all.

- An active filter **hides** the variants it did not match, on the Issues list and in the stamp picker alike (#631, superseding #186's fading). #186 left the choice open and the fading was what the picker happened to ship; #631 settles it as *hide* and, on the collector's call, settles it for **both** surfaces rather than only the list — one tree, one behaviour, and no rule to remember about which screen you are on. The argument for hiding is the same in each: an Infla tree runs to dozens of variants and a page of grey around three matches is a page nobody can scan. The argument that had been offered for keeping the picker faded — that its tree is a *chooser*, so a stamp you were about to pick going missing is worse than one drawn faintly — does not survive contact with when the narrowing actually fires: **only** where the issue's own header did not explain the hit, which is to say only where the collector was hunting a particular stamp rather than browsing an issue. Nothing is hidden from a browse. What narrows is the **stamp-level** half of the filter set — the quick search and the catalog-number filter, the two a member stamp can satisfy — never area or year, which are the issue's own; several active ones **intersect**, because the server ANDs them and an issue returned by both was returned for stamps satisfying both. The rule the picker derived for itself (#604) is now the shared, unit-tested `src/lib/issue-stamp-match.ts`: `needsInnerStampMatch` asks whether the row's own name, year, `issueNo` or declared range accounts for a filter, and `matchedStampsInIssue` returns the matching stamps or **null** — null for no stamp-level filter, for a hit the header already explains, *and* for nothing matching inside after all, since a tree drawn whole beats an issue drawn empty, which reads as data loss rather than as a filter. Structural types rather than `IssueListItem`/`StampNodeData`, so it unit-tests without Prisma. The **one** thing the two still do differently is the probe: the picker reads a collapsed row's members so it can open itself on a match (#186's auto-expand), while the list does not — hiding only matters once the tree is on screen, and a probe per row is a query per row on every keystroke. The list's rows are not opened by a search, so there is nothing to open. A narrowed node starts **expanded** — everything left is a match or the numbering one hangs under, and a match behind a collapsed arrow is a match nobody can see — and the collector's own toggle still wins after that. Both narrowings are dropped while reordering, the checklist filter's own rule (#549). Composing the two filters would be wrong and `filterStampTreeBy` takes both at once for that reason: run in sequence, the first pass's *context* ancestors enter the second as ordinary survivors and keep a branch the other filter never matched.

- **Opening the stamp picker is what makes its answer current** (#654). `StampPickerBrowser` reads the collection through two channels that go stale in different ways, and the collector sees one symptom for both — *the area (or Issue) I just made is not here*. The **area tree is a server prop**, threaded down from each screen's page, so nothing short of a navigation replaces it; the **issue rows are the issues list's own client query** under the shared 30s stale time. Neither notices a write made anywhere else, and the write that matters is routinely made *elsewhere*: a second tab, which is how a country first met halfway through identifying a scan sheet (#567) gets added at all. The picker therefore refreshes **both** on mount — `router.refresh()` for the server tree the areas ride on, `invalidatePickerData` for the issue caches. On **open**, deliberately, rather than on a timer or on window focus: the open is the collector's own act and the one moment the tree has to be right, and it is bounded (a picker is opened, used and closed) where a focus handler fires on every alt-tab through a sitting. Neither half blanks — an invalidation refetches behind the rows already drawn, and every write on these screens already pays for a `router.refresh()`. It sits in the shared picker rather than at the call site because every entry point into it — purchase intake, tile identification and its candidate shortlist, `StampSelect` wherever a copy is added or edited, trade receive lines, auction lot lines — asks the same question and was stale in the same way; #212 and #440 are the same class of bug answered one screen at a time.

- The **stamp detail page manages the variant tree** (#630): add, edit, delete and reorder the variants under it, from the Variants card. It is not the *detail page reads* invariant being broken — that rule is about a record's **fields**, and a variant tree is the relationship *between* stamps rather than a field of any one of them, with no other home on that screen. Every write still goes through the dialog that already owned it (`StampFormDialog`, `DeleteStampDialog`), so there is exactly one editor per record and the subtype comes along for free (`isChildContext` already turns that control on for a stamp with a parent). Every tree operation is **issue-scoped** — `IssueMember.sortOrder` is per issue (#549) and a new stamp is filed under one — so the card settles on the stamp's **first** issue membership, which is what `StampListItem.issues[0]` had to be *made* into: nothing ordered `issueMemberships`, yet two readers already acted on "the first" (the edit dialog's checklists, this card's writes), so `toStampListItem` now sorts them by issue year then id. Sorted in code rather than in the select because `STAMP_LIST_SELECT` is `as const` and Prisma's `orderBy` will not take a readonly array. The card **names** that issue on screen rather than assuming it, so a stamp on two says which one is about to change — a picker was weighed and rejected as a control asked on every stamp to be answered on almost none. `getStampRelatives` grew the tree's order (`IssueMember.sortOrder` within that issue, then the catalog sort key — the variant price grid's rule, #618, so a drag here shows up there), the stamp's `position` among its siblings, and `childrenOrderable`: reordering is offered only when the children are one **complete** sibling group of that issue, because `reorderIssueMembers` refuses a partial one and a variant filed on some other issue would make it partial. A stamp on no issue keeps a read-only card. The card renders even with nothing on it, which is `DetailCard`'s stated exception (#536) rather than an oversight: its empty state carries the only way to start a tree.

- The **stamp and issue detail pages start their own record's edit** (#751) — **Edit** at the end of each identity band, opening the Issues list's own `StampFormDialog` / `IssueDialog` over the record the page is about. It is #673's rule reaching these two screens, and the invariant survives it for the reason #673 gives: what opens is *the list's dialog*, so there is still exactly one editor per record and not one field on the page becomes typeable in place. The gap it closes on the stamp screen is a peculiar one — since #630 that page has edited every stamp *under* this one while the stamp it is about could only be reached by going back to a list and finding its row again. On the issue screen the same is true of the tree it already reorders and narrows. The button sits on the **band**, not on the Details card it would change, because it is about the record as a whole. The wiring is `router.refresh()` (both pages are server-rendered) plus the originating list's `invalidateList`, since the back link is the way out and its row must not still read as it did before the edit. The stamp dialog is handed the memberships as they are — it edits the **first** one's checklists, `toStampListItem`'s own rule, the same one the Variants card writes against — and its catalog-number inputs are labelled through `vendorMapFor(areaId, firstIssueId)`, the band's own resolution, so the prefix on the form is the prefix the numbers will carry (#377). The dictionaries both dialogs need are fetched client-side rather than loaded beside the record on the server: they are cached per collection and shared with every other screen that opens the same dialog, and a page read far more often than it is edited should not pay for them on the way in.
- A **variant range** adds a whole lettered run under one base stamp in one save (#722), from the Variants card, from the stamp row's `⋮` menu on the Issues list, and from the stamp picker's own tree (`+ range`, beside `+ variant`) — everywhere a single variant is added. The picker offers it for the reason it offers `+ variant` at all (#105): a stamp met while identifying a piece is missing exactly as often as a run of six is, and leaving the picker for the Issues list loses the copy being entered. It is deliberately **not** a second stamp editor: it types the one thing that differs between six stamps (the catalog-number suffix) and the one thing they share (the subtype), and every stamp comes out exactly as `addStampToIssue` with a parent prefilled would have left it — the base stamp's year (#360), no name, and **no checklist entry**, because a variant is not the issue's set. That last one is the only write `createRangeStamps` skips when its new `parent` argument is present, which is why the root range (#219) and the variant range are one function rather than two. Numbers are for the area's **primary** catalog only: a secondary catalogue's variant lettering does not run alongside the primary's position for position, so generating it would be guesswork, and it stays typed per stamp. `parseVariantNumberSpec` reads the field: a comma-separated piece **carrying digits** is a full catalog number and goes through `parseCatalogNumberSpec`'s own resolution, a piece **without** is a suffix sequence hung off the base number (`a-f` under `240`), decided per piece so the two halves of a range always agree about which axis they are on (`240a-c` is rejected rather than guessed). A suffix *range* goes through `resolveSuffixRange`, the resolution the issue-level range field shares; a **lone** suffix is taken literally, so `309A` + `P` is `309AP` — a suffix no sequence would have produced. The spec is re-parsed **server-side** against the stored number rather than trusting the previewed list, because what `a-f` means is a fact about a stamp.
- A suffix range runs over **three** sequences, not two (#722): lowercase letters, canonical Roman numerals, and **uppercase letters** — `423A-423C` used to be an unrecognized sequence, which is the ordinary Michel shape. The last two overlap on `I V X L C D M`, and `resolveSuffixRange` settles the tie **for the pair rather than per end**: a range is Roman only when *both* ends spell a numeral, so `12I-12V` stays the numeral run it always was while `423C-423F` is lettered, because `F` is not a numeral and one end cannot be on a different axis from the other. `423C-423D` is genuinely ambiguous and goes to the numerals; writing the two values out says otherwise, which is also why a **lone** suffix in a variant spec is literal. The resolution is one function shared by `resolveCatalogRange`'s suffix branch and `parseVariantNumberSpec`, so the issue's range field and the variant field cannot drift; `parseSuffixOrdinal` was deliberately **left alone** — the span folding in `catalog-range.ts` and `offer-title-template.ts` reads it, and widening what folds into `1294A-C` in a listing title is a separate decision from what a range field accepts.
