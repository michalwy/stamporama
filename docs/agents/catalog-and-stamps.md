# Catalog, Stamps, Checklists & Wants

Format, subtype, catalog prefixes and numbers, the issue stamp tree, checklists and wants.

- Physical **format** (pair, block, strip) is an axis of its own (ADR-0020), not a stamp — superseding #135's "record a multiple as its own `Stamp` with a self-descriptive number" for *homogeneous* multiples, which collapsed on deep variant trees (Infla `309 → 309A → 309AP → 309APa`: `formats × nodes` stamps, and "a pair, variant not yet identified" inexpressible because a pair of `309BP` is not a child of a pair of `309B`). `StampFormat` is a per-collection dictionary shaped like `StampCondition`, referenced from `Item.formatId` *and* `StampCatalogPrice.formatId`. **Null means single** — no such row is seeded, exactly as a null `certificateStatusId` means "no certificate" (ADR-0006 §2) — so nothing needed backfilling. A multiple is **never decomposed**: no unit count exists, nothing multiplies or divides by one, and completeness treats format as a breakdown dimension beside condition ("the series in pairs?" like "the series in MNH?"). Zusammendrucke with their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) stay their own `Stamp` — the test is whether the catalog numbered it, not whether it holds more than one stamp. A format's price is **explicit or derived**: an explicit `StampCatalogPrice` row wins, else the single's price × a `StampFormatFactor`, because catalogs publish one factor per issue and an explicit price only where a multiple deviates. Factors live in one table with nullable anchors — the all-null row *is* the collection default (no second `defaultFactor` mechanism to explain) — resolved by **fixed precedence**, `(issue set?, area depth, condition set?)` lexicographically, never a specificity score: *where* deliberately outranks *for which condition*. The rule is pure in `src/lib/format-factor.ts`; `format-pricing.ts` wraps it per stamp because it needs the area ancestry and issue. A format is **translatable** like every other dictionary that reaches a listing (#344; `StampFormatTranslation`, two independently-falling-back columns, `format` in the shared `TranslatableEntity` union), and renders through `{format}` / `{formatAbbr}` + `{#formatLegend}` (#345) — where a **single resolves empty**, the common case, handled by the existing tidy pass rather than by a rule of its own. Lists gain an **`as`** switcher beside the condition one (#343), defaulting to Single, hidden without formats, stored as `""` because Single is not a row. A list column **derives** where nothing explicit was recorded and marks it with the same `~` + italics an unknown-variant rollup uses (#238) — one vocabulary for *inferred, not recorded*, distinguished only by tooltip. The Copies list takes format as a **filter**, never a switcher (a copy's format is a fact), and `valuateCopy` resolves at `Item.formatId`: with no explicit price and no factor a multiple is **unpriced**, never valued at the single's figure. Per-row factor resolution would be a query per row, so `makeFormatFactorLookup` loads the factor rows + area tree once and resolves in memory. A multiplier is **edited where its scope lives** — an issue's from its row on the Issues list, an area's from its row under Areas — so the anchor is never a field the surrounding screen already answers; Settings edits only the collection default and areas and **does not list issue-anchored rows at all**, excluding them *at the query* (`getCollectionFormatFactors`) rather than filtering after: there can be one per issue per format, which is thousands of rows. A scoped list shows what is set on that row alone, never what would apply through inheritance — it is an editor, and showing a parent's rule under a child invites editing it from the wrong place. The scoped editor is one component exposed both as a `{ action, dialog }` row-action hook and as a plain dialog, because the areas panel maps its rows and cannot call a hook per row. The price grid gains format **tabs**, not columns, and a derived value renders as the cell's placeholder so it stores nothing until typed over. Price cell keys grew a **trailing** `~<formatId>` segment, optional so pre-format payloads still parse. **Intake records a format too** (#573): `intakeStamps` no longer hard-codes `formatId: null`, and the field sits beside condition and certificate in the intake step — the piece is a block at the moment it is identified, and correcting it afterwards is one copy edit per piece, from memory, after the sorting pass. Single-stamp intake only, the rule photos follow (#148) and for a stronger reason — a whole-checklist intake fans out across many stamps and one format could not be true of all of them — so the server drops it for a checklist rather than refusing, and hidden entirely until the collection defines formats, as the list's own format controls are. It is deliberately **not** remembered per collection, and that asymmetry against the three fields around it is the decision, not an oversight: condition repeats down a stockbook page (all mint, all used) so remembering it saves hundreds of clicks, while single is the default state of the world and a multiple is the exception, so a sticky format would mark every later single as a block until noticed — this feature's own failure inverted, and worse, since a format nobody chose is invisible where a missing one reads as *single*. The reasoning is parked at the `useState` in `IntakeConditionDialog`, which is where someone counting three remembered fields and one not would go to "fix" it — and the reset is **enforced there too**, off the identity of the `selection` prop, rather than inherited from the dialog being conditionally rendered: a remount is a fact about the component tree, so keeping the dialog mounted across a transition later would quietly make the field sticky again, and no test can see it. `selection` is rebuilt at every pick, which a key derived from the stamp id is not — a block of four followed by singles of the same stamp is one intake run. `IntakeHoldingsLine`'s live want marker takes the format as its third axis for the same reason its docstring gave for passing null before. **Completeness takes it as a third axis too** (#133, closing what #519 left open): `CompletenessCount` carries `formatId` and `ChecklistCompletenessGrid` gains `formats` — the same disposition × condition grid per format, counted over copies of that format alone, so a block never fills a gap in a set of singles. `rows` stays the roll-up across every format and is unchanged, which is what keeps it the honest answer to *have I got the series at all*: mixing formats there is the mixing the `conditionId: null` column already does down the condition axis, not a claim that a pair is two singles. Which formats appear is **what the checklist is actually held in**, judged over its own stamps (a block held for the neighbouring specialized set opens no column here) — the dictionary supplies only the order, single first — because format is sparse where condition is not, and a grid per dictionary row would be a wall of zeros. The card draws them as **tabs**, the price grid's choice for the same reason (a third dimension inline is unreadable), and draws none at all where only one format is held, so the overwhelmingly common singles-only collection sees the card it always saw. It rides on the existing `groupBy` as one more `by` column — a format breakdown is a regrouping of the copies already read, never a second query.

- A **checklist** (#531; ADR-0031) is the collecting goal, as against `Issue`, which is the publication event — a named list of stamps that counts as one complete unit, and an issue may carry several (basic beside specialized, perforated beside imperforate, tabbed beside plain). It replaces `IssueMember.requiredForCompleteness`, one boolean that gave an issue exactly one set; the migration turned every issue with a required member into one checklist named after it and dropped the column, so **there is no required flag to consult** — membership of a `ChecklistStamp` row *is* required-ness, and an optional extra is an `IssueMember` on no checklist. `Checklist.issueId` is nullable on `StampFormatFactor`'s idiom (null spans issues), but only the issue-scoped editor exists (`useChecklistsAction`, on the issue's row, ADR-0020 §7). `sortOrder` is load-bearing: the **first** checklist is what a single-checklist row shows and what a new stamp joins by default. Every derived fact names its subject explicitly — **per checklist** for the completeness grid and the catalog-price total (a union would count a shared stamp once, for a figure answering neither question), the **union** for `requiredCount`, the declared range (#333) and the issue gallery (#137), **one named checklist** for the intake fan-out, auction lot composition and the picker's *whole set* buttons. The issue row collapses several to a `3 checklists` badge with the detail in its tooltip (#425's counting rule); the issue's detail page is where each gets its own completeness and value card. That badge stays an **indicator** — narrowing is a `MultiSelectFilter` above the row's *expanded* tree and in the detail page's Stamps card header, never in the collapsed chip line (a toolbar-sized control per row outweighs it), held in local state because a per-issue filter has no single URL parameter on a list of many issues. `filterStampTreeByChecklists` (`src/lib/stamp-tree-filter.ts`, pure) drops non-members but **keeps a node with a surviving descendant**, returning it in `contextIds` to be dimmed: a variant is read through its ancestors, and `309AP` without its `309` is a number nobody can place. The filter is on all three tree surfaces — issue row, issue detail, stamp picker (where the context dimming folds into #186's existing `dimmed`, one faded state rather than two). **`Checklist.name` has no unique constraint and nothing resolves a checklist by it** — names repeat freely across issues and never meet, since every read is scoped by `issueId`; a repeat *within* one issue gets #178's advisory ⚠, checked client-side against the already-loaded list.

- A **want** (#532; ADR-0032) is what the collection is *looking for*, and it is deliberately **not** a fourth disposition: `inCollection`/`forSale`/`forTrade` live on a copy, an `Item` is one physical copy (ADR-0007), and a wanted stamp has no copy — a `wanted` flag would force phantom rows and poison every count that reads inventory. A want carries an **acceptance set per axis, where zero rows means "any"**: `WantCondition` (plain composite key — `Item.conditionId` is required, so there is no "none" value), `WantCertificateStatus` and `WantFormat` (**nullable** FK, because a null there *is* a value — "no certificate" per ADR-0006 §2, and "single" per `StampFormat` — with `UNIQUE … NULLS NOT DISTINCT` as `stamp_catalog_price_unique` has it). **"At least X" is inexpressible on purpose**: `StampCondition.sortOrder` is display order, `U` and `MNG` are cancellation and gum rather than two points on one scale, and `CTO`/`FDC` are on no scale at all, so any minimum-quality rule would invent an ordering the dictionary does not guarantee. Upgrades then need no concept of their own — a used copy held against a mint-only acceptance set simply does not satisfy the want. `closedAt` is `Item.disposedAt`'s idiom (null = open, one column, so every filter stays a plain `where`). There is deliberately **no price on a want** — built, then dropped by `20260811140000_want_drop_max_price` before it meant anything: a want has no date, so a figure on it is a price opinion frozen the day it was typed and never corrected (ADR-0029 §2's objection to a *configured* ratio, once per row), and the whole-series add makes it unworkable outright — one field over twelve stamps worth wildly different amounts, where copying stamps one ceiling onto all of them, splitting by catalogue invents limits nobody stated *and* freezes them at today's catalogue, and splitting evenly prices a key value like a common one. What a stamp is worth **at the moment of buying** is the recommendation engine's answer from recorded results (ADR-0022/ADR-0029), against the copy in hand; two mechanisms for one question is how they drift. `priority` is what survives of "how much do I care", and it needs no maintenance to stay true. What a copy satisfies is the pure `wantMatchesCopy` (`src/lib/want-rules.ts`), shared so the intake review, the list and any later consumer (#253/#250, trade) cannot disagree; storage and reads are `src/lib/wants.ts`. The **review belongs to the moment a copy reaches the collector's hands** — the transition into `delivered` — not to the moment its row was written (#532). One rule covers every route in: a hand-added copy starts delivered and is reviewed at once; intake creates `ordered` (or `to_sort` on an already-arrived order) and raises nothing, so `intakeStampsAction` deliberately returns no `copies`; `bulkUpdateLotItems`/`Scoped` return the copies their change *moved into* delivered (candidates read **before** the write, since afterwards a copy that just arrived is indistinguishable from one that was already here), and `updateItem` returns `becameDelivered`. That is also what closes the auction-settlement gap without a second review being bolted onto it: a parcel won, settled into a purchase and sorted converges on the very transition every other route does. Both intake paths raise the **review** — `intakeStamps` now returns the copies it created rather than a count, and `createItemAction` returns the one it made — and the review offers **close / narrow / leave open** per want. **Nothing closes automatically**: that would discard a record of intent, and narrowing (the common case) is a judgement the app cannot make. What it may do is *seed* — `narrowConditionSeed` ticks every condition except the one that arrived, from the dictionary's membership and never its order, and only when the set was empty, since a set already narrowed is an answer the collector gave once. Completeness targets are a **generator, not a source** (`createWantsForMissing`): explicit rows once, wide open (a gap carries no acceptance criteria), skipping stamps with a held copy or an **open** want — a *closed* one is not a reason to skip, the gap being real again — which is what makes pressing the button twice a no-op. The add form takes **one stamp or a whole checklist** (`WantCreateInput`): `StampSelect` gained an opt-in `checklist` prop that turns on the browser's per-checklist *whole set* buttons (the copy form does not pass it — one copy is one copy), and the fan-out writes one want **per stamp** sharing the form's acceptance, priority and note, since a set-shaped want could never be half met. It skips a stamp with an **open** want and reports the count, but deliberately **not** one merely held — that is the gap generator's rule, and wanting a better copy of something held is the ordinary case. `priority` is stored as its **rank** (`Int`, 0 = high, 1 = normal, 2 = low), not as the word: the list is ordered by it and paged on the server, and the only order Postgres can put a `text` column in is its spelling — `high < low < normal`, which nobody means. `want-rules.ts` owns the vocabulary and the word is what crosses the wire, the form and the filter; one column, not a word plus a rank that must agree with it. The list row leads with the stamp's catalog photos (#137) and the screen carries the shared `ListFilterSidebar`, but the list itself is **cursor-scrolled, not fetched whole**: `listWantsPaginated` + `listWantYearFacets` share one `buildWantListWhere`, so a facet cannot count a row the page would not show, and the year is dropped only for the facets (each count says what *that* year would leave). This is deliberately not Contacts' whole-list-and-filter-locally shape — an address book is a few hundred rows, a want list is a collecting plan's shopping list and runs to thousands. The condition filter ORs in `conditions: { none: {} }`, since an empty acceptance set means "any" and such a want really would take the condition asked about. Order is `closedAt` nulls-first → `priority` → `createdAt desc` → `id`, the last being what makes an offset page stable over ties. Area and year ride in `useCollectionFilterStore`, not the URL (#143), on the stamp picker's reasoning. The row shows a **catalogue range**, not a price: a want accepts a *set* of (condition, certificate, format) combinations and each has its own value, so one number would be one combination picked out of the set answering a narrower question than the row asks (`wantCatalogRange`, pure, in `want-valuation.ts`). Each combination goes through **`valuateCopy`** — the function that prices a physical copy — so a want's figure and the copy that eventually satisfies it cannot drift; min/max in the **base currency only**, since two currencies are not a range; an unpriced or unconvertible combination is **counted, never zeroed** (a catalogue gap would drag every range to nothing) and the row reports `priced / accepted`; `estimated` is inferred from **no recorded row for the format**, not from a factor existing, because a format can be priced explicitly *and* carry one. One pricing pass **per page** — the page's stamps' prices plus the per-collection preamble the stamps list already loads — and only in `listWantsPaginated`, the intake review and the form drawing none. The row promotes **Open stamp page** (the shared `useDetailPageAction`, first in the menu as everywhere) and **Edit** to hover quick actions through `pickRowActions`, so a shortcut and its menu entry cannot drift; the stamp screen returns the favour with a read-only **Wants** card (`related-wants-card.tsx`, off a `stampId` filter) leading its right column, showing closed wants faded — noise on a list, but on one stamp the record that it was looked for and found — and **rendering nothing at all when the stamp is on no want**, loading included so it never flashes an empty state: Copies and Offers are about every stamp and print "none yet" as a real answer, while wanting one is the exception, and a card saying "you are not looking for this" on every catalogue page is furniture. Priority is a chip beside the acceptance chips, in three deliberately **different** tokens (warning / info / muted): a scale whose middle and bottom look alike is one you read the word off, and then the colour is decoration. **Flat is the shape and issue grouping is a view of it** (`listWantIssueGroups`, a remembered *By issue* toggle): a want's subject is a stamp and its acceptance sets are per stamp — within one series the key value is wanted MNH with a certificate and the rest "anything" — so an issue heading over those rows overstates, the dominant reading is matching a stamp in hand against one searchable row, and an issue-shaped spine would be a second answer to the completeness grid ADR-0031 already gives from copies *held*, re-coupling exactly what §6 separated. Grouped server-side on #424's reasoning (offset paging would split a group across a page boundary and report two half-counts), counted on the stamp's **first** issue membership and read back through an `issueId` filter matching **any** — #172's pair, not a third rule — with `NO_ISSUE` for stamps in none. The row reads `open / total`, both counted with every filter **except** status, since a denominator that moved with the Open/Closed toggle would be a fraction of nothing; which groups *appear* still obeys status, and because status narrows on `closedAt` alone that falls out of the two counts with no second query. The catalogue lists carry the want back the other way (#532): `loadStampWantSummaries` denormalizes each stamp's **open** wants onto `StampListItem.wants` and `StampNodeData.wants` — scoped to the page's ids, `loadStampCopyCounts`' call — and `WantChip` draws them, absent when there are none (a marker on a few rows is a signal; one on every row reading `0` is a column) and coloured by the *loudest* of the wants behind it. The detail is a **click popover, not a tooltip**: a dozen wants × three axes flattened into prose was unreadable, and a popover draws them as the want list draws them. Because the summary is *copied onto two other read models*, `useAddWantAction` invalidates the stamps and issues caches as well as the wants one — refreshing only its own list left the chip missing until a reload. The chip is built on the shared `STAMP_SECONDARY_CHIP` base so it sits on the line its neighbours do, and **always draws its count, one included** — an icon alone gives the chip no text to set its line box from and it came out shorter than every chip beside it. It is on **auction lot lines** too, where it answers the sharper question: a line names a concrete `(condition, certificate, format)`, so it passes a `copy` and the chip runs **`wantMatchesCopy`** — the intake review's own predicate, so a lot marked as matching and the review that greets that copy on arrival cannot disagree. A match is drawn as a **ring**, not another colour: colour is already spoken for by priority, and two meanings on it leave neither readable. That is what `StampWantSummaryEntry.acceptance` is for — the words are for reading, the ids for deciding, both off one row. The marker rides on **copies** the same way: loaded in `enrichItemRows`, the one funnel every copies view goes through (Copies list, a purchase order's intake, the lot and group readers), so no surface loads it separately — and on `CopyGroupRow`, where a group being one stamp at one condition means the answer covers every copy in it. On a held copy the ring reads as the **upgrade** signal, holding one never having closed a want. What the collection already has of a wanted stamp is a **split, not a count** (`WantCopyCounts`: held / ordered / inTransit, `to_sort` folded into held since the copy is on the desk either way) and it rides on both `WantListItem.copies` and `StampWantSummary.copies`, so the chip's popover carries it too. One figure hid the case that matters: a want stays open until the collector closes it — correct, the stamp is not here — but an *ordered* copy then looked exactly like no copy, so the same stamp at the next auction read as an untouched gap and the want urged a second bid. Held and on-its-way are different answers to "should I be bidding on this". Deliberately **derived, never stored**, and it closes nothing: no third state on the want, and ADR-0032 §7 stands. The buckets are held / **toSort** / ordered / inTransit — `to_sort` stands apart from held, an arrived-but-unsorted copy being a different answer to "have I got this" than a filed one — and the figures **leave out the copy they are drawn on** (`loadItemWantSummaries`, keyed per copy rather than per stamp so two copies of one stamp on a page each omit a different one): a purchase-order row otherwise reported *one in transit* about itself, and a count meant to say "something else is coming" must not be satisfied by the row you are reading. It is counted **twice, and the two must never be drawn as one**: per *stamp* (`WantListItem.copies`, `StampWantSummary.copies`) is the upgrade context — everything held whichever want it answers — while per *want* (`WantListItem.matchingCopies`, `StampWantSummaryEntry.copies`, filtered by `wantMatchesCopy`) is the **only** figure allowed to claim something is on its way. A used copy in the post satisfies a want for "anything" and a mint-only want not at all, so one line above a list of wants tells the collector to stop bidding on the mint copy they were right to chase. Both tallies come off **one** `loadCountedCopies` read, so they cannot be taken over different sets. Named acceptance profiles are #533 and deliberately not folded in.

- A **named acceptance profile** (#533; ADR-0032 §9) **seeds**, it is never referenced. `AcceptanceProfile` + three member tables carry exactly the axes a want carries (nullable members and `NULLS NOT DISTINCT` included), and applying one *copies* the sets onto the want — hence there is deliberately **no `profileId` on `Want`**, and that absence *is* the decision, which a schema cannot state and ADR-0032 §9 therefore does. `CollageTemplate`'s shape (#308), and the precedent is the reason: a reference would make editing a profile a silent rewrite of what every existing want accepts, closed ones included, whose acceptance is a record of a decision already taken rather than a setting. So a delete needs no in-use check and an edit needs no warning; the cost — changing a profile *and* the wants carrying its terms is two acts — is answered by a bulk edit over a **chosen** set of wants if it ever proves tedious, deliberately unbuilt. `validateAcceptance` and the `AcceptanceInput` shape live in `src/lib/acceptance.ts`, shared by `wants.ts` and `acceptance-profiles.ts` so the two cannot disagree about what "no certificate" means. The picker is inside the shared acceptance editor (`want-acceptance-fields.tsx`), so the want form and the intake review's narrow step get it from one place and the Settings editor that *defines* profiles turns it off (`profiles={false}`); which profile it shows is **derived** by comparing the sets (`acceptanceSetsEqual`, pure, in `want-rules.ts`) rather than stored — a seed leaves nothing to read, and editing one box drops it to *Custom*, the terms no longer being that profile's. The profile a want was **saved** on leads the next add (`LS_LAST_ACCEPTANCE_PROFILE`, per collection, `readRememberedProfile`/`rememberProfileFor`), the last subtype's (#342) and last condition's (#121) idiom — wants are entered in runs and a run is one set of terms. Saved rather than *picked* (a profile cancelled is not what was gone with), **derived on submit** rather than tracked as a selection (the form has no other notion of "the current profile", and a second one would be a thing to keep in step), **cleared** when the terms match no profile (an off-profile want says the run moved on, and the stale id would seed the next want with terms just chosen against), and read on **add** alone — an edit shows the want's own terms and the intake review's narrow step has ADR-0032 §7's own seed to keep. Applied during **render**, the settings panels' "adjust state when something arrives" pattern rather than an effect, and once, flagged rather than conditioned on the sets being empty so a background refetch cannot re-seed boxes deliberately cleared.

- A stamp's **catalog prefix** is resolved from *two* levels, not one (#66/#377). The per-(area, vendor) prefix on `CollectionAreaVendor.areaPrefix` is inherited down the area tree, and an **issue may override it** for its own stamps (`IssueCatalogPrefix`, one row per issue × vendor, `areaPrefix` NOT NULL — an issue has one level above it, so "inherit" is the absence of a row, which is what the dialog's blank field stores; on an *area* a null row is meaningful, being what stops inheritance). The override is the **catalog identity**, deliberately not a display layer: it decides the rendered chip, the stamp picker's match keys, generated listing texts, derived offer-set and auction-lot names, duplicate detection (#85) and the Colnect strict full-key match (#155) alike — a stamp reading `Mi·SP 1` while the duplicate checker still thinks `Mi·PL 1` is the bug this rules out. One resolution serves everything: `effectivePrefixFor` (`area-prefix.ts`) server-side, and the pure `buildAreaVendorMaps(areas, prefixByIssue)` → **`vendorMapFor(areaId, issueId)`** everywhere a row renders a number — never `vendorMapByArea.get(areaId)`, which answers only half the question. The override map is loaded **whole, once per read** (`issue-prefix.ts`; client `issues/catalog-prefixes`, keyed under `["issues", collectionId]` so existing issue invalidations cover it): the table is sparse by construction and a screen needs it before drawing its first chip. `duplicate-catalog.ts`'s `CatalogPrefixContext` additionally takes prefixes *typed into a form but not saved* — the issue create dialog checks numbers against an issue that does not exist yet, so the form is the only place its prefixes can come from. The prefix input sits **in front of** the First/Last range in the issue dialog, where it renders, with the area's prefix as its placeholder.

- A stamp's **subtype** (ADR-0010 §6; #338–#340, #342) is shown wherever stamps are listed or picked — issue tree, flat stamp list, Copies list, pickers — through the shared `SubtypeChip`, and is available in listing texts as `{subtype}`. The collection's **default** subtype renders **nothing**, on both surfaces: it is the row assigned automatically to every new child, so it carries no information the tree did not already give, and badging every variant "Variant" scales noise with the collection. Which subtype is default is already the collector's choice, so that *is* the setting. Read models report the subtype as stored (`subtypeLabel` → `{ name, isDefault }`) and the surface drops the default — except `toTitleCopy`, which drops it *before* resolving the translation so the default never surfaces as a translation gap to fill (#299). The name is user-visible listing text, hence translatable like any other (`StampSubtypeTranslation`, one `name` column — a subtype has no abbreviation). The last subtype saved is remembered per collection (`LS_LAST_SUBTYPE`) and pre-fills the next add, alongside #234's copy defaults.

- Quick-adding a catalog value is one shared dialog (`shared/quick-price-dialog.tsx`) over a `QuickPriceSubject` — a **stamp × condition × certificate**, not a copy. The Copies list, PO intake and sale-lot views pass an `ItemListItem` (it satisfies the shape structurally, a copy carrying its own condition); the Issue list builds one from a stamp-tree node plus the list's **display condition** with certificate = none, matching what the price column renders (#341). `useQuickPriceDialog` returns `{ open, dialog }` and owns the save. The trigger is a **+ catalog value** link in the row's price slot — never a `⋮` entry: pricing belongs where the price is, so every list opens it the same way (#228, #341).

- A picked stamp is carried as `PickedStamp` (`inventory/stamp-picker-shared.ts`) with `catalogLabels` — **prefix-formatted** numbers (`Mi·PL 1B`), one chip each in the summary — never a joined string of raw numbers (#357): three catalogs' numbers side by side read as "1B, 39, 1" and name none of them. Build them with `orderedCatalogLabels` (primary vendor first) at every site, including the edit-mode prefill, which must resolve the vendor map from the **copy's own area**.

- A **child stamp inherits the parent node's year**, not the issue's (#360) — a variant or reprint is dated from the node it hangs under. `StampFormDialog` skips the issue-members query when a parent is prefilled, so the caller passes `prefilledParentIssuedYear`; the Year input is uncontrolled and keyed on the derived default so re-seeding actually reaches the DOM. Root-level stamps still start from the issue year (#70). A child hangs under a node at **any** depth, in the picker as on the Issues list (#401): `SelectableStampNode` gated `+ variant` — and, surviving #239, the *unknown variant* marker — on `depth === 0`, which no rule anywhere backs (the tree is `Issue → X → Xa → Xay → XayI` by design, #54; the server has always accepted any `parentStampId`). Depth is for indentation and nothing else.

- The issue-list stamp tree **opens a parent that just gained a child** (#359). Expansion is derived, never a `setState` in an effect: the panel raises an `ExpandStampSignal` (`{ stampId, nonce }`) and each node compares it against the toggle the collector last made — so a manual collapse sticks, while a *repeat* add under the same parent carries a fresh nonce and opens it again.

- A catalog's numbers on the two dialogs that *generate* stamps are one **spec** field (#452), not a First/Last pair: `parseCatalogNumberSpec` (`src/lib/catalog-number.ts`) splits a comma-separated list and hands each piece to `resolveCatalogRange`, so every scheme #149/#150/#383 added keeps working *inside* a segment. The point is the case one range cannot state — `2895A-2897A, 2895B-2897B`, one series printed in two variants. The **declared series range is derived, not typed**: suffixes dropped, prefix kept, min to max of the bases, so that spec declares `2895–2897` while creating all six stamps. A spec may mix numbering families — `3025-3027, BL48` is a run plus the issue's block — so the declared range is measured over the **basic (prefix-less) numbering** whenever the spec has any, `computeIssueRangeExtension`'s own ranking, and over the first segment's family otherwise; a foreign-family segment still creates its stamp, it just does not widen the range. No number may repeat. **Edit issue keeps First/Last** — there the pair *is* the declared range and nothing is generated — so `parseCatalogNumbers` lives on beside `parseCatalogNumberSpecs` in `src/app/actions/issues.ts`.

- **Auto-creating an issue's stamps** (#70) has no master switch (#451): the per-catalog *Assign to stamps* boxes on the **Add issue** dialog *are* the decision, and `createIssueAction` gates on the presence of any `autoCreateVendor_*` field. They tick themselves off the (uncontrolled) range inputs, re-read on every `formVersion` bump — the primary when its own range can generate stamps at all (parses, ≤ 50), the rest when the primary is on and their span matches it. A box the collector clicked is **pinned** and never auto-set again, so a deliberate choice outlives further typing; #185's on-blur *Last* fill writes the DOM directly, so it bumps `formVersion` itself or the ticks would not follow.

- A **catalog-number chip copies its number on click** (#420, `shared/catalog-number-chip.tsx`), everywhere one is drawn — stamp/issue/copy rows, the pickers, the quick-price dialog. What it copies is narrower than what it reads: the **area prefix stays and the vendor abbreviation goes** (`Mi·PL 200` → `PL 200`), because the prefix is part of the number's identity (#66/#377) while the catalogue is context the collector already has in the field they are pasting into. The rule is pure (`catalogChipCopyValue` from the parts, `catalogChipCopyValueFromLabel` where a surface only carries a formatted label — the pickers' `catalogLabels`, an issue's declared range; a label whose head is not a short letter run is left whole, since eating a multi-word number like `Ark. 103` is the worse mistake). Confirmation **recolours the chip** instead of adding a ✓: these sit in wrapping rows of four or five and a glyph appearing would reflow the line under them. It renders a `<button>`, which is also what keeps it safe inside a click-through row (#374).

- A **missing name prints nothing, not a placeholder** (#535). `StampTitle` (`shared/issue-view.tsx`) draws the stamp name on the issue tree and the picker; a stamp without one now renders an empty string rather than "(unnamed)", and its date loses the comma that was separating it from the absent name. A stamp is read by its catalog number, which the detail line under it already carries, so a column of "(unnamed)" was the same non-fact repeated down every row. The flat stamp list already worked this way (`stamps/stamp-row.tsx` omits the whole name line). This is about **display**; a `?? "(unnamed…)"` in a *label* — a delete confirmation, a dialog title, a picker's summary line — stays, because a sentence naming the thing it is about cannot have a hole in it.

- The issue's **stamp tree is ordered by hand** (#549, `IssueMember.sortOrder`). Until it existed the tree had no `ORDER BY` at all, so this is the first time the order is *stated*; existing members were seeded in **insertion order** (`stamp.createdAt`), which is what the default has to be — a collector who has arranged nothing should see the stamps in the order they were added. The value is only ever read **within one sibling group** — the issue's roots against each other, one parent's variants against each other, and the two never compared — so a reorder densely renumbers the single group it was handed and leaves every other group's values alone, and a value shared across groups is not a collision. That is also why an append is `max(sortOrder) over the whole issue + 1`: one number is past every group at once, and it is the right answer before the newcomer's parent is even known. Both readers of `MEMBER_SELECT` must agree — `listIssueMembers` orders in SQL, `toIssueData` through `orderIssueMembers`, both `sortOrder` then `stampId`, because the select is `as const` and a readonly `orderBy` is not assignable to Prisma's input type (the same reason `checklists` is ordered in the mapper). Arriving stamps land **at the end, keeping their own relative order**: `moveStampNode` and `mergeIssues` both re-stamp what they move, a position being a statement about *one* issue's tree and nothing a stamp carries between them. The pure half is `src/lib/issue-member-order.ts`, and its one real rule is that a reorder names a **complete** sibling group: the tree can be narrowed by #531's checklist filter, and a drag inside a narrowed tree would move a stamp past a sibling that was never on screen — which is why the UI puts that filter away while reordering *and* the server refuses a partial group, one being a courtesy and the other the guarantee. `effectiveParentId` mirrors `buildStampTree`'s roots rule (a variant whose base belongs to another issue is drawn as a root, so it is grouped as one), or the order would be validated against a grouping nobody can see. The UI is `shared/stamp-tree-reorder.tsx` over #306/#313's `useReorderList`: reordering is **a mode, not an always-on affordance** — thirty rows each carrying a permanent grip read as a list you are expected to be rearranging, which is not what looking a number up is — and the toggle sits at the **foot** of the tree beside **+ Add stamp**, both being things done to the tree as a whole rather than to a row in it. `StampTreeGroup` is a component rather than a hook call per level because a group needs its own `useReorderList` instance and the groups are found by recursion; it takes a `renderNode`, so the list row's editable node and the detail page's linked one stay two different rows on one wiring. The drag is optimistic and rolls back on refusal, a drag that snapped back a third of a second later reading as a drag that did not take. There is deliberately **no "custom order" sort on the flat Stamps list**: it spans issues, so there is no single sequence to sort by, and the tree — which has never had a sort switcher — simply *is* the order.
