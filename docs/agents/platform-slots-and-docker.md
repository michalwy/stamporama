# Platform: worktree slots and `docker` on the PATH

Per-worktree port slots (local-only) and why `docker` missing from a PATH is not `docker` missing from the machine. Split out of [`platform.md`](platform.md) (#2700).

- *(Local-only, like the next four bullets: a cloud thread's fresh clone is the main worktree and so slot 0, with its VM to itself — #2687.)* **Every host port this project pins comes from a per-worktree *slot*** (#781). Two sessions in two worktrees could not both run the suite before this: `docker-compose.e2e.yml` had no `name:`, so Compose named the project after the directory — two directories, two projects, both binding host 5433, and the second `docker compose up -d --wait` dying on `port is already allocated`. A slot is a small integer, and slot N shifts every pinned port by 10 × N: the app container's 3000, a bare `next dev`'s 3002, the e2e database's 5433. It also names the e2e Compose project `stamporama-N`, so the project follows the slot instead of the directory. **The main worktree is slot 0 and writes nothing down** — that is today's numbers and today's project name exactly, which matters because it is the path the project is actually used on. Linked worktrees take 1, 2, 3… on first use. `scripts/dev-slot.sh` resolves it, `pnpm slot` prints the table — and only prints it, see below — and `pnpm test:integration` / `pnpm e2e:db:reset` go through `scripts/e2e-db.sh` — which is why `localhost:5433` no longer appears three times in `package.json`.

- **A slot is reclaimed by the worktree going away.** There is deliberately no shared registry: a slot lives in that worktree's own untracked `.env.slot`, and allocation reads those files through `git worktree list`. A directory that is gone therefore holds nothing, and no table exists that could outlive the thing it describes — which is the failure this design is avoiding, because a port held by a worktree nobody removed surfaces weeks later, in an unrelated session, as `port is already allocated` with no visible cause. `pnpm slot release` frees a number without removing the worktree, and writing `STAMPORAMA_SLOT=` into `.env.slot` (or the environment) pins a particular one. **`package.json` declares that script as the path alone, with no verb of its own, and `dev-slot.sh` defaults to `show`** (#913): pnpm *appends* a script's arguments rather than inserting them, so the `show` that used to be written there occupied `$1` and pushed the caller's verb into `$2`, where nothing read it — `pnpm slot release` printed the table and released nothing, for as long as the command has existed, and two sessions reported a slot freed that was still held. The default has to be `show` rather than the older `env` for bare `pnpm slot` to keep printing the table as the bullet above says it does; nothing depended on the old default, because `scripts/e2e-db.sh` is the only caller that wants the `export` lines and it names `env` explicitly. The *container* is reclaimed with the slot for the same reason the project name is derived from the slot: a container left behind by a removed worktree is the one Compose reuses when the next worktree takes that number, rather than a stranger holding the port. What that does not tidy is a slot nobody claims again — `pnpm slot` shows who holds what and `pnpm e2e:db:down` stops one, as does `docker compose -p stamporama-N -f docker-compose.e2e.yml down`.

- **`pnpm slot` reads; only `env` and `number` allocate** (#922). The table used to resolve the current worktree's slot before printing it, so that it showed the number the worktree *would* get — a fair answer while one session ran at a time, and a trap once the end-of-task drill became `pnpm e2e:db:down && pnpm slot release`: the natural next act, looking at the table, took the number straight back. So `show` writes nothing, and a worktree without a slot — this one included — reads `(no slot yet)`. The number is taken by the first thing that needs a port, which is any `scripts/e2e-db.sh` command (through `env`), or `scripts/dev-slot.sh number` asked outright. `pnpm slot release && pnpm slot` therefore leaves the slot released.
- **An exhausted pool stops the command before anything exists** (#1203). With 1–9 all held, `env` and `number` exit non-zero with a message that names the exhaustion and the way out — `pnpm e2e:db:down` then `pnpm slot release` in a worktree that no longer needs its slot, or removing that worktree — and write no `.env.slot`; `scripts/e2e-db.sh` stops on that before starting any container. It used to carry on, and how it did is the reusable part: **bash switches `set -e` off inside a command substitution, and `eval "$(…)"` succeeds on empty text.** `resolve_slot` runs inside `$(…)`, so the allocation's failure did not stop it — it wrote `STAMPORAMA_SLOT=` and printed nothing — and the `eval` in `e2e-db.sh` evaluated that nothing successfully, so the suite started a Compose project named `stamporama-` on slot 0's port 5433, the main checkout's, and failed only at `prisma migrate deploy` with an unreachable database that pointed nowhere near the cause. Both scripts now propagate a failed substitution with an explicit `|| exit 1` and capture the `env` output before evaluating it; `set -e` is not trusted across a `$(…)` boundary in either.
- Two things sit outside the slot on purpose. `.claude/` is untracked and per-worktree, so `.claude/launch.json` cannot interpolate anything and cannot follow the slot: a worktree that starts a dev server through it sets that file's port by hand to the number `pnpm slot` prints. And `max_connections=300` on the e2e database stays where it is — it was sized for **one** suite (workers × Prisma pool), and slots give each worktree its own database precisely so that budget is never split between two.

- *(The OrbStack PATH below is local-only; a cloud thread's VM has `docker` on its PATH, and whether its daemon is running is the environment's setup, #2688 — #2687.)* **`docker` must be on the PATH `pnpm test:integration` is run with, and *absent from this PATH* is a different claim from *not installed*** (#933). The two are indistinguishable from inside a session and were confused four times in two days: two sessions checked Docker Desktop, colima, podman, `~/.docker/bin` and `~/.rd/bin`, found none of them, and reported that the machine had no Docker. Every check was correct and the conclusion was false. **The cost is never the failed command; it is the suite that stops being run** — this file's own rule sends a session to `pnpm test:integration` before a schema or domain-logic change, and a session that believes the runtime is missing does not verify some other way, it stops verifying, honestly, and CI sees those cases first.

- **The reusable half is *why* the two claims come apart: a session does not compute its PATH, it inherits it**, from whatever process launched it — so it can be running an environment older than the machine's own configuration. That is exactly what happened here, and it is measurable rather than inferred. The user moved from Docker Desktop to OrbStack on the evening of 2026-09-07 and `~/.zshrc` gained `export PATH="$HOME/.orbstack/bin:$PATH"` as its **line 17**, at an mtime of `2026-09-07 20:03`. A session's PATH here begins `antigravity-ide`, then `postgresql@18`, then `nvm` — `.zshrc` lines 15, 12 and 10, in the order three unconditional *prepends* produce — and does not contain line 17 at all. **If the rc file were simply unread, the first two would be missing too**; a clean non-interactive `zsh -c` carries none of the three, which is what unread actually looks like. So the file was read, by something that started before line 17 existed, and the fix for that is restarting whatever launches sessions rather than anything in this repository. `scripts/e2e-db.sh` therefore **requires** `docker` and does not go looking for it: the guard is the message, which names the requirement, prints the PATH it actually has, and says how to tell a stale environment from a missing install. It runs before `scripts/dev-slot.sh env`, because resolving a slot *allocates* one and a run about to die for want of a runtime should not take a number with it. **Nothing checked in reaches into a home directory or an app bundle for a binary** — a candidate-path search was written, and was withdrawn by the user on 2026-09-08 on the grounds that it makes this repository carry one machine's install layout; the shape of that mistake is the same one the issue is about, one level up. `scripts/install.sh` and `scripts/update.sh` are unaffected and keep their own preflight: they are the `curl … | bash` self-hosting scripts, they run on somebody else's server, and `docker info` and `docker compose version` are the right questions there. `scripts/dev-slot.sh` invokes no container command at all.
