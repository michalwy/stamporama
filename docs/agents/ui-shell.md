# Dialogs, Sidebar & App Shell

Dialog primitives, the escape stack, sidebar structure, config screen placement, notifications.

- Modal dialogs for list actions (add, edit). Build with shared `src/app/dialog-shell.tsx` primitives — do not duplicate dialog header, close, viewport constraint, or height behavior. A dialog rendered **from inside a row** must portal to `<body>` whenever any ancestor makes its own stacking context — a transform-centred dialog panel, but also a plain `opacity` below 1, which is how an ended auction row is muted (#354). Inside one, `DialogShell`'s z-index only ranks the dialog *within that row*, so the sticky toolbar and the app header paint straight over it.

- **Dialog buttons are one shape** (`baseBtn` in `dialog-shell.tsx`) and two details keep a footer's buttons the same **height**: `inline-flex` centring, because `Icon` is an inline-block with a `vertical-align` below the baseline and so stretches a button's line box — an icon-bearing *Discard* rendered taller than the plain-text primary beside it — and a **transparent** 1px border, so the borderless primary matches the secondary/destructive whenever content exceeds `minHeight`. Deliberately **no `gap`**: call sites write `<Icon /> Label` and that literal space is their spacing. `DialogActions` groups its footer **by role** — the other ways out (a step back, an alternative outcome, a control qualifying the action) in `leading` on the left, cancel and the action on the right, each group tight within itself — rather than letting `leading`'s bare `margin-right: auto` set the spacing and a four-button footer read as four unrelated buttons.

- **Escape closes one surface**, the topmost (#361). Every dismissable overlay registers with `useEscapeLayer` (`src/app/escape-stack.ts`); the stack is ordered by mount, which *is* the order surfaces were opened in, so the last entry is the only one that hears the key. `DialogShell` and `PhotoLightbox` register for you — a nested dialog, picker or lightbox therefore needs no Escape handling of its own. Do **not** go back to a document-level capture listener with `stopImmediatePropagation`: that only wins by registration order, so the *outer* dialog ran first and closed itself out from under the lightbox that had just opened above it. The shared listener deliberately does not stop the event, so popovers that are not layers (row-action menus, autocompletes, the translation popover) keep their own listeners and their own behavior; a dialog that must yield to one steps out of the stack with `dismissable={false}` (compose-set while the gap popover is up).

- Sidebar sections follow **what the collector is doing**, not what the data is: `Catalog`, `Collection`, then trading split by direction into **Selling** (Offers, Sales) and **Buying** (Purchases, Auctions) — selling first, because buying is what a collection is built from but selling is what is worked on daily, and the section reached first should be the one opened most. Auctions is a **`NavGroup`** (#376) — an icon'd heading over two indented entries, *Lots* and *Sales*. They are two entries because they answer different questions on different days ("what do I bid on next", across sellers, versus "what do I owe for this parcel"), and reaching the second only through the first made the daily screen double as a doorway; they are *nested* because they are two views of one subject rather than two parts of the collection the way Purchases and Offers are. The group row is a **heading, not a link**: pointing it at one of its own children would duplicate that child and light two rows at once. Children take no icon — the group's names the subject and the indent says who belongs to it. `isActive` takes an `exact` flag for the pair: every sale route lives under `/auctions`, so `startsWith` would light *Lots* on a sale. One `Trading` heading over five entries meant reading the whole list to find either half. **Contacts belongs to neither** — the same address book holds the house you bid with and the marketplace you list on — so it trails both, set apart by `NavItem`'s `spacedAbove` rather than by a heading over a single item.

- Config screen placement: **catalog taxonomy** that is set up once (Areas, Catalogs, Conditions) lives in **Settings** tabs; **operational data** touched routinely (Locations) gets its own **Collection** nav page. Both reuse the same adjacency-list tree pattern (`buildTree`, `*-tree-select.tsx`, `RowActionsMenu`) — mirror `areas-panel.tsx` / `locations-panel.tsx` rather than reinventing tree/list/dialog scaffolding.

- The sidebar's **top row is identity, not a control**: the collection's initial and name, with the notification bell beside it. There is no collection switcher — changing collection is rare, so it is an **All collections** entry in the footer beside Settings, and a dropdown was a permanent control in the chrome's most prominent row for an occasional act. The collection layout therefore no longer loads the owner's other collections on every screen.

- The **notification centre** (#367) is a bell **in the sidebar's top row**, beside the collection name — the app has no top chrome, and a badge in the footer beside Sign out is a badge nobody sees. An **icon with a count bubble**, never a nav entry: it is not a destination, and a full-width labelled row put a permanent extra item in the list of places to go for something that is usually empty. The bubble sits *on* the bell rather than beside it, so a count appearing does not shift the row's other contents; the switcher button gives up its own bottom border to the row that now holds both. It **reports nothing of its own**: every group is an existing derivation read through the same exported function its own screen reads it through (`listAuctionLots` at the lots screen's own `closing` windows; the needs-action SQL, ADR-0013 §4), so the panel and the screen its "N more →" lands on cannot disagree about what "closing today" means. Sources are **providers, not groups**, in `src/lib/action-items.ts`: a provider returns one *or more* groups, which is what lets the two offer groups come out of one read — they are one flag split by *reason* (#167's sold copy vs #215's live bid), and the derived offer label they need would otherwise pay for the area tree twice (#379). Adding a source is one entry in `PROVIDERS`; the route handler, the badge and the panel are written against the shape and never against the list. `NeedsActionRow` therefore carries `soldCount`/`biddingCount` **beside** the untouched `deadCount` — a copy dead both ways is one dead copy and two problems, so they are counted separately rather than derived from one another, and the badge's total is the **rows** under it for the same reason. A group carries a **severity** (`critical` / `warning` / `info`), which is what decides both its tint and the panel's reading order — graded by **consequence, not by subject**: a possible **double sale** is `critical` (both offer groups: one piece of stock committed in two places, costing money and a rating, undoable only by the collector), a **deadline that can still be met** is `warning` (a lot closing today), and **bookkeeping that never fixes itself** is `info` (an ended lot with no outcome). It is the lot list's own rule — colour means *act now*, which is why an ended lot there is muted rather than reddened — applied across sources. Provider order is only the tie-break, so a source's place in `PROVIDERS` can never outrank a worse problem from another one. The badge is tinted by `ActionItemsResult.severity` — the **worst** thing waiting, never the count, or three ended lots would outshout one double sale — and that grade is resolved **server-side** so the bell and the panel cannot grade one list two ways. In the panel the **heading** carries the tint, not the rows: a list of names is read, and tinting every line makes it harder to triage rather than easier. An item carries its instant as ISO and the client formats it (`formatRelative`): "in 3 hours" needs the browser's clock and locale, and a server-rendered string goes stale while the panel sits open. Hrefs are **collection-relative** — the slug is a routing concern and the domain layer only holds the id. It **refreshes off the query cache itself**: the bell subscribes to `getQueryCache()` and re-reads (debounced) whenever any *other* key is invalidated, because every mutation here is a server action followed by the screen invalidating what it shows — so recording a lot's outcome empties a group and drops the badge at once, without a single mutation site knowing the panel exists. Wiring each source's mutations in by hand would undo the registry: a new provider would mean hunting down every action that could feed it. The interval and the focus refetch stay as the backstop for anything that refreshes by `router.refresh()` alone. Nothing is acted on in the panel: an action taken in a popover is one taken without the context that makes it the right one. It is a **popover, not a layer**, so it keeps its own Escape/outside-click rather than joining the escape stack (#361), and it **portals to `<body>`** — the sidebar scrolls, so it sets `overflow-y`, and a box that is not `visible` on one axis is not visible on the other either. `QueryProvider` moved up in the collection layout to wrap the sidebar too, so the shell and the screen share one cache.

- Tabs inside dialogs are visual grouping only — one logical save action. Dialog height determined by default tab; switching tabs must not change height. Body scrolls, header/footer fixed. The default panel therefore stays **in flow** and every other one overlays it (`position: absolute; inset: 0`, own `overflow-y`), hidden with `display: none` and **never unmounted** — a hidden panel's fields must still reach `FormData`, since a tab is grouping and not a second form. The contact dialog (#403) is the case that forced this: it grew a **Platform** and an **Auction defaults** tab beside **Contact** because the platform role alone now carries six groups of settings, and one column of them was a wall. Which tabs exist follows the **roles ticked**, so a plain address-book contact still sees no tab bar; unticking a role *does* unmount its panel, deliberately, because that is how the action learns to clear what the role carried. Which tab is shown is **derived** from the requested one against the roles present — never a `setState` in an effect — so unticking Platform while standing on its tab falls back on the same render. A `required` field on a hidden tab is not focusable and the browser refuses the submit without saying why, so it carries an `onInvalid` that returns to its own tab.
