# Release Versioning

- Never assume the last released version from memory or from local git tags — always run `gh release list` fresh, since a release agent can tag a new version mid-session.
- When asked to cut a new version, first review the changes merged since the previous released tag, then decide patch vs minor (`feat:` commits -> minor, `fix:`/`chore:` only -> patch).
- Never bump the major version unless the user explicitly asks for a major bump.
- **The version bump cannot be pushed to `main`.** `main` is protected with no bypass for anyone — a pull request is the only way in (`collaboration.md`). The sequence is:
  1. Branch from `main`, commit the bump as `chore: bump version to X.Y.Z`, push the branch and open a pull request.
  2. `gh pr merge --rebase --auto` — auto-merge is enabled on the repository, so GitHub merges the moment the four required checks are green and the branch is up to date. Nothing else is in the pull request, so this is the whole of the wait.
  3. **Fetch `main` and tag the commit that landed there** — `git fetch origin && git checkout main && git pull --ff-only`. Rebase merge rewrites the commit, so the SHA on your branch is *not* the SHA on `main`; tagging the branch commit would tag something that is not in `main`'s history at all. Tag refs are outside the ruleset, so pushing `vX.Y.Z` and force-pushing `latest` still work as before.
- **The tagged commit always has a completed CI run of its own to read.** Runs on `main` and on release tags are never cancelled by a later push (dc4577f); before that fix, seven of forty runs had been cancelled and every one was on `main`, including the `chore: bump version to 0.129.0` commit that v0.129.0 was tagged from. This used to depend on the release session remembering to wait for `main`'s run before tagging. It no longer does — but still read the run, because "never cancelled" is not "green".
- After tagging and pushing a new version, always create a GitHub Release (`gh release create vX.Y.Z --title vX.Y.Z --generate-notes`) automatically.
- After creating the GitHub Release, move the `latest` git tag to the same commit and force-push it: `git tag -f latest vX.Y.Z && git push origin latest --force`.
- If, after reviewing the changes since the previous tag, a new release does not seem warranted, ask the user for confirmation before deciding either way.
- Always write a proper, human-readable release description instead of relying on bare `--generate-notes` output. Group changes into sections (e.g. Highlights/Fixes/Other), summarize each commit/PR in plain English with its reference number, and keep the auto-generated "Full Changelog" compare link at the end.
- Every release tag also publishes the Assistant extension, **when the `CWS_PUBLISH_ENABLED` repository variable is `true`** — CI packs a store ZIP stamped with the release version and submits it to the unlisted Chrome Web Store listing (#288, ADR-0017). The switch exists because the store rejects an upload while a previous version is still in review; when it is off, releases proceed and the extension is submitted later by flipping it back on. A green job means *submitted for review*, not live, so a release note should not promise the extension is already updated — and it may equally mean **nothing was submitted**: the job asks the store which version it already holds (published or in review) and skips when `extension/` has not changed since that release's tag, because most releases touch nothing there and every submission costs a review. So the extension's live version legitimately trails the app's; only mention it in a release note when the job actually submitted something.
- In backlog-review sessions, only suggest a release — do not prepare, tag, push, or create it yourself. Release preparation is handled by a separate dedicated agent, and a release session changes nothing else, so that its transcript reads afterwards as the record of one release (`collaboration.md`).
