# Colnect List Sync

Keeping a Colnect list in step with this collection: what a list is configured to mirror, how an export is held, and what a difference between the two sides is. The track is #684–#690; the foundation (#684), the import (#685), the report screen (#686), the
local-side fixes (#687), the wish-list adoption (#688) and the write back to Colnect (#689) are
built.

- **The loop is export → load → compare → fix, because Colnect gives nothing else** (#684). There is no API and no import — only an **Export list** button producing a CSV, the very file `colnect-list-rules.ts` already reads for trades (#645). So synchronisation cannot be a push and is not attempted as one: an export is loaded here, the two sides are compared, and the collector fixes whichever side is wrong — this one through ordinary screens (#687, #688), Colnect's through the browser extension acting on the page (#689). Nothing in the **app** ever calls Colnect — the server holds no Colnect credential and is given none — which is why the report proposes rather than performs, and why carrying its proposal out is the extension's job, in the collector's own browser under their own session (#689, ADR-0042).

- **The join key is `Stamp.colnectId` (#247), and a stamp without one is not comparable.** That is a third state, not a difference: it is neither *on both sides* nor *missing from one*, because nothing was ever asked. A report that counted unlinked stamps as missing on Colnect would say the collection is thousands of items out of step when it is only partly linked, which is a statement about the Assistant's backfill (#250, #280) rather than about the list. Filling those ids in is the Assistant's job and stays there.

- **Scale is the constraint that shapes everything here.** The account read on 2026-08-22 held Collection 5,346 · Swap 3,119 · Sell 3,419 · **Wish 25,145**, plus a dozen custom lists. Any design that assumes a short report is wrong: the snapshot is a table rather than a parsed file kept in memory, the report is a screen with filters rather than a list, and a bulk adopt (#688) exists precisely because twenty-five thousand rows cannot be worked through one at a time.

- **`sourceOfTruth` is a per-list column because Wish disagrees with the other three.** Collection, Swap and Sell are maintained here and published there, so what is here is right and an item only on Colnect is proposed for removal *there*. Wish is the opposite: it is years of clicking *I want this* on Colnect against far fewer `Want` rows, so trusting this side would open with a proposal to delete twenty-five thousand things — formally correct and useless (#688). Two lists in one account genuinely have different answers, which is why this is a column and not a setting.

- **`lt` is a plain integer, not an enum.** Colnect's list ids are visible as `div.ibox_list[data-lt=N]` on every item row — 2 = Collection, 3 = Swap, 4 = Wish, 5 = Sell — and a custom list carries its own number in its `custom_list__N` URL (11, 15, 16 …). Settings offers only the standard four, because Colnect states no *name* for a custom list anywhere a file or a row can be read, so offering one means asking the collector to type it — a screen rather than a constant. The column already holds them, so that screen needs no migration.

- **The settings panel is the condition mapping's shape (#404), not the catalog mapping's (#248)** — every standard list is listed, configured or not, because the set is Colnect's and is fixed; there is nothing to create and nothing to delete. A row appears in the database on the **first touch** of any of its controls, seeded with the built-in defaults plus the change, so ticking *Sync* alone yields a list mirroring what it obviously should. `enabled` off and no row at all are both "not synced" and differ only in whether the setup was kept. One write per control, no draft, no Save.

- **A snapshot is one per mapping and is replaced by the next import** (#685). A history of exports answers a question nothing asks: the report is always about the list *as it stands*, and an old snapshot beside a new one is a second answer to "what is on Colnect" that nothing would choose between. The rows are stored already read — `colnectId` out of the row's `Link`, since the export has no id column — with `quantity` and `conditionAbbrev` taken **for that list** out of the positional per-list columns. `(snapshotId, colnectId)` is indexed and deliberately **not** unique: a hand-edited file may repeat an item, and whether that is an error is the import's judgement, not a constraint failure twenty thousand rows into a bulk insert.

- **"Accepted" hangs off the mapping; "done on Colnect" hangs off the snapshot. The asymmetry is the decision.** `ColnectListDecision` is a standing *ignore this difference*, a judgement about this collection, and a judgement does not expire because a file was read again — so it survives a re-import. "Done" (#686) is a *claim about the state of Colnect*, and a re-import reads that state afresh: a row that comes back is a row that was not actually done, and the report must say so rather than remember a claim that turned out false. A decision's key includes its `kind` — `only-colnect` / `only-local`, and since the report `quantity` / `grade`, which a plain string column let it add without a migration — because the direction can flip between imports — an item removed there for a stamp still `forTrade` here becomes the opposite difference — and one acceptance silently swallowing the other is how a report comes to omit something nobody decided about.

- **The source predicates are a named list, not a filter expression** (`colnect-list-sync-rules.ts`). Four of them: `items_in_collection`, `items_for_trade`, `items_for_sale`, `wants_open`. The copy predicates all mean *in hand* — delivered, not disposed — since a copy already sold is not on offer and a Colnect list still naming it is the discrepancy, not an input to it. Wants are not about copies at all, and anything general enough to express both would be a query language sitting in a settings row. The report evaluates them (#686): `colnectListSourceShape` resolves a stored string to *which flag on `Item`* or *wants*, which is the one thing the query needs about a predicate that Settings does not, and it is pure so the mapping from a string to a column is asserted without a database.

- **The import resolves its own target, because the file names it** (#685). Every row of an export carries the lists that stamp is on, and `colnect-list-rules.ts` counts them and names the likeliest — the one the most rows carry, which in an export of one list is all of them. Matching that name against the configured labels resolves the mapping without a question; the picker is a question only where it matches none, which is what a custom list or one renamed on Colnect looks like. The screen also asks **which list's columns** to read where the file names more than one, and that is a second question rather than the same one: a collector may well load the file's `Test Swap FROM` group into the list they call Swap, and a row's `Quantity` / `Condition` groups are positional, so reading the wrong one stores the wrong count and the wrong grade for every row on two lists.

- **A row with no `Link` is counted, not dropped silently** (#685). The id in that URL is the only join key the two sides share, so such a row cannot become a snapshot row — but it was in the file, and a snapshot quietly holding fewer rows than the export would make every count on the report a lie. Same reasoning as `declaredCount`, which is reported against the rows actually read and never enforced.

- **The report is one SQL query, not a diff in memory** (#686, `colnect-list-report.ts`). Wish is 25,145 rows against a few thousand local ones; loading both sides per scroll page would be megabytes a page. One statement full-outer-joins the two aggregates on `Stamp.colnectId`, buckets each row, applies the filters and returns the page; two more group the same relation for the bucket counts and the country facets. Only the page's own stamps are then hydrated through Prisma. The relation keeps its `in-sync` rows and the callers drop them, so *what a difference is* is spelled once.

- **A row is filed under exactly one bucket, quantity before grade** (#686). A stamp can differ in both, and the row prints both sides' quantity *and* grade either way — but the bucket is the `kind` an *ignore* and a *done* are keyed by, and a row in two buckets would let one acceptance swallow the other, which is the very thing #684 made `kind` part of the key to prevent. Correcting the quantity and re-importing brings the row back under **Grade**, which is correct: it still disagrees.

- **Grade is compared only where the local side agrees on one** (#686). Colnect holds one grade per list entry and this side holds N copies; three copies — two MNH, one used — have no honest single answer, and a precedence rule would quietly under- or over-state the offer. The same sentence reads a want: one naming several acceptable conditions states no grade, and a stamp whose open wants disagree states none either. An unmapped condition (#404) is compared against nothing rather than guessed at. **Quantity and grade *are* compared for a want-backed list** (the collector's call): the local count is the number of open wants, normally one.

- **Country is one string with two sources, and no mapping is invented between them** (#686). Where the row has a local side it is the stamp's primary area **path**, built in the query by a recursive CTE off the same separator `buildAreaPath` prints with; where it does not, it is the export's own `Country`. The path rather than the leaf because a collection files Poland under `Poland › People's Republic` and a row naming only the leaf is a row about a country it never states — and *in the query* because that one string is the row's label, the facet and the filter's value at once, so deriving it on the client would leave the chips saying one thing and the rows another. Translating Colnect's country names into this collection's area names would be a third mapping table nobody asked for, and a wrong one would silently hide rows from a filter.

- **A stamp with no name of its own is named by its issue, and `(unnamed)` is not a name** (#686). Most of a Colnect list is unnamed stamps, and a column of italic placeholders identifies nothing; the issue and its year are what the collector recognises, so they stand in the name's slot — in the placeholder's own muted italic, because an issue is not the stamp's name. `StampIdentity` grew one optional prop for it (`unnamed`) rather than the report drawing its own identity line: the chips, the name and the Colnect chip are one thing everywhere else, and a second spelling of them here is how a screen starts formatting stamps its own way. Where the stamp *has* a name the issue moves to the muted line beside the country — the fact is printed once, in the most prominent slot it can have.

- **Link sits beside Search on the report, which is the offer card's pairing (#423) reused** (#686). The whole `not-comparable` bucket is stamps with no item-ID, so the report is exactly where that gap is noticed — and the match handoff already existed, on its own element, with a doorbell that fires for *any* match written to this instance. So the report re-reads itself when one lands, whether it started the handoff or the collector matched a Colnect page from the toolbar. Beside rather than instead of Search: a browser with no Assistant still has the search, and the button is absent — not disabled — where the extension is not scripting this origin. Two elements rather than one on this screen, because an answer about a match must not land where an apply run's progress is read.

- **`ColnectListDoneMark` is a table and not a column, for the asymmetry #684 stated.** It hangs off the **snapshot** and cascades with it, so a re-import clears every claim; `ColnectListDecision` hangs off the mapping and survives. A "done" is a claim about *Colnect's* state that only a fresh export can check — a row that comes back was not done — while an *ignore* is a judgement about this collection that no file can expire. `not-comparable` rows can carry neither, and cannot: both are keyed by a `colnectId` those rows do not have.

- **A list with no snapshot gets the import offered, not a report drawn** (#686). Comparing against an empty Colnect side would announce that the whole collection is missing from the list — formally what the query says, and a lie about what was checked.

- **A row carries its *candidate* as well as its local side, and they are different questions** (#687). The report's local side is narrowed by the predicate, so an `only-colnect` row has none by construction — which says nothing about whether the collection holds the stamp. It very often does, untagged, and that is exactly the row a local fix acts on. `candidateStampId` answers *which stamp is this Colnect item here*, predicate or no predicate, and `candidateCopies` how many copies a *set the flag* fix would touch. It changes no bucket; `Stamp.colnectId` gained an index for it, since #688 asks the same question five hundred rows at a time.

- **Which fixes a row admits is one answer, in the pure rules module, asked twice** (`colnectLocalFixesFor`, #687). The `⋮` menu is a client component and asks it to decide what to draw; `colnect-list-fix.ts` asks it again before writing. A menu offering a fix the write then refuses is the drift a shared answer prevents — and it is why the vocabulary lives beside the buckets rather than beside the Prisma calls. A fix a row does not admit is **absent** from the menu, never disabled: a list of greyed-out entries on every row is noise, while the one disabled entry that menu already had is about a row with no identity at all, which is a different sentence.

- **A fix re-resolves from the live predicate and names what it will touch.** Nothing is taken from the request but the row — list, Colnect id, bucket. The copies are worked out again at write time, because the row was rendered from a read that may be seconds old and the report's promise is that a fix acts on what the predicate holds for *now*; the preview is a separate call for the same reason. And it lists them by copy number: several copies of one stamp qualify routinely, and *unflag this stamp* silently meaning *unflag four copies* is how a report loses trust. A fix writes nothing else — no done mark, no decision — because the row leaves the report on the next read for the only honest reason, that the predicate changed.

- **Grade admits a fix on a want and never on a copy** (#687, the collector's call). A want's accepted conditions are a statement of intent and rewriting one is reversible; a copy's condition is a judgement about the physical piece in hand, and a line on a Colnect list is no evidence about it. Quantity admits none on either — a count is corrected by adding or removing copies, which is the inventory screen's work. The reverse read of `ColnectConditionMapping` is the direction that can fail (the unique is on the condition, so two may claim one grade); where it does not answer exactly one, the fix refuses rather than picking, which is #686's grade silence applied to a write.

- **The wish-list adopt runs in capped passes, and the pass is its own resume record** (#688). Twenty-five thousand rows cannot be walked one at a time, and they cannot be swept in one request either — the resolution is minutes of work at that scale and a request that long is lost whole by a reload. `COLNECT_ADOPT_PASS_SIZE` rows per call, in the report's own order, under the screen's own filters. Nothing stores a cursor because nothing needs to: an adopted row leaves the `only-colnect` bucket, so the next pass starts where the last stopped by construction, and running the same pass twice writes nothing twice.

- **The adopt resolves through the Assistant's matrix, in `dryRun`, and takes only `auto`** (#688). `Stamp.colnectId` first — free, the report already looked it up — then `matchColnectItems` over the export's own catalog codes, read by the export's own parser (`parseColnectCatalogCodes`). The dry run is the point: adopting a wish list must not write thousands of Colnect ids onto the collection, because learning an id is a deliberate act against a page the collector is looking at (#250). A `needs-confirm` is a question, and answering hundreds of them in bulk is the very thing that matrix exists to prevent. **A row resolving to no stamp is an outcome, not an error** — counted, reported, left on the report; on this list that set is the largest number the preview shows, and it is the honest one.

- **`alreadyWanted` is rarer than it sounds, and is counted over rows.** A stamp whose own Colnect id is on the export and whose want is open is *in step*, so it never reaches the bucket at all. What does reach it is a row the matcher resolved to a stamp wanted under a different id, or under none — which is why the count exists and why it is per row rather than per stamp: it answers *why did five hundred rows write forty*.

- **Writing to Colnect is a step change with an ADR of its own** (#689, ADR-0042). Until it, the app only ever read Colnect. What is written is `POST /item/col`, `act=check`, **membership only** — the same endpoint carries quantity, grade and both note fields, and none is touched, because the local side often has no single honest answer to give (which is exactly why the grade comparison stays silent). The authority is the collector's own session cookie on a colnect.com page: the write happens in the **content script**, not the service worker, because the call is authenticated by cookie alone with no CSRF token and so has to be same-origin — and because a worker quietly posting to somebody else's site with their cookies is a far wider capability than a page doing what its own checkbox does. `platform/colnect/list-write.ts` is the only place that builds the request, pure and unit-tested, so an undocumented endpoint's shape is a failing assertion rather than three thousand silently wrong writes.

- **Removals are guarded by the export's age; additions are not** (#689). They are not symmetrical acts. An addition is taken on the strength of the **local** side, read this second: the collection holds it, so the list should name it. A removal is taken on the strength of the **file** — and if that file is a fortnight old the collector may well have added the item on Colnect since, deliberately. So a worklist older than `COLNECT_APPLY_MAX_SNAPSHOT_AGE_DAYS` keeps its additions, drops its removals, and says so in a sentence naming the import as the way through. The age is Colnect's own `exportedAt` where the preamble gave one: a file exported in March and loaded this morning is three months old.

- **The worklist is the report's own relation, projected to ids** (`listColnectReportKeys`, #689). The page hydrates stamps because it is drawing rows; a Wish worklist is tens of thousands of ids and no pictures. Same statement, same filters, same idea of what a difference is — a second spelling here would be a bulk write acting on rows the screen never showed. Rows already put away are excluded, which is the same rule: a run carries out what the screen shows.

- **What lands is marked done as it lands, in small batches.** The claim is the ordinary one (#686) and dies the ordinary way — it hangs off the snapshot, so the next import checks it against a fresh reading of Colnect. Batched because a run paced at one write every 1.6 seconds must not open a second connection beside each of them; *small* batches because a crash mid-run has to leave the report describing exactly what got through. A `changed` item (Colnect's `410`) is **not** marked: it is one Colnect no longer holds in the shape the export described, and claiming that fixed would be a lie the next import would catch.
