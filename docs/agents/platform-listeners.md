# Platform: `MaxListenersExceededWarning`

How to read the warning, how to find the adder, and what #1123 found. Split out of [`platform.md`](platform.md) (#2700).

- **A `MaxListenersExceededWarning` is not a measurement, and reading it as one sends you after the wrong thing** (#1123). `EventEmitter._addListener` sets `warned = true` the first time a count passes the limit, so a given (emitter, event name) warns **once**, and the number it prints is always `maxListeners + 1`. A stream that goes on to collect 500 listeners logs the identical message as one that stops at the threshold and never speaks again. **Every count quoted in this bullet and the next is 11, because the whole of #1123 was diagnosed against Node's default of 10 — and since #1137 this project no longer runs on it.** `src/lib/max-listeners-rules.ts` raises `EventEmitter.defaultMaxListeners` to **20** at the server's single entry point, so in a running server the number is **21** and a warning at all means something crossed twenty, which nothing measured here does. Read the elevens below as the arithmetic rather than as what this app now prints. Two consequences, and the first is the one that cost a session: **no volume of production logging can tell a bounded fan-out from a leak**, because the count in the message cannot climb — so *"every line says 11, therefore it is bounded at 11"* is an inference the instrument cannot support, and 11 is a floor rather than a bound. And **repeating warnings mean many emitters rather than one growing**: each line is a different object crossing the threshold for the first time, so the rate tracks how often that object is *created* — per request, per read — rather than uptime. **And the mirror of that is the half everyone misses: where the count is present it is a floor, where a warning is *absent* it is a ceiling.** Silence about an event name means ten or fewer listeners, never none. A threshold-crossing indicator is not a measurement in either direction, and reading it as one has now gone wrong three times on one issue — *always 11 so it is bounded*, *bounded so it is harmless*, and *no `end` line so no `end` listener* — the third by the author of this bullet, one commit after writing it. `tests/unit/max-listeners-warning.test.ts` pins both directions, because both are Node's behaviour and neither is ours; `node` is on the never-alone list in `renovate.json`, so a bump reaches a person, and that suite is what gives them something to read.

- **The emitter's name in that warning is exact, and it is the cheapest discriminator there is** (#1123). Node renders it with `inspect(target, { depth: -1 })`, so a subclass prints under its own name: `[PassThrough]` is a plain `PassThrough` and is **not** `@google-cloud/storage`'s `PassThroughShim`, which prints `[PassThroughShim]`. That one observation ruled the SDK's own download stream out of #1123 before any of its code was read, and it rules candidates out far faster than tracing them in. The filesystem storage backend is out on a plainer ground — `createReadStream` returns a `ReadStream`, so that path constructs no `PassThrough` at all.

- **Which events a warning names is a signature, and it identifies the adder faster than any grep** (#1123). Measured against this tree's own Node and react-dom rather than reasoned about, one call each on a fresh `PassThrough`:

  | call | registers |
  | --- | --- |
  | `finished(p)` — any options, `readable:false`/`writable:false` included | error, close, **end, finish** |
  | `Readable.toWeb(p)`, `new Response(p)` | error, close, **end, finish** |
  | `src.pipe(p)` (`p` as destination) | error, close, **finish, unpipe** |
  | `pipeline(…, p, …)` | error ×3, close ×3, **end, finish** |
  | React's `renderToPipeableStream().pipe(p)` | error, close, **drain** |
  | a hand-written `p.on('error')` + `p.on('close')` | error, close |

  **Every Node stream API adds `end` and `finish`**, whatever options it is given. **Read that against the log carefully, because the obvious reading is too strong**: warnings for `error` and `close` and none for `end` do not say the stream has no `end` listeners — they say it has **ten or fewer**, which is a ceiling and not a zero. A stream sitting at 12 `error`, 12 `close` and 8 `end` prints exactly the two lines and nothing about `end`. So what the last two rows are the whole space of is **the repeated adder** — the thing applied eleven or more times — because eleven applications of any other row would have carried a third and fourth line up with them. Those rows stay perfectly available as **one-off contributors** to the same stream. **The corollary is worth more than the table: ask which event names appear before asking anything else**, because it is one question to whoever has the log and it narrows the multiplier at once.

- **And the number itself is not a clue — do not go looking for a fan-out of eleven** (#1123). Eleven is `EventEmitter.defaultMaxListeners + 1` and nothing else; it is a property of Node's threshold, not of the code being diagnosed. A stream that attaches twelve, or five hundred, reports the same eleven. Searching for something that fans out to *exactly* eleven — counting a plugin list against it, say — is fitting a hypothesis to an artefact, and two readers of this issue reached for it before the semantics above were written down.

- **What answers the question the warning withholds is `scripts/listener-probe.mjs`** (#1123). It is a `--require` preload, so it needs no change to any source file: it patches `EventEmitter.prototype` and reports the real peak listener count per (constructor, event), how many instances were seen, and the stacks that added them. `NODE_OPTIONS="--import ./scripts/listener-probe.mjs" pnpm start`, then `kill -USR2` the **`next-server`** process — `next start` runs the server in a child, so `NODE_OPTIONS` is inherited and the signal is not, and signalling the `pnpm` process dumps nothing. It is deliberately not wired into the app and not a `package.json` script: it sits on the path every stream in the process takes, so it is something a person turns on while diagnosing and off again after. `--trace-warnings` is the lighter instrument and answers a different question — *where did the 11th listener come from* — where the probe answers *how many are there really*, which is the one a log cannot.

- **What the probe measured, and the outcome: a bounded fan-out, not a leak, and changing nothing in the fan-out is the correct response** (#1123, #1136). **One run, on the user's production instance (GCS backend), on 2026-09-10** — a record of that workload, not a property of the software:

  ```
  PassThrough|error:  peak=12 on one instance, instances=312
  PassThrough|close:  peak=11 on one instance, instances=312
  PassThrough|end:    peak=10 on one instance, instances=312
  PassThrough|finish: peak=7  on one instance, instances=106
  ```

  **Peak twelve over 312 instances**: many short-lived streams, none growing. **`end` at ten is the whole of the signature** — three counts climbing together on the same emitters, two crossing eleven and the third missing by one, which is why only `error` and `close` ever warned. **Five eliminations were drawn from that signature and every one was wrong**: `pipeline()`, `pipe()`, `finished()`, `Readable.toWeb()` and `new Response()` were each ruled out for "also adding `end`", and `pipeline()` was the adder all along. A different workload can push `end` past ten and print a third line; **that would not mean anything had broken**. The source is nested `pipeline()` calls down the `@google-cloud/storage` → `teeny-request` → `node-fetch` stack — `node-fetch@3` `src/index.js:253` and `teeny-request@11` `build/src/index.js:194` each `pipeline()` onto a `PassThrough`, two to three `error` listeners apiece — and **no file in this repository constructs a `PassThrough`**. It fires on a **cache miss, not a write**: `CachingStorage.get` passes `access: "delivery"` through to the backend, so a photo's first fetch is a real GCS round trip and the second is served from disk, which is why one operation triggers it once and then not again (the photo-promotion path that multiplies those fetches is #1134). **`setMaxListeners` on the emitter is refused**: it is constructed inside `teeny-request` and is not ours, so there is nothing to call it on. **The global handle is a different matter** — #1123 first refused it as blinding the process to a real leak, retracted that the same evening (a leak crosses twenty as surely as eleven), and #1137 took it: `src/lib/max-listeners-rules.ts` carries the number, the cost and when to revisit it.
