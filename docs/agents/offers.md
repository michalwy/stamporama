# Offers & Listings

The offer model, listing texts, pricing, photos, platform state, and the offer screens.

- The **bulk listing workspace** (#322) is a *sub-route* of Offers (`offers/listing/`) — the static segment takes precedence over `[offerId]` — and since #502 it is also a **nav entry of its own** under the Offers group, beside `Sold on Allegro` (`offers/allegro/`), on the reasoning #376 split Auctions with: three views of one subject, the list leading. The toolbar button stays, because it carries the platform filter across. The group's own `Offers` entry uses `isActive`'s `except` list rather than `exact`, since `offers/[offerId]` is still the list's own screen. It is scoped to one **platform** and to `ready` offers, reads its batch through one unpaginated route handler (`offers/listing`), and does grouping, filtering and year facets **client-side** from pure helpers in `src/lib/listing-groups.ts` (unit-tested) — a `ready` batch is bounded by what a person is about to type in by hand, and instant facets beat a page boundary. The per-offer posting kit (texts, photos) is loaded **on expand** through the existing `useOfferDetail` / `useOfferPhotoPlan` endpoints, so a forty-offer batch does not fetch forty descriptions to draw forty collapsed lines. Grouping and filtering are deliberately **different questions**: an offer is *grouped* under the `(area, year)` pair every copy shares (else **Mixed**, which the area rail carries as its own entry via `AreaFilterSidebar`'s `extraEntry`), but it *matches* an area filter when every copy is inside that subtree — so a year-spanning offer is Mixed yet still appears under its area. A copy's area is its stamp's **primary** area link and its year is `stamp.issuedYear`, matching the inventory list (#142). Publishing goes through `publishOffer`, which transitions first and writes the URL after, so a refused publication leaves no listing URL behind. The **offer's own screen** publishes the same way (#399): `ready → active` from the quick-advance button or the ⋮ *Activate* entry opens `ActivateOfferDialog` — moved up to `offers/` since it now serves both — and goes through `publishOfferAction`, but **only while the offer has no URL**; one that already carries a link has nothing to hand over and the header's field takes a correction. A transition asked for in two places had to ask the same question in both, or the URL was silently skipped on the surface a single listing is actually posted from. Which card is open is **derived, not stored** — a tri-state (`undefined` = nothing chosen for this batch yet → open the first; `null` = the collector shut it → honour that; an id → that card), so the first offer opens on arrival and after any batch change without a `setState`-in-effect. Publishing resolves its successor *before* the mutation, while the published offer is still in the list, and falls back to `undefined` when it was the last. Its **batch photo actions** (#323) act on the *visible* offers, never on the whole platform's ready set — the filters are how a session is scoped. Regeneration is `enqueueOfferPhotoGeneration` per offer, so #315's sold-set exclusion and the idempotent queue are inherited rather than re-decided; a per-offer refusal is **collected, not thrown** (`generateOffersPhotosAction` returns `{ queued, skipped[] }`), because one unrenderable offer is no reason to abandon the other twenty-nine, and the listing query polls while any offer is `queued`/`running` because the per-offer plan poll only covers the card that happens to be open. The batch **archive** (`buildOffersPhotoArchive`) is a folder per offer over the same per-offer upload set the single ZIP uses, so a file unpacked from either is identical and identically named (#326); namesake offers get their id appended rather than merging two listings' uploads into one folder. It is a **POST** (`offers/photos/zip`, another static segment ahead of `[offerId]`) with the batch in the body and a client-driven blob download, because forty ids in a query string is a URL-length gamble; it is buffered like the single-offer one and therefore capped, past which the honest answer is to narrow the session.

- A platform's **default starting price** (#362, narrowed to auctions by #449) is the *highest-priority* opening figure since #553: a new auction takes `Contact.defaultStartingPrice` even when the lot's suggested price (#190) or the copies' catalog value (#230) — both of which reach the form as a filled-in figure — has something to say, those two filling the starting price only when the platform states no opening figure of its own. The reversal is the auction's own economics: a lot is opened deliberately **below** what the goods are worth to attract bids, so a house that always opens at the same price knows better than a figure derived from what the stamps are worth; #362's order still holds for a **quick buy**, whose price does follow from the goods and which has no platform default at all. It lives in the dialog (`platformOpensAuction` in `offer-form-dialog.tsx`), not the server: `resolveOfferPricing` still reads the default only as a fallback for a blank submission, and the dialog now submits it, so the two agree. It carries **no currency of its own**: the platform already locks one (#196), and a second one could only disagree with it. The fallback lives in `createOffer` (`resolveOfferPricing`), resolved *before* the live-status checks so an auction created straight as `ready` on a house that always opens at the same figure is not rejected as unpriced — the server is the single point that applies it, because a plain create does not even show the price fields. The dialog pre-fills it too, into the **starting-price** field and only while untouched, so what the collector sees is what the server would have written; it never reaches the current price, which no default and no suggestion may fill. Read at creation and never again: unlike the listing templates and photo defaults it is not *seeded* onto anything, since the offer's own columns are the record. It was originally a flat *asking* price for a quick-buy platform, and #449 narrowed it deliberately — the column is kept only while `defaultListingType` is `auction` (the contact writers clear it otherwise, and the form hides the field), because a quick buy's price follows from the goods and the two suggestions above are exactly the ones that describe the goods; a flat default there could only overrule them with a figure nobody had looked at the stamps to arrive at. The migration therefore renamed the column and **cleared** every value, every platform predating `defaultListingType` reading as a quick buy — a figure left on one would be a stored fact nothing reads.

- A platform's **minimum price** (#731) is `Contact.minimumPrice`, and it is the one per-listing figure on that row that is neither seeded nor read at creation: it is **advisory, and applied only by hand**. Nothing writes it onto an offer, nothing clamps a price to it, and no gate refuses a price under it — it is offered back beside the price with a `Use minimum` button, on the offer's own screen and in the listing wizard's price step (#730), and that is its whole mechanism. The restraint is the point. A floor that filled itself in would be indistinguishable, the moment it had, from a price somebody arrived at by looking at the stamps; and a floor that *refused* prices under it would be a rule about money the collector states once and then has to argue with, on a hobby database where the exception (a giveaway, a lot cleared at cost) is ordinary. What it answers is narrower than either: what a marketplace's own fees make the cheapest listing worth posting — 2 zł on Colnect, the case it was written for — so that a cheap common needs no arithmetic per listing. It differs from `defaultStartingPrice` beside it in **two** ways, both following from that. It is **not tied to `defaultListingType`**: the writers keep it whatever the format is, and it is applied to the figure the seller *states* — the asking price on a quick buy, the **starting** price on an auction, never the current one, which is where the bidding has got to and is not the collector's to floor (`askingPriceField` on the detail panel is the wizard's `priceField` rule said again on the other surface). And it is offered **at any point in an offer's life**, on an offer that already carries a price, where the default starting price is offered back only while the offer has none — showing a creation-time seed to somebody who has already decided is inviting them to undo the decision, while asking for the floor back is a decision in its own right, which is the whole reason there is a button. It carries **no currency of its own**, for #553's reason: the platform locks one (#196) and a second could only disagree with it — the issue's "amount + currency" reads as an amount in the platform's currency. It is drawn **last** of the three figures in the wizard's price step and under the suggestion on the offer's screen, and reads *minimum* rather than *suggested*, because that ordering is the only thing saying it is the weakest claim of the three: the catalog value says what the goods are worth, the opening figure what this house does, the floor only what the platform costs to post on. It is shown whether or not the figures above already clear it — dropping deliberately to the floor is precisely the case it exists for — but never as the default.

- An offer is sold as a **quick buy or by auction** (#449) — `Offer.listingType` = `fixed` | `auction`, a fact about *this listing* and never about the platform, since a marketplace running both formats carries offers of either kind. The interesting decision is that `price` was **not** split: it keeps its column and gains a second reading — the asking price of a quick buy, the **current** figure of an auction (the standing bid, or the opening price while nobody has bid) — because every reader wants the live number and only the live number: the list rows and their base-currency equivalent (#208), the suggested-price comparison (#190), the ready/active price gate (#336), the listing kit (#405), the sale. A separate `currentPrice` beside a `price` holding the opening figure would have branched all of them on the listing type to arrive back at the same value, and two columns claiming one fact is how they drift. What the auction adds is `startingPrice` — where it opened — and `priceCheckedAt`, the auction lot's `checkedAt` (#351) on an offer, since refreshing a bid is manual by decision (ADR-0021 §8) and an undated figure says nothing about how current it is. All of it is resolved in **one** place, `resolveOfferPricing` in `offers.ts`, shared by `createOffer` / `duplicateOffer` / `updateOffer`, so a quick buy clears the auction pair wherever it is written — including a listing switched back to one, where a stale check date would describe a format it is no longer in. The price is dated only when the figure actually **moved**: a header save that retypes the same number is not an observation of the bidding, and neither is any other field on that form. `patchOffer` refuses a `startingPrice` on a quick buy rather than ignoring it — changing format is the header form's job, not a field quietly appearing beside the price. **Which of the two figures is required** is the format's own question and the counterpart of #336: going `ready`/`active` needs an asking price, but on an auction it needs the **starting** price (`requiresStartingPrice`), because that is the number the seller states while the current one is an observation — and an auction that is up with nobody bidding has none to make. The two are therefore **alternatives, not a pair**, and nothing is ever invented for `price`: an unbid auction carries `0` and reads as **No bids yet** rather than *No price yet*, because copying the opening figure into it would put a bid in the record that never happened. They move independently — correcting the opening price never touches a recorded bid, and `patchOffer` refuses to clear a live auction's *starting* price while freely clearing its current one, that one being an observation and "no bids after all" a legitimate correction. `missingPriceField` is the single server-side rule behind every refusal, returning *which* field is missing so each call site can name it; `pricingReadyFor` is that same rule for both quick-advance buttons, so a button offered is a transition the server will take. The same reasoning decides where a **suggested** figure lands in the dialog (a lot's price, the copies' catalog value, the source offer's when duplicating): a suggestion is what one would *ask* for the goods, which on an auction is what one would *open* at, so it fills the starting price and leaves the current one blank. A platform's **default listing type** (`Contact.defaultListingType`, nullable, null = *no preference* and deliberately not a stored `fixed`) is `defaultStartingPrice`'s rule again (#362) — read at creation and then owned by the offer — reaching the domain through `assertPlatform` and the dialog through `listOfferPlatforms`, and it is also what decides whether the default starting price beside it means anything at all (the two are written together in `platformListingDefaults`, since a price is meaningless without the format); an **edit** passes no defaults, since switching platforms must not re-describe a listing that already exists, and the dialog stops re-seeding the moment the collector answers the question themselves. Both defaults only ever reach an offer whose form **left the question unasked**, so `readOfferInput` distinguishes *absent* from *unrecognised* (#589): a missing `listingType` field is passed on as `undefined` and the platform decides, while a value that was sent and is not one of the two still reads as `fixed`. Normalizing the absent case to `fixed` in the action had made the domain's own fallback unreachable from any caller that does not draw the form — quick offer mode (#537), which states the platform and the status and nothing else, so its offers were quick buys on auction-only houses and silently missed the opening figure too. The picker's platform facts travel as one `PlatformOfferDefaults` object rather than a fourth positional callback argument. The vocabulary, the parser (`parseStartingPrice`, which unlike `parsePrice` reads blank as *not recorded* rather than as an error — the transition gate is what asks for the figure, not the parser) and the price's own **label** (`priceLabel`) are pure in `offer-rules.ts`: what the field is called differs per listing type on three surfaces, and a ternary per surface is how two of them end up saying different things. The chip is deliberately shown for an **auction only** — a quick buy is what an offer ordinarily is, and a chip on every row of a long list is noise — and it sits beside, never instead of, *In bidding* (#215): one says the listing is an auction, the other that somebody has actually bid and the collector is committed.

- A platform's **shipping methods** (#468) are a dictionary hung off the *platform*, not the collection — `ShippingMethod(platformId, name, cost, currency)`, unique per (platform, name) — because postage is quoted by the marketplace the parcel sold on. It is managed in its own dialog off the contact form's **Platform** tab (beside `Templates…`), and that dialog **writes as it goes**: the rows are records of their own, so nothing waits for the contact's Save, and it needs a contact that already exists. On a sale the method is a **pair** of columns, written together: `Sale.shippingMethodId` (Restrict) links the dictionary row, `Sale.shippingMethodName` snapshots what it was called then — a price list gets re-priced and renamed, and a sale must keep saying which service was bought. A one-off *Custom* method (the `CUSTOM_SHIPPING_METHOD` token in `sale-rules.ts`) stores the name alone. Picking a method pre-fills `shippingCost` / `shippingCurrency` (#206) from the row and both stay editable — the price is what the method usually costs, not what this parcel cost — and a blank cost clears the money fields while leaving the method standing. It is picked in **two** places, the sale header dialog and the detail's `− My shipping` row, both going through `resolveSaleShipping`, which re-reads the row against the sale's own platform rather than trusting the client's name.

- An offer's **stamps on the platform's own catalogue** (#423) are a card of their own on the offer detail, between the images and the sets — the two pages a seller opens while pricing a listing: what the stamp *is* (its catalog page, #290) and what it is currently being **asked for** (the marketplace search at that grade). Keyed on `stamp × condition` and not on the copy, because that is what the marketplace pages are keyed on and a komplet is dozens of copies over a handful of stamps; a row states how many of the offer's copies it stands for rather than repeating itself. The market URL's condition segment is a **third Colnect vocabulary** — `ColnectGrade.marketSlug` (`mint_never_hinged`) beside the sale form's numeric `value` — stated in the table rather than derived from the label, since nothing guarantees the two agree; it is the one thing here that could not be verified against the live site (#419's interstitial refuses anything scripted) and is derived from the single confirmed example in #423, which is why it is one table and a one-line correction. `colnectMarketUrl` returns **null rather than a condition-less search**: a price for "any grade" is not the figure being judged, and a link that quietly answers a different question is worse than no link. Gated on `platformModule` exactly as the blockers are — one marketplace's catalogue, not a general fact about an offer — but deliberately **not** on the listing preconditions (#405): the collector is asking what the market wants, which is a fair question of an offer at any stage. A row an unmatched stamp (#247) or an unmapped condition (#404) leaves link-less is therefore **still listed**, disabled with its reason (#273), because the list that would have taken them to the market is where that gap gets noticed. It reads nothing of its own — the item-IDs come off the set select the screen already loads and the grades off the condition map already read once per offer. The card's last column is the *other* gap it is read for, and it draws **one of two things** (#618): a stamp with no catalog value at that condition gets the quick `+ CV` dialog, while a row whose item-ID could not be derived because a **variant carries no price** (#617's `unpriced-variants`, reported on `OfferPlatformItem.unpricedVariantStampId`) gets **Price variants** instead — the whole tree on one grid. It replaces `+ CV` there rather than sitting beside it, because pricing the umbrella itself does not close that gap: the rollup reads the *variants*, and until every one of them is priced there is nothing to say which is cheapest. That row is also the one with no catalogue link *and* nothing to search for, so the affordance is the only thing in it. It opens the grid **narrowed to the row's own copy** (#633) — its condition, certificate and format, the last two carried on `OfferPlatformItem` as the first copy's answer exactly like the derived variant beside them — because what blocks the listing is one cell of each of the tree's rows, and the other columns are a question nobody asked here. Narrowed in **rows** as well since #679 (`subtree`): the tree is drawn from the umbrella being listed rather than from its root, the ancestors of `Mi·NL 175E` being no part of a question asked about `175E`. Since #669 the card is drawn on an offer for **any** platform and is headed **Items**, not *On <platform>*. It was Colnect-only at first and #471 narrowed it to that after it appeared over an Allegro listing headed *On Allegro* with Colnect's buttons under it — but that complaint was about the **heading claiming the wrong catalogue**, not about rows nobody wanted: linking a stamp to its Colnect entry is how its catalogue numbers and its date get filled in (#280/#655), and a stamp needs that whatever it is being sold on. So the gate came off `platformItemsFor`, the heading names nothing and only what a link *does* names Colnect, and the *not matched* chip drops its "the listing cannot be posted yet" on a platform that lists by category — there it is a gap in the stamp's own data and nothing more, which is the one thing `usesPlatformCatalogue` still decides here (the card reads it from `platformModule`, the prop that replaced `platformName`). Two reads follow the card rather than the module now: the Colnect condition map, loaded on every platform by `getOffer` (one small per-collection read for a screen that draws the market links either way, still gated in the **batch** read where nothing draws them), and the variant derivation, which `resolveSetCatalogItemIds` takes a `derive` override for — without it an Allegro offer's umbrella row would carry a **Listed as…** button whose choice the derivation then ignored. Every row also **edits its own stamp** (#676): the shared `StampFormDialog` (#54) over one of the row's copies — the row carries formatted labels for reading while the dialog edits `vendor × number` pairs, and the offer's copies are already on the screen. It belongs on this card above all others because this is the surface read *against* the platform's own catalogue, which is exactly when a number recorded wrong or a name never filled in is noticed, and the Copies list is two screens away; the button is plain rather than amber, being a correction the collector may make and not a gap that has to be closed, and it edits the **row's own** stamp even on an umbrella standing under a variant — that variant is a different entry, reached from its own catalog page. The header's buttons sit **beside the heading**, not pushed to the card's right edge: everything they stand with is a per-row button a few centimetres from the title, and a card-wide action at the far edge made the whole width a mouse journey between two halves of one job (the same reading as the summary bar's left-hand amount columns). The header carries a **refresh** beside *Link all* (#677), drawn whether or not the Assistant is present, unlike *Link all* itself: what a row says goes stale from any write this screen never hears about, and the collector who linked a stamp in another tab is precisely the one looking at an unchanged card. It re-reads the offer rather than the page, and it is a **workaround by design** — the several cache paths that would each have to invalidate this card are the standing bug (#212/#440/#624/#654), and one honest button beats chasing every one of them. Beside it sits **+ CV all** (#720), the last column's dialog with the rows stacked: a komplet is a page of `+ CV` buttons, each opening a dialog and each closed again before the next, while the rows are already keyed on exactly what a catalog value is recorded against. `offer-catalog-values-dialog.tsx` is one line per `stamp × condition`, one figure per row, and it **writes through `quickSetCatalogPrices` row by row** (`quickSetCatalogPricesBulkAction`) rather than pricing anything itself — the latest edition of each catalog, at the single, which is the one way a value is ever set here. Its read is the bulk shape of the per-row one (`getBulkQuickCatalogPriceContext`), the same catalogs and the same latest edition in a fixed number of queries, and it drops the two panels a grid has no room for (the other recorded prices, the shown format's derivation), both a click away on the row's own `+ CV` — which stays, one gap noticed while reading a row still being one dialog. Two things about the row itself are deliberate, and both follow from *which* catalogue is open in front of the collector. The row is the **stamp as a list draws it** — `PhotoThumb` + the shared `StampIdentity`, plus its issue and area — and not the card's one-line summary: the card is read against the platform's catalogue, where a number is enough to find the entry again, while this is read against a paper catalogue open at a page, and the picture is the fastest thing a stamp is matched by. And it draws **one column, the area's primary catalog** — #593's rule and its reason: the per-row dialog prices every vendor active on the area and stays where it is for that case, but a listing's worth of rows is scanned rather than read, the primary is the only catalogue the closing checks and the valuation ever ask about, and two more columns of mostly empty inputs are what stop the one that matters from being filled in. The book is named **once in the heading** when every row agrees on it and beside the input otherwise, since a grid spanning areas is the only case where the name is news. The read stays the general one (`primaryCatalogNameId` is a field of it, not its whole answer), so a surface that does want every vendor has it without a second query. Three further decisions differ from the card's own vocabulary and each is deliberate. **Every row is listed and a recorded value is prefilled**, unlike the card where the gap is the news and the number is not: a grid opened to type into is where a figure entered wrong is corrected rather than re-noticed, and only the gaps are marked — in the card's amber, and off the card's own answer (`copy.value.unpriced`) rather than off what the grid found, so the two cannot disagree about which rows are the work. **One Save, not a write per cell**, which is the opposite of #618's rule and rests on the same argument: a tree worked through over minutes cannot afford a lost draft, while a listing copied down one catalogue column is one sitting and one submit — so every amount is parsed before anything is written, and a refusal part-way through reports how many rows went in and marks those saved rather than offering them again. **An umbrella row is locked** as #627 has it, on either of the two rows where the operative figure is the tree's and not the stamp's: one standing under its cheapest variant (#238/#616), which shows that figure `≈`-prefixed and names the variant, and one whose tree cannot be rolled up at all (#617), which says so and sends the collector to *Price variants* — pricing the umbrella closes neither, and an open input there would look like the answer. Tab walks **down a catalog column**, #626's rule in this grid's axes, so all three price surfaces agree about it — and off the **last** cell it goes to Save rather than to Cancel (#726), which is where the footer's own DOM order had been sending it: the walk is how a column is typed and its last step is the one that commits it, so `DialogPrimaryButton` takes a `ref` (`ComponentPropsWithRef`) and the grid focuses it. Only while it can be focused at all: with nothing to write Save is disabled, and the browser's order then stands.

- The **listing kit** (#405) is one read-only call — `GET …/offers/[offerId]/listing-kit`, session **or** Assistant token like the matcher (#250) — answering "everything this offer wants filled into a marketplace form": the copies' catalog item-IDs (#247), each copy's condition **already translated** into the platform's vocabulary (#404), the quantity, the price in the platform's currency, the two generated texts, and the photo plan's **upload set** in upload order as fetchable photo-route paths (the same route already takes the token, #253). **Platform-neutral in shape**: it says what the listing *holds*, never how a form is laid out — that mapping is the extension's platform module (#408/#410). One Colnect-shaped assumption is confined to `src/lib/listing-kit.ts`: the grade vocabulary comes from the collection's Colnect map, which is per collection precisely because Colnect's list is fixed and global (#402); a second marketplace with its own vocabulary turns `platformCondition` into a per-platform lookup and moves nothing else. `quantity` is the **number of sets** and `items` describes **one** of them — which is only truthful over interchangeable sets, hence the preconditions. Those are pure and separate (`src/lib/listing-preconditions.ts`, unit-tested), because the endpoint refuses on them and #406's card has to state the same reasons: not Ready, no copies, a stamp with no item-ID, an unmapped condition, or sets that differ. Homogeneity compares **what the form would receive** — item-ID + grade, order-insensitively — with the local ids standing in where either is missing, so two unmatched sets are never called interchangeable on the strength of two nulls. `not-ready` / `no-sets` return **alone**: with no composition there is nothing else to say, and listing four faults under an unfinished offer buries the one thing to do. A failing precondition is a **refusal** (409 with the blockers), never a payload with holes in it, because a wrong grade or an untruthful quantity misdescribes the goods — while an over-long text is not a blocker at all (#403): the platform's own field visibly refuses a long paste, and nothing about the stamps is misstated. The kit is still *returned* by the domain function with its blockers and its nulls, so the workspace card and the endpoint read one evaluation. Photos are taken from `getOfferPhotoPlanState`, filtered to `publish && !overLimit`, so the kit, the Photos card and the plan's ZIP can never disagree about which images are uploaded or what they are called; `outOfDate` travels as a signal and never as a refusal, stored images still being truthful pictures of these stamps. **Which platforms they apply to** (#406) is `Contact.platformModule` — the extension's `PlatformModule` id (`COLNECT_PLATFORM_MODULE`, `src/lib/platform-modules.ts`), nullable, and set **in Settings → Colnect by picking the platform** (`setColnectPlatform`), never on the contact form: it is one fact per collection — which platform *is* Colnect — and the collector deciding it is already on that tab setting up the catalog and condition mappings it belongs with, which is also why the picker leads the tab. The setter is **exclusive** (it clears the previous holder in the same transaction, so "which platform is Colnect" always has one answer) and refuses a contact that is not a platform of the collection. There is deliberately no registry of modules to pick from: Colnect is the only one and the value is written by that one setter, so an enumeration would be a vocabulary nothing reads. It exists because the preconditions are **one module's rules**, not a general truth about listings: without it a Delcampe batch would carry a chip per card about a form nobody is going to fill from here. The two ends treat a module-less platform differently, deliberately: the evaluator returns `no-platform-module` **alone** and the kit endpoint refuses on it (a caller that asked for a posting payload asked for something impossible), while `listReadyOffersForListing` **skips the evaluation entirely** and reports nothing — the card answers "what do I fix", and "this platform is listed by hand" is not a fault. It also skips the condition-map read, so a non-Assistant batch pays for none of it. **Where they are surfaced** (#406) is the bulk listing workspace's own row — `ListingWorkspaceOffer.blockers`, evaluated in `listReadyOffersForListing` over one extra select (the stamp's item-ID, the copy's condition) and one condition-map load for the whole batch — and *not* the expanded kit: which of a session's forty offers the Assistant can post is a question asked while scanning, and an answer that needs forty expansions is no answer. The row carries a **Can't list** chip and the expanded card spells the reasons out, one per line and never a count, because each is fixed in a different place; they render from the row, so they are stated even while the kit is still loading or failed to load. They gate the **Assistant handoff** (#407) and nothing else — **Publish stays open**, since posting the form by hand is exactly what a collector does about a gap the Assistant cannot fill. No per-reason link: an unmatched stamp is matched on the platform's own catalog pages through the extension, which the app cannot navigate to. The **handoff** itself (#407, `listing/assistant-handoff.ts`) is the page half of #409's contract, mirrored by hand like the registration payload: **⚡ List via Assistant** beside Publish fetches the kit, writes `{ v, requestId, task }` into one hidden node the panel owns, and follows `data-listing-state` off it. Session-wide and **one at a time**, both for the same reason — the extension puts a marketplace tab in front, so a second handoff would be two forms fighting over one window; presence is `useAssistantPresence` over `<html>`'s `data-stamporama-assistant` through `useSyncExternalStore` with a null server snapshot (the script runs at `document_idle`, and reading the attribute in render would disagree with the server's output). Which platform offers the button at all is `platformModule`, now carried by `listOfferPlatforms` — absent means no module, and the button is *not rendered*; a blocked one is **disabled with its reason** (#273), the reasons being a failing precondition, no extension, or another offer mid-flight. The outcome is rendered as a strip under the card's own line, whether or not the kit is expanded: skips one per line (each is fixed somewhere different), the filled fields in one muted line (what went in is checked in the form, which is now in front of the collector). It **publishes nothing** — filling stops before submit, so the offer is still Ready and the listing does not exist yet; the card's own Publish, one line above and in view at the same time, is the next step, so the strip carries **no Publish of its own** — a second one there is the same button twice. Closing that loop without a paste is #412's, which adds `listed` / `unread` / `activated` to the same strip: `listed` is the URL arriving, `activated` the publication it performs, `unread` a listing posted whose URL could not be read — warning-toned, since nothing failed and the offer is simply activated here. The fill's own filled/skipped detail is **kept** across those states rather than replaced, the post-Save answer carrying only the URL. The workspace treats an offer activated this way exactly as one it published (out of the batch, next card open); the offer's own screen re-reads itself and keeps the strip. The **offer's own header offers the same handoff** (#414), beside Activate and only while `ready`, for #399's reason exactly: a single listing is routinely posted from there, and a step offered on one surface only is the one that gets silently skipped on the other. Button, hint rules and report strip are therefore *one* implementation in `offers/assistant-listing.tsx` (the caller supplies only the button's style, since it sits among a card's small controls on one screen and among the header's chips on the other) — when the Assistant may be asked is a fact about the offer, not about the screen. `OfferDetail` consequently carries `platformModule` + `listingBlockers`, evaluated by the same `listingBlockersFor` over a set select that is a **superset** of `LISTING_SETS_SELECT`, at the offer's **own** state (so anything not Ready reports `not-ready` alone and the header simply shows no button); the condition map is still read only where a module asks for it. The same preconditions **gate `preparing → ready`** (#418, `readReadyBlockers` in `setOfferState`): a fault is worth catching while the offer is still being assembled, not once thirty of them are open in a posting session. It is the one transition gated, deliberately — an offer already live is a listing that exists, and refusing to pause, withdraw or sell it over a mapping gap would trap the collector — and it is evaluated at the **target** state, which is the whole reason it cannot reuse `OfferDetail.listingBlockers` (`not-ready` alone on a `preparing` offer). Hence `OfferDetail.readyBlockers`, the same pure evaluation at `"ready"` over the same sets and condition map, non-empty only while `preparing`; the header's quick-advance button is then **disabled with the reasons** (#273) instead of vanishing the way a missing set or price makes it, since each of these is fixed on another screen. The server refuses regardless of surface (`listing-preconditions`), which is what covers the Offers list, whose rows deliberately carry no blockers of their own: evaluating every page of offers would pay the workspace's per-batch cost on a screen that is not about listing, and the refusal message states the same reasons.

- An **unknown-variant umbrella is listed under its cheapest variant** (#616, `src/lib/listing-catalog-ids.ts`). Colnect keys its marketplace on the most precise catalogue number it knows and a sale attaches to one specific variant, while a large part of this collection cannot be resolved that far — a colour needs comparison material, a gum variety is unidentifiable in principle on a used stamp — and the established practice there is to list such a piece under its cheapest variant. Nothing about that is new to the app: `valuateCopy` already values such a copy at the **lowest** price among its variant descendants (#238), at that copy's own `condition × certificate × format`, at any depth. What #616 fixes is that the listing side did not read the same answer — the kit took `catalogItemId` off `Stamp.colnectId`, an umbrella carries none, and the offer was refused. So the item-ID is **derived, never stored**, and derived by the very function that values the copy: `CopyValuation.sourceStampId` names the variant the rollup took its figure from (which is why `pickLowestByBase` is generic over its candidates and returns the candidate itself), and `resolveListingCatalogItemIds` reads that stamp's `colnectId`. What a listing stands under and what it is valued at then cannot drift apart, and neither can go stale: pasting the cheapest variant's id onto every umbrella by hand is a great deal of work *and* a figure frozen the day it was pasted, silently invalidated by the next catalogue correction. Three calls follow from it being a claim about a **listing** and not about the stamp. It is **never written back** — the matcher stays the only writer of `colnectId`, because recording a resolved id would assert that the umbrella *is* that variant, which is exactly what is unknown; an umbrella matched by hand therefore still **wins**, the same precedence `valuateCopy` gives an own price over the rollup. The winner is **per condition** (per certificate and format too), so two copies of one umbrella can resolve to two item-IDs — and two umbrellas to one, which `colnect/listing.ts` already deduplicates when declaring a komplet (#410). And a cheapest variant carrying **no item-ID of its own** changes nothing: the copy resolves to nothing, the precondition refuses and names it, and the second-cheapest variant is *not* tried in its place — that would be a different claim about the goods. (#617 revised the *other* empty answer: a tree that is not fully priced no longer resolves at all, since the cheapest variant is not knowable there.) One resolution serves every reader, which is the point of the module: the kit, both blocker lists, the ready gate and the **Items** card (#423) all read one map, so the page cannot call a stamp unmatched in one place and link its variant's market page in another. It is asked over as many sets as the caller holds at once — the workspace's whole batch in a single `valuateItemRows` — and reads **nothing at all** for an offer whose stamps are matched or a module that lists against no catalogue (#493). Both surfaces that show it **name the variant**, in #238's `~` + muted-italic vocabulary for *inferred, not recorded*: the Assistant's report strip from the kit it handed over rather than from the extension's answer — the form is filled identically either way, so there is nothing for the extension to report about it — and the **Items** card on a line of its own beneath the row (`↳ listed as ~ Mi·PL 900b`), which is where the row's platform links now live. They moved there because the entry they lead to *is* the variant: a row headed `Mi·PL 900` whose Catalog button opened `Mi·PL 900b` was one line standing for two stamps, and a chip beside the name said which variant without saying which stamp the buttons meant. The line takes the links cell **and two more cells**, so the grid's five tracks stay filled and the next row still starts in column one; the umbrella's own cell is rendered empty rather than dropped, for the same reason. What made the change worth making is the **unmatched** case: `sourceLabel` is null there by design (no derived id exists to mark inferred), so the card said nothing at all just where the answer mattered most — the offer being blocked *because* that variant carries no item-ID. The row now reads the name out of the gap itself (`unmatched-variant` already carries `stampId` + `label`, #617), so it is named matched or not, and **Search / ⚡ Link are built from the variant's number rather than the umbrella's**: matching from the umbrella's search would write `colnectId` onto the umbrella, asserting it *is* that variant — the one thing not known about it, and the write this whole derivation exists to avoid. The handoff's own label follows the search for the same reason a mismatch there reads as a bug. The third empty answer names nothing and gets no line: an unpriced tree (#617) has no cheapest variant to name, and its row keeps **Price variants** instead.

- **Which variant an offer lists an umbrella under can be said by hand** (`OfferListedVariant`, `src/lib/listing-variant-choice.ts`). #616's derivation is a default and a default needs an override: a collector may rule a variant out from the piece in front of them, may prefer the variant actually being traded, and may not want to price a whole tree (#617) to post one offer. It is keyed on **offer × stamp × condition** — the Items card (#669, the **Items** card until then)'s own row — for three reasons that all point the same way: `OfferSetItem` is N:M, so a per-copy choice would follow the copy into every other offer holding it; one offer's sets have to stay interchangeable (#405), which this key *guarantees* rather than permits; and "cheapest" is resolved per condition, so a used and an MNH copy of one umbrella may legitimately want different variants. The certificate and format axes the rollup also resolves at are deliberately outside the key — the surface the choice is made on is keyed on `stamp × condition`, and a choice made on a line has to apply to that line. It reaches the derivation as `ListingCatalogCopy.listedAsStampId`, folded on by the caller rather than looked up inside: the function is asked over as many offers' copies as the caller holds (the workspace's whole batch), so it has no offer of its own, and `LISTING_SETS_SELECT` grew `offerId` for exactly that. A chosen variant **short-circuits the rollup entirely** — no valuation is asked for that copy, which is what makes it an answer where an unpriced tree had none — and then resolves off that variant's own `colnectId` exactly as a derived one does, so a choice that is unmatched is refused in the same words (`missing-catalog-id`) against the stamp the collector picked, whose `⚡ Link` is on the card beside it. **Any** variant in the subtree may be chosen, matched or not and umbrella or leaf: requiring a match first would mean not being able to say what you want to sell until you had already gone and matched it, and the subtree check lives in the writer because a subtree is not expressible as a constraint. What a choice may **not** do is either of #616's two rules: it never writes `Stamp.colnectId` (recording an id on the umbrella would assert it *is* that variant, still the unknown), and it never moves the **valuation** — #616 could promise that a listing and its value never drift apart because both were derived, and a choice is the collector electing that drift, which is why `ResolvedCatalogItemId.sourceChosen` exists at all: a surface that marks a derivation `~` for *inferred* (#238) must not mark a decision the same way. Clearing is a **delete**, absence already meaning "derive it", and a stored null would be a second spelling every reader would have to know. The write re-runs `syncGeneratedTexts` — but only where a template names `{listedAs}` (#619's own guard, #415's rule), a description reading `Offered under Mi·PL 865b` while the form is filled with `865c` being precisely the drift #619 exists to prevent. On the card the variant's **name is the picker's trigger** (what is being changed is which entry the line is about, so a separate button would be a second thing to find on a line that says one thing), a chosen variant drops the `~` *and* the italics with no glyph of its own — the absence of the inferred mark is the statement — and the two rows that name no variant carry **Listed as…** in the last column instead: an unpriced tree, where it sits beside `Price variants` as the shortcut past the whole question, and an umbrella whose own catalogue price won the valuation, which has no rollup gap at all and would otherwise have nowhere to say it. The picker leads with **automatic**, naming what automatic resolves to *today* or which of #617's two gaps is in the way, because a default you cannot see is a default nobody can decide against; its prices come from `valuateItemRows` with each variant standing as its own identified copy, so the figures compared in the dialog are the figures the rollup compared rather than a second pricing path that would eventually disagree.

- **A listing may only be derived from a fully priced variant tree, and the two ways the rollup comes up empty are told apart** (#617). The first half is a correction to #616: the rollup picks the lowest among the variants that *have* a price, which is a sound catalogue **estimate** — flagged `uncertain` and drawn as one (#238) — but it is not an answer to *which variant is the cheapest*. A collector who has so far priced one variant would have every such copy listed under exactly that variant, and if the priced one is the dearest, silently under the worst possible entry. So `resolveListingCatalogItemIds` refuses a copy whose tree has an unpriced variant, however much of the tree is priced, and the **valuation side is deliberately left alone**: an estimate may be marked as an estimate, while a sale attaches to one specific catalogue entry. What must be priced are the tree's **leaves** — a node with variant children is itself an unknown-variant umbrella (ADR-0010 §3) whose value *is* the lowest of its children, so a catalogue prices it through them and an unpriced one is no gap. That is `VariantPrices.identified`, resolved in `item-valuation.ts` off one extra `parentId` column over a result set that already holds the whole subtree, and reported back as `CopyValuation.unpricedVariantIds` — computed inside the rollup rather than re-derived on the listing side, the same argument that put `sourceStampId` there (#616). The second half is why there are **two codes**: an unpriced variant is a gap in the *catalogue prices*, fixed in that variant's own price grid, while a cheapest variant with no item-ID is a gap in *matching*, fixed in the match window — and listing blockers are printed one per line precisely so each can be acted on, so two faults sharing one line sent the collector to the wrong screen half the time. A shared code with a variable sentence was not an option either: the codes are what the surfaces route on, and that is how a link ends up pointing at the wrong screen. So `no-variant-price` joins the seven and **names the unpriced variants themselves** (they are what wants a price), taking precedence over the matching gap, which cannot even be judged while it holds; `missing-catalog-id` keeps its code and its `subjects` / `stampIds` / `stampSubjects` now **name the variant** rather than the umbrella, the surface that offers to go and match a stamp (#406) having to point at the stamp an item-ID would be *recorded on* — never the umbrella (#616). A third empty answer stays exactly as it was: an umbrella whose **own** catalogue price won the valuation was never rolled up at all, so there is no rollup gap and the plain refusal against the umbrella is already the right one. Both are still refusals (#405) and nothing is substituted. The unpriced one is the **first blocker with a link**, which is what `ListingBlocker.stampSubjects` exists for — the stamps of `stampIds` with the name each is reported under, a field of its own because `subjects` and `stampIds` are deduplicated on different things (a name a collector reads, an identity) and positions read off two such lists eventually name the wrong stamp. It opens each variant in the **variant price grid** (#618) rather than on that variant's own screen, and over a *tree* of prices and not one stamp: a screen that prices one stamp would send the collector back for the next one. Which tree is the **umbrella being listed** (#679, `StampSubject.treeStampId`) — the variant names the link and its umbrella is what the grid draws, from there down, since pricing the one named variant never says which is cheapest while its ancestors were never the question; #406's "no per-reason link" stands everywhere else for the reason it always did — a match happens on the platform's own catalog pages, which the app cannot navigate to. Each named variant carries the **axes of the copy it was reported for** (`StampSubject.axes`, #633) so the grid opens at the cell the listing is blocked on; where two copies at different grades name one variant the first is kept, as it already is for the label. That is what `PreconditionCopy` grew a certificate and a format for — the condition alone was never the key a price is recorded against (#616).

- **The variant price grid follows the *pricing* gap, not the listing one** (#734). The Items card raised **Price variants** off `OfferPlatformItem.unpricedVariantStampId`, which is set from the rollup's `unpriced-variants` gap (#617) — and that gap is only ever reported for an umbrella carrying **no item-ID of its own**, since `resolveListingCatalogItemIds` short-circuits on `ownCatalogItemId` before it asks the valuation anything. A matched umbrella therefore had no button at all, while its value went on being rolled up from its variants all the same: `valuateCopy` rolls up whenever the umbrella has no catalogue price of its own, and `colnectId` is not one of its inputs. That is the *ordinary* shape of the case, not a corner of it — Colnect keeps a page for the umbrella and the paper catalogue prices only the variants — so the row that most needed the grid was the one row that never offered it, and the only control on it was `+ CV` on a stamp the collector has no figure for. The gap is read instead off `CopyValuation.unpricedVariantIds` (#617's coverage report) on the copies the card already loads, matched to the row on its **whole** valuation key and not on `stamp × condition`: coverage is reported at a `condition × certificate × format`, which is also the cell the grid is opened at, and a hole found at one certificate would otherwise open the grid on another's priced cell. Nothing moved to the server — `platformItemsFor` deliberately reads nothing of its own (#423), and the valuations are on the screen already. **`+ CV` stays beside it on a matched umbrella and stays suppressed on an unmatched one**, which looks like an inconsistency and is the whole point: on the unmatched row an own price does not close the gap but *ends the rollup*, turning `no-variant-price` into `missing-catalog-id` and quietly taking the listing off the cheapest variant, while on the matched row the listing is already resolved against the umbrella and an own price is an ordinary uncertain valuation (#238) the collector may prefer. The two tooltips say which row it is; only the blocking one talks about listing.

- A blocker carries a **short title beside its sentence** (`ListingBlocker.title`, `PhotoReadinessBlocker.title`, #617), because the ready gate states up to four of them in a **hover hint** and four full sentences there are one unreadable block — the one thing a hint must not be. The title is the fault alone, the `subjects` are stated beside it rather than folded into it, and the hint shows nothing else: what to do about it is a sentence, and a sentence belongs on a surface with room. The workspace card is that surface and shows both, the title leading in strong type and the message following muted, so three reasons can be scanned for the one to deal with next. It is stated by the **domain**, not derived per surface from the code, for the reason the messages are: two surfaces inventing their own wording is how they end up disagreeing about what is wrong.

- **A listing text can say that the variant was never identified** (#619). An offer listed under an umbrella's cheapest variant (#616) stands on a Colnect page naming a *specific* variant, and the buyer has to be told the piece was not identified that far — which variant it might be, and which one it is being sold under. The templates could say none of it: the engine had repeating blocks and legends but nothing conditional, and nothing naming the stamp the listing resolved to. So `{#unknownVariant}…{/unknownVariant}` is the engine's **one conditional block** — it renders its body once, narrowed to the copies in scope that are unknown-variant umbrellas, and not at all when there are none. That single rule is deliberately both things a template wants: at description level it is one caveat for the whole listing, and inside `{#copy}` — where the scope is already one copy — it is a per-copy aside, without a second kind of block to explain. It **narrows** rather than merely testing, `legendScopes`' rule, so `{catalog}` inside it names exactly the unidentified pieces and never the identified ones beside them. The two value tokens are `{listedAs}` (what it is sold as) and `{variants}` (what it might be), named for the state the rest of the app calls by that name (#238/#239) — one word per thing. `{variants}` is the umbrella's **direct** variant children, not every descendant leaf: *which of these is it* is the question the collector could not answer, and a flattened deep tree names variants nobody was choosing between. It is written through `compactCatalogNumbers`, so `123a-d` collapses in the notation every other surface uses (#150/#400), resolved at the **umbrella's** own area and issue rather than each child's — a range only collapses while every member is written under one prefix, and a variant hangs under its parent. Which facts are resolved where follows from what they are *about*: `unknownVariant` and `variants` describe the **goods**, so they ride on the shared copy normalisation (`toTitleCopy`) and hold on a marketplace listing against no catalogue at all, while `{listedAs}` describes the **listing** and is #616's own `sourceStampId` read through `resolveListingCatalogItemIds` — never a second derivation, so a description cannot name a different variant than the form is filled with. It is therefore gated twice, on `templateUsesListedAs` (`{offerUrl}`'s guard, #415, keeping a valuation pass off every ordinary regeneration) and on `usesPlatformCatalogue` (#493: a platform listing by category is served an empty token rather than a number read off a catalogue it is not in), and it reaches the engine as a **resolved value** folded onto the copy in `templateSets` — the last point a copy still has an id — so the engine stays pure and knows nothing about the rollup. All three are **listing-text only**: a title carrying one renders empty and the block renders nothing, `{offerUrl}`'s rule (#415), which needs an explicit `TemplateScope.listingText` here because their value rides on the copy rather than on an absent context — and a `Mi 865a-c` in a title would read as a span the listing holds. `sourceLabel` being null is what makes the three empty answers of #616/#617 render as silence: an umbrella matched by hand keeps its own entry, and a tree that cannot be resolved has no variant to name. The variant children are ordered by catalog sort key with an id tiebreak in the mapper rather than left to the database, for #429's reason with #380's stakes: these texts are *stored*, so an unpinned order rewrites a description on nothing but a re-read.

- A listing **title** (#209/#210) is *stored*, and the derived label (`offerLabel`) is only what a surface falls back to while `Offer.name` is null. It is generated at creation — but an offer created **empty** renders over no copies, so `backfillOfferTitle` fills it in on the first mutation that adds copies (`addOfferSet`, `addOfferSetsPerCopy`, `addItemToOfferSet`; #365), and only while the field is still null. Growing a listing never rewrites a title it already has: that is what ↻ Regenerate is for. Without this the detail header looked right and everything reading the stored value — the copy control (#327), the bulk listing workspace (#322) — got nothing. Editing the title likewise seeds the input from what is *displayed*, derived label included (#363); `InlineText` only commits a changed draft, so opening and closing the editor still stores nothing. In generated titles, catalog numbers collapse on **both** of #150's axes (`compactCatalogNumbers`): consecutive bases within a prefix+suffix family (`BL31-33`, `40-42A`), then — over what stayed single — consecutive suffixes on one base (`BL92a-b`, `12I-III`; #364, via `parseSuffixOrdinal`). A span that already collapsed a base run is never folded by suffix: `31-32a` + `31-32b` are two runs, and joining them would claim a span the offer does not list. A number that is **itself** a Roman numeral (#383) carries no digit run and so reaches neither axis — it folds in a third pass keyed on the constant text in front of it (`I-III`, and `Mi·PL I-III` where the caller passes prefixed numbers, as the auction lot label does; #384), never merging with a digit-bearing number or with another prefix's numerals. That numeral may itself carry a **letter suffix** (#426), so the third pass runs both of #150's axes over it in turn, the numeral standing where the base does: the numeral under a constant suffix first — written at **both** ends (`IA-VIIIA`) unlike the numeric axis's `40-42A`, because a numeral and a letter suffix are both letters and `I-VIIIA` would read as a bare-numeral span with a stray letter hung off it — then the suffix on one numeral (`Ia-c`). An **uppercase** suffix folds on neither: `parseSuffixOrdinal`'s sequences are lowercase letters and numerals, and one that is itself a Roman digit (the `C` of `IC`) is read as part of the numeral, there being nothing that could tell the two apart. How a resolved span is **written** is `src/lib/catalog-range.ts` (#400, pure, unit-tested), one module for every surface that shows a range: the end drops the digits it **shares** with the start (`1298-302`, `1298-99`, `240-56`), a floor of two digits so `1298-9` cannot happen, and nothing at all when the endpoints differ in digit count (`98-102`, where a shortened end would read as the smaller number); the suffix axis writes the base once (`128a-c`). `compactCatalogNumbers` renders its spans through it, so a generated title, an offer set label, an auction lot name and the Issues list's declared-range chip (`formatIssueCatalogNumber`, en dash) are one notation. It is **display of a known range, never detection** — `resolveCatalogRange` stays the only reader of typed input — and deliberately absent where a range is being *edited or confirmed* (the issue form's First/Last, the range-extension and recompute prompts): those endpoints are about to be stored, and a shortened one would misdescribe what is being agreed to.

- An offer's generated texts are **subscriptions, not snapshots** (#380). Title, description and private note are re-rendered from the platform's templates after **every** mutation that changes what `offerComposition()` returns — sets added/removed, copies added, a set renamed, either order rearranged — through one `syncGeneratedTexts`, which subsumes #365's title backfill (an offer created empty gets its title for the same reason it later gets a fresh one). Three `Offer.*Edited` flags stop that: `patchOffer` sets one when the collector writes the field, `regenerateOfferText` clears it, so ↻ is literally "hand this back to the template". **Clearing** a field clears the flag too — the flag protects *written wording* and an emptied field holds none; blanking the title is how one asks for the derived label back (#209), which follows the composition by definition. That is also the rule the migration read existing rows by: a non-null text became `edited`, because the two cases are indistinguishable after the fact and losing typed wording is far worse than not refreshing generated wording. A field whose platform template is blank is never written, so clearing a template leaves the last text standing instead of emptying a live listing as a side effect of a settings change; a render that comes out empty likewise keeps what is there. **Terminal offers are skipped**: what a sold listing said is history, and the only composition change one allows is removing a set — ↻ still works there, because that is an explicit act. The `edited` chip on the detail screen is not decoration: without it "why didn't my title update?" has no visible answer.

- A listing text carries exactly one token that is **not** about the copies — `{offerUrl}` (#415), an absolute link to the offer's own screen here, for a private note read on the marketplace page. It therefore reaches the engine through a `ListingTemplateContext` argument rather than through `TitleTemplateCopy`, and the engine stays pure: the URL is built in `src/lib/app-url.ts` off `BETTER_AUTH_URL` (the base a deployment already has to get right for Better Auth, rather than a second setting that could disagree with it), and is null — token empty, glue separator and empty line dropped by the existing tidy passes — when it is unset. It is deliberately **not** a title token, but `resolveTokenValue` still knows it everywhere, so a `{offerUrl}` typed into a title renders empty instead of showing literal braces. The awkward case is creation: an offer's texts are generated *before* its row exists, so the id it needs is not there yet. Rather than splitting generation, `createOffer` / `duplicateOffer` pass a null id and then re-run `syncGeneratedTexts` — but **only** when the platform's templates actually name the token (`templateUsesOfferContext`), which is also the guard that keeps the slug lookup off every ordinary render. The second pass is safe because it is the same function every composition change already uses: the edited-flag and terminal-state rules are not restated anywhere. What it renders is the **short** address (#416): `Offer.offerNo` is a per-collection sequence allocated exactly as `Item.itemNo` is (#268) — `allocateOfferNumber`, an atomic counter bump on `Collection.nextOfferNo` inside the creating transaction, never `max + 1`, because a number published in a marketplace note must not later mean a different listing. `/o/<collectionSlug>/<offerNo>` is a **redirect** to the canonical `/c/<slug>/offers/<id>` and nothing else: an offer has one screen, and this is an address for it. It carries the slug because the number is per collection. The whole reason it exists is that Colnect's private note is `maxlength=100` (#402) and the canonical URL is 69 of them before the collector writes a word — with an over-long text posted **not at all** rather than truncated (#405), so the long form silently cost the note.

- A **derived offer set label** (#379) is the offer title's own catalogue vocabulary, not a join of bare numbers: `compactCatalogNumberGroups` (factored out of `{catalog}`'s own resolver, so the token and the label cannot drift) groups by vendor + area prefix, collapses each group through #150's `compactCatalogNumbers` and writes the prefix once — `Mi·RU-NW 15-19`, `Mi·RU-NW 15-16 / Fi·PL 3`. `15 + 16 + 17 + 18 + 19` named no catalogue and stopped being readable at the second set. Which vendor leads follows from the stamp's primary area link, so a label needs the area tree: `makeOfferLabeller(collectionId)` (`src/lib/offer-labels.ts`) reads it **once per page** and resolves through the same pure `buildAreaVendorMaps` the client renders chips with — the auction lot name's pattern (#353). It is shared with `sales.ts` and `offer-photo-generation.ts` rather than reimplemented, so a set reads identically on the sets card, the photo card, the sellable-offer picker and a sale line. A **copy's** own label stays a bare number: it is listed inside a set whose label already names the catalogue. Set labels are deliberately absent from the photo fingerprint, so this changed no stored image.

- **`assertAddableCopies` answers in the order it was asked**, and that is not a nicety. It is the one chokepoint every composition path goes through (#394's disposal guard lives there too), and `addOfferSetsPerCopy` numbers a set per copy straight off its answer — while `OfferSet.sortOrder` is *canonical*, being what a buyer reads as "the second lot" (#306). It used to return the ids in `findMany` row order, so those positions were **whatever Postgres handed back**: a stock of duplicates ticked in one order could be listed in another, with nothing on screen saying why, and the same call could answer differently twice on identical data. The fix is to filter the **caller's** list (deduplicated — a copy named twice is one copy) rather than to iterate the query result, which is the general rule for any `where: { id: { in: ids } }` read whose *order* is then used for anything: a set has no order until someone writes one down, and `orderBy` on the read cannot recover an order the write got wrong. CI is what found it — the assertion that broke was on offer titles, three features away — which is the argument for pinning an order in a test wherever a write derives one.

- A **set's own value** (#378) — catalogue value + purchase cost — rides on `OfferDetailSet.holdings`, from `getHoldingsValuationByGroup` with one group per set: every copy is fetched and valued once for the whole offer, and the detail's suggested price (#190) is summed from those same figures rather than from a second valuation pass. Per set rather than per offer because a set is what a buyer takes, so it is the number the asking price is judged against. The same pair is given **twice** where the offer prices in another currency, in the header's own grammar: the **offer's currency leads** in strong type and the base figure follows muted behind `≈` (`MoneyPair`), converted with a single rate fetched once for the whole screen (the one `suggestedPrice` already used). The offer's currency leads even though the base figure is the *stored* one — a catalog value is valued in base and a cost basis frozen there — because it is the currency the collector operates in: the price, the platform and the buyer are all stated in it. So `≈` marks the **secondary reading** on this screen, never "the derived one": on the asking price it carries base, here it also carries base, and the two lines read alike. With no conversion available there is one figure and it takes the strong type. A **roll-up bar** in the sets **header band** adds the offer-wide total and the **per-set average** (`OfferSetsTotals`). That band is one row owned by `OfferSetsView` — the section heading and *Add set* are passed *in* from the detail panel as `heading` / `primaryAction`, and *Collapse all* is stacked under the button — because everything that addresses the whole section has to share one rhythm and one right edge: rendered as a heading row in the panel plus a toolbar row here, the two aligned to nothing in particular and the tall figures box stretched whichever row it landed in, summed from the per-set figures rather than re-aggregated — an offer never lists a copy twice, so its sets partition its copies and the parts add up exactly. An average divides by the sets that *carried* a figure, never by all of them: an unpriced set is a gap in the data, and averaging it in reports the listing as cheaper than anything in it is (it is the same rule, and the same number, as `suggestedPrice`, #190). It renders as an **amount column at the right edge** of the card header — money is right-aligned everywhere in the app — placed *after* the status chips so the column lands in the same place whether or not a card carries one. Both it and the roll-up bar are **grids**, never rows of self-measuring cells: the bar's two headings have to sit over the pairs they name and `cat`/`cost` have to line up whatever they contain, and a per-row flex layout drifts the moment one line carries an equivalent and the other carries `—`. `MoneyPair` therefore emits bare *cells* and no wrapper, and the hover sits on the row's **label**, since a tooltip wrapper around a row would be one grid item holding four. The equivalent column is dropped entirely (not left empty) when the offer prices in the base currency, so an offer with nothing to convert carries no dead track.

- A listing **description** (#266) carries a **format** — `plain | html | markdown` (#319; ADR-0019). It is configured on the platform next to the description template it applies to, and **seeded** onto each offer (`Offer.descriptionFormat`), so changing the platform never re-reads a listing already written. Rendering goes `descriptionToUnsafeHtml` (`src/lib/description-format.ts`, pure, DOM-free, unit-tested) → **DOMPurify** in `shared/rendered-description.tsx`; never inject the unsanitised HTML anywhere else. The same sanitised markup is what the copy control puts on `text/html` (with the source on `text/plain`) when copying formatted. The private note (#267) has no format.

- A platform's **listing-text length limits** (#403) are the text-side counterpart of #308's photo limits and sit beside them on `Contact`: `maxTitleLength` / `maxDescriptionLength` / `maxPrivateNoteLength`, nullable, **read live and never seeded** (#310's rule — they describe the platform, so tightening one reaches every prepared offer at once), surfaced on `OfferDetail.platformTextLimits`. Three columns because platforms cap the texts independently; Colnect using 100 for two of them (#402) is not a reason to fuse them, and the title cap arrived last (#610) because no platform's *form* had ever refused a title. Nothing truncates, ever: the wording is the collector's, and a text shortened to fit is a listing nobody proofread. Counted in **UTF-16 code units** (`listing-text-limits.ts`, pure), because an HTML `maxlength` counts in those and the platform's own field is the authority on its own number — being cleverer with code points would report 99 where the platform reports 100. The shared `TextLengthCounter` renders **nothing** without a limit, so every surface passes one unconditionally; on the offer's own card it counts the **draft** while the field is open (watching the number come down as you cut is the point) and the stored **source** otherwise — what `⧉` copies, tags included, which is what the platform's field will hold.

- **An over-long text blocks the `preparing → ready` gate** (#636, `evaluateListingTextLimits`). #403 deliberately made the cap a *report*: a Colnect or Allegro form refuses one over-long text in front of the collector, so learning about it there costs one paste, and the cap was pointedly **not** a listing precondition — a wrong grade is a false claim about the goods, a long description is a paste that visibly fails. Delcampe changed the arithmetic rather than the principle. Its listings are created from a CSV (#610) and Easy Uploader refuses the **whole file**, after a batch of forty was assembled, marked ready and exported — which is the sentence `listing-text-limits.ts` had carried in its own header since #403: *a limit discovered in that form is discovered too late*. So the caps join #418's preconditions on the one transition that means "this listing is assembled", in the same shape and the same hover hint; nothing new is invented and **nothing is still truncated**. The blocker names the text, both numbers and where it is fixed, because a count with no target is not actionable in a batch of forty. Because the caps are read **live** (#310), tightening one in Settings reaches offers that are already Ready — they cannot report on a Ready gate they have passed, so what reports them is the **bulk listing workspace**, whose cards carry the same two kinds of reason (`ListingCardBlocker`) and whose heading is therefore neutral about who is refusing: the Assistant's preconditions apply only to a platform with a module, while a cap applies to every platform, Delcampe included, where nothing is posted by an Assistant at all. The Delcampe export refuses on the same numbers from its own side (ADR-0036 §3), which is belt and braces on purpose: the gate stops a batch being assembled, the export stops one being written.

- **One photo per copy** (#434) is the bulk form of #313 mode a, a second button beside *Add attachments* on the photos card: `attachOfferItemFrontPhotos` walks the offer's sets in plan order and attaches each copy's **front** scan as its own `copy_photo` attachment. Front or nothing — a back is the other side of a stamp the front already shows and an extra is a detail shot, so a copy with no front scan is **skipped and named** in the result (#314's "visible rather than silently missing"), never quietly substituted. Sets the plan excludes (#315) are excluded here too, and a front scan already attached on its own is passed over, so pressing it again tops the plan up instead of doubling it — a scan that is only a *tile* of a hand-built collage (#331) does not count as attached, since breaking out of that grouping is the point.

- **Paired front and back** (#694) is a fourth `photoSides` value, `paired`, and a `pairSides` flag on `CollageTemplate` — both, because the two answer different questions: the platform (and the offer) says *which* sides are photographed, the template says *how* the two are arranged, and `applyCollagePairing` is the single rule where they meet. Pairing therefore only ever moves between `both` and `paired` and leaves a one-sided listing untouched, whichever side is edited — seeding from a platform's default template, and picking a template by hand in the photo-settings dialog, apply the same function. It is not a fifth thing to choose: a paired listing photographs exactly the scans `both` does. Mechanically a paired cell is **one tile whose bytes are the two scans joined**, composited in `photos/collage.ts` before the layout runs, which is what keeps the geometry one mechanism — `collage-layout.ts` never learns about pairs, a cell is simply a wider tile, the label strip spans it for free (#312) and `auto` scores it as one (#413/#514). The one thing that cannot be solved per cell is `trueSizeScales`, which normalises against the worst-shrunk scan on the whole image, so every scan is scaled first and the pairs are joined after; a cell's two scans sit half a gap apart, a share rather than a setting of its own, because at the full gap a pair is indistinguishable from two neighbours. The **all-or-nothing rule is deliberately not applied here**: a cell pairs whatever its copy has, a copy scanned on one side takes a narrower single-scan cell, and the group never loses its image over an unscanned reverse — the gap is visible in the picture, which is the thing that rule guarantees elsewhere. What is still reported (#314) is a copy with **no scan at all**, which takes no cell and would otherwise vanish unremarked. The grouping cost (#521) and the rendering read one `groupImages` helper, because a paired group costs one upload slot where `both` costs two and the two must never disagree about which images exist.

- A listing **sold on its platform but not yet recorded here** (#499) is counted as **sold**, not as active (#501) — a reclassification of the *aggregates* and the *state chips*, never of `Offer.state`, which only recording the sale moves. Three places read it: `aggregateOfferAsking` partitions the flagged rows out of the asking value (and out of the per-platform rows and the holdings pass behind them) into its own `platformSold` total, which the bar draws as a second line when non-zero; `offerFilterCounts` moves each flagged offer out of its stored state's bucket into `sold`; and `stateSelectionWhere` makes the chips *list* what they count — picking `sold` ORs the flagged ids in, picking anything else NOTs them out. The **default view stays untouched** on purpose: with no state chip on, a flagged offer is exactly the one needing attention, and hiding it behind a chip would undo what #499 flagged it for. `offerListWhere` accumulates into a single `AND` list (the `lotListWhere` rule) — the search is an `OR` and this selection can be either, so sibling keys would silently replace one another.

- The **flagged-offer id set is not an overlay** when a state chip is on: `resolveOfferOverlays` returns `platformSoldIds` *beside* `ids` rather than inside it, since being flagged decides which chip an offer answers to, while only selecting the *Sold, not recorded* chip narrows the list to the flagged ones.

- **Stepping from one offer to the next** (#429) is the filtered list carried into the detail screen: the offer row appends `offerListContextQuery(filters)` to the link it opens (`offers/list-context.ts`, pure and unit-tested), the detail page parses it back and renders `‹ Previous · 3 of 12 · Next ›` beside its **← Offers** link, which now points at the list *as it was*. It travels in the **URL, not off #325's remembered filters**, for two reasons: an offer is opened from other screens too (the copies popup, a short link, a bookmark), where a walk through a list nobody is looking at would be an invention — hence `from=list` as an explicit marker, since a context with *no* filters is a legitimate walk over the whole list and is otherwise indistinguishable from a plain deep link — and a link to "the third preparing offer on Colnect" then still means that when it is reopened. The remembered **show-closed** toggle (#245) is part of what the list was showing, so the walk carries it (`closed=1`) even though the list keeps it out of its own URL; the way *back* deliberately drops it again, the list reading its own stored value. Server-side it is `offerListNeighbours` — the ids alone, over the same `where` and the same `OFFER_LIST_ORDER_BY` the list reads, which is where the order got its `id` tiebreak: offers created in one transaction share a `createdAt`, and an unstable order both repeats a row across pages and skips its neighbour. Position falls out of the same array, so the indicator is free. The query is asked **once per offer and then frozen** (`staleTime: Infinity`, and a key outside `offerKeys.all` so `invalidateAll` cannot reach it): the use case is finishing an offer — which usually moves it *out* of the filter that was showing it — and stepping on, so an answer that refreshed itself would take the walk away at the moment it is needed. An offer not in the filtered set at all reports `position: null` and the strip is absent; the two ends are disabled rather than hidden (#273), the position beside them saying which end.

- Quick-sell (#225) is reachable from the offers list **and** from an offer's own detail screen (#390). `SellOfferFlowDialog` takes a structural `SellableOfferSubject` (id, name, label, platform, price, currency) rather than `OfferListItem`, so `OfferDetail` satisfies it and there is one flow rather than two that drift; the precondition is the same at both ends — non-terminal, ≥1 set. The detail page computes `today` at request time exactly as the list page does, so a sale started from either place defaults to the same date.

- **Acting on a selection of offers** is #373's multi-select brought to the offers list, with three deliberate divergences from the copies one. The selection is keyed on the filter signature and dropped when it changes (adjusted during render, never a `setState` in an effect) and it holds the **offers themselves** rather than their ids, because a bulk run reports its refusals per offer and the row it names has to survive the invalidate-and-refetch that follows. First divergence: **every row gets a checkbox**, terminal ones included — the copies list has *one* eligibility rule covering every bulk action, while these two disagree (a withdrawn offer has nothing to withdraw but is still deletable; one holding a sold set is withdrawable but never deletable), so a gutter following either would misdescribe the other, and what an action cannot do it refuses per offer and names. Second: the bar is **always drawn while there are rows**, not only once something is ticked, because the select-all box lives in it — aligned to the rows' own `SELECT_STRIP` gutter — and a bar that appears after the first tick leaves the whole feature undiscoverable; its box is **indeterminate** on a partial selection, a box reading "off" over twelve ticked rows being the one thing it must not say. Third: *select all* covers the **loaded** rows and says how many that is, the list being cursor-paginated — "all" over the whole filtered set would be a promise about offers never fetched, and one click deleting three hundred listings most of which were never on screen. Server-side both are `runOverOffers` in `actions/offers.ts`, which **collects refusals rather than throwing** (`generateOffersPhotosAction`'s rule, #323) and calls the same `setOfferState` / `deleteOffer` a single row does, so the lifecycle guard and the sold-set guard are each stated once. The client keeps **exactly the refused offers ticked** afterwards — they are what is left to deal with, and a selection left whole is an invitation to run it twice — and lists the reasons one per line under the bar, never a count, each being fixed somewhere different. A run where **nothing** succeeded keeps the confirm dialog open with the reason in it (a blocking failure belongs next to the decision that caused it), while a partial one closes and reports in the strip.

- A **flag shown on a list is shown on the thing's own screen too** (#505): the *Sold on Allegro* chip reaches `OfferDetail.platformSale` from the same `unrecordedPlatformSales` the list reads (narrowed to the one offer), never a second comparison. A chip seen in passing and then missing from the page it was clicked through to reads as having been dealt with.

- **A copy promised in an agreed trade cannot go live** (#639). The mirror of the gate `setTradeStatus` runs at `agreed`, refusing on this end at **`active`** and nowhere earlier: a `preparing` or `ready` offer competes for nothing, and a collector may perfectly well prepare the listing they will post the day the trade falls through — `isLiveState`'s own answer, not a second reading of it. `setOfferState`, `createOffer`'s live-status path and the three composition paths **onto an already-active offer** all ask the same question, because adding a committed copy to a live listing puts it in front of buyers just as surely as activating the offer around it would. It refuses **by name** (#418's shape, the trade and its partner) and, unlike `assertAddableCopies`' silent drop of a sold copy, refuses the **whole add**: a sold copy is gone and there is nothing to decide, while a promised one is a decision the collector has already made and may want to unmake, so leaving it quietly out would hide the very fact they need. `OfferDetail.tradeCommitments` carries the same list to the offer's own screen at **every** state — a flag shown on a list is shown on the thing's own screen too, and an offer being assembled out of stock that is already spoken for is worth knowing about while there is still time to compose it differently. Nothing is stored anywhere: a commitment is a give line on an agreed trade, read through `trade-reservations.ts`, which sits below both domains and imports neither.

- **The listing's own id is stored, not parsed out of its address** (#696). `Offer.colnectSaleId`, beside `allegroOfferId` (#477) and `delcampeItemId` (#611) and unique per collection exactly as the latter is. #412 already captures the entry Colnect lands on after a Save and #462 reads the sale code back out of it, which is enough to *edit* a listing and not enough to *find* one: Colnect states one code at two addresses — `/<locale>/market/sale/<code>` and `/<locale>/sell/edit/sale_id/<code>` — and the locale segment is **whatever Colnect served**, so an offer looked up by its URL string is looked up on a value that varies with the language of the answer, cannot be indexed and cannot be made unique. The transaction import (#698) does that lookup once per row. Both are kept and neither is derived at read time: the URL is the address a person clicks, this is the id the app joins on. It is written **wherever the URL is written** — `resolveColnectSaleId` in `offers.ts`, called from `patchOffer`, `updateOffer`, `createOffer` and `duplicateOffer` — rather than only on the capture path, and that is the change of mind worth recording: a code left standing behind a *corrected* URL would send #462's update to somebody else's listing, and that is the one step in this app that writes to a live marketplace. So a URL naming no sale **clears** the column, and the pair can never come to disagree. A code another offer holds is refused **by name** (`duplicate-listing`, naming that offer's `offerNo`) with the unique index as the real backstop — a raw constraint violation says nothing a collector can act on, while "offer #41 is already this listing" says which of the two has the wrong link on it. `publishOffer` asks the question **before** its transition even though `patchOffer` asks it again on the way in, since a refusal after the state had moved would leave a live listing with no address recorded on it, which is precisely what the URL-after-transition order exists to prevent. The parser is `colnectSaleCode` in the pure `colnect-link.ts`, mirrored by hand from the extension's own (separate builds, no import path) — and the migration's backfill strips query + fragment **before** matching so the SQL reads the same string `URL.pathname` gives the parser, writing a code only where it is unique inside its collection and leaving both rows of a collision null. It reaches the Assistant as `OfferListingKit.listingId`, deliberately neutral rather than a Colnect-shaped field: a module turns an id into whatever address it needs, and `colnectSaleEditUrl` prefers it while keeping the URL parse as the fallback for a listing posted before the column existed. The mirror on the extension side is **optional** (`listingId?`), so an older instance's kit is still a valid task.

- **Which set left on a sale line is a decision, not a fact about the order** (#697). `SaleLine.setChoicePending` — the line still names a set and `offerSetId` stays NOT NULL, so every read that assumes one keeps working; the flag says the set was **picked, not chosen**. An offer at quantity 3 has three sets and a buyer who takes one has said *one of these*, not *this one*: the sets of one offer are the same thing at the same price, which is why they are one listing, so which copy leaves is the seller's own fulfilment choice, made at the packing table — and it changes after the fact when a copy turns out to have a thin. That is why `mapLineToSets` answering `ambiguous` over a multi-quantity order (#463/#612) is correct as a statement about the order and useless as a workflow, and it is the state #698 and #699 both need to be able to write. `swapSaleLineSet` is the correction, and it exists because `removeSaleLine` + `addSaleLines` — the only path before it — throws away the line's **price** and its per-copy **`packed`** marks on the way. Here the price is untouched (it is what the buyer paid, and swapping which copy goes does not change it), the `SaleLineItem` rows are rewritten to the target's full current copy set (whole-set integrity unchanged), `packed` marks are **dropped with the copies they were about** — a different copy has not been packed — and the flag clears. Choosing the set the line **already names** is *confirming* it: the flag clears and nothing else moves, so a line whose copies are already in the parcel keeps its packing. The target must be of the **same offer** (another offer's set is a different listing another buyer is looking at) and still free, with the `sale_line_item.itemId` unique as the backstop; the offer's own `sold` state is deliberately **not** recomputed, a swap inside one offer leaving the number of its sets that have sold exactly where it was. `listSaleLineSetOptions` serves the picker in `SaleSetOption`'s shape — the one `listSellableOffers` already serves the sale-creation flow, so the collector chooses from the same list in the same words — and unlike that read it asks nothing about the **offer's state**: an offer every set of which has sold is `sold`, and is exactly the offer a quantity sale is being re-allocated inside. A pending line is flagged on the sale detail *and* on the sales list (`SaleListItem.pendingSetChoiceCount`), from the same column, in the `warning` tint rather than *Needs action*'s `error` — nothing is wrong with the record, there is simply a decision nobody has made yet. Three things about the **picker** are decisions rather than incidentals. It draws the set list **at every length, the single-set offer included**: what the collector opened it for is *which set this line is standing on*, and a sentence saying there is nothing else to choose answers a question nobody asked while withholding the one they did — the one row marked *On this line now* says both at once, and `Choose` stays enabled there because confirming is an idempotent write and a lone disabled affordance is a puzzle. It shows each set's **copies opened out**, as the Copies list' own `InventoryItemRow`s **with their scans**, which is why `SaleLineSetChoice` carries `copies: ItemListItem[]` from one read rather than a list of labels: choosing among interchangeable sets is choosing among *physical pieces*, and the thin, the short perf and the cancel that separate two copies of one stamp are visible in the scan and nowhere else — behind a details toggle this dialog would name three identical rows and send the collector to another screen to do the comparing. And the **chip is the affordance as well as the signal** — pressing *Set not chosen* opens the very picker the `⋮` entry opens, a flag that announces an outstanding decision and then makes the reader go and find its control being two clicks where one will do. **Filtering** happens at both altitudes, and the one that matters is on the **sale detail**, where the sold units are: `SoldUnitsView` grows a *Set — All / Not chosen (N)* group beside *Packed*, narrowing the unit cards so a collector can work through exactly what is outstanding. Three things about it are decisions. It is **not persisted** the way the group / sort / packed prefs beside it are (`usePersistentString`, #325) — those record how this collector likes to *read* a packing list, while this is a question asked of *this* sale today, and a remembered one would open the next sale showing fewer units than it holds, which reads as a lost line rather than as a filter. It is **drawn only while `pendingCount > 0`**, because on almost every sale every set was chosen on the way in and a permanent control for a condition nothing meets is furniture on the one screen that is read while working. And it **self-clears** — `setFilter` is derived as `pendingCount > 0 ? raw : "all"` rather than held — so settling the last outstanding unit cannot empty the screen under the collector who just settled it, which is also why the view needs no empty state for it. It is scoped to the Lot grouping, the other two drawing a copy stream with no unit cards to narrow. The **list-side** counterpart (`SaleListFilters.setChoicePending`, `?setChoice=1`, `lines: { some: … }` — one undecided line stops the whole parcel) answers the prior question, *which parcels* need attention: deliberately **not** a chip among the fulfilment statuses and not remembered either, since it selects on a different axis — a decision outstanding *inside* a sale, which can be outstanding in any status. Both are worklists that empty themselves as the decisions are made.

- **The buyer is asked which copy they want, through a link** (#699; [ADR-0013](../decisions/0013-offer-owned-sale-composition.md) §7). #697 leaves the set choice with the seller; on a listing of three identical copies the seller is not the best person to make it, because the three are the same thing only as far as the listing was concerned — the centring, a corner perf and the exact shade differ, and the person who is going to own one has an opinion. `SaleShareToken` is `TradeShareToken`'s shape (ADR-0039 §9) with the trade swapped for a **single sale**, and that swap is the whole security argument one table over: the token names one sale and every read it authorises is about that sale's own pending lines and the copies their candidate sets hold. One row per sale, regenerating replaces it, the hash resolves and the seal is for display (#681) — and `share-address.ts` is the old `trade-share-address.ts`, renamed rather than duplicated, because two token kinds now seal the same way. What the sale token deliberately has **no** counterpart of is `showValues`: a trade's page is a column of figures and disclosing them is a real choice, while this page carries none — the buyer knows what they paid — so there is no setting. The pick is `swapSaleLineSet` and nothing beside it (the copies move, the price stands, `packed` marks drop with the copies they were about, the flag clears), plus one column in the same write: `SaleLine.setChosenByBuyerAt` says the answer is the buyer's, which is how the seller reads *Buyer chose* on the unit card and how the page knows which **settled** lines are still the buyer's to change. Any later swap by the seller clears it — the parcel is theirs to pack, and an overridden pick is no longer the buyer's answer. Three decisions are worth keeping. The **window is the parcel** and closes at `packed`: from there the question has been answered in the physical world, and a pick landing afterwards would rewrite the record while dropping packing marks — the link still opens (the buyer is entitled to see what was chosen) and says why it no longer asks, and the seller's own override stays available in every status. The buyer may **re-pick** until then, which is why the page keeps a line they answered instead of dropping it the moment the pick clears `setChoicePending`. And **nothing is pre-selected** while nobody has chosen: the set the line names then was picked, not chosen, so marking it would present an automatic pick as a decision the buyer had taken part in. The page (`/s/[token]`, its `choice` and `photos` routes beside it) reuses the partner page's stylesheet and its `SharePhotos` — moved to `src/app/share/` and given a `base` prop, since what differs between two share pages is the address the pictures come from — and the candidate sets come from `listSaleLineSetOptions` itself (`{ withCopies: false }`), so the two ends of one link cannot come to offer different sets.

- **A Colnect sale comes back from the transaction the collector is packing from** (#698; [ADR-0041](../decisions/0041-colnect-transaction-import.md)). #612's flow on the marketplace next door, and deliberately its shape rather than a second design: the Assistant marks each transaction with what it is here, one click records it, `Sale.externalRef` carries Colnect's transaction id so a re-import is a link rather than a second sale, and the order is **all lines or nothing** with every reason named at once. The pure half is `colnect-order-rules.ts` (the amount, date and item-count readers, `chooseColnectSets`, `planColnectOrderSale`), `colnect-order.ts` performs it, behind `GET …/sales/by-colnect-order` and `POST …/sales/colnect-order` — session-or-token, like the marker endpoints they are the sibling of. Five things differ from Delcampe's, and each is something Colnect **states** that Delcampe did not. **One join key**: a transaction row prints no seller reference, so a row finds its offer through `Offer.colnectSaleId` (#696) and nowhere else — the way through a refusal is one address pasted onto the offer, which is why #698 waited for #696. **A pick instead of a refusal** (#697): an offer with more sets left than the row bought records the lowest-`sortOrder` ones with `setChoicePending`, where `mapLineToSets` answers `ambiguous`; quantity *greater* than the sets left still refuses, that being the order disagreeing with the inventory. **A labelled total**: the header prints `Items total`, `Shipping price`, `Discount` and `Total with shipping`, so #205's anchor is chosen **by its words** — on a transaction with no postage the first and the last are the same number, and picking the larger figure would be picking the meaning by accident. **A shipping method** (#468): written as printed and matched against the platform's dictionary by name (`matchShippingMethod`, the one thing that stayed in `allegro-sale-rules.ts` when the rest moved to `order-sale-rules.ts`), with **no cost** either way — the dictionary says what postage usually costs, not what this parcel did (#206). **One date for the order** (`Started:`), so ADR-0038's latest-of-the-rows rule is not repeated. What is unchanged is what matters: the sale's currency is the platform's (#196) and a figure naming another refuses — Colnect renders every amount in the **viewer's** display currency, which is a seller-level setting (#402) and not a fact about the sale — a zero-priced row refuses, the buyer is a login and a name with the postal address on the same page never read, and Colnect's own ladder is not mirrored onto `Sale.status`. The one deliberate hole is **`Item count` greater than 1**, which refuses: the observed transaction's fifteen prices sum exactly to `Items total`, so nothing distinguishes a row's unit price from its line total while `SaleLine.price` is per set — answer it on the first real multi-item row and lift the refusal (ADR-0041 §5).

- **A sale is a composition change, and the strongest one** (#700). Every offer mutation that alters what a live listing would show stamps `Offer.listingContentChangedAt` (#542) — sets added or removed, copies joined, reorders, texts, the header fields `headerChangeIsDrift` counts. Selling was the one that did not, and it is the change that matters most: the sold set leaves what is sellable, `readInputs` drops it from the photo plan (#315), and the entry on the marketplace goes on offering a quantity it no longer has with a picture of a copy that has gone. So `addSaleLines` stamps it, **after** its own `sold` flip — an offer that just sold out is `sold`, which `LISTED_OFFER_STATES` excludes, so the sale that *closes* a listing asks nobody to go and fix it while the one that leaves something behind does. `removeSaleLine` and `deleteSale` stamp it too, the set coming back being the same change in reverse. Deliberately **not** a fourth needs-action reason: ADR-0013 §4's three are collisions — one piece of stock committed twice — while this is a listing out of step with its own record, which is exactly what #542 already means, badges, filter, notification group and all three ways of clearing it (the Assistant's update #462, a republication, *Mark as up to date*). The two writes behind the column moved to `offer-listing-sync.ts` for this: `sales.ts` must reach the same rule rather than spell it a second time, and it must be able to make the write inside its own transaction, so the stamp and the lines that caused it stand or fall together. - **The Assistant generates the listing photos on its way to the form** (#727). An offer whose images do not exist yet is not a reason to withhold **⚡ List via Assistant**: generating them is a press on another card and then a wait, which is exactly the errand a posting session should not be interrupted by — so the handoff *does* it, as step one of `useAssistantHandoff.start`, in front of the kit fetch. What "not ready" means is not re-decided there: `evaluatePhotoReadiness` is the same pure rule `preparing → ready` is refused by (#311/#418), asked from the client over the plan the Photos card reads (`plan.imageCount`, not the state's `plannedCount`, which is what the *last run* planned). The run is `generateOfferPhotosAction` and then a poll of the photos endpoint at the card's own 2s cadence, capped — past the cap the strip stops and says the run carries on, a spinner that never ends being the one outcome that tells the collector nothing. A run already queued or in flight is **waited on rather than stacked**. The state is `generating`, first of the same sequence the extension finishes, because the collector asked one question. Three consequences worth stating. A plan that is merely **out of date** is re-rendered too: the kit still serves stale images as a signal and never a refusal (#405) — an offer already live must not become unlistable because it gained a set — but that is about what may be *served*, not about what somebody who has just asked for this listing to be posted should get, and one rule for both is what lets the button stop disabling itself. `isPhotoReadinessBlocker` is that split, on the codes rather than the wording: the offer screen's **List via Assistant** counts only the gate's non-photo half against itself while **Mark ready** beside it still counts all of it, since only one of the two buttons goes and fixes the photos. And the **Preparing** path (#554) inverts: the `preparing → ready` transition is now the handoff's `prepare` callback, run *after* the photos and before the kit, because that transition is refused on exactly the blockers step one clears — a refusal comes back as a message and stops the run in its own words. What the run could not draw (#314) is **reported, not refused**: skipped sides become `AssistantHandoff.notes`, warning lines in the strip above the extension's own field skips, on the rule the handoff has always followed — a set of eight whose back collage is missing over one unscanned reverse still lists, with one picture fewer. The one photo outcome that *does* stop it is a run that produced **nothing to upload** (measured on the kit's own `publish && !overLimit` filter), where the form would be filled and the pictures a buyer decides on would simply be absent.

- The **listing wizard** (#730, `offer-listing-wizard-dialog.tsx`) is a *stepped dialog* over the offer's own screen — Items, Price, Publish — and it chains pieces that already exist rather than adding any of its own: step one is the Items card (#423/#669) drawn `embedded` (always open, no card chrome, and the collapse memory untouched, since the wizard is not a visit to the detail screen), step two is the offer's price field with its catalog-value suggestion and one **Market** link per row, step three is **List via Assistant** (#407/#554/#727) with the run's own report strip. The three shapes were weighed: a sub-route would re-fetch the offer and re-state its header, and a stepped mode over the page itself would rewire the screen every other job is done on — a dialog leaves the offer intact one Escape away, which is what a walk stepped *out of* the moment something needs fixing elsewhere actually needs. **Nothing in it gates**: the first step names its gaps (`src/lib/offer-listing-wizard.ts`, whose `listingItemGaps` the Items card's own `+ CV all` chip is counted by, so a summary and the heading under it cannot disagree) and lets the collector go on regardless, because every one of those gaps is already reported by the ready gate (#418) and refused by the Assistant itself — a second, stricter rule enforced only inside one dialog would be a rule no other surface knows about. It drives the **screen's** handoff rather than opening one of its own (one hidden element per screen, else two race for the extension's reply) and writes the price through the screen's own `patch`. The end of the walk is `?wizard=1` on a **Next offer** link built from #429's context — the list the offer was opened from, or, opened from nowhere, the offers still `preparing` on this platform — and the neighbour is read once and never re-asked, since posting takes the offer out of a `preparing` filter and a re-asked question would answer "not in this list" at the moment the next one is wanted. It is offered wherever `hasListingModule` is true and the offer is `preparing` or `ready`: nothing in the three steps is Colnect's. Opening it made the Items card's own dialogs (`+ CV all`, quick value, **Listed as…**, the variant price grid, the stamp form) **portalled to the document**, the way every dialog openable from inside another one already is — `DialogShell` centres its panel with a transform, which makes that panel the containing block for a fixed-position child and clips it to its `overflow: hidden`.
