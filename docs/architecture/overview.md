# Architecture Overview

## Deployment Model

Stamporama uses separate Docker Compose files for local development and self-hosted production.

| File | Purpose | Command |
|---|---|---|
| `docker-compose.yml` | Local dev: app + bundled PostgreSQL, built locally | `docker compose up` |
| `docker-compose.dev.yml` | Hot-reload overlay, source mounted | `docker compose -f docker-compose.yml -f docker-compose.dev.yml up` |
| `docker-compose.prod.yml` | Self-hosted production: prebuilt GHCR image, external DB | `docker compose -f docker-compose.prod.yml up -d` |
| `docker-compose.network.yml` | Optional overlay: connect app to a shared Docker network for DB access | combined with `docker-compose.prod.yml` via `COMPOSE_FILE` |
| `docker-compose.e2e.yml` | Isolated PostgreSQL on port 5433 for integration tests | started by `pnpm test:integration` |

The `COMPOSE_FILE` variable in `.env` sets the active file list so operators can run bare `docker compose` commands without specifying `-f` flags.

## Production services

Production does not run a database container. The operator provides an external PostgreSQL via `DATABASE_URL`. **PostgreSQL 15 or newer is required** — migrations use `NULLS NOT DISTINCT` unique indexes (see [ADR-0006](../decisions/0006-multidimensional-catalog-prices.md)). The bundled dev/e2e containers run Postgres 16.

```
┌─────────────────────────────────┐
│  app  (Next.js, port 3000)      │
│  ghcr.io/michalwy/stamporama    │
└──────────────┬──────────────────┘
               │ DATABASE_URL (external)
               ▼
         [operator's PostgreSQL]

Optional (autoupdate profile):
┌─────────────────────────────────┐
│  watchtower                     │
│  polls GHCR, restarts on update │
└─────────────────────────────────┘
```

## Docker Image

The `Dockerfile` uses four stages:

| Stage | Base | Purpose |
|---|---|---|
| `base` | node:22-alpine | corepack + pnpm |
| `deps` | base | install dependencies only |
| `builder` | base | generate Prisma client + build Next.js |
| `runner` | node:22-alpine | runtime image with full `node_modules` |

The runner stage ships the full `node_modules` (not Next.js standalone output), so `pnpm start` works without re-installing. `pnpm-workspace.yaml` is copied to the runner as a safety net for the build-scripts allowlist.

The `STAMPORAMA_VERSION` build argument is baked into the image and exposed at runtime via `process.env.STAMPORAMA_VERSION`. The `getAppVersion()` function in `src/lib/version.ts` reads it.

## Prisma / Database

Stamporama uses [Prisma](https://www.prisma.io/) with the `@prisma/adapter-pg` driver adapter. The adapter uses the `pg` npm package for PostgreSQL connections — no native query engine binary is required.

**Generated client:** `pnpm prisma:generate` writes the TypeScript client to `src/generated/prisma/`. This directory is generated and should not be edited by hand; it is committed to the repository so that CI jobs that do not run `prisma:generate` before type-checking can still compile.

**Migration workflow:**

| Context | Command | Notes |
|---|---|---|
| Local development | `pnpm prisma:migrate` | Applies + generates new migration against local dev DB |
| Docker Compose (any stack) | `prisma migrate deploy` | Runs automatically on container start before `pnpm start`/`pnpm dev` |
| Integration tests | `pnpm exec prisma migrate deploy` | Applied automatically by `pnpm test:integration` |
| CI (integration job) | `pnpm exec prisma migrate deploy` | Runs against a fresh service-container DB |
| Production | Handled automatically on container start | `docker-compose.prod.yml` runs migrate deploy before `pnpm start` |

**Schema:** `prisma/schema.prisma` — PostgreSQL datasource, client output at `src/generated/prisma`.

**Config:** `prisma.config.ts` — loads `DATABASE_URL` from the environment (via dotenv), sets schema and migrations paths.

**Client singleton:** `src/lib/db.ts` — exports `prisma`, a `PrismaClient` instance initialized with the `PrismaPg` adapter. Uses `globalThis` caching to avoid exhausting connections during Next.js hot-reload.

## Domain Model

### Collection

The `Collection` model is the top-level organizing unit. All stamp data belongs to a collection. A user can own multiple collections; each collection belongs to exactly one user.

**Prisma model** (`prisma/schema.prisma`):

```prisma
model Collection {
  id        String   @id @default(cuid())
  slug      String
  name      String
  ownerId   String
  createdAt DateTime @default(now())
  owner     User     @relation(fields: [ownerId], references: [id], onDelete: Cascade)

  @@unique([ownerId, slug])
  @@map("collection")
}
```

**Key design decisions:**
- `@@unique([ownerId, slug])` enforces slug uniqueness per user at the database level and serves as the index for fast slug lookups.
- Slugs are auto-generated from the collection name (lowercase, hyphens); collisions within a user's collections get a numeric suffix (`-2`, `-3`, …).
- Authorization uses `getCollectionBySlug(ownerId, slug)` — a lookup by the compound unique key. A slug that belongs to a different user returns `null`, producing a 404 rather than a 403 to avoid leaking slug existence.

**Domain layer:** `src/lib/collections.ts` — `createCollection`, `getCollectionsByOwner`, `getCollectionBySlug`. Imports `"server-only"` to prevent accidental bundling into client code. Pure slug utilities live separately in `src/lib/slug.ts` (no `"server-only"`, unit-testable).

**Collection routes:** `/c/[collectionSlug]/` — the layout validates the slug and authorizes the session user as owner before rendering.

**Dialog primitive:** All modal dialogs use the shared shell at `src/app/dialog-shell.tsx`. It provides: backdrop, header with close button, scrollable body, optional fixed footer.

### Physical holdings (`Item`)

`Item` represents a collector's physical copies. Per ADR-0007, there is **one row per physical copy** — no quantity field — because copies of the same stamp and condition can differ (e.g. postmark type) in ways that affect value and intent.

- `stampId` → `Stamp` at any level of the variant tree: a base stamp (`parentId = null`) means the variant is unknown; a variant row means the copy is identified. The tree level implicitly encodes variant certainty; there is no "unknown" flag.
- A `Stamp` may carry a `colnectId` (#247, part of #155): the numeric Colnect Marketplace item-ID, stored as a plain optional column — **not** through the `CatalogVendor`/`StampCatalogNumber` machinery. A Colnect item-ID is an external identifier, not a priced catalog number, and must be settable on any stamp regardless of area, so it needs neither a vendor row nor per-area attachment. No uniqueness constraint. It surfaces in stamp reads and is editable in the stamp form alongside the catalog numbers; a later browser agent (#155) will populate it in bulk.
- `ColnectCatalogMapping` (#248, part of #155) translates a **Colnect catalog abbreviation** (Mi, Sn, Yt, Sg, AFA, Pol…) to one of the collection's local `CatalogVendor`s, so future number-matching can line Colnect's catalogs up with ours (Colnect `Pol` = our Fischer `Fi`). One row per `(collectionId, colnectAbbrev)`; only mismatches need a row. Resolution (`src/lib/colnect.ts` `resolveColnectAbbreviation`): an explicit row wins; else it falls back to a local vendor whose own `abbreviation` matches (case-insensitive); else `null` — unmapped abbreviations are ignored by the matcher, not errors. Edited under **Settings → Colnect**.
- **Colnect catalog-number matcher** (#250, part of #155) — `POST /api/collections/[id]/colnect/match` takes a batch of extracted Colnect items (`{ colnectId, catalogRefs: [{ catalog, number }] }`) and decides which of our stamps each one is, writing the Colnect ID onto unambiguous matches. Matching is **strict full-key**: a Colnect ref matches only when `vendorAbbrev + effectiveAreaPrefix + number` — folded of spacing/punctuation (`catalogMatchKey`) — is exactly equal, after resolving the ref's abbreviation through `ColnectCatalogMapping` and reconstructing the stamp's key from its area's inherited per-vendor prefix (`src/lib/area-prefix.ts`). The decision matrix (`src/lib/colnect-match.ts` `decideColnectItem`, pure/unit-tested): 0 candidates → `skipped`; 1 clean candidate → `auto` (write); 1 candidate that partly conflicts, or that already holds a *different* `colnectId`, or >1 candidates → `needs-confirm` with the candidate list — an existing ID is **never** silently overwritten. A `dryRun` flag computes everything and persists nothing (preview / write safety net). `POST …/colnect/confirm` commits a user-chosen match, refusing to overwrite a different existing ID unless `allowOverwrite` is set (409). Orchestration in `src/lib/colnect.ts` (`matchColnectItems`, `confirmColnectMatch`).
- **Colnect catalog-number backfill** (#280, part of #155) — an opt-in `backfill` flag on both matcher endpoints fills a matched stamp's **missing** catalogs from the numbers the Colnect page prints. Writing is the **inverse of matching**: we store the bare `StampCatalogNumber.number` while Colnect prints it joined with the country code, so the area prefix has to be stripped. The split rule (`src/lib/colnect-backfill.ts`, pure/unit-tested): the prefix is the **leading space-separated, digit-free token** (`PL 3690` → `PL` + `3690`; `BL132`, `3706-3711`, `ATM2.2x` have none). Per reference — matches our number → nothing; we hold a different one → `conflict` (reported, never written); no prefix printed → stored verbatim; prefix equals the area's effective prefix for that vendor → bare remainder stored; area sets no prefix → `skipped-no-area-prefix`; prefixes differ → `prefix-mismatch`; unmapped abbreviation (#248) → ignored. Proposals hang off each `ColnectCandidate`, so a dry-run preview shows exactly what a write would add — including for the candidates of a `needs-confirm` item, which `…/colnect/confirm` then applies to the stamp the user picks (it takes the item's `catalogRefs` alongside the match). A fill colliding with an existing catalog identity respects `duplicateCatalogMode` (#85): `duplicate` (not written) under *block*, written with a `duplicateWarning` under *warn*. Applies to already-linked stamps too, and recomputes `primaryCatalogSortKey` for touched stamps (#181, ADR-0014). Off unless requested, so an older client can never write numbers by accident.
- **Collection route auth — session or token** (`src/lib/route-auth.ts` `resolveCollectionOwner`). The Colnect matcher endpoints **and the photo-serving route** accept either a Better Auth session **or** an `Authorization: Bearer` **Assistant token** (`AssistantToken`, #253). The token is stored only as a SHA-256 hash (`src/lib/api-tokens.ts`), authorizes as the collection's owner for that one collection, and is required because the browser extension calls us cross-site from colnect.com where the Lax session cookie is not sent. It is issued either by **registration** (below) or by hand under **Settings → Assistant**.
- **Assistant registration** (#252, part of #155) — the instance registers itself into the extension so no URL, collection id, or token is ever typed. **Settings → Assistant** mints a short-lived (5 min), single-use `AssistantRegistrationCode` (`src/lib/assistant-registration.ts`; SHA-256 hash-stored like a token, superseding the collection's previous code) and exposes a payload — `{ v, name, apiBaseUrl = the page's own origin, collectionId, collectionName, regCode, expiresAt }` — as JSON in a hidden `#stamporama-assistant-registration` element. The extension reads it on a toolbar-icon click (`activeTab`) and `POST`s the code to the session-less **`/api/assistant/register`**, which claims it atomically (conditional `updateMany` on `usedAt`/`expiresAt`) and returns a freshly minted `AssistantToken` plus the collection identity. The long-lived token therefore never appears in a URL, a fragment, or the page; possession of an unspent code is the whole authorization, and every rejection is the same generic 400. The extension writes the outcome back onto the payload element as `data-registration-state`/`-message`, which the page renders.
- **Stamporama Assistant extension** (`extension/`, #253; ADR-0015) — an isolated MV3 workspace package (esbuild + hand-written manifest, its own tsconfig; excluded from the app's lint/typecheck). A pluggable `PlatformModule` interface — with the Colnect list-page parser as the first module (`extension/src/platform/colnect/`, #249: `div.pl-it` cards → item-ID + "Catalog codes" refs kept verbatim, `Unlisted` skipped) — feeds extracted refs to a background-service-worker matching client that calls the endpoints above with the Assistant token (background fetch is CORS-exempt under host_permissions). The popup previews decisions (dry-run) and writes only behind a confirm that names the active profile. Two behaviour switches live in `chrome.storage.local` (`extension/src/core/settings.ts`), both default on and both read by the service worker so the load-time match, the window's preview, and every write agree: `matchOnLoad` and `catalogBackfill` (#280 — the window's **Fill missing catalog numbers** toggle, mirrored in Options; changing it drops the per-tab result cache and re-previews). **Connection profiles** (#251) hold the instances/collections it can talk to — `{ name, apiBaseUrl, collectionId, collectionName, token }` in `chrome.storage.local`, one active at a time, managed in Options and switchable from the Assistant window's header; the active one is shown in an always-visible badge coloured from its target (hashed instance+collection, de-collided), and switching drops results and per-tab caches belonging to the instance being left. A profile is normally created by **registering from the instance** (#252, above) rather than typed in: the icon click reads the page's payload, redeems the code, and stores the resulting token — updating in place when a profile for that instance+collection already exists, which is also how a revoked token is replaced.
- **Assistant packaging & distribution** (#288; ADR-0017, superseding ADR-0016) — the extension ships through an **unlisted Chrome Web Store listing**, because Chrome only force-installs from a non-store update URL on an enterprise-managed machine, which a hand-installed configuration profile does not produce. The store assigns the released ID and signs the package, so nothing is signed here and the instance serves nothing: `extension/archive.mjs` (deterministic ZIP writer, verified in `extension/archive.test.ts`) + `pack.mjs` write `dist-store/stamporama-assistant.zip` with the **app's** version stamped into the manifest, and CI's `publish-extension` job uploads and publishes it per `v*` tag against `chromewebstore.googleapis.com/v2` (secrets `CWS_CLIENT_ID`/`CWS_CLIENT_SECRET`/`CWS_REFRESH_TOKEN`, variables `CWS_PUBLISHER_ID`/`CWS_EXTENSION_ID`). Review is asynchronous, so a green job means submitted, not live; the first listing must be created by hand, since the API only updates an existing item. **Two build flavours are two extensions** (`extension/identity.mjs`): `build.mjs` (default → `dist/`, unpacked) stamps in a committed dev-only public key, a ` (dev)` name suffix and amber icons → ID `idmgaeimkafaifpfbjonmjdfbmgffcbh`; `build.mjs --release` (→ `dist-release/`) leaves the manifest bare for the store to identify. `manifest.json` itself carries no `key`. That is what lets a dev build and the store build coexist in one browser — Chrome refuses two extensions with one ID, and per-extension `chrome.storage.local` keeps a dev profile from ever reaching a production collection.
- `conditionId` → `StampCondition` and `certificateStatusId?` → `CertificateStatus` reference the per-collection configurable sets (Issues #93/#94), mirroring `StampCatalogPrice`.
- `formatId?` → `StampFormat` records the copy's **physical format** — a pair, a block, a strip (ADR-0020), a third per-collection dictionary alongside the two above and referenced from `StampCatalogPrice` the same way. **Null means single**, so no such row is seeded (as with `certificateStatusId`). A multiple is one copy in one format and is **never** decomposed into N singles — there is no unit count, and completeness treats format as a breakdown dimension beside condition rather than a factor on counts. This supersedes #135's "a multiple is its own `Stamp` with a self-descriptive number" for homogeneous multiples, which multiplied formats by variant-tree nodes and made "a pair whose variant is not yet identified" unrecordable; se-tenant combinations carrying their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) are genuinely distinct entries and remain their own `Stamp`.
- Disposition is three **independent booleans** — `inCollection`, `forSale`, `forTrade` — not a mutually-exclusive status. A copy can hold any combination.
- Acquisition & cost (ADR-0009, #118): a copy links to its acquisition via `lotId?` → `PurchaseLot` (`onDelete: Restrict`) — one channel among several, so nullable. Supplier, date, and price live on `Purchase`/`PurchaseLot`, not on `Item`; the flat fields from ADR-0007 (`contactId`, `acquiredDate`, `purchasePrice`, `purchaseCurrency`) were removed. `costBasis?` `Decimal(10,2)` is a base-currency snapshot (null = pending). `deliveryState` (`in_transit | delivered | not_delivered | damaged`, default `delivered`) is an independent physical-delivery axis. `notes` holds free-form per-copy detail. **No copy-level UI captures purchase data yet** — the purchase CRUD/intake screens land in #120+.
- Physical storage (#56): `locationId?` → `Location` (an assignable storage node) records where the copy is filed; `locationRef?` is a free-text identifier within that location (e.g. a page/pocket like `p.12`), per copy and **not unique**. Only `assignable = true` locations are valid targets, enforced server-side.
- `ItemVariantHistory` records in-place re-pointing of `stampId` when an unknown-variant copy is later identified (`fromStampId`, `toStampId`, `changedAt`, `note?`), giving a refinement trail without versioning the whole `Item`.

Referential actions: `collectionId` and `stampId` cascade; `conditionId`, `certificateStatusId`, `formatId`, `lotId`, and `locationId` restrict (mirrors `StampCatalogPrice`). Indexed on `collectionId`, `stampId`, `conditionId`, `formatId`, `lotId`, `locationId`.

Valuation of an unknown-variant copy (lowest child-variant catalog price, flagged uncertain) is shared domain logic and belongs out of UI components; it lands with a later child issue.

### Contacts (`Contact`)

`Contact` is a per-collection address book of everyone the collector deals with — sellers, buyers, exchange partners, auction houses, platforms (see [ADR-0008](../decisions/0008-contact-entity.md)). It is the supplier reference for purchases (ADR-0009) and the platform/sale reference for the sales layer (ADR-0012).

- `name` is **unique per collection**; `notes`, `email`, `phone` are optional.
- Roles are six **independent booleans** — `buyer`, `seller`, `exchangePartner`, `auctionHouse`, `platform`, `other` — not an enum. A contact can hold several at once, mirroring the `Item` disposition flags.
- A contact may be created with **no roles set** (roles are filled in later).
- Platform-only fields: `platformCurrency?` (the fixed transaction currency inherited + locked by every offer/sale on the platform, #196), `titleTemplate?` (a free-text `{token}` template pre-filling offer + set titles for the platform, #210 — resolved by the pure `src/lib/offer-title-template.ts`; blank falls back to the derived label), `descriptionTemplate?` / `privateNoteTemplate?` (the same engine's multi-line form, pre-filling an offer's description #266 and seller-only private note #267; blank here means **generate nothing** — there is no built-in default, and it is also how a platform without private notes is configured), and `titleLanguage?` (the ISO 639-1 language the platform's generated text is written in, #293 — see *Per-language entity text* below).

- Seller-only fields: `defaultCurrency?`, `defaultShippingCost?`, `buyerPremiumPercent?`, `buyerPremiumFixed?` — the terms this seller normally trades on, **seeded** onto an `AuctionSale` at creation and edited there afterwards (#350, ADR-0021; see *Auction tracking* below). Shown in the contact form under either buying-from role, since an auction house is a seller that happens to run sales.
- `collectionId` cascades. Foreign keys pointing *at* a contact (from `Purchase`, from `Offer` / `Sale`, and from `AuctionSale` as seller and as platform) use `onDelete: Restrict` so a referenced contact cannot be deleted without first detaching it.
- Domain module `src/lib/contacts.ts` (server-only) exposes `listContacts` / `searchContacts` / `createContact`, all collection-owner-authorized.

### Per-language entity text

Different marketplaces list in different languages, so entity text used in generated titles is stored per language (design in #265, foundation in #293).

- Each translatable entity gets **its own child table**, primary key `(parent, language)`, FK `onDelete: Cascade`. A generic `(entityType, entityId, field, value)` table was rejected: it cannot carry FKs across several parents, and every new entity needs a migration either way. Seven exist: `CollectionAreaTranslation(collectionAreaId, language, titleName?)` (#293), `StampConditionTranslation`, `CertificateStatusTranslation` and `StampFormatTranslation` (`(parent, language, name?, abbreviation?)`, #294/#344), `IssueTranslation`, `StampTranslation` and `StampSubtypeTranslation` (`(parent, language, name?)`, #295/#296/#338).
- A translation's fields fall back **independently**: a null column means "use the entity's default-language value for *this* field", so a Polish condition can translate `Mint Never Hinged` and keep `MNH`. A row is written when any field is non-blank and deleted once all of them are blank, so "cleared" and "never set" are one state.
- The shared rules — parsing the form's `<field>:<lang>` inputs, deciding upsert-vs-delete, collapsing rows into `<field>ByLanguage` read models, and resolving a field for a language — live once in the pure `src/lib/translations.ts` (`parseTranslationValues` / `syncEntityTranslations` / `translationsByLanguage` / `resolveTranslation`). Each domain module supplies only its own Prisma delegate. Entity write inputs take a `translations` map; languages absent from it are left untouched, so a form rendering only the languages currently in use cannot drop a translation for a language temporarily removed from the platform list.
- The entity's existing single-language column (`CollectionArea.titleName`, …) stays the **default-language** value. Translation rows are purely additive — nothing is backfilled or moved.
- `language` is a free ISO 639-1 code (`src/lib/languages.ts` normalises it and supplies the picker list). `Collection.defaultLanguage` (NOT NULL, `@default("en")` — existing collections were backfilled to `en` by the column default) records which language the entity's own columns are written in; it is edited in Settings → General. The set of languages needing translation is **derived** as the distinct `Contact.titleLanguage` over the collection's platforms **minus** `defaultLanguage` — there is no separate language-configuration screen, and a platform listing in the default language resolves straight to the default columns with no rows at all.
- UI: entity forms keep **one** default-language input per field (labelled with `defaultLanguage` once any translation language exists) and open the shared `TranslationsDialog` (`src/app/c/[collectionSlug]/shared/translations-dialog.tsx`) from a 🌐 icon button beside it, badged with the number of languages still falling back, so a form does not grow a field per language. `TranslationsField` (`…/shared/translations-field.tsx`) packages the button, the badge and the hidden `<field>:<lang>` inputs, so the seven entity forms share one implementation. An entity with **several** translatable fields gives **each** its own button and its own single-field dialog rather than one dialog listing both: a badge then refers to exactly one field, and translating names never means scrolling past abbreviations left deliberately untranslated. The dialog fixes its panel height so the language grid scrolls internally rather than stretching, and portals to `document.body`, since it opens from inside another dialog's transformed panel. Its confirm button is **Done**, not Save: it stages values back into the entity form on the existing save path, leaving the entity's own dialog as the single logical save. Persisting from the nested dialog is not an option anyway — a not-yet-created entity has no id to attach rows to.
- Server-rendered screens (Settings, Areas) get the language set from their page loader. The issue and stamp dialogs cannot — they open from six client call sites — so they read it through `useTitleLanguages` (`…/shared/use-title-languages.ts`), a cached TanStack query over `getCollectionTranslationContext`. Stamp translations are likewise fetched by `stampId` inside the dialog, next to the subtype assignment and the photos, so no caller's row shape has to carry them.
- Resolution runs off the platform's `titleLanguage`, threaded through `makeTitleCopyMapper` (`src/lib/title-copy.ts`). `{area}` resolves in `buildAreaTitleMap` (`src/lib/area-vendor.ts`) with a **per-node** fallback: each area on the roll-up chain resolves its translation, then its default `titleName`, then its own `name` — the roll-up decides which area names the title, the language only how it is spelled. The other tokens resolve in `toTitleCopy`, which selects each entity's translation rows unfiltered (a handful per entity) and picks the language there, rather than parameterising the shared static `TITLE_COPY_SELECT`. Missing translations fall back silently in the stored title, and are **reported** alongside it (#298): `resolveTranslationWithFallback` / `buildAreaTitleEntries` say whether each field came from a translation, `toTitleCopy` collects the ones that did not into the copy's `fallbacks`, and the pure engine turns that into `renderTitleTemplateSegments` (the title split into flagged runs, using control-char sentinels so `tidy` still runs on the whole string and segments can never disagree with `renderTitleTemplate`) plus `titleFallbackTokens` (the token names, for the preview's summary line). `makeTitleCopyMapper` normalises a language equal to `Collection.defaultLanguage` to null, so a platform listing in the default language resolves the same and flags nothing.
- The language is **per generation, not per offer** (#297): the Add-set dialog and the offer header's ⋮ menu pass an optional override into `addOfferSet` / `addOfferSetsPerCopy` / `regenerateOfferText`, defaulting to the platform's `titleLanguage`. Nothing about the choice is persisted — only the title it produced, which stays editable (#209). The dialog previews it through `previewOfferTitle` (a read-only twin of `generateConfiguredTitle` sharing its `titleCopies` load path, so the preview and the stored title cannot drift); both preview surfaces render through `TitlePreviewText` / `TitleFallbackNote` (`…/shared/title-preview.tsx`).
- A reported fallback also names the **entity row that would fix it** (#299), so a gap can be filled where it is seen. A copy's `fallbacks` are `TitleFallback`s — `{ field, entityType, entityId, entityField, defaultValue }` — the copy field the token renders from *plus* the entity's own translation column, which differ because one copy flattens six entities (`{conditionAbbr}` is the condition's `abbreviation`, and `{area}` is a `titleName` on whichever ancestor won the roll-up, hence `AreaTitleEntry.sourceAreaId`). `templateFallbacks` / `titleFallbacks` / `listingFallbacks` walk the same placeholders as their `*FallbackTokens` twins and return those entries deduped per entity row, so **a gap offered for filling and a token flagged in the preview are the same thing seen from two ends**: a translatable field no template renders is not a gap. `TitleSegment` carries the `field` of a flagged run (the sentinel wraps `field` + value), which is what lets a click on the run open the right editor (#300).
- Filling one is a **standalone entity write**, not part of the offer: `saveEntityTranslation` (`src/lib/entity-translations.ts`) writes one field of one language, checking the owner *and* that the entity really belongs to the collection, refusing the collection's own default language and any field the entity does not have, and reading a multi-field entity's stored siblings back so filling a name cannot clear an abbreviation. It reuses `syncEntityTranslations`, so a gap filled from an offer dialog and one filled in the entity's own dialog store exactly the same thing (including the all-blank-deletes rule). The six per-entity delegates live in that one module rather than as a setter per domain module, since the paths differ only in which table they resolve and upsert. UI: `TranslationGapsPanel` / `TranslationGapPopover` (`…/shared/translation-gaps.tsx`) — one row per gap, saved on Enter/blur — under the compose dialog's preview and, over the offer's whole composition and all three templates in the platform's own language, on the offer detail screen (`useOfferTranslationGaps`). The compose dialog re-runs its preview after a save; the detail screen does **not** rewrite the stored texts, which may have been edited by hand, leaving that to each field's ↻.

#### Listing texts (#266/#267)

- The same pure engine renders an offer's **description** and **private note**, in a multi-line mode. Rendering scope is grouped by set — `TemplateSet = { title, copies }` — so a template can enumerate a listing: `{#set}…{/set}` repeats its body once per set and `{#copy}…{/copy}` once per copy (of the enclosing set, or of the whole offer at the top level), with tokens inside a block narrowed to that iteration. `renderTitleTemplate` / `…Segments` keep their flat-copies signature by wrapping the copies as one anonymous set, so #210 is unchanged. Unbalanced block tags stay literal, like an unknown token.
- **Legend blocks** (#318) reuse the same mechanism over a different axis: `{#conditionLegend}…{/conditionLegend}` / `{#certificateLegend}…{/certificateLegend}` — named `…Legend`, not after the dictionary, so the tag cannot be misread as the `{condition}` token it wraps — iterate the **distinct dictionary entries** the copies in scope use — keyed on the (name, abbreviation) pair, first-seen order, copies recording neither skipped — narrowing the scope to the copies carrying each entry (`legendScopes`). So `{conditionAbbr} = {condition}` inside the block names that one entry while `{catalog}` names what it applies to, and the entry's format stays the collector's to write rather than a hard-coded `ABBR = Name`. `=` joined the tidy pass's glue separators so a dictionary row without an abbreviation renders its name alone.
- Multi-line tidying runs **per line**: a line whose placeholders all resolved empty is dropped whole (no bare `Condition:` left behind), a line with no placeholders — including a blank paragraph separator — is kept, and leading indentation survives. A `VALUE_MARK` control character alongside the existing `EMPTY_MARK` is what distinguishes the two cases. The same pass also fixed a long-standing title wart: an empty token flanked by separators used to eat **both**, and `:` / `;` were not treated as glue at all.
- `src/lib/offers.ts` generates all three texts in one copy load (`generateListingTexts`) at create and duplicate, and regenerates **one** field at a time (`regenerateOfferText`) over the offer's present composition (`offerComposition`), so a hand-edited title survives regenerating the description. `OfferDetail.regeneratable` reports which fields the platform has a template for, which is what the per-field ↻ enables itself on.
- UI: the platform's three templates share **one** dialog off the contact form — `ListingTemplatesDialog` (`…/contacts/listing-templates-dialog.tsx`): a fixed-size panel (`DialogShell height`) scrolling internally, with the shared `TemplateSamplePicker` pinned above the body and the three `TemplateBuilder` sections stacked inside it — each collapsible to a one-line summary row — and one save. Sample copies load once per dialog (two of them, so a `{#set}` block visibly repeats), so all three previews describe the same stamps. `TemplateBuilder` / `TemplateSamplePicker` / `TemplateSyntaxLegend` / `useTemplateSamples` live in `…/shared/template-builder.tsx`, replacing the old single-template `TemplateBuilderDialog`. The offer's own texts live in `OfferListingText` (`…/offers/[offerId]/offer-listing-text.tsx`) below the header card, collapsed to one row while both are empty.

### Purchases (`Purchase` / `PurchaseLot` / `PurchaseExpense`)

The purchase model (see [ADR-0009](../decisions/0009-purchase-record-model.md), schema in #118) is the channel-agnostic source of cost-basis. **CRUD is live** (#120): the pure allocation engine landed in #119, and lot close / item intake follow in #121+.

- `Purchase` — transaction header: optional `contactId?` → `Contact` supplier and optional `platformId?` → `Contact` platform (the marketplace/intermediary, e.g. Allegro — a contact with the `platform` role; both FKs `onDelete: Restrict`), `purchasedAt` (date), a single `currency`, `fxRateToBase?` frozen at `purchasedAt` (`Decimal(65,30)`, reuses the `ExchangeRate` mechanism), `shippingCost?` `Decimal(10,2)` (shared cost), and a delivery `status` (`preparing | in_transit | arrived`). Scoped to `Collection` (`onDelete: Cascade`).
- `PurchaseLot` — inventory line: `price` `Decimal(10,2)`, intake `status` (`open | closed`), and the `Item`s it resolves into. `onDelete: Cascade` from `Purchase`.
- `PurchaseExpense` — non-inventory line (e.g. a magnifier): `label` + `price` `Decimal(10,2)`, no lifecycle and no items. `onDelete: Cascade` from `Purchase`.
- Statuses are `String` columns (the schema uses no native Postgres enums), with allowed values documented in the schema and enforced by the domain layer.
- Domain module `src/lib/purchases.ts` (server-only) exposes `listPurchasesPaginated` / `getPurchase` / `createPurchase` / `updatePurchase` / `deletePurchase`, all collection-owner-authorized. Create/update persist the **header only** (supplier, platform, date, currency, delivery status, and the shared shipping cost) and freeze `fxRateToBase` (best-effort) via the `ExchangeRate` mechanism. The supplier and platform fields each submit both a picked contact id and the typed name; `resolvePurchaseContact` (in `contacts.ts`) resolves them on save — a valid in-collection id wins, else an existing contact is matched by name (case-insensitive) and reused, else a new contact is created carrying the field's role (`seller` for suppliers, `platform` for platforms). The pickers filter suggestions to that role via the `?role=` param on the #107 contact search. **The order's line items are intentionally not written by #120** — both inventory lots and non-inventory expenses are added during lot intake (#121), so `createPurchase`/`updatePurchase` never touch them; the read/list side still surfaces lot and expense counts and rolls them into the total. The `Purchases` screen (`src/app/c/[collectionSlug]/purchases/`) is a URL-state, card-row infinite-scroll list with a dialog-shell header add/edit form; the paginated list is served by `GET /api/collections/[collectionId]/purchases` and mutations go through server actions in `src/app/actions/purchases.ts`.

### Auction tracking (`AuctionSale` / `AuctionLot` / `AuctionLotLine`)

Auction tracking (see [ADR-0021](../decisions/0021-auction-tracking-model.md), design in #23, schema in #350) is a **bidding watchlist with a fork at the end**, not a register of market results fed from outside: lots the collector is bidding on, resolved as won or lost. A lost lot's final price is the price signal #24 consumes — a by-product of the workflow rather than a corpus somebody has to populate. **Schema and seller defaults** (#350), **the screens** (#351/#352) and **composition + catalogue value** (#353) so far; settlement lands in #28.

- `AuctionSale` — **one settlement with one seller**, i.e. what ships in one parcel, deliberately not "an auction as an event". For a house it coincides with the house's own sale (`Köhler 385`); on a marketplace it is an open-ended basket of everything currently being bid on with one seller. That is what makes shipping distribution fall out of ADR-0009 §3 for free — the grouping is made at bidding time, so settlement never asks "which purchase does this go into?". `sellerId` + `platformId` → `Contact` (both `onDelete: Restrict`), mirroring `Purchase`: a house selling directly is the same contact in both, a house listing through philasearch is seller = house, platform = philasearch. `name` (the house's sale identifier lives here — there is no sale-number column), `url?`, `endsAt?` (a **default for new lots**, never the sale's own date), `currency`, `shippingCost?` / `premiumPercent?` `Decimal(5,2)` / `premiumFixed?`, `status` = `open | settled | closed`, and `purchaseId?` (unique, `onDelete: SetNull`) set on settlement. Scoped to `Collection` (`onDelete: Cascade`).
- `AuctionLot` — one thing being bid on: `lotNo?`, `url?`, `title?`, its **own** `endsAt` (on a marketplace every lot closes at a different moment), `currentBid?` + `checkedAt?`, `maxBid?`, `finalPrice?`, `status` = `watching | won | lost | cancelled`, `purchaseLotId?` (unique, `onDelete: SetNull`), `notes?`. `onDelete: Cascade` from `AuctionSale`. Outcome lives **on the lot, never on the sale** — within one settlement some lots are won and others lost, which is the ordinary case. The bid is a single overwritten figure, **not a history**: refreshing is manual (no scraping, no scheduled polling), so `checkedAt` answers the only question a history would. `finalPrice` is optional because a lot that vanished from view yields no datapoint.
- `AuctionLotLine` — composition as `stampId` × `conditionId` × `certificateStatusId?` × `formatId?` × `quantity` (all four FKs `Restrict`; `onDelete: Cascade` from the lot), which is exactly the shape a `StampCatalogPrice` is keyed on. The certificate arrived with #353 (nullable, null = none as on `Item`, so nothing needed backfilling): a house lot sold with a Fotoattest is worth a different figure, and matching is strict, so a line naming one is unpriced until a price exists at that level. Structured, never free text: that is what makes catalogue value computable before the close and a lost lot usable afterwards. **No new pricing machinery** — an unknown-variant umbrella rolls up from the cheapest child exactly as the issue list does (#238), and `formatId` prices multiples through `StampFormatFactor` (ADR-0020, null = single).
- Valuing that composition (#353) lives in `src/lib/auction-lines.ts`, and reuses the **copy** valuation literally: `valuateItemRows` (exported from `items.ts`) values a `stamp × condition × certificate × format` row, of which a copy is one instance and a lot line another at a **null certificate** — a lot is described before it is owned. It is called **once per page of lots**, so `makeFormatFactorLookup` and the area tree load once rather than per row. Value pivots **base currency → the sale's**, converted once per sale currency, because the bid, premium and ceiling are all denominated there; a missing rate makes a line **unconvertible**, a state deliberately distinct from *unpriced* (it has a value that cannot be counted, and calling it unpriced would send the collector to enter a figure that already exists). A composition entered but unpriced values at `null`, never `0.00` — a zero would make every headroom read as a catastrophic overbid — and unpriced/unconvertible lines are counted beside the total rather than dropped. The pure roll-up is `summarizeLotComposition` in `auction-lot.ts`; quantity multiplies and nothing else does, since a multiple is never decomposed (ADR-0020). Read through `GET /api/collections/[collectionId]/auctions/lots/[lotId]/lines`, written by server actions. A lot with no `title` takes a **derived name** from its lines (`deriveAuctionLotLabel`) — prefix-formatted catalogue numbers collapsed into spans (`buildAreaVendorMaps` + `formatStampCN` over `readCollectionAreas`), plus the shared issue — computed on every read beside the valuation and never stored, since it is read only on our own screens. Entry offers a **whole-issue** pick alongside a single stamp, expanded in the action layer by `resolveAuctionLineStamps` into one line per `requiredForCompleteness` member — the purchase intake's rule (`lots.ts`), reused rather than restated. Written from three surfaces — the sale detail's cards, the watchlist dialog, and `createAuctionLot` itself, which takes `lines` and writes lot + composition in one nested create with every line validated first. Reading: the **sale detail** draws each lot as a collapsible card over its lines (the PO-intake / offer-detail layout — shared `LotIssueGroupHeader`, `lot-view-prefs` toolbar, `sortSortableCopies`), and only that read carries them (`AuctionLotDetailItem`); the **flat watchlist** opens the same list in a dialog, its rows carrying the total alone.
- `Contact` seller defaults — `defaultCurrency?`, `defaultShippingCost?`, `buyerPremiumPercent?` `Decimal(5,2)`, `buyerPremiumFixed?`, all optional and **seeded** onto a sale at creation, never read live: the same rule as seeding listing templates and photo configuration from a platform onto an offer (#308, #319), so changing a seller's terms cannot re-price a sale already tracked or settled. Currency belongs to the **seller** — philasearch aggregates houses listing in EUR, CHF and GBP, so `platformCurrency` (#196) does not apply. Edited in the contact form under the seller / auction-house roles.
- Arithmetic is pure in `src/lib/auction-lot.ts` (no Prisma, unit-tested, mirroring `offer-summary.ts`): `allIn(bid, fees)` = `bid + bid × premiumPercent / 100 + premiumFixed + shippingCost`, `headroom(catalogValue, bid, fees)`, and `summarizeAuctionSale` over a sale's lots. Comparing catalogue value against the hammer price alone systematically overpays on cheap lots, where shipping and a fixed lot fee are a large share of the total. The rollup counts only **payable** lots (`watching` / `won`) and adds shipping **once** for the parcel — which is only expressible because the sale is one settlement.
- Settlement (#28) is a **1:1 transcription**: `AuctionSale` → `Purchase`, each `won` lot → `PurchaseLot` at hammer + premium, lost lots skipped, shipping then distributed by ADR-0009 §3. The `SetNull` links mean deleting the purchase leaves the bidding record standing, because that record is a datapoint in its own right.

### Sales (`Lot` / `Offer` / `Sale` / `SaleLine` / `SaleLineItem`)

The sales model (see [ADR-0012](../decisions/0012-sales-record-model.md), schema in #162) is the mirror image of purchases and the consumer of `Item.costBasis`. **Schema, the pure P/L allocation engine, lot composition, and per-platform offers so far** (#162/#163/#164/#165) — the sale flow lands in #166+. It has two orthogonal axes, symmetric to purchases: the platform-agnostic **package** (`Lot`) and the per-platform **listing** (`Offer`); the `Item` is the thread tying platforms together. Lot composition + lifecycle live in the pure rules module `src/lib/sale-lot-rules.ts` (kind invariants, derived sale status, sub-lot cycle guard; unit-tested in `tests/unit/sale-lot-rules.test.ts`) and the server domain module `src/lib/sale-lots.ts`; the **Lots** screen (`src/app/c/[collectionSlug]/lots/`) drives compose → ready → dissolve.

Offers (#165) are the per-platform listing layer. The pure offer state machine + validation live in `src/lib/offer-rules.ts` (`preparing → ready → active ↔ paused → sold/withdrawn`, linear but reversible; `sold` reachable only via a sale; unit-tested in `tests/unit/offer-rules.test.ts`); the server domain module `src/lib/offers.ts` owns CRUD, the paginated list (platform/state/lot filters), the eligible-lot picker, and the collision lookup. The **at most one active offer per (`Item` × platform)** rule is a **non-blocking live warning** in the offer dialog (a lookup over active offers on the platform sharing a copy with the lot), not a hard guard — deeper coordination is #167. Offers are managed from the **Offers** screen (`src/app/c/[collectionSlug]/offers/`) and from a lot's detail **Offers** section; the paginated list is served by `GET /api/collections/[collectionId]/offers` (with `offers/collision`, `offers/eligible-lots`, `offers/platforms` helpers) and mutations go through server actions in `src/app/actions/offers.ts`.

- `Lot` — a **recursive** sale package scoped to `Collection` (`onDelete: Cascade`). `kind` = `unit` (the atomic sellable unit — a single stamp or an indivisible *komplet* — holding `Item`s directly via `lot_item`, an **`Item` N:M `Lot`** join so a copy can be packaged differently per platform) or `quantity` (groups N interchangeable sub-lots via the `lot_sub_lot` self N:M relation, holding no items directly). Lifecycle `state` = `draft | ready | dissolved`; `sold` / `partially-sold` are **derived**, never stored. The kind invariants are domain guards, not DB constraints.
- `Offer` — a `Lot` listed on one platform (`Lot` 1:N `Offer`): `platformId` → `Contact` with the `platform` role (`onDelete: Restrict`), an editable `name?` (the listing title, #209 — generated from the platform's `titleTemplate` over the offer's copies, null falls back to the derived label), editable `description?` / `privateNote?` (the long listing text and the seller-only note, #266/#267 — generated from the platform's own templates over the offer's **sets**, null when it has none), each regenerated on demand and independently via `regenerateOfferText(ownerId, offerId, field, language?)`, `url?`, `price` `Decimal(10,2)` + `currency` (per-offer, platforms price independently), `state` = `preparing | ready | active | paused | sold | withdrawn` (+ a derived "needs action" flag; sold/withdrawn hidden from the list by default, #245). `onDelete: Cascade` from both `Collection` and `Lot`.
- `Sale` — the transaction header: single `platformId` → `Contact` (`onDelete: Restrict`), `soldAt` (date, FX frozen here), one `currency`, `fxRateToBase?` `Decimal(65,30)`, and three shared amounts — `buyerHandling?` (+), `shippingCost?` (−, my cost), `commission?` (−, manual) — all `Decimal(10,2)`. Scoped to `Collection` (`onDelete: Cascade`). A **`status`** string tracks fulfillment in a fixed lifecycle `ordered → paid → packed → sent → received` (default `ordered`, #191), an axis orthogonal to copies/offers; each transition also appends a **`SaleStatusEvent`** (`saleId`, `status`, `changedAt`, `onDelete: Cascade`) so the progression is preserved for reporting/audit. Set inline from the detail header (`setSaleStatus` → `setSaleStatusAction`).
- `SaleLine` — the unit lot or sub-lot that sold: `offerId?` → `Offer` (`onDelete: SetNull`, so a historical sale survives offer cleanup), `lotId` → `Lot` (`onDelete: Restrict`), `price` `Decimal(10,2)` in the sale currency. `SaleLineItem` records the exact copies that left; its **`@@unique([itemId])` is the DB-level no-double-sale guard**, and `Item` FK is `onDelete: Restrict`. No sold flag is added to `Item` — sold state is read through this join. Each `SaleLineItem` also carries a **`packed`** boolean (#192), toggled per copy in the packing view (`setSaleLineItemPacked`), independent of the sale's `status`; the inventory list hides copies present in this join by default (`excludeSold`, #207), with an "Include sold" toggle.
- Statuses/kinds are `String` columns (no native Postgres enums), enforced by the domain layer. The other guards — one active offer per (item × platform) (a non-blocking warning, #165), quantity decrement — are derived/domain-level.
- Pure module `src/lib/sale-allocation.ts` (no Prisma, unit-tested in `tests/unit/sale-allocation.test.ts`, #163) is symmetric to `purchase-allocation.ts`: it distributes the three shared amounts across lines by sale price, resolves each line's net (`price + handling − shipping − commission`, possibly negative), converts to base currency at the frozen rate, splits a line's net across its copies by primary-catalog weight (single-item lines short-circuit), and computes per-copy P/L against `costBasis` (`null` cost-basis → `null` P/L). Everything reconciles to the cent via largest-remainder apportionment.

### Storage locations (`Location`)

`Location` is a per-collection **adjacency-list hierarchy** of physical storage — cabinets, stockbooks, albums, boxes — reusing the same pattern as `CollectionArea` (see [ADR-0010](../decisions/0010-storage-location-model.md), design in #55, built in #56).

- Fields: `id`, `collectionId`, `name`, `parentId?` (arbitrary depth), `description?`, `assignable` (`Boolean`, default `true`), `createdAt`.
- `assignable` distinguishes grouping-only nodes (a cabinet — `false`) from leaf storage that can actually hold copies (a stockbook — `true`). A copy's `locationId` may only point at an `assignable = true` location.
- `collectionId` cascades; the self `parentId` FK is `SetNull` (matching `CollectionArea`), but deleting a location that still has children or stored copies is blocked in the domain layer. The `Item.locationId` FK is `onDelete: Restrict` so a stored copy is never orphaned.
- Filtering the inventory by a location includes the whole **subtree** (a parent selection shows copies in its descendants), resolved server-side in `src/lib/items.ts`.
- Domain module `src/lib/locations.ts` (server-only) exposes `getLocations` / `createLocation` / `updateLocation` / `deleteLocation`, all collection-owner-authorized, with the cycle, assignable, and delete guards.

### Photos (`Photo` / `PhotoUpload`)

Copies, catalog stamps **and offers** can carry photos (see [ADR-0011](../decisions/0011-photo-storage-interface.md), #112/#137/#311). `Photo` is **polymorphic**: it hangs off exactly one owner — an `Item` (copy), a `Stamp` (catalog-level reference image) or an `Offer` (a generated listing image). `PhotoUpload` is a short-lived staging row for eager, pre-Save uploads, shared by the two upload owners.

- `Photo` fields: `id`, `itemId?` (`onDelete: Cascade`), `stampId?` (`onDelete: Cascade`), `offerId?` (`onDelete: Cascade`), `kind` (`original | generated`, default `original`), `role?` (`front | back | main | null`), `title?`, `storageBackend` (default `filesystem`), `storageKey`, `mime`, `width`, `height`, `sizeBytes`, `sortOrder`, `createdAt`. A raw `CHECK (num_nonnulls(itemId, stampId, offerId) = 1)` enforces **exactly one owner**. Three *partial* unique indexes — `(itemId, role) WHERE itemId IS NOT NULL` and the same for `stampId` / `offerId` — make each reserved role a **singleton slot per owner** (a plain unique on the now-nullable `itemId` would let every stamp photo collide on `(NULL, ...)`; Postgres keeps NULL roles distinct, so titled extras stay unlimited). Which slots an owner uses is a UI concern: **copies** use `front`/`back`, **stamps** use a single `main`, **offer** images use none — they order via their plan entry (#311). `kind` records how the bytes came to exist and exists so generated bytes can later be purged and recreated on demand, which originals never can.
- `PhotoUpload` fields: `id`, `collectionId`, `storageBackend`, `storageKey`, `mime`, `width`, `height`, `originalWidth`, `originalHeight`, `sizeBytes`, `createdAt` (indexed for the GC cutoff scan).
- **Storage interface** (`src/lib/storage/`): `put` / `get` / `delete` / `move` / `resolveUrl`, async + streaming. `FilesystemStorage` is the only binding, rooted at `STAMPORAMA_DATA_DIR` (default `/data`; `./.data` in dev). `resolveUrl` returns a discriminated `{kind:"stream"} | {kind:"redirect"}` result so a future GCS binding can 302 to a signed URL. Writes go to the active backend (`getActiveStorage`); reads dispatch per-photo by `storageBackend` (`getStorage`) — write-one, read-many. A `storageKey` is a **prefix**; the two variants hang under it as `<prefix>/{full,thumb}.<ext>` (permanent `<collectionId>/<photoId>`, staging `staging/<uploadId>`).
- **Processing** (`src/lib/photos/process.ts`): `sharp` decodes once and emits a **2500px** full derivative plus a **320px** thumbnail eagerly. Accepts JPEG/PNG/WebP up to ~60 MB (the whole file is buffered before the decode, so the cap is a memory bound as much as a policy). The source's own dimensions are recorded alongside them as `Photo.originalWidth`/`originalHeight` — the original bytes are never kept, so this row is the only record of how far a scan was shrunk, and the collage renderer needs it to put a clamped scan back on a common scale with an unclamped one (see *Collage renderer*). EXIF orientation is normalised by hand there, because `metadata()` reports pre-rotation dimensions. Null on rows predating the columns: nothing to backfill from, and readers fall back to `width`/`height`, i.e. "never downscaled". `thumbnailFor` derives *only* a thumbnail, for images the app produced itself (#311): a collage's `full` bytes are the renderer's own output, already sized and encoded to the platform's limits, so re-encoding them would undo that work.
- **Domain** (`src/lib/photos.ts`, server-only): `stageUpload`, the owner-agnostic change-set apply exposed as `applyPhotoChangeSet` (copy) / `applyStampPhotoChangeSet` (stamp) (atomic Save of the dialog's pending change-set — adds/removals/role-changes/reorders), `listItemPhotos` / `listStampPhotos`, `promoteCopyPhotoToStamp` (duplicate a copy photo's bytes into an independent stamp `Photo`, then on up the variant tree to each photo-less ancestor, stopping at the first that has one — #347, and at the first node whose effective `actsAsVariant` is false, since an error or plate flaw pictures itself rather than its parent — #368; the automatic seed behind it only fires for copies in the default physical format, #346), `getPhotoForServing` (resolves any of the three owners), `deletePhotoBytesForItem` / `deletePhotoBytesForStamp` (called by `deleteItem` / `deleteStamp`), and `gcStaleUploads`. All collection-owner-authorized. Offer-owned images deliberately do **not** go through the `PhotoOwner` change-set seam — they are generated from a plan, not edited in a dialog, so their lifecycle lives in `src/lib/offer-photo-generation.ts` (#311).
- **Transport & serving**: multipart uploads go through the route handler `POST /api/collections/[collectionId]/photos/uploads` (not a server action); bytes are served by `GET /api/collections/[collectionId]/photos/[photoId]/[variant]`, authorized by the photo's owning collection + owner (item, stamp **or** offer). Files never sit under `public/`.
- **Cleanup**: deleting a photo, its `Item`, its `Stamp` or its `Offer` deletes the stored bytes (cascade drops rows only). Abandoned staging uploads are swept hourly by an idempotent in-process GC started from `src/instrumentation.ts` `register()` (TTL `STAMPORAMA_PHOTO_UPLOAD_TTL_HOURS`, default 3h) — no separate compose service.
- **Storage total** (#144) sums `sizeBytes` across all three owners; generated images count, because they occupy the volume like any other file.

### Collage templates (`CollageTemplate`)

A collection-level, named render preset for offer photo collages (#307) — `name`, `rows`, `columns`, `gapPercent`, `background`, `labelPercent`, cascade-deleted with its collection, edited under **Settings → Collage templates** (`collage-templates-panel.tsx`, mirroring `subtypes-panel.tsx`). It exists because collage capacity is a property of **stamp size**, not of the platform or of one listing.

- **Capacity, not frame.** `rows × columns` is a maximum; the renderer (#310) shrinks the canvas to the actual contents, so 4 copies under a 5×4 template give a one-row image. A 1×1 template is the single-stamp case, which keeps one rendering path for every image.
- **Seeded, not referenced.** A template is picked on an offer and its values are **copied onto the offer** (#308), exactly as `Contact.descriptionTemplate` seeds `Offer.description`; no *offer* points back at the table. Editing or deleting a template therefore cannot retroactively change offers already prepared, and there is no in-use check on delete. The one reference is `Contact.defaultCollageTemplateId` — which template a new offer on that platform seeds from — and it is `onDelete: SetNull`, so delete stays unguarded.
- **Percentages of the stamp, not pixels** (#312). `gapPercent` and `labelPercent` are shares of the **median tile height** of the collage being rendered. Pixels were tried first and are unusable: the canvas is built from scans of an unknown DPI and is then scaled down by one shared factor to the platform's limits, so the collector would have to know both numbers in advance to pick a readable strip height — and labels came out illegible for exactly that reason. A percentage needs neither: how a label reads *beside its stamp* is invariant under the shared downscale, and an image scaled far enough for the label to vanish has already lost the stamp. The median rather than the tallest tile, so one souvenir sheet cannot inflate a whole page's strips. One value serves both axes of the gap.
- Platform limits (max photos / longest edge / file size) are **not** here — they live on `Contact` and are read live at render time (#308, #310).
- No rows are seeded into a new collection: sizing conventions depend on the material a collector actually sells.
- Validation is a pure module (`src/lib/collage-template-rules.ts`, unit-tested), reused by the offer-side photo-settings form through `src/lib/offer-photo-config.ts` (#308); the server module (`src/lib/collage-templates.ts`) is owner-authorized like every other config entity.

### Offer photo configuration (#308)

Photo configuration sits on **two levels**, following the `titleTemplate` / `descriptionTemplate` pattern: the platform holds defaults, the offer holds the values it was seeded with.

- **`Contact` (platform).** Hard limits — `maxPhotos`, `maxPhotoEdge`, `maxPhotoFileSizeMib` — all optional (`null` = no limit) and **read live** at render time (#310): they describe what the platform physically accepts, so tightening one applies to every offer at once. Alongside them, the defaults a new offer is seeded from: `photoSides` (`front | back | both`), `tileLabelLeftTemplate` / `tileLabelRightTemplate` (#312, configured as the last two fields of the listing-templates dialog) and `defaultCollageTemplateId`.
- **`Offer`.** Its own `photoSides`, `photoLabelLeftTemplate` / `photoLabelRightTemplate` and the collage numbers `collageRows` / `collageColumns` / `collageGapPercent` / `collageBackground` / `collageLabelPercent`, copied from the platform's default template at creation (`seedPhotoConfig` in `src/lib/offers.ts`, applied by both `createOffer` and `duplicateOffer` — a clone is seeded from the platform it is cloned *onto*). The collage columns are nullable **as a group**: a platform with no default template leaves an offer with no collage until one is picked on it.
- **Why stored, not read.** Changing a platform setting must never silently alter offers already prepared or listed. This matters most for the label templates: a buyer referring to a label on an image already uploaded must keep getting that label after a regeneration (#315). Editing any of these marks the generated photo plan out of date (#311).
- Rules live in `src/lib/offer-photo-config.ts` (Prisma-free, unit-tested): the sides vocabulary, limit parsing, and the all-or-nothing collage group. `updateOfferPhotoConfig` replaces the whole configuration in one write, mirroring the dialog's single save; it is allowed in every offer state, like the listing texts.

### Offer photo plan (#309)

`src/lib/offer-photo-plan.ts` — `planOfferPhotos()` turns an offer's sets, copies, photo configuration and the platform's limits into an **ordered list of planned images**. Pure and Prisma-free like `offer-title-template.ts`, so the server generator (#311) and a client-side preview run identical rules, and it is unit-tested without a database. An offer's photos are a sequence, not "one main image plus extras"; a single image is a 1×1 collage, so there is exactly one rendering path (#310).

- **Grouping.** A multi-copy set gets its own group (split into consecutive groups of its own if it holds more copies than `rows × columns`). Single-copy sets are collected **across set boundaries** and chunked to capacity — a collage of one stamp is pointless. Mixed offers are not a designed-for case, but stay predictable: a run of single-copy sets flushes before the next multi-copy set, so plan order always follows set order (#306), and tile order follows copy order.
- **Front / back.** `photoSides` decides which sides are attempted. A side is rendered **only if every copy in the group has that scan** — all or nothing, no gaps — so a group yields a front/back pair with identical contents (emitted interleaved), or a degenerate group of one image, or none. Nothing may assume a group has two members.
- **Nothing is dropped; two marks decide the upload set** (#313). Every planned image is rendered. `publish: false` is the collector's own do-not-publish mark; `overLimit: true` is derived — among the published images, in plan order, this one falls past `maxPhotos`. Both keep an image out of the numbered upload run and the ZIP, and neither stops it being generated: an image that does not fit today is still one the collector wants to see, and hiding a published image frees its slot so another comes under the limit. The allowance fills **from the front of the plan order**, and nothing is protected — not a front/back pair, not an attachment — because once the order is the collector's, the order *is* the priority order. `plan.uploaded` is the images with neither mark; `overLimitCount` counts the rest.
- An offer with no collage numbers yet plans no collages (`configured: false`); its attachments still appear.
- A side a group cannot produce is returned in `skipped` rather than quietly left out (#314), so the UI can name the copies whose scans are missing.

### Collage renderer (#310)

The only genuinely new mechanism in the image pipeline: `src/lib/collage-layout.ts` (pure geometry, unit-tested on plain numbers) plus `src/lib/photos/collage.ts` (`renderCollage()`, the `sharp` compositing), turning a planned image (#309) into bytes ready to upload.

- **True proportions.** Stamps are scanned, not photographed, so scanner DPI is constant and pixel sizes already carry true relative sizes. Tiles are composited at their **native** size and only the finished canvas is scaled — one shared factor for the whole collage, never per tile or per row. No millimetres anywhere. The upload cap is the one thing that breaks the premise: a scan over `FULL_MAX_EDGE` is *stored* downscaled, so a clamped tile and an unclamped one are no longer on a common scale — a block twice the size of its neighbour would composite the same size. `trueSizeScales` (`src/lib/collage-layout.ts`, pure) repairs it from each tile's recorded original: per-tile shrink `r = originalEdge / storedEdge`, normalised against `max(r)` so every factor lands in `(0, 1]` and the correction is applied by **downscaling** — a clamped tile is never interpolated back up, and the resolution the smaller tiles give up is mostly notional because the canvas is scaled to the platform's limits afterwards anyway. Photos with no recorded original (uploaded before the columns existed) read as un-downscaled and render exactly as they did before.
- **Row-based packing.** Rows hold up to `columns` tiles; a row is as tall as its tallest stamp and tiles are vertically centred in it, with the label strip (#312) reserved below each tile on one shared baseline. Rows are **centred** against the widest row, and `gap` doubles as the outer margin. Justified rows (each row stretched to full width) are rejected: they scale each row differently and would destroy the proportions that are the point of the feature. `rows × columns` is capacity — the canvas shrinks to the actual contents (#307) — and a single stamp is a 1×1 collage, so there is one rendering path.
- **Output limits** (#308, read live from the platform, each skipped when null): longest edge via `fit: "inside"` — the `FULL_MAX_EDGE` convention from `process.ts` — then the file-size target. The byte target is what `process.ts` cannot do: it encodes once at a fixed quality and never checks the result, which is fine for one small scan. `renderCollage` bisects JPEG quality between `COLLAGE_QUALITY_MIN`/`MAX` and, only when even the floor is too heavy, shrinks the canvas by the measured overshoot and searches again (bounded rounds, floor scale). An unreachable limit returns the best effort with `exceedsFileSizeLimit: true` rather than throwing or looping.
- **Always JPEG.** Collages are photo-like and the quality knob is what makes a byte target reachable at all (PNG has none, WebP is still refused by some marketplaces). Source scans keep their own format; this is the offer-photo output only.
- **Tile labels** (#312, `src/lib/collage-label.ts` — pure, unit-tested): each tile carries **two** annotations, drawn flush left and flush right on the strip the layout reserved, at **one shared font size** so the strip reads as a single line. Two rather than one because what a tile has to say is an identifier the buyer quotes back *and* something descriptive beside it; through one template that is a single long line that then has to shrink. A lone annotation is centred instead. The layer is **one canvas-sized SVG** composited before the output limits, so labels shrink with the stamps rather than growing relative to them. **One font size for the whole collage**, the smallest any tile needed, drawn in two passes (measure every tile, then re-fit the text to the shared size): sized per tile, a narrow stamp beside a wide one carries a visibly smaller label, which reads as a mistake rather than as fitting. Within a strip the two sides share the width **in proportion to their length**, not half each, so a location ref beside a pair of catalog numbers does not squeeze the long side while the short one sits in white space. Below a fraction of the strip's own size the text is **truncated with an ellipsis** rather than shrunk further; ink is black or white by the background's luminance. Every size in the module is a fraction of the strip, which is itself a fraction of the stamp, so nothing depends on the scan resolution. A side with no text is simply not drawn. Drawing SVG text needs a font on the host, so the app image installs DejaVu Sans (see the `Dockerfile`); without one, labels come out as fallback glyphs.
- Stamps coming out small after a downscale is not warned about — picking a collage template suited to the platform is the collector's call.

### Generated offer images (`OfferPhotoGeneration` / `OfferPhotoEntry`, #311)

Where the plan (#309) and the renderer (#310) meet persistence. See [ADR-0018](../decisions/0018-db-queued-in-process-jobs.md) for the queue pattern.

- **Persisted, because the file is the deliverable.** These images are uploaded to a marketplace, so what matters is being able to download the *same bytes* again — the ones a buyer already sees in a live listing, with the labels they may be quoting (#312). Rendering on download would silently produce a different file after any change, so nothing regenerates implicitly: generation is explicit (a **Generate** button), its output is stored, and staleness is only ever *reported*.
- **`OfferPhotoGeneration`** — one row per offer (unique `offerId`), acting as both the queue entry and the state the UI polls: `status` (`queued | running | ready | failed`), `fingerprint`, `plannedCount` / `renderedCount`, `error`, `queuedAt` / `startedAt` / `finishedAt`. Enqueuing an offer that already has a queued or running run is a **no-op**, so a double click renders once.
- **`OfferPhotoEntry`** — the thin plan metadata pointing at each generated `Photo` (unique `photoId`): `sortOrder` (upload order), `source` (`collage` for a group, `copy_photo` / `upload` / `manual_collage` for a manual attachment, #313/#331 — `manual_collage` rather than `collage`, since in this vocabulary a plain collage is one the rules derived), `side`, `pairKey` (the front/back pair), `setIds`, `itemIds`. Plan metadata does not belong on `Photo`, which describes a *file*. `setIds` / `itemIds` are plain arrays, not FKs: one group can cover several single-copy sets, and the plan is a snapshot — a set removed afterwards is staleness, not a referential error. `itemIds` exists because `setIds` cannot answer "what is in this image" on its own (#314): a set larger than the collage's capacity is split into several groups that all name it.
- **Staleness** (`src/lib/offer-photo-fingerprint.ts`, pure + unit-tested): a sha256 over composition and *effective* order (#306), source photo ids, the offer's photo configuration (#308) and the platform's live limits, plus a hand-bumped `FINGERPRINT_VERSION` for when the renderer's own output changes. Hand-confirming an order catalog order already produced does **not** change it. Compared against the fingerprint stored by the last successful run to mark a plan **out of date** — a signal, never a trigger.
- **Replacement, not patching** (`runOfferPhotoGeneration`): the whole plan is rendered first, then swapped in one transaction — new `Photo` + entry rows in, the previous generated rows out, displaced bytes deleted post-commit. A failed run therefore leaves the previous images intact, and every image is a new `Photo` id, so the immutable-bytes-per-key assumption behind the serving route's cache headers holds.
- **Worker** (`src/lib/offer-photo-worker.ts`): started from `src/instrumentation.ts` `register()` beside the photo GC; requeues rows left `running` by a restart (a render is a full replacement, so repeating one is safe), then polls every 5s, **one job at a time** because rendering is CPU-bound through `sharp`. `kickOfferPhotoWorker()` nudges it right after an enqueue so Generate feels immediate; the poll is what guarantees the job runs. Worker state is pinned to `globalThis` like the Prisma/GCS clients, so `next dev` hot reloads cannot stack a second interval.
- **Surfaces**: `generateOfferPhotosAction` (enqueue + kick) and `GET /api/collections/[collectionId]/offers/[offerId]/photos` (state + stored images + what a Generate would produce now), polled by the Photos card on offer detail while a run is in flight. Bytes reuse the shared photo-serving route unchanged.
- **Tile labels** (#312): `readInputs` resolves the offer's two label templates **once per copy** through the title-template engine (`renderTitleTemplate` over a single copy, in the platform's listing language), and hands both texts to the renderer with that copy's tile. Per copy, not per group — a token resolved across a collage's copies would render the same joined value under every stamp, which is the opposite of identifying one of them. Usually `{ref}`, the copy's location ref, so the label is derived from the copy's own data and survives regeneration without renumbering, gaps or plan versioning. A blank template leaves that side undrawn; a copy with no value for either template's tokens gets an unlabelled tile, with no special-casing. Duplicate `locationRef` values inside one offer are possible and deliberately not handled.
- **Labels are fingerprinted as rendered text**, not as a template: the label is drawn into the pixels, so editing a copy's location ref changes the images exactly as replacing its scan does and must read as out of date for the same reason.

### Manual photo attachments (`OfferPhotoAttachment`, #313, #331)

Not everything a listing needs is derivable from the composition. An attachment is a plan entry the collector adds **by hand**, in one of three modes, and it is a *plan* row rather than a photo row precisely so a regeneration (#315) can recompute the derived images and leave these alone.

- **`copy_photo`** — a **specific** photo of a copy already in the offer (front, back, or an extra), so a perforation, a flaw or a cancel can be shown on its own. Guarded on creation: the copy must be in one of the offer's sets and own that photo. Its tile annotation resolves from that copy as usual, so a detail shot carries the same ref as that copy's tile in a collage.
- **`upload`** — an arbitrary image uploaded to the offer, promoted from the owner-agnostic `PhotoUpload` staging (#112) into an offer-owned `Photo` with `kind = original`. Rendering resolves the label templates against **no copy at all**: inventory tokens come out empty (the engine tidies the separators they leave) and only literal text survives. The offer owns both the original and the image generated from it, so purging generated bytes later leaves the original intact.
- **`manual_collage`** (#331) — several **chosen** photos, copy scans and offer uploads mixed freely, composited into one image at a column count the collector picks. This is the grouping the rules cannot produce: they group by set composition (#309), and what a listing wants to show sometimes cuts across that. Its images are `OfferPhotoAttachmentTile` rows (`sortOrder`, per-tile `source` / `photoId` / `itemId`) and its own `photoId` is null; a per-mode CHECK in the migration keeps the three shapes honest. **Rows are not stored** — a template's rows × columns is a *capacity* the plan fills, whereas here the contents are explicit, so only the width is an open question and the row count follows. Editing what one shows is not offered: remove and rebuild.
- **Never a pass-through, and one shape for all three.** Every attachment is "N tiles in C columns" rendered through `renderTiles` with the offer's own gap, strip, background and output limits — the single-image modes being N = C = 1, which is what they always were. That keeps "no image is ever unlabelled" (#312) true without a second code path, and is why #331 needed no new plan concept: `PlanAttachment` / `PlannedAttachment` simply carry `tiles` and `columns`. An offer with no collage numbers therefore still cannot generate, attachments or not.
- **Identity survives edits.** An attachment's plan token is `a:<attachmentId>` — unlike a collage side's `c:<side>:<itemIds>` it does not describe the contents, so a hand-built collage keeps its place in the plan order whatever it shows.
- **Append, then reorder.** A new attachment lands at the end of the plan (`sortOrder` past the last planned image, which the engine clamps); from there it is dragged. Its *position* is not stored on the attachment, though — see the plan order below. An attachment gets no special treatment under the platform's photo limit either: like every other image it is in the upload set or over the limit according to where the collector put it.
- **Bytes.** Removing an `upload` attachment deletes its `Photo` row and bytes; a `copy_photo` only ever pointed at the copy's own scan. A `manual_collage` applies the same rule tile by tile — which is why each tile records its own `source` — so its uploads go and its borrowed scans stay. `photoId` cascades: deleting the copy's scan removes the attachment from future plans while the image already generated from it survives — which is the staleness the fingerprint reports, not a referential error.
- **Batch.** The dialog attaches several at once (`attachOfferCopyPhotos` / `attachOfferUploads` / `attachOfferPhotoCollage`), validated up front — and, for uploads, moved into place up front — so a bad pick fails the whole batch rather than half-attaching. Its **Combine into one collage** tick turns the two tabs into a single selection, because a hand-built collage exists precisely to mix them.
- **Surfaces**: `src/lib/offer-photo-attachments.ts` (owner-checked domain), the `attachOffer*` / `removeOfferPhotoAttachment` actions, and the Photos card's **Plan** list (`getOfferPhotoPlanState().plan.images`). The plan list exists as its own surface because it shows entries that are not files yet — an attachment's position among *planned* groups is not something a list of stored images could show.

### Manual plan order and publishing (`Offer.photoPlanOrder` / `photoPlanUnpublished`, #313)

The generated collages had no order of their own — their sequence came from the set order (#306) and the grouping. The collector can now drag the **whole** plan, collages and attachments alike, into an order that is theirs, and hold individual images back from the upload. Both are keyed by the same **plan token**, which is also written on each stored image (`OfferPhotoEntry.token`) so a rendered file can be matched back to the entry it was rendered for.

- **Stored as tokens, not positions.** `Offer.photoPlanOrder` is a `String[]` of one stable token per planned image — `c:<side>:<sortedItemIds>` for a collage side, `a:<attachmentId>` for an attachment (`collageToken` / `attachmentToken` in the pure engine). A token identifies an image by *what it shows*, so it survives the thing a positional index cannot: a set reordered elsewhere, a copy added, a regeneration.
- **An override, reconciled at read time** (`applyManualOrder`, pure + unit-tested). The engine still derives the grouping and the natural order; this list then re-seats the images it names. A token the offer no longer contains is ignored (a sold-out collage leaves no gap); an image the list does not name (added since the last reorder) sorts **just after its natural predecessor**, so a new collage or attachment lands where the derivation put it rather than at the end. Empty (the default, and every existing offer's backfill) means the derived order, unchanged — so an offer never reordered behaves exactly as before, and `setOfferPhotoPlanOrder([])` clears the override.
- **Every drag stores the full sequence.** The card sends all tokens in their new order, so the override is total and the derived order cannot creep back in for the images left untouched.
- **Applied to the stored images, not just to the plan.** `setOfferPhotoPlanOrder` renumbers the offer's entries (`sortOrder`) into the resolved order, so the plan, the stored-files list, the upload numbering and the ZIP can never disagree. Only `sortOrder` moves — no bytes, no ids — which is why either list can be the drag surface and why a reorder is **not** a reason to regenerate.
- **Do not publish** (`photoPlanUnpublished`, `setOfferPhotoPublish`). A token list for the same reason the order is one: a generated collage has no row of its own, and unlike an attachment it cannot be removed. The image stays rendered and downloadable; it only leaves the upload set, which frees its slot under `maxPhotos` — hence the entries are renumbered after a toggle too. The card offers it on collages only, since an attachment has a delete.
- **Numbering.** Upload names (`01.jpg`…) are assigned over the **upload set** alone, so the ZIP is a gapless `1..n`; held-back images get `unpublished-NN` / `over-limit-NN`, which cannot be mistaken for a slot in the listing.
- **Fingerprint.** The order is deliberately **not** hashed — it is applied to the stored images, so it can never leave them stale. What is hashed is the **set** of rendered tokens, and only when the offer carries a manual order or a do-not-publish mark: those are the only things that can change which images exist without changing the composition or the limits, which are hashed already. An offer using neither keeps the hash it had before any of this existed.

### Sold sets leave the plan (#315)

When a copy sells, the collages of every offer still holding it advertise something that cannot be bought. `readInputs` (`offer-photo-generation.ts`) therefore drops the affected sets from the plan's inputs before the engine sees them — the plan, the fingerprint and the renderer all read the offer as *what is still sellable*.

- **The unit is the whole set.** An `OfferSet` sells together and indivisibly, so a series missing one stamp is not sellable anyway; one gone copy condemns its set. `excludedSetsFor` is one batched lookup mirroring the "needs action" derivation (ADR-0013 §4): the set has its own sale line (a partial sale of a multi-set offer), one of its copies sold through another offer's set, or one of its copies is held by another active offer **in active bidding** (#215).
- **No new state, no new trigger.** Composition is already what the fingerprint hashes, so a sale marks the stored images **out of date** by itself; nothing regenerates implicitly, exactly as with every other change. The stored images keep showing the sold set until the collector presses Regenerate — they may be live in a listing.
- **Only derived entries are recomputed.** Manual attachments (#313) are plan rows precisely because a rule cannot reproduce them; a regeneration renders them again untouched, including one pointing at a copy in a sold set. Labels are unaffected too: they derive from each copy's own data (#312), so the remaining stamps keep the labels a buyer may already be quoting.
- **Terminal offers are exempt** (`sold` / `withdrawn`): their images document a listing that is over, and recomputing them against an empty composition would only declare them permanently stale.
- **Surfaced, not silent.** `plan.excludedSets` (set id, label, `sold` | `bidding`) rides along in the panel state, so the card can say which sets left the plan and why — a collage that is no longer planned looks exactly like one nobody asked for.

### Getting the files out (#314)

Delivery is a **manual upload** — there is no Delcampe API (#154 is an open scoping question) — so the deliverable is a correctly ordered set of ready-to-upload files. The Photos card sits under the listing texts on offer detail and expands in place (no dialog, no route of its own) into the plan in upload order: each image with what it was rendered from, a lightbox, a per-image download, and a whole-plan ZIP.

- **Collapsed by default, one toggle.** Expanded the card is the tallest thing on the screen, and generating is a step taken once a listing is otherwise ready. Collapsing therefore hides *detail only*: the run's state, `outOfDate` and a skipped-side count stay in the header as chips, and Generate / Download all stay pressable. There is no second toggle inside — expanded means the whole plan.

- **Numbering** is ours, not the platform's: files are `01.jpg`, `02.jpg`… by plan position, because plain numbers sort into upload order in any file manager. Drift between our number and the position a listing ended up with is deliberately **not** defended against — labels (#312) identify copies independently of image position.
- **`src/lib/zip.ts`** — a dependency-free, deterministic ZIP writer, deflating only when that actually shrinks a payload (collages are already-compressed JPEG, so in practice they are stored verbatim). Same reasoning as `extension/archive.mjs`, which is kept separate: that one is a build script outside the app's module graph. No ZIP64; a plan is bounded by the platform's own photo-count and file-size limits.
- **`buildOfferPhotoArchive`** reads the stored bytes and zips them in plan order, served by `GET .../offers/[offerId]/photos/zip` with a `Content-Disposition` named after the offer. Buffered, not streamed — the archive is a handful of megabytes and a stream would hold the same central directory anyway. Nothing is re-rendered on download, so an archive pulled twice from unchanged images is byte-identical.
- **Skipped sides are reported, not omitted.** `planOfferPhotos` returns `skipped` (side, group, the copies with no scan for it) alongside the images, and the card shows it whether or not the preview is expanded: a set of eight losing its back collage over one missing reverse scan is invisible otherwise. A group the photo-count limit dropped outright is *not* reported twice — the drop count already says it.

## CI

The `ci.yml` GitHub Actions workflow runs three jobs on every push and pull request:

- **static-checks** — lint, typecheck, build (generates Prisma client first)
- **unit** — unit tests (generates Prisma client first)
- **integration** — spins up a PostgreSQL 16 service container, applies migrations via `prisma migrate deploy`, then runs `tests/integration/`

The **publish-image** job triggers only on `v*` tags and requires all three jobs to pass. It pushes a multi-arch image (`linux/amd64`, `linux/arm64`) to `ghcr.io/michalwy/stamporama`.

## Authentication

Stamporama uses [Better Auth](https://better-auth.com/) with the email/password provider.

**Server instance:** `src/lib/auth.ts` — initializes Better Auth with the Prisma adapter (sharing the `prisma` singleton from `src/lib/db.ts`) and the email/password provider.

**Client instance:** `src/lib/auth-client.ts` — `createAuthClient()` for use in client components. Defaults to the same origin (`/api/auth/*`); no explicit `baseURL` required.

**API handler:** `src/app/api/auth/[...all]/route.ts` — catches all Better Auth API requests (`GET` + `POST`) via `toNextJsHandler(auth)`.

**Middleware:** `src/middleware.ts` — protects `/c/*` (collection routes) and `/collections` (collection picker). Runs on the Next.js Edge runtime; calls `/api/auth/get-session` via native `fetch` to avoid importing Node.js-only modules in Edge context. Unauthenticated requests are redirected to `/sign-in`.

**Prisma schema:** Better Auth manages four tables — `user`, `session`, `account`, `verification` — added in migration `20260714190000_add_better_auth_schema`.

**Session check in Server Components:** call `auth.api.getSession({ headers: await headers() })` directly (Node.js runtime, safe outside middleware).
