# Architecture Overview

## Deployment Model

Stamporama uses separate Docker Compose files for local development and self-hosted production.

| File | Purpose | Command |
|---|---|---|
| `docker-compose.yml` | Local dev: app + bundled PostgreSQL, built locally | `docker compose up` |
| `docker-compose.dev.yml` | Hot-reload overlay, source mounted | `docker compose -f docker-compose.yml -f docker-compose.dev.yml up` |
| `docker-compose.prod.yml` | Self-hosted production: prebuilt GHCR image, external DB | `docker compose -f docker-compose.prod.yml up -d` |
| `docker-compose.network.yml` | Optional overlay: connect app to a shared Docker network for DB access | combined with `docker-compose.prod.yml` via `COMPOSE_FILE` |
| `docker-compose.e2e.yml` | Isolated PostgreSQL on port 5433 for integration tests | started by `pnpm test:integration` |

The `COMPOSE_FILE` variable in `.env` sets the active file list so operators can run bare `docker compose` commands without specifying `-f` flags.

## Production services

Production does not run a database container. The operator provides an external PostgreSQL via `DATABASE_URL`. **PostgreSQL 15 or newer is required** — migrations use `NULLS NOT DISTINCT` unique indexes (see [ADR-0006](../decisions/0006-multidimensional-catalog-prices.md)). The bundled dev/e2e containers run Postgres 18, mounted at `/var/lib/postgresql` because 18+ images keep the cluster in a major-version-specific subdirectory; bumping that major requires a dump/restore of the dev volume (see [Upgrading the local Postgres major version](../development/postgres-upgrade.md)).

### Behind a reverse proxy

Nearly every self-hosted deployment sits behind one — nginx, Caddy, a Cloudflare tunnel — and there
is exactly one thing it has to be told, since #590:

> **The proxy must pass the *chunk* size, not the file size.**

A card scanned at 1200 dpi is 100–200 MB, and no ordinary proxy passes a request body that large:
nginx defaults `client_max_body_size` to 1 MB, and Cloudflare caps a body at 100 MB on Free and Pro
and 200 MB on Business. So a card scan is **uploaded in pieces** (`STAMPORAMA_UPLOAD_CHUNK_KB`,
default 512 KB) and no single request carries more than one of them. The default is below every
proxy default we know of, which means an unconfigured proxy needs nothing done to it at all — and a
proxy configured to pass 200 MB was never going to be enough anyway, because the app's ceiling is
what a card may weigh and not what a request may.

Raising `client_max_body_size` to the size of a *scan* is therefore the wrong fix and is no longer
needed. What is worth checking is the opposite: a proxy configured **below 512 KB** needs
`STAMPORAMA_UPLOAD_CHUNK_KB` lowered to match, and one on a permissive path can raise it to make
fewer, larger requests. Copy photos still upload in a single request — a few megabytes, comfortably
inside every default.

## Docker Image

The `Dockerfile` uses four stages:

| Stage | Base | Purpose |
|---|---|---|
| `base` | node:22-alpine | corepack + pnpm |
| `deps` | base | install dependencies only |
| `builder` | base | generate Prisma client + build Next.js |
| `runner` | node:22-alpine | runtime image with full `node_modules` |

The runner stage ships the full `node_modules` (not Next.js standalone output), so `pnpm start` works without re-installing. `pnpm-workspace.yaml` is copied to the runner as a safety net for the build-scripts allowlist.

The `STAMPORAMA_VERSION` build argument is baked into the image and exposed at runtime via `process.env.STAMPORAMA_VERSION`. The `getAppVersion()` function in `src/lib/version.ts` reads it.

`STAMPORAMA_BUILD_DATE` (#507) is baked the same way and read by `getAppReleaseDate()`, which returns the instant as an ISO string or `null` — an unstamped build (every local `pnpm dev`) shows no date rather than an invented one. CI sets it from the image's own `org.opencontainers.image.created` label, so the date shown in the UI and the date on the image agree. The value crosses to the client as a string and is formatted there (`AppVersionLabel`): the inline day is the UTC calendar date sliced off the ISO string, so a server-rendered shell cannot disagree with the browser, while the full instant is localized inside a hover tooltip that never exists in the server's HTML.

## Prisma / Database

Stamporama uses [Prisma](https://www.prisma.io/) with the `@prisma/adapter-pg` driver adapter. The adapter uses the `pg` npm package for PostgreSQL connections — no native query engine binary is required.

**Generated client:** `pnpm prisma:generate` writes the TypeScript client to `src/generated/prisma/`. This directory is generated and should not be edited by hand; it is committed to the repository so that CI jobs that do not run `prisma:generate` before type-checking can still compile.

**Migration workflow:**

| Context | Command | Notes |
|---|---|---|
| Local development | `pnpm prisma:migrate` | Applies + generates new migration against local dev DB |
| Docker Compose (any stack) | `prisma migrate deploy` | Runs automatically on container start before `pnpm start`/`pnpm dev` |
| Integration tests | `pnpm exec prisma migrate deploy` | Applied automatically by `pnpm test:integration` |
| CI (integration job) | `pnpm exec prisma migrate deploy` | Runs against a fresh service-container DB |
| Production | Handled automatically on container start | `docker-compose.prod.yml` runs migrate deploy before `pnpm start` |

**Schema:** `prisma/schema.prisma` — PostgreSQL datasource, client output at `src/generated/prisma`.

**Config:** `prisma.config.ts` — loads `DATABASE_URL` from the environment (via dotenv), sets schema and migrations paths.

**Client singleton:** `src/lib/db.ts` — exports `prisma`, a `PrismaClient` instance initialized with the `PrismaPg` adapter. Uses `globalThis` caching to avoid exhausting connections during Next.js hot-reload.

## Domain Model

### Collection

The `Collection` model is the top-level organizing unit. All stamp data belongs to a collection. A user can own multiple collections; each collection belongs to exactly one user.

**Prisma model** (`prisma/schema.prisma`):

```prisma
model Collection {
  id        String   @id @default(cuid())
  slug      String
  name      String
  ownerId   String
  createdAt DateTime @default(now())
  owner     User     @relation(fields: [ownerId], references: [id], onDelete: Cascade)

  @@unique([ownerId, slug])
  @@map("collection")
}
```

**Key design decisions:**
- `@@unique([ownerId, slug])` enforces slug uniqueness per user at the database level and serves as the index for fast slug lookups.
- Slugs are auto-generated from the collection name (lowercase, hyphens); collisions within a user's collections get a numeric suffix (`-2`, `-3`, …).
- Authorization uses `getCollectionBySlug(ownerId, slug)` — a lookup by the compound unique key. A slug that belongs to a different user returns `null`, producing a 404 rather than a 403 to avoid leaking slug existence.

**Domain layer:** `src/lib/collections.ts` — `createCollection`, `getCollectionsByOwner`, `getCollectionBySlug`. Imports `"server-only"` to prevent accidental bundling into client code. Pure slug utilities live separately in `src/lib/slug.ts` (no `"server-only"`, unit-testable).

**Collection routes:** `/c/[collectionSlug]/` — the layout validates the slug and authorizes the session user as owner before rendering.

**Dialog primitive:** All modal dialogs use the shared shell at `src/app/dialog-shell.tsx`. It provides: backdrop, header with close button, scrollable body, optional fixed footer.

**Icons** (#459; [ADR-0030](../decisions/0030-one-icon-vocabulary.md)): `src/app/icons.tsx` is the app's only icon module and the only file importing `lucide-react`. Icons are named for **meaning** (`<Icon name="edit" />`), `IconName` is a closed union so an unknown name fails typecheck, and size (five steps, `md` default), stroke (`1.75`), inherited colour and text alignment are all decided there rather than per call site. `RowAction.icon` and `CountFilterChip`'s `icon` take a name and are sized by the component drawing them. Typographic characters (`…`, `×` between dimensions, the `›` path separator, prose arrows) stay text; `extension/` is out of scope, having no React.

### Catalog prefixes (`CollectionAreaVendor` / `IssueCatalogPrefix`, #66/#377)

A stamp's catalog number is stored **bare** (`200`); its identity is `vendor + effective prefix + number` (`Mi·PL 200`). The prefix is set per (area, vendor) on `CollectionAreaVendor.areaPrefix` and **inherited down the area tree** — resolution walks toward the root until an area sets one, so a null row *stops* inheritance and means "no prefix here".

An **issue may override it** (#377): `IssueCatalogPrefix (issueId, catalogVendorId, areaPrefix)` replaces the inherited prefix for that issue's stamps and that one vendor, for issues numbered under a special or commemorative sub-catalog. `areaPrefix` is NOT NULL here, unlike the area's — an issue has exactly one level above it, so "inherit" is simply the absence of a row, which is what a blank field in the issue dialog stores.

The override is the **catalog identity**, not a display layer, so one resolution serves every consumer:

- **Server**, `src/lib/area-prefix.ts` `effectivePrefixFor(areaId, vendorId, nodes, issueId, issuePrefixes)` — the issue's override, else the area walk. Used by the stamp picker's labels *and* match keys (`stamps.ts`), the Colnect matcher and backfill (`colnect.ts`), and duplicate detection (`duplicate-catalog.ts`, whose `CatalogPrefixContext` also accepts prefixes typed into a form but not saved yet, since the issue *create* dialog has no row to read).
- **Pure / shared**, `src/lib/area-vendor.ts` `buildAreaVendorMaps(areas, prefixByIssue)` → `vendorMapFor(areaId, issueId)`, an override-applied `AreaCatalogEntry` lookup memoized per (area, issue) pair. Every row that renders a catalog chip resolves through it, so the *area* map is never read directly where an issue is in play. Server label builders (`offer-labels.ts`, `auction-lines.ts`, `items.ts`, `title-copy.ts`, the packing list) pass the map in; the client gets it from `useAreaVendorMaps(areas, collectionId)`.
- The override map is loaded **whole, once per read** (`src/lib/issue-prefix.ts` `loadIssuePrefixMap`; client `GET /api/collections/[id]/issues/catalog-prefixes`). The table is sparse by construction — only issues that override something have a row — and every list screen needs the answer before it can draw a single chip. The client query lives under the `["issues", collectionId]` key namespace so the existing issue-mutation invalidations cover it.

### Variant price grid (#618)

No schema of its own — it writes ordinary `StampCatalogPrice` rows (ADR-0006, ADR-0020) — and exists because the unknown-variant rollup (#238, #616) is worth exactly as much as the completeness of the variant prices behind it, while entering those prices was one dialog per stamp against a catalogue that prints a whole tree on one line. Rows are the stamp tree, columns are the collection's conditions; the edition, the certificate (default none) and the format (tabs) are chosen once above the grid. **One write per cell, no draft and no Save** (#404's idiom), and clearing a cell **deletes** the row rather than storing a zero.

Server half is `src/lib/variant-prices.ts`: `getVariantPriceGrid(ownerId, scope)` returns the tree, the dictionaries, the area's editions, every price already on those stamps and the resolved format multipliers in one payload — the three controls above the grid are flicked constantly, and a refetch per flick is the worse trade. `scope` is `{ kind: "issue" }` or `{ kind: "stamp" }`, and a stamp scope **resolves up to its tree's root**, which is what lets #617's per-variant blocker links and the On Colnect card's umbrella row open the same grid. `setVariantCatalogPrice` validates every axis against the collection and takes the currency from the edition's own catalog, and find-then-writes because `stamp_catalog_price_unique` is `NULLS NOT DISTINCT`.

The **worklist** (`listUnpricedVariantTrees`, screen at `/c/[slug]/stamps/variant-prices`) is umbrellas whose variants are not fully priced, counted over **the conditions the collection actually holds or lists at** (the distinct conditions of its undisposed copies) rather than over the whole dictionary. The rule is pure and unit-tested in `src/lib/variant-price-coverage.ts` (`unpricedVariantCells`): certificate none, format single, and whichever edition is newest *with* a price, so a figure recorded once and never repeated still counts. Only stamps with children are considered and their descendants' prices are read in one query, `loadVariantPricesForUmbrellas`' shape.

### Checklists (`Checklist` / `ChecklistStamp`, #531; [ADR-0031](../decisions/0031-checklists.md))

A **checklist** is a named list of stamps that counts as one complete unit — the collecting goal, as against `Issue`, which is the publication event. It replaces `IssueMember.requiredForCompleteness`, one boolean that gave an issue exactly one complete set; the migration turned every issue with a required member into one checklist named after it, and dropped the column. `ChecklistStamp` is many-to-many both ways, and **membership is required-ness**: an optional extra is an `IssueMember` on no checklist.

`Checklist.issueId` is **nullable**, the same anchor idiom `StampFormatFactor` uses — null means the checklist spans issues (a thematic set). Only the issue-scoped editor is built (`useChecklistsAction`, on the issue's row, per ADR-0020 §7); a cross-issue checklist has no home yet. `sortOrder` is load-bearing: the first checklist is what a single-checklist row shows and what a new stamp joins by default.

Reads split by subject, and each consumer states which it means. **Per checklist**: the completeness grid (`src/lib/checklist-completeness.ts` + its pure `-rules` half) and the catalog-price total (`IssueListItem.checklists[].priceTotal`; `getChecklistPriceDetails`) — summing the union would count a stamp two sets share once, for a figure answering neither. **Union of the issue's checklists**: `requiredCount`, the declared-range suggestions (#333) and the issue-level photo gallery (#137), since an issue publishes one range of numbers however many goals sit inside it. **One named checklist**: the intake fan-out (`intakeStamps`), auction lot composition (`resolveAuctionLineStamps`) and the picker's *whole set* buttons.

Storage and reads live in `src/lib/checklists.ts`; the `default` sentinel the stamp form submits when an issue has no checklist yet is in the pure `src/lib/checklist-vocabulary.ts`, since the form is a client component.

### Want list (`Want` / `WantCondition` / `WantCertificateStatus` / `WantFormat`, #532; [ADR-0032](../decisions/0032-want-list.md))

A **want** is what the collector is looking for — a stamp not held yet, or one held in a shape meant to be replaced. Deliberately **not** a fourth disposition: `inCollection`/`forSale`/`forTrade` live on `Item`, an `Item` is one physical copy, and a wanted stamp has no copy, so a `wanted` flag would force phantom rows and break every count that reads inventory.

A want carries an **acceptance set per axis, where zero rows means "any"**. `WantCondition` has a plain composite key; `WantCertificateStatus` and `WantFormat` have a **nullable** FK, because a null there is a value of its own — "no certificate" (ADR-0006 §2) and "single" — with uniqueness enforced by `UNIQUE ... NULLS NOT DISTINCT`, the idiom `stamp_catalog_price_unique` already uses. Nothing derives a "minimum quality": `StampCondition.sortOrder` is display order, and `U` vs `MNG` are different axes rather than points on one scale. `closedAt` is null while the want is open — `Item.disposedAt`'s idiom. There is deliberately **no price** on a want (ADR-0032 §5): a want has no date, so a figure on it is a price opinion frozen the day it was typed and never corrected, and on a whole-series add it is one number over stamps worth wildly different amounts. What a stamp is worth at the moment of buying is the recommendation engine's answer from recorded results (ADR-0022/ADR-0029), against the copy actually in hand.

What a copy satisfies is the pure `wantMatchesCopy` in `src/lib/want-rules.ts`, shared by every consumer; storage and reads are `src/lib/wants.ts`. `priority` is stored as its **rank** (`Int`, 0 = high), not as the word: the list is ordered by it and paged on the server, and the only order Postgres can put a `text` column in is its spelling, where `high < low < normal` is not what anybody means. The vocabulary lives in `want-rules.ts` and the word is what travels on the wire.

What the collection has of a wanted stamp is a **derived split** (`WantCopyCounts`: held / ordered / inTransit, `to_sort` folded into held) — a single count made an ordered-but-unarrived copy look like no copy, and the want then urged a second bid at the next auction. Buckets are held / toSort / ordered / inTransit, and the figures **exclude the copy they are drawn on** (`loadItemWantSummaries`, keyed per copy so two copies of one stamp each omit a different one) — a purchase-order row otherwise counted itself as *one in transit*. It is counted per **stamp** (`WantListItem.copies`, `StampWantSummary.copies` — the upgrade context) *and* per **want** (`WantListItem.matchingCopies`, `StampWantSummaryEntry.copies`, filtered through `wantMatchesCopy`), off one `loadCountedCopies` read; only the per-want figure may claim something is *on its way*, since a used copy in the post answers a want for "anything" and a mint-only want not at all. The row carries the wanted stamp's catalog photos (#137), and the list is **cursor-scrolled like every other large list** — `listWantsPaginated` + `listWantYearFacets`, both over one `buildWantListWhere`, so a facet can never count a row the page would not show. It is deliberately *not* the whole-list-and-filter-in-the-browser shape Contacts uses: a collection's contacts are a few hundred, a want list is a shopping list for a whole collecting plan and runs to thousands. Every filter — status, priority, acceptable condition, area, year, free text — is a `where`; the condition filter ORs `conditions: { none: {} }` in, because an empty acceptance set means "any" and such a want *would* take the condition asked about. Ordering is `closedAt` (nulls first) → `priority` → `createdAt desc` → `id`, the last of which is what makes an offset page stable over ties. The row also carries a **catalogue range** (`want-valuation.ts`, pure): a want accepts a *set* of (condition, certificate, format) combinations, each with its own value, so the honest figure is min–max in the base currency rather than one number picked out of the set. Each combination is valued with `valuateCopy` — the same function that prices a copy, so a want and the copy that satisfies it cannot drift — with unpriced combinations counted but never zeroed, and `estimated` inferred from the absence of a recorded row for the format rather than from a factor existing. Computed once per page (the page's stamps' prices plus the per-collection pricing preamble the stamps list already loads), and only in `listWantsPaginated`. A `stampId` filter is what the stamp detail screen's read-only **Wants** card reads (#518's shape), and `loadStampWantSummaries` denormalizes each stamp's open wants onto `StampListItem.wants` / `StampNodeData.wants` for the catalogue lists' want chip — scoped to the page's ids like the copy counts beside it, which is also why creating a want invalidates the stamps and issues caches and not only the wants one. `ItemListItem` and `CopyGroupRow` carry it through `enrichItemRows`, the single funnel every copies view uses, and `AuctionLotLineItem` carries the same summary, and because a line names a concrete `(condition, certificate, format)` the chip there runs `wantMatchesCopy` over each entry's raw `acceptance` — the intake review's predicate — to say not just *wanted* but *this one would satisfy it*. `listWantIssueGroups` is the same list as one row per series — a **view**, not the list's shape: a want's subject is a stamp and its acceptance sets are per stamp, so an issue heading over rows whose terms differ overstates, and the issue page's completeness grid already answers "how far along am I" from copies held. Grouped server-side for #424's reason (offset paging would split a group across pages), counted on the stamp's *first* issue membership and read back through an `issueId` filter matching *any*, with `NO_ISSUE` for the stamps in none. The row's `open / total` is counted with every filter except open/closed, so the fraction means the same thing from either side of the toggle; which groups appear still obeys it. The screen renders the shared `ListFilterSidebar`; area and year come from `useCollectionFilterStore` rather than the URL (#143), as they do in the stamp picker: every other filter on this screen is local state, and half a toolbar in the address bar would be a second mechanism for one job. The **review is raised by arrival, not by creation**: a copy becoming `delivered` is the transition, whichever route it took — added by hand (which starts delivered), sorted out of a purchase lot, or won at auction and settled into one, which is what closes that path without a second review of its own. `bulkUpdateLotItems`/`Scoped` return the copies their change moved into `delivered` (candidates read *before* the write, since afterwards an arrival is indistinguishable from a copy already here) and `updateItem` returns `becameDelivered`; `intakeStamps` raises nothing, its copies being `ordered`. The review then offers close / narrow / leave open per want. Nothing closes automatically, and narrowing is seeded (every condition except the one that arrived) but never decided by the app. Completeness targets are a **generator, not a source**: `createWantsForMissing` materialises explicit rows once from a checklist's gaps, skipping stamps with a held copy or an open want, so pressing it twice is a no-op. The Issue list runs the same generator over a whole issue (#548) — `createWantsForIssue`, with `previewIssueMissingWants` behind the confirmation — and the two share `wantGapForStamps`, since a preview that computed the gap by its own rules would state a count the write then disagrees with. The unit of choice there is still the **checklist**, not the issue: an issue may hold several goals (#531) and a stamp on none of them is an optional extra nobody is shopping for, so the dialog ticks checklists and the write unions the picked ones — the gap being recomputed over that union, which is also what keeps a stamp on two of them one want rather than two. That run carries **terms**, wide open by default, and both halves of the gap are read through them: *missing* is "no counted copy `wantMatchesCopy` would take" rather than "no copy at all", and *already wanted* is an open want whose sets are `acceptanceSetsEqual` to these rather than any open want — so a used copy in the album leaves a stamp missing for an MNH run, and *used, for sale* beside *mint, for me* is two wants on one stamp rather than a duplicate to suppress. Wide open, both reduce to the original rules exactly, which is what lets the completeness card's own button stay the same call with `ANY_ACCEPTANCE`. The terms are part of the preview's **query key**, not a filter applied to a cached answer, for the same reason.

**Named acceptance profiles** (`AcceptanceProfile` + three member tables mirroring the want's, #533; ADR-0032 §9) are a collection dictionary of reusable acceptance sets — "any mint", "anything" — carrying exactly the three axes a want carries, nullable members and `NULLS NOT DISTINCT` included, so nothing expressible on a want is inexpressible on a profile. Applying one **seeds**: the sets are copied onto the want and the link ends there, which is why there is deliberately **no `profileId` on `Want`** — the absence *is* the decision, a schema cannot state it, and ADR-0032 §9 does. It is `CollageTemplate`'s shape (#308) and the precedent is the reason: a reference would make editing a profile a silent rewrite of what every existing want accepts, closed ones included, whose acceptance is a record of a decision already taken rather than a setting. Nothing already written can therefore be affected, so a delete needs no in-use check and an edit needs no warning; changing a profile *and* the wants carrying its terms is two acts, and the bulk edit that would make it one is left unbuilt on the same trigger #533 itself waited on. `validateAcceptance` and the `AcceptanceInput` shape moved to `src/lib/acceptance.ts`, shared by `wants.ts` and `acceptance-profiles.ts` so the two cannot come to disagree about what "no certificate" means; storage and reads are `src/lib/acceptance-profiles.ts`, and a duplicate name is its own error rather than a constraint violation the panel can only call "please try again". The picker lives inside the shared acceptance editor (`want-acceptance-fields.tsx`), so the want form and the intake review's narrow step both get it from one place and the Settings editor that *defines* profiles turns it off; which profile it shows is **derived** by comparing the sets (`acceptanceSetsEqual`, pure, in `want-rules.ts`) rather than stored, since a seed leaves nothing to read — edit one box and it drops to *Custom*, the terms no longer being that profile's. The profile a want was **saved** on leads the next add (`LS_LAST_ACCEPTANCE_PROFILE`, per collection, in `add-copy-defaults.ts` beside the last subtype and the last condition): saved rather than *picked*, derived on submit rather than tracked as a selection, **cleared** when the terms match no profile, and read on **add** alone — an edit shows the want's own terms and the narrow step keeps §7's seed. Applied during render, once, flagged rather than conditioned on the sets being empty so a refetch cannot re-seed boxes deliberately cleared.

### Currency conversion (`ExchangeRate`, #20)

Every figure that has to be comparable across currencies — catalogue values, holdings valuation, purchase and sale totals, auction headroom — pivots through the collection's `baseCurrency`. The rates behind that live in `src/lib/exchange-rates.ts`, fed by the ECB daily reference feed.

- The cache is **one dated EUR-anchored snapshot per collection**, not a bag of per-pair rates: rows are `fromCurrency = 'EUR'`, one per currency, all sharing a single `fetchedAt`. Any pair is derived as `X_to / X_from` (`convertViaEur`), the same arithmetic applied to a freshly fetched table.
- That shape exists for **consistency, not storage**. Pair-wise rows were fetched and expired independently, so `EUR → PLN` and `PLN → EUR` could come from different ECB publications and their product was not 1 — anything converted into the base currency and back drifted ~0.1%, by a different amount each day. An auction lot's catalogue value does exactly that round trip (`auction-lines.ts` pivots base → sale currency), so a 1500 EUR price on a EUR sale read as `1498.44`. With one snapshot behind both directions the rates are exact reciprocals and the round trip is lossless.
- Staleness is a property of the **snapshot**, dated by its oldest row: past 24 h the whole table is refetched and rewritten (delete-then-insert in one transaction), never patched pair by pair. An unreachable feed falls back to the existing snapshot flagged `isStale`; only a snapshot that cannot answer the pair at all throws.
- Migration `20260729120000_exchange_rate_eur_snapshot` drops the legacy non-EUR-anchored rows — no schema change, only the meaning of the rows. `src/lib/demo/seed-inventory.ts` seeds the same shape from static reference rates so the demo converts offline.
- Rates frozen onto a record (`Purchase.fxRateToBase`, `Sale.fxRateToBase`, `AuctionLot.fxRateToBase`) are unaffected: they are dated observations copied out of this mechanism at the moment the transaction happened, and are never recomputed.

### Physical holdings (`Item`)

`Item` represents a collector's physical copies. Per ADR-0007, there is **one row per physical copy** — no quantity field — because copies of the same stamp and condition can differ (e.g. postmark type) in ways that affect value and intent.

- `stampId` → `Stamp` at any level of the variant tree: a base stamp (`parentId = null`) means the variant is unknown; a variant row means the copy is identified. The tree level implicitly encodes variant certainty; there is no "unknown" flag.
- A `Stamp` may carry a `colnectId` (#247, part of #155): the numeric Colnect Marketplace item-ID, stored as a plain optional column — **not** through the `CatalogVendor`/`StampCatalogNumber` machinery. A Colnect item-ID is an external identifier, not a priced catalog number, and must be settable on any stamp regardless of area, so it needs neither a vendor row nor per-area attachment. No uniqueness constraint. It surfaces in stamp reads and is editable in the stamp form alongside the catalog numbers; a later browser agent (#155) will populate it in bulk.
- `ColnectCatalogMapping` (#248, part of #155) translates a **Colnect catalog abbreviation** (Mi, Sn, Yt, Sg, AFA, Pol…) to one of the collection's local `CatalogVendor`s, so future number-matching can line Colnect's catalogs up with ours (Colnect `Pol` = our Fischer `Fi`). One row per `(collectionId, colnectAbbrev)`; only mismatches need a row. Resolution (`src/lib/colnect.ts` `resolveColnectAbbreviation`): an explicit row wins; else it falls back to a local vendor whose own `abbreviation` matches (case-insensitive); else `null` — unmapped abbreviations are ignored by the matcher, not errors. Edited under **Settings → Colnect**.
- **Colnect catalog-number matcher** (#250, part of #155) — `POST /api/collections/[id]/colnect/match` takes a batch of extracted Colnect items (`{ colnectId, catalogRefs: [{ catalog, number }] }`) and decides which of our stamps each one is, writing the Colnect ID onto unambiguous matches. Matching is **strict full-key**: a Colnect ref matches only when `vendorAbbrev + effectiveAreaPrefix + number` — folded of spacing/punctuation (`catalogMatchKey`) — is exactly equal, after resolving the ref's abbreviation through `ColnectCatalogMapping` and reconstructing the stamp's key from its effective per-vendor prefix — its area's inherited one, or its issue's override (#377) — via `src/lib/area-prefix.ts`. The decision matrix (`src/lib/colnect-match.ts` `decideColnectItem`, pure/unit-tested): 0 candidates → `skipped`; 1 clean candidate → `auto` (write); 1 candidate that partly conflicts, or that already holds a *different* `colnectId`, or >1 candidates → `needs-confirm` with the candidate list — an existing ID is **never** silently overwritten. A `dryRun` flag computes everything and persists nothing (preview / write safety net). Recall (the coarse net that a batch's strict keys are then checked against, in memory) is asked of `StampCatalogNumber` and the stamps loaded by id — **not** as an `OR` of `catalogNumbers: { some }` on `Stamp`, which Prisma emits as one correlated `EXISTS` per condition: ~60 of them in a 25-item batch costed the plan at ~900k, over Postgres's JIT inlining threshold, and ~1.7s went on compiling a query whose work is ~10ms. Flattened it is ~5ms. `stamp_catalog_number` carries a `(catalogVendorId, number)` index for the same reverse direction; the recall predicate is a substring match and cannot use it, so it is there to keep the planner's estimates honest as a collection grows. `POST …/colnect/confirm` commits a user-chosen match, refusing to overwrite a different existing ID unless `allowOverwrite` is set (409). Orchestration in `src/lib/colnect.ts` (`matchColnectItems`, `confirmColnectMatch`).
- **Colnect catalog-number backfill** (#280, part of #155) — an opt-in `backfill` flag on both matcher endpoints fills a matched stamp's **missing** catalogs from the numbers the Colnect page prints. Writing is the **inverse of matching**: we store the bare `StampCatalogNumber.number` while Colnect prints it joined with the country code, so the area prefix has to be stripped. The split rule (`src/lib/colnect-backfill.ts`, pure/unit-tested): the prefix is the **leading space-separated, digit-free token** (`PL 3690` → `PL` + `3690`; `BL132`, `3706-3711`, `ATM2.2x` have none). Per reference — matches our number → nothing; we hold a different one → `conflict` (reported, never written); no prefix printed → stored verbatim; prefix equals the area's effective prefix for that vendor → bare remainder stored; area sets no prefix → `skipped-no-area-prefix`; prefixes differ → `prefix-mismatch`; unmapped abbreviation (#248) → ignored. Proposals hang off each `ColnectCandidate`, so a dry-run preview shows exactly what a write would add — including for the candidates of a `needs-confirm` item, which `…/colnect/confirm` then applies to the stamp the user picks (it takes the item's `catalogRefs` alongside the match). A fill colliding with an existing catalog identity respects `duplicateCatalogMode` (#85): `duplicate` (not written) under *block*, written with a `duplicateWarning` under *warn*. Applies to already-linked stamps too, and recomputes `primaryCatalogSortKey` for touched stamps (#181, ADR-0014). Off unless requested, so an older client can never write numbers by accident.
- **Listing kit** (#405, part of #155) — `GET /api/collections/[id]/offers/[offerId]/listing-kit`, read-only, session **or** Assistant token. One call answering "everything this offer wants filled into a marketplace form": each copy's catalog item-ID (`Stamp.colnectId`, #247) and its condition already translated into the platform's vocabulary (`ColnectConditionMapping`, #404), the `quantity` (the number of sets, with `items` describing one of them), the price and currency, the generated description / private note with the description's format (#319), and the photo plan's **upload set** in upload order as paths on the photo route — which takes the same bearer, so the extension fetches the bytes with the token it read the kit with. Platform-neutral in shape; how each value maps onto Colnect's form belongs to the extension's platform module (#408/#410). Orchestration in `src/lib/listing-kit.ts` (`getOfferListingKit`), which loads the area tree and the condition map **once per offer** and reads the photos through `getOfferPhotoPlanState` (filtered to `publish && !overLimit`) so the kit, the Photos card and the plan's ZIP cannot disagree. **Preconditions** (#406) are pure and unit-tested in `src/lib/listing-preconditions.ts` (`evaluateListingPreconditions`), and apply only to a platform naming an Assistant module — `Contact.platformModule`, the extension's `PlatformModule` id (`COLNECT_PLATFORM_MODULE` in `src/lib/platform-modules.ts`), set in **Settings → Colnect** by picking the platform (`setColnectPlatform` / `getColnectPlatform` / `listPlatformContacts` in `colnect.ts`) rather than on the contact form — it is one fact per collection, and it leads the tab whose two mappings only matter for that platform. The setter is exclusive (the previous holder is cleared in the same transaction) and refuses a contact that is not a platform of the collection. **Which checks apply is the module's own answer** (#493, `listingModuleRules`): the item-ID and the grade are Colnect's rules, Allegro's entry claims neither, and the homogeneity of the sets is asked of every module. So a platform with no listing half yields `no-platform-module` **alone** (the kit endpoint refuses on it; the workspace skips the evaluation and its condition-map read altogether and reports nothing, since "listed by hand" is not a fault to fix). The rest: not `ready`, no copies, a stamp with no item-ID, an unmapped condition, or sets that are not interchangeable — compared on *what the form would receive* (item-ID + grade, order-insensitive), with the local ids standing in where either is missing so two unmatched sets are never judged interchangeable. `not-ready` / `no-sets` return alone; the others are reported together, each naming what to fix. The route serves the kit on an empty list and **409 `{ error: "preconditions", blockers }`** otherwise — a wrong grade or an untruthful quantity misdescribes the goods, unlike an over-long text (#403), which is not a blocker. The domain function always returns the kit *with* its blockers, so the bulk listing card and the endpoint read one evaluation. The workspace row carries the same list (`ListingWorkspaceOffer.blockers`, computed in `listReadyOffersForListing` from one extra select plus a single condition-map load per batch) and renders it as a **Can't list** chip on the collapsed line with the reasons spelled out when expanded — scanning a batch must not require expanding it. It gates the Assistant handoff (#407) only; **Publish is untouched**, since posting by hand is what a collector does about a gap the Assistant cannot fill.
- **Collection route auth — session or token** (`src/lib/route-auth.ts` `resolveCollectionOwner`). The Colnect matcher endpoints **and the photo-serving route** accept either a Better Auth session **or** an `Authorization: Bearer` **Assistant token** (`AssistantToken`, #253). The token is stored only as a SHA-256 hash (`src/lib/api-tokens.ts`), authorizes as the collection's owner for that one collection, and is required because the browser extension calls us cross-site from colnect.com where the Lax session cookie is not sent. It is issued either by **registration** (below) or by hand under **Settings → Assistant**.
- **Assistant registration** (#252, part of #155) — the instance registers itself into the extension so no URL, collection id, or token is ever typed. **Settings → Assistant** mints a short-lived (5 min), single-use `AssistantRegistrationCode` (`src/lib/assistant-registration.ts`; SHA-256 hash-stored like a token, superseding the collection's previous code) and exposes a payload — `{ v, name, apiBaseUrl = the page's own origin, collectionId, collectionName, regCode, expiresAt }` — as JSON in a hidden `#stamporama-assistant-registration` element. The extension reads it on a toolbar-icon click (`activeTab`) and `POST`s the code to the session-less **`/api/assistant/register`**, which claims it atomically (conditional `updateMany` on `usedAt`/`expiresAt`) and returns a freshly minted `AssistantToken` plus the collection identity. The long-lived token therefore never appears in a URL, a fragment, or the page; possession of an unspent code is the whole authorization, and every rejection is the same generic 400. The extension writes the outcome back onto the payload element as `data-registration-state`/`-message`, which the page renders.
- **Stamporama Assistant extension** (`extension/`, #253; ADR-0015) — an isolated MV3 workspace package (esbuild + hand-written manifest, its own tsconfig; excluded from the app's lint/typecheck). A pluggable `PlatformModule` interface — with the Colnect list-page parser as the first module (`extension/src/platform/colnect/`, #249: `div.pl-it` cards → item-ID + "Catalog codes" refs kept verbatim, `Unlisted` skipped) — feeds extracted refs to a background-service-worker matching client that calls the endpoints above with the Assistant token (background fetch is CORS-exempt under host_permissions). The popup previews decisions (dry-run) and writes only behind a confirm that names the active profile. Two behaviour switches live in `chrome.storage.local` (`extension/src/core/settings.ts`), both default on and both read by the service worker so the load-time match, the window's preview, and every write agree: `matchOnLoad` and `catalogBackfill` (#280 — the window's **Fill missing catalog numbers** toggle, mirrored in Options; changing it drops the per-tab result cache and re-previews). **Connection profiles** (#251) hold the instances/collections it can talk to — `{ name, apiBaseUrl, collectionId, collectionName, token }` in `chrome.storage.local`, one active at a time, managed in Options and switchable from the Assistant window's header; the active one is shown in an always-visible badge coloured from its target (hashed instance+collection, de-collided), and switching drops results and per-tab caches belonging to the instance being left. A profile is normally created by **registering from the instance** (#252, above) rather than typed in: the icon click reads the page's payload, redeems the code, and stores the resulting token — updating in place when a profile for that instance+collection already exists, which is also how a revoked token is replaced.
- **Assistant packaging & distribution** (#288; ADR-0017, superseding ADR-0016) — the extension ships through an **unlisted Chrome Web Store listing**, because Chrome only force-installs from a non-store update URL on an enterprise-managed machine, which a hand-installed configuration profile does not produce. The store assigns the released ID and signs the package, so nothing is signed here and the instance serves nothing: `extension/archive.mjs` (deterministic ZIP writer, verified in `extension/archive.test.ts`) + `pack.mjs` write `dist-store/stamporama-assistant.zip` with the **app's** version stamped into the manifest, and CI's `publish-extension` job uploads and publishes it per `v*` tag against `chromewebstore.googleapis.com/v2` (secrets `CWS_CLIENT_ID`/`CWS_CLIENT_SECRET`/`CWS_REFRESH_TOKEN`, variables `CWS_PUBLISHER_ID`/`CWS_EXTENSION_ID`). Review is asynchronous, so a green job means submitted, not live; the first listing must be created by hand, since the API only updates an existing item. **Two build flavours are two extensions** (`extension/identity.mjs`): `build.mjs` (default → `dist/`, unpacked) stamps in a committed dev-only public key, a ` (dev)` name suffix and amber icons → ID `idmgaeimkafaifpfbjonmjdfbmgffcbh`; `build.mjs --release` (→ `dist-release/`) leaves the manifest bare for the store to identify. `manifest.json` itself carries no `key`. That is what lets a dev build and the store build coexist in one browser — Chrome refuses two extensions with one ID, and per-extension `chrome.storage.local` keeps a dev profile from ever reaching a production collection.
- `conditionId` → `StampCondition` and `certificateStatusId?` → `CertificateStatus` reference the per-collection configurable sets (Issues #93/#94), mirroring `StampCatalogPrice`.
- `formatId?` → `StampFormat` records the copy's **physical format** — a pair, a block, a strip (ADR-0020), a third per-collection dictionary alongside the two above and referenced from `StampCatalogPrice` the same way. **Null means single**, so no such row is seeded (as with `certificateStatusId`). A multiple is one copy in one format and is **never** decomposed into N singles — there is no unit count, and completeness treats format as a breakdown dimension beside condition rather than a factor on counts. This supersedes #135's "a multiple is its own `Stamp` with a self-descriptive number" for homogeneous multiples, which multiplied formats by variant-tree nodes and made "a pair whose variant is not yet identified" unrecordable; se-tenant combinations carrying their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) are genuinely distinct entries and remain their own `Stamp`.
- Disposition is three **independent booleans** — `inCollection`, `forSale`, `forTrade` — not a mutually-exclusive status. A copy can hold any combination.
- Acquisition & cost (ADR-0009, #118): a copy links to its acquisition via `lotId?` → `PurchaseLot` (`onDelete: Restrict`) — one channel among several, so nullable. Supplier, date, and price live on `Purchase`/`PurchaseLot`, not on `Item`; the flat fields from ADR-0007 (`contactId`, `acquiredDate`, `purchasePrice`, `purchaseCurrency`) were removed. `costBasis?` `Decimal(10,2)` is a base-currency snapshot (null = pending). `deliveryState` (`in_transit | delivered | not_delivered | damaged`, default `delivered`) is an independent physical-delivery axis. `notes` holds free-form per-copy detail. **No copy-level UI captures purchase data yet** — the purchase CRUD/intake screens land in #120+.
- Physical storage (#56): `locationId?` → `Location` (an assignable storage node) records where the copy is filed; `locationRef?` is a free-text identifier within that location (e.g. a page/pocket like `p.12`), per copy and **not unique**. Only `assignable = true` locations are valid targets, enforced server-side.
- `ItemVariantHistory` records in-place re-pointing of `stampId` when an unknown-variant copy is later identified (`fromStampId`, `toStampId`, `changedAt`, `note?`), giving a refinement trail without versioning the whole `Item`.

Referential actions: `collectionId` and `stampId` cascade; `conditionId`, `certificateStatusId`, `formatId`, `lotId`, and `locationId` restrict (mirrors `StampCatalogPrice`). Indexed on `collectionId`, `stampId`, `conditionId`, `formatId`, `lotId`, `locationId`.

Valuation of an unknown-variant copy (lowest child-variant catalog price, flagged uncertain) is shared domain logic and belongs out of UI components; it lands with a later child issue.

### Contacts (`Contact`)

`Contact` is a per-collection address book of everyone the collector deals with — sellers, buyers, exchange partners, auction houses, platforms (see [ADR-0008](../decisions/0008-contact-entity.md)). It is the supplier reference for purchases (ADR-0009) and the platform/sale reference for the sales layer (ADR-0012).

- `name` is **unique per collection**; `notes`, `fullName`, `email`, `phone` are optional.
- `fullName` (#463) is the **legal** name beside the filed-under one, and exists because a marketplace buyer is two different names: the login the collector recognises them by (and files them under) and the name the parcel has to carry. Folding both into `name` would either rename every buyer or lose the one that goes on the label. `searchContacts` reads both, so a buyer filed under `bronek_1980` is still found by typing their surname — a field that is only ever written is a field nobody keeps.
- Roles are six **independent booleans** — `buyer`, `seller`, `exchangePartner`, `auctionHouse`, `platform`, `other` — not an enum. A contact can hold several at once, mirroring the `Item` disposition flags.
- A contact may be created with **no roles set** (roles are filled in later).
- Platform-only fields: `platformCurrency?` (the fixed transaction currency inherited + locked by every offer/sale on the platform, #196), `titleTemplate?` (a free-text `{token}` template pre-filling offer + set titles for the platform, #210 — resolved by the pure `src/lib/offer-title-template.ts`; blank falls back to the derived label), `descriptionTemplate?` / `privateNoteTemplate?` (the same engine's multi-line form, pre-filling an offer's description #266 and seller-only private note #267; blank here means **generate nothing** — there is no built-in default, and it is also how a platform without private notes is configured), and `titleLanguage?` (the ISO 639-1 language the platform's generated text is written in, #293 — see *Per-language entity text* below).

- Seller-only fields: `defaultCurrency?`, `defaultShippingCost?`, `buyerPremiumPercent?`, `buyerPremiumFixed?` — the terms this seller normally trades on, **seeded** onto an `AuctionSale` at creation and edited there afterwards (#350, ADR-0021; see *Auction tracking* below). Shown in the contact form under either buying-from role, since an auction house is a seller that happens to run sales.
- `ShippingMethod` (#468) — the platform's own postage price list, `platformId` → `Contact` (`onDelete: Cascade`, a method belongs to its platform) plus `collectionId` for scoping, `name` + `cost` `Decimal(10,2)` + `currency`, `@@unique([platformId, name])`. A dictionary in the sense `StampCondition` / `CertificateStatus` are, hung off the **platform** rather than the collection because postage is quoted by the marketplace the parcel sold on. `cost` is the *current* price, read when a method is picked on a sale and copied onto that sale from there; nothing recalculates a sale already recorded. Managed from the contact dialog's Platform tab (its own dialog, writing as it goes — the rows are records, not fields of the contact). An optional `carrierId?` → `Carrier` (`onDelete: Restrict`, #491) names who *usually* moves a parcel sent this way — a **default seeded into the sale**, never the fact: a marketplace sells a service ("Courier"), and which courier it goes with is settled at the parcel counter days later.
- `Carrier` (#491) — the collection's own list of post offices and couriers: `collectionId`, `name`, `trackingUrlTemplate?`, `@@unique([collectionId, name])`. Deliberately **collection-scoped where `ShippingMethod` is platform-scoped**, and that asymmetry is the reason it is a separate table: postage is *priced* by the marketplace, but the same Poczta Polska carries an Allegro parcel and a Delcampe one and tracks both at the same address, so a template kept per platform would be one line typed per marketplace and stale in all but one. The template carries a `{code}` token, validated on save by the pure `src/lib/tracking-rules.ts` (`parseTrackingUrlTemplate` — absolute http(s) and the token present, since a template without it builds the same link for every parcel); `buildTrackingUrl` substitutes the percent-encoded code on read. Managed under **Settings → Shipping** (`carriers-panel.tsx`, domain `src/lib/carriers.ts`). Referenced from two places, and the pair is the design: `ShippingMethod.carrierId` is the *default*, `Sale.carrierId` is what carried that parcel, and `getSaleDetail` resolves `sale.carrier ?? sale.shippingMethod.carrier` into one effective `carrierId` / `carrierName` / `trackingUrl` so three screens cannot spell the fallback three ways.
- `collectionId` cascades. Foreign keys pointing *at* a contact (from `Purchase`, from `Offer` / `Sale`, and from `AuctionSale` as seller and as platform) use `onDelete: Restrict` so a referenced contact cannot be deleted without first detaching it.
- Domain module `src/lib/contacts.ts` (server-only) exposes `listContacts` / `searchContacts` / `createContact`, all collection-owner-authorized. `resolvePurchaseContact` is the find-or-create every picker writes through, matching on `name` case-insensitively — which is why the Allegro sale flow files a buyer under their login (#463): it is the name the match will be made on next time.

### Per-language entity text

Different marketplaces list in different languages, so entity text used in generated titles is stored per language (design in #265, foundation in #293).

- Each translatable entity gets **its own child table**, primary key `(parent, language)`, FK `onDelete: Cascade`. A generic `(entityType, entityId, field, value)` table was rejected: it cannot carry FKs across several parents, and every new entity needs a migration either way. Seven exist: `CollectionAreaTranslation(collectionAreaId, language, titleName?)` (#293), `StampConditionTranslation`, `CertificateStatusTranslation` and `StampFormatTranslation` (`(parent, language, name?, abbreviation?)`, #294/#344), `IssueTranslation`, `StampTranslation` and `StampSubtypeTranslation` (`(parent, language, name?)`, #295/#296/#338).
- A translation's fields fall back **independently**: a null column means "use the entity's default-language value for *this* field", so a Polish condition can translate `Mint Never Hinged` and keep `MNH`. A row is written when any field is non-blank and deleted once all of them are blank, so "cleared" and "never set" are one state.
- The shared rules — parsing the form's `<field>:<lang>` inputs, deciding upsert-vs-delete, collapsing rows into `<field>ByLanguage` read models, and resolving a field for a language — live once in the pure `src/lib/translations.ts` (`parseTranslationValues` / `syncEntityTranslations` / `translationsByLanguage` / `resolveTranslation`). Each domain module supplies only its own Prisma delegate. Entity write inputs take a `translations` map; languages absent from it are left untouched, so a form rendering only the languages currently in use cannot drop a translation for a language temporarily removed from the platform list.
- The entity's existing single-language column (`CollectionArea.titleName`, …) stays the **default-language** value. Translation rows are purely additive — nothing is backfilled or moved.
- `language` is a free ISO 639-1 code (`src/lib/languages.ts` normalises it and supplies the picker list). `Collection.defaultLanguage` (NOT NULL, `@default("en")` — existing collections were backfilled to `en` by the column default) records which language the entity's own columns are written in; it is edited in Settings → General. The set of languages needing translation is **derived** as the distinct `Contact.titleLanguage` over the collection's platforms **minus** `defaultLanguage` — there is no separate language-configuration screen, and a platform listing in the default language resolves straight to the default columns with no rows at all.
- UI: entity forms keep **one** default-language input per field (labelled with `defaultLanguage` once any translation language exists) and open the shared `TranslationsDialog` (`src/app/c/[collectionSlug]/shared/translations-dialog.tsx`) from a globe icon button beside it, badged with the number of languages still falling back, so a form does not grow a field per language. `TranslationsField` (`…/shared/translations-field.tsx`) packages the button, the badge and the hidden `<field>:<lang>` inputs, so the seven entity forms share one implementation. An entity with **several** translatable fields gives **each** its own button and its own single-field dialog rather than one dialog listing both: a badge then refers to exactly one field, and translating names never means scrolling past abbreviations left deliberately untranslated. The dialog fixes its panel height so the language grid scrolls internally rather than stretching, and portals to `document.body`, since it opens from inside another dialog's transformed panel. Its confirm button is **Done**, not Save: it stages values back into the entity form on the existing save path, leaving the entity's own dialog as the single logical save. Persisting from the nested dialog is not an option anyway — a not-yet-created entity has no id to attach rows to.
- Server-rendered screens (Settings, Areas) get the language set from their page loader. The issue and stamp dialogs cannot — they open from six client call sites — so they read it through `useTitleLanguages` (`…/shared/use-title-languages.ts`), a cached TanStack query over `getCollectionTranslationContext`. Stamp translations are likewise fetched by `stampId` inside the dialog, next to the subtype assignment and the photos, so no caller's row shape has to carry them.
- Resolution runs off the platform's `titleLanguage`, threaded through `makeTitleCopyMapper` (`src/lib/title-copy.ts`). `{area}` resolves in `buildAreaTitleMap` (`src/lib/area-vendor.ts`) with a **per-node** fallback: each area on the roll-up chain resolves its translation, then its default `titleName`, then its own `name` — the roll-up decides which area names the title, the language only how it is spelled. The other tokens resolve in `toTitleCopy`, which selects each entity's translation rows unfiltered (a handful per entity) and picks the language there, rather than parameterising the shared static `TITLE_COPY_SELECT`. Missing translations fall back silently in the stored title, and are **reported** alongside it (#298): `resolveTranslationWithFallback` / `buildAreaTitleEntries` say whether each field came from a translation, `toTitleCopy` collects the ones that did not into the copy's `fallbacks`, and the pure engine turns that into `renderTitleTemplateSegments` (the title split into flagged runs, using control-char sentinels so `tidy` still runs on the whole string and segments can never disagree with `renderTitleTemplate`) plus `titleFallbackTokens` (the token names, for the preview's summary line). `makeTitleCopyMapper` normalises a language equal to `Collection.defaultLanguage` to null, so a platform listing in the default language resolves the same and flags nothing.
- The language is **per generation, not per offer** (#297): the Add-set dialog and the offer header's ⋮ menu pass an optional override into `addOfferSet` / `addOfferSetsPerCopy` / `regenerateOfferText`, defaulting to the platform's `titleLanguage`. Nothing about the choice is persisted — only the title it produced, which stays editable (#209). The dialog previews it through `previewOfferTitle` (a read-only twin of `generateConfiguredTitle` sharing its `titleCopies` load path, so the preview and the stored title cannot drift); both preview surfaces render through `TitlePreviewText` / `TitleFallbackNote` (`…/shared/title-preview.tsx`).
- A reported fallback also names the **entity row that would fix it** (#299), so a gap can be filled where it is seen. A copy's `fallbacks` are `TitleFallback`s — `{ field, entityType, entityId, entityField, defaultValue }` — the copy field the token renders from *plus* the entity's own translation column, which differ because one copy flattens six entities (`{conditionAbbr}` is the condition's `abbreviation`, and `{area}` is a `titleName` on whichever ancestor won the roll-up, hence `AreaTitleEntry.sourceAreaId`). `templateFallbacks` / `titleFallbacks` / `listingFallbacks` walk the same placeholders as their `*FallbackTokens` twins and return those entries deduped per entity row, so **a gap offered for filling and a token flagged in the preview are the same thing seen from two ends**: a translatable field no template renders is not a gap. `TitleSegment` carries the `field` of a flagged run (the sentinel wraps `field` + value), which is what lets a click on the run open the right editor (#300).
- Filling one is a **standalone entity write**, not part of the offer: `saveEntityTranslation` (`src/lib/entity-translations.ts`) writes one field of one language, checking the owner *and* that the entity really belongs to the collection, refusing the collection's own default language and any field the entity does not have, and reading a multi-field entity's stored siblings back so filling a name cannot clear an abbreviation. It reuses `syncEntityTranslations`, so a gap filled from an offer dialog and one filled in the entity's own dialog store exactly the same thing (including the all-blank-deletes rule). The six per-entity delegates live in that one module rather than as a setter per domain module, since the paths differ only in which table they resolve and upsert. UI: `TranslationGapsPanel` / `TranslationGapPopover` (`…/shared/translation-gaps.tsx`) — one row per gap, saved on Enter/blur — under the compose dialog's preview and, over the offer's whole composition and all three templates in the platform's own language, on the offer detail screen (`useOfferTranslationGaps`). The compose dialog re-runs its preview after a save; the detail screen does **not** rewrite the stored texts, which may have been edited by hand, leaving that to each field's ↻.

#### Listing texts (#266/#267)

- The same pure engine renders an offer's **description** and **private note**, in a multi-line mode. Rendering scope is grouped by set — `TemplateSet = { title, copies }` — so a template can enumerate a listing: `{#set}…{/set}` repeats its body once per set and `{#copy}…{/copy}` once per copy (of the enclosing set, or of the whole offer at the top level), with tokens inside a block narrowed to that iteration. `renderTitleTemplate` / `…Segments` keep their flat-copies signature by wrapping the copies as one anonymous set, so #210 is unchanged. Unbalanced block tags stay literal, like an unknown token.
- **Legend blocks** (#318) reuse the same mechanism over a different axis: `{#conditionLegend}…{/conditionLegend}` / `{#certificateLegend}…{/certificateLegend}` — named `…Legend`, not after the dictionary, so the tag cannot be misread as the `{condition}` token it wraps — iterate the **distinct dictionary entries** the copies in scope use — keyed on the (name, abbreviation) pair, first-seen order, copies recording neither skipped — narrowing the scope to the copies carrying each entry (`legendScopes`). So `{conditionAbbr} = {condition}` inside the block names that one entry while `{catalog}` names what it applies to, and the entry's format stays the collector's to write rather than a hard-coded `ABBR = Name`. `=` joined the tidy pass's glue separators so a dictionary row without an abbreviation renders its name alone.
- **The unknown-variant caveat (#619)** is the engine's one *conditional* block plus two value tokens. `{#unknownVariant}…{/unknownVariant}` renders its body **once**, narrowed (as `legendScopes` narrows) to the copies in scope whose stamp is an unknown-variant umbrella, and not at all when there are none — which at description level is one caveat for the listing and inside `{#copy}` a per-copy one, from a single rule. `{listedAs}` names the variant the listing resolved to and `{variants}` the umbrella's **direct** variant children, both arriving on `TitleTemplateCopy` as strings the caller already prefixed and collapsed, so the engine still knows nothing about the rollup. All three are **listing-text only**: `TemplateScope.listingText` (set from `renderSegments`' `multiline`) blanks the tokens and skips the block in a title, since their value rides on the copy rather than on a context and a range in a title would read as a span the listing holds. `unknownVariant` / `variants` are resolved in `toTitleCopy` off one `variants` relation on `TITLE_COPY_SELECT` — ordered by `primaryCatalogSortKey` + id in the mapper, because the text is stored and a database order would rewrite it on a re-read — through `catalogLabel` and `compactCatalogNumbers`, at the **umbrella's** own area and issue so the range collapses under one prefix. `listedAs` is folded on in `templateSets` from `listedAsByItem`, which reads #616's `resolveListingCatalogItemIds` and only when `templateUsesListedAs` says a template asks *and* `usesPlatformCatalogue` says the platform lists against one (#493) — the `{offerUrl}` guard pattern, keeping a valuation pass off every ordinary render.
- Multi-line tidying runs **per line**: a line whose placeholders all resolved empty is dropped whole (no bare `Condition:` left behind), a line with no placeholders — including a blank paragraph separator — is kept, and leading indentation survives. A `VALUE_MARK` control character alongside the existing `EMPTY_MARK` is what distinguishes the two cases. The same pass also fixed a long-standing title wart: an empty token flanked by separators used to eat **both**, and `:` / `;` were not treated as glue at all.
- `src/lib/offers.ts` generates all three texts in one copy load (`generateListingTexts`) at create and duplicate, and regenerates **one** field at a time (`regenerateOfferText`) over the offer's present composition (`offerComposition`), so a hand-edited title survives regenerating the description. `OfferDetail.regeneratable` reports which fields the platform has a template for, which is what the per-field ↻ enables itself on.
- **Length limits (#403).** `Contact.maxDescriptionLength` / `maxPrivateNoteLength` — nullable `Int`s beside the photo limits, and the same *kind* of fact: a hard technical cap on what the platform's form physically accepts (Colnect takes 100 characters for each, #402). Two columns because platforms cap the two texts independently. **Read live, never seeded** (the photo-limit rule, #310), surfaced on `OfferDetail.platformTextLimits`, and **never enforced**: nothing truncates, and an over-long text does not block Ready or publication — the app reports, the wording stays the collector's. Parsing and counting are pure in `src/lib/listing-text-limits.ts` (`parsePlatformTextLimits`, `textLengthState`), counted in **UTF-16 code units** because that is what an HTML `maxlength` enforces and the platform's own field is the authority on its own number. `TextLengthCounter` (`…/shared/text-length-counter.tsx`) renders **nothing** when the platform states no limit, so both surfaces that show a listing text — the offer's own card and the bulk listing kit (#322) — call it unconditionally; the offer card passes the **draft** while a field is open and the stored source otherwise, since the source is what the copy control puts on the clipboard.
- UI: the platform's three templates share **one** dialog off the contact form — `ListingTemplatesDialog` (`…/contacts/listing-templates-dialog.tsx`): a fixed-size panel (`DialogShell height`) scrolling internally, with the shared `TemplateSamplePicker` pinned above the body and the three `TemplateBuilder` sections stacked inside it — each collapsible to a one-line summary row — and one save. Sample copies load once per dialog (two of them, so a `{#set}` block visibly repeats), so all three previews describe the same stamps. `TemplateBuilder` / `TemplateSamplePicker` / `TemplateSyntaxLegend` / `useTemplateSamples` live in `…/shared/template-builder.tsx`, replacing the old single-template `TemplateBuilderDialog`. The offer's own texts live in `OfferListingText` (`…/offers/[offerId]/offer-listing-text.tsx`) below the header card, collapsed to one row while both are empty.

### Purchases (`Purchase` / `PurchaseLot` / `PurchaseExpense`)

The purchase model (see [ADR-0009](../decisions/0009-purchase-record-model.md), schema in #118) is the channel-agnostic source of cost-basis. **CRUD is live** (#120): the pure allocation engine landed in #119, and lot close / item intake follow in #121+.

- `Purchase` — transaction header: optional `contactId?` → `Contact` supplier and optional `platformId?` → `Contact` platform (the marketplace/intermediary, e.g. Allegro — a contact with the `platform` role; both FKs `onDelete: Restrict`), `purchasedAt` (date), a single `currency`, `fxRateToBase?` frozen at `purchasedAt` (`Decimal(65,30)`, reuses the `ExchangeRate` mechanism), `shippingCost?` `Decimal(10,2)` (shared cost), and a delivery `status` (`preparing | in_transit | arrived`). Scoped to `Collection` (`onDelete: Cascade`).
- `PurchaseLot` — inventory line: `price` `Decimal(10,2)`, intake `status` (`open | closed`), and the `Item`s it resolves into. `onDelete: Cascade` from `Purchase`.
- `PurchaseExpense` — non-inventory line (e.g. a magnifier): `label` + `price` `Decimal(10,2)`, no lifecycle and no items. `onDelete: Cascade` from `Purchase`.
- Statuses are `String` columns (the schema uses no native Postgres enums), with allowed values documented in the schema and enforced by the domain layer.
- Domain module `src/lib/purchases.ts` (server-only) exposes `listPurchasesPaginated` / `getPurchase` / `createPurchase` / `updatePurchase` / `deletePurchase`, all collection-owner-authorized. Create/update persist the **header only** (supplier, platform, date, currency, delivery status, and the shared shipping cost) and freeze `fxRateToBase` (best-effort) via the `ExchangeRate` mechanism. The supplier and platform fields each submit both a picked contact id and the typed name; `resolvePurchaseContact` (in `contacts.ts`) resolves them on save — a valid in-collection id wins, else an existing contact is matched by name (case-insensitive) and reused, else a new contact is created carrying the field's role (`seller` for suppliers, `platform` for platforms). The pickers filter suggestions to that role via the `?role=` param on the #107 contact search. **The order's line items are intentionally not written by #120** — both inventory lots and non-inventory expenses are added during lot intake (#121), so `createPurchase`/`updatePurchase` never touch them; the read/list side still surfaces lot and expense counts and rolls them into the total. The `Purchases` screen (`src/app/c/[collectionSlug]/purchases/`) is a URL-state, card-row infinite-scroll list with a dialog-shell header add/edit form; the paginated list is served by `GET /api/collections/[collectionId]/purchases` and mutations go through server actions in `src/app/actions/purchases.ts`.

### Auction tracking (`AuctionSale` / `AuctionLot` / `AuctionLotLine`)

Auction tracking (see [ADR-0021](../decisions/0021-auction-tracking-model.md), design in #23, schema in #350) is a **bidding watchlist with a fork at the end**, not a register of market results fed from outside: lots the collector is bidding on, whose outcome falls out of the money once they close. A closed lot's final price is the price signal #24 consumes — a by-product of the workflow rather than a corpus somebody has to populate. **Schema and seller defaults** (#350), **the screens** (#351/#352) and **composition + catalogue value** (#353) so far; settlement lands in #28.

- `AuctionSale` — **one settlement with one seller**, i.e. what ships in one parcel, deliberately not "an auction as an event". For a house it coincides with the house's own sale (`Köhler 385`); on a marketplace it is an open-ended basket of everything currently being bid on with one seller. That is what makes shipping distribution fall out of ADR-0009 §3 for free — the grouping is made at bidding time, so settlement never asks "which purchase does this go into?". `sellerId` + `platformId` → `Contact` (both `onDelete: Restrict`), mirroring `Purchase`: a house selling directly is the same contact in both, a house listing through philasearch is seller = house, platform = philasearch. `name` (the house's sale identifier lives here — there is no sale-number column), `url?`, `endsAt?` (a **default for new lots**, never the sale's own date), `currency`, `shippingCost?` / `premiumPercent?` `Decimal(5,2)` / `premiumFixed?`, `status` = `open | settled | closed`, and `purchaseId?` (unique, `onDelete: SetNull`) set on settlement. Scoped to `Collection` (`onDelete: Cascade`).
- `AuctionLot` — one thing being bid on: `lotNo?`, `url?`, `title?`, its **own** `endsAt` (on a marketplace every lot closes at a different moment), `currentBid?` + `checkedAt?`, `maxBid?`, `myBid?`, `finalPrice?`, `status` = `open | closed | cancelled`, `wonTie?`, `purchaseLotId?` (unique, `onDelete: SetNull`), `notes?`. `onDelete: Cascade` from `AuctionSale`. Outcome lives **on the lot, never on the sale** — within one settlement some lots are won and others lost, which is the ordinary case. It is also **derived, never stored** (ADR-0021 §4): `status` is the lifecycle the collector records, and `lotOutcome` reads `pending | won | lost | observed | cancelled` off `myBid` against `finalPrice` — winning pays under your own maximum, being outbid puts the result above it. That retires a whole class of bug (a lot filed `won` whose figures said otherwise) and gives *observed* — a lot tracked purely to record what it fetched, with no bid ever placed — a home it never had. `wonTie` is the one thing the money cannot say and so the one thing stored: at equal figures bid order decided it, and nothing else records that. The bid is a single overwritten figure, **not a history**: refreshing is manual (no scraping, no scheduled polling), so `checkedAt` answers the only question a history would. Filtering is by outcome, restated as SQL predicates in `outcomeWhere`.
- `AuctionLotLine` — composition as `stampId` × `conditionId` × `certificateStatusId?` × `formatId?` × `quantity` (all four FKs `Restrict`; `onDelete: Cascade` from the lot), which is exactly the shape a `StampCatalogPrice` is keyed on. The certificate arrived with #353 (nullable, null = none as on `Item`, so nothing needed backfilling): a house lot sold with a Fotoattest is worth a different figure, and matching is strict, so a line naming one is unpriced until a price exists at that level. Structured, never free text: that is what makes catalogue value computable before the close and a closed lot usable afterwards. **No new pricing machinery** — an unknown-variant umbrella rolls up from the cheapest child exactly as the issue list does (#238), and `formatId` prices multiples through `StampFormatFactor` (ADR-0020, null = single).
- Valuing that composition (#353) lives in `src/lib/auction-lines.ts`, and reuses the **copy** valuation literally: `valuateItemRows` (exported from `items.ts`) values a `stamp × condition × certificate × format` row, of which a copy is one instance and a lot line another at a **null certificate** — a lot is described before it is owned. It is called **once per page of lots**, so `makeFormatFactorLookup` and the area tree load once rather than per row. Value pivots **base currency → the sale's**, converted once per sale currency, because the bid, premium and ceiling are all denominated there; a missing rate makes a line **unconvertible**, a state deliberately distinct from *unpriced* (it has a value that cannot be counted, and calling it unpriced would send the collector to enter a figure that already exists). A composition entered but unpriced values at `null`, never `0.00` — a zero would make every headroom read as a catastrophic overbid — and unpriced/unconvertible lines are counted beside the total rather than dropped. The pure roll-up is `summarizeLotComposition` in `auction-lot.ts`; quantity multiplies and nothing else does, since a multiple is never decomposed (ADR-0020). Read through `GET /api/collections/[collectionId]/auctions/lots/[lotId]/lines`, written by server actions. A lot with no `title` takes a **derived name** from its lines (`deriveAuctionLotLabel`) — prefix-formatted catalogue numbers collapsed into spans (`buildAreaVendorMaps` + `formatStampCN` over `readCollectionAreas`), plus the shared issue — computed on every read beside the valuation and never stored, since it is read only on our own screens. Entry offers a **whole-checklist** pick alongside a single stamp (#531; ADR-0031), expanded in the action layer by `resolveAuctionLineStamps` into one line per stamp on it — the purchase intake's rule (`lots.ts`), reused rather than restated. Written from three surfaces — the sale detail's cards, the watchlist dialog, and `createAuctionLot` itself, which takes `lines` and writes lot + composition in one nested create with every line validated first. Reading: the **sale detail** draws each lot as a collapsible card over its lines (the PO-intake / offer-detail layout — shared `LotIssueGroupHeader`, `lot-view-prefs` toolbar, `sortSortableCopies`), and only that read carries them (`AuctionLotDetailItem`); the **flat watchlist** opens the same list in a dialog, its rows carrying the total alone.
- `Contact` seller defaults — `defaultCurrency?`, `defaultShippingCost?`, `buyerPremiumPercent?` `Decimal(5,2)`, `buyerPremiumFixed?`, all optional and **seeded** onto a sale at creation, never read live: the same rule as seeding listing templates and photo configuration from a platform onto an offer (#308, #319), so changing a seller's terms cannot re-price a sale already tracked or settled. Currency belongs to the **seller** — philasearch aggregates houses listing in EUR, CHF and GBP, so `platformCurrency` (#196) does not apply. Edited in the contact form under the seller / auction-house roles.
- Arithmetic is pure in `src/lib/auction-lot.ts` (no Prisma, unit-tested, mirroring `offer-summary.ts`): `allIn(bid, fees)` = `bid + bid × premiumPercent / 100 + premiumFixed + shippingCost`, `headroom(catalogValue, bid, fees)`, and `summarizeAuctionSale` over a sale's lots. Comparing catalogue value against the hammer price alone systematically overpays on cheap lots, where shipping and a fixed lot fee are a large share of the total. The rollup counts only **payable** lots (derived `pending` / `won`) and adds shipping **once** for the parcel — which is only expressible because the sale is one settlement.
- **Market valuation** (see [ADR-0022](../decisions/0022-market-valuation-from-auction-results.md), design in #24) is what a closed lot's price is *for*, and it is the third pure module here: `src/lib/market-value.ts` (#455) extracts one **datapoint** per line of every `closed` lot carrying a `finalPrice` — `finalPrice × fxRateToBase` at the rate frozen at `endsAt` (#354), **excluding** premium and shipping, which are the seller's terms rather than the stamp's worth. The derived outcome is not consulted: `won`, `lost` and `observed` are all real prices, and a lot added purely to watch what it fetches is the case ADR-0021 §4 exists for. A single-line lot is `amount ÷ quantity` and needs no catalogue price; a mixed lot is split **pro-rata by each line's total catalogue value** and skipped *whole* if any line has none, since a partial split hands the missing line's share to its neighbours. A foreign-currency lot with no frozen rate yields nothing — `fxRateToBase` is null both when no conversion was needed and when none could be had, so the pure input carries an explicit `inBaseCurrency` flag beside the rate. Datapoints group on `stamp × condition × certificate × format` — the `StampCatalogPrice` key minus the **edition** axis, since a hammer price belongs to a date and not to a published book — and aggregate over **all** of them with no minimum sample and no time window, because a self-built base cannot afford a threshold that discards most of what has been recorded. The headline is the **median**; thin and stale evidence is answered by a 0–100 **confidence score** (sample · recency · agreement · purity, bucketed `low` / `medium` / `high`), which is only ever shown next to the facts that produced it and which no rule keys off. `realizationRatio` is `median ÷ catalogueValue` in base currency, and a key with no datapoints shows **no** market value — nothing is synthesized from comparable keys' ratios. The server half is `src/lib/market-values.ts` + `GET /api/collections/[collectionId]/stamps/market-value?stampId=…` (#456): **computed on demand, nothing stored** (§7 — no table, no queued recompute, no invalidation edges, so editing a lot's price changes the next screen that asks), one query for the closed lots *mentioning* the asked-about stamps and then **all** of those lots' lines — the ones pointing elsewhere are what the split weighs against — with catalogue values resolved by `valuateItemRows` so the unknown-variant rollup (#238) and format pricing (ADR-0020) are reused rather than re-derived. The UI (#457) and collection totals (#458) come later.
- Bid recommendations (see [ADR-0029](../decisions/0029-bid-recommendations.md), design in #25) are being built beside that arithmetic, not inside it: `src/lib/bid-recommendation.ts` (#509) is a second pure module taking **already resolved** lines — one `anchor` per `AuctionLotLine`, in the sale's currency, with the `market | catalogue` source that produced it — and returning the three figures ADR-0029 §3 states: `fair` = Σ `anchor × quantity` (**null when no line is anchored**, since an unpriceable lot is unanswered rather than worthless), `floor` and `walkAway` as percentages of it, each also carrying the hammer price that fits inside it through the existing `maxBidWithin` on the sale's **per-lot** fees (shipping stripped, as everywhere a single lot is costed). Unanchored and unconvertible lines are counted and reported, never summed as zero — the same distinction `summarizeLotComposition` already draws. No series premium and no bulk discount (§6). The percentages are collection settings (#508): `Collection.bidFloorPercent` / `bidCeilingPercent` (75 / 125) are the collector's own trading band, and `bidFallbackPercent` (100) is what a catalogue value is anchored at **only** while nothing has been learned. What fraction of catalogue a stamp actually fetches is deliberately **not** a setting — it is learned per area × condition × period from recorded results (#520, §2), because a single configured percentage is a market opinion stated once and wrong nearly everywhere. What reads all of it is the lots screen (#511, §8), through `src/lib/bid-recommendations.ts` — the domain half — split the way the composition already is: the **three figures ride on the lot read** (`AuctionLotListItem.recommendation`, resolved for a whole page over the compositions `compositionsFor` has already valued, which is why `resolveAuctionLotAnchors` accepts them rather than valuing the page twice), while the **per-line evidence is fetched only while the popover is open** (`GET …/auctions/lots/[lotId]/recommendation`). The figures have to be on the row because `fair` is drawn there as a **column of the *worth* section** beside catalogue value — two answers to "what is this worth", against the same `value` / `headroom` labels — and because `REC` is a quick fill that must know what it would write before it is clicked; the evidence must not be, or a forty-lot watchlist fetches forty lots' market medians to draw forty collapsed rows. That recommendation cell is itself the popover's trigger, as the catalogue cell is the way in to the composition editor, and every level inside the panel writes itself into the ceiling (all three are in the `⋮` menu too; the row's `REC` stays on `fair`) — §8 revised, since refusing the floor and walk-away outright made the one judgement the feature exists to support the one thing it would not help with. The page-wide resolve is **best-effort**, like `attachBaseRates`: a failed market read leaves the rows without a recommendation rather than failing the list. Nothing is stored, here or below it (§10) — a lot recommended differently a month later is the price base having learned something, not a cache going stale.
- Settlement (#28) is a **1:1 transcription**: `AuctionSale` → `Purchase`, each lot deriving to `won` → `PurchaseLot` at hammer + premium, everything else skipped, shipping then distributed by ADR-0009 §3. The `SetNull` links mean deleting the purchase leaves the bidding record standing, because that record is a datapoint in its own right.

### Sales (`Lot` / `Offer` / `Sale` / `SaleLine` / `SaleLineItem`)

The sales model (see [ADR-0012](../decisions/0012-sales-record-model.md), schema in #162) is the mirror image of purchases and the consumer of `Item.costBasis`. **Schema, the pure P/L allocation engine, lot composition, and per-platform offers so far** (#162/#163/#164/#165) — the sale flow lands in #166+. It has two orthogonal axes, symmetric to purchases: the platform-agnostic **package** (`Lot`) and the per-platform **listing** (`Offer`); the `Item` is the thread tying platforms together. Lot composition + lifecycle live in the pure rules module `src/lib/sale-lot-rules.ts` (kind invariants, derived sale status, sub-lot cycle guard; unit-tested in `tests/unit/sale-lot-rules.test.ts`) and the server domain module `src/lib/sale-lots.ts`; the **Lots** screen (`src/app/c/[collectionSlug]/lots/`) drives compose → ready → dissolve.

Offers (#165) are the per-platform listing layer. The pure offer state machine + validation live in `src/lib/offer-rules.ts` (`preparing → ready → active ↔ paused → sold/withdrawn`, linear but reversible; `sold` reachable only via a sale; unit-tested in `tests/unit/offer-rules.test.ts`); the server domain module `src/lib/offers.ts` owns CRUD, the paginated list (platform/state/lot filters), the eligible-lot picker, and the collision lookup. The **at most one active offer per (`Item` × platform)** rule is a **non-blocking live warning** in the offer dialog (a lookup over active offers on the platform sharing a copy with the lot), not a hard guard — deeper coordination is #167. Offers are managed from the **Offers** screen (`src/app/c/[collectionSlug]/offers/`) and from a lot's detail **Offers** section; the paginated list is served by `GET /api/collections/[collectionId]/offers` (with `offers/collision`, `offers/eligible-lots`, `offers/platforms` helpers) and mutations go through server actions in `src/app/actions/offers.ts`.

- `Lot` — a **recursive** sale package scoped to `Collection` (`onDelete: Cascade`). `kind` = `unit` (the atomic sellable unit — a single stamp or an indivisible *komplet* — holding `Item`s directly via `lot_item`, an **`Item` N:M `Lot`** join so a copy can be packaged differently per platform) or `quantity` (groups N interchangeable sub-lots via the `lot_sub_lot` self N:M relation, holding no items directly). Lifecycle `state` = `draft | ready | dissolved`; `sold` / `partially-sold` are **derived**, never stored. The kind invariants are domain guards, not DB constraints.
- `Offer` — a `Lot` listed on one platform (`Lot` 1:N `Offer`): `platformId` → `Contact` with the `platform` role (`onDelete: Restrict`), an editable `name?` (the listing title, #209 — generated from the platform's `titleTemplate` over the offer's copies, null falls back to the derived label), editable `description?` / `privateNote?` (the long listing text and the seller-only note, #266/#267 — generated from the platform's own templates over the offer's **sets**, null when it has none), each regenerated on demand and independently via `regenerateOfferText(ownerId, offerId, field, language?)`, `url?`, `price` `Decimal(10,2)` + `currency` (per-offer, platforms price independently), `state` = `preparing | ready | active | paused | sold | withdrawn` (+ a derived "needs action" flag; sold/withdrawn hidden from the list by default, #245). `onDelete: Cascade` from both `Collection` and `Lot`.
  - **How it is sold** (#449): `listingType` = `fixed` (default) | `auction`, a fact about *this* listing rather than about the platform — a marketplace running both formats carries offers of either kind. `price` keeps its column and gains a second reading: the asking price of a quick buy, the **current** figure of an auction. Deliberately not split into `startingPrice` + `currentPrice`, because everything downstream — the list rows, the base-currency conversion (#208), the suggested-price comparison (#190), the ready/active price gate (#336), the listing kit (#405) and the sale — wants the live number, and a second column claiming the same fact is how the two drift. The auction adds `startingPrice?` (what it opened at) and `priceCheckedAt?` (the auction lot's `checkedAt`, #351 — an undated figure says nothing about how current it is), plus `bidderCount?` (#481). Refreshing a bid is manual on everything not connected (ADR-0021 §8) and **automatic on a connected selling platform**, where the marketplace's own feed states both (ADR-0024 §8a): `bidderCount` is written by that sync and by nothing else, which is what makes it the provenance of the figure beside it. All of it is resolved in one place, `resolveOfferPricing` in `offers.ts`, shared by `createOffer` / `duplicateOffer` / `updateOffer`: a quick buy clears the auction pair, an auction is dated only when the figure actually **moved** (a header save that retypes the same number is not an observation), and `patchOffer` refuses a `startingPrice` on a quick buy — changing format is the header form's job, not a field appearing beside the price.
  - **Which figure is required** is the format's own question, and the two are **alternatives, not a pair**. Going `ready` / `active` needs an asking price (#336); on an auction it needs the **starting** price *instead* (`pricingReadyFor`, `requiresStartingPrice`), because that is the number the seller states, while the current one is an *observation* of the bidding — and an auction that is up with nobody bidding has none to make. So nothing is ever invented for `price`: an unbid auction carries `0`, renders as **No bids yet** rather than *No price yet*, and the two figures move independently (correcting the opening price never touches a recorded bid; `patchOffer` refuses to clear a live auction's *starting* price and freely clears its current one). `missingPriceField` in `offers.ts` is the single server-side rule behind every refusal, returning which field is missing so each call site can name it; `pricingReadyFor` is the same rule for both quick-advance buttons, so an offered button is a transition the server will take.
  - **The platform's own defaults** are two columns written together in `contacts.ts` (`platformListingDefaults`), because the price is meaningless without the format: `Contact.defaultListingType` (nullable, null = no preference) and `Contact.defaultStartingPrice` — `defaultOfferPrice` renamed, narrowed to auctions and **kept only while the type is `auction`** (#449 over #362). Both follow the same rule: read at creation, then owned by the offer. There is deliberately no default price for a quick buy — its price follows from the goods, which the lot's suggested price (#190) and the copies' catalog value (#230) already answer — so the contact form hides the field unless the type is Auction, the writers clear the column otherwise, and the migration renamed it and cleared every existing value (every platform predating `defaultListingType` reads as a quick buy). They reach `createOffer` / `duplicateOffer` through `assertPlatform` and the new-offer dialog through `listOfferPlatforms` + the contact picker, whose platform facts now travel as one `PlatformOfferDefaults` object rather than a growing tail of positional callback arguments; the dialog fills the **starting-price** field from the default — the field a *suggested* price (a lot's, the copies' catalog value, the source offer's) fills too, that being what one would ask for the goods and so, on an auction, what one would open at; the current price is left empty either way, since a suggestion is not a bid. Between the two the platform's default **wins on an auction** (#553, `platformOpensAuction` in `offer-form-dialog.tsx`): an auction is opened deliberately below what the goods are worth, so a house that always opens at the same figure outranks a suggestion describing the goods — the reverse of the quick-buy order, which #362 leaves untouched, and it yields to a figure the collector has typed themselves. `resolveOfferPricing` needs no change for it: the dialog submits the default, and the server's own fallback still applies when nothing is submitted. An **edit** passes no platform defaults — switching platforms must not re-describe a listing that already exists.
  - Vocabulary, the price's own label and every one of those rules are pure in `offer-rules.ts` (`normalizeListingType`, `priceLabel`, `requiresStartingPrice`, `resolveCurrentPrice`, `pricingReadyFor`, `parseStartingPrice` — which unlike `parsePrice` accepts blank as "not recorded", the figure being asked for by the transition gate rather than by the parser).
- `Sale` — the transaction header: single `platformId` → `Contact` (`onDelete: Restrict`), `soldAt` (date, FX frozen here), one `currency`, `fxRateToBase?` `Decimal(65,30)`, and three shared amounts — `buyerHandling?` (+), `shippingCost?` (−, my cost), `commission?` (−, manual) — all `Decimal(10,2)`. **How it was shipped** (#468) rides beside the cost as a *pair*: `shippingMethodId?` → `ShippingMethod` (`onDelete: Restrict`) is the live link, and `shippingMethodName?` is the name **snapshotted at sale time** — the dictionary is a price list the collector re-prices and renames as the carriers do, so the link answers "which row" and the snapshot answers "what was actually bought". A one-off *Custom* method stores the name alone; both null is a sale that says nothing about how it went, which is every sale recorded before the dictionary existed. The method is resolved against the sale's **own platform** on every write, and moving a sale to another platform drops the link while keeping the name. Scoped to `Collection` (`onDelete: Cascade`). **`trackingCode?`** + **`carrierId?`** (#491, `onDelete: Restrict`) are what the parcel itself is: the tracking number as the carrier stated it (free text — every carrier numbers its consignments its own way) and who took it. Deliberately a code rather than a link — the address is built on read from the carrier's `trackingUrlTemplate`, so a carrier that moves its tracking site is corrected once instead of on every sale it ever carried, and a sale with no carrier keeps the number as plain text. A null `carrierId` falls back to the shipping method's default rather than being backfilled, so "never said" and "said this one" stay distinguishable. Both are written together by `updateSaleShipment` — one act, decided at one counter. A **`status`** string tracks fulfillment in a fixed lifecycle `ordered → paid → packed → sent → received` (default `ordered`, #191; the last step is *labelled* **Delivered** since #492 — the token is unchanged, because the rename was about the word on screen), an axis orthogonal to copies/offers; each transition also appends a **`SaleStatusEvent`** (`saleId`, `status`, `changedAt`, `onDelete: Cascade`) so the progression is preserved for reporting/audit. Set inline from the detail header (`setSaleStatus` → `setSaleStatusAction`); the `paid` and `sent` transitions each prompt for the one fact known at exactly that moment when the sale carries none — the buyer-paid total (#443) and the carrier + tracking number (#491, the `ShipmentDialog`, reopenable from the header to correct either) — saving it and the transition in one run so a refused save never leaves the two disagreeing.
- `SaleLine` — the unit lot or sub-lot that sold: `offerId?` → `Offer` (`onDelete: SetNull`, so a historical sale survives offer cleanup), `lotId` → `Lot` (`onDelete: Restrict`), `price` `Decimal(10,2)` in the sale currency. `SaleLineItem` records the exact copies that left; its **`@@unique([itemId])` is the DB-level no-double-sale guard**, and `Item` FK is `onDelete: Restrict`. No sold flag is added to `Item` — sold state is read through this join. Each `SaleLineItem` also carries a **`packed`** boolean (#192), toggled per copy in the packing view (`setSaleLineItemPacked`), independent of the sale's `status`; the inventory list hides copies present in this join by default (`excludeSold`, #207), with an "Include sold" toggle.
- Statuses/kinds are `String` columns (no native Postgres enums), enforced by the domain layer. The other guards — one active offer per (item × platform) (a non-blocking warning, #165), quantity decrement — are derived/domain-level.
- Pure module `src/lib/sale-allocation.ts` (no Prisma, unit-tested in `tests/unit/sale-allocation.test.ts`, #163) is symmetric to `purchase-allocation.ts`: it distributes the three shared amounts across lines by sale price, resolves each line's net (`price + handling − shipping − commission`, possibly negative), converts to base currency at the frozen rate, splits a line's net across its copies by primary-catalog weight (single-item lines short-circuit), and computes per-copy P/L against `costBasis` (`null` cost-basis → `null` P/L). Everything reconciles to the cent via largest-remainder apportionment.

### Allegro sold-listing sync (`AllegroSyncState` / `AllegroOrderLine` / `AllegroListing`, #467)

Server-side over Allegro's REST API on the connection #476 established ([ADR-0024](../decisions/0024-allegro-sold-listing-sync.md)). It produces **observations**, never financial records: creating the `Sale` stays an explicit act (#463, below — pre-filled from the order, written only on the collector's own save), and the only thing it writes outside its own tables is the bidding on the collector's **own auctions** (#481, below) — a fact that commits them the moment it happens.

- `AllegroSyncState` — one row per collection, beside `AllegroConnection` rather than on it (that table exists to hold as few secrets as possible; this holds a cursor and an error message). Carries `orderCursor` (Allegro's own event id), `ordersSyncedAt`, `listingsSweptAt`, `lastSucceededAt` / `lastFailedAt` / `lastError`, the bidding poll's own `offerEventCursor` / `eventPolledAt` / `eventPollError` (#481 — its own cadence, so its own cursor and its own error; a failing bid check must not make the sold worklist read as stale), and a `running` + `startedAt` claim so the poll and a **Sync now** click cannot read one stream twice. The claim times out (`SYNC_LOCK_TIMEOUT_MS`) — a lock nothing can release would end the sync for good, and a second pass over idempotent writes is cheaper than that.
- `AllegroOrder` — the order header, `@@unique([collectionId, orderId])` on Allegro's checkout-form id (which is what a `Sale` records as `externalRef`). Holds Allegro's `status`, the derived `paymentStatus`, `boughtAt` (the earliest of its lines), the buyer's `buyerLogin` + `buyerName`, and `totalPaid` + `currency` from Allegro's own `summary.totalToPay` — delivery included, so it is what changed hands rather than a sum of goods. The buyer's email, phone and address are deliberately **not** read: those are the sale's, and #463 fetches the order by id at confirmation time.
- `AllegroOrderLine` — one row per ordered line, `@@unique([allegroOrderId, lineItemId])`, cascading from the header. Per line rather than per offer because an order line is not one-to-one with a listing (stock above one sells a copy at a time; one order can carry several offers). Holds the offer id, the external id, the title, quantity, unit price, its own `boughtAt`, the matched `offerId` (`SetNull`) with `matchedBy`, and `observedAt`.
- `AllegroListing` — the snapshot of the account's **active** listings, `@@unique([collectionId, platformOfferId])`. Also carries what Allegro said about the **bidding** (#481): `format` (its own `sellingMode.format`, recorded rather than inferred from the local `listingType`, which can disagree), `biddersCount`, and `currentPrice` + `currentCurrency`. A row the newest sweep did not see is marked `ENDED` rather than deleted, and its `observedAt` is deliberately left where it was, so it reads as "last seen up". That absence *is* the ended-without-selling signal; paging every listing an account ever ended would be unbounded and answer a question nobody asked.
- **Pure rules** in `src/lib/allegro-sync-rules.ts` (unit-tested): `paymentStatusFor`, `lineAwaitsSale`, `matchListingToOffer`, `windowFloor`, `syncFreshness`, plus the constants (30-day first window, 15-minute poll, 1-hour staleness). `src/lib/allegro-sync.ts` is the I/O half and makes no judgement of its own; `src/lib/allegro-worklist.ts` is the read half.
- **Matching** is the external id first — an exact statement of identity, present when the listing was published through the API — then the stored `Offer.url` at the address's own boundaries. That second rule is `src/lib/platform-offer-url.ts`, shared with the Assistant's lot capture (#355), which asks the identical question of the identical marketplace. Ambiguity is a **refusal**: two offers claiming one listing leaves the line unmatched, and an unmatched line is shown rather than dropped. Every pass ends with `rematchUnmatched`, which gives the rows that matched nothing another go against the current offers — one query, no Allegro request, and without it fixing an offer's URL never reached an order the event stream had no reason to rewrite. Rows already matched are left alone, a match being something the collector may have acted on.
- **Cursor with a dated fallback**: passes follow `/order/events` from the stored cursor; with no usable cursor (a first sync, or one Allegro no longer accepts) the pass reads `/order/checkout-forms` over the last 30 days and mints a fresh cursor from `/order/event-stats` *before* that read. The fallback is safe precisely because every write is an upsert.
- **The obvious sale is derived, not searched for** (#480, `attachSuggestedSales`): a line matched an offer and `SaleLine.offerId` names that same offer from the sale's side, so where the two meet on **exactly one** sale carrying no `externalRef`, the card proposes it by number and links in one click. Several is not a tie to be broken — an offer can sit on several sales (#473) and a multi-line order can point at different ones — so ambiguity proposes nothing and falls through to #479's picker. One query for the whole page, indexed by offer. It stays a **proposal**: the sync never writes `externalRef`, since an inferred link that emptied a row on its own would take the signal away exactly when the inference was wrong.
- **Linking an order to a sale already recorded** (#479, `listSalesLinkableToAllegroOrder` / `linkAllegroOrderToSale`) is the second direction of the *same* key rather than a second rule: it writes the order id into `Sale.externalRef`, which is the one thing the worklist drops an order on. Candidates are sales with **no `externalRef`** (one that already names an order is spoken for and is never overwritten), on the Allegro platform where one is marked, within 90 days of the order and sorted by distance from its date; the picker fetches them on open, not with the worklist, since the question is only interesting for the order being looked at. Only `externalRef` is written — the collector recorded that sale deliberately. An order another sale already claims is refused **by sale number**, because "already recorded, as sale #12" is an answer and "failed" is not.
- **An order becoming a `Sale`** (#463, `src/lib/allegro-sale.ts` + the pure `allegro-sale-rules.ts`) is the write half, and it is two calls with the collector between them: `getAllegroOrderSalePrefill` works out what the sale *would* be and writes nothing, `recordAllegroOrderSale` writes what was saved on the ordinary `SaleFormDialog`, pre-filled. The prefill re-reads the order **live** (the delivery method and the buyer's email were never stored, ADR-0024 §9) and degrades to the stored row when that fails. `externalRef` is the flow's own, never the form's — one order is one sale, and a second confirmation adds the lines the first did not rather than duplicating. Allegro's `totalToPay` becomes `buyerPaidTotal` (#205's anchor, so handling is derived); the buyer's delivery payment never becomes `shippingCost`, which is the collector's own postage. A line maps to sets only when the quantity equals the sets still sellable on the matched offer — anything else is named, left out and left to the per-line sell flow, since a wrong composition is worse than none (#355). A paid order advances the new sale to `paid` (#191). The **buyer is filed under their Allegro login**, not the name on the order (`buyerIdentityFor`): the login is what `resolvePurchaseContact` will match on next time and how the address book already names buyers, so filing them by legal name would create a second contact for the same person on every order. The order's name lands in `Contact.fullName` instead, and an existing contact is looked for under both. `fullName` and `email` are filled in only where the contact has neither — never overwriting what the collector typed. Coverage against `SaleLine.offerId` is what keeps a **partly** recorded order on the worklist (§6a).
- **The screen** (`offers/allegro`, a sub-route like the bulk listing workspace — and, since #502, a nav entry beside it under the Offers group) filters the sold section on **two independent axes** — paid/not paid over orders, matched/unmatched over lines — OR within an axis and AND across them (#475's chips), client-side over the one unpaginated batch (#322's reasoning). An order left with no line by the match axis falls out; the chip counts are over the whole batch, so they say what is there to filter *to*.
- **Automatic "in active bidding"** (#481; ADR-0024 §8a) is the one thing here that writes to the collector's own data, and only on their own auctions: a reported bidder sets `Offer.inActiveBidding`, the standing bid into `Offer.price` + `priceCheckedAt`, and `Offer.bidderCount` — which no other path ever writes, so its presence is the provenance of both. The rule is pure (`bidWriteFor` in `allegro-sync-rules.ts`): both sides must call it an auction, the bid is only written in the offer's own currency, an unbid auction keeps a zero price, and **nothing ever clears the flag**. Visible by design, and as an **event rather than a state**: the same write raises `Offer.biddingNoticeAt`, the offer screen clears it on open (arriving *is* the acknowledgement), and the `offer-bidding-started` group lists only unread notices — a hundred running auctions with bids on them are a hundred things already known, and listing them until they closed would make the badge meaningless. The standing view is the offers list's `bidding=1` filter, which is what the group links to. A flagged offer the platform now reports **no bidders** on is the one non-expiring case, `offer-bid-withdrawn` (`warning`): stock held out of every other listing for a bid that no longer exists, and nothing here will clear it for the collector. Beside both, the bidder count on the offer and the counts in **Sync now**'s own answer.
- **Event poll** every 2 minutes (`runAllegroEventPoll`), its own timer beside the sync's, over **both** streams: `GET /sale/offer-events` (`OFFER_BID_PLACED` / `OFFER_BID_CANCELED`) from `offerEventCursor`, reading details only for the offers those events name (`GET /sale/offers?offer.id=…`, batched), and `GET /order/events` from the sync's own `orderCursor`, fetching only the orders it names — through the same `recordListing` / `writeOrder` the full pass writes through. A poll on a quiet account is two requests. It takes the same claim as the full pass and does **no** sweep, no window import and no re-match: with a missing or refused order cursor it clears it and leaves the import to the pass built for it, and the offer stream's 24-hour retention means a refused cursor there is ordinary — it seeks to the end and applies nothing, the sweep restating every listing's bidding anyway.
- **Background poll** every 15 minutes from `src/instrumentation-node.ts`, beside the photo GC and the render worker; `syncAllegroNowAction` is the same pass on demand. It is the *full* pass — the only one that sweeps every listing, and so the only one that can derive ended-without-selling, run the dated fallback import or re-match. New orders and new bids do not wait for it: they arrive through the two-minute event poll above, which follows both streams and costs two requests when nothing happened. A 401 latches `AllegroConnection.needsReconnect` (ADR-0023's one unusable state), everything else lands in `lastError` — which the worklist header states, along with staleness, so a list that has stopped being current can never look current.

#### Listing profiles (#486; [ADR-0025](../decisions/0025-allegro-listing-profiles.md))

The seller-side settings a *published* listing needs and no offer has any notion of — the shipping rate set and handling time, the return policy and implied warranty, where the parcel is sent from, the invoice promise — held as a named `AllegroListingProfile` on the Allegro platform `Contact` (`src/lib/allegro-listing-profile.ts`, vocabularies in the pure `allegro-listing-profile-vocabulary.ts`). All of it is the collector's **account configuration** rather than anything about a stamp: identical for a 1918 Polish issue and a modern block, changing when they move house or add a courier. The category and its parameters are deliberately elsewhere (#488) — those *are* about the stamp and are learned rather than configured.

- **A default per platform, overridable per offer.** `Contact.defaultAllegroListingProfileId` is what a listing goes out with; `Offer.allegroListingProfileId` names another and is null on essentially every offer. The `defaultCollageTemplateId` shape (#308): a default is one row of the list, not a flag on every row something has to keep exclusive. Both references are `SetNull` — deleting a profile is never blocked by a listing that merely preferred it — and nothing is promoted when the default itself goes, since choosing what the next listing carries is the collector's decision. One resolver, `resolveAllegroListingProfileForOffer`, is the whole of the fallback rule, so the settings screen and #477's publish cannot disagree about which settings a listing carries.
- **Allegro's ids, with a snapshot name beside each.** The three dictionary fields hold ids that exist only in the collector's Allegro account (`GET /sale/shipping-rates`, `GET /after-sales-service-conditions/*`, read through `allegro-api.ts`); the `*Name` beside each is a label for a screen, written from what the account said at save time. Nothing can be *created* from here, so an empty dictionary is stated and pointed at Allegro rather than shown as an empty select.
- **Validated at publish time, not on save** (ADR-0025 §3). A rate set can be deleted on Allegro at any moment, so the question has one honest answer time. The editor instead reads the account **live** every time it opens and on demand, and a save checks only the fields Allegro requires and the two vocabularies — which keeps a settings screen working while the connection is down. Not our `ShippingMethod` (#468) at any point: that one is what the buyer paid on a recorded sale, this one is Allegro's table of what a listing offers.

#### Listing images (#487; [ADR-0023](../decisions/0023-allegro-api-authentication.md) §8)

An Allegro offer references `images[]` as **URLs**, so the bytes go up first: `uploadOfferPhotosToAllegro` (`src/lib/allegro-images.ts`) posts each picture to `POST /sale/images` — a **binary** body under the image's own media type, on Allegro's separate `upload.` host — and returns the URLs #477 publishes with, in the plan's own order. Linking ours instead is not an option: they are private bytes behind the Assistant token (#253), and an instance on `localhost` has no address Allegro could fetch from.

- **The plan is read, not re-derived.** `readOfferUploadImages` is `getOfferPhotoPlanState`'s upload set (#311/#313) — do-not-publish and over-limit already dropped, the collector's order kept — and the same read both ZIPs are built from, so an uploaded image and one unpacked from the archive are the same bytes under the same name. First image first: the first is the listing's thumbnail.
- **No URL is cached.** Allegro states an `expiresAt` and removes an image no listing has used, so a stored URL goes stale unobserved and a re-publish simply re-uploads. It also means a failed publication leaves nothing to clean up.
- **Sequential, and a refusal is about a picture.** `AllegroImageUploadError` names the photo, its plan file name and its 1-based position; the pure `allegro-image-rules.ts` turns 413 / 415 / 422 into three different next steps and judges only the format locally, inventing no size limit Allegro does not publish. The first failure stops the run — a listing with fewer pictures than were prepared is what this is designed against.

#### Learned categories (#488; [ADR-0026](../decisions/0026-allegro-learned-categories.md))

The other half of what a listing needs, and the half that is about the **stamp** rather than the account: `category.id` and that category's `parameters[]`. Neither can be configured — a 1935 Polish used definitive and a modern German souvenir sheet belong in different categories and answer their categories' questions differently — so nothing is filled in up front and the app watches what was actually published. `src/lib/allegro-category.ts` is the I/O half; every judgement is in the pure, unit-tested `allegro-category-rules.ts`.

- **Two registers.** `PlatformCategoryLesson` maps an (area, year, condition, subtype) key → category; `AllegroCategoryParameterMemory` maps a (category, parameter) → the value last answered, **one row per parameter**. Separate because the second is what makes a *new* key cheap once its category has been picked and the first is what makes an old key free; one combined register would relearn every parameter the first time an area gained a new year. Both per (collection, platform), the `AllegroListingProfile` ownership. That separation is also what made #609 cheap: the first register was **generalised across marketplaces** and renamed off `AllegroCategoryLesson`, having been keyed per platform from the start, while the parameter half stayed exactly where it is — Delcampe's categories carry none. The key, the ladder and the ranking now live in `platform-category-rules.ts` / `platform-category.ts`.
- **Every key part is nullable, and null means absent from the key.** Produced two ways, identical to lookup: the offer is **mixed** — each fact enters the key only where the copies agree, so a bundle spanning 1935 and 1938 still asks about its area, condition and subtype — or the fact does not exist. The area names a node of the area tree.
- **Lookup relaxes rather than fails**, in one fixed order shared by every caller: the exact key, drop the **year**, drop the **subtype**, then one level **up the area tree** and repeat. The **condition is never dropped** — used and mint are different categories far more often than not. A rung is a *filter over rows*, not a row lookup (rows carry the fullest key their offer supported, so "any year" must still match rows that have one), and an area rung matches a node **or any descendant**, which is what makes a lesson learned on Poland → Provinces reach Poland → Republic. Within a rung: this branch's own row first, then `timesUsed`, then recency. A key nothing matches falls to `GET /sale/matching-categories` from the title, then to a manual pick — there is no failing outcome.
- **Recorded from an offer the collector has finished preparing** — `preparing → ready`, #494 having moved it off publication (see below) — through `recordAllegroCategoryLesson`. A draft teaches nothing, and correcting a suggestion and publishing again is itself a lesson — the newer choice overwrites and bumps `timesUsed`, rather than adding a second row (which is why the key index is `NULLS NOT DISTINCT`, ADR-0006). A key that asks nothing is not recorded at all: it would answer every future lookup with whatever went out last.
- **Always a suggestion, always correctable.** The shared `shared/allegro-category-picker.tsx` walks the tree (`GET /sale/categories?parent.id=`) to a leaf and renders that leaf's parameters (`GET /sale/categories/{id}/parameters`) by type with the recalled answers filled in and required ones enforced — read live every time, because what a category *asks* is Allegro's and only the answers are remembered. Settings → Allegro lists both registers with their support counts, and a row can be re-pointed (its count starting again, the new category never having been published into) or forgotten: a wrong association must never need a wrong listing to fix it.

#### Publishing an offer (#477; [ADR-0027](../decisions/0027-allegro-offer-publishing.md))

The act the three sections above exist for, and the one thing here that writes to the collector's live selling account. `src/lib/allegro-publish.ts` fetches, sends, polls and writes; every judgement is in the pure, unit-tested `allegro-publish-rules.ts`. It sits **beside** the Assistant listing path (#407/#408) rather than replacing it — a marketplace with no API is driven through its own sale form, and one with an API is not.

- **The listing kit is shared, its blockers are not.** `getOfferListingKit` (#405) is read directly here for what the offer *holds* — title, description and its format, price, currency, the number of interchangeable sets. Its own `blockers` are Colnect's rules (#406, narrowed by #471) and are replaced by Allegro's; the one rule the two genuinely share is exported once as `differingSets` (`listing-preconditions.ts`), since a single quantity may only describe interchangeable sets whether it is a form field or `stock.available`. `setIdentity`'s fallback to the local stamp + condition is what makes that comparison answerable on a platform with no catalogue of its own here.
- **The request is assembled purely.** `buildAllegroOfferRequest` turns the kit, the profile (#486), the category with its answers (#488) and the uploaded image URLs (#487) into one `POST /sale/product-offers` body. `sellingMode` carries the format (#449) and only the figure that format *states* — `BUY_NOW` at the asking price, `AUCTION` at the **starting** price, since an auction's `price` is an observation of the bidding — and `external.id` is `Offer.offerNo` (#416), which is exactly what the sync above matches on.
- **Draft or live, chosen per publish, draft the default.** Allegro takes `publication.status` in the create itself. `INACTIVE` leaves the listing unlisted in the collector's account and the offer `ready`; `ACTIVE` goes through `publishOffer` (#246/#320), never around it. `activateAllegroDraft` is the same conclusion taken later, from the same control (`offers/allegro/publish-to-allegro.tsx`).
- **Refusals before the request.** `evaluateAllegroPublishBlockers` reports the connection first and alone (#485's write scope included — a scope that could not be *read* is deliberately not a refusal), then a listing already published, then an unfinished offer, then everything else together, one line each. An over-long title is refused rather than shortened: Allegro caps 75, the kit does not, and a title the app cut is not the title that was written.
- **201 and 202 are not one thing.** A 202 is polled at `GET /sale/product-offers/{offerId}/operations/{operationId}` to succeeded / failed-in-Allegro's-own-words / still-running-at-the-bound; the third records the Allegro offer id so a second press cannot duplicate the listing, and moves nothing. An unrecognised operation status reads as still running.
- **Allegro sells through the API from business accounts only**, and that is unaskable in advance: the grant is issued, refreshed and used for reading orders and bids without complaint, and the refusal arrives the first time a listing is published (*"You cannot use the Public API method when selling with a Regular Account"*). It is latched in Allegro's own words on `AllegroConnection.publishRefusedReason` and every later publish is refused before a request — deliberately **not** `needsReconnect` (this connection is not unusable, and reconnecting fixes nothing), and cleared by a fresh grant or a re-registered application, which are the two moments the answer could change. Detected on the wording (`namesIneligibleAccount`), the code being undocumented. On a private account the whole publish path is therefore a named refusal rather than a feature; listing to Allegro from one is the Assistant's job (#493).
- **The category, its answers and the profile live on the `Offer`** (#494, `src/lib/allegro-offer-listing.ts`), not in the publish dialog: two paths post to Allegro — the API and the Assistant's sale form (#493) — and a value each of them resolved for itself is a value the two would disagree about. `allegroCategoryId` / `Name` / `Path` / `Source` / `MatchedOn` / `Parameters` beside #486's `allegroListingProfileId`, surfaced as `OfferDetail.allegroListing` and edited on the offer's own **On Allegro** card. Filled in by `backfillAllegroCategory` from the three mutations that add copies — `syncGeneratedTexts`'s own call sites (#365/#380) — but as a **backfill, never a refresh**: a title describes the composition, a category is a decision about what the goods are, and re-deriving it under a correction would undo it silently; ↻ is the explicit re-match. The backfill **cannot fail the mutation it hangs off** (a marketplace that is down costs a blank card, never a refused set). Nothing is a gate — whatever matched is what publishes, with `source` + `matchedOn` carrying the provenance — except a **required offer-section parameter with no answer**, which Allegro refuses by a field name nobody saw. **Both** parameter sections are stored, each with its own `describesProduct`: Allegro's sale form asks for both and the collector answers both, and only the API request drops the product half (ADR-0027 §2). The register learns on **`preparing → ready`** in `setOfferState` — not at publication, which is the moment ADR-0026 §5 originally named and the wrong one for a collection worked in runs: offers are prepared ten at a time and published later, so learning at publication asks the same question ten times and answers it the day after. `ready` is where the collector has said what the stamps are. It hangs off the transition rather than off each listing path so that a new path cannot forget it.
- **What a conclusion writes**: `Offer.url` + the transition on a live publish, `Offer.allegroOfferId` / `allegroPublishStatus`, and the category lesson — **only** on a success. The id is not a second copy of what the sync matches on: a draft has no public page and so no URL, and the id is the address activation is sent to.

#### Listing through the Assistant (#493; [ADR-0028](../decisions/0028-allegro-listing-through-the-assistant.md))

The second path to Allegro, and the one a **private (Regular) account** has: the Assistant fills Allegro's own sale form. It sits beside the API path (#477), which stays the better one where Allegro allows it; both are offered on a `ready` Allegro offer and nothing inspects the connection to choose between them.

- **The preconditions became per module first** (`listingModuleRules` in `src/lib/platform-modules.ts`). `hasListingModule()` going true for Allegro would otherwise have turned **Colnect's** rules on for every Allegro offer — an item-ID on every stamp, a mapped grade for every condition — and refused them all `ready` over a catalogue Allegro does not list against. A module now states what its own form asks for; what stays shell-wide is being Ready, holding copies, and the sets being interchangeable, those being facts about the offer. The same entry gates the two reads that only ever existed for Colnect: the condition map (`usesPlatformConditions`) and the platform-catalogue card (#423, `usesPlatformCatalogue`).
- **Allegro's refusals split by who they are about.** `src/lib/allegro-listing-rules.ts` holds the **listing** group — title over 75, untruthful stock, no price, no profile, no category, no pictures — evaluated by both paths; `allegro-publish-rules.ts` keeps `evaluateAllegroApiBlockers` (connection, write scope, account eligibility, already-published) and composes the two, so neither path can drift from the other.
- **The configuration travels as a named section**: `kit.allegro` (`src/lib/allegro-listing-task.ts`, `readAllegroListingSection`), null for every other platform, read through #494's `readAllegroListingInputs` and never resolved a second time. It carries **both** parameter sections (the form asks for both; only the API request drops the product half) and each answer's **display value** beside its dictionary ids, because the form's `select` submits the option's *text* while the API takes `valuesIds`. The labels come from the category form Allegro is already asked for, **best-effort** — a read that fails costs labels, not the task. The kit endpoint refuses on `kit.allegro.blockers` exactly as it refuses on #406's.
- **The module** is `extension/src/platform/allegro/listing.ts`, and it fills Allegro's **legacy** one-screen form: every value maps onto a stable element `id`, and each category parameter onto **Allegro's own parameter id** (`#213`), with the profile's three ids being the option values of `#shippingRatesId` / `#estimatedShippingTimeId` / `#return-policies` verbatim. No class name is read (#355's rule — they are hashed per build). The description goes into TinyMCE's same-origin `iframe#id_ifr`; text fields are written through React's **native** value setter plus an `input` event, or the next render puts the old value back.
- **Getting there is a sequence, so `PlatformListing` gained one optional member**: `prepare?(doc, task): Promise<void>`. A Regular account is redirected off the legacy address, and the way back runs *recommerce landing* → opt-out link → product search → *Kontynuuj bez wybierania produktu* → the category modal → the category number, of which only the ends are page loads. `fill` is synchronous DOM work and cannot wait for a search. The shell calls `prepare` exactly where it already reported `retry` (#419) — at `isFormUrl`, not `isFormDocument` — then fills once more; the content script's fill message is answered asynchronously for it. Allegro's is the only module that has one.
- **The profile carries what only the form asks for** (#493): `AllegroListingProfile.durationLimit` (nullable — "leave the form as served") and `autoRepublish` (a boolean, written in both directions since an unticked box is a decision). Neither is sent by #477's API request, which takes Allegro's own defaults and whose behaviour with these was not established. **Durations match by length, not by string** (`isoDurationHours`): the profile holds the API's notation (`P3D`) and the form offers its own (`PT72H`), so an equality test selects nothing and leaves the default — which is how a three-day handling time went out as one day.
- **`prepare` unfolds the form as well as walking the entry**, and therefore runs before *every* fill. Three things this task needs are absent from the served document: the rest of the category's parameters (behind *więcej parametrów*), an auction's `#auction-starting-price` and `#auctionDurationSelect` (which appear only once `#auction-checkbox` is ticked, and *replace* `#durationLimit`), and the description editor (`iframe#id_ifr` — TinyMCE mounts only when the placeholder is clicked). Each is a React re-render, so none can live in the synchronous `fill`.
- **The AI-watermark dialog is answered, never chosen.** Allegro opens it over the uploader the moment files arrive (AI Act marking); the module confirms it with **nothing ticked** — the truthful answer for photographs of stamps, and a declaration it must never make for the collector — matched on the dialog's own `#modal-title` rather than on the *Potwierdź wybór* button alone. This is why `PlatformListing.attachPhotos` may now return a promise and `attachListingPhotos` awaits it: the handover is not finished until that question is. Colnect's returns directly and is unchanged.
- **The listed URL is read off the page, not off a navigation** (#412's other half). Allegro answers a submitted form by re-rendering the same document into `#thank-you-page` — the offer's link is in it, the address bar stays on the form — so `PlatformListing` gained **`listedUrlInDocument?(doc)`** beside `listedUrl(url)`, and the content script watches for that page with a `MutationObserver` — armed **when the form is filled, never on `submit`**, because Allegro posts through script and raises none, which is how the first attempt failed silently — then messages `listed-here`; the background delivers it through the very same pending record and write-back. Without it every Allegro run ends "submitted, URL unread". The offer named is awaiting Allegro's review, which does not change what is recorded.
- **Left to the collector, and reported**: the auction fields (ticking *licytacja* reshapes the pricing section), and the sending address (Allegro's own account setting, not a form field). The listing comes back through #412's existing write-back — `listedUrl` recognises `/oferta/<slug>-<id>`, the same shape #355 and #467 match on — and the category register needs no hook, having learned on `preparing → ready` (#494).

### Delcampe listing profiles (`DelcampeListingProfile`, #608; [ADR-0034](../decisions/0034-delcampe-listing-profiles.md))

Everything an **Easy Uploader** row states that no offer knows about itself, held as a named profile on the Delcampe platform `Contact` (`src/lib/delcampe-listing-profile.ts`, pure rules in `delcampe-listing-profile-rules.ts`). Delcampe is listed to by uploading a CSV rather than through its API — that sits behind the paid API Pass and is deliberately not taken — so the file's columns are the contract: the shipping model the row names, the renewal counters, the five chargeable `option_*` promotions, and the bid step. Everything else a row needs the app already answers (templates #210/#266, price and `selling_type` from the offer #449, currency #196, images from the photo plan).

- **One profile, four groups.** All of it travels together rather than in a dictionary each, because the case that makes a second answer necessary is one case — a heavier lot wanting the other shipping model, chosen when the row is built. `Contact.defaultDelcampeListingProfileId` is the default, `Offer.delcampeListingProfileId` overrides it, both `SetNull`, nothing promoted when the default goes, and `resolveDelcampeListingProfileForOffer` is the whole of the fallback rule — ADR-0025 §2 restated for a second marketplace.
- **The shipping model is an unvalidatable name**, inverted from Allegro's stored id + label: the CSV carries the name itself, no id is held in reserve, and `GET /shippingModels` is API-Pass-only. Stored as data that cannot be checked, and said out loud in the editor, so a renamed model's rejected upload does not read as a fault in the export.
- **`minimum_bid_step` is a threshold rule** (`minBidStepThreshold` / `Below` / `AtOrAbove`, applied by the pure `delcampeMinimumBidStep`, boundary **inclusive at the top**). The threshold is a stored field because it was never confirmed against Delcampe — a guess in a settings field is corrected the first time a listing disagrees, a guess in the exporter is not.
- **`platformModule` gains `"delcampe"` as a marker only.** Set on its own Settings tab through the shared exclusive `setModulePlatform`, and absent from `LISTING_MODULE_RULES`: `hasListingModule` answers false, so no Assistant handoff is offered and none of Colnect's preconditions is asked of a Delcampe offer (#471's distinction). Auctions (#620) are deliberately elsewhere.

#### Learned categories and Delcampe's own list (#609; [ADR-0035](../decisions/0035-delcampe-learned-categories.md))

The last column of an Easy Uploader row that is about the *stamps*: `category_id`. A dictionary cannot answer it — Delcampe's tree is cut by period where this collection is cut by area, and a souvenir sheet goes somewhere else again from the same country's singles — so #488's **register** answers it instead, and the register itself was generalised rather than twinned.

- **`PlatformCategoryLesson` is the same table Allegro reads**, renamed. `platform-category-rules.ts` (pure: key, ladder, ranking, the "Learned from …" sentence) and `platform-category.ts` (reads and writes) are shared; `allegro-category*.ts` keeps the parameter register and the title guess, `delcampe-offer-listing.ts` the Delcampe half. The key gained **no axis** — one for the souvenir-sheet case would be a claim this app cannot make and would change Allegro's behaviour.
- **Two sources, not three.** `Offer.delcampeCategoryId` / `Name` / `Path` / `Source` / `MatchedOn`, where `Source` is `learned | manual`: Delcampe has no title-guess endpoint, so an unmatched key falls to the picker. `backfillDelcampeCategory` sits beside the Allegro one in the same three mutations (backfill, never refresh); ↻ *Match again* **clears** on a miss rather than keeping a value the register did not give. Learning is on `preparing → ready` in `setOfferState`, which matters more here than on Allegro — the CSV goes up days later.
- **`DelcampeCategory` is Delcampe's published tree**, snapshotted from `delcampe.net/en_GB/collectables/category-id/` because there is no API. A **dictionary, not a mapping**, and the one table in this schema with **no `collectionId`**: the taxonomy is identical for every collection here (`StorageCacheEntry` is the precedent). Refreshed daily in `instrumentation-node.ts` — and only on an instance that has named a Delcampe platform, only when the snapshot is over twenty hours old, sequentially at ~1.2 s, ending the pass on a 429, and **deleting only after a complete pass**. The parser reports only links a page did *not* expand in place, which is what keeps the walk at a few hundred requests. **Every tick logs** — a skip with its reason, a run with `added / removed / changed / unchanged` counts (`describeDelcampeCatalogChanges`, shared with the settings panel and the command) — against the quiet-when-nothing-moved rule the hourly sweeps follow, because for a daily job on somebody else's site silence cannot tell "not running" from "nothing changed". `pnpm delcampe:categories` runs the same pass by hand.

#### The Easy Uploader export (#610; [ADR-0036](../decisions/0036-delcampe-easy-uploader-export.md))

What turns a prepared batch into a listing: `delcampe-export-rules.ts` (pure — the column list in the file's own order, the decimal **comma**, RFC 4180 quoting, one row, and the refusals a row can carry) and `delcampe-export.ts` (the batch), behind `POST /api/collections/[collectionId]/offers/delcampe-export` and a Delcampe-only button on the bulk listing workspace (#322), which is already scoped to one platform's `ready` offers — the shape of one Easy Uploader batch.

- **One flat ZIP**: `delcampe-upload.csv` beside its pictures, no folders, because `images` names files by name alone. The pictures come from `readOfferUploadSet` — the same read the per-offer ZIP (#314) and the batch archive (#323) are built from, so a bundled file is byte-identical to and named exactly as the same file downloaded on its own. Two offers whose titles slug the same are suffixed **per offer**, so one listing's run keeps one stem.
- **A refusal is the whole batch.** No category, no photos, no profile, no price, a title over the cap, an auction — every reason for every offer at once, and no file. The inverse of the photo archive's skip-and-report, and deliberately: a missing folder in a download is visible, a missing *row* is a listing that never happened. Nothing is truncated to fit (#405/#477).
- **`personal_reference` is the offer's short URL** (`offerScreenUrl`, #415/#416), which is what makes #611's reconciliation exact; an instance with no `BETTER_AUTH_URL` refuses rather than writing unmatched rows.
- **`Contact.maxTitleLength`** joins #403's two caps — the second unconfirmed number in this file to be a settings field rather than a constant, after `minBidStepThreshold`. The **ongoing-sales ceiling is deliberately not held**: this app cannot see the seller's live count, so anything it counted would be its own offers wearing a guarantee's clothes.

### Storage locations (`Location`)

`Location` is a per-collection **adjacency-list hierarchy** of physical storage — cabinets, stockbooks, albums, boxes — reusing the same pattern as `CollectionArea` (see [ADR-0010](../decisions/0010-storage-location-model.md), design in #55, built in #56).

- Fields: `id`, `collectionId`, `name`, `parentId?` (arbitrary depth), `description?`, `assignable` (`Boolean`, default `true`), `createdAt`.
- `assignable` distinguishes grouping-only nodes (a cabinet — `false`) from leaf storage that can actually hold copies (a stockbook — `true`). A copy's `locationId` may only point at an `assignable = true` location.
- `collectionId` cascades; the self `parentId` FK is `SetNull` (matching `CollectionArea`), but deleting a location that still has children or stored copies is blocked in the domain layer. The `Item.locationId` FK is `onDelete: Restrict` so a stored copy is never orphaned.
- Filtering the inventory by a location includes the whole **subtree** (a parent selection shows copies in its descendants), resolved server-side in `src/lib/items.ts`.
- Domain module `src/lib/locations.ts` (server-only) exposes `getLocations` / `createLocation` / `updateLocation` / `deleteLocation`, all collection-owner-authorized, with the cycle, assignable, and delete guards.

### Photos (`Photo` / `PhotoUpload`)

Copies, catalog stamps **and offers** can carry photos (see [ADR-0011](../decisions/0011-photo-storage-interface.md), #112/#137/#311). `Photo` is **polymorphic**: it hangs off exactly one owner — an `Item` (copy), a `Stamp` (catalog-level reference image) or an `Offer` (a generated listing image). `PhotoUpload` is a short-lived staging row for eager, pre-Save uploads, shared by the two upload owners.

- `Photo` fields: `id`, `itemId?` (`onDelete: Cascade`), `stampId?` (`onDelete: Cascade`), `offerId?` (`onDelete: Cascade`), `kind` (`original | generated`, default `original`), `role?` (`front | back | main | null`), `title?`, `storageBackend` (default `filesystem`), `storageKey`, `mime`, `width`, `height`, `sizeBytes`, `sortOrder`, `createdAt`. A raw `CHECK (num_nonnulls(itemId, stampId, offerId) = 1)` enforces **exactly one owner**. Three *partial* unique indexes — `(itemId, role) WHERE itemId IS NOT NULL` and the same for `stampId` / `offerId` — make each reserved role a **singleton slot per owner** (a plain unique on the now-nullable `itemId` would let every stamp photo collide on `(NULL, ...)`; Postgres keeps NULL roles distinct, so titled extras stay unlimited). Which slots an owner uses is a UI concern: **copies** use `front`/`back`, **stamps** use a single `main`, **offer** images use none — they order via their plan entry (#311). `kind` records how the bytes came to exist and exists so generated bytes can later be purged and recreated on demand, which originals never can.
- `PhotoUpload` fields: `id`, `collectionId`, `storageBackend`, `storageKey`, `mime`, `width`, `height`, `originalWidth`, `originalHeight`, `sizeBytes`, `createdAt` (indexed for the GC cutoff scan).
- **Storage interface** (`src/lib/storage/`): `put` / `get` / `delete` / `move` / `resolveUrl`, async + streaming. `FilesystemStorage` is the only binding, rooted at `STAMPORAMA_DATA_DIR` (default `/data`; `./.data` in dev). `resolveUrl` returns a discriminated `{kind:"stream"} | {kind:"redirect"}` result so a future GCS binding can 302 to a signed URL. Writes go to the active backend (`getActiveStorage`); reads dispatch per-photo by `storageBackend` (`getStorage`) — write-one, read-many. A `storageKey` is a **prefix**; the two variants hang under it as `<prefix>/{full,thumb}.<ext>` (permanent `<collectionId>/<photoId>`, staging `staging/<uploadId>`).
- **Processing** (`src/lib/photos/process.ts`): `sharp` decodes once and emits a **2500px** full derivative plus a **320px** thumbnail eagerly. Accepts JPEG/PNG/WebP up to **200 MB** (the whole file is buffered before the decode, so the cap is a memory bound as much as a policy). That figure is fitted to a full-resolution **card scan** (#566/#567) rather than to a photograph — a stockbook card at 1200 dpi passes 60 MB, and its bytes are retained uncapped because the cut is taken from the original — and it is deliberately **one number for every upload**, since two caps would need every route and message to say which one it meant while the ordinary photo path never approaches either. The source's own dimensions are recorded alongside them as `Photo.originalWidth`/`originalHeight` — the original bytes are never kept, so this row is the only record of how far a scan was shrunk, and the collage renderer needs it to put a clamped scan back on a common scale with an unclamped one (see *Collage renderer*). EXIF orientation is normalised by hand there, because `metadata()` reports pre-rotation dimensions. Null on rows predating the columns: nothing to backfill from, and readers fall back to `width`/`height`, i.e. "never downscaled". `thumbnailFor` derives *only* a thumbnail, for images the app produced itself (#311): a collage's `full` bytes are the renderer's own output, already sized and encoded to the platform's limits, so re-encoding them would undo that work.
- **Domain** (`src/lib/photos.ts`, server-only): `stageUpload`, the owner-agnostic change-set apply exposed as `applyPhotoChangeSet` (copy) / `applyStampPhotoChangeSet` (stamp) (atomic Save of the dialog's pending change-set — adds/removals/role-changes/reorders), `listItemPhotos` / `listStampPhotos`, `promoteCopyPhotoToStamp` (duplicate a copy photo's bytes into an independent stamp `Photo`, then on up the variant tree to each photo-less ancestor, stopping at the first that has one — #347, and at the first node whose effective `actsAsVariant` is false, since an error or plate flaw pictures itself rather than its parent — #368; the automatic seed behind it only fires for copies in the default physical format, #346), `getPhotoForServing` (resolves any of the three owners), `deletePhotoBytesForItem` / `deletePhotoBytesForStamp` (called by `deleteItem` / `deleteStamp`), and `gcStaleUploads`. All collection-owner-authorized. Offer-owned images deliberately do **not** go through the `PhotoOwner` change-set seam — they are generated from a plan, not edited in a dialog, so their lifecycle lives in `src/lib/offer-photo-generation.ts` (#311).
- **Transport & serving**: multipart uploads go through the route handler `POST /api/collections/[collectionId]/photos/uploads` (not a server action); bytes are served by `GET /api/collections/[collectionId]/photos/[photoId]/[variant]`, authorized by the photo's owning collection + owner (item, stamp **or** offer). Files never sit under `public/`.
- **Cleanup**: deleting a photo, its `Item`, its `Stamp` or its `Offer` deletes the stored bytes (cascade drops rows only). Abandoned staging uploads are swept hourly by an idempotent in-process GC started from `src/instrumentation.ts` `register()` (TTL `STAMPORAMA_PHOTO_UPLOAD_TTL_HOURS`, default 3h) — no separate compose service. That pass takes **two kinds** of staging since #590: a dropped-but-unsaved photo, and a chunked card-scan upload whose parts stopped arriving (`scan_upload` plus its directory under `<STAMPORAMA_DATA_DIR>/scan-uploads/` — **local disk, never the storage backend**, since a chunk is written once, read once and deleted; aged from the last accepted chunk rather than from the open, because a 200 MB card over a home connection can legitimately be in flight for hours). One TTL for both, because a part-sent scan is staging in exactly the sense an unsaved photo is. A second hourly sweep beside it, `purgeClosedOfferPhotos` (#512), deletes the **generated** images of offers closed (`sold` / `withdrawn`) longer than that collection's retention period. Since #577 the period is **per collection**, resolved in `src/lib/offer-photo-retention.ts` as `Collection.closedOfferPhotoTtlDays` → `STAMPORAMA_CLOSED_OFFER_PHOTO_TTL_DAYS` → the built-in default of 7 days; all three speak one grammar (`off` / `never` keeps for ever, `0` purges at the next sweep, otherwise days), parsed by the one function that has always parsed it. The sweep therefore makes a pass per collection — the cutoff differs for each, and a collection that keeps for ever has none — and the boot log states the *instance default* rather than a figure that would be wrong for any collection setting its own. It reads `Offer.closedAt`, stamped by every write of a terminal state and cleared when a deleted sale reopens a listing. Only `kind = 'generated'` rows go — a copy's scan and an attachment's uploaded original (#313) are sources nothing could recreate — and the plan itself (photo settings, attachment rows, `photoPlanOrder`) is untouched, so Regenerate makes the images again. The `OfferPhotoGeneration` row survives at `status = 'purged'` rather than being deleted, so the card says the images were cleaned up rather than never made; an offer with a `queued` / `running` job is skipped. A **third** hourly sweep, `purgeFinishedScanSheets` (#578), deletes the retained card scans of batches nothing can be cut from again — `ScanSheet.batchDoneAt` (#567) is stamped when the last tile of a batch leaves `unidentified` and cleared if one comes back, so the clock never runs on a batch still being worked. It resolves its period the same three ways (`Collection.scanSheetTtlDays` → `STAMPORAMA_SCAN_SHEET_TTL_DAYS` → the built-in default) in `src/lib/scan-sheet-retention.ts`, and speaks the same grammar through the shared parser in `src/lib/retention-ttl.ts` — but its built-in default is **keep for ever**, because a card scan is a *source* and not output: a stockbook cannot be re-scanned once it has been broken up, so the sweep ships off and is switched on per collection. It takes the **bytes and not the row**: the sheet is marked `purgedAt` with `sizeBytes` zeroed, so the storage total drops while a re-cut refuses with *the scan has been deleted* and the batch still lists what the card held; the serving and region routes answer 404 for a purged sheet.
- **Storage total** (#144) sums `sizeBytes` across all three owners; generated images count, because they occupy the volume like any other file.

### Collage templates (`CollageTemplate`)

A collection-level, named render preset for offer photo collages (#307) — `name`, `gridMode`, `rows`, `columns`, `gapPercent`, `background`, `labelPercent`, cascade-deleted with its collection, edited under **Settings → Collage templates** (`collage-templates-panel.tsx`, mirroring `subtypes-panel.tsx`). It exists because collage capacity is a property of **stamp size**, not of the platform or of one listing.

- **Capacity, not frame.** `rows × columns` is a maximum; the renderer (#310) shrinks the canvas to the actual contents, so 4 copies under a 5×4 template give a one-row image. A 1×1 template is the single-stamp case, which keeps one rendering path for every image.
- **Seeded, not referenced.** A template is picked on an offer and its values are **copied onto the offer** (#308), exactly as `Contact.descriptionTemplate` seeds `Offer.description`; no *offer* points back at the table. Editing or deleting a template therefore cannot retroactively change offers already prepared, and there is no in-use check on delete. The one reference is `Contact.defaultCollageTemplateId` — which template a new offer on that platform seeds from — and it is `onDelete: SetNull`, so delete stays unguarded.
- **Two ways to read the capacity** (#413, `gridMode`). `fixed` is the original behaviour: `columns` is both the bound and the shape, so every row is filled to it and the last one is short. `auto` reads the pair as *max* rows and *max* columns and lets the renderer choose the width per image from its tile count — the product stays the capacity, so grouping (#309) is untouched and only the shape moves. It exists because the numbers belong to the *material* while the count belongs to the *offer*: a template written for nine small definitives laid five out as 4 + 1, and the fix was to edit the template between listings. `resolveCollageColumns` (`collage-layout.ts`, pure) scores every allowed width by `empty cells + |columns − rows|` and breaks ties towards the wider grid. Two terms because each alone is absurd: empty cells alone always answers *one column* (a single column never wastes a cell), and squareness alone puts ten into 3 + 3 + 3 + 1 rather than 4 + 4 + 2. Defaults to `fixed` on the template, and **null = fixed** on the offer — which is also why `collageGridMode` sits deliberately *outside* the offer’s all-or-nothing collage group, and why the fingerprint appends it only when it is `auto`: an offer prepared before the mode existed must keep the digest it already stored.
- **Percentages of the stamp, not pixels** (#312). `gapPercent` and `labelPercent` are shares of the **median tile height** of the collage being rendered. Pixels were tried first and are unusable: the canvas is built from scans of an unknown DPI and is then scaled down by one shared factor to the platform's limits, so the collector would have to know both numbers in advance to pick a readable strip height — and labels came out illegible for exactly that reason. A percentage needs neither: how a label reads *beside its stamp* is invariant under the shared downscale, and an image scaled far enough for the label to vanish has already lost the stamp. The median rather than the tallest tile, so one souvenir sheet cannot inflate a whole page's strips. One value serves both axes of the gap.
- Platform limits (max photos / longest edge / file size) are **not** here — they live on `Contact` and are read live at render time (#308, #310).
- No rows are seeded into a new collection: sizing conventions depend on the material a collector actually sells.
- Validation is a pure module (`src/lib/collage-template-rules.ts`, unit-tested), reused by the offer-side photo-settings form through `src/lib/offer-photo-config.ts` (#308); the server module (`src/lib/collage-templates.ts`) is owner-authorized like every other config entity.

### Ref card templates (`RefCardTemplate`)

A collection-level, named dictionary of **paper card sizes** (#569) — `name`, `cardWidthMm`, `cardHeightMm`, `fontSizeMm`, `paddingTopMm`, cascade-deleted with its collection, edited under **Settings → Ref cards** (`ref-card-templates-panel.tsx`, mirroring `collage-templates-panel.tsx`), read by the blank ref-card sheet (`locations/ref-cards/`, #565). It exists because a ref card is slipped into a transport card's pocket, so its size is a property of the collector's **stationery** — the sheet shipped with those numbers hardcoded, and a sheet in the wrong format is not a worse sheet, it is one that never gets printed.

- **Read live, seeded nowhere** — the deliberate inverse of `CollageTemplate` above. Nothing about a printed sheet is recorded, so there is nothing for a copy to protect and nothing an edit could contradict retroactively: no column anywhere points at the table, delete is unguarded, and editing a template changes only the next print. The seeding pattern exists for a problem this does not have.
- **Millimetres throughout, fractional.** The sheet previously mixed `cm` and `rem`; for something whose purpose is fitting a physical pocket, one print unit beats the convenience, and whole millimetres cannot state 62.5 mm stock.
- **Layout is derived, never configured.** No rows/columns columns exist: the sheet lays cards out with `grid-template-columns: repeat(auto-fill, <cardWidthMm>mm)`, so the browser fits as many per row as the paper allows and A4 and Letter both work without the page knowing the paper size. How many cards there are is the strip's own answer (`start` + `count`); `break-inside: avoid` keeps a card off a page break.
- **One rule between two cards.** Each card draws its border **right and bottom** only and the grid closes **top and left**. `gap: 0` alone is not enough — two neighbours each keeping their own border print a double rule, and a cut down the middle of it leaves ink on both halves.
- **The card carries the ref and nothing else**, pinned to the top by `paddingTopMm`: the rest of it is hidden inside the pocket. There are deliberately no fields for what is printed.
- **Last used is remembered per collection** in localStorage (`LS_LAST_REF_CARD_TEMPLATE`, `add-copy-defaults.ts`' idiom) and carried into the URL, so the sheet stays a plain server render (#330) and a reprinted address states what it was printed on. With no template at all, the built-in `DEFAULT_REF_CARD_GEOMETRY` prints — a constant, not a seeded row.
- Validation is a pure module (`src/lib/ref-card-template-rules.ts`, unit-tested); the server module (`src/lib/ref-card-templates.ts`) is owner-authorized, and a duplicate name is `RefCardTemplateNameTakenError` off `P2002` rather than a generic failed save (`AcceptanceProfile`'s rule, #533).

### Offer photo configuration (#308)

Photo configuration sits on **two levels**, following the `titleTemplate` / `descriptionTemplate` pattern: the platform holds defaults, the offer holds the values it was seeded with.

- **`Contact` (platform).** Hard limits — `maxPhotos`, `maxPhotoEdge`, `maxPhotoFileSizeMib` — all optional (`null` = no limit) and **read live** at render time (#310): they describe what the platform physically accepts, so tightening one applies to every offer at once. Alongside them, the defaults a new offer is seeded from: `photoSides` (`front | back | both`), `tileLabelLeftTemplate` / `tileLabelRightTemplate` (#312, configured as the last two fields of the listing-templates dialog), `photoPreferSingles` (#521) and `defaultCollageTemplateId`.
- **`Offer`.** Its own `photoSides`, `photoPreferSingles` (#521 — whether single-copy sets are photographed alone while the platform's photo limit has room), `photoLabelLeftTemplate` / `photoLabelRightTemplate`, the collage numbers `collageRows` / `collageColumns` / `collageGapPercent` / `collageBackground` / `collageLabelPercent` and the `collageGridMode` that says how the first two are read (#413, null = `fixed`), copied from the platform's default template at creation (`seedPhotoConfig` in `src/lib/offers.ts`, applied by both `createOffer` and `duplicateOffer` — a clone is seeded from the platform it is cloned *onto*). The collage columns are nullable **as a group**: a platform with no default template leaves an offer with no collage until one is picked on it.
- **Why stored, not read.** Changing a platform setting must never silently alter offers already prepared or listed. This matters most for the label templates: a buyer referring to a label on an image already uploaded must keep getting that label after a regeneration (#315). Editing any of these marks the generated photo plan out of date (#311).
- Rules live in `src/lib/offer-photo-config.ts` (Prisma-free, unit-tested): the sides vocabulary, limit parsing, and the all-or-nothing collage group. `updateOfferPhotoConfig` replaces the whole configuration in one write, mirroring the dialog's single save; it is allowed in every offer state, like the listing texts.

### Offer photo plan (#309)

`src/lib/offer-photo-plan.ts` — `planOfferPhotos()` turns an offer's sets, copies, photo configuration and the platform's limits into an **ordered list of planned images**. Pure and Prisma-free like `offer-title-template.ts`, so the server generator (#311) and a client-side preview run identical rules, and it is unit-tested without a database. An offer's photos are a sequence, not "one main image plus extras"; a single image is a 1×1 collage, so there is exactly one rendering path (#310).

- **Grouping.** A multi-copy set gets its own group (split into consecutive groups of its own if it holds more copies than `rows × columns`). Single-copy sets are collected **across set boundaries** and chunked to capacity — a collage of one stamp is pointless. Mixed offers are not a designed-for case, but stay predictable: a run of single-copy sets flushes before the next multi-copy set, so plan order always follows set order (#306), and tile order follows copy order.
- **Single photos first** (#521, `preferSingles` from `Offer.photoPreferSingles`, seeded from `Contact.photoPreferSingles`, on by default). A collage is how more stamps fit than the listing has slots for, so with slots to spare the single-copy pool is spent one image per copy and only the tail is chunked: the largest `k` whose plan fits, where the budget is `maxPhotos` less what the multi-copy groups and the attachments already cost (front/back counted as it actually falls — an incomplete side costs nothing — and a do-not-publish image costing nothing either). No `maxPhotos` means every single-copy set stands alone. `k` is **never zero** while the pool is non-empty: the first image is the marketplace's thumbnail, so the slot is spent even when the budget cannot afford it and `overLimit` reports the overflow. Multi-copy sets are untouched, and the tail's collages are seated at the end of the **last** run of singles, the arithmetic being over the whole pool. Off is exactly the rule above it, which is what an offer prepared before #521 keeps — the migration turns it off for every offer with images already rendered, and the fingerprint hashes it only when on, so the upgrade marks nothing out of date.
- **Front / back.** `photoSides` decides which sides are attempted. A side is rendered **only if every copy in the group has that scan** — all or nothing, no gaps — so a group yields a front/back pair with identical contents (emitted interleaved), or a degenerate group of one image, or none. Nothing may assume a group has two members.
- **Nothing is dropped; two marks decide the upload set** (#313). Every planned image is rendered. `publish: false` is the collector's own do-not-publish mark; `overLimit: true` is derived — among the published images, in plan order, this one falls past `maxPhotos`. Both keep an image out of the numbered upload run and the ZIP, and neither stops it being generated: an image that does not fit today is still one the collector wants to see, and hiding a published image frees its slot so another comes under the limit. The allowance fills **from the front of the plan order**, and nothing is protected — not a front/back pair, not an attachment — because once the order is the collector's, the order *is* the priority order. `plan.uploaded` is the images with neither mark; `overLimitCount` counts the rest.
- An offer with no collage numbers yet plans no collages (`configured: false`); its attachments still appear.
- A side a group cannot produce is returned in `skipped` rather than quietly left out (#314), so the UI can name the copies whose scans are missing.

### Collage renderer (#310)

The only genuinely new mechanism in the image pipeline: `src/lib/collage-layout.ts` (pure geometry, unit-tested on plain numbers) plus `src/lib/photos/collage.ts` (`renderCollage()`, the `sharp` compositing), turning a planned image (#309) into bytes ready to upload.

- **True proportions.** Stamps are scanned, not photographed, so scanner DPI is constant and pixel sizes already carry true relative sizes. Tiles are composited at their **native** size and only the finished canvas is scaled — one shared factor for the whole collage, never per tile or per row. No millimetres anywhere. The upload cap is the one thing that breaks the premise: a scan over `FULL_MAX_EDGE` is *stored* downscaled, so a clamped tile and an unclamped one are no longer on a common scale — a block twice the size of its neighbour would composite the same size. `trueSizeScales` (`src/lib/collage-layout.ts`, pure) repairs it from each tile's recorded original: per-tile shrink `r = originalEdge / storedEdge`, normalised against `max(r)` so every factor lands in `(0, 1]` and the correction is applied by **downscaling** — a clamped tile is never interpolated back up, and the resolution the smaller tiles give up is mostly notional because the canvas is scaled to the platform's limits afterwards anyway. Photos with no recorded original (uploaded before the columns existed) read as un-downscaled and render exactly as they did before.
- **Row-based packing.** Rows hold up to `columns` tiles; a row is as tall as its tallest stamp and tiles are vertically centred in it, with the label strip (#312) reserved below each tile on one shared baseline. Rows are **centred** against the widest row, and `gap` doubles as the outer margin. Justified rows (each row stretched to full width) are rejected: they scale each row differently and would destroy the proportions that are the point of the feature. `rows × columns` is capacity — the canvas shrinks to the actual contents (#307) — and a single stamp is a 1×1 collage, so there is one rendering path. In the template’s `auto` mode (#413) the width is resolved per image by `resolveCollageColumns` before the layout runs; `layOutCollage` still receives one concrete `columns`, so the geometry never learns a mode exists.
- **Output limits** (#308, read live from the platform, each skipped when null): longest edge via `fit: "inside"` — the `FULL_MAX_EDGE` convention from `process.ts` — then the file-size target. The byte target is what `process.ts` cannot do: it encodes once at a fixed quality and never checks the result, which is fine for one small scan. `renderCollage` bisects JPEG quality between `COLLAGE_QUALITY_MIN`/`MAX` and, only when even the floor is too heavy, shrinks the canvas by the measured overshoot and searches again (bounded rounds, floor scale). An unreachable limit returns the best effort with `exceedsFileSizeLimit: true` rather than throwing or looping.
- **Always JPEG.** Collages are photo-like and the quality knob is what makes a byte target reachable at all (PNG has none, WebP is still refused by some marketplaces). Source scans keep their own format; this is the offer-photo output only.
- **Tile labels** (#312, `src/lib/collage-label.ts` — pure, unit-tested): each tile carries **two** annotations, drawn flush left and flush right on the strip the layout reserved, at **one shared font size** so the strip reads as a single line. Two rather than one because what a tile has to say is an identifier the buyer quotes back *and* something descriptive beside it; through one template that is a single long line that then has to shrink. A lone annotation is centred instead. The layer is **one canvas-sized SVG** composited before the output limits, so labels shrink with the stamps rather than growing relative to them. **One font size for the whole collage**, the smallest any tile needed, drawn in two passes (measure every tile, then re-fit the text to the shared size): sized per tile, a narrow stamp beside a wide one carries a visibly smaller label, which reads as a mistake rather than as fitting. Within a strip the two sides share the width **in proportion to their length**, not half each, so a location ref beside a pair of catalog numbers does not squeeze the long side while the short one sits in white space. Below a fraction of the strip's own size the text is **truncated with an ellipsis** rather than shrunk further; ink is black or white by the background's luminance. Every size in the module is a fraction of the strip, which is itself a fraction of the stamp, so nothing depends on the scan resolution. A side with no text is simply not drawn. Drawing SVG text needs a font on the host, so the app image installs DejaVu Sans (see the `Dockerfile`); without one, labels come out as fallback glyphs.
- Stamps coming out small after a downscale is not warned about — picking a collage template suited to the platform is the collector's call.

### Generated offer images (`OfferPhotoGeneration` / `OfferPhotoEntry`, #311)

Where the plan (#309) and the renderer (#310) meet persistence. See [ADR-0018](../decisions/0018-db-queued-in-process-jobs.md) for the queue pattern.

- **Persisted, because the file is the deliverable.** These images are uploaded to a marketplace, so what matters is being able to download the *same bytes* again — the ones a buyer already sees in a live listing, with the labels they may be quoting (#312). Rendering on download would silently produce a different file after any change, so nothing regenerates implicitly: generation is explicit (a **Generate** button), its output is stored, and staleness is only ever *reported*.
- **`OfferPhotoGeneration`** — one row per offer (unique `offerId`), acting as both the queue entry and the state the UI polls: `status` (`queued | running | ready | failed`), `fingerprint`, `plannedCount` / `renderedCount`, `error`, `queuedAt` / `startedAt` / `finishedAt`. Enqueuing an offer that already has a queued or running run is a **no-op**, so a double click renders once.
- **`OfferPhotoEntry`** — the thin plan metadata pointing at each generated `Photo` (unique `photoId`): `sortOrder` (upload order), `source` (`collage` for a group, `copy_photo` / `upload` / `manual_collage` for a manual attachment, #313/#331 — `manual_collage` rather than `collage`, since in this vocabulary a plain collage is one the rules derived), `side`, `pairKey` (the front/back pair), `setIds`, `itemIds`. Plan metadata does not belong on `Photo`, which describes a *file*. `setIds` / `itemIds` are plain arrays, not FKs: one group can cover several single-copy sets, and the plan is a snapshot — a set removed afterwards is staleness, not a referential error. `itemIds` exists because `setIds` cannot answer "what is in this image" on its own (#314): a set larger than the collage's capacity is split into several groups that all name it.
- **Staleness** (`src/lib/offer-photo-fingerprint.ts`, pure + unit-tested): a sha256 over composition and *effective* order (#306), source photo ids, the offer's photo configuration (#308) and the platform's live limits, plus a hand-bumped `FINGERPRINT_VERSION` for when the renderer's own output changes. Hand-confirming an order catalog order already produced does **not** change it. Compared against the fingerprint stored by the last successful run to mark a plan **out of date** — a signal, never a trigger.
- **Replacement, not patching** (`runOfferPhotoGeneration`): the whole plan is rendered first, then swapped in one transaction — new `Photo` + entry rows in, the previous generated rows out, displaced bytes deleted post-commit. A failed run therefore leaves the previous images intact, and every image is a new `Photo` id, so the immutable-bytes-per-key assumption behind the serving route's cache headers holds.
- **Worker** (`src/lib/offer-photo-worker.ts`): started from `src/instrumentation.ts` `register()` beside the photo GC; requeues rows left `running` by a restart (a render is a full replacement, so repeating one is safe), then polls every 5s, **one job at a time** because rendering is CPU-bound through `sharp`. `kickOfferPhotoWorker()` nudges it right after an enqueue so Generate feels immediate; the poll is what guarantees the job runs. Worker state is pinned to `globalThis` like the Prisma/GCS clients, so `next dev` hot reloads cannot stack a second interval.
- **Surfaces**: `generateOfferPhotosAction` (enqueue + kick) and `GET /api/collections/[collectionId]/offers/[offerId]/photos` (state + stored images + what a Generate would produce now), polled by the Photos card on offer detail while a run is in flight. Bytes reuse the shared photo-serving route unchanged.
- **Tile labels** (#312): `readInputs` resolves the offer's two label templates **once per copy** through the title-template engine (`renderTitleTemplate` over a single copy, in the platform's listing language), and hands both texts to the renderer with that copy's tile. Per copy, not per group — a token resolved across a collage's copies would render the same joined value under every stamp, which is the opposite of identifying one of them. Usually `{ref}`, the copy's location ref, so the label is derived from the copy's own data and survives regeneration without renumbering, gaps or plan versioning. A blank template leaves that side undrawn; a copy with no value for either template's tokens gets an unlabelled tile, with no special-casing. Duplicate `locationRef` values inside one offer are possible and deliberately not handled.
- **Labels are fingerprinted as rendered text**, not as a template: the label is drawn into the pixels, so editing a copy's location ref changes the images exactly as replacing its scan does and must read as out of date for the same reason.

### Manual photo attachments (`OfferPhotoAttachment`, #313, #331)

Not everything a listing needs is derivable from the composition. An attachment is a plan entry the collector adds **by hand**, in one of three modes, and it is a *plan* row rather than a photo row precisely so a regeneration (#315) can recompute the derived images and leave these alone.

- **`copy_photo`** — a **specific** photo of a copy already in the offer (front, back, or an extra), so a perforation, a flaw or a cancel can be shown on its own. Guarded on creation: the copy must be in one of the offer's sets and own that photo. Its tile annotation resolves from that copy as usual, so a detail shot carries the same ref as that copy's tile in a collage.
- **`upload`** — an arbitrary image uploaded to the offer, promoted from the owner-agnostic `PhotoUpload` staging (#112) into an offer-owned `Photo` with `kind = original`. Rendering resolves the label templates against **no copy at all**: inventory tokens come out empty (the engine tidies the separators they leave) and only literal text survives. The offer owns both the original and the image generated from it, so purging generated bytes later leaves the original intact.
- **`manual_collage`** (#331) — several **chosen** photos, copy scans and offer uploads mixed freely, composited into one image at a column count the collector picks. This is the grouping the rules cannot produce: they group by set composition (#309), and what a listing wants to show sometimes cuts across that. Its images are `OfferPhotoAttachmentTile` rows (`sortOrder`, per-tile `source` / `photoId` / `itemId`) and its own `photoId` is null; a per-mode CHECK in the migration keeps the three shapes honest. **Rows are not stored** — a template's rows × columns is a *capacity* the plan fills, whereas here the contents are explicit, so only the width is an open question and the row count follows. Editing what one shows is not offered: remove and rebuild.
- **Never a pass-through, and one shape for all three.** Every attachment is "N tiles in C columns" rendered through `renderTiles` with the offer's own gap, strip, background and output limits — the single-image modes being N = C = 1, which is what they always were. That keeps "no image is ever unlabelled" (#312) true without a second code path, and is why #331 needed no new plan concept: `PlanAttachment` / `PlannedAttachment` simply carry `tiles` and `columns`. An offer with no collage numbers therefore still cannot generate, attachments or not.
- **Identity survives edits.** An attachment's plan token is `a:<attachmentId>` — unlike a collage side's `c:<side>:<itemIds>` it does not describe the contents, so a hand-built collage keeps its place in the plan order whatever it shows.
- **Append, then reorder.** A new attachment lands at the end of the plan (`sortOrder` past the last planned image, which the engine clamps); from there it is dragged. Its *position* is not stored on the attachment, though — see the plan order below. An attachment gets no special treatment under the platform's photo limit either: like every other image it is in the upload set or over the limit according to where the collector put it.
- **Bytes.** Removing an `upload` attachment deletes its `Photo` row and bytes; a `copy_photo` only ever pointed at the copy's own scan. A `manual_collage` applies the same rule tile by tile — which is why each tile records its own `source` — so its uploads go and its borrowed scans stay. `photoId` cascades: deleting the copy's scan removes the attachment from future plans while the image already generated from it survives — which is the staleness the fingerprint reports, not a referential error.
- **Batch.** The dialog attaches several at once (`attachOfferCopyPhotos` / `attachOfferUploads` / `attachOfferPhotoCollage`), validated up front — and, for uploads, moved into place up front — so a bad pick fails the whole batch rather than half-attaching. Its **Combine into one collage** tick turns the two tabs into a single selection, because a hand-built collage exists precisely to mix them.
- **Surfaces**: `src/lib/offer-photo-attachments.ts` (owner-checked domain), the `attachOffer*` / `removeOfferPhotoAttachment` actions, and the Photos card's **Plan** list (`getOfferPhotoPlanState().plan.images`). The plan list exists as its own surface because it shows entries that are not files yet — an attachment's position among *planned* groups is not something a list of stored images could show.

### Manual plan order and publishing (`Offer.photoPlanOrder` / `photoPlanUnpublished`, #313)

The generated collages had no order of their own — their sequence came from the set order (#306) and the grouping. The collector can now drag the **whole** plan, collages and attachments alike, into an order that is theirs, and hold individual images back from the upload. Both are keyed by the same **plan token**, which is also written on each stored image (`OfferPhotoEntry.token`) so a rendered file can be matched back to the entry it was rendered for.

- **Stored as tokens, not positions.** `Offer.photoPlanOrder` is a `String[]` of one stable token per planned image — `c:<side>:<sortedItemIds>` for a collage side, `a:<attachmentId>` for an attachment (`collageToken` / `attachmentToken` in the pure engine). A token identifies an image by *what it shows*, so it survives the thing a positional index cannot: a set reordered elsewhere, a copy added, a regeneration.
- **An override, reconciled at read time** (`applyManualOrder`, pure + unit-tested). The engine still derives the grouping and the natural order; this list then re-seats the images it names. A token the offer no longer contains is ignored (a sold-out collage leaves no gap); an image the list does not name (added since the last reorder) sorts **just after its natural predecessor**, so a new collage or attachment lands where the derivation put it rather than at the end. Empty (the default, and every existing offer's backfill) means the derived order, unchanged — so an offer never reordered behaves exactly as before, and `setOfferPhotoPlanOrder([])` clears the override.
- **Every drag stores the full sequence.** The card sends all tokens in their new order, so the override is total and the derived order cannot creep back in for the images left untouched.
- **Applied to the stored images, not just to the plan.** `setOfferPhotoPlanOrder` renumbers the offer's entries (`sortOrder`) into the resolved order, so the plan, the stored-files list, the upload numbering and the ZIP can never disagree. Only `sortOrder` moves — no bytes, no ids — which is why either list can be the drag surface and why a reorder is **not** a reason to regenerate.
- **Do not publish** (`photoPlanUnpublished`, `setOfferPhotoPublish`). A token list for the same reason the order is one: a generated collage has no row of its own, and unlike an attachment it cannot be removed. The image stays rendered and downloadable; it only leaves the upload set, which frees its slot under `maxPhotos` — hence the entries are renumbered after a toggle too. The card offers it on collages only, since an attachment has a delete.
- **Numbering.** Upload names (`01.jpg`…) are assigned over the **upload set** alone, so the ZIP is a gapless `1..n`; held-back images get `unpublished-NN` / `over-limit-NN`, which cannot be mistaken for a slot in the listing.
- **Fingerprint.** The order is deliberately **not** hashed — it is applied to the stored images, so it can never leave them stale. What is hashed is the **set** of rendered tokens, and only when the offer carries a manual order or a do-not-publish mark: those are the only things that can change which images exist without changing the composition or the limits, which are hashed already. An offer using neither keeps the hash it had before any of this existed.

### Sold sets leave the plan (#315)

When a copy sells, the collages of every offer still holding it advertise something that cannot be bought. `readInputs` (`offer-photo-generation.ts`) therefore drops the affected sets from the plan's inputs before the engine sees them — the plan, the fingerprint and the renderer all read the offer as *what is still sellable*.

- **The unit is the whole set.** An `OfferSet` sells together and indivisibly, so a series missing one stamp is not sellable anyway; one gone copy condemns its set. `excludedSetsFor` is one batched lookup mirroring the "needs action" derivation (ADR-0013 §4): the set has its own sale line (a partial sale of a multi-set offer), one of its copies sold through another offer's set, or one of its copies is held by another active offer **in active bidding** (#215).
- **No new state, no new trigger.** Composition is already what the fingerprint hashes, so a sale marks the stored images **out of date** by itself; nothing regenerates implicitly, exactly as with every other change. The stored images keep showing the sold set until the collector presses Regenerate — they may be live in a listing.
- **Only derived entries are recomputed.** Manual attachments (#313) are plan rows precisely because a rule cannot reproduce them; a regeneration renders them again untouched, including one pointing at a copy in a sold set. Labels are unaffected too: they derive from each copy's own data (#312), so the remaining stamps keep the labels a buyer may already be quoting.
- **Terminal offers are exempt** (`sold` / `withdrawn`): their images document a listing that is over, and recomputing them against an empty composition would only declare them permanently stale.
- **Surfaced, not silent.** `plan.excludedSets` (set id, label, `sold` | `bidding`) rides along in the panel state, so the card can say which sets left the plan and why — a collage that is no longer planned looks exactly like one nobody asked for.

### Getting the files out (#314)

Delivery is a **manual upload** — there is no Delcampe API (#154 is an open scoping question) — so the deliverable is a correctly ordered set of ready-to-upload files. The Photos card sits under the listing texts on offer detail and expands in place (no dialog, no route of its own) into the plan in upload order: each image with what it was rendered from, a lightbox, a per-image download, and a whole-plan ZIP.

- **Collapsed by default, one toggle.** Expanded the card is the tallest thing on the screen, and generating is a step taken once a listing is otherwise ready. Collapsing therefore hides *detail only*: the run's state, `outOfDate` and a skipped-side count stay in the header as chips, and Generate / Download all stay pressable. There is no second toggle inside — expanded means the whole plan.

- **Numbering** is ours, not the platform's: files are `01.jpg`, `02.jpg`… by plan position, because plain numbers sort into upload order in any file manager. Drift between our number and the position a listing ended up with is deliberately **not** defended against — labels (#312) identify copies independently of image position.
- **`src/lib/zip.ts`** — a dependency-free, deterministic ZIP writer, deflating only when that actually shrinks a payload (collages are already-compressed JPEG, so in practice they are stored verbatim). Same reasoning as `extension/archive.mjs`, which is kept separate: that one is a build script outside the app's module graph. No ZIP64; a plan is bounded by the platform's own photo-count and file-size limits.
- **`buildOfferPhotoArchive`** reads the stored bytes and zips them in plan order, served by `GET .../offers/[offerId]/photos/zip` with a `Content-Disposition` named after the offer. Buffered, not streamed — the archive is a handful of megabytes and a stream would hold the same central directory anyway. Nothing is re-rendered on download, so an archive pulled twice from unchanged images is byte-identical.
- **Skipped sides are reported, not omitted.** `planOfferPhotos` returns `skipped` (side, group, the copies with no scan for it) alongside the images, and the card shows it whether or not the preview is expanded: a set of eight losing its back collage over one missing reverse scan is invisible otherwise. A group the photo-count limit dropped outright is *not* reported twice — the drop count already says it.

## CI

The `ci.yml` GitHub Actions workflow runs three jobs on every push and pull request:

- **static-checks** — lint, typecheck, build (generates Prisma client first)
- **unit** — unit tests (generates Prisma client first)
- **integration** — spins up a PostgreSQL 16 service container, applies migrations via `prisma migrate deploy`, then runs `tests/integration/`

The **publish-image** job triggers only on `v*` tags and requires all three jobs to pass. It pushes a multi-arch image (`linux/amd64`, `linux/arm64`) to `ghcr.io/michalwy/stamporama`.

## Authentication

Stamporama uses [Better Auth](https://better-auth.com/) with the email/password provider.

**Server instance:** `src/lib/auth.ts` — initializes Better Auth with the Prisma adapter (sharing the `prisma` singleton from `src/lib/db.ts`) and the email/password provider.

**Client instance:** `src/lib/auth-client.ts` — `createAuthClient()` for use in client components. Defaults to the same origin (`/api/auth/*`); no explicit `baseURL` required.

**API handler:** `src/app/api/auth/[...all]/route.ts` — catches all Better Auth API requests (`GET` + `POST`) via `toNextJsHandler(auth)`.

**Middleware:** `src/middleware.ts` — protects `/c/*` (collection routes) and `/collections` (collection picker). Runs on the Next.js Edge runtime; calls `/api/auth/get-session` via native `fetch` to avoid importing Node.js-only modules in Edge context. Unauthenticated requests are redirected to `/sign-in`.

**Prisma schema:** Better Auth manages four tables — `user`, `session`, `account`, `verification` — added in migration `20260714190000_add_better_auth_schema`.

**Session check in Server Components:** call `auth.api.getSession({ headers: await headers() })` directly (Node.js runtime, safe outside middleware).

| `STAMPORAMA_SCAN_SHEET_TTL_DAYS` | no | The **instance default** for how long a batch that has been finished with keeps its retained card scans before the sweep deletes them (#578; default `off`). Same grammar as the row above — `0` sweeps at the next pass, `off` / `never` keeps for ever — and a collection may set its own period in Settings → General. Defaults to keeping, because a scan is a source and a broken-up stockbook cannot be scanned again |
| `STAMPORAMA_SECRET_KEY` | when connecting Allegro | Encrypts third-party credentials at rest — the Allegro client secret and OAuth tokens (#476; ADR-0023). Generate with `openssl rand -base64 32`. Changing it invalidates every stored connection |
