# Agent Instructions

This project is intentionally vibe-coded. Future agents must preserve product intent, avoid invented requirements, and ask clarifying questions when the next step is not clear.

## Product Context

- Product name: Stamporama
- Purpose: a self-hosted web app for stamp collectors
- Desktop browsers only; no mobile layouts or breakpoints.
- Core concept: **collection** — the top-level organizing unit that scopes all stamp data for a user

## Working Rules

- Do not assume domain behavior. Ask before defining catalog standards, condition scales, trade workflows, auction integration behavior, or pricing logic. Ask one question at a time.
- Do not add user-facing functionality unless the current task explicitly asks for it.
- Prefer small, reversible changes with clear documentation.
- When changing user-visible behavior, update `docs/user-guide/` in the same task.
- When changing behavior, data model, setup flow, or architecture assumptions, update every affected document (`README.md`, `docs/product/brief.md`, `docs/architecture/overview.md`, relevant ADRs, `docs/user-guide/`).
- When introducing a framework, library, or major pattern, add or update an ADR in `docs/decisions/`.
- Update this `AGENTS.md` file when new project knowledge or workflow rules would help future agents.
- Favor boring, well-supported tools over novelty. Preserve existing user changes.
- Use GitHub Issues as the shared backlog. Use Conventional Commits for issue titles. Always assign labels (`backlog` + type + priority when known). Do not maintain a local `TODO.md`.
- If GitHub connector cannot create issues, use `gh` CLI as fallback.
- All GitHub content must be in English.
- Do not create git commits unless the user explicitly asks. Do not push unless explicitly asked.
- Solo project: commit directly to `main` by default. Create feature branches only when the user asks for a PR.
- When pushing to `main`, try `git push origin main` first. If rejected, fetch, rebase, rerun verification, push again.
- Use Conventional Commits: `feat:`, `fix:`, `docs:`, etc. Include GitHub issue reference when one exists.
- When a commit title alone would omit useful context, include an extended commit message body.
- Use a separate git worktree only when the user explicitly asks for one.

## Multi-Step Implementation Plans

When a task spans more than one logical area, write an implementation plan before starting. Store it under `.claude/plans/`. A plan is executed fully within a single session.

- Begin with a `## Progress` section containing a checkbox list of numbered steps.
- Steps are executed in order. Mark each step `[x]` immediately after completing it.
- Each step must state a **Done when** criterion.

## Agent Collaboration

Use specialized roles only when the task benefits from them. Small, localized tasks can be handled by one agent.

Use specialized roles for larger changes that cross domain, data, authorization, or user-flow boundaries:

- Architect: schema, ADRs, major patterns.
- Designer: UI flows, dialogs, interaction design.
- Developer: scoped implementation.
- Tester/Reviewer: browser flows, regressions.

Prefer Architect before changing Prisma schema, permissions, collection scoping, authentication, routing, or ADR-documented patterns. Prefer Tester/Reviewer after changing forms, dialogs, collection routing, authentication, permissions, or migrations.

## Technical Direction

- Collection-scoped access control: `collectionId` on data, owner has full access, checks live server-side.
- Collection URLs: `/c/[collectionSlug]/...`; slug resolution authorizes by internal `collectionId`.
- Better Auth for authentication.
- Prisma with PostgreSQL (minimum **version 15** — migrations use `NULLS NOT DISTINCT`; see ADR-0006). Treat schema changes as product decisions.
- SPA-like collection interaction: Next.js App Router as route/auth shell, client-side queries/mutations for rich screens.
- TanStack Query for data fetching, TanStack Table for list views.
- Cursor-backed infinite scrolling for large lists via shared primitives.
- Keep domain logic out of UI components. Keep authorization server-side.
- Explicit module boundaries under `src/`.
- Self-hosted deployment: CI pushes multi-arch image to `ghcr.io/michalwy/stamporama` for release tags only. `docker-compose.prod.yml` + `.env` for production. `scripts/install.sh` is the curl-able installer. Version baked via `STAMPORAMA_VERSION` build arg, shown through `getAppVersion()` in `src/lib/version.ts`.
- Browser extension (Stamporama Assistant, #253; ADR-0015) lives in `extension/` — a separate pnpm-workspace package (MV3, esbuild + hand-written `manifest.json`, own `tsconfig`). It is **excluded from the app's** `pnpm lint`/`typecheck`; build and check it on its own with `cd extension && pnpm build|typecheck`. It calls the Colnect matcher endpoints with an `AssistantToken` bearer (session-or-token auth via `src/lib/route-auth.ts`), because the extension reaches us cross-site from colnect.com. Its match window groups results and hides the decisions the collector has effectively already taken (#305): a `needs-confirm` row every candidate of which already carries some Colnect ID — the matcher never silently overwrites (#250), so those rows return on every re-scan. One free candidate keeps the row, since that free stamp is most likely the answer (`isAlreadyLinkedElsewhere` in `core/decisions.ts`). The reveal control lives in the toolbar row, not the section heading: with every such row hidden the section is gone and would take the only way back with it. Tokens are obtained by **self-registration** (#252): Settings → Assistant exposes a one-time code + the instance's own origin on the page, and a toolbar-icon click exchanges it at `POST /api/assistant/register` (`src/lib/assistant-registration.ts`).
- Assistant **distribution** (#288; ADR-0017, superseding ADR-0016) — published to an **unlisted Chrome Web Store listing**; the store assigns the ID and signs, so there is no CRX, no signing key and nothing served by the instance. `extension/pack.mjs` (`pnpm assistant:zip` from the root) writes a store ZIP with the app version stamped in; CI's `publish-extension` job uploads and publishes it per release tag (`CWS_CLIENT_ID`/`CWS_CLIENT_SECRET`/`CWS_REFRESH_TOKEN` secrets, `CWS_PUBLISHER_ID`/`CWS_EXTENSION_ID` variables), but only when `extension/` changed since the release the **store** already holds — asked for with `:fetchStatus`, taking the newer of the published and in-review revision, so a submission that failed or was paused is picked up by the next release rather than lost. The store's `uploadState` is `SUCCEEDED` on this API (v1.1's `SUCCESS` is accepted too); the job is also dispatchable on a tag, so a refused submission is retried without moving it. Self-hosted force-install was tried and fails: Chrome honours a non-store `update_url` only on an enterprise-managed machine. The unpacked dev build and the store build stay **two extensions** with two IDs (`extension/identity.mjs`; `manifest.json` carries no `key`), so both can live in one browser and a dev profile can never reach a production collection.
- Binary assets (photos, #112) sit behind the `src/lib/storage/` interface (filesystem + GCS, #138; ADR-0011; active write backend via `STAMPORAMA_STORAGE_BACKEND`, per-photo reads) — async/streaming, `resolveUrl` returns stream-or-redirect, write-one/read-many by per-row `storageBackend`. Bytes live under `STAMPORAMA_DATA_DIR` (the `stamporama-data` volume), never in `public/`; serve them through collection-scoped route handlers. Multipart uploads use route handlers, not server actions. `Photo` is polymorphic over **three** owners — `Item`, `Stamp`, `Offer` (#311, generated listing images, `kind = generated`; #313, images uploaded straight to an offer for a manual attachment, `kind = original`) — with a `num_nonnulls(...) = 1` CHECK; deleting any owner must delete the bytes explicitly (the cascade only drops rows). An offer's photo plan is part rule-derived and part manual: `OfferPhotoAttachment` (#313) is the *plan entry* that carries the distinction, so a regeneration recomputes the collages and leaves the attachments alone (#315). An attachment is **N tiles in C columns** — `copy_photo` and `upload` being N = C = 1, and `manual_collage` (#331) the collector's own selection (`OfferPhotoAttachmentTile`, mixing copy scans and offer uploads) at a width they pick, rows never stored because the contents are explicit. In the plan's vocabulary a plain `collage` is always one the rules derived, hence `manual_collage` for the hand-built one. Sets that have gone — sold here, sold from under the offer, or held by an offer in active bidding — are dropped from the plan's inputs in `readInputs` (whole sets, never single copies), which marks the stored images out of date through the fingerprint alone; terminal offers are exempt. Attachments render through the same one-tile collage path as everything else — there is no unlabelled pass-through (#312). A tile caption is sized from the **label strip alone** and never from its own text (#337): sizing to the text made one image carry a full-height label and the next a visibly smaller one. Text that does not fit the tile's width is truncated with an ellipsis, and a *shorter* strip is what makes more of it fit. The strip itself is `labelPercent` of the **finished image's longest edge** — not of the stamp, which is what the gap still uses: every image of a listing is scaled to the same platform limit, so only a share of the image renders at one size across a collage, a single scan and a wide detail crop. It is therefore circular (the strip grows the canvas it is a share of) and `collage-layout.ts` solves for it, capping all the strips together at half the page so a many-row collage stays solvable. The column is a **float**: against the whole image the usable band is about one to two percent and a whole number cannot land inside it. The **upload order** over the whole plan (collages and attachments) is the collector's to set: `Offer.photoPlanOrder` is a `String[]` of stable per-image tokens (`c:<side>:<sortedItemIds>` / `a:<attachmentId>`, also written on each stored `OfferPhotoEntry.token`), an *override* the pure engine reconciles against the derived order at read time — so a manual order survives a composition change or regeneration. A reorder is **applied to the stored images** (their entries are renumbered; bytes untouched), so either list can be the drag surface and reordering never marks anything out of date. **Nothing is ever dropped from the plan**: an image the collector marked do-not-publish (`Offer.photoPlanUnpublished`) or one past the platform's `maxPhotos` is still rendered and shown, just kept out of the numbered upload run and the ZIP — and the limit fills from the front of the order, protecting nothing, because the order is the priority order.
- The **bulk listing workspace** (#322) is a *sub-route* of Offers (`offers/listing/`), not a nav page: posting a prepared batch is a step in the offer lifecycle, and the static segment takes precedence over `[offerId]`. It is scoped to one **platform** and to `ready` offers, reads its batch through one unpaginated route handler (`offers/listing`), and does grouping, filtering and year facets **client-side** from pure helpers in `src/lib/listing-groups.ts` (unit-tested) — a `ready` batch is bounded by what a person is about to type in by hand, and instant facets beat a page boundary. The per-offer posting kit (texts, photos) is loaded **on expand** through the existing `useOfferDetail` / `useOfferPhotoPlan` endpoints, so a forty-offer batch does not fetch forty descriptions to draw forty collapsed lines. Grouping and filtering are deliberately **different questions**: an offer is *grouped* under the `(area, year)` pair every copy shares (else **Mixed**, which the area rail carries as its own entry via `AreaFilterSidebar`'s `extraEntry`), but it *matches* an area filter when every copy is inside that subtree — so a year-spanning offer is Mixed yet still appears under its area. A copy's area is its stamp's **primary** area link and its year is `stamp.issuedYear`, matching the inventory list (#142). Publishing goes through `publishOffer`, which transitions first and writes the URL after, so a refused publication leaves no listing URL behind. Which card is open is **derived, not stored** — a tri-state (`undefined` = nothing chosen for this batch yet → open the first; `null` = the collector shut it → honour that; an id → that card), so the first offer opens on arrival and after any batch change without a `setState`-in-effect. Publishing resolves its successor *before* the mutation, while the published offer is still in the list, and falls back to `undefined` when it was the last. Its **batch photo actions** (#323) act on the *visible* offers, never on the whole platform's ready set — the filters are how a session is scoped. Regeneration is `enqueueOfferPhotoGeneration` per offer, so #315's sold-set exclusion and the idempotent queue are inherited rather than re-decided; a per-offer refusal is **collected, not thrown** (`generateOffersPhotosAction` returns `{ queued, skipped[] }`), because one unrenderable offer is no reason to abandon the other twenty-nine, and the listing query polls while any offer is `queued`/`running` because the per-offer plan poll only covers the card that happens to be open. The batch **archive** (`buildOffersPhotoArchive`) is a folder per offer over the same per-offer upload set the single ZIP uses, so a file unpacked from either is identical and identically named (#326); namesake offers get their id appended rather than merging two listings' uploads into one folder. It is a **POST** (`offers/photos/zip`, another static segment ahead of `[offerId]`) with the batch in the body and a client-driven blob download, because forty ids in a query string is a URL-length gamble; it is buffered like the single-offer one and therefore capped, past which the honest answer is to narrow the session.
- A platform's **default offer price** (#362) is the *lowest-priority* price suggestion: a new offer takes `Contact.defaultOfferPrice` only when the lot's suggested price (#190) and the copies' catalog value (#230) — both of which reach the form as a filled-in figure — had nothing to say. It carries **no currency of its own**: the platform already locks one (#196), and a second one could only disagree with it. The fallback lives in `createOffer`, resolved *before* the live-status checks so a `ready` offer on a flat-price platform is not rejected as unpriced — the server is the single point that applies it, because a plain create does not even show the price field. The form pre-fills it too, but only where the field is shown and untouched, so what the collector sees is what the server would have written. Read at creation and never again: unlike the listing templates and photo defaults it is not *seeded* onto anything, since the offer's own `price` is the record.
- A listing **title** (#209/#210) is *stored*, and the derived label (`offerLabel`) is only what a surface falls back to while `Offer.name` is null. It is generated at creation — but an offer created **empty** renders over no copies, so `backfillOfferTitle` fills it in on the first mutation that adds copies (`addOfferSet`, `addOfferSetsPerCopy`, `addItemToOfferSet`; #365), and only while the field is still null. Growing a listing never rewrites a title it already has: that is what ↻ Regenerate is for. Without this the detail header looked right and everything reading the stored value — the copy control (#327), the bulk listing workspace (#322) — got nothing. Editing the title likewise seeds the input from what is *displayed*, derived label included (#363); `InlineText` only commits a changed draft, so opening and closing the editor still stores nothing. In generated titles, catalog numbers collapse on **both** of #150's axes (`compactCatalogNumbers`): consecutive bases within a prefix+suffix family (`BL31-33`, `40-42A`), then — over what stayed single — consecutive suffixes on one base (`BL92a-b`, `12I-III`; #364, via `parseSuffixOrdinal`). A span that already collapsed a base run is never folded by suffix: `31-32a` + `31-32b` are two runs, and joining them would claim a span the offer does not list.
- A listing **description** (#266) carries a **format** — `plain | html | markdown` (#319; ADR-0019). It is configured on the platform next to the description template it applies to, and **seeded** onto each offer (`Offer.descriptionFormat`), so changing the platform never re-reads a listing already written. Rendering goes `descriptionToUnsafeHtml` (`src/lib/description-format.ts`, pure, DOM-free, unit-tested) → **DOMPurify** in `shared/rendered-description.tsx`; never inject the unsanitised HTML anywhere else. The same sanitised markup is what the copy control puts on `text/html` (with the source on `text/plain`) when copying formatted. The private note (#267) has no format.
- **Auction tracking** (#23; ADR-0021, schema in #350) is a *bidding watchlist with a fork at the end*, not a register of market results fed from outside — the market data is a by-product of losing. `AuctionSale ⊃ AuctionLot ⊃ AuctionLotLine`. The parent is **one settlement with one seller** — what ships in one parcel — never "an auction as an event": a house's own sale for a house, an open-ended basket of everything currently bid on with one seller for a marketplace. That definition is load-bearing, because it makes shipping distribution fall out of ADR-0009 §3 for free (the grouping is made at bidding time, so settlement never asks "which purchase does this go into?") and it is what lets the sale-level rollup add shipping **once**. Seller and platform are two `Contact`s exactly as on `Purchase`, both `Restrict`. Currency and the two fee components live on the **seller** and are **seeded** onto the sale — the #308/#319 seeding rule again, so a seller raising their premium cannot re-price a parcel already tracked or settled — and `platformCurrency` (#196) does not apply, because an aggregator like philasearch carries houses listing in EUR, CHF and GBP alike. Outcome is **per lot, never per sale**: within one settlement some lots are won and others lost. The bid is a single overwritten figure with `checkedAt` and **no history** — refreshing is manual (no scraping, no scheduled polling), so `checkedAt` answers the one question a history would; `finalPrice` stays optional, because a lot that vanished from view is an absent observation rather than an error. **Recording the outcome** (#354, `recordAuctionLotOutcome`) is `won` / `lost` / `cancelled` / back to `watching` from the row's ⋮ menu. The two priced outcomes share one dialog and differ in exactly one rule: a lost lot's price is **optional** (an unseen result is an absent observation) and a won lot's is **required** (you cannot have missed what you paid, and #28 prices its purchase line from it — a `won` lot is also the input that action operates on, so it must be reachable here). Marking won stops at status + price and writes **no** `Purchase`: a parcel settles as a whole, once, when the seller invoices it. It does immediately sharpen the sale rollup, which costs `won`/`watching` lots at `finalPrice ?? currentBid`. Marking lost freezes `AuctionLot.fxRateToBase` the way `Purchase` does at `purchasedAt` (ADR-0009 §4, #20), and **only when a price was recorded**: a rate exists to convert a figure, so null covers base-currency, no-rate and no-result alike. Nothing is inferred into the price — the last observed bid is a lower bound, so the field opens blank and blank is a valid answer — and `cancelled` clears price and rate, as does reopening, since neither carries a datapoint. Once a result exists the row renders it in place of the bid: it is what the lot went for, and it is already what `allIn` is computed from. Composition is structured (`stamp × condition × certificate × format × quantity` — the shape a catalogue price is keyed on; the certificate arrived with #353, null = none as on a copy, because a house lot sold with a Fotoattest is worth a different figure and matching is strict) because free text makes catalogue value uncomputable and a lost lot unusable, and it **reuses** the unknown-variant rollup (#238) and format pricing (ADR-0020) rather than re-deciding them — literally, through the exported `valuateItemRows` (`items.ts`), which values a `stamp × condition × certificate × format` row of which a copy is one instance and a lot line another at a **null certificate** (a lot is described before it is owned). `auction-lines.ts` calls it **once per page of lots**, so the factor table and area tree load once. Catalogue value pivots **base currency → the sale's**, converted once per sale currency, because the bid, premium and ceiling are all denominated there; a missing rate makes a line **unconvertible**, which is not *unpriced* — it has a value that cannot be counted, and calling it unpriced would send the collector to enter a figure that already exists. A composition entered but unpriced is `null`, never `0.00`: a zero makes every headroom read as a catastrophic overbid. Unpriced/unconvertible lines are **counted beside the total**, never dropped. A **row's** headroom excludes shipping (premium only, exactly as `allIn` does) and the **sale's** includes it once. The price slot carries the shared quick-price dialog (#228/#341) over a `QuickPriceSubject`, which a lot line satisfies structurally. Composition has **two surfaces, deliberately**: on the **sale's own screen** each lot is a collapsible **card over its lines**, the purchase-order intake / offer-detail layout (#121/#165) — same `LotIssueGroupHeader`, same *Group by* / *Only* / *Sort* toolbar persisted through `lot-view-prefs`, and the watchlist row itself as the card header so a bid is still refreshed in place; on the **flat watchlist** the same list opens as a dialog off the row. The split follows the question each screen asks — "what do I bid on next", across sellers, versus "what am I actually paying for", within one parcel — and is the same one the offers list has with an offer's own screen. Only the sale detail carries the lines (`AuctionLotDetailItem`); the flat list would otherwise fetch forty compositions to draw forty collapsed rows, and its row only needs the total. Entering a line is **two modals**, the purchase intake's flow (#121): `StampPickerBrowser`, then `AuctionLotLineDialog` for condition / certificate / format / quantity, with the pick restated and a ← Back. Two sources, two questions — the catalogue tree answers the first, the listing text the second. The dialog **portals to `<body>`** (it is opened from inside other dialogs, whose transform-centred panels would otherwise be the containing block for its `position: fixed`), and pre-fills condition + certificate from `LS_LAST_CONDITION`/`LS_LAST_CERT` — the same remembered pair every add-copy entry point uses. Going through `StampPickerBrowser` directly (not `StampSelect`) is also what gives the purchase intake's **whole-issue** pick: a series expands — in the *action* layer, `resolveAuctionLineStamps` — into one line per member `requiredForCompleteness`, because a house lot is routinely "Mi 1–12 complete" and twelve trips through the picker is why it would go undescribed. The issue is an **entry shortcut only**; a stored line is always one stamp, since catalogue value sums per stamp and a lost lot must be attributable per stamp. Editing offers stamps alone — one line becoming twelve is not an edit. The remaining fields do not render until something is picked — a line *is* a stamp at a condition, and four greyed-out selects is a form pretending to be busy. **Add lot** carries the same composition section and `createAuctionLot` writes lot + lines in one nested create, every line validated first so a refusal leaves no half-entered lot. A lot card on the sale screen passes `showParties={false}`: a sale is one settlement with one seller, so both are fixed and the header states them. A lot with no `title` is **named after its composition** (`deriveAuctionLotLabel`, pure in `auction-rules.ts`): collapsed catalogue numbers **with their prefix** (`Mi·PL 1-12`) — through the listing engine's own `compactCatalogNumbers`, now exported, since two implementations of #150's collapsing would drift. The prefix rides *inside* the collapsing (it is just the numbering family's constant part), so it is written once around a span and a lot spanning two areas stays honest as `Mi·PL 1-3,Mi·DE 5`. Resolved server-side through the same pure `buildAreaVendorMaps` + `formatStampCN` the client renders chips with, over `readCollectionAreas` — `getCollectionAreas` minus the ownership check, split out rather than threading an `ownerId` into modules with no other use for one — then the issue when the lines share one, and a mixed lot reads as its size (`14 stamps · 3 issues`) because a name is scanned, not studied. **Derived on every read, never stored**, unlike an offer's title (#209/#365): a lot name is never published anywhere, and a lot is described line by line, so a stored value would freeze on the first stamp. It outranks `Lot {lotNo}` in `lotLabel` — the number is already its own chip and says only where the lot sits in someone else's catalogue. `AuctionLotLineItem.catalogNumbers` is ordered **primary vendor first** (`buildPrimaryVendorByAreaMap`, once per page) so the name picks one catalogue rather than three. A line row is **not** `InventoryItemRow`: a line is a stamp a lot is *described* as holding, so there is no copy number, location, disposition, delivery state or cost basis to show — it mirrors the copy row's four-line layout and adds quantity. `copy-sort.ts` was generalised to a structural `SortableCopy` + `sortSortableCopies(…, amountOf)` so both orderings are literally one comparison, the amount differing because a copy's is a base-currency catalog figure and a line's a sale-currency total. The arithmetic is pure in `src/lib/auction-lot.ts` (`allIn` = bid + percentage + fixed + shipping, `headroom`, `summarizeAuctionSale` over the *payable* — `watching`/`won` — lots): a ceiling set against the hammer price alone systematically overpays on cheap lots. **Settlement** (#28, `settleAuctionSale`) is a **1:1 transcription** into `Purchase`/`PurchaseLot`, the links unique and `SetNull` so deleting the purchase leaves the bidding record standing — which is also the undo, `assertLotEditable` freezing a settled lot because the purchase now holds what was actually paid. Seller/platform/currency/shipping come off the sale; each settled `won` lot is one line at `settlementLinePrice` = hammer + premium and **never** shipping, which becomes `Purchase.shippingCost` and is distributed across those very lines by ADR-0009 §3 — charging it per line would bill it twice. The composition is **written as copies, not proposed**: a line already is `stamp × condition × certificate × format × quantity`, so a confirm step would re-ask what was typed to decide the bid; a line of quantity N becomes N `Item`s (`ordered`, out of collection, cost pending, one `allocateItemNumbers` range for the parcel) and the existing intake runs unchanged. What *is* reviewed is the money — date, shipping, every line price and **which** won lots are in the parcel — because the seller's invoice is the authority, not our arithmetic; a won lot left out stays `won` and unsettled, since a lot shipped separately is a fact, not an error. Refused while any lot is still `watching` (the parcel's contents are not known) and with nothing selected (a sale where nothing was won is **closed**, not settled). The review dialog is built from the already-loaded `AuctionSaleDetail` — there is no settlement-preview endpoint, because a won lot's line price is the row's own all-in figure.
- Background work runs **in-process**, started from `src/instrumentation.ts` `register()` — no extra compose service. Two shapes: *periodic* stateless sweeps (the photo orphan GC, #112) and *triggered* jobs queued in a **table** whose row is also the state the UI polls (offer photo generation, #311; ADR-0018). A queued job must be idempotent — `running` rows are requeued at boot — and enqueuing must be a no-op while a run is already queued or in flight. Pin worker state to `globalThis` so `next dev` HMR cannot stack a second interval.

## UI Direction

- Modal dialogs for list actions (add, edit). Build with shared `src/app/dialog-shell.tsx` primitives — do not duplicate dialog header, close, viewport constraint, or height behavior. A dialog rendered **from inside a row** must portal to `<body>` whenever any ancestor makes its own stacking context — a transform-centred dialog panel, but also a plain `opacity` below 1, which is how an ended auction row is muted (#354). Inside one, `DialogShell`'s z-index only ranks the dialog *within that row*, so the sticky toolbar and the app header paint straight over it.
- **Escape closes one surface**, the topmost (#361). Every dismissable overlay registers with `useEscapeLayer` (`src/app/escape-stack.ts`); the stack is ordered by mount, which *is* the order surfaces were opened in, so the last entry is the only one that hears the key. `DialogShell` and `PhotoLightbox` register for you — a nested dialog, picker or lightbox therefore needs no Escape handling of its own. Do **not** go back to a document-level capture listener with `stopImmediatePropagation`: that only wins by registration order, so the *outer* dialog ran first and closed itself out from under the lightbox that had just opened above it. The shared listener deliberately does not stop the event, so popovers that are not layers (row-action menus, autocompletes, the translation popover) keep their own listeners and their own behavior; a dialog that must yield to one steps out of the stack with `dismissable={false}` (compose-set while the gap popover is up).
- Row-level actions go in a single `⋮` menu, not a cluster of per-row buttons. Use the shared `RowActionsMenu` (`src/app/c/[collectionSlug]/shared/row-actions-menu.tsx`); destructive actions get `danger` + `separatorBefore`. Dialog-opening actions expose `{ action, dialog }` hooks rendered at the row level (see `use-price-details-action.tsx`, `use-inventory-copy-actions.tsx`) so the dialog survives the menu closing. Section-level adds (e.g. + Add area) stay as standalone buttons. An action a *precondition* blocks is **disabled with a `hint`**, not hidden (#273): the hint is a muted second line under the label saying why, because a disabled control never gets a hover event and a silently missing entry is unguessable. Hide it only when the row itself already answers the question — a copy not marked *For sale* shows no offer action, since the disposition chip is right there.
- Sidebar sections follow **what the collector is doing**, not what the data is: `Catalog`, `Collection`, then trading split by direction into **Buying** (Purchases, Auction sales) and **Selling** (Offers, Sales). One `Trading` heading over five entries meant reading the whole list to find either half. **Contacts belongs to neither** — the same address book holds the house you bid with and the marketplace you list on — so it trails both, set apart by `NavItem`'s `spacedAbove` rather than by a heading over a single item.
- Config screen placement: **catalog taxonomy** that is set up once (Areas, Catalogs, Conditions) lives in **Settings** tabs; **operational data** touched routinely (Locations) gets its own **Collection** nav page. Both reuse the same adjacency-list tree pattern (`buildTree`, `*-tree-select.tsx`, `RowActionsMenu`) — mirror `areas-panel.tsx` / `locations-panel.tsx` rather than reinventing tree/list/dialog scaffolding.

- Physical **format** (pair, block, strip) is an axis of its own (ADR-0020), not a stamp — superseding #135's "record a multiple as its own `Stamp` with a self-descriptive number" for *homogeneous* multiples, which collapsed on deep variant trees (Infla `309 → 309A → 309AP → 309APa`: `formats × nodes` stamps, and "a pair, variant not yet identified" inexpressible because a pair of `309BP` is not a child of a pair of `309B`). `StampFormat` is a per-collection dictionary shaped like `StampCondition`, referenced from `Item.formatId` *and* `StampCatalogPrice.formatId`. **Null means single** — no such row is seeded, exactly as a null `certificateStatusId` means "no certificate" (ADR-0006 §2) — so nothing needed backfilling. A multiple is **never decomposed**: no unit count exists, nothing multiplies or divides by one, and completeness treats format as a breakdown dimension beside condition ("the series in pairs?" like "the series in MNH?"). Zusammendrucke with their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) stay their own `Stamp` — the test is whether the catalog numbered it, not whether it holds more than one stamp. A format's price is **explicit or derived**: an explicit `StampCatalogPrice` row wins, else the single's price × a `StampFormatFactor`, because catalogs publish one factor per issue and an explicit price only where a multiple deviates. Factors live in one table with nullable anchors — the all-null row *is* the collection default (no second `defaultFactor` mechanism to explain) — resolved by **fixed precedence**, `(issue set?, area depth, condition set?)` lexicographically, never a specificity score: *where* deliberately outranks *for which condition*. The rule is pure in `src/lib/format-factor.ts`; `format-pricing.ts` wraps it per stamp because it needs the area ancestry and issue. A format is **translatable** like every other dictionary that reaches a listing (#344; `StampFormatTranslation`, two independently-falling-back columns, `format` in the shared `TranslatableEntity` union), and renders through `{format}` / `{formatAbbr}` + `{#formatLegend}` (#345) — where a **single resolves empty**, the common case, handled by the existing tidy pass rather than by a rule of its own. Lists gain an **`as`** switcher beside the condition one (#343), defaulting to Single, hidden without formats, stored as `""` because Single is not a row. A list column **derives** where nothing explicit was recorded and marks it with the same `~` + italics an unknown-variant rollup uses (#238) — one vocabulary for *inferred, not recorded*, distinguished only by tooltip. The Copies list takes format as a **filter**, never a switcher (a copy's format is a fact), and `valuateCopy` resolves at `Item.formatId`: with no explicit price and no factor a multiple is **unpriced**, never valued at the single's figure. Per-row factor resolution would be a query per row, so `makeFormatFactorLookup` loads the factor rows + area tree once and resolves in memory. A multiplier is **edited where its scope lives** — an issue's from its row on the Issues list, an area's from its row under Areas — so the anchor is never a field the surrounding screen already answers; Settings edits only the collection default and areas and **does not list issue-anchored rows at all**, excluding them *at the query* (`getCollectionFormatFactors`) rather than filtering after: there can be one per issue per format, which is thousands of rows. A scoped list shows what is set on that row alone, never what would apply through inheritance — it is an editor, and showing a parent's rule under a child invites editing it from the wrong place. The scoped editor is one component exposed both as a `{ action, dialog }` row-action hook and as a plain dialog, because the areas panel maps its rows and cannot call a hook per row. The price grid gains format **tabs**, not columns, and a derived value renders as the cell's placeholder so it stores nothing until typed over. Price cell keys grew a **trailing** `~<formatId>` segment, optional so pre-format payloads still parse.

The collection's **default** subtype renders **nothing**, on both surfaces: it is the row assigned automatically to every new child, so it carries no information the tree did not already give, and badging every variant "Variant" scales noise with the collection. Which subtype is default is already the collector's choice, so that *is* the setting. The last subtype saved is remembered per collection (`LS_LAST_SUBTYPE`) and pre-fills the next add, alongside #234's copy defaults.

The Copies list, PO intake and sale-lot views pass an `ItemListItem` (it satisfies the shape structurally, a copy carrying its own condition); the Issue list builds one from a stamp-tree node plus the list's **display condition** with certificate = none, matching what the price column renders (#341). `useQuickPriceDialog` returns `{ open, dialog }` and owns the save. Where the display is itself interactive (a link that opens), pass `editControl` so a separate ✎ enters edit mode instead of the display's own click being hijacked (#214). - Tabs inside dialogs are visual grouping only — one logical save action. Dialog height determined by default tab; switching tabs must not change height. Body scrolls, header/footer fixed.
- A **hover hint is the shared `Tooltip`** (`shared/tooltip.tsx`), never the browser's `title` attribute (#291) — a native tooltip ignores the theme, appears after a delay nothing else in the app has, and cannot carry formatting. Native `title` survives in exactly two places: revealing text that is *already on screen* but ellipsized (the hint repeats the visible string, which is the browser's overflow affordance, not a tooltip), and the printable packing sheet, a server-rendered artifact that should not become a client component for hover text that never prints. Three things follow from the wrapper the component inserts. **Empty content renders no bubble**, so a conditional hint stays one code path instead of branching between a wrapped and an unwrapped child — which would move the child in the layout. Layout the child carried (`flex`, `marginLeft: auto`, `position: absolute`, `width: 100%`) moves to the wrapper's **`style`**, or the row shifts around it. And a tooltip **inside** another tooltip suppresses the outer one while it is open, matching what nesting `title` did — triggers nest constantly here (a chip with its own hint inside a clickable row that has one), and `mouseenter` does not re-fire on the ancestor, so both bubbles would otherwise sit on screen at once. `title` doubling as an icon-only control's accessible name is not a reason to keep it: give the control an `aria-label` and the hint a `Tooltip`.
- Prefer in-place editing for fields where inline edits are practical.
- A list's **filter toolbar is sticky** (`STICKY_TOOLBAR_STYLE` in `shared/list-toolbar.tsx`, #358): the page itself scrolls — there is no inner scroll container — so `top: 0` is the app's own top edge, and the z-index (5) must stay under the portalled row-action menus (200) and dialogs (100). `ListToolbar` carries it for the card-embedded lists (Issues, Stamps, Copies, Sales); the Offers and Purchases panels build their own toolbar row and spread it together with the **page** background, since a transparent bar would let rows scroll through it.

Build them with `orderedCatalogLabels` (primary vendor first) at every site, including the edit-mode prefill, which must resolve the vendor map from the **copy's own area**.
- A **child stamp inherits the parent node's year**, not the issue's (#360) — a variant or reprint is dated from the node it hangs under. `StampFormDialog` skips the issue-members query when a parent is prefilled, so the caller passes `prefilledParentIssuedYear`; the Year input is uncontrolled and keyed on the derived default so re-seeding actually reaches the DOM. Root-level stamps still start from the issue year (#70).

Expansion is derived, never a `setState` in an effect: the panel raises an `ExpandStampSignal` (`{ stampId, nonce }`) and each node compares it against the toggle the collector last made — so a manual collapse sticks, while a *repeat* add under the same parent carries a fresh nonce and opens it again.

- Use semantic color tokens from `src/app/globals.css` for UI intent. New tokens must have values in both `:root` (light) and `.dark` blocks.
- URL state for navigation/filters/sorting/pagination; toast for ephemeral feedback. A remembered **client preference** (localStorage) that a *server-rendered* screen reads must go through `useSyncExternalStore` with a **null `getServerSnapshot`** — `usePersistedFlag` and `usePersistedSort` are the pattern. Reading `localStorage` straight in render makes the pre-hydration render disagree with the server's, and React then discards the whole tree and re-renders it on the client. `usePersistedSearch` is the exception, and only because the pickers using it are portalled after a click and never server-render.- Printable views (#330, the sale packing list) are their own route rendering a plain server-side sheet — no filters, no lazy loading — because the artifact is the printout, not an interactive screen. Print support lives in `globals.css`: mark app chrome and on-screen controls `.no-print`, wrap the sheet in `.print-sheet` (drops screen padding), and rely on the `@media print` block that forces the colour tokens to an ink-friendly light palette (so the dark theme never prints as a black page). Use real `<table>` markup so headers repeat across pages, and `.print-footer` to pin a provenance footer to the foot of the page (fixed in paged media; the sheet reserves the strip with its bottom padding). Which columns a sheet prints is a per-user choice stored **globally** (one `usePersistentString` key holding a CSV of column keys — a stored empty string must read as "all off", which a set of booleans can't express), not scoped to the collection or the record.
- A list's **summary bar** sums the *filtered* set, read whole through its own endpoint rather than summed from the loaded pages — a total that grows as you scroll is worse than none — and renders a mode-matched skeleton so nothing below it shifts (#151). The offers one (#317) leads with **asking value** alone, because the per-state counts it would otherwise repeat already live in the filter chips (#332); **More** reveals the copies' catalog value + purchase cost (the holdings pair, #134) and a per-platform split, behind an expander because they cost a valuation pass and answer an occasional question. Its copy count is **per membership** (a copy on two platforms is two sellable offers) while the holdings figures **deduplicate** (it is one piece of stock) — the divergence is deliberate and documented at `OffersAskingSummary.itemCount`. The per-platform breakdown repeats **all three** figures — a slice answers the same questions as the total — as a grid whose amount columns sit at the **left**, beside the platform name (a right-aligned far edge makes a wide screen unreadable), the asking column landing under the total's. Platform rows are each complete in themselves and deliberately **do not sum to the total**: a copy on two marketplaces is valued in both. Overlapping slices are why the valuation is a single pass — `getHoldingsValuationByGroup` fetches and values the union once and aggregates per group, so adding a platform costs an aggregation, not a pricing run. The arithmetic is pure in `src/lib/offer-summary.ts` (unit-tested, no Prisma), mirroring `aggregateHoldings`; `offersSummary` and `listOffersPaginated` share one `offerListWhere` so the bar and the rows can never disagree.
- A copy's **internal number** (#268) is a per-collection sequence on `Item.itemNo`, unique with `collectionId`, assigned at creation and never editable. It is handed out by bumping `Collection.nextItemNo` in one `UPDATE ... RETURNING` (`allocateItemNumbers` in `src/lib/items.ts`, which takes a range for a bulk intake) — **never** `max(itemNo) + 1`: the number gets written on the physical piece, so a deleted copy must retire its number rather than pass it to the next one. Every `item.create*` site must supply it. Display and search parsing are pure in `src/lib/item-number.ts` (`formatItemNo` → `#00123`, zero-padded so a column lines up; `parseItemNoSearch` accepts `123` / `00123` / `#00123`). A numeric search matches the number **in addition to** the text search, never instead of it — `200` is also a plausible catalog number. It rides in the row's meta line and the Edit dialog's title, not in a form field: a permanently disabled input earns no space. How wide it renders is the collector's choice — `Collection.itemNoPad` (Settings → General), display-only, so changing it renumbers nothing and cannot break a search (leading zeros are insignificant to `parseItemNoSearch`). Client surfaces read it through `useCollectionItemNoPad`, a query rather than a prop, because `InventoryItemRow` is rendered from eight screens. In listing texts it is `{itemNo}` / `{itemNo:N}` (#268) — padded to the collection width, or to `N`; an unusable `N` falls back to the collection width rather than emptying the token, and **no `#` is added**, since a template is literal text. `TitleTemplateCopy` therefore carries `itemNo` *and* `itemNoPad`: collection-level data on a per-copy shape, because the pure engine has no other channel.
- **Copies held per stamp** (#348) come from `src/lib/copy-counts.ts` — one `groupBy` over the disposition flags for a whole page of stamps, never a count per row — and render through the shared `CopyCountBadge` on every surface that lists a stamp (issue tree, flat list, pickers). Counted **per stamp exactly**, never rolled up from variant children (the tree shows the child's own badge one line down, so a rollup would show one copy twice), and **excluding sold copies**, because the badge sits beside *View copies* and must agree with what that popup lists (#207). Delivery state is deliberately *not* filtered — a copy in transit is bought. A stamp with none shows **nothing**, the same unmarked-default rule as the subtype chip and the single format. The disposition figures are markers that overlap (in collection *and* for sale), so they are listed in the tooltip, never summed.
- **Which offers something is in** (#276, #349) is a read-only popup off the Copies, Stamps and Issues row menus, fed by `listOffersForTarget` (`offers/for-target`, a static segment ahead of `[offerId]`) — unpaginated, because a target sits on a handful of listings at most. It is scoped by an `OfferLookupTarget` (`item | stamp | issue`) mirroring the copies popup's targeting (#110), and a **stamp matches exactly**, never rolled up from its variant children — the same rule as the copies-held badge (#348), since the tree shows a child's own entry one line down and a rollup would report one listing twice. The stamp/issue surfaces go through `useOffersPopupAction`, the `{ action, dialog }` row-action hook; the Copies list keeps its panel-level dialog union. It lists **every** state, terminal included (unlike the offers list, which hides closed ones by default, #245): a sold or withdrawn listing is exactly what one asks a piece's history for. Ordered live-first (`active → paused → ready → preparing → sold → withdrawn`), newest first within a rank, so "where is this on sale right now?" is answered by the top of the list. The row reuses the Offers list's presentation (platform/state chips, needs-action + bidding badges, asking price with base-currency equivalent), opens the offer's detail screen on click, and links the platform listing separately. The action is **unconditional** — a sold copy's past listings are as much the question as a live one's, and the row carries no offer count to hide it by.
- A copy's **delivery state** (ADR-0009 §5) has one vocabulary: `src/lib/delivery-state.ts` (pure — valid set, labels, tint tokens, lifecycle order, `isDelivered`), read by the domain layer, the route handlers and every screen. Do not restate the list. On the Copies list it is a chip **only when the copy is not delivered** (#272) — delivered is what a hand-added copy starts as and every sorted copy ends as, so chipping it would badge nearly every row, the same reasoning that leaves a single format unlabelled — plus a single-select filter, threaded through the list, holdings-valuation and year-facet endpoints alike so the bar and the panel never disagree with the rows. The two exception outcomes (`UNAVAILABLE_DELIVERY_STATES`) are excluded from the *not offered on platform X* worklist (#259): a copy that never arrived or arrived damaged is paid for but not in hand and never will be, so it cannot be listed — while the in-flight states stay, since a copy on its way is exactly what one prepares a listing for. The intake screen renders its own editable delivery control, so it passes `hideDeliveryState` exactly as it passes `hideDispositions`.
- **Auction sales** get their own collection nav page, and the **flat list of lots is the primary screen** (#351) — status / platform / seller filter chips (#332), sale as a column with optional grouping, inline bid editing — so "everything I have running on Allegro" needs no navigating between sales. Sale detail exists separately, for settlement and shipping. This follows from the sale being a *settlement boundary*: it matters twice (when a lot is added and when the parcel is paid for) and is in the way the rest of the time, whereas scanning closing times and refreshing bids is what happens daily. Consequently adding a lot never starts by picking a sale (#352): the dialog takes seller and platform and **proposes** the open sale for that pair when one exists, with the option to start a new one — the proposal is re-read server-side rather than trusted from the client, and refusing it (`startNewSale`) is what a second parcel from a seller who has already shipped needs. The screens live under `auctions/` (`/auctions` the lots, `/auctions/sales` the settlement list, `/auctions/sales/[saleId]` the detail), the vocabulary + staleness + parsing in `auction-rules.ts`, the reads/writes in `auctions.ts`. Four decisions the code depends on. **Staleness is relative**: a reading may be a quarter of the time that was left when it was taken old before it counts stale, capped at a day — one ratio instead of a threshold table, tightening exactly as the close approaches; a live lot past `endsAt` reports `closed` instead, because that is the only signal that never fixes itself. The toolbar filters on **two different questions**, and the split is deliberate: *signals* (`LotSignal` in `auction-lot.ts` — can-still-bid, outbid, leading, over-ceiling, won-pending) are **derived** from the figures and answer "what do I do about this now", while *statuses* are **recorded** and answer "how did this end". A watchlist is worked through by the first and filed by the second. Signals describe `watching` lots only. They span two tables plus arithmetic, so no `where` expresses them: `resolveSignals` walks the live lots once in memory and hands ids to the page query — the offers list's needs-action pattern (ADR-0013 §4), and sound for the same reason, a watchlist being bounded by what one person is currently bidding on. **Colour means "act now"**, and nothing else: an ended lot is *muted* (row opacity included), never red — there is nothing to react to, and an alarm on it would compete daily with the lots that can still be won. That is why the `Ended` / `Closing today` / `This week` window filter exists (server-side on `endsAt`, the boundary read from the server's clock so two tabs and the counts cannot disagree; deliberately **not** remembered between visits, unlike the other filters, since a list silently narrowed to old lots would hide everything running). Past the close, `BidStandingChip` stops reading as a position and reads as a **result** — *Won?* / *Lost?*, with the question mark, because it is inferred from the last bid anyone recorded rather than from the platform; a lot whose outcome *is* recorded renders no standing chip at all, its status chip saying it without the doubt. The closing time is tinted by `closingUrgency` — **absolute** thresholds (past / ≤2 h / ≤24 h), deliberately unlike the relative staleness rule beside it: staleness asks "is this reading still good?", which depends on the time left, while urgency asks "must I deal with it now?", and an hour is an hour. Its wording follows the *clock*, not the status: a `watching` lot an hour past its close reads "closed", because it plainly does not still close in the future. A recorded bid **always** stamps `checkedAt` — including an unchanged one via *Bid unchanged*, since "still at 40" is the observation being asked for — while editing anything else on the lot leaves it alone, or a three-day-old reading would look current after a title fix. The last platform is remembered **per seller and in the database** (`Contact.defaultAuctionPlatformId`, a self-FK, `SetNull`), not as one value and not in `localStorage`: where you bid follows from who you buy from, so a single "last platform" would be wrong for every seller but the one just used, and the memory has to survive a change of device. It is deliberately **not** the offers screen's remembered platform — an auction platform is not a selling platform. It is *remembered, not configured*: nothing in the contact form writes it, `rememberSellerPlatform` does, from `createAuctionLot`/`createAuctionSale` — server-side, because a seller and a platform typed in by name only become contacts once the server has resolved them, which is where both ids first exist. Its `updateMany` guard needs the explicit **null branch** (`OR: [{ id: null }, { not: id }]`): `<> 'x'` is NULL for a NULL column, so a seller who has never been tracked matches no inequality. Pre-filling it remounts the picker (`key`), because `PurchaseContactSelect` seeds its own state on mount, it is adjusted **during render** rather than in an effect (the value arrives with a query), and a platform the collector has touched is never overwritten. The `sales/open` endpoint therefore takes `platformId` as **optional** — the pre-fill must be answerable before a platform exists, or it would deadlock the very field it feeds. A lot carries **three** money fields that are constantly confused and must not be merged: `currentBid` is an observation of the auction (what it stands at, whoever is winning), `myBid` is a commitment the collector made to the platform (a proxy/maximum bid), and `maxBid` is a private valuation (the ceiling). Only the first stamps `checkedAt` — it is the only one that dates an observation. **Leading / outbid is derived** (`bidStanding`, `myBid >= currentBid`, a tie going to the bid already placed), never stored: a flag would be a fourth thing to keep current and would be wrong the moment the price moved. *Bid my ceiling* uses `maxBidWithin` — the **inverse of `allIn`**, `(ceiling − fixed − shipping) / (1 + pct/100)`, rounded **down** — because a ceiling is an all-in figure while a bid box takes a hammer price, so bidding the ceiling itself overshoots by exactly the fees. `AuctionLot.startingPrice` is a **record, never a figure**: it is what the lot opened at, so it is displayed muted in the bid slot while no bid exists (`from 20 PLN`) and enters no arithmetic at all — a lot nobody has bid on costs nothing whatever it opens at. The row renders the three as a **3 × 2 grid** (Auction / Mine / Ceiling × bid / all-in): each figure exists twice, and columns are what make them comparable. Exactly one cell of each pair is stored and editable — the two bids are hammer prices, a ceiling is an all-in valuation — and the other is derived and muted, which is why the ceiling's *bid* cell is `bidRoom`, the very figure *Bid my ceiling* places. The two bid cells are tinted **together** by `standing` (green/red), because they are one comparison; the collector's own cells go **amber** when `myBidOverCeiling` — their commitment costing more than their ceiling is a different fact from the market outrunning them, and the only one they can take back. A row's **all-in excludes shipping** (premium only): shipping belongs to the parcel and the sale's total adds it once, so charging it per row would double it the moment two lots are open with one seller. And the list's **reading order** is decided by the status chip — `watching` soonest-closing first, a terminal status most-recent first, no chip at all newest-tracked first, because the two orders contradict each other in a mixed list.
- In-location refs (`A234`) are ordered by `compareLocationRef` (`src/lib/location-ref.ts`): prefix first, then the trailing number, separators ignored, blanks last. Use it anywhere refs are sorted — a plain numeric collator disagrees as soon as the separator varies.

## Testing Direction

- `pnpm lint` — run before finishing any task that touches source files.
- `pnpm typecheck` — TypeScript verification.
- `pnpm test:unit` — pure logic only, no Prisma imports.
- `pnpm test:integration` — requires real database via `docker-compose.e2e.yml`. Run before committing schema or domain logic changes.
- Write migration SQL manually. Create directory and `migration.sql` by hand under `prisma/migrations/`. Then `pnpm exec prisma generate`.
- Never run `prisma migrate dev`, `prisma migrate reset`, or `prisma db push` directly. Exception: `pnpm e2e:db:reset` is safe.
- When starting a local dev server for verification, use `pnpm exec next dev --webpack -p 3002` and stop it before finishing.
- Always run the dev server on **webpack** (`next dev --webpack`), never the default Turbopack: Turbopack's dev/HMR leaks memory until the container OOMs (an open, idle browser tab grows the server heap unbounded; webpack plateaus). The `docker-compose.dev.yml` overlay is pinned to `--webpack` for this reason. See issue #161; re-test Turbopack after Next.js upgrades and revert once fixed upstream.
- The user tests the app through Docker Compose. Do not leave dev servers running.

## Before Implementing Features

If a request would require defining product behavior, ask targeted questions first. Good questions are concrete and bounded:

- What is the first workflow we want to support?
- Should catalog numbers be per-standard (Michel, Scott, Fischer) or free-form?
- Should condition follow a standard scale or be free-form?
- Should a collection be shareable with other users?
