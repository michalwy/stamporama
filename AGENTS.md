# Agent Instructions

This project is intentionally vibe-coded. Future agents must preserve product intent, avoid invented requirements, and ask clarifying questions when the next step is not clear.

## Product Context

- Product name: Stamporama
- Purpose: a self-hosted web app for stamp collectors
- Desktop browsers only; no mobile layouts or breakpoints.
- Core concept: **collection** — the top-level organizing unit that scopes all stamp data for a user

## Working Rules

- Do not assume domain behavior. Ask before defining catalog standards, condition scales, trade workflows, auction integration behavior, or pricing logic. Ask one question at a time.
- Do not add user-facing functionality unless the current task explicitly asks for it.
- Prefer small, reversible changes with clear documentation.
- When changing user-visible behavior, update `docs/user-guide/` in the same task.
- When changing behavior, data model, setup flow, or architecture assumptions, update every affected document (`README.md`, `docs/product/brief.md`, `docs/architecture/overview.md`, relevant ADRs, `docs/user-guide/`).
- When introducing a framework, library, or major pattern, add or update an ADR in `docs/decisions/`.
- Update this `AGENTS.md` file when new project knowledge or workflow rules would help future agents.
- Favor boring, well-supported tools over novelty. Preserve existing user changes.
- Use GitHub Issues as the shared backlog. Use Conventional Commits for issue titles. Always assign labels (`backlog` + type + priority when known). Do not maintain a local `TODO.md`.
- If GitHub connector cannot create issues, use `gh` CLI as fallback.
- All GitHub content must be in English.
- Do not create git commits unless the user explicitly asks. Do not push unless explicitly asked.
- Solo project: commit directly to `main` by default. Create feature branches only when the user asks for a PR.
- When pushing to `main`, try `git push origin main` first. If rejected, fetch, rebase, rerun verification, push again.
- Use Conventional Commits: `feat:`, `fix:`, `docs:`, etc. Include GitHub issue reference when one exists.
- When a commit title alone would omit useful context, include an extended commit message body.
- Use a separate git worktree only when the user explicitly asks for one.

## Multi-Step Implementation Plans

When a task spans more than one logical area, write an implementation plan before starting. Store it under `.claude/plans/`. A plan is executed fully within a single session.

- Begin with a `## Progress` section containing a checkbox list of numbered steps.
- Steps are executed in order. Mark each step `[x]` immediately after completing it.
- Each step must state a **Done when** criterion.

## Agent Collaboration

Use specialized roles only when the task benefits from them. Small, localized tasks can be handled by one agent.

Use specialized roles for larger changes that cross domain, data, authorization, or user-flow boundaries:

- Architect: schema, ADRs, major patterns.
- Designer: UI flows, dialogs, interaction design.
- Developer: scoped implementation.
- Tester/Reviewer: browser flows, regressions.

Prefer Architect before changing Prisma schema, permissions, collection scoping, authentication, routing, or ADR-documented patterns. Prefer Tester/Reviewer after changing forms, dialogs, collection routing, authentication, permissions, or migrations.

## Technical Direction

- Collection-scoped access control: `collectionId` on data, owner has full access, checks live server-side.
- Collection URLs: `/c/[collectionSlug]/...`; slug resolution authorizes by internal `collectionId`.
- Better Auth for authentication.
- Prisma with PostgreSQL (minimum **version 15** — migrations use `NULLS NOT DISTINCT`; see ADR-0006). Treat schema changes as product decisions.
- Bumping the bundled `postgres:` image to a new major breaks the dev stack: the `db_data` volume keeps the old cluster and 18+ images relocated the data directory. It needs a dump/restore, never just a tag change — follow `docs/development/postgres-upgrade.md`. Production uses an external database and is unaffected.
- SPA-like collection interaction: Next.js App Router as route/auth shell, client-side queries/mutations for rich screens.
- TanStack Query for data fetching, TanStack Table for list views.
- Cursor-backed infinite scrolling for large lists via shared primitives.
- Keep domain logic out of UI components. Keep authorization server-side.
- Explicit module boundaries under `src/`.
- Self-hosted deployment: CI pushes multi-arch image to `ghcr.io/michalwy/stamporama` for release tags only. `docker-compose.prod.yml` + `.env` for production. `scripts/install.sh` is the curl-able installer. Version baked via `STAMPORAMA_VERSION` build arg, shown through `getAppVersion()` in `src/lib/version.ts`; the **release instant** rides beside it as `STAMPORAMA_BUILD_DATE` (#507), read by `getAppReleaseDate()` and rendered by the shared `AppVersionLabel` on both surfaces that show a version. CI stamps it from the image's own `org.opencontainers.image.created` label so the two cannot disagree. Null is the ordinary case, not a failure — an unstamped build says nothing rather than dating itself, the same call an unset version makes in reading as `dev`. The inline day is the **UTC date sliced off the ISO string** and the localized instant lives only in the hover `Tooltip`: this renders inside a server-rendered shell, and a browser-formatted date in it would disagree with the server's for anyone west of UTC, while a bubble created on hover is never in the server's HTML at all.
- Browser extension (Stamporama Assistant, #253; ADR-0015) lives in `extension/` — a separate pnpm-workspace package (MV3, esbuild + hand-written `manifest.json`, own `tsconfig`). It is **excluded from the app's** `pnpm lint`/`typecheck`; build and check it on its own with `cd extension && pnpm build|typecheck`. It calls the Colnect matcher endpoints with an `AssistantToken` bearer (session-or-token auth via `src/lib/route-auth.ts`), because the extension reaches us cross-site from colnect.com. Its match window groups results and hides the decisions the collector has effectively already taken (#305): a `needs-confirm` row every candidate of which already carries some Colnect ID — the matcher never silently overwrites (#250), so those rows return on every re-scan. One free candidate keeps the row, since that free stamp is most likely the answer (`isAlreadyLinkedElsewhere` in `core/decisions.ts`). The same rule governs the *numbers*: the backfill (#280) fills a catalog the stamp has none for and only **reports** one the two sides disagree on, so #433 is the collector settling one of those disagreements by hand — `proposeBackfill` resolves each conflict's `overwriteNumber` by the very rules a fill uses (a prefix it cannot recover or one from another area offers nothing, exactly as it writes nothing), and `overwriteColnectCatalogNumber` (`POST …/colnect/overwrite-number`) replaces that one vendor's row, refusing a catalog the stamp holds no number in — that is the backfill's job, and two paths claiming one field is how they drift. It is deliberately **not** part of confirming a match: linking an item and rewriting a number already held are two different claims, and only the second destroys something, hence its own confirm naming both values and its own route rather than a flag on `confirm`. The duplicate policy (#85) is the fill's, run over a proposal shaped like one so an overwrite and a fill can never disagree about what collides; the write **rings no doorbell** (#423's `data-stamporama-assistant-matched`), which announces a *match*, not a number. Offered only on rows that name a single stamp — a linked one or a one-candidate `needs-confirm` — since correcting a number on an unchosen sibling is a change nobody would think to look for. What the matcher compares is strict and pure, but what it *recalls* out of the database is a `contains` net, and that net is built from **each digit run** of the printed number and never from all its digits at once (`catalogDigitRuns`, ANDed on one `some`, in both readers — the matcher's and the picker's): `PL BL30 B4` concatenates to `304`, which no stored `BL30 B4` contains, so the item read as `no-candidates` with the stamp sitting right there (#435). A run survives every spacing and punctuation difference between the two sides, which is exactly what the key already folds away; a digit-free number (Michel's Roman local issues) still recalls on its bare value, case-insensitively. The reveal control lives in the toolbar row, not the section heading: with every such row hidden the section is gone and would take the only way back with it. Tokens are obtained by **self-registration** (#252): Settings → Assistant exposes a one-time code + the instance's own origin on the page, and a toolbar-icon click exchanges it at `POST /api/assistant/register` (`src/lib/assistant-registration.ts`). A `PlatformModule` has **two halves** (#408): extraction (`matches`/`extract`, required) and **listing** (`listing: { formUrl, isFormUrl, fill, listedUrl, attachPhotos? }`, optional) — reading a marketplace page and posting to one are the symmetric halves of one job, so listing lives in the neutral interface rather than inside the Colnect module, which is what lets Delcampe (#154) and Allegro (#355) reuse it. A read-only module is a *complete* module and its platform simply offers no **List via Assistant** (#407); `moduleReports()` says which modules carry which half, so no surface hard-codes ids. The task is the **listing kit** (#405) unchanged, mirrored by hand in `extension/src/platform/listing.ts` as `core/decisions.ts` mirrors the matcher response — it states what the listing *holds*, never how a form is laid out, so Colnect's URL shape and field names appear nowhere outside `src/platform/colnect/` (#410). Driving one is `listing-run.ts`, **two pure steps** because a navigation separates them (`resolveListingTarget` → `fillListing`), leaving the tab-opening and the report back to the instance to the wiring (#407/#409). Filling **stops before submit** — the collector clicks the platform's own button — the page is checked with `isFormUrl` **and** with `isFormDocument` first — two questions because a marketplace answers the form's own address with something that is not the form yet (#419: Colnect's anti-bot interstitial, which reloads itself into it), and filling that page wrote nothing while reporting every field as missing, so the text half of a listing vanished and only the pictures — attached later, on the reloaded form — landed. The document check is therefore a **`retry`, not a refusal**: `fillListing` says "not yet", and the wiring (`fillThroughReloads`) waits for the tab's next `complete` and starts the whole attempt over, injection included, since a fresh document holds no content script. The watcher is armed **before** the fill, or a reload landing while the message is in flight is the one event it misses; it is bounded by both a short wait and an attempt count, because a page that never becomes the form (a sign-in, a challenge) has to end in the error it already has rather than in a spinner. A URL that is not the form's at all stays an outright refusal — that is the collector having navigated away, not a page on its way. The outcome is a **report, not a verdict**: `filled` *and* `skipped` both come back, each named for the collector rather than for the DOM, because a field the task cannot answer (an unmapped condition above all) is no reason to abandon the rest of the form. The three ways a task finds no module — the platform names none, the id is unknown here, the module only reads — are three different answers. That **wiring** (#409) is the registration contract a second time, on a second element (`#stamporama-assistant-listing`, `extension/src/core/listing-handoff.ts`): the workspace writes `{ v, requestId, task }` into it as text and the extension answers with `data-listing-state` / `-message` / `-request` / `-report` on the same node — the page owns the node and re-renders it, so text in and attributes out is the only direction that survives. The gesture is what differs from #252: a listing starts from a click on an offer *card*, so there is no toolbar click to grant `activeTab`, and the extension instead **registers a content script for the profile's origin** (`background/instance-scripts.ts`, `chrome.scripting.registerContentScripts`, port included so `:3002` is not `:3000`) — reconciled against the stored profiles off `chrome.storage.local` changing, so registering, correcting a URL and deleting a profile are one code path, and injected into that origin's already-open tabs, a freshly registered script only reaching documents loaded after it. `host_permissions` is already `http://*/*` + `https://*/*`, so none of it prompts. `requestId` is minted by the page and echoed back — an answer names the handoff it answers, and a request already answered is ignored, so a re-render is not read as the collector asking again — and `<html>` carries `data-stamporama-assistant` (the version) on every instance page, without which **List via Assistant** is a button that silently does nothing on a browser with no extension. The worker (`background/listing.ts`) then does the part `listing-run.ts` deliberately has no `chrome.*` for: open the form **beside** the workspace tab, wait (capped, a closed tab reported as such — a promise that never settles leaves the card spinning), have the *content* script fill it because the DOM is there, report back. It needs **no profile and makes no instance call**: a task is self-contained and the origin that wrote it is one the collector registered. Storing the URL and moving Ready → Active stays the page's own job (#407) — the extension reports, the instance decides. **Closing that loop** is #412: the entry's URL exists only after the collector presses Save, so `PlatformListing` gains one more neutral member — `listedUrl(url)`, the same knowledge `isFormUrl` carries on the other side of Save, returning the URL rather than a boolean because it is *stored* and the module is what decides which part of the address bar is the record (Colnect lands straight on `/…/market/sale/<code>`, confirmed by posting one, and drops query + fragment). The wait between filling and Save is written to `chrome.storage.local` per listing tab (`background/pending-listings.ts`, pruned at 12h), never held in the worker: a collector takes minutes over a form and an MV3 service worker is unloaded in seconds, so a navigation wakes it with nothing but a tab id and the record is what turns that into meaning. The content script also arms a one-shot `submit` watcher, which buys the one distinction the capture cannot make on its own — a **posted** listing whose entry page was never recognised is reported when the tab closes, while an **abandoned** form is silence, because an untouched Ready offer is not news (a form re-served with validation errors is why the report waits for the tab to close rather than firing on the first unrecognised page). The write-back has **two deliverers, in order**: the answer goes onto the handoff node and the *page* publishes it through the same `publishOfferAction` its own Publish calls — #407's rule, with the collector watching — and the instance content script replies whether it is `taken`, which it decides by re-reading the node's **text** for that `requestId` (the page's own half of the contract, so "is anyone still following this" is answerable without inventing a channel). Not taken — dismissed, replaced by the next offer's handoff, tab closed — and the worker POSTs to `…/offers/[offerId]/listed` with the profile matching the page's **origin + the task's collection**, the only pair that names one connection. `recordOfferListed` is therefore **idempotent**: `ready` publishes, an already-`active` offer has a *blank* URL filled in and a recorded one left alone, anything else is refused, so the two paths racing is a no-op and never a conflict — and a marketplace submission can never quietly take a paused or sold offer live. Colnect's own half (#410, `colnect/listing.ts`, against the form mapped in #402) declares the **komplet in the URL** (`…/sell/new/category/stamps/item/<id>%2C<id>…` over the copies' item-IDs in listing order, **deduplicated** — the form keys one fieldset per item, so a second copy of one stamp cannot be declared twice and is named in the report instead of dropped). It fills each copy's condition (`new_sale[cond_20_<id>]`, through #404's mapping), the price, the number of sets and the two texts, and leaves `expiry_date` / `auto_renewal_*` exactly as served — required, pre-filled, matching nothing here, so writing our own would clobber the collector's defaults; `options[] = separate_listings` is never touched either, but a *ticked* one is reported, since it moves pricing to the per-item fields and turns pictures off. An **over-long text is neither written nor truncated**: truncating mangles chosen wording, and a scripted assignment past `maxlength` is not refused the way a paste is, so the form would carry a value Colnect then rejects — the report gives both numbers and points at #403's counter. Colnect's **currency is a seller-level setting** and not a form field, which is what a platform locking its currency (#196) is for. A `<select>` is set by **selecting the option**, never by assigning `value`: a grade the form does not offer is then a refusal rather than a silent no-op. **Pictures** (#411) are one more optional neutral member — `attachPhotos(doc, photos)` — and are the run's **last** step, never part of `fill`: Colnect's Dropzone posts each picture over AJAX the moment it is handed over, minting a draft `sale_id` *before* the sale is saved (#402), so this is the first thing in a whole listing that writes to the marketplace at all and it happens with a filled form already in front of the collector. Whether that leaves orphans behind on an abandoned form is still #402's open question; putting photos last is what makes the answer not matter much either way. The images are what the kit already carries (#405) — the upload set, in upload order, under the ZIP's own names (#314/#326) — so nothing on the app side changed. Three pure decisions sit in `listing-run.ts` before a byte moves: a module with no uploader is **silence, not a gap**; a plan that is not `ready` is a skip naming what Stamporama is doing about it; and a set past `LISTING_PHOTO_BUDGET_BYTES` fills **from the front**, the plan's order being the priority order (#313), exactly as the platform's own photo limit fills it. An **out-of-date** render is none of those and is deliberately not reported here — the offer's Photos card already carries that signal, and repeating it in a fill report would turn a signal into a warning. The bytes are fetched in the **worker** (`background/photo-client.ts`, the photo route's own Assistant token, the profile named by page origin + task collection exactly as #412's write-back names it) and cross to the content script **base64** over `attach-photos`, because extension messaging is JSON and a `File` does not survive it — which is also where the budget comes from, and why the ceiling is stated rather than hidden. The `File`s are built in the page, the realm the form is in. Colnect's own half finds the Dropzone's real `<input type="file">` **structurally**, by what it accepts: it is the one control in the form #402 mapped that Colnect does not address by a `new_sale[...]` name, so there is no name to match on. Every failure is a **skip, never a refusal** — an unaccepted file type, a `disabled` uploader (which is what ticking *separate listings* does), a non-`multiple` input, a fetch that failed — because the fallback the scope asks for is dragging the offer's ZIP in, not redoing the listing. The report says the pictures were **handed over**, not that they arrived: the upload is Colnect's own AJAX and the thumbnails appearing in the Dropzone are what confirms it, right where the collector is already looking. The **match handoff** is that same contract a third time (`#stamporama-assistant-match`, `extension/src/core/match-handoff.ts` ↔ `src/app/c/[collectionSlug]/offers/assistant-match-handoff.ts`), for the step *before* a listing: posting needs every stamp matched, so an offer's On Colnect card hands over the catalogue search it already builds (#423) and the worker does the two things a page cannot — open the tab and put the match window in front of it (`open-match`, answered `running` → `opened`, since what happens in that window is the collector's own work). A **third** node rather than a task type on the listing one, because an offer being prepared is matched *and* listed and the two answers must not overwrite each other; the URL is re-parsed on the extension side and refused unless http(s), it being handed straight to `chrome.tabs.create`. The write comes back not down that path but as a **doorbell**: every confirmed match sets a changing `data-stamporama-assistant-matched` on `<html>` of every instance tab, carrying no request id on purpose — any match may be the one a screen is waiting for, re-reading an offer is cheap, and matching started from the toolbar icon has no handoff to answer at all. **Link all** is therefore page-driven, a queue taken when the walk starts and advanced on each ring: the extension cannot know what is still missing, and a walk re-derived from fresh data would reopen the row the collector deliberately skipped. **Going back to a live listing** (#462) is that same run at a second address: `PlatformListing` gained one more optional member, `editUrl(task)`, because on Colnect the edit page *is* the sale form — `…/sell/edit/sale_id/<code>` over the code the stored entry URL already carries (#412), same `new_sale[…]` names, same five grades, same Dropzone — so `fill` has no variant, `isFormUrl` answers for both addresses, and the task's `mode` decides the URL and nothing else. Optional for `attachPhotos`' reason: posting to a marketplace is no promise a posted listing can be reached again, and Allegro's Assistant form (#493) is entered through a sequence that exists only on the way to a *new* listing — hence `supportsUpdate` on `listingModuleRules`, a third question beside the two #471 already separated. The preconditions are **one evaluation asked about two acts**: everything about the goods is identical on an edit form, and only the leading state check moves — `create` wants Ready, `update` wants Active *and* a listing URL, each standing alone as `not-ready` does. Nothing records what was last posted, deliberately: an update reloads **every** field whether or not it changed, since a field left out because it looked unchanged is how a listing quietly keeps an older value, and a stored snapshot would be a second copy of the offer to keep honest — so the button is simply always there. What that reasoning ruled out was a *per-field* diff, and #542 later separated the coarser question out of it: `Offer.listingContentChangedAt` (`offer-listing-drift.ts`) is stamped when an offer that is **up** — `active` or `paused`, both being listings a buyer can see — has its composition, its stated price or one of its texts changed, and answers "which of my live listings did I change?" without claiming to know *what* in them changed. It is a timestamp of the **first** such change and not a snapshot, so it reads as "diverging since…" (the figure a collector triages by), it cannot fall out of step with the offer the way a stored copy would, and it is two plain columns (`LISTING_DRIFT_WHERE`) rather than another comparison that has to be resolved to ids (#499's). It carries **no filter chip of its own**: it is the same category as `needsAction` — a live marketplace entry that is wrong and only the collector can put right — so *Needs action* selects **both**, unioned as ids in `resolveOfferOverlays` (never folded into `needsActionRows`, which counts *dead copies*, which drift is not) and deduplicated for the facet, since removing a set that sold elsewhere is itself a change and one offer must not be counted twice by a badge that opens one list. The URL narrowing survives as `listingOutOfDate=1` with a chip rendered **only while it is on**, the #481 rule — a filter reached by a link with no way back off it is a list quietly lying about what it holds — because the notification centre's own group (`offer-listing-changed`, `warning`, graded below the `critical` pair on the one line drawn everywhere here: no double sale is possible) has to land on exactly the rows it counted. That group is read **oldest-divergence-first**: it is a backlog, not news, and nothing in the world will ever mention a stale listing if it does not. The trigger is #513: a set joining an offer that was already posted is the case the whole signal exists for. Two changes sit outside it on purpose — an auction's **current** price is an observation of the bidding (#449/#481), not something the seller changed, while its **starting** price is the seller's own statement and counts; and the generated photos keep their own out-of-date signal (#311), which says the same kind of thing about the images and says it on the card the images are on. It clears on exactly three acts, each of which genuinely puts the current contents in front of buyers: publication (`ready → active`), an Assistant **update** that saved — reported `updated` and written by the *page* through `markOfferListingSyncedAction`, the same "the extension reports, the instance decides" rule (#407) the publish path follows, and the one write #462 said an update makes — and **Mark listing up to date** by hand, which every platform with no update flow needs and which is also the answer when the change was not worth going back for. Pausing and **resuming** clear nothing: a resume puts the same entry back up. And a closed listing simply stops reporting, the flag being *derived* as `listingContentChangedAt && isListedState(state)` in both readers rather than cleaned up on every terminal transition. Pictures are a **replacement**: the listing's existing set is deleted first (`a.del-button`, Colnect's own AJAX, one at a time and each waited out — a burst is how an account earns a 429 mid-edit, #487's reasoning arriving at the same answer), because appending would leave the live listing carrying two of everything on the second run; a deletion Colnect does not confirm **stops the upload** rather than duplicating the set, the form staying filled and the offer's ZIP being the fallback #411 already wrote down. That is also why `attachPhotos` may answer asynchronously here — #493 opened that door for Allegro's watermark dialog and this walks through it for a plainer reason. A saved edit is reported `updated` and writes **nothing**: the offer was Active before the run and carries the very URL the run was sent to, so the publish path is not merely skipped but unreachable — which is what `PendingListing.mode` is for, Colnect answering a saved edit with the identical entry page a saved new sale lands on. The bulk workspace (#322) is untouched, being scoped to Ready offers because posting is what a batch is for.
- Assistant **lot capture** (#355; ADR-0015 §third-half, ADR-0021 §8) is the extension's third module half — `capture` (`isListingUrl` / `capture`, `extension/src/platform/capture.ts`), beside `extraction` (now optional too) and `listing`. Allegro carries **capture alone**, and that is a complete module: a marketplace this collection only ever bids on is neither a catalogue to match against nor a shop to list into, so `PlatformModule` has no required half left and `moduleReports()` names all three. The toolbar click therefore has a **third meaning**, decided in the worker off the URL alone (`findCaptureModuleForUrl`) because the click is what grants `activeTab` and no content script has run yet: registration, capture, match. Capture opens `capture.html` — a window of its own, sharing only the profile badge and the window slot with the match window, since one lot's five fields and a page of candidate stamps are different questions. Reading is the **page's own JSON**, never its markup: Allegro renders through `opbox` boxes that ship their data beside them as `<script type="application/json">` while every class name is hashed per build, so a selector would break silently and a capture that breaks silently records a lot with no bid. Three blobs found **by shape** (the box ids are opaque and per-page): `biddingSection` → closing instant + current figure + currency + `popularityLabel`, `sellerName` → the seller, JSON-LD `Product` → the title (`document.title` carries Allegro's own suffixes). The auction test is `biddingSection.visible` — a *Kup teraz* offer carries the identical section with `visible: false` and a null `endingDate` — and a fixed-price page is a **refusal naming what the page is**, not an error: there is no bid to observe and no close to age against, and a lot invented from one would sit in the watchlist forever. The one judgement the module makes is **bid or opening price**, from the bidder count (`/licytuj/`, so the fixed-price *"9 osób kupiło"* in the same field reads as none): with nobody bidding, Allegro still prints "Aktualna cena", and recording that as a bid would cost the parcel money nobody has offered (#351). Allegro's *Numer oferty* is the same digits as the offer id and is carried **twice on purpose**: `platformOfferId` is the listing's identity, matched on and never shown, while `lotNo` is a number *on a lot* — the slot a house sale's lot number occupies, displayed and editable — so the watchlist reads the same however a lot got there. The URL stored is the canonical `/oferta/<offerId>`, never the slug or the `/produkt/…?offerId=` shape — the id is the part of every address that is the listing, and it is what makes a **re-capture a refresh**. `findCapturedLot` looks for it in **both places it is recorded**, because a lot added by hand carries whichever the collector happened to type: `lotNo` **equal** to the offer id, scoped to sales on that platform (an offer number is unique on the marketplace, so equality is the whole test — and the scope is what stops a house sale's `Lot 42` being read as offer 42, one field over two vocabularies), or the `url` at the **address's own boundaries** (`/<id>`, `-<id>`, `offerId=<id>`) and never as a bare substring, `8795065609` otherwise matching the middle of `18795065609` and refreshing a different auction's bid. A match then writes and then writes `currentBid` + `checkedAt` through `setAuctionLotBid` and **nothing else**, because the title, the closing time and the composition are what the collector has since typed. Everything about *where* it lands is server-side: the platform from `Contact.platformModule = "allegro"` (Settings → Allegro, one select, the exclusive setter now shared with Colnect's identical question in `module-platform.ts`), the seller resolved by name through `resolvePurchaseContact` as a typed-in name is, the parcel through #352's open-sale matching. `dryRun` is the same function answering what *would* happen, so the window's preview can never describe something the save would not do — and it resolves nothing into existence, hence the seller **lookup** rather than a resolve on that path. There is deliberately **no declarative content script for allegro.pl**: the feature starts with a click, which is also what grants access, so the script is injected then rather than run on every page of a shop the collector browses. An unset platform is a refusal pointing at the tab that fixes it (`no-platform-module`), never a guess. **Find in Stamporama** (#529) is the extension's fourth gesture and the only one that is not a toolbar click: a *selection*, right-clicked, on any page at all (`contextMenus`, `contexts: ["selection"]`). The icon's three meanings are decided by what the page **is**, and this one by what the collector **pointed at** — a different question, so a different affordance rather than a fourth branch in `chrome.action.onClicked`. It needs no content script and no `activeTab`, the text arriving inside the click (`info.selectionText`), which is exactly what makes it work on the marketplaces no module here covers. The window (`search.html`, `extension/src/search/`) shares the Assistant window slot with the match and capture windows and carries the selection as `?q=`, put in an **editable** box rather than searched for silently: a selection catches whatever the mouse caught, so refining it is a keystroke instead of a second drag on the page. The read is `GET …/api/collections/<id>/search?q=` (`src/lib/collection-search.ts`, session-or-token as every other Assistant route), and it **decides nothing about what matches** — the stamp half is the inventory picker's own search (#104/#73), the issue half the issue picker's, the copy half the Copies list's (#106), because the three lists a collector reads already disagree about what a query means and a fourth notion invented here would answer a question no screen would then repeat. The *stamps* group carries the answer the menu was clicked for, and the window renders it as **two sections**: the stamps carrying open **wants** (#532) are split out into a section of their own, **first**, and *Stamps* is what is left. A section rather than a chip on a row, because a want found by scrolling past twenty stamps is a want found too late; **split** rather than highlighted, because a row appearing in both would make the leading section a decoration rather than an answer (the link is the same either way, so moving it costs nothing). Wanted leads because it is the answer that decides a bid — holding a copy does not close a want, so a stamp already in the collection may be exactly what is being looked for in another condition, and a count that only said how many are held would answer the easier half. A want row is **one row per want**, ordered most urgent first across the whole result and edged in the priority colour, led by the axes in the want list's own wording with the *stamp underneath* — the inverse of every other row here, since at an auction the decision is made on the condition, and a chip reading `1 want` sends the collector back to the app. Two wants on one stamp are two decisions and never a count. The `here` / `coming` figures are that **want's own**, not the stamp's — a mint-only want reads zero beside a used copy in the drawer — and `coming` is what stops a second purchase of something already ordered; `toSort` folds into `here`, sorted-versus-on-the-desk deciding nothing at an auction. The acceptance **ids** the app's summary carries are dropped at the boundary: nothing in that window holds a copy to test them against. The held count rides on want rows too (that pair *is* the upgrade case), travels as both figures (#348 and #528's variant descendants), is **never summed** — a copy of a specific variant is not a copy of the umbrella — and reads **Not held** at zero, an empty badge being indistinguishable from a badge that failed. The **negative** want answer is a sentence rather than an absent section, which is indistinguishable from a window that never asked. Rows carry **relative paths** and the origin is composed extension-side against the one the profile authenticated against, #466's rule; the menu is `removeAll` + `create` on both `onInstalled` and `onStartup`, Chrome persisting context menus and refusing a duplicate id, so a bare `create` would make an update the one event that breaks the entry.

- The match window **confirms a decision, not a write** (#515). `askConfirm` in `extension/src/popup/index.ts` is raised by `confirmOne` (which names the one candidate stamp it links, out of several) and by `overwriteOne` (which destroys a catalog number we hold) — and by nothing else. `writeAuto` writes without one: the button already reads `Write 8 auto-matches + 3 catalog numbers` and the badge above it names the target, so the overlay only restated the label just clicked, and an auto-match is by definition the case the matcher (#250) had no doubt about. It then **closes the window** the moment the instance answers — no pause to let the result line be read, which would only be the dismiss step this removed worn differently. A batch write is the last act in this window, and closing loses nothing, since the write is already on the instance and the next icon click re-scans; the merge and status line before the close stay as what the window falls back to should the close not take. The auto-close is the *batch* button's alone: resolving ambiguous matches is done several in a row, so those keep the window up. The **capture window closes on a successful save** for the same reason (#522): one lot is one window, the composition is entered in the app rather than here, so the save is the last act — and a failed save keeps the window up, holding the corrections typed into the form beside the reason they did not land.
- The instance's own **Allegro API access** (#476; ADR-0023) is the other half of Settings → Allegro and has nothing to do with the capture module above it: the select names a marketplace the collection *buys* on, this connects the account it *sells* from, and #467 (sold-listing worklist) and #463 (order → `Sale`) are what read through it. It ends at *connected* and reads no business data. Naming the account is a **courtesy, not a gate**: `storeGrant` writes the grant first and *then* tries `GET /me`, because that endpoint needs the profile scope an application registered only for offers and orders does not carry — making it the precondition turned a token Allegro had just issued into "Not connected yet.", which is the worst possible answer to a collector who has just confirmed a code on their phone. A null `accountLogin` therefore renders as a connection without a name, and `testAllegroConnection` reads **403 as success** (Allegro accepted the token and declined *this endpoint*) against 401's failure — telling those two apart is the entire value of that button. Self-hosting is what puts credentials in the database at all: no OAuth application can ship in a public image, so each instance registers its own at `apps.developer.allegro.pl`, and `AllegroConnection` is **one row per collection** (the app has one authorization model — `collectionId` + owner check — and an instance-level secret would sit outside it). The **device code flow leads** and the authorization code flow is offered beside it, never instead: an install with no inbound DNS is the common case, and only the device flow works there. Which flow made a grant is deliberately **not stored**: the refresh is identical either way — same endpoint, same two parameters, no `redirect_uri`, which belongs to the initial code exchange alone. Where the two *do* differ is unguessable and cost a debugging session: `POST /auth/oauth/device` takes `client_id` in the **query string** while every other exchange uses the form body, and sending it in the body is answered *"OAuth 2.0 Parameter: client_id"* — not a wrong id but no id, Allegro never reading the body. Hence `deviceCodeUrl()`, exported so the shape is unit-tested rather than trusted; **neither** request asks for scopes, which come from the application's own registration and can be granted nowhere else — requesting one the application lacks fails the whole authorization, and Allegro reports *that* as `client_id` as well, so two unrelated faults arrive under one misleading message. Accepting whatever the application carries costs least-privilege and buys a setup that cannot fail opaquely; the collector registers the application for Stamporama, so narrowing it is theirs to do where it is visible. The client secret and both tokens are **sealed** (`src/lib/secret-box.ts`, AES-256-GCM under `STAMPORAMA_SECRET_KEY`): `api-tokens.ts`'s hashes do not transfer, a refresh token being replayed rather than verified, and a database dump is a routinely-copied artefact in a self-hosted install. GCM specifically, so a flipped byte fails *here* rather than downstream as an Allegro rejection that reads like an expired grant; the client *id* stays plain so Settings can name the application even with the key missing. `allegro-connection.ts` is the only module that decrypts anything and `getAllegroAccessToken` is the whole downstream contract — a token good for the next two minutes, or `AllegroNotConnectedError`, never a decision about refreshing. Every unusable state converges on **one** latched `needsReconnect` + `lastError`: a rejected refresh, a 401, and secrets that no longer decrypt are one situation to the collector, and the next step is the same for all three. Disconnect drops **locally only** — a local drop always succeeds, including from the dead-token state one is most likely disconnecting *from*, while a revoke's only honest failure handling is to disconnect anyway; the guide says the grant stays listed on Allegro. `allegro-api.ts` is the thin client (base URL, `application/vnd.allegro.public.v1+json`, bearer, 429/5xx with Allegro's own `Retry-After` honoured and capped) and imports **nothing** from the store — the store calls into it, which is what keeps the two from being a cycle and the backoff rules testable without a database. Sandbox is a property of the **connection**, not the deployment, because a sandbox application has its own credentials; changing the client id or that toggle drops the grant, since a token belongs to the application that issued it. The pending device code and the code flow's `state` live in memory on `globalThis`, deliberately: both are single-use and expire in minutes, and persisting them would add a third and fourth secret to a table whose point is holding as few as possible — losing them to a restart costs one click, losing a *token* is what the row is for. The callback route (`/api/allegro/callback`) is not collection-scoped and reads no session: the redirect URI is one fixed registered string, and the `state` is the entire authorization. `STAMPORAMA_SECRET_KEY` carries a **fixed local-dev default** in `docker-compose.yml` and in `.env.example` — `POSTGRES_PASSWORD:-stamporama`'s precedent, since that file only ever runs the local stack — but deliberately **none in `secret-box.ts`**: a production install that forgets the variable has to fail loudly on the Settings tab rather than quietly seal real credentials under a key published in this repository. `.env.prod.example` therefore ships it commented out, and `scripts/install.sh` **generates** one — deliberately with no menu, unlike `BETTER_AUTH_SECRET` beside it: rotating this key silently turns every stored connection into "needs reconnecting", so the installer only ever ensures a key exists (fresh install, or an upgrade predating the variable) and never touches one already there. Rotating is an explicit `.env` edit, which is the friction it deserves. Every request to Allegro — API **and** token endpoints — carries a `User-Agent` of `Name/Version (+repo URL)`, which Allegro requires (mandatory from the end of June 2026) so they can contact whoever generates the traffic: `allegroUserAgent` (pure, unit-tested) builds it from `AllegroConnection.applicationName`, the name the collector gave their *own* registered application, and falls back to `Stamporama` when unset — a label, not a credential, so a blank field clears it rather than keeping the stored one, unlike the client secret beside it. It rides on `AllegroCallCredentials` (`accessToken` + `sandbox` + `userAgent`), the object `getAllegroAccessToken` returns and the sync already spread whole.

- The **Allegro sold-listing worklist** (#467; ADR-0024) is what reads through that connection, and it produces **observations, never financial records**: `runAllegroSync` writes to no table the collector owns, and creating the `Sale` stays #463's explicit act. The observation lives in **rows of its own** rather than as a state on `Offer` — an order line is not one-to-one with a listing (stock above one sells a copy and the offer stays `ACTIVE`; one order carries several offers; an unmatched line has to live somewhere or the collector never learns a listing was posted outside Stamporama), so it is `AllegroOrder` + `AllegroOrderLine`, keyed on **Allegro's own ids** (`@@unique([collectionId, orderId])`, `@@unique([allegroOrderId, lineItemId])`), which is the whole of what makes a re-run a refresh rather than a re-import. The **header is its own row** rather than order columns repeated per line — status, buyer and total are facts about the order, one order routinely carries several listings, and the screen reads at that level too, a card being an order. The buyer is read down to **who, never how to reach them**: `buyerLogin` + `buyerName` and `totalPaid`/`currency` from Allegro's own `summary.totalToPay` (delivery included, so it is what changed hands and is `Sale.buyerPaidTotal`'s anchor, #205 — a sum of the lines is a *different* number that would quietly disagree with the sale about one order). The email, phone and delivery address on the same payload are deliberately **unread**: they are the sale's, and #463 fetches the order by id at the moment the collector confirms it rather than a background job keeping personal data warm for a feature that may never touch that order. Where the answer is **derivable it is derived, not searched for** (#480, `attachSuggestedSales`): a line matched an offer and `SaleLine.offerId` names that same offer from the sale's side, so the two meeting on **exactly one** sale with no `externalRef` is not something to make the collector recognise — the card proposes it by number and links in one click. Several is **not a tie to be broken**: an offer can sit on several sales (#473 sells one set at a time) and a multi-line order can point at different ones, so ambiguity proposes nothing and falls through to the picker, since a proposal has to be better than a guess or it is just the guess with a confident label. One query for the whole page, indexed by offer. It stays a **proposal** and the sync never writes `externalRef` itself — an inferred link that emptied a row on its own would take the signal away exactly when the inference was wrong, which is #467's whole thesis applied to its own cleverness. **Linking an order to a sale recorded by hand** (#479) is deliberately the *same* key read the other way, never a second rule: `linkAllegroOrderToSale` writes the order id into `Sale.externalRef`, the one column the list already drops an order on, so a sale written months ago and one written from this screen leave the worklist for identical reasons. Candidates are sales with **no `externalRef`** — one that already names an order is spoken for, and offering it would be offering to overwrite somebody's link — on the Allegro platform where one is marked (no platform marked widens to the collection rather than refusing, the date and total being right there to judge by), within 90 days and sorted by distance from the order's date, fetched **on open** rather than with the worklist since thirty cards would otherwise carry thirty candidate lists nobody asked for. **Only `externalRef` is written**: the collector recorded that sale deliberately, amounts, buyer and lines included. An order another sale already claims is refused **naming that sale's number**, because "already recorded, as sale #12" is an answer and "failed" is not. The sold list filters on **two independent axes** — paid/not-paid over orders, matched/unmatched over lines — OR within an axis and AND across them (#475's chips), client-side over the one unpaginated batch (#322's reasoning); they are applied at the level each fact lives at, so an order left with no line falls out and a mixed order's *matched* lines can never appear under **Unmatched**, and the chip counts are over the whole batch, a count that moved as you filtered saying nothing about what is there to filter to. The **ended-unsold** half is deliberately not a second read: paging `publication.status=ENDED` answers with every listing the account has ever ended, so the sweep reads the **active** ones, `AllegroListing` is its snapshot, and a row the newest sweep did not see is marked `ENDED` rather than deleted — that **absence is the signal**, keeping the row is what lets it be shown with the date the listing was last seen up (hence `observedAt` is *not* restamped on that transition), and the derivation only ever runs off a sweep that finished (`listingsSweptAt`), a half-finished one reporting everything it had not reached yet as ended. The two sit **beside** each other on `offers/allegro` rather than in one list: a sold row is a sale to record and an ended row is an offer whose state here is wrong, and one list carrying both needs a chip per row explaining what it wants. An unmatched *ended* listing is reported nowhere — the action is "correct an offer" and there is no offer to point at — while an unmatched *sold* line very much is, the missing match being the news. A **cancelled** order appears in neither: nothing is waiting, and offering a sale for an order the buyer withdrew is the app making a financial suggestion about a transaction that did not happen. Passes follow `/order/events` from a stored cursor because a dated read cannot see an order whose only change was **a payment landing**, which is exactly the transition the list cares about; with no usable cursor (first sync, or one Allegro no longer accepts) the pass reads `/order/checkout-forms` over 30 days and mints the cursor from `/order/event-stats` **before** that read, so an order landing during the import is caught by the next pass rather than falling between the two — and a rejected cursor is therefore not an error at all but the stream having moved past us, the fallback being safe precisely because every write is an upsert. **Matching** is the external id (the offer number, exact, present only where the listing was published through the API) and then the stored `Offer.url` at the address's own boundaries — `platform-offer-url.ts`, now **shared with #355's capture** in two readings, a Prisma `OR` arm and an in-memory predicate, since the sync holds its candidates already; two offers claiming one listing is a **refusal**, not a coin toss. Every pass ends with `rematchUnmatched`, and it is **not** an optimisation but the thing that makes the fix work at all: a match is decided when a row is written and the event stream only rewrites orders that *changed*, so an order imported before its offer had a URL stayed unmatched for ever however carefully the field was then filled in — the only escape being to clear the cursor and re-import a month to recompute one column. It costs one query and no Allegro request (the candidates are loaded once per pass), and it touches **only the unmatched**: a match already made is a fact the collector may have acted on, and re-deciding it quarter-hourly would let an edited URL silently move an observation from one offer to another. Every judgement is pure in `allegro-sync-rules.ts` (`paymentStatusFor`, `lineAwaitsSale`, `matchListingToOffer`, `windowFloor`, `syncFreshness`), `allegro-sync.ts` is the I/O half and decides nothing, `allegro-worklist.ts` is the read. The poll is quarter-hourly in the existing in-process pattern (`src/instrumentation-node.ts`, ADR-0018) with a **Sync now** beside it; a pass claims its collection so the two cannot read one stream twice, and the claim **times out**, a lock nothing can release being worse than a second pass over idempotent writes. Failure is visible **where the list is read**: the header names not-connected, needs-reconnect, no-platform-marked-as-Allegro, the last failure with Allegro's own message, and an hour without a pass — a stale worklist that looks current is the failure mode the whole thing is designed against. A **401 latches `needsReconnect`** rather than `lastError` (ADR-0023's single convergence point), and *not connected* reports `skipped`, not a failed sync. - A `Contact.platformModule` id is **not a promise about listing** (#471). Ask `hasListingModule()` (`src/lib/platform-modules.ts`), never `platformModule !== null`: only Colnect's module has a sale form here, while Allegro's (#355) names the marketplace a captured auction lot belongs to. Everything about listing — the preconditions (#406), the listing kit (#405), **⚡ List via Assistant** and the platform-catalogue card (#423) — is Colnect's rule, and the truthiness test quietly promoted Allegro to a listable platform: its offers were drawn a card of Colnect links and refused `ready` over Colnect item-IDs nobody had recorded. A third module added for some other purpose must not inherit those rules by existing.

- The client's **write half** (#485; ADR-0023 §6–7) is `allegroPost` / `allegroPatch` / `allegroUploadImage` beside `allegroGet`, sharing the base URL, the versioned media type (which is the `Content-Type` of a JSON write as well as the `Accept`), the bearer, the `User-Agent` and the error parsing — and **not** the retry policy, which is the one thing that is not the same conversation on a write. A read repeats a 429, a 5xx and a dropped connection alike; a write repeats **only a 429**, because a rate limit is Allegro refusing the request before doing anything with it while a 5xx may be an offer created and then not reported, and `POST /sale/product-offers` carries no idempotency key — two listings on a live selling account for one press of Publish is worse than a failure the collector repeats by hand. `PATCH` follows the same rule despite HTTP idempotency (a repeat this app decided is still a second edit of a live listing). The **image upload is not a form upload** and was corrected by #487 before it had a caller: `POST /sale/images` takes the picture as a **raw body** under the image's own `Content-Type` (`image/jpeg` / `image/png` / `image/webp`) and lives on a **host of its own** — `upload.allegro.pl`, `upload.allegro.pl.allegrosandbox.pl` in the sandbox, hence the third member of `allegroHosts` — so #485's `multipart/form-data` POST against the API base was wrong on both counts and is now `allegroUploadImage`. A create answers **201 or 202** and the two are not one thing: `AllegroWriteResult` (`status` / `accepted` / `body` / `location`) is what stops a 202 — work accepted, operation still running — being recorded as a published listing. **Scopes** are still never requested (ADR-0023 §1) but are now read *back*: Allegro's access token is a JWT carrying a `scope` array, so `readTokenScopes` + `grantsOfferPublishing` (pure, `allegro-oauth.ts`) put the connected application's own permissions on Settings → Allegro, decoded **for display only and never verified** — nothing is authorized on the strength of it. Unknown is kept apart from none: an unreadable token reads as *permissions could not be read*, never as an empty list. Publishing needs `allegro:api:sale:offers:write`, which a connection made for #476's read-only work does not carry, and adding it to the application requires a **reconnection** — a grant keeps the scopes it was issued with, which is what the panel and the guide say. A refusal that is a missing scope is reported as one: `WWW-Authenticate: …insufficient_scope` is the only thing separating it from any other 403 (Allegro's body says only "access is denied"), so `AllegroApiError.insufficientScope` carries it and the message names the fix — and it deliberately does **not** set `unauthorized`, that flag latching needs-reconnect, which is exactly what does not fix a permission the application was never registered with.
- An **Allegro listing profile** (#486; ADR-0025) is what a listing is published *with*, and it is the collector's **account configuration** rather than anything about a stamp: the shipping rate set + handling time, the return policy and implied warranty, the city/post code the parcel leaves from, the invoice promise. Held as a named `AllegroListingProfile` on the Allegro platform `Contact` (like #468's price list), with `Contact.defaultAllegroListingProfileId` the one every listing uses and a nullable `Offer.allegroListingProfileId` overriding it — the `defaultCollageTemplateId` shape (#308), both `SetNull`, and `resolveAllegroListingProfileForOffer` the single statement of the fallback so #477's publish never restates it. The three dictionary fields are **Allegro's own ids** (`GET /sale/shipping-rates`, `GET /after-sales-service-conditions/*`), each with a snapshot `*Name` that is a screen label and never the truth; they are read **live** whenever the editor opens and **not re-validated on save** — a rate set deleted on Allegro is #477's refusal, and a save that called the marketplace would only mean a settings screen that stops working when the connection is down. Deliberately **not** `ShippingMethod` (#468), which is what a buyer paid on a recorded sale, and deliberately not the category/parameters (#488), which are about the stamp and are learned rather than configured.
- An offer's **photos reach Allegro as an upload, not as a link** (#487; ADR-0023 §8, `src/lib/allegro-images.ts` + the pure `allegro-image-rules.ts`): an Allegro offer carries `images[]` as **URLs**, and ours are private bytes behind the Assistant token (#253) — an instance on `localhost` has no address Allegro could fetch from and one on a VPS should not publish an authenticated route to a marketplace — so the server sends the bytes, which unlike the Assistant path (#411) it already holds. The set and its order are **read, never re-derived**: `readOfferUploadImages` is `getOfferPhotoPlanState`'s own upload set (#311/#313, do-not-publish and over-limit already dropped, the collector's order kept), the very read both ZIPs are built from, so an uploaded picture and an unpacked one are the same bytes under the same name — first image first, the first being the listing's thumbnail. **Nothing is cached on the photo row**: Allegro states an `expiresAt` and deletes an image no listing used, so a stored URL goes stale on its own with nothing here to notice, and a published listing pointing at nothing is the cost of getting that wrong; a re-publish re-uploads, and a failed one therefore leaves nothing behind to clean up. Uploads run **in sequence** (a burst of parallel multiparts is how an account earns a 429 mid-publish) and the first failure **stops the run** naming *the picture* — `AllegroImageUploadError` carries the photo, its plan name and its 1-based position, and `describeAllegroImageRefusal` turns 413 / 415 / 422 into three different next steps, since a listing with fewer pictures than were prepared is the outcome this exists to prevent. Only the **format** is judged locally (the three Allegro takes); no byte ceiling is invented, because Allegro publishes none and a made-up limit reported as theirs would refuse what the store would have accepted. A dead token or a missing scope is re-raised as the `AllegroApiError` it arrived as — that is about the connection, not about a photo.
- Allegro **categories are learned, not configured** (#488; ADR-0026, `src/lib/allegro-category.ts` + the pure `allegro-category-rules.ts`): a listing needs `category.id` and that category's `parameters[]`, and unlike #486's profile neither is a property of the account — they are a property of *this stamp*, which is why nothing is filled in up front and the app watches what was published instead. **Two registers**, deliberately: `AllegroCategoryLesson` maps an (area, year, condition, subtype) key → category, `AllegroCategoryParameterMemory` maps a (category, parameter) → the value last answered, one row per parameter. They are separate because the second is what makes a *new* key cheap once its category is picked and the first is what makes an old key free; one combined register would relearn every parameter the first time an area gains a new year. Every key part is nullable and null means **absent from this key**, produced either by a mixed offer (each fact enters the key only where the copies **agree** — a bundle spanning two years still asks about its area, condition and subtype) or by the fact not existing. Lookup **relaxes rather than fails**, in one fixed order: the exact key, then drop the year, then the subtype, then one level up the area tree and repeat — and the **condition is never dropped**. A rung is a *filter over rows*, not a row lookup (rows carry the fullest key the offer supported, so "any year" must match rows that have one), and an area rung matches a node **or any descendant**, which is what makes a lesson from Poland → Provinces reach Poland → Republic. A key nothing matches falls to `GET /sale/matching-categories` from the title, then to a manual pick from the tree — lookup has no failing outcome. Rows are per (collection, platform) with `timesUsed`/`lastUsedAt`, and recorded **on success only** by #477's call into `recordAllegroCategoryLesson` (a refused publish teaches nothing; the newer choice wins). The picker (`shared/allegro-category-picker.tsx`) and the correctable list in Settings → Allegro are the "always a suggestion, never a decision" half.
- **Publishing an offer through Allegro's API** (#477; ADR-0027, `src/lib/allegro-publish.ts` + the pure `allegro-publish-rules.ts`) is the fourth quarter of the Allegro selling half and the one act that writes to the collector's live selling account. It sits **beside** the Assistant listing path (#407/#408), never instead of it: a marketplace with no API is driven through its own sale form, and one with an API is not. The **listing kit** (#405) stays the shared statement of what an offer holds and is read here **directly rather than through its endpoint**, because the kit's own `blockers` are Colnect's rules (#406, narrowed by #471) — a Colnect item-ID, a Colnect grade — and asking them of an Allegro offer reports faults in a form nobody will fill. Allegro's refusals are its own, and the single rule the two genuinely share is exported once (`differingSets` in `listing-preconditions.ts`): one quantity may only describe interchangeable sets, which on Colnect is a form field and here is `stock.available`, and two implementations of "these sets are the same goods" is how they drift. `setIdentity`'s fallback to the **local** stamp + condition is what makes that answerable on a platform with no catalogue of its own here. The request is assembled **purely** so what would be sent is assertable without a marketplace, and two of its shapes are decisions rather than transcription: `sellingMode` carries the format (#449) and only the figure that format *states* — `BUY_NOW` at the asking price, `AUCTION` at the **starting** price, an auction's `price` being an observation of the bidding that would put a bid nobody made into the listing — and **`external.id` is the offer number** (#416), which is the whole reason the read side (#467) is exact rather than derived from an address. **Draft leads**: Allegro takes `publication.status` in the create call itself, so both are offered at no cost and `INACTIVE` is the default — a listing seen by buyers has been seen — with `ACTIVE` moving the offer `ready → active` through `publishOffer` (#246/#320), never around it. **Activate** is the same control in the same place afterwards, a draft reachable only by going to Allegro being a listing nobody returns to. Every refusal is named **before** the request: the connection first and alone (#485's write scope included, where `null` is *unreadable* and deliberately not a refusal — nothing is authorized on the strength of a decoded token), then a listing already published, then an unfinished offer, and then everything else **together, one line each**, since each is fixed somewhere different. An **over-long title is refused, not shortened** — Allegro caps 75 and the kit does not, a cap being the platform's — which is #405's answer to an over-long Colnect text. A create answers **201 or 202** and #485's `AllegroWriteResult` keeps them apart: a 202 is polled at `GET /sale/product-offers/{offerId}/operations/{operationId}` to one of three outcomes, none of which is "probably fine" — succeeded, **failed reported in Allegro's own words**, or **still running at the bound**, which records the Allegro offer id (so a second press cannot duplicate the listing) and moves nothing. An unrecognised operation status reads as *still running*, since treating an unknown answer as success is how a listing Allegro later refused is recorded here as live. Only a conclusive success writes: `Offer.url` + the transition on a live publish, `Offer.allegroOfferId` / `allegroPublishStatus`, and the category lesson (#488, ADR-0026 §5) — a refused publish teaches nothing, and a register write failing is not worth losing a published listing over, so it is swallowed. The id is **not** a second copy of what #467 matches on (that runs off `external.id` and `url`): a draft has no public page and so no URL, and the id is the address activation is sent to. The **description is rewritten on the way out** (`allegro-description.ts`, pure, no DOM and no dependency, ADR-0027 §4a): Allegro's `description.sections[].items[].content` is not an HTML field but seven tags — `<p>`, `<h1>`, `<h2>`, `<ul>`, `<ol>`, `<li>`, `<b>` — with **no attributes at all**, while our shared renderer emits `<p style="white-space:pre-wrap">` for `plain` and `<strong>`/`<em>`/`<a href>`/`<h3>` for `markdown`, so sending what the offer screen shows is a 422 naming the field and nothing else — which is how it was found. The conversion is **lossy on purpose and never destructive** (an unsupported tag is dropped and its text kept, a link becomes its words, `<h4>`→`<h2>`, `<br>`→a paragraph, loose text wrapped), and it lives at the one point that knows the text is going to Allegro rather than narrowing what a collector may type. A **refusal names the fields, not the sentence** (§4b): Allegro's `errors[]` carries one entry per bad field with the information in `path` + `message` while every entry's `userMessage` repeats *"Request contains invalid data"*, so `describeFailure` reads them all, prefixes the path, dedupes and caps, and `AllegroApiError.details` carries them as data for the dialog to render a line each. **Neither wording leads** and that took two goes: the first `userMessage` alone turns a per-field refusal into one sentence naming nothing, while `message` alone turns Allegro's *most* informative refusals into `"Unprocessable Entity"` — which is exactly where Allegro puts the HTTP phrase while the sentence sits in `userMessage` (`ParameterCategoryException`, and the business-account refusal). Both are kept and `informativeMessage` discards whichever is boilerplate; this is load-bearing rather than cosmetic, since `namesIneligibleAccount` reads that same string and under the `message`-only rule would never have latched. `STAMPORAMA_ALLEGRO_DEBUG=1` logs a refused call whole (request body + raw answer, never the bearer), off by default since a publish body is the entire listing — but **on** in `docker-compose.yml`, `STAMPORAMA_SECRET_KEY`'s fixed-local-default precedent, since that file only ever runs the local stack and a refusal there lands in the developer's own terminal (the dev overlay inherits it; `0` in the environment turns it off). Only a category's **offer** parameters are *sent*, but **both** sections are asked for and stored (#494): Allegro splits them into an offer section and a product one (`options.describesProduct`), and product-offers refuses a product parameter among the offer's own by name (`ParameterCategoryException`, *"`9525:Klej` should not be specified as in section `offer`"*) — it belongs in `productSet[].product.parameters`, the catalog path, which is a non-goal. The filter therefore lives **in the request that has the restriction** and nowhere earlier: an intermediate pass applied it at `getAllegroCategoryForm`, the read the picker and the offer's card share, which quietly stopped the collector being asked for values the *other* listing path needs — Allegro's own sale form (#493) asks for both sections and the collector answers both. Each stored answer carries its own `describesProduct`, and a required *product* parameter is deliberately **not** a publish blocker, this request being unable to carry it either way. The category, its answers and the profile all live on the **offer** (#494; ADR-0027 §1a, `allegro-offer-listing.ts`) rather than in the publish dialog, so both listing paths read one place: `Offer.allegroCategory*` + `allegroCategoryParameters` beside #486's `allegroListingProfileId`, surfaced as `OfferDetail.allegroListing` and edited on the offer's **On Allegro** card. The category is filled in by `backfillAllegroCategory` from the same three add-copies mutations `syncGeneratedTexts` hangs off (#365/#380), but as a **backfill and never a refresh** — a title *describes* the composition while a category is a decision about what the goods *are*, and re-deriving it under a correction would undo it silently; ↻ on the card is the explicit re-match, and the backfill can never fail the mutation it hangs off (a marketplace that is down costs a blank card, not a refused set). **Nothing is a gate**: whatever matched is what publishes, `source` (`learned`/`allegro`/`manual`) + `matchedOn` carrying the provenance, because a value nobody can account for is one re-checked by hand every time. The register learns on **`preparing → ready`** in `setOfferState`, deliberately *not* at publication: ADR-0026 §5's "on a successful publish" is the wrong moment for a collection worked in runs — offers are prepared ten or twenty at a time and published days later, so a register learning at publication asks the same question twenty times and answers it after it stopped mattering. `ready` is where the collector has said what the stamps *are*, which is the whole of what a lesson claims, and an offer left in `preparing` still teaches nothing. It hangs off the **transition** rather than off each listing path so a new path cannot forget it; a category corrected on an already-`ready` offer is re-taught the next time it passes through, or corrected in Settings → Allegro. A category whose **required** parameters the register has never seen answered is refused *before* the request too — #488 remembers answers, not questions, and a suggestion alone cannot fill a field nobody has ever filled. Allegro's **selling endpoints are open to business accounts only** (ADR-0027 §4c), which is unaskable in advance — a private seller's grant is issued, refreshed and used for reading orders and bids without complaint, and the refusal arrives the first time something is published (*"You cannot use the Public API method when selling with a Regular Account"*). So it is **latched in Allegro's own words** on `AllegroConnection.publishRefusedReason` and every later publish is refused before a request. Deliberately **not** `needsReconnect` — ADR-0023 converges every *unusable* state there and this connection is not unusable, so saying "reconnect" would be a loop with no exit — and deliberately Allegro's sentence rather than a code of ours, this being a rule about somebody's account status the app does not administer. Cleared by a fresh grant and by re-registering the application (a sandbox one above all, where a business account is free): asking again costs one refused publish, never asking costs a permanent refusal that stopped being true. Detected on the **wording** (`namesIneligibleAccount`), the error code being undocumented and observed once. The practical consequence is that on a private account this whole path is a named refusal rather than a feature — and listing to Allegro from one is the **Assistant's** job, a listing half for #355's module and the sibling of #410. , and a create that then fails leaves nothing to clean up — Allegro removes an image no listing used, which is also why nothing is cached on a photo row. Editing a published listing, ending one, and publishing a **batch** are all deliberately out: each is a different act with a different failure story, and #322's workspace is the Assistant path's.
- **Listing to Allegro through the Assistant** (#493; ADR-0028, `extension/src/platform/allegro/listing.ts` + `src/lib/allegro-listing-task.ts`) is the second path to the same marketplace and the one a **private (Regular) account** has, #477's API being open to business accounts only. It sits beside that path, never instead of it, and nothing inspects the connection to choose: both are offered on a `ready` Allegro offer. Three things had to move before the module could exist. **The preconditions became per module** (`listingModuleRules` in `platform-modules.ts`) — `hasListingModule()` going true for Allegro would otherwise have turned Colnect's rules on for every Allegro offer and refused them all `ready` over a catalogue Allegro does not list against; what stays shell-wide is being Ready, holding copies and the sets being interchangeable, and the same entry gates the condition-map read and the platform-catalogue card (#423). **Allegro's refusals split by who they are about**: `allegro-listing-rules.ts` holds the listing group (title over 75, untruthful stock, no price/profile/category/pictures) which *both* paths evaluate, and `allegro-publish-rules.ts` keeps the API's own (connection, scope, account eligibility, already-published) and composes the two. **The configuration travels as `kit.allegro`**, a named section beside the neutral fields rather than Allegro-shaped fields on the kit, carrying **both** parameter sections and each answer's **display value** beside its dictionary ids — the form's `select` submits the option's *text* while the API takes `valuesIds`, and the labels are resolved best-effort from the category form. The module fills Allegro's **legacy** one-screen form, where every value maps onto a stable element `id` and each parameter onto **Allegro's own parameter id** (`#213`), the profile's three ids being the option values of `#shippingRatesId` / `#estimatedShippingTimeId` / `#return-policies`; no class name is ever read (#355). Text goes in through React's **native** value setter plus `input`, the description into TinyMCE's same-origin `iframe#id_ifr`. Getting to that form is a sequence whose middle steps are not page loads — a Regular account is redirected off the legacy address, and the way back is opt-out link → product search → *Kontynuuj bez wybierania produktu* → the category modal → the category number — so `PlatformListing` gained one optional member, **`prepare?(doc, task): Promise<void>`**, called exactly where the shell already reported `retry` (#419) and implemented by Allegro's module alone. The auction fields and the sending address are reported rather than set. The **listed URL is read off the page rather than off a navigation**: Allegro answers a submitted form by re-rendering the same document into `#thank-you-page` (the offer's link is in it, the address bar never changes), so `PlatformListing` gained `listedUrlInDocument?(doc)` beside `listedUrl(url)` and the content script watches for that page with a `MutationObserver` armed **at fill time, never on `submit`** (Allegro posts through script and raises no `submit` — a watch gated on one never starts), messaging `listed-here`; everything downstream is #412's existing write-back. Two fields the form needs and nothing else here answers live on the **profile** (#486's row): `durationLimit` (nullable — "leave the form as served") and `autoRepublish` (a plain boolean, written both ways), neither sent by the API path, which takes Allegro's own defaults. **Durations are matched by length, not string**: the profile holds `P3D` because that is what the API takes while the form offers `PT72H`, and an equality test silently leaves the default standing. `prepare` also **unfolds the form** before every fill — the rest of the parameters (behind *więcej parametrów*), an auction's own opening-price and duration fields (ticking *licytacja* replaces the quick buy's duration select), and the description editor (TinyMCE mounts only on a click into the placeholder) are none of them in the served document, and each is a React re-render, which is why they cannot live in the synchronous `fill`. Allegro also opens its **AI-watermark dialog** the moment pictures reach the uploader, and the module confirms it with **nothing ticked** — the truthful answer for photographs of stamps, and a claim it must never make on the collector's behalf — which is why `attachPhotos` may now answer asynchronously (Colnect's still returns directly).
- Assistant **distribution** (#288; ADR-0017, superseding ADR-0016) — published to an **unlisted Chrome Web Store listing**; the store assigns the ID and signs, so there is no CRX, no signing key and nothing served by the instance. `extension/pack.mjs` (`pnpm assistant:zip` from the root) writes a store ZIP with the app version stamped in; CI's `publish-extension` job uploads and publishes it per release tag (`CWS_CLIENT_ID`/`CWS_CLIENT_SECRET`/`CWS_REFRESH_TOKEN` secrets, `CWS_PUBLISHER_ID`/`CWS_EXTENSION_ID` variables), but only when `extension/` changed since the release the **store** already holds — asked for with `:fetchStatus`, taking the newer of the published and in-review revision, so a submission that failed or was paused is picked up by the next release rather than lost. The store's `uploadState` is `SUCCEEDED` on this API (v1.1's `SUCCESS` is accepted too); the job is also dispatchable on a tag, so a refused submission is retried without moving it. Self-hosted force-install was tried and fails: Chrome honours a non-store `update_url` only on an enterprise-managed machine. The unpacked dev build and the store build stay **two extensions** with two IDs (`extension/identity.mjs`; `manifest.json` carries no `key`), so both can live in one browser and a dev profile can never reach a production collection.
- Binary assets (photos, #112) sit behind the `src/lib/storage/` interface (filesystem + GCS, #138; ADR-0011; active write backend via `STAMPORAMA_STORAGE_BACKEND`, per-photo reads) — async/streaming, `resolveUrl` returns stream-or-redirect, write-one/read-many by per-row `storageBackend`. Bytes live under `STAMPORAMA_DATA_DIR` (the `stamporama-data` volume), never in `public/`; serve them through collection-scoped route handlers. Multipart uploads use route handlers, not server actions. `Photo` is polymorphic over **three** owners — `Item`, `Stamp`, `Offer` (#311, generated listing images, `kind = generated`; #313, images uploaded straight to an offer for a manual attachment, `kind = original`) — with a `num_nonnulls(...) = 1` CHECK; deleting any owner must delete the bytes explicitly (the cascade only drops rows). An offer's photo plan is part rule-derived and part manual: `OfferPhotoAttachment` (#313) is the *plan entry* that carries the distinction, so a regeneration recomputes the collages and leaves the attachments alone (#315). An attachment is **N tiles in C columns** — `copy_photo` and `upload` being N = C = 1, and `manual_collage` (#331) the collector's own selection (`OfferPhotoAttachmentTile`, mixing copy scans and offer uploads) at a width they pick, rows never stored because the contents are explicit. In the plan's vocabulary a plain `collage` is always one the rules derived, hence `manual_collage` for the hand-built one. Sets that have gone — sold here, sold from under the offer, or held by an offer in active bidding — are dropped from the plan's inputs in `readInputs` (whole sets, never single copies), which marks the stored images out of date through the fingerprint alone; terminal offers are exempt. Attachments render through the same one-tile collage path as everything else — there is no unlabelled pass-through (#312). A tile caption is sized from the **label strip alone** and never from its own text (#337): sizing to the text made one image carry a full-height label and the next a visibly smaller one. Text that does not fit the tile's width is truncated with an ellipsis, and a *shorter* strip is what makes more of it fit. The strip itself is `labelPercent` of the **finished image's longest edge** — not of the stamp, which is what the gap still uses: every image of a listing is scaled to the same platform limit, so only a share of the image renders at one size across a collage, a single scan and a wide detail crop. It is therefore circular (the strip grows the canvas it is a share of) and `collage-layout.ts` solves for it, capping all the strips together at half the page so a many-row collage stays solvable. The column is a **float**: against the whole image the usable band is about one to two percent and a whole number cannot land inside it. A template’s `rows` × `columns` has always been **capacity, not a frame**, and #413 adds the second reading of it: `gridMode = auto` treats the pair as *bounds* and `resolveCollageColumns` picks each image’s width from the tiles it actually holds, scoring every allowed width by `empty cells + |columns − rows|` and breaking ties wider — two terms because empty cells alone always answers *one column* and squareness alone puts ten stamps into 3 + 3 + 3 + 1. #514 keeps both terms and moves them onto **pixels**: the width is scored on the canvas it would actually produce (`autoGridCost`), `empty cells` becoming the uncovered canvas area over the mean tile area — which now also counts the space a definitive leaves beside a souvenir sheet in its own row — and squareness becoming a term on the canvas's real aspect rather than its cell counts, so a page of wide detail crops is judged on the letterbox it makes. #526 then replaces the *target* of that term: a collage is looked at on a monitor and as a listing thumbnail, so the grid aims at a **landscape band** — `shapePenalty` is 0 anywhere between 4:3 and 16:9 and grows with the log distance to the nearest edge outside it — rather than at a square, which used to let a page of tall stamps settle into a hole-free portrait column. Portrait canvases are still reachable, just never preferred. `SHAPE_WEIGHT = 3` is unchanged, and still what sets the parity between a step off shape and one tile-sized hole. Two consequences worth knowing: a row wider than the tile count is no longer a candidate (the canvas shrinks to its contents, so those columns are free and would win every tie), and the sizes are read from the **photo rows** (`plannedTileSizes` + `trueScaledSizes`, `FULL_MAX_EDGE` clamp undone as in the renderer) rather than by decoding, so the grid is solved before a byte is read. Gap and label strip are deliberately left out of the scoring — the strip is a share of the very shape being chosen, and the gap shifts every candidate alike. The product is still the capacity, so grouping (#309) never learns of the mode, and `layOutCollage` is still handed one concrete number. It is seeded onto the offer like every other collage value, where **null means `fixed`** — hence it is not one of the columns the all-or-nothing collage group tests, and the fingerprint hashes it **only when it is `auto`**, or every plan already generated would report itself out of date over images unchanged by a pixel. The **upload order** over the whole plan (collages and attachments) is the collector's to set: `Offer.photoPlanOrder` is a `String[]` of stable per-image tokens (`c:<side>:<sortedItemIds>` / `a:<attachmentId>`, also written on each stored `OfferPhotoEntry.token`), an *override* the pure engine reconciles against the derived order at read time — so a manual order survives a composition change or regeneration. A reorder is **applied to the stored images** (their entries are renumbered; bytes untouched), so either list can be the drag surface and reordering never marks anything out of date. **Nothing is ever dropped from the plan**: an image the collector marked do-not-publish (`Offer.photoPlanUnpublished`) or one past the platform's `maxPhotos` is still rendered and shown, just kept out of the numbered upload run and the ZIP — and the limit fills from the front of the order, protecting nothing, because the order is the priority order. **Grouping reads the platform's photo limit** since #521 (`Offer.photoPreferSingles`, seeded from `Contact.photoPreferSingles`, on by default): a collage is how more stamps fit than a listing has slots for, so the single-copy pool is spent on *one image per copy* first and only the tail is chunked — the largest `k` with `k + ceil((N−k)/capacity)` inside the budget, the budget being `maxPhotos` less what the multi-copy sets' collages and the attachments already cost (front/back counted as it actually falls, do-not-publish costing nothing). No `maxPhotos` is no collage at all for singles. `k` is **never zero** while the pool has a copy: the first image is the marketplace's thumbnail and one stamp reads better there than a grid, so the slot is spent even when the budget cannot afford it and `overLimit` reports the overflow. Multi-copy sets are untouched — a set is one thing being sold. The tail's collages sit at the **end of the last run of singles**, the arithmetic being over the whole pool. The flag is hashed **only when on**, and the migration leaves every offer with rendered images off, so the upgrade declares nothing stale; off is exactly #309's original chunking, which is what the pre-#521 tests and fixtures pin.
- The **bulk listing workspace** (#322) is a *sub-route* of Offers (`offers/listing/`) — the static segment takes precedence over `[offerId]` — and since #502 it is also a **nav entry of its own** under the Offers group, beside `Sold on Allegro` (`offers/allegro/`), on the reasoning #376 split Auctions with: three views of one subject, the list leading. The toolbar button stays, because it carries the platform filter across. The group's own `Offers` entry uses `isActive`'s `except` list rather than `exact`, since `offers/[offerId]` is still the list's own screen. It is scoped to one **platform** and to `ready` offers, reads its batch through one unpaginated route handler (`offers/listing`), and does grouping, filtering and year facets **client-side** from pure helpers in `src/lib/listing-groups.ts` (unit-tested) — a `ready` batch is bounded by what a person is about to type in by hand, and instant facets beat a page boundary. The per-offer posting kit (texts, photos) is loaded **on expand** through the existing `useOfferDetail` / `useOfferPhotoPlan` endpoints, so a forty-offer batch does not fetch forty descriptions to draw forty collapsed lines. Grouping and filtering are deliberately **different questions**: an offer is *grouped* under the `(area, year)` pair every copy shares (else **Mixed**, which the area rail carries as its own entry via `AreaFilterSidebar`'s `extraEntry`), but it *matches* an area filter when every copy is inside that subtree — so a year-spanning offer is Mixed yet still appears under its area. A copy's area is its stamp's **primary** area link and its year is `stamp.issuedYear`, matching the inventory list (#142). Publishing goes through `publishOffer`, which transitions first and writes the URL after, so a refused publication leaves no listing URL behind. The **offer's own screen** publishes the same way (#399): `ready → active` from the quick-advance button or the ⋮ *Activate* entry opens `ActivateOfferDialog` — moved up to `offers/` since it now serves both — and goes through `publishOfferAction`, but **only while the offer has no URL**; one that already carries a link has nothing to hand over and the header's field takes a correction. A transition asked for in two places had to ask the same question in both, or the URL was silently skipped on the surface a single listing is actually posted from. Which card is open is **derived, not stored** — a tri-state (`undefined` = nothing chosen for this batch yet → open the first; `null` = the collector shut it → honour that; an id → that card), so the first offer opens on arrival and after any batch change without a `setState`-in-effect. - A platform's **default starting price** (#362, narrowed to auctions by #449) is the *lowest-priority* price suggestion: a new auction takes `Contact.defaultStartingPrice` only when the lot's suggested price (#190) and the copies' catalog value (#230) — both of which reach the form as a filled-in figure — had nothing to say. It carries **no currency of its own**: the platform already locks one (#196), and a second one could only disagree with it. The fallback lives in `createOffer` (`resolveOfferPricing`), resolved *before* the live-status checks so an auction created straight as `ready` on a house that always opens at the same figure is not rejected as unpriced — the server is the single point that applies it, because a plain create does not even show the price fields. The dialog pre-fills it too, into the **starting-price** field and only while untouched, so what the collector sees is what the server would have written; it never reaches the current price, which no default and no suggestion may fill. Read at creation and never again: unlike the listing templates and photo defaults it is not *seeded* onto anything, since the offer's own columns are the record. It was originally a flat *asking* price for a quick-buy platform, and #449 narrowed it deliberately — the column is kept only while `defaultListingType` is `auction` (the contact writers clear it otherwise, and the form hides the field), because a quick buy's price follows from the goods and the two suggestions above are exactly the ones that describe the goods; a flat default there could only overrule them with a figure nobody had looked at the stamps to arrive at. The migration therefore renamed the column and **cleared** every value, every platform predating `defaultListingType` reading as a quick buy — a figure left on one would be a stored fact nothing reads.
- An offer is sold as a **quick buy or by auction** (#449) — `Offer.listingType` = `fixed` | `auction`, a fact about *this listing* and never about the platform, since a marketplace running both formats carries offers of either kind. The interesting decision is that `price` was **not** split: it keeps its column and gains a second reading — the asking price of a quick buy, the **current** figure of an auction (the standing bid, or the opening price while nobody has bid) — because every reader wants the live number and only the live number: the list rows and their base-currency equivalent (#208), the suggested-price comparison (#190), the ready/active price gate (#336), the listing kit (#405), the sale. A separate `currentPrice` beside a `price` holding the opening figure would have branched all of them on the listing type to arrive back at the same value, and two columns claiming one fact is how they drift. What the auction adds is `startingPrice` — where it opened — and `priceCheckedAt`, the auction lot's `checkedAt` (#351) on an offer, since refreshing a bid is manual by decision (ADR-0021 §8) and an undated figure says nothing about how current it is. All of it is resolved in **one** place, `resolveOfferPricing` in `offers.ts`, shared by `createOffer` / `duplicateOffer` / `updateOffer`, so a quick buy clears the auction pair wherever it is written — including a listing switched back to one, where a stale check date would describe a format it is no longer in. The price is dated only when the figure actually **moved**: a header save that retypes the same number is not an observation of the bidding, and neither is any other field on that form. `patchOffer` refuses a `startingPrice` on a quick buy rather than ignoring it — changing format is the header form's job, not a field quietly appearing beside the price. **Which of the two figures is required** is the format's own question and the counterpart of #336: going `ready`/`active` needs an asking price, but on an auction it needs the **starting** price (`requiresStartingPrice`), because that is the number the seller states while the current one is an observation — and an auction that is up with nobody bidding has none to make. The two are therefore **alternatives, not a pair**, and nothing is ever invented for `price`: an unbid auction carries `0` and reads as **No bids yet** rather than *No price yet*, because copying the opening figure into it would put a bid in the record that never happened. They move independently — correcting the opening price never touches a recorded bid, and `patchOffer` refuses to clear a live auction's *starting* price while freely clearing its current one, that one being an observation and "no bids after all" a legitimate correction. `missingPriceField` is the single server-side rule behind every refusal, returning *which* field is missing so each call site can name it; `pricingReadyFor` is that same rule for both quick-advance buttons, so a button offered is a transition the server will take. The same reasoning decides where a **suggested** figure lands in the dialog (a lot's price, the copies' catalog value, the source offer's when duplicating): a suggestion is what one would *ask* for the goods, which on an auction is what one would *open* at, so it fills the starting price and leaves the current one blank. A platform's **default listing type** (`Contact.defaultListingType`, nullable, null = *no preference* and deliberately not a stored `fixed`) is `defaultStartingPrice`'s rule again (#362) — read at creation and then owned by the offer — reaching the domain through `assertPlatform` and the dialog through `listOfferPlatforms`, and it is also what decides whether the default starting price beside it means anything at all (the two are written together in `platformListingDefaults`, since a price is meaningless without the format); an **edit** passes no defaults, since switching platforms must not re-describe a listing that already exists, and the dialog stops re-seeding the moment the collector answers the question themselves. The picker's platform facts travel as one `PlatformOfferDefaults` object rather than a fourth positional callback argument. The vocabulary, the parser (`parseStartingPrice`, which unlike `parsePrice` reads blank as *not recorded* rather than as an error — the transition gate is what asks for the figure, not the parser) and the price's own **label** (`priceLabel`) are pure in `offer-rules.ts`: what the field is called differs per listing type on three surfaces, and a ternary per surface is how two of them end up saying different things. The chip is deliberately shown for an **auction only** — a quick buy is what an offer ordinarily is, and a chip on every row of a long list is noise — and it sits beside, never instead of, *In bidding* (#215): one says the listing is an auction, the other that somebody has actually bid and the collector is committed.
- A platform's **shipping methods** (#468) are a dictionary hung off the *platform*, not the collection — `ShippingMethod(platformId, name, cost, currency)`, unique per (platform, name) — because postage is quoted by the marketplace the parcel sold on. Picking a method pre-fills `shippingCost` / `shippingCurrency` (#206) from the row and both stay editable — the price is what the method usually costs, not what this parcel cost — and a blank cost clears the money fields while leaving the method standing. It is picked in **two** places, the sale header dialog and the detail's `− My shipping` row, both going through `resolveSaleShipping`, which re-reads the row against the sale's own platform rather than trusting the client's name.
- An offer's **stamps on the platform's own catalogue** (#423) are a card of their own on the offer detail, between the images and the sets — the two pages a seller opens while pricing a listing: what the stamp *is* (its catalog page, #290) and what it is currently being **asked for** (the marketplace search at that grade). Keyed on `stamp × condition` and not on the copy, because that is what the marketplace pages are keyed on and a komplet is dozens of copies over a handful of stamps; a row states how many of the offer's copies it stands for rather than repeating itself. The market URL's condition segment is a **third Colnect vocabulary** — `ColnectGrade.marketSlug` (`mint_never_hinged`) beside the sale form's numeric `value` — stated in the table rather than derived from the label, since nothing guarantees the two agree; it is the one thing here that could not be verified against the live site (#419's interstitial refuses anything scripted) and is derived from the single confirmed example in #423, which is why it is one table and a one-line correction. `colnectMarketUrl` returns **null rather than a condition-less search**: a price for "any grade" is not the figure being judged, and a link that quietly answers a different question is worse than no link. Gated on `platformModule` exactly as the blockers are — one marketplace's catalogue, not a general fact about an offer — but deliberately **not** on the listing preconditions (#405): the collector is asking what the market wants, which is a fair question of an offer at any stage. A row an unmatched stamp (#247) or an unmapped condition (#404) leaves link-less is therefore **still listed**, disabled with its reason (#273), because the list that would have taken them to the market is where that gap gets noticed. It reads nothing of its own — the item-IDs come off the set select the screen already loads and the grades off the condition map already read once per offer.
- The **Colnect condition mapping** (#404) is the condition-side counterpart of #248's catalog-abbreviation mapping, and lives in the same place: one row per `StampCondition`, per collection, in **Settings → Colnect**. Per collection and not per platform `Contact`, because Colnect's vocabulary is **fixed and global** (#402 — the identical five options render under every item of a multi-item sale form), so only Colnect's option value is stored and the label it renders as lives in code (`src/lib/colnect-conditions.ts`, pure). The two rules it does **not** inherit from #248 are the interesting ones: there is no exact-abbreviation fallback and nothing is silently ignored — an unmapped condition is a listing **precondition failure** (#406), because a wrong grade on a published listing is worse than a blank the collector fills in. `guessColnectGrade` exists but matches the **abbreviation alone** and only ever proposes. Every condition is listed whether or not it is mapped, so a blank select *is* the unmapped state and a legitimate answer (no cover grade exists on Colnect); clearing a mapping **deletes the row**, so "unmapped" has one representation everywhere. The panel has no draft and no Save — the select is the control, one write per change — and `setColnectConditionMapping` validates against the built-in list, so a stored value can always be rendered and posted. `loadColnectConditionMap(collectionId)` is the read primitive #405/#406 build on, loaded **once per offer**: a komplet is dozens of copies over a handful of conditions.
- The **listing kit** (#405) is one read-only call — `GET …/offers/[offerId]/listing-kit`, session **or** Assistant token like the matcher (#250) — answering "everything this offer wants filled into a marketplace form": the copies' catalog item-IDs (#247), each copy's condition **already translated** into the platform's vocabulary (#404), the quantity, the price in the platform's currency, the two generated texts, and the photo plan's **upload set** in upload order as fetchable photo-route paths (the same route already takes the token, #253). **Platform-neutral in shape**: it says what the listing *holds*, never how a form is laid out — that mapping is the extension's platform module (#408/#410). One Colnect-shaped assumption is confined to `src/lib/listing-kit.ts`: the grade vocabulary comes from the collection's Colnect map, which is per collection precisely because Colnect's list is fixed and global (#402); a second marketplace with its own vocabulary turns `platformCondition` into a per-platform lookup and moves nothing else. `quantity` is the **number of sets** and `items` describes **one** of them — which is only truthful over interchangeable sets, hence the preconditions. Those are pure and separate (`src/lib/listing-preconditions.ts`, unit-tested), because the endpoint refuses on them and #406's card has to state the same reasons: not Ready, no copies, a stamp with no item-ID, an unmapped condition, or sets that differ. Homogeneity compares **what the form would receive** — item-ID + grade, order-insensitively — with the local ids standing in where either is missing, so two unmatched sets are never called interchangeable on the strength of two nulls. `not-ready` / `no-sets` return **alone**: with no composition there is nothing else to say, and listing four faults under an unfinished offer buries the one thing to do. A failing precondition is a **refusal** (409 with the blockers), never a payload with holes in it, because a wrong grade or an untruthful quantity misdescribes the goods — while an over-long text is not a blocker at all (#403): the platform's own field visibly refuses a long paste, and nothing about the stamps is misstated. The kit is still *returned* by the domain function with its blockers and its nulls, so the workspace card and the endpoint read one evaluation. Photos are taken from `getOfferPhotoPlanState`, filtered to `publish && !overLimit`, so the kit, the Photos card and the plan's ZIP can never disagree about which images are uploaded or what they are called; `outOfDate` travels as a signal and never as a refusal, stored images still being truthful pictures of these stamps. **Which platforms they apply to** (#406) is `Contact.platformModule` — the extension's `PlatformModule` id (`COLNECT_PLATFORM_MODULE`, `src/lib/platform-modules.ts`), nullable, and set **in Settings → Colnect by picking the platform** (`setColnectPlatform`), never on the contact form: it is one fact per collection — which platform *is* Colnect — and the collector deciding it is already on that tab setting up the catalog and condition mappings it belongs with, which is also why the picker leads the tab. The setter is **exclusive** (it clears the previous holder in the same transaction, so "which platform is Colnect" always has one answer) and refuses a contact that is not a platform of the collection. There is deliberately no registry of modules to pick from: Colnect is the only one and the value is written by that one setter, so an enumeration would be a vocabulary nothing reads. It exists because the preconditions are **one module's rules**, not a general truth about listings: without it a Delcampe batch would carry a chip per card about a form nobody is going to fill from here. The two ends treat a module-less platform differently, deliberately: the evaluator returns `no-platform-module` **alone** and the kit endpoint refuses on it (a caller that asked for a posting payload asked for something impossible), while `listReadyOffersForListing` **skips the evaluation entirely** and reports nothing — the card answers "what do I fix", and "this platform is listed by hand" is not a fault. It also skips the condition-map read, so a non-Assistant batch pays for none of it. **Where they are surfaced** (#406) is the bulk listing workspace's own row — `ListingWorkspaceOffer.blockers`, evaluated in `listReadyOffersForListing` over one extra select (the stamp's item-ID, the copy's condition) and one condition-map load for the whole batch — and *not* the expanded kit: which of a session's forty offers the Assistant can post is a question asked while scanning, and an answer that needs forty expansions is no answer. The row carries a **Can't list** chip and the expanded card spells the reasons out, one per line and never a count, because each is fixed in a different place; they render from the row, so they are stated even while the kit is still loading or failed to load. They gate the **Assistant handoff** (#407) and nothing else — **Publish stays open**, since posting the form by hand is exactly what a collector does about a gap the Assistant cannot fill. No per-reason link: an unmatched stamp is matched on the platform's own catalog pages through the extension, which the app cannot navigate to. The **handoff** itself (#407, `listing/assistant-handoff.ts`) is the page half of #409's contract, mirrored by hand like the registration payload: **⚡ List via Assistant** beside Publish fetches the kit, writes `{ v, requestId, task }` into one hidden node the panel owns, and follows `data-listing-state` off it. Session-wide and **one at a time**, both for the same reason — the extension puts a marketplace tab in front, so a second handoff would be two forms fighting over one window; presence is `useAssistantPresence` over `<html>`'s `data-stamporama-assistant` through `useSyncExternalStore` with a null server snapshot (the script runs at `document_idle`, and reading the attribute in render would disagree with the server's output). Which platform offers the button at all is `platformModule`, now carried by `listOfferPlatforms` — absent means no module, and the button is *not rendered*; a blocked one is **disabled with its reason** (#273), the reasons being a failing precondition, no extension, or another offer mid-flight. The outcome is rendered as a strip under the card's own line, whether or not the kit is expanded: skips one per line (each is fixed somewhere different), the filled fields in one muted line (what went in is checked in the form, which is now in front of the collector). It **publishes nothing** — filling stops before submit, so the offer is still Ready and the listing does not exist yet; the card's own Publish, one line above and in view at the same time, is the next step, so the strip carries **no Publish of its own** — a second one there is the same button twice. Closing that loop without a paste is #412's, which adds `listed` / `unread` / `activated` to the same strip: `listed` is the URL arriving, `activated` the publication it performs, `unread` a listing posted whose URL could not be read — warning-toned, since nothing failed and the offer is simply activated here. The fill's own filled/skipped detail is **kept** across those states rather than replaced, the post-Save answer carrying only the URL. The workspace treats an offer activated this way exactly as one it published (out of the batch, next card open); the offer's own screen re-reads itself and keeps the strip. The **offer's own header offers the same handoff** (#414), beside Activate and only while `ready`, for #399's reason exactly: a single listing is routinely posted from there, and a step offered on one surface only is the one that gets silently skipped on the other. Button, hint rules and report strip are therefore *one* implementation in `offers/assistant-listing.tsx` (the caller supplies only the button's style, since it sits among a card's small controls on one screen and among the header's chips on the other) — when the Assistant may be asked is a fact about the offer, not about the screen. `OfferDetail` consequently carries `platformModule` + `listingBlockers`, evaluated by the same `listingBlockersFor` over a set select that is a **superset** of `LISTING_SETS_SELECT`, at the offer's **own** state (so anything not Ready reports `not-ready` alone and the header simply shows no button); the condition map is still read only where a module asks for it. The same preconditions **gate `preparing → ready`** (#418, `readReadyBlockers` in `setOfferState`): a fault is worth catching while the offer is still being assembled, not once thirty of them are open in a posting session. It is the one transition gated, deliberately — an offer already live is a listing that exists, and refusing to pause, withdraw or sell it over a mapping gap would trap the collector — and it is evaluated at the **target** state, which is the whole reason it cannot reuse `OfferDetail.listingBlockers` (`not-ready` alone on a `preparing` offer). Hence `OfferDetail.readyBlockers`, the same pure evaluation at `"ready"` over the same sets and condition map, non-empty only while `preparing`; the header's quick-advance button is then **disabled with the reasons** (#273) instead of vanishing the way a missing set or price makes it, since each of these is fixed on another screen. The server refuses regardless of surface (`listing-preconditions`), which is what covers the Offers list, whose rows deliberately carry no blockers of their own: evaluating every page of offers would pay the workspace's per-batch cost on a screen that is not about listing, and the refusal message states the same reasons.
- A listing **title** (#209/#210) is *stored*, and the derived label (`offerLabel`) is only what a surface falls back to while `Offer.name` is null. It is generated at creation — but an offer created **empty** renders over no copies, so `backfillOfferTitle` fills it in on the first mutation that adds copies (`addOfferSet`, `addOfferSetsPerCopy`, `addItemToOfferSet`; #365), and only while the field is still null. Growing a listing never rewrites a title it already has: that is what ↻ Regenerate is for. Without this the detail header looked right and everything reading the stored value — the copy control (#327), the bulk listing workspace (#322) — got nothing. Editing the title likewise seeds the input from what is *displayed*, derived label included (#363); `InlineText` only commits a changed draft, so opening and closing the editor still stores nothing. In generated titles, catalog numbers collapse on **both** of #150's axes (`compactCatalogNumbers`): consecutive bases within a prefix+suffix family (`BL31-33`, `40-42A`), then — over what stayed single — consecutive suffixes on one base (`BL92a-b`, `12I-III`; #364, via `parseSuffixOrdinal`). A span that already collapsed a base run is never folded by suffix: `31-32a` + `31-32b` are two runs, and joining them would claim a span the offer does not list. A number that is **itself** a Roman numeral (#383) carries no digit run and so reaches neither axis — it folds in a third pass keyed on the constant text in front of it (`I-III`, and `Mi·PL I-III` where the caller passes prefixed numbers, as the auction lot label does; #384), never merging with a digit-bearing number or with another prefix's numerals. That numeral may itself carry a **letter suffix** (#426), so the third pass runs both of #150's axes over it in turn, the numeral standing where the base does: the numeral under a constant suffix first — written at **both** ends (`IA-VIIIA`) unlike the numeric axis's `40-42A`, because a numeral and a letter suffix are both letters and `I-VIIIA` would read as a bare-numeral span with a stray letter hung off it — then the suffix on one numeral (`Ia-c`). An **uppercase** suffix folds on neither: `parseSuffixOrdinal`'s sequences are lowercase letters and numerals, and one that is itself a Roman digit (the `C` of `IC`) is read as part of the numeral, there being nothing that could tell the two apart. How a resolved span is **written** is `src/lib/catalog-range.ts` (#400, pure, unit-tested), one module for every surface that shows a range: the end drops the digits it **shares** with the start (`1298-302`, `1298-99`, `240-56`), a floor of two digits so `1298-9` cannot happen, and nothing at all when the endpoints differ in digit count (`98-102`, where a shortened end would read as the smaller number); the suffix axis writes the base once (`128a-c`). `compactCatalogNumbers` renders its spans through it, so a generated title, an offer set label, an auction lot name and the Issues list's declared-range chip (`formatIssueCatalogNumber`, en dash) are one notation. It is **display of a known range, never detection** — `resolveCatalogRange` stays the only reader of typed input — and deliberately absent where a range is being *edited or confirmed* (the issue form's First/Last, the range-extension and recompute prompts): those endpoints are about to be stored, and a shortened one would misdescribe what is being agreed to.
- An offer's generated texts are **subscriptions, not snapshots** (#380). Title, description and private note are re-rendered from the platform's templates after **every** mutation that changes what `offerComposition()` returns — sets added/removed, copies added, a set renamed, either order rearranged — through one `syncGeneratedTexts`, which subsumes #365's title backfill (an offer created empty gets its title for the same reason it later gets a fresh one). Three `Offer.*Edited` flags stop that: `patchOffer` sets one when the collector writes the field, `regenerateOfferText` clears it, so ↻ is literally "hand this back to the template". **Clearing** a field clears the flag too — the flag protects *written wording* and an emptied field holds none; blanking the title is how one asks for the derived label back (#209), which follows the composition by definition. That is also the rule the migration read existing rows by: a non-null text became `edited`, because the two cases are indistinguishable after the fact and losing typed wording is far worse than not refreshing generated wording. A field whose platform template is blank is never written, so clearing a template leaves the last text standing instead of emptying a live listing as a side effect of a settings change; a render that comes out empty likewise keeps what is there. **Terminal offers are skipped**: what a sold listing said is history, and the only composition change one allows is removing a set — ↻ still works there, because that is an explicit act. The `edited` chip on the detail screen is not decoration: without it "why didn't my title update?" has no visible answer.
- A listing text carries exactly one token that is **not** about the copies — `{offerUrl}` (#415), an absolute link to the offer's own screen here, for a private note read on the marketplace page. It therefore reaches the engine through a `ListingTemplateContext` argument rather than through `TitleTemplateCopy`, and the engine stays pure: the URL is built in `src/lib/app-url.ts` off `BETTER_AUTH_URL` (the base a deployment already has to get right for Better Auth, rather than a second setting that could disagree with it), and is null — token empty, glue separator and empty line dropped by the existing tidy passes — when it is unset. It is deliberately **not** a title token, but `resolveTokenValue` still knows it everywhere, so a `{offerUrl}` typed into a title renders empty instead of showing literal braces. The awkward case is creation: an offer's texts are generated *before* its row exists, so the id it needs is not there yet. Rather than splitting generation, `createOffer` / `duplicateOffer` pass a null id and then re-run `syncGeneratedTexts` — but **only** when the platform's templates actually name the token (`templateUsesOfferContext`), which is also the guard that keeps the slug lookup off every ordinary render. The second pass is safe because it is the same function every composition change already uses: the edited-flag and terminal-state rules are not restated anywhere. What it renders is the **short** address (#416): `Offer.offerNo` is a per-collection sequence allocated exactly as `Item.itemNo` is (#268) — `allocateOfferNumber`, an atomic counter bump on `Collection.nextOfferNo` inside the creating transaction, never `max + 1`, because a number published in a marketplace note must not later mean a different listing. `/o/<collectionSlug>/<offerNo>` is a **redirect** to the canonical `/c/<slug>/offers/<id>` and nothing else: an offer has one screen, and this is an address for it. It carries the slug because the number is per collection. The whole reason it exists is that Colnect's private note is `maxlength=100` (#402) and the canonical URL is 69 of them before the collector writes a word — with an over-long text posted **not at all** rather than truncated (#405), so the long form silently cost the note.
- Colnect prints a private note as **plain text**, so a link in one is not clickable — which is what `extension/src/core/instance-links.ts` (#417) fixes, on the sale page's own `._sl-private-note` element and nowhere else. Two rules, and they are separate on purpose: **origin decides whether** (only an instance in `chrome.storage.local` is rewritten — an extension that linkifies arbitrary text on a third-party page is a phishing vector, and "an address I hold a token for" is the one definition page content cannot spoof), and **path decides what it says** (`/o/<slug>/<no>` → `Offer #42`; the older `/c/<slug>/offers/<cuid>` → a plain `Stamporama offer`, a cuid being worth nobody's eyes). Matching on origin alone is also why both shapes are one case: notes published before #416 keep working. The mark comes from `extension/src/core/mark.ts`, which inlines it through esbuild's `dataurl` loader — deliberately rather than `chrome.runtime.getURL`, which would need a `web_accessible_resources` entry handing every page the extension's id, and 355 bytes is cheaper than that trade. It picks the icon **matching this build's toolbar** off a `__DEV_BUILD__` define (amber unpacked, blue released, ADR-0017): a collector running both copies reads the colour to know which extension just spoke to them, so a mark that is always blue lies on half of those pages. Pure DOM, so it is unit-tested under `linkedom` like the platform modules; idempotent, and it skips text already inside an `<a>`.
- The **link from a listing back to the offer it is here** (#466) is the selling-side counterpart of that: `extension/src/core/offer-marker.ts` draws it in **two shapes**, both opening in a new tab: a corner card on an Allegro offer page (that page *is* one offer), and a **plain** `Offer #42` link after the row's own `nr: <id>` line in **Mój asortyment** (there the question is asked once per row, and the row already prints its identifier there). The number is found by *being that id* — the leaf whose whole text is it — a fact about content rather than about markup, with the anchor as the fallback. Plain and not a chip: a bordered box with its own background pushes a cell laid out by the marketplace around, which is exactly what the first cut did. The list is watched with a `MutationObserver` and every anchor records **which** listing it was answered for — paging that table reuses its row elements, so a bare "already linked" flag would leave a row pointing at the previous page's offer — and a listing that matched nothing is recorded too, or a table of somebody else's offers is re-tested for ever. It is drawn *into the page* rather than offered by the toolbar click, because that click already means **capture this as an auction lot** (#355) and quietly changing what a gesture does is worse than a second, separate affordance; and because "this one is mine" is worth knowing before any click. A page it is on states only *which listing* it is — the id off the address, through the capture half's own `listingId(url)`, so the shell never names Allegro — and the **instance** decides whether that listing is ours: a listing being bid on and one being sold are the same URL and the same markup. `findOffersForListings` (`src/lib/offers.ts`, `GET …/offers/by-listing`, session-or-token like the matcher) answers it from Allegro's synced ids first (`AllegroListing` / `AllegroOrderLine`, #467 — exact) and falls back to the boundary rule over `Offer.url` — resolved **in memory** (`urlNamesPlatformOffer`) over the collection's stored addresses, because a batch of 200 ids as `OR` arms would be a thousand `LIKE`s while the addresses are two small columns read once. It takes **many ids per call**: a list asks about every row it draws, and per-row lookups would be a request per row. It answers a **relative** path: the extension joins it to the base URL it authenticated against, so the address never depends on `BETTER_AUTH_URL`. Neither shape is anchored to a class name — every Allegro class is hashed per build, which is why the capture module reads the page's JSON and never its markup — so the card floats where no selector is needed and the inline link hangs off an anchor found by its **address**. This is also the one place the extension scripts a marketplace declaratively without a click, narrowed to `/oferta/*`, `/produkt/*` and `…/obsluga-ofert/moj-asortyment*` (ADR-0015).
- A **derived offer set label** (#379) is the offer title's own catalogue vocabulary, not a join of bare numbers: `compactCatalogNumberGroups` (factored out of `{catalog}`'s own resolver, so the token and the label cannot drift) groups by vendor + area prefix, collapses each group through #150's `compactCatalogNumbers` and writes the prefix once — `Mi·RU-NW 15-19`, `Mi·RU-NW 15-16 / Fi·PL 3`. `15 + 16 + 17 + 18 + 19` named no catalogue and stopped being readable at the second set. Which vendor leads follows from the stamp's primary area link, so a label needs the area tree: `makeOfferLabeller(collectionId)` (`src/lib/offer-labels.ts`) reads it **once per page** and resolves through the same pure `buildAreaVendorMaps` the client renders chips with — the auction lot name's pattern (#353). It is shared with `sales.ts` and `offer-photo-generation.ts` rather than reimplemented, so a set reads identically on the sets card, the photo card, the sellable-offer picker and a sale line. A **copy's** own label stays a bare number: it is listed inside a set whose label already names the catalogue. Set labels are deliberately absent from the photo fingerprint, so this changed no stored image.
- A **set's own value** (#378) — catalogue value + purchase cost — rides on `OfferDetailSet.holdings`, from `getHoldingsValuationByGroup` with one group per set: every copy is fetched and valued once for the whole offer, and the detail's suggested price (#190) is summed from those same figures rather than from a second valuation pass. Per set rather than per offer because a set is what a buyer takes, so it is the number the asking price is judged against. The same pair is given **twice** where the offer prices in another currency, in the header's own grammar: the **offer's currency leads** in strong type and the base figure follows muted behind `≈` (`MoneyPair`), converted with a single rate fetched once for the whole screen (the one `suggestedPrice` already used). The offer's currency leads even though the base figure is the *stored* one — a catalog value is valued in base and a cost basis frozen there — because it is the currency the collector operates in: the price, the platform and the buyer are all stated in it. So `≈` marks the **secondary reading** on this screen, never "the derived one": on the asking price it carries base, here it also carries base, and the two lines read alike. With no conversion available there is one figure and it takes the strong type. A **roll-up bar** in the sets **header band** adds the offer-wide total and the **per-set average** (`OfferSetsTotals`). That band is one row owned by `OfferSetsView` — the section heading and *Add set* are passed *in* from the detail panel as `heading` / `primaryAction`, and *Collapse all* is stacked under the button — because everything that addresses the whole section has to share one rhythm and one right edge: rendered as a heading row in the panel plus a toolbar row here, the two aligned to nothing in particular and the tall figures box stretched whichever row it landed in, summed from the per-set figures rather than re-aggregated — an offer never lists a copy twice, so its sets partition its copies and the parts add up exactly. An average divides by the sets that *carried* a figure, never by all of them: an unpriced set is a gap in the data, and averaging it in reports the listing as cheaper than anything in it is (it is the same rule, and the same number, as `suggestedPrice`, #190). It renders as an **amount column at the right edge** of the card header — money is right-aligned everywhere in the app — placed *after* the status chips so the column lands in the same place whether or not a card carries one. Both it and the roll-up bar are **grids**, never rows of self-measuring cells: the bar's two headings have to sit over the pairs they name and `cat`/`cost` have to line up whatever they contain, and a per-row flex layout drifts the moment one line carries an equivalent and the other carries `—`. `MoneyPair` therefore emits bare *cells* and no wrapper, and the hover sits on the row's **label**, since a tooltip wrapper around a row would be one grid item holding four. The equivalent column is dropped entirely (not left empty) when the offer prices in the base currency, so an offer with nothing to convert carries no dead track.
- A listing **description** (#266) carries a **format** — `plain | html | markdown` (#319; ADR-0019). It is configured on the platform next to the description template it applies to, and **seeded** onto each offer (`Offer.descriptionFormat`), so changing the platform never re-reads a listing already written. Rendering goes `descriptionToUnsafeHtml` (`src/lib/description-format.ts`, pure, DOM-free, unit-tested) → **DOMPurify** in `shared/rendered-description.tsx`; never inject the unsanitised HTML anywhere else. The same sanitised markup is what the copy control puts on `text/html` (with the source on `text/plain`) when copying formatted. The private note (#267) has no format.
- A platform's **listing-text length limits** (#403) are the text-side counterpart of #308's photo limits and sit beside them on `Contact`: `maxDescriptionLength` / `maxPrivateNoteLength`, nullable, **read live and never seeded** (#310's rule — they describe the platform, so tightening one reaches every prepared offer at once), surfaced on `OfferDetail.platformTextLimits`. Two columns because platforms cap the two texts independently; Colnect using 100 for both (#402) is not a reason to fuse them. The counter is a **report and never a cut** — nothing truncates, and an over-long text still goes Ready and still publishes, because the wording is the collector's and the app's job is only that they learn about the cap here rather than in the platform's form with the listing half posted. - **One photo per copy** (#434) is the bulk form of #313 mode a, a second button beside *Add attachments* on the photos card: `attachOfferItemFrontPhotos` walks the offer's sets in plan order and attaches each copy's **front** scan as its own `copy_photo` attachment. Sets the plan excludes (#315) are excluded here too, and a front scan already attached on its own is passed over, so pressing it again tops the plan up instead of doubling it — a scan that is only a *tile* of a hand-built collage (#331) does not count as attached, since breaking out of that grouping is the point.
- **Auction tracking** (#23; ADR-0021, schema in #350) is a *bidding watchlist with a fork at the end*, not a register of market results fed from outside — the market data is a by-product of losing. `AuctionSale ⊃ AuctionLot ⊃ AuctionLotLine`. The parent is **one settlement with one seller** — what ships in one parcel — never "an auction as an event": a house's own sale for a house, an open-ended basket of everything currently bid on with one seller for a marketplace. That definition is load-bearing, because it makes shipping distribution fall out of ADR-0009 §3 for free (the grouping is made at bidding time, so settlement never asks "which purchase does this go into?") and it is what lets the sale-level rollup add shipping **once**. Seller and platform are two `Contact`s exactly as on `Purchase`, both `Restrict`. Currency and the two fee components live on the **seller** and are **seeded** onto the sale — the #308/#319 seeding rule again, so a seller raising their premium cannot re-price a parcel already tracked or settled — and `platformCurrency` (#196) does not apply, because an aggregator like philasearch carries houses listing in EUR, CHF and GBP alike. Outcome is **per lot, never per sale**: within one settlement some lots are won and others lost. The bid is a single overwritten figure with `checkedAt` and **no history** — refreshing is manual (no scraping, no scheduled polling), so `checkedAt` answers the one question a history would; `finalPrice` stays optional, because a lot that vanished from view is an absent observation rather than an error. **Recording the outcome** (#354, `recordAuctionLotOutcome`) is `won` / `lost` / `cancelled` / back to `watching` from the row's ⋮ menu. The two priced outcomes share one dialog and differ in exactly one rule: a lost lot's price is **optional** (an unseen result is an absent observation) and a won lot's is **required** (you cannot have missed what you paid, and #28 prices its purchase line from it — a `won` lot is also the input that action operates on, so it must be reachable here). Marking won stops at status + price and writes **no** `Purchase`: a parcel settles as a whole, once, when the seller invoices it. It does immediately sharpen the sale rollup, which costs `won`/`watching` lots at `finalPrice ?? currentBid`. Marking lost freezes `AuctionLot.fxRateToBase` the way `Purchase` does at `purchasedAt` (ADR-0009 §4, #20), and **only when a price was recorded**: a rate exists to convert a figure, so null covers base-currency, no-rate and no-result alike. Nothing is inferred into the price — the last observed bid is a lower bound, so the field opens blank and blank is a valid answer — and `cancelled` clears price and rate, as does reopening, since neither carries a datapoint. Once a result exists the row renders it in place of the bid: it is what the lot went for, and it is already what `allIn` is computed from. Composition is structured (`stamp × condition × certificate × format × quantity` — the shape a catalogue price is keyed on; the certificate arrived with #353, null = none as on a copy, because a house lot sold with a Fotoattest is worth a different figure and matching is strict) because free text makes catalogue value uncomputable and a lost lot unusable, and it **reuses** the unknown-variant rollup (#238) and format pricing (ADR-0020) rather than re-deciding them — literally, through the exported `valuateItemRows` (`items.ts`), which values a `stamp × condition × certificate × format` row of which a copy is one instance and a lot line another at a **null certificate** (a lot is described before it is owned). `auction-lines.ts` calls it **once per page of lots**, so the factor table and area tree load once. Catalogue value pivots **base currency → the sale's**, converted once per sale currency, because the bid, premium and ceiling are all denominated there; a missing rate makes a line **unconvertible**, which is not *unpriced* — it has a value that cannot be counted, and calling it unpriced would send the collector to enter a figure that already exists. A composition entered but unpriced is `null`, never `0.00`: a zero makes every headroom read as a catastrophic overbid. Unpriced/unconvertible lines are **counted beside the total**, never dropped. A **row's** headroom excludes shipping (premium only, exactly as `allIn` does) and the **sale's** includes it once. The price slot carries the shared quick-price dialog (#228/#341) over a `QuickPriceSubject`, which a lot line satisfies structurally. Composition has **two surfaces, deliberately**: on the **sale's own screen** each lot is a collapsible **card over its lines**, the purchase-order intake / offer-detail layout (#121/#165) — same `LotIssueGroupHeader`, same *Group by* / *Only* / *Sort* toolbar persisted through `lot-view-prefs`, and the watchlist row itself as the card header so a bid is still refreshed in place; on the **flat watchlist** the same list opens as a dialog off the row. The split follows the question each screen asks — "what do I bid on next", across sellers, versus "what am I actually paying for", within one parcel — and is the same one the offers list has with an offer's own screen. Only the sale detail carries the lines (`AuctionLotDetailItem`); the flat list would otherwise fetch forty compositions to draw forty collapsed rows, and its row only needs the total. Entering a line is **two modals**, the purchase intake's flow (#121): `StampPickerBrowser`, then `AuctionLotLineDialog` for condition / certificate / format / quantity, with the pick restated and a ← Back. Two sources, two questions — the catalogue tree answers the first, the listing text the second. The dialog **portals to `<body>`** (it is opened from inside other dialogs, whose transform-centred panels would otherwise be the containing block for its `position: fixed`), and pre-fills condition + certificate from `LS_LAST_CONDITION`/`LS_LAST_CERT` — the same remembered pair every add-copy entry point uses. Going through `StampPickerBrowser` directly (not `StampSelect`) is also what gives the purchase intake's **whole-issue** pick: a series expands — in the *action* layer, `resolveAuctionLineStamps` — into one line per member `requiredForCompleteness`, because a house lot is routinely "Mi 1–12 complete" and twelve trips through the picker is why it would go undescribed. The issue is an **entry shortcut only**; a stored line is always one stamp, since catalogue value sums per stamp and a lost lot must be attributable per stamp. Editing offers stamps alone — one line becoming twelve is not an edit. The remaining fields do not render until something is picked — a line *is* a stamp at a condition, and four greyed-out selects is a form pretending to be busy. **Add lot** carries the same composition section and `createAuctionLot` writes lot + lines in one nested create, every line validated first so a refusal leaves no half-entered lot. A lot card on the sale screen passes `showParties={false}`: a sale is one settlement with one seller, so both are fixed and the header states them. A lot with no `title` is **named after its composition** (`deriveAuctionLotLabel`, pure in `auction-rules.ts`): collapsed catalogue numbers **with their prefix** (`Mi·PL 1-12`) — through the listing engine's own `compactCatalogNumbers`, now exported, since two implementations of #150's collapsing would drift. The prefix rides *inside* the collapsing (it is just the numbering family's constant part), so it is written once around a span and a lot spanning two areas stays honest as `Mi·PL 1-3,Mi·DE 5`. Resolved server-side through the same pure `buildAreaVendorMaps` + `formatStampCN` the client renders chips with, over `readCollectionAreas` — `getCollectionAreas` minus the ownership check, split out rather than threading an `ownerId` into modules with no other use for one — then the issue when the lines share one, and a mixed lot reads as its size (`14 stamps · 3 issues`) because a name is scanned, not studied. **Derived on every read, never stored**, unlike an offer's title (#209/#365): a lot name is never published anywhere, and a lot is described line by line, so a stored value would freeze on the first stamp. It outranks `Lot {lotNo}` in `lotLabel` — the number is already its own chip and says only where the lot sits in someone else's catalogue. `AuctionLotLineItem.catalogNumbers` is ordered **primary vendor first** (`buildPrimaryVendorByAreaMap`, once per page) so the name picks one catalogue rather than three. A line row is **not** `InventoryItemRow`: a line is a stamp a lot is *described* as holding, so there is no copy number, location, disposition, delivery state or cost basis to show — it mirrors the copy row's four-line layout and adds quantity. `copy-sort.ts` was generalised to a structural `SortableCopy` + `sortSortableCopies(…, amountOf)` so both orderings are literally one comparison, the amount differing because a copy's is a base-currency catalog figure and a line's a sale-currency total. The arithmetic is pure in `src/lib/auction-lot.ts` (`allIn` = bid + percentage + fixed + shipping, `headroom`, `summarizeAuctionSale` over the *payable* — `watching`/`won` — lots): a ceiling set against the hammer price alone systematically overpays on cheap lots. **Settlement** (#28, `settleAuctionSale`) is a **1:1 transcription** into `Purchase`/`PurchaseLot`, the links unique and `SetNull` so deleting the purchase leaves the bidding record standing — which is also the undo, `assertLotEditable` freezing a settled lot because the purchase now holds what was actually paid. Seller/platform/currency/shipping come off the sale; each settled `won` lot is one line at `settlementLinePrice` = hammer + premium and **never** shipping, which becomes `Purchase.shippingCost` and is distributed across those very lines by ADR-0009 §3 — charging it per line would bill it twice. The composition is **written as copies, not proposed**: a line already is `stamp × condition × certificate × format × quantity`, so a confirm step would re-ask what was typed to decide the bid; a line of quantity N becomes N `Item`s (`ordered`, out of collection, cost pending, one `allocateItemNumbers` range for the parcel) and the existing intake runs unchanged. What *is* reviewed is the money — date, shipping, every line price and **which** won lots are in the parcel — because the seller's invoice is the authority, not our arithmetic; a won lot left out stays `won` and unsettled, since a lot shipped separately is a fact, not an error. Refused while any lot is still `watching` (the parcel's contents are not known) and with nothing selected (a sale where nothing was won is **closed**, not settled). The review dialog is built from the already-loaded `AuctionSaleDetail` — there is no settlement-preview endpoint, because a won lot's line price is the row's own all-in figure.
- **Market valuation** (#24/#455/#456; ADR-0022) is the layer above auction tracking: what the market *paid*, as against `valuation.ts`'s catalogue valuation of copies (ADR-0007 §7) — two modules that are never merged, because they answer different questions. The arithmetic is pure, in `src/lib/market-value.ts`: a **datapoint** per `AuctionLotLine` of a `closed` lot carrying a `finalPrice`, at `finalPrice × fxRateToBase` (the rate frozen at `endsAt`, #354) and **excluding** premium and shipping, since those are the seller's terms rather than the stamp's worth. The derived outcome is deliberately not consulted — `won`, `lost` and `observed` are all real prices, and dropping the won ones would discard the results the collector knows best. A single-line lot is `amount ÷ quantity` and needs no catalogue price at all; a **mixed** lot is split pro-rata by each line's *total* catalogue value (unit × quantity) and is skipped **whole** if any line has none, because a partial split hands the missing line's share to its neighbours. A foreign-currency lot with no frozen rate yields nothing — `AuctionLot.fxRateToBase` is null both when no conversion was needed and when none could be had, so the pure input carries an explicit `inBaseCurrency` flag beside the rate. The key is `stamp × condition × certificate × format` — the `StampCatalogPrice` key minus the **edition** axis, since a hammer price belongs to a date and not to a published book — with nulls matched exactly, no fall-back. Aggregation is over **all** datapoints with no minimum sample and no time window (a self-built base cannot afford a threshold that throws away most of what has been recorded), and the headline is the **median**; thin and stale evidence is instead answered by a 0–100 **confidence score** from sample · recency · agreement · purity, bucketed `low`/`medium`/`high`, always shown next to the facts that produced it and never keyed off by any rule. `realizationRatio` is `median ÷ catalogueValue` in base currency, and a key with no datapoints shows **no** market value — nothing is ever synthesized from comparable keys. The server half is `src/lib/market-values.ts` + `GET …/stamps/market-value?stampId=…`: computed **on demand, nothing stored** (ADR-0022 §7 — no table, no queued recompute, no invalidation), one query for the closed lots *mentioning* the asked-about stamps and then **all** of those lots' lines, whose catalogue values come from `valuateItemRows` so the unknown-variant rollup (#238) and format pricing (ADR-0020) are reused rather than re-derived.
- The **learned realization ratio** (#520; ADR-0029 §2) is the catalogue side of a bid anchor: `ratio = perUnitMarketValue ÷ catalogueValue`, one per ADR-0022 datapoint, resolved through a five-rung ladder in the pure `src/lib/realization-ratio.ts` — area × condition × period, area × condition, area, collection, then `bidFallbackPercent` (#508) — taking the **median** of the most specific bucket holding at least `MIN_RATIO_SAMPLE = 3`. Condition drops out *before* area on purpose (the catalogue already prices condition; it does not carry a whole area running high or low), the period axis is a sliding `issuedYear ± 2` window centred on the stamp being anchored rather than a decade bucket, and split-derived ratios are **deduplicated by lot within each bucket** — ADR-0022 §3 gives every line of a mixed lot the same ratio by construction, so counting them separately would let one dealer lot dominate the median. Both constants are code, not settings. `src/lib/realization-ratios.ts` is the domain half: one read of the collection's closed, priced lots per page (nothing stored, nothing invalidated), catalogue values from `valuateItemRows` as everywhere else, and the bucket **named** (`Poland, MNH, 1948–1952`) because a learned ratio has to be arguable rather than magic.
- **What anchors an auction lot line** (#510; ADR-0029 §1, §5, §7) is `src/lib/auction-lot-anchors.ts`, the layer between the valuation modules and `bid-recommendation.ts`: market median for the line's exact key when it has any datapoint, else catalogue × the learned ratio, else nothing — resolved **per line, never per lot**, since one lot routinely mixes a well-recorded key with one never seen. It decides nothing the modules below it decided: the composition rollup, `readStampMarketValues` (the ownership-checked `getStampMarketValues` split the way `readCollectionAreas` is) and #520's ladder are reused whole. Catalogue anchors need no conversion (they already roll up in the sale's currency and a ratio is unitless); market medians are converted base → sale at the **current** rate, and a line that cannot be converted is *unconvertible*, never unanchored. Copies already held come per `stamp × condition` from `countCopiesByStampAndCondition` and are **shown, never computed with** — a duplicate haircut would under-bid exactly the material bought deliberately for trade.
- The **bid recommendation on the lots screen** (#511; ADR-0029 §3, §5, §8) is where the four modules above meet, and the split is the composition's own (#353): the **three figures ride on the lot read** — `AuctionLotListItem.recommendation`, filled by `recommendationsFor` over the compositions `compositionsFor` already valued, which is why `resolveAuctionLotAnchors` takes a `valued` map rather than valuing a page twice — while the **evidence is fetched per lot only while its popover is open** (`auctions/lots/[lotId]/recommendation`, `getAuctionLotBidEvidence` in `src/lib/bid-recommendations.ts`, the domain half of #509's pure module). The figures have to be on the row because `REC` is a quick fill and must know what it would write before it is clicked; the evidence must not be, or a forty-lot watchlist fetches forty lots' market medians to draw forty collapsed rows. `recommendationsFor` is **best-effort** like `attachBaseRates`: a recommendation is an extra column on a screen whose other figures are the record, so a failed market read leaves the rows without one rather than failing the list. On the row `fair` is a **column of the grid's *worth* section** (track 10, beside `Catalogue`, against the same `value` / `headroom` labels — which is what the grid's own note already said anything answering "what is this worth" should be), and its `headroom` cell is the catalogue column's very subtraction against the other value, `headroom(fair, finalPrice ?? currentBid, fees)`. That **cell is the popover's trigger**, exactly as the catalogue cell is the way in to the composition editor: a disclosure revealed on hover is one most collectors never find, and the evidence is the whole argument for trusting the figure. `REC` is a *third* quick fill stacked under `CAT` in the ceiling gutter and never replaces it — "what the catalogue says" and "what it is worth bidding" are different statements. `bid-recommendation-popover.tsx` is portalled and positioned exactly as `RowActionsMenu` is and for the same two reasons (clipped list overflow, and an ended row's `opacity: 0.6` trapping a fixed panel); it opens on **any described lot, including one where nothing could be anchored**, which is precisely the lot whose empty cell needs explaining. **All three levels are takeable and each is taken where its evidence is**: every level in the panel is a button writing itself into the ceiling (a `subgrid` row, hence no `Tooltip` on it — the wrapper span would become the grid item), and all three are in the `⋮` menu; the row's own `REC` stays on `fair` alone, so a scanned row carries one answer. ADR-0029 §8 originally refused the other two outright and was **revised, not quietly contradicted**: the "not in a row that is scanned" argument holds for the row and is why `REC` is still fair-only, but it was wrong to conclude the judgement should be unavailable. The panel also carries one row per line naming its anchor (market median with `n`/span/ADR-0022 badge, or the ratio with the bucket it was learned from and its `n`), the ownership counts as evidence only, and the unanchored/unconvertible tallies so a partial total never reads as complete.
- **What the watchlist can cost** (#523) is two figures, not one, and the distinction is the whole point: `AuctionSaleSummary.committedTotal` costs each open lot at the **proxy maximum placed** (`myBid`) — a commitment made to the platform, so it is what a budget is checked against — and `ceilingTotal` costs it at `max(maxBid, allIn(myBid))`, what carrying the bidding to the collector's own ceiling would come to. A ceiling is **already an all-in figure** (ADR-0021 §6, which is why `maxBidWithin` exists), so nothing ever runs `allIn()` over `maxBid` — that charges the premium and the shipping twice, and the issue's own wording asked for exactly that. `currentBid` is an observation and never enters either total. On the lots list the figure is `auctionLotExposure` over the same `lotListWhere` the list and the counts use (#151), rolled up **per sale** before it is summed — the premium and the shipping are the sale's, shipping lands once per parcel however many of its lots the filter shows — and converted into the base currency per sale, a watchlist spanning platforms having no single currency to sum in.
- Background work runs **in-process**, started from `src/instrumentation.ts` `register()` — no extra compose service. Two shapes: *periodic* stateless sweeps (the photo orphan GC, #112) and *triggered* jobs queued in a **table** whose row is also the state the UI polls (offer photo generation, #311; ADR-0018). A queued job must be idempotent — `running` rows are requeued at boot — and enqueuing must be a no-op while a run is already queued or in flight. Pin worker state to `globalThis` so `next dev` HMR cannot stack a second interval.

## UI Direction

- Modal dialogs for list actions (add, edit). Build with shared `src/app/dialog-shell.tsx` primitives — do not duplicate dialog header, close, viewport constraint, or height behavior. A dialog rendered **from inside a row** must portal to `<body>` whenever any ancestor makes its own stacking context — a transform-centred dialog panel, but also a plain `opacity` below 1, which is how an ended auction row is muted (#354). Inside one, `DialogShell`'s z-index only ranks the dialog *within that row*, so the sticky toolbar and the app header paint straight over it.
- **Escape closes one surface**, the topmost (#361). Every dismissable overlay registers with `useEscapeLayer` (`src/app/escape-stack.ts`); the stack is ordered by mount, which *is* the order surfaces were opened in, so the last entry is the only one that hears the key. `DialogShell` and `PhotoLightbox` register for you — a nested dialog, picker or lightbox therefore needs no Escape handling of its own. Do **not** go back to a document-level capture listener with `stopImmediatePropagation`: that only wins by registration order, so the *outer* dialog ran first and closed itself out from under the lightbox that had just opened above it. The shared listener deliberately does not stop the event, so popovers that are not layers (row-action menus, autocompletes, the translation popover) keep their own listeners and their own behavior; a dialog that must yield to one steps out of the stack with `dismissable={false}` (compose-set while the gap popover is up).
- A list filter over **several values at once** is `MultiSelectFilter` (`shared/multi-select-filter.tsx`, #425) — a toolbar-sized button that opens a checkbox list, never a `<select multiple>`, which turns into a scrolling box the height of the toolbar. It reads the one value's name when one is ticked and **counts** them when more are (`3 conditions`), so the control cannot grow and shove the toolbar around. Selection applies as it is made — the list behind it is what says what a tick did, so an Apply button would only ask the collector to confirm what they can already see — and *clearing* is the list's own first row rather than a control beside the trigger, since clearing and unticking everything are one act. It is a **popover, not a layer**: it keeps its own Escape and outside-click instead of joining the escape stack (#361), the same call the notification centre makes, and portals to `<body>` with fixed positioning so a toolbar's `overflow` cannot clip it. The value rides in the URL comma-separated, exactly as `areaIds` does, and an empty list is the **absence** of the filter rather than an unmatchable empty set. Server-side, one axis keeps **one** filter on it: `conditionIds` / `formatIds` / `deliveryStates` (#425, #427) replaced their singular forms on `ItemListFiltersPaginated` **outright**, and every caller pinning one value — a duplicate group addressing its own members, the sale-lot composition picker's `delivered` (#164), `GROUP_ELIGIBILITY` — passes a single-entry list through the same field, so there is never a second knob to keep in step. Renaming rather than adding is also the only way the compiler finds the callers; where one is reached by a **spread** it cannot (`GROUP_ELIGIBILITY`, the duplicate-grouping valuation filters), so those carry a `satisfies` / an explicit annotation — an unrenamed key in a spread is silently dropped, and dropping `deliveryState: "delivered"` would quietly widen a group's eligibility. Two axes are **not a plain `in`**, and share one helper (`nullableIdWhere`): format, where `"single"` is the *null* format (ADR-0020), and certificate, where `"none"` is (ADR-0006 §2, #428). A null is never a member of an `in`, so ticking the sentinel beside a real value is two branches ORed — and that `OR` goes into `buildItemWhere`'s **AND list**, never the top level, where the search's own `OR` would collide with it (and where two such axes at once would swallow one another). Certificate had **no filter at all** before #428 — the field existed only so a duplicate group could address its own members — which is why adding the control came with the rename rather than after it. An unrecognised delivery state is **dropped** from the list rather than passed through, so a stale link narrows to the states it does name and, once nothing is left, shows the whole list rather than an empty screen.
- **Quick offer mode** (#537) is the Copies list's bulk-listing pass: the platform and the starting status are set once in a bar above the rows (`inventory/quick-offer-bar.tsx`) and every **Add to new offer** from then on — the row's `⋮` entry, its promoted icon and the selection bar's `New offer` buttons (#277/#497) — calls `createOfferAction` outright instead of opening `OfferFormDialog`. It goes **further than #234**, which pre-fills the dialog: pre-filling still leaves the dialog, and the dialog is the mouse trip. The offers carry **no price and no URL** deliberately — that is what makes it a bulk pass, and both land on the offer's own screen once the listing exists — so the catalog-value pre-fill (#230) is the ordinary flow's, not this one's. The bar **is** the mode's whole affordance and is why a silent create is safe: which platform, which status and how many offers the pass has made are impossible not to see, and a failure has nowhere else to be reported. It is therefore **not persisted**, unlike every other way of working this list remembers (`groupMode`, the split axes, the worklist platform): a mode that skips a confirmation must never be in force on a screen the collector has just opened. The `⋮` entry **renames itself** (`New offer on Colnect`, via `CopyRowActions.quickOffer`) rather than reading the same in both modes. A platform with **no `platformCurrency`** does not arm it — the currency is fixed at the platform on its first offer (#196) and that choice belongs in the create form, so the ordinary dialog stays in effect rather than the pass failing per click or quietly fixing a currency for good.
- Row-level actions go in a single `⋮` menu, not a cluster of per-row buttons. Use the shared `RowActionsMenu` (`src/app/c/[collectionSlug]/shared/row-actions-menu.tsx`); destructive actions get `danger` + `separatorBefore`. Dialog-opening actions expose `{ action, dialog }` hooks rendered at the row level (see `use-price-details-action.tsx`, `use-inventory-copy-actions.tsx`) so the dialog survives the menu closing. Section-level adds (e.g. + Add area) stay as standalone buttons. An action a *precondition* blocks is **disabled with a `hint`**, not hidden (#273): the hint is a muted second line under the label saying why, because a disabled control never gets a hover event and a silently missing entry is unguessable. Hide it only when the row itself already answers the question — a copy not marked *For sale* shows no offer action, since the disposition chip is right there. A handful of the most-repeated actions are additionally **promoted onto the row** as icon buttons (`RowQuickActions` + `pickRowActions`, `shared/row-quick-actions.tsx`), which is the shape #261 was missing: a promotion is a **shortcut, never a move** (the entry stays in the menu, so nothing is reachable only by the icon), the button is an **icon with a tooltip and no label**, and it is **always drawn — dimmed at rest, full strength on row hover**, never revealed *by* the hover: appearing on hover makes aiming a two-step move (hover to find out where the buttons are, then aim), which is worse than the dimmed icon it was meant to save. It carries `tabIndex={-1}` (#445/#446) so a row keeps one tab stop. A **grouped** list keeps the menu (#516): the copies inside an expanded duplicate / filing / issue group are ordinary `InventoryItemRow`s, and grouping decides what a row is listed *under*, never what may be done to it. The three grouped branches used to pass `readOnly` instead — which is what hid it — so the handlers now travel as one `CopyRowActions` bundle (`inventory-copy-list.tsx`), built once in `InventoryListPanel` and spread onto the flat list and threaded through each group list and row. One prop rather than thirteen at each of two layers is the point: a new action reaches the grouped views without anyone remembering to plumb it, which is the failure mode #516 *was*. The **group row itself** still carries no menu — #422 deliberately replaced its one entry with the select-gutter checkbox. Callers pass the *same* `RowAction` objects they gave the menu, so a shortcut and its entry cannot drift — which is why an icon must name its action on its own (`Add copy` is `⧉`, not a second `＋` beside `Add stamp`). Promoted so far: the Issues list (issue row: edit / add stamp / add copy; stamp row: edit / add child stamp / add copy), the **Copies** list (edit / edit stamp / add to offer / add to new offer), the flat **Stamps** list (edit / add copy), the **Wants** list (detail page / edit), the **Offers** list (edit / sell), the **Purchases** list (edit alone) and the **Auction lots** list (bid unchanged / contents) — with the **Sales** list deliberately left alone (#527). Each list promotes what *it* repeats rather than a fixed trio — the flat stamp list has no *add child stamp*, because a variant is added from the issue tree where its parent is on screen, and the copies list promotes **both** offer verbs because they are one decision made per copy ("does this join a listing or open one"), and promoting only *add to offer* would have made it the accidental default for want of a second click. The copy row is rendered from eight screens and takes an `actionsOverride`, so the promotion is picked from the *resolved* list: a screen that hands the row fewer actions simply shows fewer icons, and `pickRowActions` skipping an absent key is what makes that silent rather than a crash. What a list does **not** promote is decided by three subtractions, which is what settled #527's four remaining lists: an action the **row's own click** already performs (*Open* everywhere, *Open sale* on a lot) is not promoted, since an icon aimed at what the whole row does is a smaller target for the same result; an action the row already draws as a **labelled control** — the offer row's and the lot row's `Listing` chip, the sale row's `Transaction` chip — is not promoted either, a shortcut past the menu being the point rather than a second copy of a control that is already on screen; and **destructive** entries are never promoted at all. Applied honestly this leaves *one* icon on Purchases and **none** on Sales, and both are the right answer rather than a shortfall — "no promotion" is a valid outcome, and two dimmed icons duplicating visible controls is exactly the sprawl #125 collapsed. The **auction lot** row is the density case: the busiest menu of the set on the row that already carries inline bid fields, and it takes two — `checked` + `contents`, the watchlist pass itself — while every *bid-fill* entry stays in the menu because the row's own cells are where a new figure is typed. Both are present on every lot (a blocked one disabled with its hint, #273), so the promoted pair is a **constant width** and cannot shunt the closing time and the `⋮` about from row to row, which is what that column's fixed widths exist to prevent. The menu **portals to `<body>`** at z-index 200, so rows living *inside a dialog* must raise it past that dialog's own `zIndexBase + 1` (`zIndex` prop) — otherwise it opens behind the panel, invisible, and the click meant for an entry lands on the backdrop and closes the dialog (#468 hit exactly this). It is also not an escape layer, so a dialog holding such rows takes `dismissable={!menuOpen}` off the menu's `onOpenChange`, or one Escape closes menu and dialog together (#361).
- Sidebar sections follow **what the collector is doing**, not what the data is: `Catalog`, `Collection`, then trading split by direction into **Selling** (Offers, Sales) and **Buying** (Purchases, Auctions) — selling first, because buying is what a collection is built from but selling is what is worked on daily, and the section reached first should be the one opened most. Auctions is a **`NavGroup`** (#376) — an icon'd heading over two indented entries, *Lots* and *Sales*. They are two entries because they answer different questions on different days ("what do I bid on next", across sellers, versus "what do I owe for this parcel"), and reaching the second only through the first made the daily screen double as a doorway; they are *nested* because they are two views of one subject rather than two parts of the collection the way Purchases and Offers are. The group row is a **heading, not a link**: pointing it at one of its own children would duplicate that child and light two rows at once. Children take no icon — the group's names the subject and the indent says who belongs to it. `isActive` takes an `exact` flag for the pair: every sale route lives under `/auctions`, so `startsWith` would light *Lots* on a sale. One `Trading` heading over five entries meant reading the whole list to find either half. **Contacts belongs to neither** — the same address book holds the house you bid with and the marketplace you list on — so it trails both, set apart by `NavItem`'s `spacedAbove` rather than by a heading over a single item.
- Config screen placement: **catalog taxonomy** that is set up once (Areas, Catalogs, Conditions) lives in **Settings** tabs; **operational data** touched routinely (Locations) gets its own **Collection** nav page. Both reuse the same adjacency-list tree pattern (`buildTree`, `*-tree-select.tsx`, `RowActionsMenu`) — mirror `areas-panel.tsx` / `locations-panel.tsx` rather than reinventing tree/list/dialog scaffolding.
- **Lot / set cards are collapsed by default** (#382) — purchase-order lots, offer sets and an auction sale's lots alike, through the shared `useCardExpansion` (`shared/use-card-expansion.ts`), which owns the state at the *panel* level so one screen has one rule and a Collapse all / Expand all control to operate it. These screens are **scanned** first ("which lots are in this order", "which sets are in this listing") and a card's contents are a second question asked of one of them; expanded-by-default meant a four-lot order opened as several screens of copy rows. Exactly two things open a card unasked: the card the collector **navigated to** (#374's `?lot=`, passed as `initiallyExpandedId` and *seeded* into the state, so it can still be closed by hand and clearing the highlight does not shut it), and a card that **appears while the screen is open** — it was created here, so it is what is being looked at. The latter is derived from the ids themselves rather than from a just-added signal: it covers a create that yields several cards, needs no plumbing through the dialogs, and the first render is the baseline (all three views mount after their data has loaded), so an ordinary page load opens nothing. A lone card is **not** an exception — one rule, nothing to infer. The **sale's packing view** (#166) keeps its cards expanded, deliberately, because a packing list is read rather than scanned, and that exemption is the reason to leave `sold-units-view.tsx` alone.
- A **grouped list** is collapsed by default too, but through `useGroupExpansion` (`shared/use-group-expansion.ts`, #538) and **not** `useCardExpansion` — the Copies list's three groupings (#372/#421/#424) hold the state at the panel so Expand all / Collapse all can speak for the whole list, and the three group rows lost their own `useState`. The two hooks differ on the case that matters: a *card* appearing while the screen is open was created here and opens itself, whereas a grouped list is cursor-scrolled and its rows appear because the collector scrolled — and every open group **fetches its own members**, so a page of forty arriving pre-expanded is four hundred copies nobody asked for. The state is therefore a **mode plus its exceptions** (`expandAll` + `overrides`) rather than a set of open ids: a group loaded *after* Expand all comes in open, which is what the control means on a list whose end has not been reached, while `allExpanded` is read over the ids currently loaded so the label always describes what is on screen. `resetKey` is the grouping mode, since carrying `expandAll` across would open every row of a list nobody has looked at. `toggleAll` clears the exceptions — a statement about the whole list is exactly what overrules the rows toggled by hand. The control sits on its **own line above the rows**, right-aligned, as #382's does: in the filter toolbar it read as one more way of narrowing the list.
- A control that is **auxiliary to a field beside it** carries `tabIndex={-1}` (#445/#446). Tab is how a form is filled in, so it should walk the *fields* — a stop per helper turns a card of three texts or a dialog of six vendors into a slalom, and the collector's hands leave the keyboard for something they never asked to visit. The line is **not "icon vs. label" and not "small vs. large"**, it is *could this control be skipped and the field still be completed*: a copy `⧉` (#327), a 🌐 translations opener (#293–#296), a template's click-to-insert token chips (the syntax can be typed), a search box's own clearing `✕`, a price grid's ⤴ carry-forward and the issue dialog's per-vendor prefix overrides (#377 — rare, and one per vendor stands in front of the numbers) are all skipped, because each is a shortcut to something the field itself already offers. What **stays** in the order is anything that is the only way to reach a piece of state from the keyboard: a `✎` that opens the field at all, a Save / Cancel pair on an inline edit, a `+ Add` that commits the select next to it, a `✕` that removes a row, a sort-direction toggle, a filter chip. Those are controls in their own right that happen to sit near an input, not helpers on it. Bake the rule into the shared component (`copy-button.tsx`, `translations-field.tsx`, `template-builder.tsx`'s chips, `list-toolbar.tsx`'s `CLEAR_BTN`) rather than at each call site, so a new caller inherits it. Mouse reachability is unchanged, and everything inside a dialog such a control opens tabs normally — the exclusion is about the *route in*, never about the surface it leads to. A dialog whose fields are **remembered** puts the cursor in the one field that is not: the Add copy dialog (#534) focuses the in-location **Ref** on open, because condition, location and disposition all come back from the last copy (#234) and only the ref changes per item in an intake pass. Mount-only, and it stays a no-op when the field it names is disabled (Ref needs a location) — a focus effect that fires later pulls the cursor out from under a collector who has already started typing, which is why #222's focus-after-picking-a-location is a *separate*, flag-driven effect and not this one widened.
- Drag-to-reorder lists use the shared kit in `src/app/c/[collectionSlug]/shared/reorder-list.tsx` (`useReorderList`, `InsertionLine`, `DragGrip`, `showLineAt`, `dragStyle`) — the container is the drop target, not the row. `handleOnly` starts a drag only from a row's ⠿ grip, so a stray press on the row body doesn't (offer photo plan, #313).
- Physical **format** (pair, block, strip) is an axis of its own (ADR-0020), not a stamp — superseding #135's "record a multiple as its own `Stamp` with a self-descriptive number" for *homogeneous* multiples, which collapsed on deep variant trees (Infla `309 → 309A → 309AP → 309APa`: `formats × nodes` stamps, and "a pair, variant not yet identified" inexpressible because a pair of `309BP` is not a child of a pair of `309B`). `StampFormat` is a per-collection dictionary shaped like `StampCondition`, referenced from `Item.formatId` *and* `StampCatalogPrice.formatId`. **Null means single** — no such row is seeded, exactly as a null `certificateStatusId` means "no certificate" (ADR-0006 §2) — so nothing needed backfilling. A multiple is **never decomposed**: no unit count exists, nothing multiplies or divides by one, and completeness treats format as a breakdown dimension beside condition ("the series in pairs?" like "the series in MNH?"). Zusammendrucke with their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) stay their own `Stamp` — the test is whether the catalog numbered it, not whether it holds more than one stamp. A format's price is **explicit or derived**: an explicit `StampCatalogPrice` row wins, else the single's price × a `StampFormatFactor`, because catalogs publish one factor per issue and an explicit price only where a multiple deviates. Factors live in one table with nullable anchors — the all-null row *is* the collection default (no second `defaultFactor` mechanism to explain) — resolved by **fixed precedence**, `(issue set?, area depth, condition set?)` lexicographically, never a specificity score: *where* deliberately outranks *for which condition*. The rule is pure in `src/lib/format-factor.ts`; `format-pricing.ts` wraps it per stamp because it needs the area ancestry and issue. A format is **translatable** like every other dictionary that reaches a listing (#344; `StampFormatTranslation`, two independently-falling-back columns, `format` in the shared `TranslatableEntity` union), and renders through `{format}` / `{formatAbbr}` + `{#formatLegend}` (#345) — where a **single resolves empty**, the common case, handled by the existing tidy pass rather than by a rule of its own. Lists gain an **`as`** switcher beside the condition one (#343), defaulting to Single, hidden without formats, stored as `""` because Single is not a row. A list column **derives** where nothing explicit was recorded and marks it with the same `~` + italics an unknown-variant rollup uses (#238) — one vocabulary for *inferred, not recorded*, distinguished only by tooltip. The Copies list takes format as a **filter**, never a switcher (a copy's format is a fact), and `valuateCopy` resolves at `Item.formatId`: with no explicit price and no factor a multiple is **unpriced**, never valued at the single's figure. Per-row factor resolution would be a query per row, so `makeFormatFactorLookup` loads the factor rows + area tree once and resolves in memory. A multiplier is **edited where its scope lives** — an issue's from its row on the Issues list, an area's from its row under Areas — so the anchor is never a field the surrounding screen already answers; Settings edits only the collection default and areas and **does not list issue-anchored rows at all**, excluding them *at the query* (`getCollectionFormatFactors`) rather than filtering after: there can be one per issue per format, which is thousands of rows. A scoped list shows what is set on that row alone, never what would apply through inheritance — it is an editor, and showing a parent's rule under a child invites editing it from the wrong place. The scoped editor is one component exposed both as a `{ action, dialog }` row-action hook and as a plain dialog, because the areas panel maps its rows and cannot call a hook per row. The price grid gains format **tabs**, not columns, and a derived value renders as the cell's placeholder so it stores nothing until typed over. Price cell keys grew a **trailing** `~<formatId>` segment, optional so pre-format payloads still parse.
- A **checklist** (#531; ADR-0031) is the collecting goal, as against `Issue`, which is the publication event — a named list of stamps that counts as one complete unit, and an issue may carry several (basic beside specialized, perforated beside imperforate, tabbed beside plain). It replaces `IssueMember.requiredForCompleteness`, one boolean that gave an issue exactly one set; the migration turned every issue with a required member into one checklist named after it and dropped the column, so **there is no required flag to consult** — membership of a `ChecklistStamp` row *is* required-ness, and an optional extra is an `IssueMember` on no checklist. `Checklist.issueId` is nullable on `StampFormatFactor`'s idiom (null spans issues), but only the issue-scoped editor exists (`useChecklistsAction`, on the issue's row, ADR-0020 §7). `sortOrder` is load-bearing: the **first** checklist is what a single-checklist row shows and what a new stamp joins by default. Every derived fact names its subject explicitly — **per checklist** for the completeness grid and the catalog-price total (a union would count a shared stamp once, for a figure answering neither question), the **union** for `requiredCount`, the declared range (#333) and the issue gallery (#137), **one named checklist** for the intake fan-out, auction lot composition and the picker's *whole set* buttons. The issue row collapses several to a `3 checklists` badge with the detail in its tooltip (#425's counting rule); the issue's detail page is where each gets its own completeness and value card. That badge stays an **indicator** — narrowing is a `MultiSelectFilter` above the row's *expanded* tree and in the detail page's Stamps card header, never in the collapsed chip line (a toolbar-sized control per row outweighs it), held in local state because a per-issue filter has no single URL parameter on a list of many issues. `filterStampTreeByChecklists` (`src/lib/stamp-tree-filter.ts`, pure) drops non-members but **keeps a node with a surviving descendant**, returning it in `contextIds` to be dimmed: a variant is read through its ancestors, and `309AP` without its `309` is a number nobody can place. The filter is on all three tree surfaces — issue row, issue detail, stamp picker (where the context dimming folds into #186's existing `dimmed`, one faded state rather than two). **`Checklist.name` has no unique constraint and nothing resolves a checklist by it** — names repeat freely across issues and never meet, since every read is scoped by `issueId`; a repeat *within* one issue gets #178's advisory ⚠, checked client-side against the already-loaded list.
- A **want** (#532; ADR-0032) is what the collection is *looking for*, and it is deliberately **not** a fourth disposition: `inCollection`/`forSale`/`forTrade` live on a copy, an `Item` is one physical copy (ADR-0007), and a wanted stamp has no copy — a `wanted` flag would force phantom rows and poison every count that reads inventory. A want carries an **acceptance set per axis, where zero rows means "any"**: `WantCondition` (plain composite key — `Item.conditionId` is required, so there is no "none" value), `WantCertificateStatus` and `WantFormat` (**nullable** FK, because a null there *is* a value — "no certificate" per ADR-0006 §2, and "single" per `StampFormat` — with `UNIQUE … NULLS NOT DISTINCT` as `stamp_catalog_price_unique` has it). **"At least X" is inexpressible on purpose**: `StampCondition.sortOrder` is display order, `U` and `MNG` are cancellation and gum rather than two points on one scale, and `CTO`/`FDC` are on no scale at all, so any minimum-quality rule would invent an ordering the dictionary does not guarantee. Upgrades then need no concept of their own — a used copy held against a mint-only acceptance set simply does not satisfy the want. `closedAt` is `Item.disposedAt`'s idiom (null = open, one column, so every filter stays a plain `where`). There is deliberately **no price on a want** — built, then dropped by `20260811140000_want_drop_max_price` before it meant anything: a want has no date, so a figure on it is a price opinion frozen the day it was typed and never corrected (ADR-0029 §2's objection to a *configured* ratio, once per row), and the whole-series add makes it unworkable outright — one field over twelve stamps worth wildly different amounts, where copying stamps one ceiling onto all of them, splitting by catalogue invents limits nobody stated *and* freezes them at today's catalogue, and splitting evenly prices a key value like a common one. What a stamp is worth **at the moment of buying** is the recommendation engine's answer from recorded results (ADR-0022/ADR-0029), against the copy in hand; two mechanisms for one question is how they drift. `priority` is what survives of "how much do I care", and it needs no maintenance to stay true. What a copy satisfies is the pure `wantMatchesCopy` (`src/lib/want-rules.ts`), shared so the intake review, the list and any later consumer (#253/#250, trade) cannot disagree; storage and reads are `src/lib/wants.ts`. The **review belongs to the moment a copy reaches the collector's hands** — the transition into `delivered` — not to the moment its row was written (#532). One rule covers every route in: a hand-added copy starts delivered and is reviewed at once; intake creates `ordered` (or `to_sort` on an already-arrived order) and raises nothing, so `intakeStampsAction` deliberately returns no `copies`; `bulkUpdateLotItems`/`Scoped` return the copies their change *moved into* delivered (candidates read **before** the write, since afterwards a copy that just arrived is indistinguishable from one that was already here), and `updateItem` returns `becameDelivered`. That is also what closes the auction-settlement gap without a second review being bolted onto it: a parcel won, settled into a purchase and sorted converges on the very transition every other route does. Both intake paths raise the **review** — `intakeStamps` now returns the copies it created rather than a count, and `createItemAction` returns the one it made — and the review offers **close / narrow / leave open** per want. **Nothing closes automatically**: that would discard a record of intent, and narrowing (the common case) is a judgement the app cannot make. What it may do is *seed* — `narrowConditionSeed` ticks every condition except the one that arrived, from the dictionary's membership and never its order, and only when the set was empty, since a set already narrowed is an answer the collector gave once. Completeness targets are a **generator, not a source** (`createWantsForMissing`): explicit rows once, wide open (a gap carries no acceptance criteria), skipping stamps with a held copy or an **open** want — a *closed* one is not a reason to skip, the gap being real again — which is what makes pressing the button twice a no-op. The add form takes **one stamp or a whole checklist** (`WantCreateInput`): `StampSelect` gained an opt-in `checklist` prop that turns on the browser's per-checklist *whole set* buttons (the copy form does not pass it — one copy is one copy), and the fan-out writes one want **per stamp** sharing the form's acceptance, priority and note, since a set-shaped want could never be half met. It skips a stamp with an **open** want and reports the count, but deliberately **not** one merely held — that is the gap generator's rule, and wanting a better copy of something held is the ordinary case. `priority` is stored as its **rank** (`Int`, 0 = high, 1 = normal, 2 = low), not as the word: the list is ordered by it and paged on the server, and the only order Postgres can put a `text` column in is its spelling — `high < low < normal`, which nobody means. `want-rules.ts` owns the vocabulary and the word is what crosses the wire, the form and the filter; one column, not a word plus a rank that must agree with it. The list row leads with the stamp's catalog photos (#137) and the screen carries the shared `ListFilterSidebar`, but the list itself is **cursor-scrolled, not fetched whole**: `listWantsPaginated` + `listWantYearFacets` share one `buildWantListWhere`, so a facet cannot count a row the page would not show, and the year is dropped only for the facets (each count says what *that* year would leave). This is deliberately not Contacts' whole-list-and-filter-locally shape — an address book is a few hundred rows, a want list is a collecting plan's shopping list and runs to thousands. The condition filter ORs in `conditions: { none: {} }`, since an empty acceptance set means "any" and such a want really would take the condition asked about. Order is `closedAt` nulls-first → `priority` → `createdAt desc` → `id`, the last being what makes an offset page stable over ties. Area and year ride in `useCollectionFilterStore`, not the URL (#143), on the stamp picker's reasoning. The row shows a **catalogue range**, not a price: a want accepts a *set* of (condition, certificate, format) combinations and each has its own value, so one number would be one combination picked out of the set answering a narrower question than the row asks (`wantCatalogRange`, pure, in `want-valuation.ts`). Each combination goes through **`valuateCopy`** — the function that prices a physical copy — so a want's figure and the copy that eventually satisfies it cannot drift; min/max in the **base currency only**, since two currencies are not a range; an unpriced or unconvertible combination is **counted, never zeroed** (a catalogue gap would drag every range to nothing) and the row reports `priced / accepted`; `estimated` is inferred from **no recorded row for the format**, not from a factor existing, because a format can be priced explicitly *and* carry one. One pricing pass **per page** — the page's stamps' prices plus the per-collection preamble the stamps list already loads — and only in `listWantsPaginated`, the intake review and the form drawing none. The row promotes **Open stamp page** (the shared `useDetailPageAction`, first in the menu as everywhere) and **Edit** to hover quick actions through `pickRowActions`, so a shortcut and its menu entry cannot drift; the stamp screen returns the favour with a read-only **Wants** card (`related-wants-card.tsx`, off a `stampId` filter) leading its right column, showing closed wants faded — noise on a list, but on one stamp the record that it was looked for and found — and **rendering nothing at all when the stamp is on no want**, loading included so it never flashes an empty state: Copies and Offers are about every stamp and print "none yet" as a real answer, while wanting one is the exception, and a card saying "you are not looking for this" on every catalogue page is furniture. Priority is a chip beside the acceptance chips, in three deliberately **different** tokens (warning / info / muted): a scale whose middle and bottom look alike is one you read the word off, and then the colour is decoration. **Flat is the shape and issue grouping is a view of it** (`listWantIssueGroups`, a remembered *By issue* toggle): a want's subject is a stamp and its acceptance sets are per stamp — within one series the key value is wanted MNH with a certificate and the rest "anything" — so an issue heading over those rows overstates, the dominant reading is matching a stamp in hand against one searchable row, and an issue-shaped spine would be a second answer to the completeness grid ADR-0031 already gives from copies *held*, re-coupling exactly what §6 separated. Grouped server-side on #424's reasoning (offset paging would split a group across a page boundary and report two half-counts), counted on the stamp's **first** issue membership and read back through an `issueId` filter matching **any** — #172's pair, not a third rule — with `NO_ISSUE` for stamps in none. The row reads `open / total`, both counted with every filter **except** status, since a denominator that moved with the Open/Closed toggle would be a fraction of nothing; which groups *appear* still obeys status, and because status narrows on `closedAt` alone that falls out of the two counts with no second query. The catalogue lists carry the want back the other way (#532): `loadStampWantSummaries` denormalizes each stamp's **open** wants onto `StampListItem.wants` and `StampNodeData.wants` — scoped to the page's ids, `loadStampCopyCounts`' call — and `WantChip` draws them, absent when there are none (a marker on a few rows is a signal; one on every row reading `0` is a column) and coloured by the *loudest* of the wants behind it. The detail is a **click popover, not a tooltip**: a dozen wants × three axes flattened into prose was unreadable, and a popover draws them as the want list draws them. Because the summary is *copied onto two other read models*, `useAddWantAction` invalidates the stamps and issues caches as well as the wants one — refreshing only its own list left the chip missing until a reload. The chip is built on the shared `STAMP_SECONDARY_CHIP` base so it sits on the line its neighbours do, and **always draws its count, one included** — an icon alone gives the chip no text to set its line box from and it came out shorter than every chip beside it. It is on **auction lot lines** too, where it answers the sharper question: a line names a concrete `(condition, certificate, format)`, so it passes a `copy` and the chip runs **`wantMatchesCopy`** — the intake review's own predicate, so a lot marked as matching and the review that greets that copy on arrival cannot disagree. A match is drawn as a **ring**, not another colour: colour is already spoken for by priority, and two meanings on it leave neither readable. That is what `StampWantSummaryEntry.acceptance` is for — the words are for reading, the ids for deciding, both off one row. The marker rides on **copies** the same way: loaded in `enrichItemRows`, the one funnel every copies view goes through (Copies list, a purchase order's intake, the lot and group readers), so no surface loads it separately — and on `CopyGroupRow`, where a group being one stamp at one condition means the answer covers every copy in it. On a held copy the ring reads as the **upgrade** signal, holding one never having closed a want. What the collection already has of a wanted stamp is a **split, not a count** (`WantCopyCounts`: held / ordered / inTransit, `to_sort` folded into held since the copy is on the desk either way) and it rides on both `WantListItem.copies` and `StampWantSummary.copies`, so the chip's popover carries it too. One figure hid the case that matters: a want stays open until the collector closes it — correct, the stamp is not here — but an *ordered* copy then looked exactly like no copy, so the same stamp at the next auction read as an untouched gap and the want urged a second bid. Held and on-its-way are different answers to "should I be bidding on this". Deliberately **derived, never stored**, and it closes nothing: no third state on the want, and ADR-0032 §7 stands. The buckets are held / **toSort** / ordered / inTransit — `to_sort` stands apart from held, an arrived-but-unsorted copy being a different answer to "have I got this" than a filed one — and the figures **leave out the copy they are drawn on** (`loadItemWantSummaries`, keyed per copy rather than per stamp so two copies of one stamp on a page each omit a different one): a purchase-order row otherwise reported *one in transit* about itself, and a count meant to say "something else is coming" must not be satisfied by the row you are reading. It is counted **twice, and the two must never be drawn as one**: per *stamp* (`WantListItem.copies`, `StampWantSummary.copies`) is the upgrade context — everything held whichever want it answers — while per *want* (`WantListItem.matchingCopies`, `StampWantSummaryEntry.copies`, filtered by `wantMatchesCopy`) is the **only** figure allowed to claim something is on its way. A used copy in the post satisfies a want for "anything" and a mint-only want not at all, so one line above a list of wants tells the collector to stop bidding on the mint copy they were right to chase. Both tallies come off **one** `loadCountedCopies` read, so they cannot be taken over different sets. Named acceptance profiles are #533 and deliberately not folded in.
- A **named acceptance profile** (#533; ADR-0032 §9) **seeds**, it is never referenced. `AcceptanceProfile` + three member tables carry exactly the axes a want carries (nullable members and `NULLS NOT DISTINCT` included), and applying one *copies* the sets onto the want — hence there is deliberately **no `profileId` on `Want`**, and that absence *is* the decision, which a schema cannot state and ADR-0032 §9 therefore does. `CollageTemplate`'s shape (#308), and the precedent is the reason: a reference would make editing a profile a silent rewrite of what every existing want accepts, closed ones included, whose acceptance is a record of a decision already taken rather than a setting. So a delete needs no in-use check and an edit needs no warning; the cost — changing a profile *and* the wants carrying its terms is two acts — is answered by a bulk edit over a **chosen** set of wants if it ever proves tedious, deliberately unbuilt. `validateAcceptance` and the `AcceptanceInput` shape live in `src/lib/acceptance.ts`, shared by `wants.ts` and `acceptance-profiles.ts` so the two cannot disagree about what "no certificate" means. The picker is inside the shared acceptance editor (`want-acceptance-fields.tsx`), so the want form and the intake review's narrow step get it from one place and the Settings editor that *defines* profiles turns it off (`profiles={false}`); which profile it shows is **derived** by comparing the sets (`acceptanceSetsEqual`, pure, in `want-rules.ts`) rather than stored — a seed leaves nothing to read, and editing one box drops it to *Custom*, the terms no longer being that profile's. The profile a want was **saved** on leads the next add (`LS_LAST_ACCEPTANCE_PROFILE`, per collection, `readRememberedProfile`/`rememberProfileFor`), the last subtype's (#342) and last condition's (#121) idiom — wants are entered in runs and a run is one set of terms. Saved rather than *picked* (a profile cancelled is not what was gone with), **derived on submit** rather than tracked as a selection (the form has no other notion of "the current profile", and a second one would be a thing to keep in step), **cleared** when the terms match no profile (an off-profile want says the run moved on, and the stale id would seed the next want with terms just chosen against), and read on **add** alone — an edit shows the want's own terms and the intake review's narrow step has ADR-0032 §7's own seed to keep. Applied during **render**, the settings panels' "adjust state when something arrives" pattern rather than an effect, and once, flagged rather than conditioned on the sets being empty so a background refetch cannot re-seed boxes deliberately cleared.
- A stamp's **catalog prefix** is resolved from *two* levels, not one (#66/#377). The per-(area, vendor) prefix on `CollectionAreaVendor.areaPrefix` is inherited down the area tree, and an **issue may override it** for its own stamps (`IssueCatalogPrefix`, one row per issue × vendor, `areaPrefix` NOT NULL — an issue has one level above it, so "inherit" is the absence of a row, which is what the dialog's blank field stores; on an *area* a null row is meaningful, being what stops inheritance). The override is the **catalog identity**, deliberately not a display layer: it decides the rendered chip, the stamp picker's match keys, generated listing texts, derived offer-set and auction-lot names, duplicate detection (#85) and the Colnect strict full-key match (#155) alike — a stamp reading `Mi·SP 1` while the duplicate checker still thinks `Mi·PL 1` is the bug this rules out. The override map is loaded **whole, once per read** (`issue-prefix.ts`; client `issues/catalog-prefixes`, keyed under `["issues", collectionId]` so existing issue invalidations cover it): the table is sparse by construction and a screen needs it before drawing its first chip. `duplicate-catalog.ts`'s `CatalogPrefixContext` additionally takes prefixes *typed into a form but not saved* — the issue create dialog checks numbers against an issue that does not exist yet, so the form is the only place its prefixes can come from. The prefix input sits **in front of** the First/Last range in the issue dialog, where it renders, with the area's prefix as its placeholder.

A group carries a **severity** (`critical` / `warning` / `info`), which is what decides both its tint and the panel's reading order — graded by **consequence, not by subject**: a possible **double sale** is `critical` (both offer groups: one piece of stock committed in two places, costing money and a rating, undoable only by the collector), a **deadline that can still be met** is `warning` (a lot closing today), and **bookkeeping that never fixes itself** is `info` (an ended lot with no outcome). It is the lot list's own rule — colour means *act now*, which is why an ended lot there is muted rather than reddened — applied across sources. Provider order is only the tie-break, so a source's place in `PROVIDERS` can never outrank a worse problem from another one. The badge is tinted by `ActionItemsResult.severity` — the **worst** thing waiting, never the count, or three ended lots would outshout one double sale — and that grade is resolved **server-side** so the bell and the panel cannot grade one list two ways. In the panel the **heading** carries the tint, not the rows: a list of names is read, and tinting every line makes it harder to triage rather than easier. An item carries its instant as ISO and the client formats it (`formatRelative`): "in 3 hours" needs the browser's clock and locale, and a server-rendered string goes stale while the panel sits open. - A **hover hint is the shared `Tooltip`** (`shared/tooltip.tsx`), never the browser's `title` attribute (#291). The bubble portals to `<body>` with `fixed` coordinates, so no ancestor's `overflow` clips it, and it is **clamped to the window** by `TooltipBubble` — measured in a layout effect, then *flipped* to the trigger's other side when it overruns vertically (sliding would cover the control it describes) and *slid* when it overruns horizontally (a trigger has no other side to flip to). That clamp lives in the primitive on purpose: a hint is most needed on the controls sitting at the edges of the screen, which are exactly the ones whose bubble runs off it, and leaving it to callers meant every such site had to notice the problem first. `placement`/`align` are therefore a **preference, not a guard** — set `align` where the anchoring itself reads better, not to avoid an edge — a native tooltip ignores the theme, appears after a delay nothing else in the app has, and cannot carry formatting. Three things follow from the wrapper the component inserts. **Empty content renders no bubble**, so a conditional hint stays one code path instead of branching between a wrapped and an unwrapped child — which would move the child in the layout. Layout the child carried (`flex`, `marginLeft: auto`, `position: absolute`, `width: 100%`) moves to the wrapper's **`style`**, or the row shifts around it. And a tooltip **inside** another tooltip suppresses the outer one while it is open, matching what nesting `title` did — triggers nest constantly here (a chip with its own hint inside a clickable row that has one), and `mouseenter` does not re-fire on the ancestor, so both bubbles would otherwise sit on screen at once. `title` doubling as an icon-only control's accessible name is not a reason to keep it: give the control an `aria-label` and the hint a `Tooltip`.

- **Copies held per stamp** (#348) come from `src/lib/copy-counts.ts` — one `groupBy` over the disposition flags for a whole page of stamps, never a count per row — and render through the shared `CopyCountBadge` on every surface that lists a stamp (issue tree, flat list, pickers). Counted **per stamp exactly**, never rolled up from variant children (the tree shows the child's own badge one line down, so a rollup would show one copy twice), and **excluding sold copies**, because the badge sits beside *View copies* and must agree with what that popup lists (#207). The in-flight delivery states are deliberately *not* filtered — a copy in transit is bought — while the two exception outcomes (`UNAVAILABLE_DELIVERY_STATES`) and disposed-of copies are, since #396: the badge answers *how many of this do I have*. A stamp with none shows **nothing**, the same unmarked-default rule as the subtype chip and the single format. The disposition figures are markers that overlap (in collection *and* for sale), so they are listed in the tooltip, never summed. What the **variants** hold is the *second* number **inside the same chip** (#528, `countVariantDescendantCopies`, drawn as a muted parenthesised `3 (+2) copies` by the same `CopyCountBadge` — a second chip on a line that already carries catalog numbers, a Colnect link, a subtype and a price read as noise): copies of every descendant whose effective `actsAsVariant` is true, at any depth — ADR-0010 §3's rule as #101/#130's valuation and #238's price rollup apply it, so a distinct entry (error, plate flaw, overprint) is out while a variant filed *under* one is in. Two numbers, never one sum: they answer different questions, and the tree already draws each child's own badge one line down. Its totals come from `countCopiesByStamp` rather than a second `groupBy`, so "a copy you hold" cannot come to mean two things; `loadStampCopyCounts` is the one entry point loading the pair, because every surface showing one shows the other. It is the one thing that makes the badge show a **zero** — `0 (+2) copies`, when the stamp has no copies of its own, which is the ordinary shape of an unknown-variant umbrella whose copies are all filed under specific variants; the no-badge-for-none rule is untouched, since that row does hold something.
- **Which offers something is in** (#276, #349) is a read-only popup off the Copies, Stamps and Issues row menus, fed by `listOffersForTarget` (`offers/for-target`, a static segment ahead of `[offerId]`) — unpaginated, because a target sits on a handful of listings at most. It is scoped by an `OfferLookupTarget` (`item | stamp | issue`) mirroring the copies popup's targeting (#110), and a **stamp matches exactly**, never rolled up from its variant children — the same rule as the copies-held badge (#348), since the tree shows a child's own entry one line down and a rollup would report one listing twice. The stamp/issue surfaces go through `useOffersPopupAction`, the `{ action, dialog }` row-action hook; the Copies list keeps its panel-level dialog union. It lists **every** state, terminal included (unlike the offers list, which hides closed ones by default, #245): a sold or withdrawn listing is exactly what one asks a piece's history for. Ordered live-first (`active → paused → ready → preparing → sold → withdrawn`), newest first within a rank, so "where is this on sale right now?" is answered by the top of the list. The row reuses the Offers list's presentation (platform/state chips, needs-action + bidding badges, asking price with base-currency equivalent), opens the offer's detail screen on click, and links the platform listing separately. The action is **unconditional** — a sold copy's past listings are as much the question as a live one's, and the row carries no offer count to hide it by.
- A copy's **delivery state** (ADR-0009 §5) has one vocabulary: `src/lib/delivery-state.ts` (pure — valid set, labels, tint tokens, lifecycle order, `isDelivered`), read by the domain layer, the route handlers and every screen. Do not restate the list. On the Copies list it is a chip **only when the copy is not delivered** (#272) — delivered is what a hand-added copy starts as and every sorted copy ends as, so chipping it would badge nearly every row, the same reasoning that leaves a single format unlabelled — plus a single-select filter, threaded through the list, holdings-valuation and year-facet endpoints alike so the bar and the panel never disagree with the rows. The two exception outcomes (`UNAVAILABLE_DELIVERY_STATES`) are excluded from the *not offered on platform X* worklist (#259): a copy that never arrived or arrived damaged is paid for but not in hand and never will be, so it cannot be listed — while the in-flight states stay, since a copy on its way is exactly what one prepares a listing for. The intake screen renders its own editable delivery control, so it passes `hideDeliveryState` exactly as it passes `hideDispositions`.
- A **platform exclusion** (#506) is the collector saying the *not offered on platform X* worklist (#259) has already been answered for one copy: `ItemPlatformExclusion`, a `(itemId, platformId)` row whose *presence* is the whole state — no reason column, because the worklist only needs the question settled and the copy's own `notes` are where a why belongs, and because a flag with nothing to fill in is what lets the bulk write be one press. Both FKs **cascade**, unlike every reference that records something that happened: an exclusion is a preference, so deleting the platform contact must not be blocked by it and the copy takes its own with it. It reads as one more `and.push` inside the same `notOfferedPlatformId` branch — every other clause there says a copy *cannot* be listed yet, this one says the collector has decided — beside `excludedPlatformId`, the review half, which carries **no `forSale` implication** on purpose: a copy set aside and then taken off sale would otherwise fall out of both readings at once and be unreachable. One `setItemPlatformExclusion` serves the row and the bulk bar, because a decision about one copy and about a thousand is the same decision; it is idempotent in both directions (`createMany … skipDuplicates` / `deleteMany`), which is what makes it safe to point at a selection already in a mix of states, and it **refuses** an unknown platform while merely *dropping* copy ids from elsewhere — the platform is what the call is about, the copies are a set. The copy form owns the whole set (`excludedPlatformIds`, absent meaning *leave alone*, a list meaning *replace*), while the row's ⋮ entry and the bulk button turn exactly one platform on or off and are therefore offered **only while the filter names one** — a decision always names a platform, and inventing a picker for it would be a second way to answer what the form already asks. Both halves live in one toolbar `<select>` (`EXCLUDED_OPTION_PREFIX`, two `optgroup`s) since the second exists only to correct the first; only the worklist choice is remembered per collection (#275), because the review is somewhere one goes to look, not the list one works from.
- A **stamp × condition collision** (#513) is the *other* duplicate question, beside #167's "this very copy is on two active offers of one platform": a **different** copy of the same stamp in the same condition is the mistake worth catching before the copies go on — Colnect refuses the second offer outright, and on a marketplace that allows it the collector is still competing with themselves. Every surface below therefore states the **fact** and never a rule (#524): *these copies are already offered on platform X, same stamp and condition*. The dialog lists on whatever platform was picked, so asserting Colnect's rule while creating a Delcampe offer was simply wrong. The pure half is `src/lib/offer-collision-rules.ts` (`collidingItemIdsByOffer`, unit-tested), keyed through `copyGroupKey` under `DEFAULT_GROUP_AXES` — literally #372's duplicate key, so the warning and the grouping cannot drift, and format/certificate never split it. A candidate the offer **already lists** is deliberately not reported: that is `containsItemIds`' fact, and one thing said twice in two vocabularies is worse than said once — but such a copy still contributes its key, since a *second* candidate beside it would still be the offer's second copy of that stamp. The read is `collidingItemIds` in `offers.ts` (one `offerSetItem` query narrowed by the candidates' stamps, condition matched in memory), feeding both `findStampConditionCollisions` (route `offers/stamp-condition-collisions`, hook `useStampConditionCollisions`) and `ComposeTargetOffer.collidingItemIds`. It counts **every live offer** — preparing/ready/active/paused, unlike #167's active-only — because a duplicate is worth catching while both listings are still drafts. Three surfaces, all warnings and never gates: the `AddToOfferDialog` picker marks a colliding offer with an amber chip (pickable, and nothing left out of the add — only *literally* already-listed copies are dropped) and grows a **Conflicts** facet beside the state ones, which cuts across them and is therefore a group of its own, unpersisted (it is a question about *this* selection, not a way the collector likes the picker to open), hidden at count zero and **released** rather than shown empty while the targets are still loading; the stacked create form takes `notice` + `onPlatformChange` on `OfferFormDialog` and re-asks when the platform changes, since the platform is what a collision is relative to; and the Copies list's bulk bar asks only while `scopedPlatform` names one (#506's shared reading of the filter), offering **Add to #12 instead** — `AddToOfferDialog`'s `initialTargetOfferId`, which also opens the picker **on the conflict facet** and forces the state facet to *All offers* until touched — arriving from the conflict is a request to look at exactly those offers, and the remembered facet would otherwise hide the very offer the picker was opened to confirm.
- A copy's **disposal** (#394–#396; ADR-0009 addendum) is a *fourth* axis on `Item`, orthogonal to disposition and delivery: it left the collector's hands **after** arriving — lost, damaged in storage, discarded. It is the involuntary counterpart to a sale, both being ways a copy stops being held, one with proceeds and one without. Not a delivery value, because `deliveryState` describes *intake* and ends at arrival: conflating "broke a year later" with its `damaged` outcome makes supplier quality unmeasurable, and `not_delivered` additionally drops the copy from its lot and redistributes the allocation (#122), which is exactly wrong here — the copy did arrive and was paid for. Not a disposition either, those being *intent* rather than possession. Three nullable columns, `disposedAt` doubling as flag and timestamp so every filter stays a plain `where`; vocabulary and predicate pure in `src/lib/disposal.ts` beside `delivery-state.ts`, a note **required** for `other` (`lost`/`damaged` say what happened, `other` says only that something did). The allocation is **never** touched — `costBasis`, `lotId`, `itemNo`, photos and history all stay, and `itemNo` is retired rather than reused. Two preconditions that name their own reason (#273's rule): only a **delivered** copy can be disposed of, and one in a **non-terminal** offer needs that offer withdrawn first — enforced at `assertAddableCopies`, the single chokepoint every composition path goes through. Reversing clears all three columns: the axis records possession, not a history of it. **`isHeld`** (not disposed, and `deliveryState` outside `UNAVAILABLE_DELIVERY_STATES`) is the single predicate behind availability, collection value and the copies-held badge (#348); in-flight states pass, being copies on their way *in*. Soldness is deliberately outside it — that already has one mechanism at every reader (`saleLineItems: { none: {} }` behind `excludeSold`, #207) and a second would be a pure field test needing a join. What the predicate excludes is **moved, not dropped**: `HoldingsSummary.writeOff` carries the retained cost basis of the copies in scope that are gone, as a third bar line — a **cost and never a catalog value**, since a copy that is gone is worth nothing to its owner however the catalog prices it, while what it cost was really spent and hiding it would flatter the purchases. Because disposed copies are hidden from the list by default (`includeDisposed`, the `includeSold` shape), `getHoldingsValuation` **lifts that one exclusion** and partitions the scope itself — summed over the *visible* set the write-off would read `0.00` in exactly the case it exists for — while leaving `excludeSold` alone, a realised sale being #168's subject rather than a loss.
- On a purchase lot, **"to sort" and "unsorted" are two different counts** (#375). The header chip and its list filter address the `to_sort` state *exactly* (`LotIntakeSummary.toSortCount`) — a copy still `ordered` or `in_transit` has not arrived, so it is not waiting on the collector, and counting it sent them looking for a stamp that is not on the table. The close confirmation keeps the wider `unsortedCount` (`ordered` / `to_sort` / `in_transit`, `UNSORTED_DELIVERY_STATES`), because a lot whose copies are all still ordered has not been through the sort pass either and closing freezes cost-basis. The chip is therefore *narrower* than the warning by design; do not re-merge them. **Mark sorted** likewise separates its two axes: the `delivered` transition always applies, while the disposition offers **Leave as is** (#274, `LotBulkChanges.keepDisposition`) beside the three flags — some copies were filed one by one during the sort pass and a blanket value would overwrite exactly the decisions that took longest. It is a chip of its own rather than an empty selection, because all-three-off already means *clear the dispositions* and the collector cannot tell the two apart otherwise; the flag exists on the server because "no disposition given" already meant "default to `inCollection`", and that default is what it suppresses.
- **Auction sales** get their own collection nav page, and the **flat list of lots is the primary screen** (#351) — status / platform / seller filter chips (#332), sale as a column with optional grouping, inline bid editing — so "everything I have running on Allegro" needs no navigating between sales. Sale detail exists separately, for settlement and shipping. This follows from the sale being a *settlement boundary*: it matters twice (when a lot is added and when the parcel is paid for) and is in the way the rest of the time, whereas scanning closing times and refreshing bids is what happens daily. Consequently adding a lot never starts by picking a sale (#352): the dialog takes seller and platform and **proposes** the open sale for that pair when one exists, with the option to start a new one — the proposal is re-read server-side rather than trusted from the client, and refusing it (`startNewSale`) is what a second parcel from a seller who has already shipped needs. The screens live under `auctions/` (`/auctions` the lots, `/auctions/sales` the settlement list, `/auctions/sales/[saleId]` the detail), the vocabulary + staleness + parsing in `auction-rules.ts`, the reads/writes in `auctions.ts`. Four decisions the code depends on. **Staleness is relative**: a reading may be a quarter of the time that was left when it was taken old before it counts stale, capped at a day — one ratio instead of a threshold table, tightening exactly as the close approaches; a live lot past `endsAt` reports `closed` instead, because that is the only signal that never fixes itself. The toolbar filters on **two different questions**, and the split is deliberate: *signals* (`LotSignal` in `auction-lot.ts` — can-still-bid, outbid, leading, over-ceiling, won-pending) are **derived** from the figures and answer "what do I do about this now", while *statuses* are **recorded** and answer "how did this end". A watchlist is worked through by the first and filed by the second. Signals describe `watching` lots only. They span two tables plus arithmetic, so no `where` expresses them: `resolveSignals` walks the live lots once in memory and hands ids to the page query — the offers list's needs-action pattern (ADR-0013 §4), and sound for the same reason, a watchlist being bounded by what one person is currently bidding on. **Colour means "act now"**, and nothing else: an ended lot is *muted* (row opacity included), never red — there is nothing to react to, and an alarm on it would compete daily with the lots that can still be won. That is why the `Ended` / `Closing today` / `This week` window filter exists (server-side on `endsAt`, the boundary read from the server's clock so two tabs and the counts cannot disagree; deliberately **not** remembered between visits, unlike the other filters, since a list silently narrowed to old lots would hide everything running). Past the close, `BidStandingChip` stops reading as a position and reads as a **result** — *Won?* / *Lost?*, with the question mark, because it is inferred from the last bid anyone recorded rather than from the platform; a lot whose outcome *is* recorded renders no standing chip at all, its status chip saying it without the doubt. The closing time is tinted by `closingUrgency` — **absolute** thresholds (past / ≤2 h / ≤24 h), deliberately unlike the relative staleness rule beside it: staleness asks "is this reading still good?", which depends on the time left, while urgency asks "must I deal with it now?", and an hour is an hour. Its wording follows the *clock*, not the status: a `watching` lot an hour past its close reads "closed", because it plainly does not still close in the future. A recorded bid **always** stamps `checkedAt` — including an unchanged one via *Bid unchanged*, since "still at 40" is the observation being asked for — while editing anything else on the lot leaves it alone, or a three-day-old reading would look current after a title fix. The last platform is remembered **per seller and in the database** (`Contact.defaultAuctionPlatformId`, a self-FK, `SetNull`), not as one value and not in `localStorage`: where you bid follows from who you buy from, so a single "last platform" would be wrong for every seller but the one just used, and the memory has to survive a change of device. It is deliberately **not** the offers screen's remembered platform — an auction platform is not a selling platform. It is *remembered, not configured*: nothing in the contact form writes it, `rememberSellerPlatform` does, from `createAuctionLot`/`createAuctionSale` — server-side, because a seller and a platform typed in by name only become contacts once the server has resolved them, which is where both ids first exist. Its `updateMany` guard needs the explicit **null branch** (`OR: [{ id: null }, { not: id }]`): `<> 'x'` is NULL for a NULL column, so a seller who has never been tracked matches no inequality. Pre-filling it remounts the picker (`key`), because `PurchaseContactSelect` seeds its own state on mount, it is adjusted **during render** rather than in an effect (the value arrives with a query), and a platform the collector has touched is never overwritten. The `sales/open` endpoint therefore takes `platformId` as **optional** — the pre-fill must be answerable before a platform exists, or it would deadlock the very field it feeds. A lot carries **three** money fields that are constantly confused and must not be merged: `currentBid` is an observation of the auction (what it stands at, whoever is winning), `myBid` is a commitment the collector made to the platform (a proxy/maximum bid), and `maxBid` is a private valuation (the ceiling). Only the first stamps `checkedAt` — it is the only one that dates an observation. **Leading / outbid is derived** (`bidStanding`, `myBid >= currentBid`, a tie going to the bid already placed), never stored: a flag would be a fourth thing to keep current and would be wrong the moment the price moved. *Bid my ceiling* uses `maxBidWithin` — the **inverse of `allIn`**, `(ceiling − fixed − shipping) / (1 + pct/100)`, rounded **down** — because a ceiling is an all-in figure while a bid box takes a hammer price, so bidding the ceiling itself overshoots by exactly the fees. It is one of **three quick fills** (#370/#371) that place a figure the row already knows into a field beside it: catalogue value → ceiling, catalogue value → *Mine*, ceiling → *Mine*. Anything landing in a **bid** goes through `maxBidWithin` (`catalogBidRoom` is the catalogue one, computed server-side beside `bidRoom`), because catalogue value is an all-in figure too — it is what `headroom` subtracts `allIn` from; only the **ceiling** takes its source unchanged, being itself an all-in valuation. None of them writes `currentBid`: that is an observation, and filling it with a figure nobody saw would stamp `checkedAt` with a reading that never happened and make `bidStanding` say the collector is leading against their own arithmetic. Each is offered **twice** — a `⋮` entry and a hover control — built from one `QuickFill` descriptor (`value === null` *is* unavailable, `hint` says why), so the two surfaces cannot disagree. The control is **the source column's heading, abbreviated** (`CEIL`, `CAT`), set in the grid's own heading style: it names the *source*, never the target, so the *Mine* column can offer two of them unexplained. Arrows were tried first and cannot do this — an arrow shows direction, and all three of these move a figure leftward into a neighbouring column, so up and down were left naming a source they had no way to name. They live in **gutter tracks of their own** (`quickFillSlot`, explicitly placed like `GRID_RULE` so everything else keeps auto-flowing) and **centred across both rows** of the column they write: a quick fill sets the whole column, and putting each control in the cell it happens to write scattered them over two different rows for no visible reason. A column offering two **stacks** them — side by side they read as one two-word label on the figure beside them. The gutter goes **after** its column, not before: amounts are right-aligned, so the empty part of a track is on its left, and a gutter placed ahead of a column ends up one gap from the *previous* column's figure and several from the one it fills. Track width is fixed unhovered, or revealing a control would shunt a figure out of its column. A quick fill goes through the same pending override an inline edit does. A **row click** opens the lot's sale with `?lot=<id>` (#374). The sale screen scrolls that card into view and flashes it once with `just-added-flash`, but the flash is only the *arrival*: the mark itself is an accent **ring** (a `box-shadow`, so the card does not resize) plus a labelled strip with a ✕, and it **persists** — a flash is over before the eye has finished reading the parcel's other lots, leaving the collector to find the row again. The URL is the whole state; clearing deletes that one param and `replace`s, so undoing a highlight is not a step to walk back through. Clicks originating in `a, button, input, select, textarea, [role="button"]` are left alone — the click-to-edit cells present as the last of those — as is a click that ends a text selection, and a modified click opens a tab. It is off (`linkToSale`) on the sale's own screen, where the click would land on the page already being read. `AuctionLot.startingPrice` is a **record, never a figure**: it is what the lot opened at, so it is displayed muted in the bid slot while no bid exists (`from 20 PLN`) and enters no arithmetic at all — a lot nobody has bid on costs nothing whatever it opens at. The row renders the three as a **3 × 2 grid** (Auction / Mine / Ceiling × bid / all-in): each figure exists twice, and columns are what make them comparable. The catalogue figures sit beside them **as a second section, behind a rule and under their own row labels** (`value` / `headroom`), because the worth side does not share the cost side's vocabulary: `all-in` there names a figure recomputed with fees, while the worth side's second line is a *subtraction* between the two. Labelling both `all-in` promised an operation the last column does not perform. Anything else answering "what is this worth" — a recommended price — is another column in that section, never a fifth cost column. Exactly one cell of each pair is **stored** — the two bids are hammer prices, a ceiling is an all-in valuation — and the other is computed from it and shown muted, which is why the ceiling's *bid* cell is `bidRoom`, the very figure *Bid my ceiling* places. But the collector's own two columns, *Mine* and *Ceiling*, are **edited from either side**: the two cells are one fact stated two ways, and which one happens to be stored is an implementation detail. A figure typed into the muted half is converted back and the stored half is what is written, through **two helpers that exist only because rounding direction is the whole question**: `bidCosting` for an all-in typed into *Mine* (the inverse rounded to the **nearest** cent, so the total reads back as the one that was typed; a target the fees alone swallow clears the column rather than inventing a bid) and `ceilingAllowing` for a bid typed into *Ceiling* (`allIn` rounded **up**, the smallest ceiling that still lets that bid be placed, with an epsilon so a whole-cent cost is not pushed to the next one). Neither is `maxBidWithin`/`allIn`: those answer a *cap* question and round down, which is right for `bidRoom` and *Bid my ceiling* and wrong here — on a 20% + 1.50 house a stated all-in of 200 came back as 199.99, which reads as arithmetic going wrong rather than as a bid being chosen. Nothing in the two-sided conversion is a limit, so nearest/up is safe: a placed bid is a *record* of a commitment, and whether it outruns what the lot is worth is what the ceiling and `myBidOverCeiling` are for. **Auction stays one-way**: its bid is an observation, and there is nothing to state twice about a price someone else set. This is why the row carries `premiumPercent`/`premiumFixed`: the derived half is computed in the row from the figure **as displayed**, through the pure module, so one pending override covers both cells of a column instead of the two disagreeing while a refetch is in flight. The two bid cells are tinted **together** by `standing` (green/red), because they are one comparison; the collector's own cells go **amber** when `myBidOverCeiling` — their commitment costing more than their ceiling is a different fact from the market outrunning them, and the only one they can take back. A row's **all-in excludes shipping** (premium only): shipping belongs to the parcel and the sale's total adds it once, so charging it per row would double it the moment two lots are open with one seller. And the list's **reading order** is decided by the status chip — `watching` soonest-closing first, a terminal status most-recent first, no chip at all newest-tracked first, because the two orders contradict each other in a mixed list.
- The lots list **hides closed lots by default** (#504) — won, lost, observed and cancelled alike, which is `outcomeWhere("pending")` applied in `lotListWhere` whenever no explicit `outcome` is chosen — on #245's rule for sold offers: a watchlist is what is still to be decided, and the archive grows without bound. An explicit outcome chip wins, and a remembered `includeClosed` flag (`Show closed`, the counterpart of `Show sold/withdrawn`) is the escape hatch the single-select chips otherwise leave no room for. A **sale's own** lots (`saleId`) are exempt: that screen is one parcel's settlement, where a won lot is the point. With the default no longer a mixed list, `lotOrderBy` reads it soonest-closing first.
- **Duplicate grouping on the Copies list** (#372) collapses the list to one row per *bag of interchangeable copies*, and **multi-select** (#373) is the escape hatch for the compositions it cannot express. The key's fixed part is `stamp × condition` — Colnect refuses a second offer for the same stamp in the same condition, so a group mixing conditions would produce an offer that cannot be posted — with **format** and **certificate** as two independently joinable axes (`CopyGroupAxes`, remembered per collection). Both on, the key is exactly the one `valuateItemRows` is computed on, so every group has one unambiguous per-copy figure; where members disagree on an axis left at *any* the row is marked **mixed**, which with the axis on cannot occur by construction. The pure half — key encode/decode, `mixedAxes`, `outlierCopyIds` — is `src/lib/copy-groups.ts` (unit-tested); the read is `listItemDuplicateGroups` in `items.ts`, beside `listItemsPaginated` so both narrow through the same private `buildItemWhere`. Grouping is **server-side** because the list is offset-paginated: a client-side grouping would split a group at a page boundary and report two half-counts. Groups order **count descending** then `stampId` (total, so pagination cannot repeat or skip one), which is why the sort control is *hidden* rather than left offering an order it cannot honour. Grouping is **not filtering** — the sidebar filters decide which copies you look at, the toggles what counts as the same item, and both compose — but it does force the composition picker's eligibility (**for sale, delivered, unsold**), so the delivery-state and *Include sold* controls grey out and the holdings bar narrows with it. **Expanding a group needs no endpoint of its own**: a key *is* a filter combination, so members come back through the ordinary items query with the panel's filters plus the key (`groupMemberFilters`) — which is what the `"none"` certificate sentinel exists for, null being a value exactly as `"single"` is for format. The group row's own action is a **selection** shortcut, not a second listing flow (#398): its members carry the list's ordinary checkboxes and the row's own checkbox — a `⋮` entry until #422 moved it into the select gutter — ticks them, so what happens to a bag of copies is decided once, in #373's bulk bar. There was a dedicated *List all as one offer* dialog first, and two ways to compose an offer out of the same rows is one more than the screen can explain — the packaging question it answered is already `AddToOfferDialog`'s *Add as* (`createOffer`'s `seedPerCopy`: one single-copy set each rather than one set holding everything). **Outliers** (differing from the group's *most common* value on an *any* axis, never a fixed "format ≠ single" test) keep their marking on the member rows and are **left out of** the quick select-all, but tick individually like any other copy. The shortcut is **not** conditioned on the group being open: it expands the row and walks the member pages to the end before ticking (a partly loaded group would tick a subset and call it "all"), holding the request as a nonce whose *served* value is a **ref** — bookkeeping about a request is not something the row renders, and a second state would be a `setState` inside the effect that discharges it. Because a grouped panel runs no flat query, `CopySelection` carries the **items**, not ids (`onToggle(item)`, `onSetMany(items, selected)`) and the panel's selection is a `Map<id, ItemListItem>`: there is no page here to resolve a member's id against. Which copies are still free **on a platform** is deliberately not re-asked in that dialog — the list's own *Not offered on…* filter (#259) is the entry point the feature exists for, and it also pre-fills the platform into the form. `AddToOfferDialog` takes `items: ItemListItem[]` throughout; `ComposeTarget*.containsItemIds` replaced the old boolean, so an offer holding *some* of a selection keeps those copies out of the add and says so, and only one holding *every* copy is disabled. Its packaging choice is **one control, not two submit buttons** (unlike `ComposeSetDialog`), because it governs the stacked create form too, whose submit lives inside the offer form. A checkbox beside an `InventoryItemRow` sits in the shared `SELECT_STRIP` (`inventory-copy-list.tsx`) — a full-height `<label>` gutter with the box centred in it — on every surface that has one: a copy row is four lines tall, so a top-aligned box reads as belonging to the first line, and a 13-pixel target is poor for a list one works through by ticking. The sale-line picker keeps its own shape, where the whole row toggles.
- The Copies list's **grouping is a mode, not a flag** (#421, #424): `none | duplicates | location | ref | issue`, one persisted per-collection preference, because they are readings of one list and exactly one can be in effect. **Filing groups** collapse the list by *where a copy is*, and differ from #372's duplicate groups on every axis that matters. They force **no eligibility** — "where is it?" is a fair question about a sold copy still on the shelf, so `Include sold` / `Include no longer held` stay live and the holdings bar is not re-narrowed. A location groups **exactly**, never rolled up: a nested location is its own row stating its full path, since a roll-up would report one copy under every ancestor and the location filter's own subtree scope (#385) is already how one asks for a branch. A ref only means anything inside its location, hence `(locationId, locationRef)` and not `locationRef` alone. The reading order is location path then #330's `compareLocationRef`, neither of which SQL can express, so `listItemLocationGroups` reads the groups **whole and pages them in memory** — bounded by the collection's locations × refs in use, not by its copies, and a *total* order, which is what makes paging over it neither repeat nor skip a group. Null and `""` refs are folded into one "no ref" group after the `groupBy`, which the database cannot do for us. Two sentinels carry the buckets an absent filter cannot express — `NO_LOCATION` / `NO_LOCATION_REF` (`location-groups.ts`, pure, so a client row can name them without importing a server module), the `"single"`/`"none"` pattern again — and a group addresses its own members through the **ordinary items query** with `locationExact: true`, so no per-group endpoint exists. A filing row is deliberately **thin** next to a duplicate row: a group is a *place*, so it states the place and the count, and what the copies are is what the member rows answer. **Issue groups** (#424) are the same shape a third time — thin row, no eligibility forced, read whole and paged in memory, members addressed through the ordinary items query — and differ in the two places the subject differs. The reading order is the **Issues list's own** (year, then `primaryCatalogSortKey`, then name; #181), because a collector scanning copies by series is reading the list they browse the catalogue in and two orders for one subject is two things to learn; the issue-less bucket sorts last, being the absence of the subject rather than a thin edge of it. And the issue lives on the *stamp*, which `groupBy` cannot reach, so the filtered set is scanned and counted in memory over a two-field select — `listItemYearFacets`'s own shape, the year being on the stamp for the same reason. Membership is many-to-many but a copy is counted under **one** issue, its stamp's first, so the groups partition the list and their counts add up to it; `FIRST_ISSUE_MEMBERSHIP` (`orderBy: { issueId: 'asc' }, take: 1`) is what makes that *one* answer — an unordered `take: 1` let the row, the grouping and the title reads each name a different issue for one copy, which is a latent bug this fixed rather than a new rule. Counting on the first membership while reading members back through the ordinary `issueId` filter (which matches **any**) is #172's existing pair, deliberately not a third rule: they differ only for a stamp filed in two issues, and an issue filter meaning "and no earlier one" would make the sidebar's own filter answer a question nobody asks of it.
- Every **grouped row shares one shell** (`inventory/copy-group-shell.tsx`, #422): the expand arrow, the select-all box, the member list and the page-walking `useGroupMembers`. The arrow is **vertically centred** (a group row is four lines tall, and one pinned to the top reads as belonging to the first line), and quick select-all (#398) is a **checkbox in the same `SELECT_STRIP` gutter the member copies use** — one click, in the column the eye is already in — rather than a `⋮` entry, which was two clicks and a menu to read for the thing the row is most used for. The duplicate row's `⋮` therefore disappeared entirely: it held nothing else. `allSelected` stays **derived from the copies actually ticked**, never from the pending request, so a box can never claim "all" before the page walk that makes it true has finished.
- A **catalog-number chip copies its number on click** (#420, `shared/catalog-number-chip.tsx`), everywhere one is drawn — stamp/issue/copy rows, the pickers, the quick-price dialog. What it copies is narrower than what it reads: the **area prefix stays and the vendor abbreviation goes** (`Mi·PL 200` → `PL 200`), because the prefix is part of the number's identity (#66/#377) while the catalogue is context the collector already has in the field they are pasting into. The rule is pure (`catalogChipCopyValue` from the parts, `catalogChipCopyValueFromLabel` where a surface only carries a formatted label — the pickers' `catalogLabels`, an issue's declared range; a label whose head is not a short letter run is left whole, since eating a multi-word number like `Ark. 103` is the worse mistake). Confirmation **recolours the chip** instead of adding a ✓: these sit in wrapping rows of four or five and a glyph appearing would reflow the line under them. It renders a `<button>`, which is also what keeps it safe inside a click-through row (#374).
- A **hierarchical filter's scope** is the collector's (#385), not a fixed rule: `useSubtreeScope(axis)` (`shared/subtree-scope.tsx`) is one persisted flag per axis — `area`, `location` — defaulting to *include descendants*, because picking "Poland" and being shown only what sits directly on that node is not what browsing a tree means. It is **global**, not per-collection like the area/year *selection* (`use-collection-filter-store`): it is a way of reading a tree, and it sits beside the equally-global collapsed-set key. The two axes resolve in different places and that is inherent: an area selection is expanded **client-side** through the shared `resolveAreaFilterIds` (never an inline `getDescendantIds` + self, which is how six screens came to each own a copy of the rule), while a location's subtree is resolved **server-side** in `resolveLocationScope` — every location-filtering read goes through it, so the list, its holdings bar and its year facets cannot disagree about what "in Klaser A" means. `SubtreeScopeToggle` renders **only when the selected node has children**: on a leaf both states select the same rows, and a control that cannot change anything is noise on a screen already dense with filters. The area sidebar's in-scope shading follows the toggle, so the tree marks the set the list is actually showing.
- A copy's row menu links to **its purchase** (#387) via `ItemListItem.purchase` (`{ id, label }`, the supplier + date pair the purchases list leads with, resolved in `ITEM_LIST_SELECT`'s lot join). The entry is **hidden, not disabled**, when there is none — a hand-added copy was never bought through an order and nothing on the row promises otherwise, which is #273's stated exception. It lands on `purchases/<id>?lot=<lotId>`, and the purchase detail gives that lot #374's arrival treatment: seeded into `useCardExpansion`, scrolled to `block: "center"` (its own header is sticky), and marked with a **persisting** ring + dismissable strip rather than only the one-shot `just-added-flash` — an order can hold a dozen lots and a flash is over before the eye has finished reading them. The `RowAction.hint` doubles here as the *object* of an enabled navigation, not only as a disabled entry's reason.
- **Attaching an existing copy to a lot** (#388, `attachItemsToLot`) is the third verb beside `intakeStamps` (which creates copies) and `removeLotItem` (which deletes them): a copy entered by hand before the receipt was recorded, or filed under the wrong purchase. Only `lotId` changes — delivery state, dispositions, location, `itemNo` and photos all stay, because a copy already in hand does not return to `ordered` on account of a late cost record. **Both ends must be open**, and for one reason: a cost basis is frozen at close (ADR-0009 §3), so a closed *target* would not include the copy in the split it has already made, and a closed *source* has already distributed its pool over a set this would silently shrink, under-costing the copies that stayed — reopening it is the way through, and the refusal says so. A copy on another **open** lot is allowed but never moved silently: `allowRelink` is a parameter the dialog sets only after the collector has confirmed a warning **naming** the orders being left (a count cannot tell them whether this is the mistake they are correcting). Copies already on the target lot are a no-op, not an error. Refusals are **collected, not thrown** — one copy stuck on a closed lot is no reason to abandon the other nineteen. Eligibility is one filter, `attachableToLotId`, expressed as two `OR` branches rather than a `lotId: { not: … }` (an inequality is not a reliable way to say "or no lot at all" about a nullable column) and pushed into `buildItemWhere`'s `and` so it cannot collide with the search's own `OR`.
- Password managers overlay their fill icon on short **identifier** inputs — a catalog prefix, an order number, a lot number, a location ref — and `autoComplete="off"` alone does not stop them (#262, #389). Spread the shared `NO_AUTOFILL` (`shared/no-autofill.ts`) onto such a field; it carries the per-vendor opt-outs (`data-lpignore`, `data-1p-ignore`, `data-bwignore`) beside `autoComplete`, because each extension only honours its own. Do not re-inline the four attributes: they were copy-pasted at eight sites before this and a new field was fixed only once someone reported it.
- A list toolbar's toggle chip is the shared `FilterChip` (`shared/filter-chip.tsx`) — the offers status filter (#332) and the sales one (#392) are one control, and `FILTER_CONTROL_STYLE` is the box every toolbar select shares with it so a mixed row lines up. A **remembered** filter follows #325's rule exactly: the URL wins where it names a value (a shared link keeps meaning what it meant), the stored per-collection value fills in otherwise, and every change writes both — so clearing the filter clears the memory of it. The sales status filter carries **no counts**: there is no sales facet endpoint, and a chip promising a number it cannot compute is worse than a bare one.
- **Stepping from one offer to the next** (#429) is the filtered list carried into the detail screen: the offer row appends `offerListContextQuery(filters)` to the link it opens (`offers/list-context.ts`, pure and unit-tested), the detail page parses it back and renders `‹ Previous · 3 of 12 · Next ›` beside its **← Offers** link, which now points at the list *as it was*. It travels in the **URL, not off #325's remembered filters**, for two reasons: an offer is opened from other screens too (the copies popup, a short link, a bookmark), where a walk through a list nobody is looking at would be an invention — hence `from=list` as an explicit marker, since a context with *no* filters is a legitimate walk over the whole list and is otherwise indistinguishable from a plain deep link — and a link to "the third preparing offer on Colnect" then still means that when it is reopened. The remembered **show-closed** toggle (#245) is part of what the list was showing, so the walk carries it (`closed=1`) even though the list keeps it out of its own URL; the way *back* deliberately drops it again, the list reading its own stored value. Server-side it is `offerListNeighbours` — the ids alone, over the same `where` and the same `OFFER_LIST_ORDER_BY` the list reads, which is where the order got its `id` tiebreak: offers created in one transaction share a `createdAt`, and an unstable order both repeats a row across pages and skips its neighbour. Position falls out of the same array, so the indicator is free. The query is asked **once per offer and then frozen** (`staleTime: Infinity`, and a key outside `offerKeys.all` so `invalidateAll` cannot reach it): the use case is finishing an offer — which usually moves it *out* of the filter that was showing it — and stepping on, so an answer that refreshed itself would take the walk away at the moment it is needed. An offer not in the filtered set at all reports `position: null` and the strip is absent; the two ends are disabled rather than hidden (#273), the position beside them saying which end.
- A **sold** copy carries its own chip on the copies list (#393), tinted `success` rather than the disposal chip's error tint — it left the collection the way it was meant to, so the chip states an outcome instead of raising an alarm. It can only ever appear under *Include sold* (#207), which is exactly the mixed view it exists for. `ItemListItem.sold` comes from `_count.saleLineItems` on `ITEM_LIST_SELECT` — the very relation `excludeSold` filters on, so the chip and the filter cannot disagree. Soldness stays outside `isHeld` (#394), as it always has.
- Quick-sell (#225) is reachable from the offers list **and** from an offer's own detail screen (#390). `SellOfferFlowDialog` takes a structural `SellableOfferSubject` (id, name, label, platform, price, currency) rather than `OfferListItem`, so `OfferDetail` satisfies it and there is one flow rather than two that drift; the precondition is the same at both ends — non-terminal, ≥1 set. The detail page computes `today` at request time exactly as the list page does, so a sale started from either place defaults to the same date.

- An **auction amount is converted with a rate, not on the server** (#498, `auction-base-amount.tsx` + `formatBase`). `AuctionLotListItem` / `AuctionSaleListItem` carry `baseCurrency` + `baseRate` and the screens do the arithmetic, because half the figures on a lot row are computed *there* from the seller's fees as they are typed (a bid's all-in cost, the bid a ceiling allows) — a server-converted field would describe the row as it was fetched. The rate is a lot's **frozen** `fxRateToBase` where it has one (a recorded result is a dated observation, ADR-0009 §4) and today's otherwise, filled by `attachBaseRates` in one batch per currency, best-effort like `attachBasePrices` (#208). Where it renders is the split #498 settled: the flat lots list and the sales list convert the **headline figure only** (the bid; the parcel's all-in total) since a list is scanned down a column, and the sale's own screen — cards and totals card alike — converts **everything**, via `AuctionLotRow`'s `baseAmounts="full"`. On the figures the collector **declares** — *Mine* and *Ceiling*, each from either of its two sides — the converted line is also **editable** (`AmountWithBase`'s `onSaveBase`, inverse `fromBase`): what leaves the account is the collector's own money, so a limit reasoned in PLN should not need dividing by a rate in the head. The stored value stays the sale's currency, exactly as the bid ↔ all-in pair stores the hammer price whichever side was typed. The *auction's* bid is deliberately not editable this way — it is an observation transcribed from the listing, in the listing's currency.

- A **flag shown on a list is shown on the thing's own screen too** (#505): the *Sold on Allegro* chip reaches `OfferDetail.platformSale` from the same `unrecordedPlatformSales` the list reads (narrowed to the one offer), never a second comparison. A chip seen in passing and then missing from the page it was clicked through to reads as having been dealt with.

- A **detail page reads; it does not become a second editor** (#517/#518/#519). A copy, a stamp and an issue each have a screen of their own — `inventory/[itemId]`, `stamps/[stampId]`, `issues/[issueId]` — reached from the list row's `⋮` menu — first entry — **and promoted to the row's quick actions** (`useDetailPageAction`, `shared/use-detail-page-action.ts`), first icon there too, since going to a record's screen is the one thing every one of these rows can do. The icon is on **rows inside the detail screens as well** (an issue's stamp tree, a stamp's variants and issues, the copies on either) through the same `RowQuickActions`: a row in a card is still a row, and reaching a record should not be a different gesture depending on which screen you met it on. That is also why a `readOnly` copy row renders **exactly this one** icon rather than none — `readOnly` means the copy is not edited from a screen that is not the Copies list, and it would be an odd kind of read-only that refused to let you read more (so the #110 popup gains it too). Whole-row click was weighed against the icon and **rejected** for these rows, the `offer-row.tsx` / `OfferTargetRow` precedent notwithstanding: a copy row is selectable (#373's checkbox is right beside it) and an issue-tree row expands, so a click there is already spoken for, and the rows are dense with controls that each mean something else (a chip copies, a thumbnail opens a lightbox, a price edits inline). They **consolidate**, they do not replace: the popups they gather (#110 copies, #114 prices, #276/#349 offers) stay exactly where they are, because a popup answers one question without leaving the list and a page is for when the whole picture is wanted — and every field on these screens is still written through the dialog that already owned it, a second editing surface for one record being a second place to keep honest. The chrome is one kit (`shared/detail-page.tsx`: `DetailLayout`, `DetailCard`, `DetailFullRow`, `FieldGrid`, `Field`, `EmptyNote`), and the layout is a **dashboard, not a column**: one column of cards down the middle of a wide monitor is a screenful of scrolling beside a grey plain. It is **two explicit columns** — `DetailColumns` + one `DetailColumn` per side — and **which card sits where is each screen's own decision**, stated in its JSX. The split is the same question on all three: the left column is what the record *is*, the right is what the collection *does* with it (copies, offers, purchase, sale) — which is also the reading order when a narrow window collapses the two into one. Two earlier attempts are worth not repeating: a `grid` places a card in a *row*, so the row is as tall as its tallest card and every shorter one beside it leaves a hole, and `dense` packing cannot rescue it (it only pulls a card forward into a gap something actually fits into, and a four-field card against a stamp tree fits nowhere); CSS **multi-column** does fix the holes — it balances columns rather than filling rows — but it *decides the order*, and the pairings that make these screens readable (an issue's stamp tree beside its completeness grid, a copy's physical facts beside its trade history) are not something a height-balancing algorithm knows about. So the columns ending at different heights is **accepted**, the alternative being a hole or an order nobody chose; keeping the taller column's tail short is what the ordering is for. `auto-fit` over a minimum width is the single-column fallback and is not a breakpoint — this app has none, being desktop-only. **A card with nothing on it is not rendered at all** (#536) — `empty` on `DetailCard`, which returns `null`, so emptiness is the card's own business rather than each page remembering its own `&&`. The Notes card was the first to work this way and the Wants card (#532) the second; #536 made it the rule, because a heading over "never sold" is furniture that answers a question nobody asked and pushes the answers that do exist further down a column these screens are trying to keep short. Pass a query's loading flag into `empty` too: a card that appears once, filled, beats one that flashes an empty shell or fills and then vanishes. `EmptyNote` survives for the other case — a card that *does* hold something and has nothing to draw right now (a checklist filter that matched none of the tree). The **exception** is a section whose empty state carries the only way to create the first entry ("No lots yet. Add a priced lot…" on a purchase order, "No lots in this sale yet" on an auction sale): that is the way in, not clutter, and it stays — which is why the older detail screens (#165 offer, #166 sale, #120 purchase) were audited under #536 and left as they are. Vertical spacing is a **margin per card**, not `gap`: `row-gap` does nothing in multi-column; the container cancels the last one. `DetailCard` carries `break-inside: avoid`, which costs nothing outside a masonry. `DetailFullRow` is also the identity band across the top. Each card that shows *related records* is shared with the popup it mirrors rather than re-rendered — `RelatedOffersCard` (which owns `OfferTargetRow`, the popup importing it back) and `RelatedCopiesCard` (the popup's `InventoryCopyList` in `readOnly`), so a listing or a copy cannot read one way inline and another in a dialog. The header identity is `shared/stamp-identity.tsx`, shared by the copy and stamp screens for the same reason. Each page reads through the **list's own** enrichment — `getStampListItem` / `getIssueListItem` beside the existing `getItemListItem` — so the page and the row it was opened from cannot describe one record differently; the copy page reads through `listItemsPaginated({ ids })` rather than `getItemListItem`, because that one is owner-scoped and the URL carries a collection slug. `CatalogPricesCard` shows the **cross-catalog averages** inline and puts the per-edition breakdown behind #114's own dialog: the average is the figure a value is read off, and copying the whole matrix onto three screens would be #114 rewritten three times. The issue screen's **completeness grid** (`issue-completeness.ts` + the pure `issue-completeness-rules.ts`) is the disposition × condition half of #133, computed on demand for one issue exactly as #133 reasoned — the list keeps #54's lightweight indicator. Two figures, and they answer different questions: **owned** is progress, **complete sets** is the *minimum* across every required member, so one missing stamp is zero however deep the pile of the others. Dispositions **overlap** (a copy is in the collection *and* for sale), so the rows never sum to *Any*; the exclusions are `copy-counts.ts`'s exactly, or the card and the badge beside it would disagree about what having one means. Format is deliberately **not** an axis here — that is the rest of #133.
- A **missing name prints nothing, not a placeholder** (#535). `StampTitle` (`shared/issue-view.tsx`) draws the stamp name on the issue tree and the picker; a stamp without one now renders an empty string rather than "(unnamed)", and its date loses the comma that was separating it from the absent name. A stamp is read by its catalog number, which the detail line under it already carries, so a column of "(unnamed)" was the same non-fact repeated down every row. The flat stamp list already worked this way (`stamps/stamp-row.tsx` omits the whole name line). This is about **display**; a `?? "(unnamed…)"` in a *label* — a delete confirmation, a dialog title, a picker's summary line — stays, because a sentence naming the thing it is about cannot have a hole in it.
- In-location refs (`A234`) are ordered by `compareLocationRef` (`src/lib/location-ref.ts`): prefix first, then the trailing number, separators ignored, blanks last. Use it anywhere refs are sorted — a plain numeric collator disagrees as soon as the separator varies.
- The issue's **stamp tree is ordered by hand** (#549, `IssueMember.sortOrder`). Until it existed the tree had no `ORDER BY` at all, so this is the first time the order is *stated*; existing members were seeded in **insertion order** (`stamp.createdAt`), which is what the default has to be — a collector who has arranged nothing should see the stamps in the order they were added. The value is only ever read **within one sibling group** — the issue's roots against each other, one parent's variants against each other, and the two never compared — so a reorder densely renumbers the single group it was handed and leaves every other group's values alone, and a value shared across groups is not a collision. That is also why an append is `max(sortOrder) over the whole issue + 1`: one number is past every group at once, and it is the right answer before the newcomer's parent is even known. Both readers of `MEMBER_SELECT` must agree — `listIssueMembers` orders in SQL, `toIssueData` through `orderIssueMembers`, both `sortOrder` then `stampId`, because the select is `as const` and a readonly `orderBy` is not assignable to Prisma's input type (the same reason `checklists` is ordered in the mapper). Arriving stamps land **at the end, keeping their own relative order**: `moveStampNode` and `mergeIssues` both re-stamp what they move, a position being a statement about *one* issue's tree and nothing a stamp carries between them. The pure half is `src/lib/issue-member-order.ts`, and its one real rule is that a reorder names a **complete** sibling group: the tree can be narrowed by #531's checklist filter, and a drag inside a narrowed tree would move a stamp past a sibling that was never on screen — which is why the UI puts that filter away while reordering *and* the server refuses a partial group, one being a courtesy and the other the guarantee. `effectiveParentId` mirrors `buildStampTree`'s roots rule (a variant whose base belongs to another issue is drawn as a root, so it is grouped as one), or the order would be validated against a grouping nobody can see. The UI is `shared/stamp-tree-reorder.tsx` over #306/#313's `useReorderList`: reordering is **a mode, not an always-on affordance** — thirty rows each carrying a permanent grip read as a list you are expected to be rearranging, which is not what looking a number up is — and the toggle sits at the **foot** of the tree beside **+ Add stamp**, both being things done to the tree as a whole rather than to a row in it. `StampTreeGroup` is a component rather than a hook call per level because a group needs its own `useReorderList` instance and the groups are found by recursion; it takes a `renderNode`, so the list row's editable node and the detail page's linked one stay two different rows on one wiring. The drag is optimistic and rolls back on refusal, a drag that snapped back a third of a second later reading as a drag that did not take. There is deliberately **no "custom order" sort on the flat Stamps list**: it spans issues, so there is no single sequence to sort by, and the tree — which has never had a sort switcher — simply *is* the order.

## Testing Direction

- `pnpm lint` — run before finishing any task that touches source files.
- `pnpm typecheck` — TypeScript verification.
- `pnpm test:unit` — pure logic only, no Prisma imports.
- `pnpm test:integration` — requires real database via `docker-compose.e2e.yml`. Run before committing schema or domain logic changes.
- Write migration SQL manually. Create directory and `migration.sql` by hand under `prisma/migrations/`. Then `pnpm exec prisma generate`.
- Never run `prisma migrate dev`, `prisma migrate reset`, or `prisma db push` directly. Exception: `pnpm e2e:db:reset` is safe.
- When starting a local dev server for verification, use `pnpm exec next dev --webpack -p 3002` and stop it before finishing.
- Always run the dev server on **webpack** (`next dev --webpack`), never the default Turbopack: Turbopack's dev/HMR leaks memory until the container OOMs (an open, idle browser tab grows the server heap unbounded; webpack plateaus). The `docker-compose.dev.yml` overlay is pinned to `--webpack` for this reason. See issue #161; re-test Turbopack after Next.js upgrades and revert once fixed upstream.
- The user tests the app through Docker Compose. Do not leave dev servers running.

## Before Implementing Features

If a request would require defining product behavior, ask targeted questions first. Good questions are concrete and bounded:

- What is the first workflow we want to support?
- Should catalog numbers be per-standard (Michel, Scott, Fischer) or free-form?
- Should condition follow a standard scale or be free-form?
- Should a collection be shareable with other users?
