# Agent Instructions

This project is intentionally vibe-coded. Future agents must preserve product intent, avoid invented requirements, and ask clarifying questions when the next step is not clear.

## Product Context

- Product name: Stamporama
- Purpose: a self-hosted web app for stamp collectors
- Desktop browsers only; no mobile layouts or breakpoints.
- Core concept: **collection** — the top-level organizing unit that scopes all stamp data for a user

## Working Rules

- Do not assume domain behavior. Ask before defining catalog standards, condition scales, trade workflows, auction integration behavior, or pricing logic. Ask one question at a time.
- Do not add user-facing functionality unless the current task explicitly asks for it.
- Prefer small, reversible changes with clear documentation.
- When changing user-visible behavior, update `docs/user-guide/` in the same task.
- When changing behavior, data model, setup flow, or architecture assumptions, update every affected document (`README.md`, `docs/product/brief.md`, `docs/architecture/overview.md`, relevant ADRs, `docs/user-guide/`).
- When introducing a framework, library, or major pattern, add or update an ADR in `docs/decisions/`.
- Update this `AGENTS.md` file when new project knowledge or workflow rules would help future agents.
- Favor boring, well-supported tools over novelty. Preserve existing user changes.
- Use GitHub Issues as the shared backlog. Use Conventional Commits for issue titles. Always assign labels (`backlog` + type + priority when known). Do not maintain a local `TODO.md`.
- If GitHub connector cannot create issues, use `gh` CLI as fallback.
- All GitHub content must be in English.
- Do not create git commits unless the user explicitly asks. Do not push unless explicitly asked.
- Solo project: commit directly to `main` by default. Create feature branches only when the user asks for a PR.
- When pushing to `main`, try `git push origin main` first. If rejected, fetch, rebase, rerun verification, push again.
- Use Conventional Commits: `feat:`, `fix:`, `docs:`, etc. Include GitHub issue reference when one exists.
- When a commit title alone would omit useful context, include an extended commit message body.
- Use a separate git worktree only when the user explicitly asks for one.

## Multi-Step Implementation Plans

When a task spans more than one logical area, write an implementation plan before starting. Store it under `.claude/plans/`. A plan is executed fully within a single session.

- Begin with a `## Progress` section containing a checkbox list of numbered steps.
- Steps are executed in order. Mark each step `[x]` immediately after completing it.
- Each step must state a **Done when** criterion.

## Agent Collaboration

Use specialized roles only when the task benefits from them. Small, localized tasks can be handled by one agent.

Use specialized roles for larger changes that cross domain, data, authorization, or user-flow boundaries:

- Architect: schema, ADRs, major patterns.
- Designer: UI flows, dialogs, interaction design.
- Developer: scoped implementation.
- Tester/Reviewer: browser flows, regressions.

Prefer Architect before changing Prisma schema, permissions, collection scoping, authentication, routing, or ADR-documented patterns. Prefer Tester/Reviewer after changing forms, dialogs, collection routing, authentication, permissions, or migrations.

## Technical Direction

- Collection-scoped access control: `collectionId` on data, owner has full access, checks live server-side.
- Collection URLs: `/c/[collectionSlug]/...`; slug resolution authorizes by internal `collectionId`.
- Better Auth for authentication.
- Prisma with PostgreSQL (minimum **version 15** — migrations use `NULLS NOT DISTINCT`; see ADR-0006). Treat schema changes as product decisions.
- Bumping the bundled `postgres:` image to a new major breaks the dev stack: the `db_data` volume keeps the old cluster and 18+ images relocated the data directory. It needs a dump/restore, never just a tag change — follow `docs/development/postgres-upgrade.md`. Production uses an external database and is unaffected.
- SPA-like collection interaction: Next.js App Router as route/auth shell, client-side queries/mutations for rich screens.
- TanStack Query for data fetching, TanStack Table for list views.
- Cursor-backed infinite scrolling for large lists via shared primitives.
- Keep domain logic out of UI components. Keep authorization server-side.
- Explicit module boundaries under `src/`.
- Self-hosted deployment: CI pushes multi-arch image to `ghcr.io/michalwy/stamporama` for release tags only. `docker-compose.prod.yml` + `.env` for production. `scripts/install.sh` is the curl-able installer. Version baked via `STAMPORAMA_VERSION` build arg, shown through `getAppVersion()` in `src/lib/version.ts`.
- Browser extension (Stamporama Assistant, #253; ADR-0015) lives in `extension/` — a separate pnpm-workspace package (MV3, esbuild + hand-written `manifest.json`, own `tsconfig`). It is **excluded from the app's** `pnpm lint`/`typecheck`; build and check it on its own with `cd extension && pnpm build|typecheck`. It calls the Colnect matcher endpoints with an `AssistantToken` bearer (session-or-token auth via `src/lib/route-auth.ts`), because the extension reaches us cross-site from colnect.com. Its match window groups results and hides the decisions the collector has effectively already taken (#305): a `needs-confirm` row every candidate of which already carries some Colnect ID — the matcher never silently overwrites (#250), so those rows return on every re-scan. One free candidate keeps the row, since that free stamp is most likely the answer (`isAlreadyLinkedElsewhere` in `core/decisions.ts`). The same rule governs the *numbers*: the backfill (#280) fills a catalog the stamp has none for and only **reports** one the two sides disagree on, so #433 is the collector settling one of those disagreements by hand — `proposeBackfill` resolves each conflict's `overwriteNumber` by the very rules a fill uses (a prefix it cannot recover or one from another area offers nothing, exactly as it writes nothing), and `overwriteColnectCatalogNumber` (`POST …/colnect/overwrite-number`) replaces that one vendor's row, refusing a catalog the stamp holds no number in — that is the backfill's job, and two paths claiming one field is how they drift. It is deliberately **not** part of confirming a match: linking an item and rewriting a number already held are two different claims, and only the second destroys something, hence its own confirm naming both values and its own route rather than a flag on `confirm`. The duplicate policy (#85) is the fill's, run over a proposal shaped like one so an overwrite and a fill can never disagree about what collides; the write **rings no doorbell** (#423's `data-stamporama-assistant-matched`), which announces a *match*, not a number. Offered only on rows that name a single stamp — a linked one or a one-candidate `needs-confirm` — since correcting a number on an unchosen sibling is a change nobody would think to look for. What the matcher compares is strict and pure, but what it *recalls* out of the database is a `contains` net, and that net is built from **each digit run** of the printed number and never from all its digits at once (`catalogDigitRuns`, ANDed on one `some`, in both readers — the matcher's and the picker's): `PL BL30 B4` concatenates to `304`, which no stored `BL30 B4` contains, so the item read as `no-candidates` with the stamp sitting right there (#435). A run survives every spacing and punctuation difference between the two sides, which is exactly what the key already folds away; a digit-free number (Michel's Roman local issues) still recalls on its bare value, case-insensitively. The reveal control lives in the toolbar row, not the section heading: with every such row hidden the section is gone and would take the only way back with it. Tokens are obtained by **self-registration** (#252): Settings → Assistant exposes a one-time code + the instance's own origin on the page, and a toolbar-icon click exchanges it at `POST /api/assistant/register` (`src/lib/assistant-registration.ts`). A `PlatformModule` has **two halves** (#408): extraction (`matches`/`extract`, required) and **listing** (`listing: { formUrl, isFormUrl, fill, listedUrl, attachPhotos? }`, optional) — reading a marketplace page and posting to one are the symmetric halves of one job, so listing lives in the neutral interface rather than inside the Colnect module, which is what lets Delcampe (#154) and Allegro (#355) reuse it. A read-only module is a *complete* module and its platform simply offers no **List via Assistant** (#407); `moduleReports()` says which modules carry which half, so no surface hard-codes ids. The task is the **listing kit** (#405) unchanged, mirrored by hand in `extension/src/platform/listing.ts` as `core/decisions.ts` mirrors the matcher response — it states what the listing *holds*, never how a form is laid out, so Colnect's URL shape and field names appear nowhere outside `src/platform/colnect/` (#410). Driving one is `listing-run.ts`, **two pure steps** because a navigation separates them (`resolveListingTarget` → `fillListing`), leaving the tab-opening and the report back to the instance to the wiring (#407/#409). Filling **stops before submit** — the collector clicks the platform's own button — the page is checked with `isFormUrl` **and** with `isFormDocument` first — two questions because a marketplace answers the form's own address with something that is not the form yet (#419: Colnect's anti-bot interstitial, which reloads itself into it), and filling that page wrote nothing while reporting every field as missing, so the text half of a listing vanished and only the pictures — attached later, on the reloaded form — landed. The document check is therefore a **`retry`, not a refusal**: `fillListing` says "not yet", and the wiring (`fillThroughReloads`) waits for the tab's next `complete` and starts the whole attempt over, injection included, since a fresh document holds no content script. The watcher is armed **before** the fill, or a reload landing while the message is in flight is the one event it misses; it is bounded by both a short wait and an attempt count, because a page that never becomes the form (a sign-in, a challenge) has to end in the error it already has rather than in a spinner. A URL that is not the form's at all stays an outright refusal — that is the collector having navigated away, not a page on its way. The outcome is a **report, not a verdict**: `filled` *and* `skipped` both come back, each named for the collector rather than for the DOM, because a field the task cannot answer (an unmapped condition above all) is no reason to abandon the rest of the form. The three ways a task finds no module — the platform names none, the id is unknown here, the module only reads — are three different answers. That **wiring** (#409) is the registration contract a second time, on a second element (`#stamporama-assistant-listing`, `extension/src/core/listing-handoff.ts`): the workspace writes `{ v, requestId, task }` into it as text and the extension answers with `data-listing-state` / `-message` / `-request` / `-report` on the same node — the page owns the node and re-renders it, so text in and attributes out is the only direction that survives. The gesture is what differs from #252: a listing starts from a click on an offer *card*, so there is no toolbar click to grant `activeTab`, and the extension instead **registers a content script for the profile's origin** (`background/instance-scripts.ts`, `chrome.scripting.registerContentScripts`, port included so `:3002` is not `:3000`) — reconciled against the stored profiles off `chrome.storage.local` changing, so registering, correcting a URL and deleting a profile are one code path, and injected into that origin's already-open tabs, a freshly registered script only reaching documents loaded after it. `host_permissions` is already `http://*/*` + `https://*/*`, so none of it prompts. `requestId` is minted by the page and echoed back — an answer names the handoff it answers, and a request already answered is ignored, so a re-render is not read as the collector asking again — and `<html>` carries `data-stamporama-assistant` (the version) on every instance page, without which **List via Assistant** is a button that silently does nothing on a browser with no extension. The worker (`background/listing.ts`) then does the part `listing-run.ts` deliberately has no `chrome.*` for: open the form **beside** the workspace tab, wait (capped, a closed tab reported as such — a promise that never settles leaves the card spinning), have the *content* script fill it because the DOM is there, report back. It needs **no profile and makes no instance call**: a task is self-contained and the origin that wrote it is one the collector registered. Storing the URL and moving Ready → Active stays the page's own job (#407) — the extension reports, the instance decides. **Closing that loop** is #412: the entry's URL exists only after the collector presses Save, so `PlatformListing` gains one more neutral member — `listedUrl(url)`, the same knowledge `isFormUrl` carries on the other side of Save, returning the URL rather than a boolean because it is *stored* and the module is what decides which part of the address bar is the record (Colnect lands straight on `/…/market/sale/<code>`, confirmed by posting one, and drops query + fragment). The wait between filling and Save is written to `chrome.storage.local` per listing tab (`background/pending-listings.ts`, pruned at 12h), never held in the worker: a collector takes minutes over a form and an MV3 service worker is unloaded in seconds, so a navigation wakes it with nothing but a tab id and the record is what turns that into meaning. The content script also arms a one-shot `submit` watcher, which buys the one distinction the capture cannot make on its own — a **posted** listing whose entry page was never recognised is reported when the tab closes, while an **abandoned** form is silence, because an untouched Ready offer is not news (a form re-served with validation errors is why the report waits for the tab to close rather than firing on the first unrecognised page). The write-back has **two deliverers, in order**: the answer goes onto the handoff node and the *page* publishes it through the same `publishOfferAction` its own Publish calls — #407's rule, with the collector watching — and the instance content script replies whether it is `taken`, which it decides by re-reading the node's **text** for that `requestId` (the page's own half of the contract, so "is anyone still following this" is answerable without inventing a channel). Not taken — dismissed, replaced by the next offer's handoff, tab closed — and the worker POSTs to `…/offers/[offerId]/listed` with the profile matching the page's **origin + the task's collection**, the only pair that names one connection. `recordOfferListed` is therefore **idempotent**: `ready` publishes, an already-`active` offer has a *blank* URL filled in and a recorded one left alone, anything else is refused, so the two paths racing is a no-op and never a conflict — and a marketplace submission can never quietly take a paused or sold offer live. Colnect's own half (#410, `colnect/listing.ts`, against the form mapped in #402) declares the **komplet in the URL** (`…/sell/new/category/stamps/item/<id>%2C<id>…` over the copies' item-IDs in listing order, **deduplicated** — the form keys one fieldset per item, so a second copy of one stamp cannot be declared twice and is named in the report instead of dropped). It fills each copy's condition (`new_sale[cond_20_<id>]`, through #404's mapping), the price, the number of sets and the two texts, and leaves `expiry_date` / `auto_renewal_*` exactly as served — required, pre-filled, matching nothing here, so writing our own would clobber the collector's defaults; `options[] = separate_listings` is never touched either, but a *ticked* one is reported, since it moves pricing to the per-item fields and turns pictures off. An **over-long text is neither written nor truncated**: truncating mangles chosen wording, and a scripted assignment past `maxlength` is not refused the way a paste is, so the form would carry a value Colnect then rejects — the report gives both numbers and points at #403's counter. Colnect's **currency is a seller-level setting** and not a form field, which is what a platform locking its currency (#196) is for. A `<select>` is set by **selecting the option**, never by assigning `value`: a grade the form does not offer is then a refusal rather than a silent no-op. **Pictures** (#411) are one more optional neutral member — `attachPhotos(doc, photos)` — and are the run's **last** step, never part of `fill`: Colnect's Dropzone posts each picture over AJAX the moment it is handed over, minting a draft `sale_id` *before* the sale is saved (#402), so this is the first thing in a whole listing that writes to the marketplace at all and it happens with a filled form already in front of the collector. Whether that leaves orphans behind on an abandoned form is still #402's open question; putting photos last is what makes the answer not matter much either way. The images are what the kit already carries (#405) — the upload set, in upload order, under the ZIP's own names (#314/#326) — so nothing on the app side changed. Three pure decisions sit in `listing-run.ts` before a byte moves: a module with no uploader is **silence, not a gap**; a plan that is not `ready` is a skip naming what Stamporama is doing about it; and a set past `LISTING_PHOTO_BUDGET_BYTES` fills **from the front**, the plan's order being the priority order (#313), exactly as the platform's own photo limit fills it. An **out-of-date** render is none of those and is deliberately not reported here — the offer's Photos card already carries that signal, and repeating it in a fill report would turn a signal into a warning. The bytes are fetched in the **worker** (`background/photo-client.ts`, the photo route's own Assistant token, the profile named by page origin + task collection exactly as #412's write-back names it) and cross to the content script **base64** over `attach-photos`, because extension messaging is JSON and a `File` does not survive it — which is also where the budget comes from, and why the ceiling is stated rather than hidden. The `File`s are built in the page, the realm the form is in. Colnect's own half finds the Dropzone's real `<input type="file">` **structurally**, by what it accepts: it is the one control in the form #402 mapped that Colnect does not address by a `new_sale[...]` name, so there is no name to match on. Every failure is a **skip, never a refusal** — an unaccepted file type, a `disabled` uploader (which is what ticking *separate listings* does), a non-`multiple` input, a fetch that failed — because the fallback the scope asks for is dragging the offer's ZIP in, not redoing the listing. The report says the pictures were **handed over**, not that they arrived: the upload is Colnect's own AJAX and the thumbnails appearing in the Dropzone are what confirms it, right where the collector is already looking. The **match handoff** is that same contract a third time (`#stamporama-assistant-match`, `extension/src/core/match-handoff.ts` ↔ `src/app/c/[collectionSlug]/offers/assistant-match-handoff.ts`), for the step *before* a listing: posting needs every stamp matched, so an offer's On Colnect card hands over the catalogue search it already builds (#423) and the worker does the two things a page cannot — open the tab and put the match window in front of it (`open-match`, answered `running` → `opened`, since what happens in that window is the collector's own work). A **third** node rather than a task type on the listing one, because an offer being prepared is matched *and* listed and the two answers must not overwrite each other; the URL is re-parsed on the extension side and refused unless http(s), it being handed straight to `chrome.tabs.create`. The write comes back not down that path but as a **doorbell**: every confirmed match sets a changing `data-stamporama-assistant-matched` on `<html>` of every instance tab, carrying no request id on purpose — any match may be the one a screen is waiting for, re-reading an offer is cheap, and matching started from the toolbar icon has no handoff to answer at all. **Link all** is therefore page-driven, a queue taken when the walk starts and advanced on each ring: the extension cannot know what is still missing, and a walk re-derived from fresh data would reopen the row the collector deliberately skipped.
- Assistant **lot capture** (#355; ADR-0015 §third-half, ADR-0021 §8) is the extension's third module half — `capture` (`isListingUrl` / `capture`, `extension/src/platform/capture.ts`), beside `extraction` (now optional too) and `listing`. Allegro carries **capture alone**, and that is a complete module: a marketplace this collection only ever bids on is neither a catalogue to match against nor a shop to list into, so `PlatformModule` has no required half left and `moduleReports()` names all three. The toolbar click therefore has a **third meaning**, decided in the worker off the URL alone (`findCaptureModuleForUrl`) because the click is what grants `activeTab` and no content script has run yet: registration, capture, match. Capture opens `capture.html` — a window of its own, sharing only the profile badge and the window slot with the match window, since one lot's five fields and a page of candidate stamps are different questions. Reading is the **page's own JSON**, never its markup: Allegro renders through `opbox` boxes that ship their data beside them as `<script type="application/json">` while every class name is hashed per build, so a selector would break silently and a capture that breaks silently records a lot with no bid. Three blobs found **by shape** (the box ids are opaque and per-page): `biddingSection` → closing instant + current figure + currency + `popularityLabel`, `sellerName` → the seller, JSON-LD `Product` → the title (`document.title` carries Allegro's own suffixes). The auction test is `biddingSection.visible` — a *Kup teraz* offer carries the identical section with `visible: false` and a null `endingDate` — and a fixed-price page is a **refusal naming what the page is**, not an error: there is no bid to observe and no close to age against, and a lot invented from one would sit in the watchlist forever. The one judgement the module makes is **bid or opening price**, from the bidder count (`/licytuj/`, so the fixed-price *"9 osób kupiło"* in the same field reads as none): with nobody bidding, Allegro still prints "Aktualna cena", and recording that as a bid would cost the parcel money nobody has offered (#351). Allegro's *Numer oferty* is the same digits as the offer id and is carried **twice on purpose**: `platformOfferId` is the listing's identity, matched on and never shown, while `lotNo` is a number *on a lot* — the slot a house sale's lot number occupies, displayed and editable — so the watchlist reads the same however a lot got there. The URL stored is the canonical `/oferta/<offerId>`, never the slug or the `/produkt/…?offerId=` shape — the id is the part of every address that is the listing, and it is what makes a **re-capture a refresh**. `findCapturedLot` looks for it in **both places it is recorded**, because a lot added by hand carries whichever the collector happened to type: `lotNo` **equal** to the offer id, scoped to sales on that platform (an offer number is unique on the marketplace, so equality is the whole test — and the scope is what stops a house sale's `Lot 42` being read as offer 42, one field over two vocabularies), or the `url` at the **address's own boundaries** (`/<id>`, `-<id>`, `offerId=<id>`) and never as a bare substring, `8795065609` otherwise matching the middle of `18795065609` and refreshing a different auction's bid. A match then writes and then writes `currentBid` + `checkedAt` through `setAuctionLotBid` and **nothing else**, because the title, the closing time and the composition are what the collector has since typed. Everything about *where* it lands is server-side: the platform from `Contact.platformModule = "allegro"` (Settings → Allegro, one select, the exclusive setter now shared with Colnect's identical question in `module-platform.ts`), the seller resolved by name through `resolvePurchaseContact` as a typed-in name is, the parcel through #352's open-sale matching. `dryRun` is the same function answering what *would* happen, so the window's preview can never describe something the save would not do — and it resolves nothing into existence, hence the seller **lookup** rather than a resolve on that path. There is deliberately **no declarative content script for allegro.pl**: the feature starts with a click, which is also what grants access, so the script is injected then rather than run on every page of a shop the collector browses. An unset platform is a refusal pointing at the tab that fixes it (`no-platform-module`), never a guess.

- The instance's own **Allegro API access** (#476; ADR-0023) is the other half of Settings → Allegro and has nothing to do with the capture module above it: the select names a marketplace the collection *buys* on, this connects the account it *sells* from, and #467 (sold-listing worklist) and #463 (order → `Sale`) are what read through it. It ends at *connected* and reads no business data. Naming the account is a **courtesy, not a gate**: `storeGrant` writes the grant first and *then* tries `GET /me`, because that endpoint needs the profile scope an application registered only for offers and orders does not carry — making it the precondition turned a token Allegro had just issued into "Not connected yet.", which is the worst possible answer to a collector who has just confirmed a code on their phone. A null `accountLogin` therefore renders as a connection without a name, and `testAllegroConnection` reads **403 as success** (Allegro accepted the token and declined *this endpoint*) against 401's failure — telling those two apart is the entire value of that button. Self-hosting is what puts credentials in the database at all: no OAuth application can ship in a public image, so each instance registers its own at `apps.developer.allegro.pl`, and `AllegroConnection` is **one row per collection** (the app has one authorization model — `collectionId` + owner check — and an instance-level secret would sit outside it). The **device code flow leads** and the authorization code flow is offered beside it, never instead: an install with no inbound DNS is the common case, and only the device flow works there. Which flow made a grant is deliberately **not stored**: the refresh is identical either way — same endpoint, same two parameters, no `redirect_uri`, which belongs to the initial code exchange alone. Where the two *do* differ is unguessable and cost a debugging session: `POST /auth/oauth/device` takes `client_id` in the **query string** while every other exchange uses the form body, and sending it in the body is answered *"OAuth 2.0 Parameter: client_id"* — not a wrong id but no id, Allegro never reading the body. Hence `deviceCodeUrl()`, exported so the shape is unit-tested rather than trusted; **neither** request asks for scopes, which come from the application's own registration and can be granted nowhere else — requesting one the application lacks fails the whole authorization, and Allegro reports *that* as `client_id` as well, so two unrelated faults arrive under one misleading message. Accepting whatever the application carries costs least-privilege and buys a setup that cannot fail opaquely; the collector registers the application for Stamporama, so narrowing it is theirs to do where it is visible. The client secret and both tokens are **sealed** (`src/lib/secret-box.ts`, AES-256-GCM under `STAMPORAMA_SECRET_KEY`): `api-tokens.ts`'s hashes do not transfer, a refresh token being replayed rather than verified, and a database dump is a routinely-copied artefact in a self-hosted install. GCM specifically, so a flipped byte fails *here* rather than downstream as an Allegro rejection that reads like an expired grant; the client *id* stays plain so Settings can name the application even with the key missing. `allegro-connection.ts` is the only module that decrypts anything and `getAllegroAccessToken` is the whole downstream contract — a token good for the next two minutes, or `AllegroNotConnectedError`, never a decision about refreshing. Every unusable state converges on **one** latched `needsReconnect` + `lastError`: a rejected refresh, a 401, and secrets that no longer decrypt are one situation to the collector, and the next step is the same for all three. Disconnect drops **locally only** — a local drop always succeeds, including from the dead-token state one is most likely disconnecting *from*, while a revoke's only honest failure handling is to disconnect anyway; the guide says the grant stays listed on Allegro. `allegro-api.ts` is the thin client (base URL, `application/vnd.allegro.public.v1+json`, bearer, 429/5xx with Allegro's own `Retry-After` honoured and capped) and imports **nothing** from the store — the store calls into it, which is what keeps the two from being a cycle and the backoff rules testable without a database. Sandbox is a property of the **connection**, not the deployment, because a sandbox application has its own credentials; changing the client id or that toggle drops the grant, since a token belongs to the application that issued it. The pending device code and the code flow's `state` live in memory on `globalThis`, deliberately: both are single-use and expire in minutes, and persisting them would add a third and fourth secret to a table whose point is holding as few as possible — losing them to a restart costs one click, losing a *token* is what the row is for. The callback route (`/api/allegro/callback`) is not collection-scoped and reads no session: the redirect URI is one fixed registered string, and the `state` is the entire authorization. `STAMPORAMA_SECRET_KEY` carries a **fixed local-dev default** in `docker-compose.yml` and in `.env.example` — `POSTGRES_PASSWORD:-stamporama`'s precedent, since that file only ever runs the local stack — but deliberately **none in `secret-box.ts`**: a production install that forgets the variable has to fail loudly on the Settings tab rather than quietly seal real credentials under a key published in this repository. `.env.prod.example` therefore ships it commented out, and `scripts/install.sh` **generates** one — deliberately with no menu, unlike `BETTER_AUTH_SECRET` beside it: rotating this key silently turns every stored connection into "needs reconnecting", so the installer only ever ensures a key exists (fresh install, or an upgrade predating the variable) and never touches one already there. Rotating is an explicit `.env` edit, which is the friction it deserves.

- The **Allegro sold-listing worklist** (#467; ADR-0024) is what reads through that connection, and it produces **observations, never financial records**: `runAllegroSync` writes to no table the collector owns, and creating the `Sale` stays #463's explicit act. The observation lives in **rows of its own** rather than as a state on `Offer` — an order line is not one-to-one with a listing (stock above one sells a copy and the offer stays `ACTIVE`; one order carries several offers; an unmatched line has to live somewhere or the collector never learns a listing was posted outside Stamporama), so it is `AllegroOrder` + `AllegroOrderLine`, keyed on **Allegro's own ids** (`@@unique([collectionId, orderId])`, `@@unique([allegroOrderId, lineItemId])`), which is the whole of what makes a re-run a refresh rather than a re-import. The **header is its own row** rather than order columns repeated per line — status, buyer and total are facts about the order, one order routinely carries several listings, and the screen reads at that level too, a card being an order. The buyer is read down to **who, never how to reach them**: `buyerLogin` + `buyerName` and `totalPaid`/`currency` from Allegro's own `summary.totalToPay` (delivery included, so it is what changed hands and is `Sale.buyerPaidTotal`'s anchor, #205 — a sum of the lines is a *different* number that would quietly disagree with the sale about one order). The email, phone and delivery address on the same payload are deliberately **unread**: they are the sale's, and #463 fetches the order by id at the moment the collector confirms it rather than a background job keeping personal data warm for a feature that may never touch that order. The sold list filters on **two independent axes** — paid/not-paid over orders, matched/unmatched over lines — OR within an axis and AND across them (#475's chips), client-side over the one unpaginated batch (#322's reasoning); they are applied at the level each fact lives at, so an order left with no line falls out and a mixed order's *matched* lines can never appear under **Unmatched**, and the chip counts are over the whole batch, a count that moved as you filtered saying nothing about what is there to filter to. The **ended-unsold** half is deliberately not a second read: paging `publication.status=ENDED` answers with every listing the account has ever ended, so the sweep reads the **active** ones, `AllegroListing` is its snapshot, and a row the newest sweep did not see is marked `ENDED` rather than deleted — that **absence is the signal**, keeping the row is what lets it be shown with the date the listing was last seen up (hence `observedAt` is *not* restamped on that transition), and the derivation only ever runs off a sweep that finished (`listingsSweptAt`), a half-finished one reporting everything it had not reached yet as ended. The two sit **beside** each other on `offers/allegro` rather than in one list: a sold row is a sale to record and an ended row is an offer whose state here is wrong, and one list carrying both needs a chip per row explaining what it wants. An unmatched *ended* listing is reported nowhere — the action is "correct an offer" and there is no offer to point at — while an unmatched *sold* line very much is, the missing match being the news. A **cancelled** order appears in neither: nothing is waiting, and offering a sale for an order the buyer withdrew is the app making a financial suggestion about a transaction that did not happen. Passes follow `/order/events` from a stored cursor because a dated read cannot see an order whose only change was **a payment landing**, which is exactly the transition the list cares about; with no usable cursor (first sync, or one Allegro no longer accepts) the pass reads `/order/checkout-forms` over 30 days and mints the cursor from `/order/event-stats` **before** that read, so an order landing during the import is caught by the next pass rather than falling between the two — and a rejected cursor is therefore not an error at all but the stream having moved past us, the fallback being safe precisely because every write is an upsert. **Matching** is the external id (the offer number, exact, present only where the listing was published through the API) and then the stored `Offer.url` at the address's own boundaries — `platform-offer-url.ts`, now **shared with #355's capture** in two readings, a Prisma `OR` arm and an in-memory predicate, since the sync holds its candidates already; two offers claiming one listing is a **refusal**, not a coin toss. Every judgement is pure in `allegro-sync-rules.ts` (`paymentStatusFor`, `lineAwaitsSale`, `matchListingToOffer`, `windowFloor`, `syncFreshness`), `allegro-sync.ts` is the I/O half and decides nothing, `allegro-worklist.ts` is the read. The poll is quarter-hourly in the existing in-process pattern (`src/instrumentation-node.ts`, ADR-0018) with a **Sync now** beside it; a pass claims its collection so the two cannot read one stream twice, and the claim **times out**, a lock nothing can release being worse than a second pass over idempotent writes. Failure is visible **where the list is read**: the header names not-connected, needs-reconnect, no-platform-marked-as-Allegro, the last failure with Allegro's own message, and an hour without a pass — a stale worklist that looks current is the failure mode the whole thing is designed against. A **401 latches `needsReconnect`** rather than `lastError` (ADR-0023's single convergence point), and *not connected* reports `skipped`, not a failed sync. - A `Contact.platformModule` id is **not a promise about listing** (#471). Ask `hasListingModule()` (`src/lib/platform-modules.ts`), never `platformModule !== null`: only Colnect's module has a sale form here, while Allegro's (#355) names the marketplace a captured auction lot belongs to. Everything about listing — the preconditions (#406), the listing kit (#405), **⚡ List via Assistant** and the platform-catalogue card (#423) — is Colnect's rule, and the truthiness test quietly promoted Allegro to a listable platform: its offers were drawn a card of Colnect links and refused `ready` over Colnect item-IDs nobody had recorded. A third module added for some other purpose must not inherit those rules by existing.

- Assistant **distribution** (#288; ADR-0017, superseding ADR-0016) — published to an **unlisted Chrome Web Store listing**; the store assigns the ID and signs, so there is no CRX, no signing key and nothing served by the instance. `extension/pack.mjs` (`pnpm assistant:zip` from the root) writes a store ZIP with the app version stamped in; CI's `publish-extension` job uploads and publishes it per release tag (`CWS_CLIENT_ID`/`CWS_CLIENT_SECRET`/`CWS_REFRESH_TOKEN` secrets, `CWS_PUBLISHER_ID`/`CWS_EXTENSION_ID` variables), but only when `extension/` changed since the release the **store** already holds — asked for with `:fetchStatus`, taking the newer of the published and in-review revision, so a submission that failed or was paused is picked up by the next release rather than lost. The store's `uploadState` is `SUCCEEDED` on this API (v1.1's `SUCCESS` is accepted too); the job is also dispatchable on a tag, so a refused submission is retried without moving it. Self-hosted force-install was tried and fails: Chrome honours a non-store `update_url` only on an enterprise-managed machine. The unpacked dev build and the store build stay **two extensions** with two IDs (`extension/identity.mjs`; `manifest.json` carries no `key`), so both can live in one browser and a dev profile can never reach a production collection.
- Binary assets (photos, #112) sit behind the `src/lib/storage/` interface (filesystem + GCS, #138; ADR-0011; active write backend via `STAMPORAMA_STORAGE_BACKEND`, per-photo reads) — async/streaming, `resolveUrl` returns stream-or-redirect, write-one/read-many by per-row `storageBackend`. Bytes live under `STAMPORAMA_DATA_DIR` (the `stamporama-data` volume), never in `public/`; serve them through collection-scoped route handlers. Multipart uploads use route handlers, not server actions. `Photo` is polymorphic over **three** owners — `Item`, `Stamp`, `Offer` (#311, generated listing images, `kind = generated`; #313, images uploaded straight to an offer for a manual attachment, `kind = original`) — with a `num_nonnulls(...) = 1` CHECK; deleting any owner must delete the bytes explicitly (the cascade only drops rows). An offer's photo plan is part rule-derived and part manual: `OfferPhotoAttachment` (#313) is the *plan entry* that carries the distinction, so a regeneration recomputes the collages and leaves the attachments alone (#315). An attachment is **N tiles in C columns** — `copy_photo` and `upload` being N = C = 1, and `manual_collage` (#331) the collector's own selection (`OfferPhotoAttachmentTile`, mixing copy scans and offer uploads) at a width they pick, rows never stored because the contents are explicit. In the plan's vocabulary a plain `collage` is always one the rules derived, hence `manual_collage` for the hand-built one. Sets that have gone — sold here, sold from under the offer, or held by an offer in active bidding — are dropped from the plan's inputs in `readInputs` (whole sets, never single copies), which marks the stored images out of date through the fingerprint alone; terminal offers are exempt. Attachments render through the same one-tile collage path as everything else — there is no unlabelled pass-through (#312). A tile caption is sized from the **label strip alone** and never from its own text (#337): sizing to the text made one image carry a full-height label and the next a visibly smaller one. Text that does not fit the tile's width is truncated with an ellipsis, and a *shorter* strip is what makes more of it fit. The strip itself is `labelPercent` of the **finished image's longest edge** — not of the stamp, which is what the gap still uses: every image of a listing is scaled to the same platform limit, so only a share of the image renders at one size across a collage, a single scan and a wide detail crop. It is therefore circular (the strip grows the canvas it is a share of) and `collage-layout.ts` solves for it, capping all the strips together at half the page so a many-row collage stays solvable. The column is a **float**: against the whole image the usable band is about one to two percent and a whole number cannot land inside it. A template’s `rows` × `columns` has always been **capacity, not a frame**, and #413 adds the second reading of it: `gridMode = auto` treats the pair as *bounds* and `resolveCollageColumns` picks each image’s width from the tiles it actually holds, scoring every allowed width by `empty cells + |columns − rows|` and breaking ties wider — two terms because empty cells alone always answers *one column* and squareness alone puts ten stamps into 3 + 3 + 3 + 1. The product is still the capacity, so grouping (#309) never learns of the mode, and `layOutCollage` is still handed one concrete number. It is seeded onto the offer like every other collage value, where **null means `fixed`** — hence it is not one of the columns the all-or-nothing collage group tests, and the fingerprint hashes it **only when it is `auto`**, or every plan already generated would report itself out of date over images unchanged by a pixel. The **upload order** over the whole plan (collages and attachments) is the collector's to set: `Offer.photoPlanOrder` is a `String[]` of stable per-image tokens (`c:<side>:<sortedItemIds>` / `a:<attachmentId>`, also written on each stored `OfferPhotoEntry.token`), an *override* the pure engine reconciles against the derived order at read time — so a manual order survives a composition change or regeneration. A reorder is **applied to the stored images** (their entries are renumbered; bytes untouched), so either list can be the drag surface and reordering never marks anything out of date. **Nothing is ever dropped from the plan**: an image the collector marked do-not-publish (`Offer.photoPlanUnpublished`) or one past the platform's `maxPhotos` is still rendered and shown, just kept out of the numbered upload run and the ZIP — and the limit fills from the front of the order, protecting nothing, because the order is the priority order.
- The **bulk listing workspace** (#322) is a *sub-route* of Offers (`offers/listing/`), not a nav page: posting a prepared batch is a step in the offer lifecycle, and the static segment takes precedence over `[offerId]`. It is scoped to one **platform** and to `ready` offers, reads its batch through one unpaginated route handler (`offers/listing`), and does grouping, filtering and year facets **client-side** from pure helpers in `src/lib/listing-groups.ts` (unit-tested) — a `ready` batch is bounded by what a person is about to type in by hand, and instant facets beat a page boundary. The per-offer posting kit (texts, photos) is loaded **on expand** through the existing `useOfferDetail` / `useOfferPhotoPlan` endpoints, so a forty-offer batch does not fetch forty descriptions to draw forty collapsed lines. Grouping and filtering are deliberately **different questions**: an offer is *grouped* under the `(area, year)` pair every copy shares (else **Mixed**, which the area rail carries as its own entry via `AreaFilterSidebar`'s `extraEntry`), but it *matches* an area filter when every copy is inside that subtree — so a year-spanning offer is Mixed yet still appears under its area. A copy's area is its stamp's **primary** area link and its year is `stamp.issuedYear`, matching the inventory list (#142). Publishing goes through `publishOffer`, which transitions first and writes the URL after, so a refused publication leaves no listing URL behind. The **offer's own screen** publishes the same way (#399): `ready → active` from the quick-advance button or the ⋮ *Activate* entry opens `ActivateOfferDialog` — moved up to `offers/` since it now serves both — and goes through `publishOfferAction`, but **only while the offer has no URL**; one that already carries a link has nothing to hand over and the header's field takes a correction. A transition asked for in two places had to ask the same question in both, or the URL was silently skipped on the surface a single listing is actually posted from. Which card is open is **derived, not stored** — a tri-state (`undefined` = nothing chosen for this batch yet → open the first; `null` = the collector shut it → honour that; an id → that card), so the first offer opens on arrival and after any batch change without a `setState`-in-effect. Publishing resolves its successor *before* the mutation, while the published offer is still in the list, and falls back to `undefined` when it was the last. Its **batch photo actions** (#323) act on the *visible* offers, never on the whole platform's ready set — the filters are how a session is scoped. Regeneration is `enqueueOfferPhotoGeneration` per offer, so #315's sold-set exclusion and the idempotent queue are inherited rather than re-decided; a per-offer refusal is **collected, not thrown** (`generateOffersPhotosAction` returns `{ queued, skipped[] }`), because one unrenderable offer is no reason to abandon the other twenty-nine, and the listing query polls while any offer is `queued`/`running` because the per-offer plan poll only covers the card that happens to be open. The batch **archive** (`buildOffersPhotoArchive`) is a folder per offer over the same per-offer upload set the single ZIP uses, so a file unpacked from either is identical and identically named (#326); namesake offers get their id appended rather than merging two listings' uploads into one folder. It is a **POST** (`offers/photos/zip`, another static segment ahead of `[offerId]`) with the batch in the body and a client-driven blob download, because forty ids in a query string is a URL-length gamble; it is buffered like the single-offer one and therefore capped, past which the honest answer is to narrow the session.
- A platform's **default starting price** (#362, narrowed to auctions by #449) is the *lowest-priority* price suggestion: a new auction takes `Contact.defaultStartingPrice` only when the lot's suggested price (#190) and the copies' catalog value (#230) — both of which reach the form as a filled-in figure — had nothing to say. It carries **no currency of its own**: the platform already locks one (#196), and a second one could only disagree with it. The fallback lives in `createOffer` (`resolveOfferPricing`), resolved *before* the live-status checks so an auction created straight as `ready` on a house that always opens at the same figure is not rejected as unpriced — the server is the single point that applies it, because a plain create does not even show the price fields. The dialog pre-fills it too, into the **starting-price** field and only while untouched, so what the collector sees is what the server would have written; it never reaches the current price, which no default and no suggestion may fill. Read at creation and never again: unlike the listing templates and photo defaults it is not *seeded* onto anything, since the offer's own columns are the record. It was originally a flat *asking* price for a quick-buy platform, and #449 narrowed it deliberately — the column is kept only while `defaultListingType` is `auction` (the contact writers clear it otherwise, and the form hides the field), because a quick buy's price follows from the goods and the two suggestions above are exactly the ones that describe the goods; a flat default there could only overrule them with a figure nobody had looked at the stamps to arrive at. The migration therefore renamed the column and **cleared** every value, every platform predating `defaultListingType` reading as a quick buy — a figure left on one would be a stored fact nothing reads.
- An offer is sold as a **quick buy or by auction** (#449) — `Offer.listingType` = `fixed` | `auction`, a fact about *this listing* and never about the platform, since a marketplace running both formats carries offers of either kind. The interesting decision is that `price` was **not** split: it keeps its column and gains a second reading — the asking price of a quick buy, the **current** figure of an auction (the standing bid, or the opening price while nobody has bid) — because every reader wants the live number and only the live number: the list rows and their base-currency equivalent (#208), the suggested-price comparison (#190), the ready/active price gate (#336), the listing kit (#405), the sale. A separate `currentPrice` beside a `price` holding the opening figure would have branched all of them on the listing type to arrive back at the same value, and two columns claiming one fact is how they drift. What the auction adds is `startingPrice` — where it opened — and `priceCheckedAt`, the auction lot's `checkedAt` (#351) on an offer, since refreshing a bid is manual by decision (ADR-0021 §8) and an undated figure says nothing about how current it is. All of it is resolved in **one** place, `resolveOfferPricing` in `offers.ts`, shared by `createOffer` / `duplicateOffer` / `updateOffer`, so a quick buy clears the auction pair wherever it is written — including a listing switched back to one, where a stale check date would describe a format it is no longer in. The price is dated only when the figure actually **moved**: a header save that retypes the same number is not an observation of the bidding, and neither is any other field on that form. `patchOffer` refuses a `startingPrice` on a quick buy rather than ignoring it — changing format is the header form's job, not a field quietly appearing beside the price. **Which of the two figures is required** is the format's own question and the counterpart of #336: going `ready`/`active` needs an asking price, but on an auction it needs the **starting** price (`requiresStartingPrice`), because that is the number the seller states while the current one is an observation — and an auction that is up with nobody bidding has none to make. The two are therefore **alternatives, not a pair**, and nothing is ever invented for `price`: an unbid auction carries `0` and reads as **No bids yet** rather than *No price yet*, because copying the opening figure into it would put a bid in the record that never happened. They move independently — correcting the opening price never touches a recorded bid, and `patchOffer` refuses to clear a live auction's *starting* price while freely clearing its current one, that one being an observation and "no bids after all" a legitimate correction. `missingPriceField` is the single server-side rule behind every refusal, returning *which* field is missing so each call site can name it; `pricingReadyFor` is that same rule for both quick-advance buttons, so a button offered is a transition the server will take. The same reasoning decides where a **suggested** figure lands in the dialog (a lot's price, the copies' catalog value, the source offer's when duplicating): a suggestion is what one would *ask* for the goods, which on an auction is what one would *open* at, so it fills the starting price and leaves the current one blank. A platform's **default listing type** (`Contact.defaultListingType`, nullable, null = *no preference* and deliberately not a stored `fixed`) is `defaultStartingPrice`'s rule again (#362) — read at creation and then owned by the offer — reaching the domain through `assertPlatform` and the dialog through `listOfferPlatforms`, and it is also what decides whether the default starting price beside it means anything at all (the two are written together in `platformListingDefaults`, since a price is meaningless without the format); an **edit** passes no defaults, since switching platforms must not re-describe a listing that already exists, and the dialog stops re-seeding the moment the collector answers the question themselves. The picker's platform facts travel as one `PlatformOfferDefaults` object rather than a fourth positional callback argument. The vocabulary, the parser (`parseStartingPrice`, which unlike `parsePrice` reads blank as *not recorded* rather than as an error — the transition gate is what asks for the figure, not the parser) and the price's own **label** (`priceLabel`) are pure in `offer-rules.ts`: what the field is called differs per listing type on three surfaces, and a ternary per surface is how two of them end up saying different things. The chip is deliberately shown for an **auction only** — a quick buy is what an offer ordinarily is, and a chip on every row of a long list is noise — and it sits beside, never instead of, *In bidding* (#215): one says the listing is an auction, the other that somebody has actually bid and the collector is committed.
- An offer's **stamps on the platform's own catalogue** (#423) are a card of their own on the offer detail, between the images and the sets — the two pages a seller opens while pricing a listing: what the stamp *is* (its catalog page, #290) and what it is currently being **asked for** (the marketplace search at that grade). Keyed on `stamp × condition` and not on the copy, because that is what the marketplace pages are keyed on and a komplet is dozens of copies over a handful of stamps; a row states how many of the offer's copies it stands for rather than repeating itself. The market URL's condition segment is a **third Colnect vocabulary** — `ColnectGrade.marketSlug` (`mint_never_hinged`) beside the sale form's numeric `value` — stated in the table rather than derived from the label, since nothing guarantees the two agree; it is the one thing here that could not be verified against the live site (#419's interstitial refuses anything scripted) and is derived from the single confirmed example in #423, which is why it is one table and a one-line correction. `colnectMarketUrl` returns **null rather than a condition-less search**: a price for "any grade" is not the figure being judged, and a link that quietly answers a different question is worse than no link. Gated on `platformModule` exactly as the blockers are — one marketplace's catalogue, not a general fact about an offer — but deliberately **not** on the listing preconditions (#405): the collector is asking what the market wants, which is a fair question of an offer at any stage. A row an unmatched stamp (#247) or an unmapped condition (#404) leaves link-less is therefore **still listed**, disabled with its reason (#273), because the list that would have taken them to the market is where that gap gets noticed. It reads nothing of its own — the item-IDs come off the set select the screen already loads and the grades off the condition map already read once per offer.
- The **Colnect condition mapping** (#404) is the condition-side counterpart of #248's catalog-abbreviation mapping, and lives in the same place: one row per `StampCondition`, per collection, in **Settings → Colnect**. Per collection and not per platform `Contact`, because Colnect's vocabulary is **fixed and global** (#402 — the identical five options render under every item of a multi-item sale form), so only Colnect's option value is stored and the label it renders as lives in code (`src/lib/colnect-conditions.ts`, pure). The two rules it does **not** inherit from #248 are the interesting ones: there is no exact-abbreviation fallback and nothing is silently ignored — an unmapped condition is a listing **precondition failure** (#406), because a wrong grade on a published listing is worse than a blank the collector fills in. `guessColnectGrade` exists but matches the **abbreviation alone** and only ever proposes. Every condition is listed whether or not it is mapped, so a blank select *is* the unmapped state and a legitimate answer (no cover grade exists on Colnect); clearing a mapping **deletes the row**, so "unmapped" has one representation everywhere. The panel has no draft and no Save — the select is the control, one write per change — and `setColnectConditionMapping` validates against the built-in list, so a stored value can always be rendered and posted. `loadColnectConditionMap(collectionId)` is the read primitive #405/#406 build on, loaded **once per offer**: a komplet is dozens of copies over a handful of conditions.
- The **listing kit** (#405) is one read-only call — `GET …/offers/[offerId]/listing-kit`, session **or** Assistant token like the matcher (#250) — answering "everything this offer wants filled into a marketplace form": the copies' catalog item-IDs (#247), each copy's condition **already translated** into the platform's vocabulary (#404), the quantity, the price in the platform's currency, the two generated texts, and the photo plan's **upload set** in upload order as fetchable photo-route paths (the same route already takes the token, #253). **Platform-neutral in shape**: it says what the listing *holds*, never how a form is laid out — that mapping is the extension's platform module (#408/#410). One Colnect-shaped assumption is confined to `src/lib/listing-kit.ts`: the grade vocabulary comes from the collection's Colnect map, which is per collection precisely because Colnect's list is fixed and global (#402); a second marketplace with its own vocabulary turns `platformCondition` into a per-platform lookup and moves nothing else. `quantity` is the **number of sets** and `items` describes **one** of them — which is only truthful over interchangeable sets, hence the preconditions. Those are pure and separate (`src/lib/listing-preconditions.ts`, unit-tested), because the endpoint refuses on them and #406's card has to state the same reasons: not Ready, no copies, a stamp with no item-ID, an unmapped condition, or sets that differ. Homogeneity compares **what the form would receive** — item-ID + grade, order-insensitively — with the local ids standing in where either is missing, so two unmatched sets are never called interchangeable on the strength of two nulls. `not-ready` / `no-sets` return **alone**: with no composition there is nothing else to say, and listing four faults under an unfinished offer buries the one thing to do. A failing precondition is a **refusal** (409 with the blockers), never a payload with holes in it, because a wrong grade or an untruthful quantity misdescribes the goods — while an over-long text is not a blocker at all (#403): the platform's own field visibly refuses a long paste, and nothing about the stamps is misstated. The kit is still *returned* by the domain function with its blockers and its nulls, so the workspace card and the endpoint read one evaluation. Photos are taken from `getOfferPhotoPlanState`, filtered to `publish && !overLimit`, so the kit, the Photos card and the plan's ZIP can never disagree about which images are uploaded or what they are called; `outOfDate` travels as a signal and never as a refusal, stored images still being truthful pictures of these stamps. **Which platforms they apply to** (#406) is `Contact.platformModule` — the extension's `PlatformModule` id (`COLNECT_PLATFORM_MODULE`, `src/lib/platform-modules.ts`), nullable, and set **in Settings → Colnect by picking the platform** (`setColnectPlatform`), never on the contact form: it is one fact per collection — which platform *is* Colnect — and the collector deciding it is already on that tab setting up the catalog and condition mappings it belongs with, which is also why the picker leads the tab. The setter is **exclusive** (it clears the previous holder in the same transaction, so "which platform is Colnect" always has one answer) and refuses a contact that is not a platform of the collection. There is deliberately no registry of modules to pick from: Colnect is the only one and the value is written by that one setter, so an enumeration would be a vocabulary nothing reads. It exists because the preconditions are **one module's rules**, not a general truth about listings: without it a Delcampe batch would carry a chip per card about a form nobody is going to fill from here. The two ends treat a module-less platform differently, deliberately: the evaluator returns `no-platform-module` **alone** and the kit endpoint refuses on it (a caller that asked for a posting payload asked for something impossible), while `listReadyOffersForListing` **skips the evaluation entirely** and reports nothing — the card answers "what do I fix", and "this platform is listed by hand" is not a fault. It also skips the condition-map read, so a non-Assistant batch pays for none of it. **Where they are surfaced** (#406) is the bulk listing workspace's own row — `ListingWorkspaceOffer.blockers`, evaluated in `listReadyOffersForListing` over one extra select (the stamp's item-ID, the copy's condition) and one condition-map load for the whole batch — and *not* the expanded kit: which of a session's forty offers the Assistant can post is a question asked while scanning, and an answer that needs forty expansions is no answer. The row carries a **Can't list** chip and the expanded card spells the reasons out, one per line and never a count, because each is fixed in a different place; they render from the row, so they are stated even while the kit is still loading or failed to load. They gate the **Assistant handoff** (#407) and nothing else — **Publish stays open**, since posting the form by hand is exactly what a collector does about a gap the Assistant cannot fill. No per-reason link: an unmatched stamp is matched on the platform's own catalog pages through the extension, which the app cannot navigate to. The **handoff** itself (#407, `listing/assistant-handoff.ts`) is the page half of #409's contract, mirrored by hand like the registration payload: **⚡ List via Assistant** beside Publish fetches the kit, writes `{ v, requestId, task }` into one hidden node the panel owns, and follows `data-listing-state` off it. Session-wide and **one at a time**, both for the same reason — the extension puts a marketplace tab in front, so a second handoff would be two forms fighting over one window; presence is `useAssistantPresence` over `<html>`'s `data-stamporama-assistant` through `useSyncExternalStore` with a null server snapshot (the script runs at `document_idle`, and reading the attribute in render would disagree with the server's output). Which platform offers the button at all is `platformModule`, now carried by `listOfferPlatforms` — absent means no module, and the button is *not rendered*; a blocked one is **disabled with its reason** (#273), the reasons being a failing precondition, no extension, or another offer mid-flight. The outcome is rendered as a strip under the card's own line, whether or not the kit is expanded: skips one per line (each is fixed somewhere different), the filled fields in one muted line (what went in is checked in the form, which is now in front of the collector). It **publishes nothing** — filling stops before submit, so the offer is still Ready and the listing does not exist yet; the card's own Publish, one line above and in view at the same time, is the next step, so the strip carries **no Publish of its own** — a second one there is the same button twice. Closing that loop without a paste is #412's, which adds `listed` / `unread` / `activated` to the same strip: `listed` is the URL arriving, `activated` the publication it performs, `unread` a listing posted whose URL could not be read — warning-toned, since nothing failed and the offer is simply activated here. The fill's own filled/skipped detail is **kept** across those states rather than replaced, the post-Save answer carrying only the URL. The workspace treats an offer activated this way exactly as one it published (out of the batch, next card open); the offer's own screen re-reads itself and keeps the strip. The **offer's own header offers the same handoff** (#414), beside Activate and only while `ready`, for #399's reason exactly: a single listing is routinely posted from there, and a step offered on one surface only is the one that gets silently skipped on the other. Button, hint rules and report strip are therefore *one* implementation in `offers/assistant-listing.tsx` (the caller supplies only the button's style, since it sits among a card's small controls on one screen and among the header's chips on the other) — when the Assistant may be asked is a fact about the offer, not about the screen. `OfferDetail` consequently carries `platformModule` + `listingBlockers`, evaluated by the same `listingBlockersFor` over a set select that is a **superset** of `LISTING_SETS_SELECT`, at the offer's **own** state (so anything not Ready reports `not-ready` alone and the header simply shows no button); the condition map is still read only where a module asks for it. The same preconditions **gate `preparing → ready`** (#418, `readReadyBlockers` in `setOfferState`): a fault is worth catching while the offer is still being assembled, not once thirty of them are open in a posting session. It is the one transition gated, deliberately — an offer already live is a listing that exists, and refusing to pause, withdraw or sell it over a mapping gap would trap the collector — and it is evaluated at the **target** state, which is the whole reason it cannot reuse `OfferDetail.listingBlockers` (`not-ready` alone on a `preparing` offer). Hence `OfferDetail.readyBlockers`, the same pure evaluation at `"ready"` over the same sets and condition map, non-empty only while `preparing`; the header's quick-advance button is then **disabled with the reasons** (#273) instead of vanishing the way a missing set or price makes it, since each of these is fixed on another screen. The server refuses regardless of surface (`listing-preconditions`), which is what covers the Offers list, whose rows deliberately carry no blockers of their own: evaluating every page of offers would pay the workspace's per-batch cost on a screen that is not about listing, and the refusal message states the same reasons.
- A listing **title** (#209/#210) is *stored*, and the derived label (`offerLabel`) is only what a surface falls back to while `Offer.name` is null. It is generated at creation — but an offer created **empty** renders over no copies, so `backfillOfferTitle` fills it in on the first mutation that adds copies (`addOfferSet`, `addOfferSetsPerCopy`, `addItemToOfferSet`; #365), and only while the field is still null. Growing a listing never rewrites a title it already has: that is what ↻ Regenerate is for. Without this the detail header looked right and everything reading the stored value — the copy control (#327), the bulk listing workspace (#322) — got nothing. Editing the title likewise seeds the input from what is *displayed*, derived label included (#363); `InlineText` only commits a changed draft, so opening and closing the editor still stores nothing. In generated titles, catalog numbers collapse on **both** of #150's axes (`compactCatalogNumbers`): consecutive bases within a prefix+suffix family (`BL31-33`, `40-42A`), then — over what stayed single — consecutive suffixes on one base (`BL92a-b`, `12I-III`; #364, via `parseSuffixOrdinal`). A span that already collapsed a base run is never folded by suffix: `31-32a` + `31-32b` are two runs, and joining them would claim a span the offer does not list. A number that is **itself** a Roman numeral (#383) carries no digit run and so reaches neither axis — it folds in a third pass keyed on the constant text in front of it (`I-III`, and `Mi·PL I-III` where the caller passes prefixed numbers, as the auction lot label does; #384), never merging with a digit-bearing number or with another prefix's numerals. That numeral may itself carry a **letter suffix** (#426), so the third pass runs both of #150's axes over it in turn, the numeral standing where the base does: the numeral under a constant suffix first — written at **both** ends (`IA-VIIIA`) unlike the numeric axis's `40-42A`, because a numeral and a letter suffix are both letters and `I-VIIIA` would read as a bare-numeral span with a stray letter hung off it — then the suffix on one numeral (`Ia-c`). An **uppercase** suffix folds on neither: `parseSuffixOrdinal`'s sequences are lowercase letters and numerals, and one that is itself a Roman digit (the `C` of `IC`) is read as part of the numeral, there being nothing that could tell the two apart. How a resolved span is **written** is `src/lib/catalog-range.ts` (#400, pure, unit-tested), one module for every surface that shows a range: the end drops the digits it **shares** with the start (`1298-302`, `1298-99`, `240-56`), a floor of two digits so `1298-9` cannot happen, and nothing at all when the endpoints differ in digit count (`98-102`, where a shortened end would read as the smaller number); the suffix axis writes the base once (`128a-c`). `compactCatalogNumbers` renders its spans through it, so a generated title, an offer set label, an auction lot name and the Issues list's declared-range chip (`formatIssueCatalogNumber`, en dash) are one notation. It is **display of a known range, never detection** — `resolveCatalogRange` stays the only reader of typed input — and deliberately absent where a range is being *edited or confirmed* (the issue form's First/Last, the range-extension and recompute prompts): those endpoints are about to be stored, and a shortened one would misdescribe what is being agreed to.
- An offer's generated texts are **subscriptions, not snapshots** (#380). Title, description and private note are re-rendered from the platform's templates after **every** mutation that changes what `offerComposition()` returns — sets added/removed, copies added, a set renamed, either order rearranged — through one `syncGeneratedTexts`, which subsumes #365's title backfill (an offer created empty gets its title for the same reason it later gets a fresh one). Three `Offer.*Edited` flags stop that: `patchOffer` sets one when the collector writes the field, `regenerateOfferText` clears it, so ↻ is literally "hand this back to the template". **Clearing** a field clears the flag too — the flag protects *written wording* and an emptied field holds none; blanking the title is how one asks for the derived label back (#209), which follows the composition by definition. That is also the rule the migration read existing rows by: a non-null text became `edited`, because the two cases are indistinguishable after the fact and losing typed wording is far worse than not refreshing generated wording. A field whose platform template is blank is never written, so clearing a template leaves the last text standing instead of emptying a live listing as a side effect of a settings change; a render that comes out empty likewise keeps what is there. **Terminal offers are skipped**: what a sold listing said is history, and the only composition change one allows is removing a set — ↻ still works there, because that is an explicit act. The `edited` chip on the detail screen is not decoration: without it "why didn't my title update?" has no visible answer.
- A listing text carries exactly one token that is **not** about the copies — `{offerUrl}` (#415), an absolute link to the offer's own screen here, for a private note read on the marketplace page. It therefore reaches the engine through a `ListingTemplateContext` argument rather than through `TitleTemplateCopy`, and the engine stays pure: the URL is built in `src/lib/app-url.ts` off `BETTER_AUTH_URL` (the base a deployment already has to get right for Better Auth, rather than a second setting that could disagree with it), and is null — token empty, glue separator and empty line dropped by the existing tidy passes — when it is unset. It is deliberately **not** a title token, but `resolveTokenValue` still knows it everywhere, so a `{offerUrl}` typed into a title renders empty instead of showing literal braces. The awkward case is creation: an offer's texts are generated *before* its row exists, so the id it needs is not there yet. Rather than splitting generation, `createOffer` / `duplicateOffer` pass a null id and then re-run `syncGeneratedTexts` — but **only** when the platform's templates actually name the token (`templateUsesOfferContext`), which is also the guard that keeps the slug lookup off every ordinary render. The second pass is safe because it is the same function every composition change already uses: the edited-flag and terminal-state rules are not restated anywhere. What it renders is the **short** address (#416): `Offer.offerNo` is a per-collection sequence allocated exactly as `Item.itemNo` is (#268) — `allocateOfferNumber`, an atomic counter bump on `Collection.nextOfferNo` inside the creating transaction, never `max + 1`, because a number published in a marketplace note must not later mean a different listing. `/o/<collectionSlug>/<offerNo>` is a **redirect** to the canonical `/c/<slug>/offers/<id>` and nothing else: an offer has one screen, and this is an address for it. It carries the slug because the number is per collection. The whole reason it exists is that Colnect's private note is `maxlength=100` (#402) and the canonical URL is 69 of them before the collector writes a word — with an over-long text posted **not at all** rather than truncated (#405), so the long form silently cost the note.
- Colnect prints a private note as **plain text**, so a link in one is not clickable — which is what `extension/src/core/instance-links.ts` (#417) fixes, on the sale page's own `._sl-private-note` element and nowhere else. Two rules, and they are separate on purpose: **origin decides whether** (only an instance in `chrome.storage.local` is rewritten — an extension that linkifies arbitrary text on a third-party page is a phishing vector, and "an address I hold a token for" is the one definition page content cannot spoof), and **path decides what it says** (`/o/<slug>/<no>` → `Offer #42`; the older `/c/<slug>/offers/<cuid>` → a plain `Stamporama offer`, a cuid being worth nobody's eyes). Matching on origin alone is also why both shapes are one case: notes published before #416 keep working. The icon is imported straight from `icons/icon-16.png` through esbuild's `dataurl` loader, deliberately rather than `chrome.runtime.getURL`, which would need a `web_accessible_resources` entry handing every page the extension's id — 355 bytes is cheaper than that trade. Pure DOM, so it is unit-tested under `linkedom` like the platform modules; idempotent, and it skips text already inside an `<a>`.
- A **derived offer set label** (#379) is the offer title's own catalogue vocabulary, not a join of bare numbers: `compactCatalogNumberGroups` (factored out of `{catalog}`'s own resolver, so the token and the label cannot drift) groups by vendor + area prefix, collapses each group through #150's `compactCatalogNumbers` and writes the prefix once — `Mi·RU-NW 15-19`, `Mi·RU-NW 15-16 / Fi·PL 3`. `15 + 16 + 17 + 18 + 19` named no catalogue and stopped being readable at the second set. Which vendor leads follows from the stamp's primary area link, so a label needs the area tree: `makeOfferLabeller(collectionId)` (`src/lib/offer-labels.ts`) reads it **once per page** and resolves through the same pure `buildAreaVendorMaps` the client renders chips with — the auction lot name's pattern (#353). It is shared with `sales.ts` and `offer-photo-generation.ts` rather than reimplemented, so a set reads identically on the sets card, the photo card, the sellable-offer picker and a sale line. A **copy's** own label stays a bare number: it is listed inside a set whose label already names the catalogue. Set labels are deliberately absent from the photo fingerprint, so this changed no stored image.
- A **set's own value** (#378) — catalogue value + purchase cost — rides on `OfferDetailSet.holdings`, from `getHoldingsValuationByGroup` with one group per set: every copy is fetched and valued once for the whole offer, and the detail's suggested price (#190) is summed from those same figures rather than from a second valuation pass. Per set rather than per offer because a set is what a buyer takes, so it is the number the asking price is judged against. The same pair is given **twice** where the offer prices in another currency, in the header's own grammar: the **offer's currency leads** in strong type and the base figure follows muted behind `≈` (`MoneyPair`), converted with a single rate fetched once for the whole screen (the one `suggestedPrice` already used). The offer's currency leads even though the base figure is the *stored* one — a catalog value is valued in base and a cost basis frozen there — because it is the currency the collector operates in: the price, the platform and the buyer are all stated in it. So `≈` marks the **secondary reading** on this screen, never "the derived one": on the asking price it carries base, here it also carries base, and the two lines read alike. With no conversion available there is one figure and it takes the strong type. A **roll-up bar** in the sets **header band** adds the offer-wide total and the **per-set average** (`OfferSetsTotals`). That band is one row owned by `OfferSetsView` — the section heading and *Add set* are passed *in* from the detail panel as `heading` / `primaryAction`, and *Collapse all* is stacked under the button — because everything that addresses the whole section has to share one rhythm and one right edge: rendered as a heading row in the panel plus a toolbar row here, the two aligned to nothing in particular and the tall figures box stretched whichever row it landed in, summed from the per-set figures rather than re-aggregated — an offer never lists a copy twice, so its sets partition its copies and the parts add up exactly. An average divides by the sets that *carried* a figure, never by all of them: an unpriced set is a gap in the data, and averaging it in reports the listing as cheaper than anything in it is (it is the same rule, and the same number, as `suggestedPrice`, #190). It renders as an **amount column at the right edge** of the card header — money is right-aligned everywhere in the app — placed *after* the status chips so the column lands in the same place whether or not a card carries one. Both it and the roll-up bar are **grids**, never rows of self-measuring cells: the bar's two headings have to sit over the pairs they name and `cat`/`cost` have to line up whatever they contain, and a per-row flex layout drifts the moment one line carries an equivalent and the other carries `—`. `MoneyPair` therefore emits bare *cells* and no wrapper, and the hover sits on the row's **label**, since a tooltip wrapper around a row would be one grid item holding four. The equivalent column is dropped entirely (not left empty) when the offer prices in the base currency, so an offer with nothing to convert carries no dead track.
- A listing **description** (#266) carries a **format** — `plain | html | markdown` (#319; ADR-0019). It is configured on the platform next to the description template it applies to, and **seeded** onto each offer (`Offer.descriptionFormat`), so changing the platform never re-reads a listing already written. Rendering goes `descriptionToUnsafeHtml` (`src/lib/description-format.ts`, pure, DOM-free, unit-tested) → **DOMPurify** in `shared/rendered-description.tsx`; never inject the unsanitised HTML anywhere else. The same sanitised markup is what the copy control puts on `text/html` (with the source on `text/plain`) when copying formatted. The private note (#267) has no format.
- A platform's **listing-text length limits** (#403) are the text-side counterpart of #308's photo limits and sit beside them on `Contact`: `maxDescriptionLength` / `maxPrivateNoteLength`, nullable, **read live and never seeded** (#310's rule — they describe the platform, so tightening one reaches every prepared offer at once), surfaced on `OfferDetail.platformTextLimits`. Two columns because platforms cap the two texts independently; Colnect using 100 for both (#402) is not a reason to fuse them. The counter is a **report and never a cut** — nothing truncates, and an over-long text still goes Ready and still publishes, because the wording is the collector's and the app's job is only that they learn about the cap here rather than in the platform's form with the listing half posted. That is also why it is not a listing precondition, unlike an unmapped Colnect condition (#406): a wrong *grade* is a false claim about the goods, while a long description is a paste that will visibly refuse. Counted in **UTF-16 code units** (`listing-text-limits.ts`, pure), because an HTML `maxlength` counts in those and the platform's own field is the authority on its own number — being cleverer with code points would report 99 where the platform reports 100. The shared `TextLengthCounter` renders **nothing** without a limit, so every surface passes one unconditionally; on the offer's own card it counts the **draft** while the field is open (watching the number come down as you cut is the point) and the stored **source** otherwise — what `⧉` copies, tags included, which is what the platform's field will hold.
- **One photo per copy** (#434) is the bulk form of #313 mode a, a second button beside *Add attachments* on the photos card: `attachOfferItemFrontPhotos` walks the offer's sets in plan order and attaches each copy's **front** scan as its own `copy_photo` attachment. Front or nothing — a back is the other side of a stamp the front already shows and an extra is a detail shot, so a copy with no front scan is **skipped and named** in the result (#314's "visible rather than silently missing"), never quietly substituted. Sets the plan excludes (#315) are excluded here too, and a front scan already attached on its own is passed over, so pressing it again tops the plan up instead of doubling it — a scan that is only a *tile* of a hand-built collage (#331) does not count as attached, since breaking out of that grouping is the point.
- **Auction tracking** (#23; ADR-0021, schema in #350) is a *bidding watchlist with a fork at the end*, not a register of market results fed from outside — the market data is a by-product of losing. `AuctionSale ⊃ AuctionLot ⊃ AuctionLotLine`. The parent is **one settlement with one seller** — what ships in one parcel — never "an auction as an event": a house's own sale for a house, an open-ended basket of everything currently bid on with one seller for a marketplace. That definition is load-bearing, because it makes shipping distribution fall out of ADR-0009 §3 for free (the grouping is made at bidding time, so settlement never asks "which purchase does this go into?") and it is what lets the sale-level rollup add shipping **once**. Seller and platform are two `Contact`s exactly as on `Purchase`, both `Restrict`. Currency and the two fee components live on the **seller** and are **seeded** onto the sale — the #308/#319 seeding rule again, so a seller raising their premium cannot re-price a parcel already tracked or settled — and `platformCurrency` (#196) does not apply, because an aggregator like philasearch carries houses listing in EUR, CHF and GBP alike. Outcome is **per lot, never per sale**: within one settlement some lots are won and others lost. The bid is a single overwritten figure with `checkedAt` and **no history** — refreshing is manual (no scraping, no scheduled polling), so `checkedAt` answers the one question a history would; `finalPrice` stays optional, because a lot that vanished from view is an absent observation rather than an error. **Recording the outcome** (#354, `recordAuctionLotOutcome`) is `won` / `lost` / `cancelled` / back to `watching` from the row's ⋮ menu. The two priced outcomes share one dialog and differ in exactly one rule: a lost lot's price is **optional** (an unseen result is an absent observation) and a won lot's is **required** (you cannot have missed what you paid, and #28 prices its purchase line from it — a `won` lot is also the input that action operates on, so it must be reachable here). Marking won stops at status + price and writes **no** `Purchase`: a parcel settles as a whole, once, when the seller invoices it. It does immediately sharpen the sale rollup, which costs `won`/`watching` lots at `finalPrice ?? currentBid`. Marking lost freezes `AuctionLot.fxRateToBase` the way `Purchase` does at `purchasedAt` (ADR-0009 §4, #20), and **only when a price was recorded**: a rate exists to convert a figure, so null covers base-currency, no-rate and no-result alike. Nothing is inferred into the price — the last observed bid is a lower bound, so the field opens blank and blank is a valid answer — and `cancelled` clears price and rate, as does reopening, since neither carries a datapoint. Once a result exists the row renders it in place of the bid: it is what the lot went for, and it is already what `allIn` is computed from. Composition is structured (`stamp × condition × certificate × format × quantity` — the shape a catalogue price is keyed on; the certificate arrived with #353, null = none as on a copy, because a house lot sold with a Fotoattest is worth a different figure and matching is strict) because free text makes catalogue value uncomputable and a lost lot unusable, and it **reuses** the unknown-variant rollup (#238) and format pricing (ADR-0020) rather than re-deciding them — literally, through the exported `valuateItemRows` (`items.ts`), which values a `stamp × condition × certificate × format` row of which a copy is one instance and a lot line another at a **null certificate** (a lot is described before it is owned). `auction-lines.ts` calls it **once per page of lots**, so the factor table and area tree load once. Catalogue value pivots **base currency → the sale's**, converted once per sale currency, because the bid, premium and ceiling are all denominated there; a missing rate makes a line **unconvertible**, which is not *unpriced* — it has a value that cannot be counted, and calling it unpriced would send the collector to enter a figure that already exists. A composition entered but unpriced is `null`, never `0.00`: a zero makes every headroom read as a catastrophic overbid. Unpriced/unconvertible lines are **counted beside the total**, never dropped. A **row's** headroom excludes shipping (premium only, exactly as `allIn` does) and the **sale's** includes it once. The price slot carries the shared quick-price dialog (#228/#341) over a `QuickPriceSubject`, which a lot line satisfies structurally. Composition has **two surfaces, deliberately**: on the **sale's own screen** each lot is a collapsible **card over its lines**, the purchase-order intake / offer-detail layout (#121/#165) — same `LotIssueGroupHeader`, same *Group by* / *Only* / *Sort* toolbar persisted through `lot-view-prefs`, and the watchlist row itself as the card header so a bid is still refreshed in place; on the **flat watchlist** the same list opens as a dialog off the row. The split follows the question each screen asks — "what do I bid on next", across sellers, versus "what am I actually paying for", within one parcel — and is the same one the offers list has with an offer's own screen. Only the sale detail carries the lines (`AuctionLotDetailItem`); the flat list would otherwise fetch forty compositions to draw forty collapsed rows, and its row only needs the total. Entering a line is **two modals**, the purchase intake's flow (#121): `StampPickerBrowser`, then `AuctionLotLineDialog` for condition / certificate / format / quantity, with the pick restated and a ← Back. Two sources, two questions — the catalogue tree answers the first, the listing text the second. The dialog **portals to `<body>`** (it is opened from inside other dialogs, whose transform-centred panels would otherwise be the containing block for its `position: fixed`), and pre-fills condition + certificate from `LS_LAST_CONDITION`/`LS_LAST_CERT` — the same remembered pair every add-copy entry point uses. Going through `StampPickerBrowser` directly (not `StampSelect`) is also what gives the purchase intake's **whole-issue** pick: a series expands — in the *action* layer, `resolveAuctionLineStamps` — into one line per member `requiredForCompleteness`, because a house lot is routinely "Mi 1–12 complete" and twelve trips through the picker is why it would go undescribed. The issue is an **entry shortcut only**; a stored line is always one stamp, since catalogue value sums per stamp and a lost lot must be attributable per stamp. Editing offers stamps alone — one line becoming twelve is not an edit. The remaining fields do not render until something is picked — a line *is* a stamp at a condition, and four greyed-out selects is a form pretending to be busy. **Add lot** carries the same composition section and `createAuctionLot` writes lot + lines in one nested create, every line validated first so a refusal leaves no half-entered lot. A lot card on the sale screen passes `showParties={false}`: a sale is one settlement with one seller, so both are fixed and the header states them. A lot with no `title` is **named after its composition** (`deriveAuctionLotLabel`, pure in `auction-rules.ts`): collapsed catalogue numbers **with their prefix** (`Mi·PL 1-12`) — through the listing engine's own `compactCatalogNumbers`, now exported, since two implementations of #150's collapsing would drift. The prefix rides *inside* the collapsing (it is just the numbering family's constant part), so it is written once around a span and a lot spanning two areas stays honest as `Mi·PL 1-3,Mi·DE 5`. Resolved server-side through the same pure `buildAreaVendorMaps` + `formatStampCN` the client renders chips with, over `readCollectionAreas` — `getCollectionAreas` minus the ownership check, split out rather than threading an `ownerId` into modules with no other use for one — then the issue when the lines share one, and a mixed lot reads as its size (`14 stamps · 3 issues`) because a name is scanned, not studied. **Derived on every read, never stored**, unlike an offer's title (#209/#365): a lot name is never published anywhere, and a lot is described line by line, so a stored value would freeze on the first stamp. It outranks `Lot {lotNo}` in `lotLabel` — the number is already its own chip and says only where the lot sits in someone else's catalogue. `AuctionLotLineItem.catalogNumbers` is ordered **primary vendor first** (`buildPrimaryVendorByAreaMap`, once per page) so the name picks one catalogue rather than three. A line row is **not** `InventoryItemRow`: a line is a stamp a lot is *described* as holding, so there is no copy number, location, disposition, delivery state or cost basis to show — it mirrors the copy row's four-line layout and adds quantity. `copy-sort.ts` was generalised to a structural `SortableCopy` + `sortSortableCopies(…, amountOf)` so both orderings are literally one comparison, the amount differing because a copy's is a base-currency catalog figure and a line's a sale-currency total. The arithmetic is pure in `src/lib/auction-lot.ts` (`allIn` = bid + percentage + fixed + shipping, `headroom`, `summarizeAuctionSale` over the *payable* — `watching`/`won` — lots): a ceiling set against the hammer price alone systematically overpays on cheap lots. **Settlement** (#28, `settleAuctionSale`) is a **1:1 transcription** into `Purchase`/`PurchaseLot`, the links unique and `SetNull` so deleting the purchase leaves the bidding record standing — which is also the undo, `assertLotEditable` freezing a settled lot because the purchase now holds what was actually paid. Seller/platform/currency/shipping come off the sale; each settled `won` lot is one line at `settlementLinePrice` = hammer + premium and **never** shipping, which becomes `Purchase.shippingCost` and is distributed across those very lines by ADR-0009 §3 — charging it per line would bill it twice. The composition is **written as copies, not proposed**: a line already is `stamp × condition × certificate × format × quantity`, so a confirm step would re-ask what was typed to decide the bid; a line of quantity N becomes N `Item`s (`ordered`, out of collection, cost pending, one `allocateItemNumbers` range for the parcel) and the existing intake runs unchanged. What *is* reviewed is the money — date, shipping, every line price and **which** won lots are in the parcel — because the seller's invoice is the authority, not our arithmetic; a won lot left out stays `won` and unsettled, since a lot shipped separately is a fact, not an error. Refused while any lot is still `watching` (the parcel's contents are not known) and with nothing selected (a sale where nothing was won is **closed**, not settled). The review dialog is built from the already-loaded `AuctionSaleDetail` — there is no settlement-preview endpoint, because a won lot's line price is the row's own all-in figure.
- Background work runs **in-process**, started from `src/instrumentation.ts` `register()` — no extra compose service. Two shapes: *periodic* stateless sweeps (the photo orphan GC, #112) and *triggered* jobs queued in a **table** whose row is also the state the UI polls (offer photo generation, #311; ADR-0018). A queued job must be idempotent — `running` rows are requeued at boot — and enqueuing must be a no-op while a run is already queued or in flight. Pin worker state to `globalThis` so `next dev` HMR cannot stack a second interval.

## UI Direction

- Modal dialogs for list actions (add, edit). Build with shared `src/app/dialog-shell.tsx` primitives — do not duplicate dialog header, close, viewport constraint, or height behavior. A dialog rendered **from inside a row** must portal to `<body>` whenever any ancestor makes its own stacking context — a transform-centred dialog panel, but also a plain `opacity` below 1, which is how an ended auction row is muted (#354). Inside one, `DialogShell`'s z-index only ranks the dialog *within that row*, so the sticky toolbar and the app header paint straight over it.
- **Escape closes one surface**, the topmost (#361). Every dismissable overlay registers with `useEscapeLayer` (`src/app/escape-stack.ts`); the stack is ordered by mount, which *is* the order surfaces were opened in, so the last entry is the only one that hears the key. `DialogShell` and `PhotoLightbox` register for you — a nested dialog, picker or lightbox therefore needs no Escape handling of its own. Do **not** go back to a document-level capture listener with `stopImmediatePropagation`: that only wins by registration order, so the *outer* dialog ran first and closed itself out from under the lightbox that had just opened above it. The shared listener deliberately does not stop the event, so popovers that are not layers (row-action menus, autocompletes, the translation popover) keep their own listeners and their own behavior; a dialog that must yield to one steps out of the stack with `dismissable={false}` (compose-set while the gap popover is up).
- A list filter over **several values at once** is `MultiSelectFilter` (`shared/multi-select-filter.tsx`, #425) — a toolbar-sized button that opens a checkbox list, never a `<select multiple>`, which turns into a scrolling box the height of the toolbar. It reads the one value's name when one is ticked and **counts** them when more are (`3 conditions`), so the control cannot grow and shove the toolbar around. Selection applies as it is made — the list behind it is what says what a tick did, so an Apply button would only ask the collector to confirm what they can already see — and *clearing* is the list's own first row rather than a control beside the trigger, since clearing and unticking everything are one act. It is a **popover, not a layer**: it keeps its own Escape and outside-click instead of joining the escape stack (#361), the same call the notification centre makes, and portals to `<body>` with fixed positioning so a toolbar's `overflow` cannot clip it. The value rides in the URL comma-separated, exactly as `areaIds` does, and an empty list is the **absence** of the filter rather than an unmatchable empty set. Server-side, one axis keeps **one** filter on it: `conditionIds` / `formatIds` / `deliveryStates` (#425, #427) replaced their singular forms on `ItemListFiltersPaginated` **outright**, and every caller pinning one value — a duplicate group addressing its own members, the sale-lot composition picker's `delivered` (#164), `GROUP_ELIGIBILITY` — passes a single-entry list through the same field, so there is never a second knob to keep in step. Renaming rather than adding is also the only way the compiler finds the callers; where one is reached by a **spread** it cannot (`GROUP_ELIGIBILITY`, the duplicate-grouping valuation filters), so those carry a `satisfies` / an explicit annotation — an unrenamed key in a spread is silently dropped, and dropping `deliveryState: "delivered"` would quietly widen a group's eligibility. Two axes are **not a plain `in`**, and share one helper (`nullableIdWhere`): format, where `"single"` is the *null* format (ADR-0020), and certificate, where `"none"` is (ADR-0006 §2, #428). A null is never a member of an `in`, so ticking the sentinel beside a real value is two branches ORed — and that `OR` goes into `buildItemWhere`'s **AND list**, never the top level, where the search's own `OR` would collide with it (and where two such axes at once would swallow one another). Certificate had **no filter at all** before #428 — the field existed only so a duplicate group could address its own members — which is why adding the control came with the rename rather than after it. An unrecognised delivery state is **dropped** from the list rather than passed through, so a stale link narrows to the states it does name and, once nothing is left, shows the whole list rather than an empty screen.

Dialog-opening actions expose `{ action, dialog }` hooks rendered at the row level (see `use-price-details-action.tsx`, `use-inventory-copy-actions.tsx`) so the dialog survives the menu closing. Section-level adds (e.g. + Add area) stay as standalone buttons. Hide it only when the row itself already answers the question — a copy not marked *For sale* shows no offer action, since the disposition chip is right there. A handful of the most-repeated actions are additionally **promoted onto the row** as icon buttons (`RowQuickActions` + `pickRowActions`, `shared/row-quick-actions.tsx`), which is the shape #261 was missing: a promotion is a **shortcut, never a move** (the entry stays in the menu, so nothing is reachable only by the icon), the button is an **icon with a tooltip and no label**, and it is **always drawn — dimmed at rest, full strength on row hover**, never revealed *by* the hover: appearing on hover makes aiming a two-step move (hover to find out where the buttons are, then aim), which is worse than the dimmed icon it was meant to save. Promoted so far: the Issues list (issue row: edit / add stamp / add copy; stamp row: edit / add child stamp / add copy).

- A control that is **auxiliary to a field beside it** carries `tabIndex={-1}` (#445/#446). Tab is how a form is filled in, so it should walk the *fields* — a stop per helper turns a card of three texts or a dialog of six vendors into a slalom, and the collector's hands leave the keyboard for something they never asked to visit. The line is **not "icon vs. label" and not "small vs. large"**, it is *could this control be skipped and the field still be completed*: a copy `⧉` (#327), a 🌐 translations opener (#293–#296), a template's click-to-insert token chips (the syntax can be typed), a search box's own clearing `✕`, a price grid's ⤴ carry-forward and the issue dialog's per-vendor prefix overrides (#377 — rare, and one per vendor stands in front of the numbers) are all skipped, because each is a shortcut to something the field itself already offers. What **stays** in the order is anything that is the only way to reach a piece of state from the keyboard: a `✎` that opens the field at all, a Save / Cancel pair on an inline edit, a `+ Add` that commits the select next to it, a `✕` that removes a row, a sort-direction toggle, a filter chip. Those are controls in their own right that happen to sit near an input, not helpers on it. Bake the rule into the shared component (`copy-button.tsx`, `translations-field.tsx`, `template-builder.tsx`'s chips, `list-toolbar.tsx`'s `CLEAR_BTN`) rather than at each call site, so a new caller inherits it. Mouse reachability is unchanged, and everything inside a dialog such a control opens tabs normally — the exclusion is about the *route in*, never about the surface it leads to.

- Physical **format** (pair, block, strip) is an axis of its own (ADR-0020), not a stamp — superseding #135's "record a multiple as its own `Stamp` with a self-descriptive number" for *homogeneous* multiples, which collapsed on deep variant trees (Infla `309 → 309A → 309AP → 309APa`: `formats × nodes` stamps, and "a pair, variant not yet identified" inexpressible because a pair of `309BP` is not a child of a pair of `309B`). `StampFormat` is a per-collection dictionary shaped like `StampCondition`, referenced from `Item.formatId` *and* `StampCatalogPrice.formatId`. **Null means single** — no such row is seeded, exactly as a null `certificateStatusId` means "no certificate" (ADR-0006 §2) — so nothing needed backfilling. A multiple is **never decomposed**: no unit count exists, nothing multiplies or divides by one, and completeness treats format as a breakdown dimension beside condition ("the series in pairs?" like "the series in MNH?"). Zusammendrucke with their **own** catalog number (Michel `S`/`W`/`K`/`Zd`) stay their own `Stamp` — the test is whether the catalog numbered it, not whether it holds more than one stamp. A format's price is **explicit or derived**: an explicit `StampCatalogPrice` row wins, else the single's price × a `StampFormatFactor`, because catalogs publish one factor per issue and an explicit price only where a multiple deviates. Factors live in one table with nullable anchors — the all-null row *is* the collection default (no second `defaultFactor` mechanism to explain) — resolved by **fixed precedence**, `(issue set?, area depth, condition set?)` lexicographically, never a specificity score: *where* deliberately outranks *for which condition*. The rule is pure in `src/lib/format-factor.ts`; `format-pricing.ts` wraps it per stamp because it needs the area ancestry and issue. A format is **translatable** like every other dictionary that reaches a listing (#344; `StampFormatTranslation`, two independently-falling-back columns, `format` in the shared `TranslatableEntity` union), and renders through `{format}` / `{formatAbbr}` + `{#formatLegend}` (#345) — where a **single resolves empty**, the common case, handled by the existing tidy pass rather than by a rule of its own. Lists gain an **`as`** switcher beside the condition one (#343), defaulting to Single, hidden without formats, stored as `""` because Single is not a row. A list column **derives** where nothing explicit was recorded and marks it with the same `~` + italics an unknown-variant rollup uses (#238) — one vocabulary for *inferred, not recorded*, distinguished only by tooltip. The Copies list takes format as a **filter**, never a switcher (a copy's format is a fact), and `valuateCopy` resolves at `Item.formatId`: with no explicit price and no factor a multiple is **unpriced**, never valued at the single's figure. Per-row factor resolution would be a query per row, so `makeFormatFactorLookup` loads the factor rows + area tree once and resolves in memory. A multiplier is **edited where its scope lives** — an issue's from its row on the Issues list, an area's from its row under Areas — so the anchor is never a field the surrounding screen already answers; Settings edits only the collection default and areas and **does not list issue-anchored rows at all**, excluding them *at the query* (`getCollectionFormatFactors`) rather than filtering after: there can be one per issue per format, which is thousands of rows. A scoped list shows what is set on that row alone, never what would apply through inheritance — it is an editor, and showing a parent's rule under a child invites editing it from the wrong place. The scoped editor is one component exposed both as a `{ action, dialog }` row-action hook and as a plain dialog, because the areas panel maps its rows and cannot call a hook per row. The price grid gains format **tabs**, not columns, and a derived value renders as the cell's placeholder so it stores nothing until typed over. Price cell keys grew a **trailing** `~<formatId>` segment, optional so pre-format payloads still parse.

The override map is loaded **whole, once per read** (`issue-prefix.ts`; client `issues/catalog-prefixes`, keyed under `["issues", collectionId]` so existing issue invalidations cover it): the table is sparse by construction and a screen needs it before drawing its first chip. `duplicate-catalog.ts`'s `CatalogPrefixContext` additionally takes prefixes *typed into a form but not saved* — the issue create dialog checks numbers against an issue that does not exist yet, so the form is the only place its prefixes can come from. - A stamp's **subtype** (ADR-0010 §6; #338–#340, #342) is shown wherever stamps are listed or picked — issue tree, flat stamp list, Copies list, pickers — through the shared `SubtypeChip`, and is available in listing texts as `{subtype}`. - The **notification centre** (#367) is a bell **in the sidebar's top row**, beside the collection name — the app has no top chrome, and a badge in the footer beside Sign out is a badge nobody sees. A group carries a **severity** (`critical` / `warning` / `info`), which is what decides both its tint and the panel's reading order — graded by **consequence, not by subject**: a possible **double sale** is `critical` (both offer groups: one piece of stock committed in two places, costing money and a rating, undoable only by the collector), a **deadline that can still be met** is `warning` (a lot closing today), and **bookkeeping that never fixes itself** is `info` (an ended lot with no outcome). It is the lot list's own rule — colour means *act now*, which is why an ended lot there is muted rather than reddened — applied across sources. Provider order is only the tie-break, so a source's place in `PROVIDERS` can never outrank a worse problem from another one. The badge is tinted by `ActionItemsResult.severity` — the **worst** thing waiting, never the count, or three ended lots would outshout one double sale — and that grade is resolved **server-side** so the bell and the panel cannot grade one list two ways. In the panel the **heading** carries the tint, not the rows: a list of names is read, and tinting every line makes it harder to triage rather than easier. An item carries its instant as ISO and the client formats it (`formatRelative`): "in 3 hours" needs the browser's clock and locale, and a server-rendered string goes stale while the panel sits open. Hrefs are **collection-relative** — the slug is a routing concern and the domain layer only holds the id. It **refreshes off the query cache itself**: the bell subscribes to `getQueryCache()` and re-reads (debounced) whenever any *other* key is invalidated, because every mutation here is a server action followed by the screen invalidating what it shows — so recording a lot's outcome empties a group and drops the badge at once, without a single mutation site knowing the panel exists. Wiring each source's mutations in by hand would undo the registry: a new provider would mean hunting down every action that could feed it. The interval and the focus refetch stay as the backstop for anything that refreshes by `router.refresh()` alone. Nothing is acted on in the panel: an action taken in a popover is one taken without the context that makes it the right one. It is a **popover, not a layer**, so it keeps its own Escape/outside-click rather than joining the escape stack (#361), and it **portals to `<body>`** — the sidebar scrolls, so it sets `overflow-y`, and a box that is not `visible` on one axis is not visible on the other either. `QueryProvider` moved up in the collection layout to wrap the sidebar too, so the shell and the screen share one cache.

- A **hover hint is the shared `Tooltip`** (`shared/tooltip.tsx`), never the browser's `title` attribute (#291). The bubble portals to `<body>` with `fixed` coordinates, so no ancestor's `overflow` clips it, and it is **clamped to the window** by `TooltipBubble` — measured in a layout effect, then *flipped* to the trigger's other side when it overruns vertically (sliding would cover the control it describes) and *slid* when it overruns horizontally (a trigger has no other side to flip to). That clamp lives in the primitive on purpose: a hint is most needed on the controls sitting at the edges of the screen, which are exactly the ones whose bubble runs off it, and leaving it to callers meant every such site had to notice the problem first. `placement`/`align` are therefore a **preference, not a guard** — set `align` where the anchoring itself reads better, not to avoid an edge — a native tooltip ignores the theme, appears after a delay nothing else in the app has, and cannot carry formatting. Native `title` survives in exactly two places: revealing text that is *already on screen* but ellipsized (the hint repeats the visible string, which is the browser's overflow affordance, not a tooltip), and the printable packing sheet, a server-rendered artifact that should not become a client component for hover text that never prints. Three things follow from the wrapper the component inserts. **Empty content renders no bubble**, so a conditional hint stays one code path instead of branching between a wrapped and an unwrapped child — which would move the child in the layout. Layout the child carried (`flex`, `marginLeft: auto`, `position: absolute`, `width: 100%`) moves to the wrapper's **`style`**, or the row shifts around it. And a tooltip **inside** another tooltip suppresses the outer one while it is open, matching what nesting `title` did — triggers nest constantly here (a chip with its own hint inside a clickable row that has one), and `mouseenter` does not re-fire on the ancestor, so both bubbles would otherwise sit on screen at once. `title` doubling as an icon-only control's accessible name is not a reason to keep it: give the control an `aria-label` and the hint a `Tooltip`.

The offers one (#317) leads with **asking value** alone, because the per-state counts it would otherwise repeat already live in the filter chips (#332); **More** reveals the copies' catalog value + purchase cost (the holdings pair, #134) and a per-platform split, behind an expander because they cost a valuation pass and answer an occasional question. The per-platform breakdown repeats **all three** figures — a slice answers the same questions as the total — as a grid whose amount columns sit at the **left**, beside the platform name (a right-aligned far edge makes a wide screen unreadable), the asking column landing under the total's. Platform rows are each complete in themselves and deliberately **do not sum to the total**: a copy on two marketplaces is valued in both. Overlapping slices are why the valuation is a single pass — `getHoldingsValuationByGroup` fetches and values the union once and aggregates per group, so adding a platform costs an aggregation, not a pricing run. - A copy's **internal number** (#268) is a per-collection sequence on `Item.itemNo`, unique with `collectionId`, assigned at creation and never editable. It is handed out by bumping `Collection.nextItemNo` in one `UPDATE ... RETURNING` (`allocateItemNumbers` in `src/lib/items.ts`, which takes a range for a bulk intake) — **never** `max(itemNo) + 1`: the number gets written on the physical piece, so a deleted copy must retire its number rather than pass it to the next one. Every `item.create*` site must supply it. Display and search parsing are pure in `src/lib/item-number.ts` (`formatItemNo` → `#00123`, zero-padded so a column lines up; `parseItemNoSearch` accepts `123` / `00123` / `#00123`). A numeric search matches the number **in addition to** the text search, never instead of it — `200` is also a plausible catalog number. It rides in the row's meta line and the Edit dialog's title, not in a form field: a permanently disabled input earns no space. How wide it renders is the collector's choice — `Collection.itemNoPad` (Settings → General), display-only, so changing it renumbers nothing and cannot break a search (leading zeros are insignificant to `parseItemNoSearch`). Client surfaces read it through `useCollectionItemNoPad`, a query rather than a prop, because `InventoryItemRow` is rendered from eight screens. In listing texts it is `{itemNo}` / `{itemNo:N}` (#268) — padded to the collection width, or to `N`; an unusable `N` falls back to the collection width rather than emptying the token, and **no `#` is added**, since a template is literal text. `TitleTemplateCopy` therefore carries `itemNo` *and* `itemNoPad`: collection-level data on a per-copy shape, because the pure engine has no other channel.
- The **short number** pattern is now every major entity's (#432), and the box that consumes them is #431. `Issue.issueNo`, `Purchase.purchaseNo`, `Sale.saleNo` and `AuctionLot.auctionLotNo` join `Item.itemNo` (#268) and `Offer.offerNo` (#416), each off its own `Collection.next<Entity>No` counter through one shared `allocateEntityNumber` (`src/lib/items.ts`) — the same atomic `UPDATE ... RETURNING`, never `max + 1`, because a number that has been quoted must not come to mean something else. One counter per entity rather than one shared sequence: a collector counts purchases and issues separately, and sharing would make every number jump for reasons nothing on screen explains. Every `create*` therefore runs **in a transaction** — `createPurchase`/`createSale`/`createAuctionLot` gained one for exactly this, so a failed create cannot burn a number. `AuctionLot` is the one without a unique index: a lot carries no `collectionId` (it reaches its collection through its sale), and denormalizing that would be a second answer to "which collection is this lot in" for the sake of a safety net the counter already provides; `auctionLotNo` is also deliberately **not** `lotNo`, which is the *house's* number — typed in, optional, repeating across sales, and the field an Allegro capture writes the offer id into (#355). `AuctionSale` gets no number: the lot is what one refers to, and it carries its sale's address. The numbers render through one `EntityNoChip` (unpadded — `Collection.itemNoPad` exists because a copy number goes on the physical piece and a column of stock cards has to line up; none of these do). The **box** is `parseQuickJump` in the pure `src/lib/quick-jump.ts` (prefix table: `i` `o` `p` `s` `iss` `lot`, longest-prefix-first so `iss12` is never `i` + `ss12`) plus `resolveQuickJump` in `quick-jump-server.ts` behind `GET /api/collections/[collectionId]/quick-jump`. It is a **jump, not a search**, and does nothing until Enter: a bare `200` is refused rather than guessed at, because it is as likely a catalog number, a year or a price. The slug in the returned href is read **server-side** off the authorized collection, never taken from the query — the answer is an address the browser is about to follow. Where each lands is a product decision stated in that module: copy and issue to their list filtered to the number (neither has a screen of its own), offer to the `/o/<slug>/<no>` redirect (#416) so a jump and a followed marketplace link are one journey, purchase/sale to their detail screens, and a lot to its **sale** with the lot highlighted (#374) — a lot is read in the company of its parcel.
- **Copies held per stamp** (#348) come from `src/lib/copy-counts.ts` — one `groupBy` over the disposition flags for a whole page of stamps, never a count per row — and render through the shared `CopyCountBadge` on every surface that lists a stamp (issue tree, flat list, pickers). Counted **per stamp exactly**, never rolled up from variant children (the tree shows the child's own badge one line down, so a rollup would show one copy twice), and **excluding sold copies**, because the badge sits beside *View copies* and must agree with what that popup lists (#207). Delivery state is deliberately *not* filtered — a copy in transit is bought. A stamp with none shows **nothing**, the same unmarked-default rule as the subtype chip and the single format. The disposition figures are markers that overlap (in collection *and* for sale), so they are listed in the tooltip, never summed.
- **Which offers something is in** (#276, #349) is a read-only popup off the Copies, Stamps and Issues row menus, fed by `listOffersForTarget` (`offers/for-target`, a static segment ahead of `[offerId]`) — unpaginated, because a target sits on a handful of listings at most. It is scoped by an `OfferLookupTarget` (`item | stamp | issue`) mirroring the copies popup's targeting (#110), and a **stamp matches exactly**, never rolled up from its variant children — the same rule as the copies-held badge (#348), since the tree shows a child's own entry one line down and a rollup would report one listing twice. The stamp/issue surfaces go through `useOffersPopupAction`, the `{ action, dialog }` row-action hook; the Copies list keeps its panel-level dialog union. It lists **every** state, terminal included (unlike the offers list, which hides closed ones by default, #245): a sold or withdrawn listing is exactly what one asks a piece's history for. Ordered live-first (`active → paused → ready → preparing → sold → withdrawn`), newest first within a rank, so "where is this on sale right now?" is answered by the top of the list. The row reuses the Offers list's presentation (platform/state chips, needs-action + bidding badges, asking price with base-currency equivalent), opens the offer's detail screen on click, and links the platform listing separately. The action is **unconditional** — a sold copy's past listings are as much the question as a live one's, and the row carries no offer count to hide it by.
- A copy's **delivery state** (ADR-0009 §5) has one vocabulary: `src/lib/delivery-state.ts` (pure — valid set, labels, tint tokens, lifecycle order, `isDelivered`), read by the domain layer, the route handlers and every screen. Do not restate the list. On the Copies list it is a chip **only when the copy is not delivered** (#272) — delivered is what a hand-added copy starts as and every sorted copy ends as, so chipping it would badge nearly every row, the same reasoning that leaves a single format unlabelled — plus a single-select filter, threaded through the list, holdings-valuation and year-facet endpoints alike so the bar and the panel never disagree with the rows. The two exception outcomes (`UNAVAILABLE_DELIVERY_STATES`) are excluded from the *not offered on platform X* worklist (#259): a copy that never arrived or arrived damaged is paid for but not in hand and never will be, so it cannot be listed — while the in-flight states stay, since a copy on its way is exactly what one prepares a listing for. The intake screen renders its own editable delivery control, so it passes `hideDeliveryState` exactly as it passes `hideDispositions`.
- A copy's **disposal** (#394–#396; ADR-0009 addendum) is a *fourth* axis on `Item`, orthogonal to disposition and delivery: it left the collector's hands **after** arriving — lost, damaged in storage, discarded. It is the involuntary counterpart to a sale, both being ways a copy stops being held, one with proceeds and one without. Not a delivery value, because `deliveryState` describes *intake* and ends at arrival: conflating "broke a year later" with its `damaged` outcome makes supplier quality unmeasurable, and `not_delivered` additionally drops the copy from its lot and redistributes the allocation (#122), which is exactly wrong here — the copy did arrive and was paid for. Not a disposition either, those being *intent* rather than possession. Three nullable columns, `disposedAt` doubling as flag and timestamp so every filter stays a plain `where`; vocabulary and predicate pure in `src/lib/disposal.ts` beside `delivery-state.ts`, a note **required** for `other` (`lost`/`damaged` say what happened, `other` says only that something did). The allocation is **never** touched — `costBasis`, `lotId`, `itemNo`, photos and history all stay, and `itemNo` is retired rather than reused. Two preconditions that name their own reason (#273's rule): only a **delivered** copy can be disposed of, and one in a **non-terminal** offer needs that offer withdrawn first — enforced at `assertAddableCopies`, the single chokepoint every composition path goes through. Reversing clears all three columns: the axis records possession, not a history of it. **`isHeld`** (not disposed, and `deliveryState` outside `UNAVAILABLE_DELIVERY_STATES`) is the single predicate behind availability, collection value and the copies-held badge (#348); in-flight states pass, being copies on their way *in*. Soldness is deliberately outside it — that already has one mechanism at every reader (`saleLineItems: { none: {} }` behind `excludeSold`, #207) and a second would be a pure field test needing a join. What the predicate excludes is **moved, not dropped**: `HoldingsSummary.writeOff` carries the retained cost basis of the copies in scope that are gone, as a third bar line — a **cost and never a catalog value**, since a copy that is gone is worth nothing to its owner however the catalog prices it, while what it cost was really spent and hiding it would flatter the purchases. Because disposed copies are hidden from the list by default (`includeDisposed`, the `includeSold` shape), `getHoldingsValuation` **lifts that one exclusion** and partitions the scope itself — summed over the *visible* set the write-off would read `0.00` in exactly the case it exists for — while leaving `excludeSold` alone, a realised sale being #168's subject rather than a loss.
- On a purchase lot, **"to sort" and "unsorted" are two different counts** (#375). The header chip and its list filter address the `to_sort` state *exactly* (`LotIntakeSummary.toSortCount`) — a copy still `ordered` or `in_transit` has not arrived, so it is not waiting on the collector, and counting it sent them looking for a stamp that is not on the table. The close confirmation keeps the wider `unsortedCount` (`ordered` / `to_sort` / `in_transit`, `UNSORTED_DELIVERY_STATES`), because a lot whose copies are all still ordered has not been through the sort pass either and closing freezes cost-basis. The chip is therefore *narrower* than the warning by design; do not re-merge them. **Mark sorted** likewise separates its two axes: the `delivered` transition always applies, while the disposition offers **Leave as is** (#274, `LotBulkChanges.keepDisposition`) beside the three flags — some copies were filed one by one during the sort pass and a blanket value would overwrite exactly the decisions that took longest. It is a chip of its own rather than an empty selection, because all-three-off already means *clear the dispositions* and the collector cannot tell the two apart otherwise; the flag exists on the server because "no disposition given" already meant "default to `inCollection`", and that default is what it suppresses.
- **Auction sales** get their own collection nav page, and the **flat list of lots is the primary screen** (#351) — status / platform / seller filter chips (#332), sale as a column with optional grouping, inline bid editing — so "everything I have running on Allegro" needs no navigating between sales. Sale detail exists separately, for settlement and shipping. This follows from the sale being a *settlement boundary*: it matters twice (when a lot is added and when the parcel is paid for) and is in the way the rest of the time, whereas scanning closing times and refreshing bids is what happens daily. Consequently adding a lot never starts by picking a sale (#352): the dialog takes seller and platform and **proposes** the open sale for that pair when one exists, with the option to start a new one — the proposal is re-read server-side rather than trusted from the client, and refusing it (`startNewSale`) is what a second parcel from a seller who has already shipped needs. The screens live under `auctions/` (`/auctions` the lots, `/auctions/sales` the settlement list, `/auctions/sales/[saleId]` the detail), the vocabulary + staleness + parsing in `auction-rules.ts`, the reads/writes in `auctions.ts`. Four decisions the code depends on. **Staleness is relative**: a reading may be a quarter of the time that was left when it was taken old before it counts stale, capped at a day — one ratio instead of a threshold table, tightening exactly as the close approaches; a live lot past `endsAt` reports `closed` instead, because that is the only signal that never fixes itself. The toolbar filters on **two different questions**, and the split is deliberate: *signals* (`LotSignal` in `auction-lot.ts` — can-still-bid, outbid, leading, over-ceiling, won-pending) are **derived** from the figures and answer "what do I do about this now", while *statuses* are **recorded** and answer "how did this end". A watchlist is worked through by the first and filed by the second. Signals describe `watching` lots only. They span two tables plus arithmetic, so no `where` expresses them: `resolveSignals` walks the live lots once in memory and hands ids to the page query — the offers list's needs-action pattern (ADR-0013 §4), and sound for the same reason, a watchlist being bounded by what one person is currently bidding on. **Colour means "act now"**, and nothing else: an ended lot is *muted* (row opacity included), never red — there is nothing to react to, and an alarm on it would compete daily with the lots that can still be won. That is why the `Ended` / `Closing today` / `This week` window filter exists (server-side on `endsAt`, the boundary read from the server's clock so two tabs and the counts cannot disagree; deliberately **not** remembered between visits, unlike the other filters, since a list silently narrowed to old lots would hide everything running). Past the close, `BidStandingChip` stops reading as a position and reads as a **result** — *Won?* / *Lost?*, with the question mark, because it is inferred from the last bid anyone recorded rather than from the platform; a lot whose outcome *is* recorded renders no standing chip at all, its status chip saying it without the doubt. The closing time is tinted by `closingUrgency` — **absolute** thresholds (past / ≤2 h / ≤24 h), deliberately unlike the relative staleness rule beside it: staleness asks "is this reading still good?", which depends on the time left, while urgency asks "must I deal with it now?", and an hour is an hour. Its wording follows the *clock*, not the status: a `watching` lot an hour past its close reads "closed", because it plainly does not still close in the future. A recorded bid **always** stamps `checkedAt` — including an unchanged one via *Bid unchanged*, since "still at 40" is the observation being asked for — while editing anything else on the lot leaves it alone, or a three-day-old reading would look current after a title fix. The last platform is remembered **per seller and in the database** (`Contact.defaultAuctionPlatformId`, a self-FK, `SetNull`), not as one value and not in `localStorage`: where you bid follows from who you buy from, so a single "last platform" would be wrong for every seller but the one just used, and the memory has to survive a change of device. It is deliberately **not** the offers screen's remembered platform — an auction platform is not a selling platform. It is *remembered, not configured*: nothing in the contact form writes it, `rememberSellerPlatform` does, from `createAuctionLot`/`createAuctionSale` — server-side, because a seller and a platform typed in by name only become contacts once the server has resolved them, which is where both ids first exist. Its `updateMany` guard needs the explicit **null branch** (`OR: [{ id: null }, { not: id }]`): `<> 'x'` is NULL for a NULL column, so a seller who has never been tracked matches no inequality. Pre-filling it remounts the picker (`key`), because `PurchaseContactSelect` seeds its own state on mount, it is adjusted **during render** rather than in an effect (the value arrives with a query), and a platform the collector has touched is never overwritten. The `sales/open` endpoint therefore takes `platformId` as **optional** — the pre-fill must be answerable before a platform exists, or it would deadlock the very field it feeds. A lot carries **three** money fields that are constantly confused and must not be merged: `currentBid` is an observation of the auction (what it stands at, whoever is winning), `myBid` is a commitment the collector made to the platform (a proxy/maximum bid), and `maxBid` is a private valuation (the ceiling). Only the first stamps `checkedAt` — it is the only one that dates an observation. **Leading / outbid is derived** (`bidStanding`, `myBid >= currentBid`, a tie going to the bid already placed), never stored: a flag would be a fourth thing to keep current and would be wrong the moment the price moved. *Bid my ceiling* uses `maxBidWithin` — the **inverse of `allIn`**, `(ceiling − fixed − shipping) / (1 + pct/100)`, rounded **down** — because a ceiling is an all-in figure while a bid box takes a hammer price, so bidding the ceiling itself overshoots by exactly the fees. It is one of **three quick fills** (#370/#371) that place a figure the row already knows into a field beside it: catalogue value → ceiling, catalogue value → *Mine*, ceiling → *Mine*. Anything landing in a **bid** goes through `maxBidWithin` (`catalogBidRoom` is the catalogue one, computed server-side beside `bidRoom`), because catalogue value is an all-in figure too — it is what `headroom` subtracts `allIn` from; only the **ceiling** takes its source unchanged, being itself an all-in valuation. None of them writes `currentBid`: that is an observation, and filling it with a figure nobody saw would stamp `checkedAt` with a reading that never happened and make `bidStanding` say the collector is leading against their own arithmetic. Each is offered **twice** — a `⋮` entry and a hover control — built from one `QuickFill` descriptor (`value === null` *is* unavailable, `hint` says why), so the two surfaces cannot disagree. The control is **the source column's heading, abbreviated** (`CEIL`, `CAT`), set in the grid's own heading style: it names the *source*, never the target, so the *Mine* column can offer two of them unexplained. Arrows were tried first and cannot do this — an arrow shows direction, and all three of these move a figure leftward into a neighbouring column, so up and down were left naming a source they had no way to name. They live in **gutter tracks of their own** (`quickFillSlot`, explicitly placed like `GRID_RULE` so everything else keeps auto-flowing) and **centred across both rows** of the column they write: a quick fill sets the whole column, and putting each control in the cell it happens to write scattered them over two different rows for no visible reason. A column offering two **stacks** them — side by side they read as one two-word label on the figure beside them. The gutter goes **after** its column, not before: amounts are right-aligned, so the empty part of a track is on its left, and a gutter placed ahead of a column ends up one gap from the *previous* column's figure and several from the one it fills. Track width is fixed unhovered, or revealing a control would shunt a figure out of its column. A quick fill goes through the same pending override an inline edit does. A **row click** opens the lot's sale with `?lot=<id>` (#374). The sale screen scrolls that card into view and flashes it once with `just-added-flash`, but the flash is only the *arrival*: the mark itself is an accent **ring** (a `box-shadow`, so the card does not resize) plus a labelled strip with a ✕, and it **persists** — a flash is over before the eye has finished reading the parcel's other lots, leaving the collector to find the row again. The URL is the whole state; clearing deletes that one param and `replace`s, so undoing a highlight is not a step to walk back through. Clicks originating in `a, button, input, select, textarea, [role="button"]` are left alone — the click-to-edit cells present as the last of those — as is a click that ends a text selection, and a modified click opens a tab. It is off (`linkToSale`) on the sale's own screen, where the click would land on the page already being read. `AuctionLot.startingPrice` is a **record, never a figure**: it is what the lot opened at, so it is displayed muted in the bid slot while no bid exists (`from 20 PLN`) and enters no arithmetic at all — a lot nobody has bid on costs nothing whatever it opens at. The row renders the three as a **3 × 2 grid** (Auction / Mine / Ceiling × bid / all-in): each figure exists twice, and columns are what make them comparable. The catalogue figures sit beside them **as a second section, behind a rule and under their own row labels** (`value` / `headroom`), because the worth side does not share the cost side's vocabulary: `all-in` there names a figure recomputed with fees, while the worth side's second line is a *subtraction* between the two. Labelling both `all-in` promised an operation the last column does not perform. Anything else answering "what is this worth" — a recommended price — is another column in that section, never a fifth cost column. Exactly one cell of each pair is **stored** — the two bids are hammer prices, a ceiling is an all-in valuation — and the other is computed from it and shown muted, which is why the ceiling's *bid* cell is `bidRoom`, the very figure *Bid my ceiling* places. But the collector's own two columns, *Mine* and *Ceiling*, are **edited from either side**: the two cells are one fact stated two ways, and which one happens to be stored is an implementation detail. A figure typed into the muted half is converted back and the stored half is what is written, through **two helpers that exist only because rounding direction is the whole question**: `bidCosting` for an all-in typed into *Mine* (the inverse rounded to the **nearest** cent, so the total reads back as the one that was typed; a target the fees alone swallow clears the column rather than inventing a bid) and `ceilingAllowing` for a bid typed into *Ceiling* (`allIn` rounded **up**, the smallest ceiling that still lets that bid be placed, with an epsilon so a whole-cent cost is not pushed to the next one). Neither is `maxBidWithin`/`allIn`: those answer a *cap* question and round down, which is right for `bidRoom` and *Bid my ceiling* and wrong here — on a 20% + 1.50 house a stated all-in of 200 came back as 199.99, which reads as arithmetic going wrong rather than as a bid being chosen. Nothing in the two-sided conversion is a limit, so nearest/up is safe: a placed bid is a *record* of a commitment, and whether it outruns what the lot is worth is what the ceiling and `myBidOverCeiling` are for. **Auction stays one-way**: its bid is an observation, and there is nothing to state twice about a price someone else set. This is why the row carries `premiumPercent`/`premiumFixed`: the derived half is computed in the row from the figure **as displayed**, through the pure module, so one pending override covers both cells of a column instead of the two disagreeing while a refetch is in flight. The two bid cells are tinted **together** by `standing` (green/red), because they are one comparison; the collector's own cells go **amber** when `myBidOverCeiling` — their commitment costing more than their ceiling is a different fact from the market outrunning them, and the only one they can take back. A row's **all-in excludes shipping** (premium only): shipping belongs to the parcel and the sale's total adds it once, so charging it per row would double it the moment two lots are open with one seller. And the list's **reading order** is decided by the status chip — `watching` soonest-closing first, a terminal status most-recent first, no chip at all newest-tracked first, because the two orders contradict each other in a mixed list.
- **Duplicate grouping on the Copies list** (#372) collapses the list to one row per *bag of interchangeable copies*, and **multi-select** (#373) is the escape hatch for the compositions it cannot express. The key's fixed part is `stamp × condition` — Colnect refuses a second offer for the same stamp in the same condition, so a group mixing conditions would produce an offer that cannot be posted — with **format** and **certificate** as two independently joinable axes (`CopyGroupAxes`, remembered per collection). Both on, the key is exactly the one `valuateItemRows` is computed on, so every group has one unambiguous per-copy figure; where members disagree on an axis left at *any* the row is marked **mixed**, which with the axis on cannot occur by construction. The pure half — key encode/decode, `mixedAxes`, `outlierCopyIds` — is `src/lib/copy-groups.ts` (unit-tested); the read is `listItemDuplicateGroups` in `items.ts`, beside `listItemsPaginated` so both narrow through the same private `buildItemWhere`. Grouping is **server-side** because the list is offset-paginated: a client-side grouping would split a group at a page boundary and report two half-counts. Groups order **count descending** then `stampId` (total, so pagination cannot repeat or skip one), which is why the sort control is *hidden* rather than left offering an order it cannot honour. Grouping is **not filtering** — the sidebar filters decide which copies you look at, the toggles what counts as the same item, and both compose — but it does force the composition picker's eligibility (**for sale, delivered, unsold**), so the delivery-state and *Include sold* controls grey out and the holdings bar narrows with it. **Expanding a group needs no endpoint of its own**: a key *is* a filter combination, so members come back through the ordinary items query with the panel's filters plus the key (`groupMemberFilters`) — which is what the `"none"` certificate sentinel exists for, null being a value exactly as `"single"` is for format. The group row's own action is a **selection** shortcut, not a second listing flow (#398): its members carry the list's ordinary checkboxes and the row's own checkbox — a `⋮` entry until #422 moved it into the select gutter — ticks them, so what happens to a bag of copies is decided once, in #373's bulk bar. There was a dedicated *List all as one offer* dialog first, and two ways to compose an offer out of the same rows is one more than the screen can explain — the packaging question it answered is already `AddToOfferDialog`'s *Add as* (`createOffer`'s `seedPerCopy`: one single-copy set each rather than one set holding everything). **Outliers** (differing from the group's *most common* value on an *any* axis, never a fixed "format ≠ single" test) keep their marking on the member rows and are **left out of** the quick select-all, but tick individually like any other copy. The shortcut is **not** conditioned on the group being open: it expands the row and walks the member pages to the end before ticking (a partly loaded group would tick a subset and call it "all"), holding the request as a nonce whose *served* value is a **ref** — bookkeeping about a request is not something the row renders, and a second state would be a `setState` inside the effect that discharges it. Because a grouped panel runs no flat query, `CopySelection` carries the **items**, not ids (`onToggle(item)`, `onSetMany(items, selected)`) and the panel's selection is a `Map<id, ItemListItem>`: there is no page here to resolve a member's id against. Which copies are still free **on a platform** is deliberately not re-asked in that dialog — the list's own *Not offered on…* filter (#259) is the entry point the feature exists for, and it also pre-fills the platform into the form. `AddToOfferDialog` takes `items: ItemListItem[]` throughout; `ComposeTarget*.containsItemIds` replaced the old boolean, so an offer holding *some* of a selection keeps those copies out of the add and says so, and only one holding *every* copy is disabled. Its packaging choice is **one control, not two submit buttons** (unlike `ComposeSetDialog`), because it governs the stacked create form too, whose submit lives inside the offer form. A checkbox beside an `InventoryItemRow` sits in the shared `SELECT_STRIP` (`inventory-copy-list.tsx`) — a full-height `<label>` gutter with the box centred in it — on every surface that has one: a copy row is four lines tall, so a top-aligned box reads as belonging to the first line, and a 13-pixel target is poor for a list one works through by ticking. The sale-line picker keeps its own shape, where the whole row toggles.
- The Copies list's **grouping is a mode, not a flag** (#421, #424): `none | duplicates | location | ref | issue`, one persisted per-collection preference, because they are readings of one list and exactly one can be in effect. **Filing groups** collapse the list by *where a copy is*, and differ from #372's duplicate groups on every axis that matters. They force **no eligibility** — "where is it?" is a fair question about a sold copy still on the shelf, so `Include sold` / `Include no longer held` stay live and the holdings bar is not re-narrowed. A location groups **exactly**, never rolled up: a nested location is its own row stating its full path, since a roll-up would report one copy under every ancestor and the location filter's own subtree scope (#385) is already how one asks for a branch. A ref only means anything inside its location, hence `(locationId, locationRef)` and not `locationRef` alone. The reading order is location path then #330's `compareLocationRef`, neither of which SQL can express, so `listItemLocationGroups` reads the groups **whole and pages them in memory** — bounded by the collection's locations × refs in use, not by its copies, and a *total* order, which is what makes paging over it neither repeat nor skip a group. Null and `""` refs are folded into one "no ref" group after the `groupBy`, which the database cannot do for us. Two sentinels carry the buckets an absent filter cannot express — `NO_LOCATION` / `NO_LOCATION_REF` (`location-groups.ts`, pure, so a client row can name them without importing a server module), the `"single"`/`"none"` pattern again — and a group addresses its own members through the **ordinary items query** with `locationExact: true`, so no per-group endpoint exists. A filing row is deliberately **thin** next to a duplicate row: a group is a *place*, so it states the place and the count, and what the copies are is what the member rows answer. **Issue groups** (#424) are the same shape a third time — thin row, no eligibility forced, read whole and paged in memory, members addressed through the ordinary items query — and differ in the two places the subject differs. The reading order is the **Issues list's own** (year, then `primaryCatalogSortKey`, then name; #181), because a collector scanning copies by series is reading the list they browse the catalogue in and two orders for one subject is two things to learn; the issue-less bucket sorts last, being the absence of the subject rather than a thin edge of it. And the issue lives on the *stamp*, which `groupBy` cannot reach, so the filtered set is scanned and counted in memory over a two-field select — `listItemYearFacets`'s own shape, the year being on the stamp for the same reason. Membership is many-to-many but a copy is counted under **one** issue, its stamp's first, so the groups partition the list and their counts add up to it; `FIRST_ISSUE_MEMBERSHIP` (`orderBy: { issueId: 'asc' }, take: 1`) is what makes that *one* answer — an unordered `take: 1` let the row, the grouping and the title reads each name a different issue for one copy, which is a latent bug this fixed rather than a new rule. Counting on the first membership while reading members back through the ordinary `issueId` filter (which matches **any**) is #172's existing pair, deliberately not a third rule: they differ only for a stamp filed in two issues, and an issue filter meaning "and no earlier one" would make the sidebar's own filter answer a question nobody asks of it.
- Every **grouped row shares one shell** (`inventory/copy-group-shell.tsx`, #422): the expand arrow, the select-all box, the member list and the page-walking `useGroupMembers`. The arrow is **vertically centred** (a group row is four lines tall, and one pinned to the top reads as belonging to the first line), and quick select-all (#398) is a **checkbox in the same `SELECT_STRIP` gutter the member copies use** — one click, in the column the eye is already in — rather than a `⋮` entry, which was two clicks and a menu to read for the thing the row is most used for. The duplicate row's `⋮` therefore disappeared entirely: it held nothing else. `allSelected` stays **derived from the copies actually ticked**, never from the pending request, so a box can never claim "all" before the page walk that makes it true has finished.
- A **catalog-number chip copies its number on click** (#420, `shared/catalog-number-chip.tsx`), everywhere one is drawn — stamp/issue/copy rows, the pickers, the quick-price dialog. What it copies is narrower than what it reads: the **area prefix stays and the vendor abbreviation goes** (`Mi·PL 200` → `PL 200`), because the prefix is part of the number's identity (#66/#377) while the catalogue is context the collector already has in the field they are pasting into. The rule is pure (`catalogChipCopyValue` from the parts, `catalogChipCopyValueFromLabel` where a surface only carries a formatted label — the pickers' `catalogLabels`, an issue's declared range; a label whose head is not a short letter run is left whole, since eating a multi-word number like `Ark. 103` is the worse mistake). Confirmation **recolours the chip** instead of adding a ✓: these sit in wrapping rows of four or five and a glyph appearing would reflow the line under them. It renders a `<button>`, which is also what keeps it safe inside a click-through row (#374).
- A **hierarchical filter's scope** is the collector's (#385), not a fixed rule: `useSubtreeScope(axis)` (`shared/subtree-scope.tsx`) is one persisted flag per axis — `area`, `location` — defaulting to *include descendants*, because picking "Poland" and being shown only what sits directly on that node is not what browsing a tree means. It is **global**, not per-collection like the area/year *selection* (`use-collection-filter-store`): it is a way of reading a tree, and it sits beside the equally-global collapsed-set key. The two axes resolve in different places and that is inherent: an area selection is expanded **client-side** through the shared `resolveAreaFilterIds` (never an inline `getDescendantIds` + self, which is how six screens came to each own a copy of the rule), while a location's subtree is resolved **server-side** in `resolveLocationScope` — every location-filtering read goes through it, so the list, its holdings bar and its year facets cannot disagree about what "in Klaser A" means. `SubtreeScopeToggle` renders **only when the selected node has children**: on a leaf both states select the same rows, and a control that cannot change anything is noise on a screen already dense with filters. The area sidebar's in-scope shading follows the toggle, so the tree marks the set the list is actually showing.
- A copy's row menu links to **its purchase** (#387) via `ItemListItem.purchase` (`{ id, label }`, the supplier + date pair the purchases list leads with, resolved in `ITEM_LIST_SELECT`'s lot join). The entry is **hidden, not disabled**, when there is none — a hand-added copy was never bought through an order and nothing on the row promises otherwise, which is #273's stated exception. It lands on `purchases/<id>?lot=<lotId>`, and the purchase detail gives that lot #374's arrival treatment: seeded into `useCardExpansion`, scrolled to `block: "center"` (its own header is sticky), and marked with a **persisting** ring + dismissable strip rather than only the one-shot `just-added-flash` — an order can hold a dozen lots and a flash is over before the eye has finished reading them. The `RowAction.hint` doubles here as the *object* of an enabled navigation, not only as a disabled entry's reason.
- **Attaching an existing copy to a lot** (#388, `attachItemsToLot`) is the third verb beside `intakeStamps` (which creates copies) and `removeLotItem` (which deletes them): a copy entered by hand before the receipt was recorded, or filed under the wrong purchase. Only `lotId` changes — delivery state, dispositions, location, `itemNo` and photos all stay, because a copy already in hand does not return to `ordered` on account of a late cost record. **Both ends must be open**, and for one reason: a cost basis is frozen at close (ADR-0009 §3), so a closed *target* would not include the copy in the split it has already made, and a closed *source* has already distributed its pool over a set this would silently shrink, under-costing the copies that stayed — reopening it is the way through, and the refusal says so. A copy on another **open** lot is allowed but never moved silently: `allowRelink` is a parameter the dialog sets only after the collector has confirmed a warning **naming** the orders being left (a count cannot tell them whether this is the mistake they are correcting). Copies already on the target lot are a no-op, not an error. Refusals are **collected, not thrown** — one copy stuck on a closed lot is no reason to abandon the other nineteen. Eligibility is one filter, `attachableToLotId`, expressed as two `OR` branches rather than a `lotId: { not: … }` (an inequality is not a reliable way to say "or no lot at all" about a nullable column) and pushed into `buildItemWhere`'s `and` so it cannot collide with the search's own `OR`.
- Password managers overlay their fill icon on short **identifier** inputs — a catalog prefix, an order number, a lot number, a location ref — and `autoComplete="off"` alone does not stop them (#262, #389). Spread the shared `NO_AUTOFILL` (`shared/no-autofill.ts`) onto such a field; it carries the per-vendor opt-outs (`data-lpignore`, `data-1p-ignore`, `data-bwignore`) beside `autoComplete`, because each extension only honours its own. Do not re-inline the four attributes: they were copy-pasted at eight sites before this and a new field was fixed only once someone reported it.
- A list toolbar's toggle chip is the shared `FilterChip` (`shared/filter-chip.tsx`) — the offers status filter (#332) and the sales one (#392) are one control, and `FILTER_CONTROL_STYLE` is the box every toolbar select shares with it so a mixed row lines up. A **remembered** filter follows #325's rule exactly: the URL wins where it names a value (a shared link keeps meaning what it meant), the stored per-collection value fills in otherwise, and every change writes both — so clearing the filter clears the memory of it. The sales status filter carries **no counts**: there is no sales facet endpoint, and a chip promising a number it cannot compute is worse than a bare one.
- **Stepping from one offer to the next** (#429) is the filtered list carried into the detail screen: the offer row appends `offerListContextQuery(filters)` to the link it opens (`offers/list-context.ts`, pure and unit-tested), the detail page parses it back and renders `‹ Previous · 3 of 12 · Next ›` beside its **← Offers** link, which now points at the list *as it was*. It travels in the **URL, not off #325's remembered filters**, for two reasons: an offer is opened from other screens too (the copies popup, a short link, a bookmark), where a walk through a list nobody is looking at would be an invention — hence `from=list` as an explicit marker, since a context with *no* filters is a legitimate walk over the whole list and is otherwise indistinguishable from a plain deep link — and a link to "the third preparing offer on Colnect" then still means that when it is reopened. The remembered **show-closed** toggle (#245) is part of what the list was showing, so the walk carries it (`closed=1`) even though the list keeps it out of its own URL; the way *back* deliberately drops it again, the list reading its own stored value. Server-side it is `offerListNeighbours` — the ids alone, over the same `where` and the same `OFFER_LIST_ORDER_BY` the list reads, which is where the order got its `id` tiebreak: offers created in one transaction share a `createdAt`, and an unstable order both repeats a row across pages and skips its neighbour. Position falls out of the same array, so the indicator is free. The query is asked **once per offer and then frozen** (`staleTime: Infinity`, and a key outside `offerKeys.all` so `invalidateAll` cannot reach it): the use case is finishing an offer — which usually moves it *out* of the filter that was showing it — and stepping on, so an answer that refreshed itself would take the walk away at the moment it is needed. An offer not in the filtered set at all reports `position: null` and the strip is absent; the two ends are disabled rather than hidden (#273), the position beside them saying which end.
- A **sold** copy carries its own chip on the copies list (#393), tinted `success` rather than the disposal chip's error tint — it left the collection the way it was meant to, so the chip states an outcome instead of raising an alarm. It can only ever appear under *Include sold* (#207), which is exactly the mixed view it exists for. `ItemListItem.sold` comes from `_count.saleLineItems` on `ITEM_LIST_SELECT` — the very relation `excludeSold` filters on, so the chip and the filter cannot disagree. Soldness stays outside `isHeld` (#394), as it always has.
- Quick-sell (#225) is reachable from the offers list **and** from an offer's own detail screen (#390). `SellOfferFlowDialog` takes a structural `SellableOfferSubject` (id, name, label, platform, price, currency) rather than `OfferListItem`, so `OfferDetail` satisfies it and there is one flow rather than two that drift; the precondition is the same at both ends — non-terminal, ≥1 set. The detail page computes `today` at request time exactly as the list page does, so a sale started from either place defaults to the same date.

- In-location refs (`A234`) are ordered by `compareLocationRef` (`src/lib/location-ref.ts`): prefix first, then the trailing number, separators ignored, blanks last. Use it anywhere refs are sorted — a plain numeric collator disagrees as soon as the separator varies.

## Testing Direction

- `pnpm lint` — run before finishing any task that touches source files.
- `pnpm typecheck` — TypeScript verification.
- `pnpm test:unit` — pure logic only, no Prisma imports.
- `pnpm test:integration` — requires real database via `docker-compose.e2e.yml`. Run before committing schema or domain logic changes.
- Write migration SQL manually. Create directory and `migration.sql` by hand under `prisma/migrations/`. Then `pnpm exec prisma generate`.
- Never run `prisma migrate dev`, `prisma migrate reset`, or `prisma db push` directly. Exception: `pnpm e2e:db:reset` is safe.
- When starting a local dev server for verification, use `pnpm exec next dev --webpack -p 3002` and stop it before finishing.
- Always run the dev server on **webpack** (`next dev --webpack`), never the default Turbopack: Turbopack's dev/HMR leaks memory until the container OOMs (an open, idle browser tab grows the server heap unbounded; webpack plateaus). The `docker-compose.dev.yml` overlay is pinned to `--webpack` for this reason. See issue #161; re-test Turbopack after Next.js upgrades and revert once fixed upstream.
- The user tests the app through Docker Compose. Do not leave dev servers running.

## Before Implementing Features

If a request would require defining product behavior, ask targeted questions first. Good questions are concrete and bounded:

- What is the first workflow we want to support?
- Should catalog numbers be per-standard (Michel, Scott, Fischer) or free-form?
- Should condition follow a standard scale or be free-form?
- Should a collection be shareable with other users?
